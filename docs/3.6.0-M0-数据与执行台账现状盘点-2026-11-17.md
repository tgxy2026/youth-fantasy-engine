## 1. 三模式存储映射（真实写入与确认边界）

| 形态 | 判定 | 写入载体 | 「已确认写入」的证据 | 未确认时的表现 |
| --- | --- | --- | --- | --- |
| 桌面 | `DESKTOP`（`lib/app/desktop.ts`） | 本机数据文件（IPC 交给主进程） | `flushDesktop()` 返回成功；`connected` 来自 `inited`（`desktop.ts:527`） | 状态显示「等待存储」，不允许把内存态当已保存 |
| 便携 | `PORTABLE`（`lib/storage/fileBackend.ts`） | 便携数据文件（File System Access / 本地路径） | `flushPortable()`；`connected` 来自 `inited`（`fileBackend.ts:152`） | 同上 |
| 网页（云端账号） | 其余情形（`components/app/Web.tsx`） | 云端 store 包装（`lib/sync/`），服务端回执 | 服务端保存回执 + `submissionState`（`lib/storage/submissionState.ts` 对 web 返回 `connected: true`） | 写失败必须落到 `lastError`，界面显示「保存出错」而非「已保存」 |

- **归属与串号保护**：`lib/storage/writeOwner.ts:4` 的 `storageWriteContext()` = `[storageContextEpoch, 账号 id]`；`captureStorageWriteOwner(projectId)` 在异步操作开始前捕获，写回前比对。`lib/storage/recordOperation.ts` 的 `beginRecordOperation()` 在项目/存储切换后抛「资料上下文已改变，请回到原项目重新操作」——本轮 H 包界面探针实测触发过该保护。
- **跨窗口**：`lib/db/taskLedger.ts:41` 的 `withTaskLedgerLock` 用 `navigator.locks`（不可用时暂停提交，不降级为无锁写入）。
- **事务能力**：IndexedDB 的 `StoreOps` 单 store 写入是事务性的，但**没有跨 store 原子提交**。项目包导入 = 逐条 `put`，中途失败会留下部分已写入（`importProject` 未包裹整体事务，靠 id 全部换新 + 重复导入幂等来兜）。⇒ 3.6.0 的 E 包**不能假设**「整章多步骤原子完成」。
- **本机专属**：`lib/sync/syncCore.ts` 的 `LOCAL_ONLY_STORES` = `backups / backupPayloads / revisionPayloads / taskHeads / taskUnits`，这些永不进云端、也不进普通项目包（`stripLocalTaskStores`）。

**关键约束（A1 实施前必须遵守）**：

1. `BundleLike = Omit<ProjectBundle, 'app'|'version'|'exportedAt'>`（`backup/shards.ts:166`）。给 `ProjectBundle` 加字段后，**必须同时在 `splitBundle`/`mergeShards` 显式落片**，否则编译通过但备份里静默丢字段。
2. 导入的 id 重映射是**白名单式**的：`remapSettingValue` 只认 `worldSubActive::` / `inspirationBox` / `chapterSets` / `exportSchemes`（`projects.ts:51-85`），其余 settings 原样搬。⇒ 存进 settings 的新记录**必须显式加一条重映射分支**，否则导入后内部引用全部悬空。
3. 无法映射的引用统一标 `missing:<id>`（章节/大纲/画布已有先例），不静默丢弃。
4. 导出会**过滤敏感键**（`isSensitiveSettingKey`，二级探测 `apiKey/secret/token/password`）⇒ 成果里不得出现这些字段名，否则会被当成密钥剥掉。
5. `LOCAL_ONLY_META_KEY_PREFIXES`（`sensitiveMeta.ts:42`）是「本机专属」的唯一判据。成果要跨设备就不能加前缀；要本机专属就必须加，并接受备份里也没有。

## 3. 执行台账（`taskHeads` / `taskUnits`）

- 结构：`lib/tasks/unitLedger.ts` 的 `TaskHead`（id/kind/projectId/**storageKey**/inputFingerprint/configFingerprint/protocolVersion/modelTag/totalUnits/status/**ownerId**/**generation**/label/时间）与 `TaskUnit`（id=`${taskId}::u${index}`/unitKey/status/attempts/**bytes**/result/failure）。
- 状态：单元 `pending|running|succeeded|failed|cancelled|interrupted`；任务 `pending|running|interrupted|done`。**`interrupted` 不是失败**（进程中途退出、产物从未落盘）。
- 配额（`unitLedger.ts:81-84`）：每项目 **5** 个任务、单任务 **20 MiB**、项目合计 **50 MiB**；按序列化后的真实字节计。
- 协议版本 `TASK_PROTOCOL_VERSION = 1`；改拆分/结果形状必须递增，旧单元键随之失效。
- 落盘：`lib/db/taskLedger.ts` —— `writeStrict` 走 store + `assertCurrent`；`claimTaskLocked` 递增 `generation`，旧执行者写入一律拒绝。
- 删除项目时级联清理（`projects.ts:231-237`），避免孤儿占配额。
- **不随包 / 不同步**：`LOCAL_ONLY_STORES` 已包含它们。

⇒ 3.6.0 的结论：**执行台账不是作者成果**。成果必须是独立记录（显式"保存为成果"），并且它的成功以「成果记录落库并读回」为准，不能拿任务 `succeeded` 冒充。

## 4. 章节保存链路与失败路径现状（E 包病灶，代码事实）

`lib/outline/autoContinue.ts` 的逐章顺序：

```
标题（suggestTitle，预算不足 ⇒ 占位「未命名章节」）
  → 摘要（aiChapterSummary，失败 .catch(() => '') 回退空串）
    → createChapterAfter(...) 一次 upsert 正文 + 摘要（:426-452）
      → onChapterSaved 回调
        → extractAndCommitSettings（实体抽取 → 登记表 → 分类 → 补登）
```

已确认的缺陷（M0 只记录，不在本文件修复）：

| 编号 | 位置 | 现状 | 影响 | 3.6.0 首期处理 |
| --- | --- | --- | --- | --- |
| E-a | `:504-505`（原） | `await loadRegistry().catch(() => null)` 后 `if (!reg) return { created: 0, failed: [] }` | **读取失败被当成「没有可补登的」**，作者看到「新增 0 条」，实际是登记表没读到 | **已修**：区分 `registry-unavailable`，返回 `state: 'failed'` + errors |
| E-b | `:515 / :524 / :548`（原） | `commitEntities(...).catch(() => empty)` 三处 | 写入异常被吞成空结果，`errors` 里也没有痕迹 | **已修**：统一走 `commitSafe()`，异常转成 failed 清单 + `commit-failed` |
| E-c | `:535`（原） | `...(r.failed.length ? [] : [])` 恒为空数组 | 新增失败清单没有进 `errors`（无效表达式，属实现错误） | **已修**：`reportOf()` 统一把失败清单折进 errors |
| E-d | `:950` | 摘要失败 `catch(() => '')` | 作者无法区分「摘要生成失败」与「本来就没写摘要」；且摘要在正文保存**之前**生成，失败后正文仍会带着空摘要落库 | 未修（需与 A 的回执契约一起做） |
| E-e | `createChapterAfter` 内 `db.saveChapter` upsert | 单 store 写入，无跨步骤回执 | 正文写入成功但后续补登失败时，界面没有「正文已保存、整理待恢复」的分步状态 | 未修（E 包主体，依赖 A 契约） |

**另外发现并已修**：`applySettingUpdates()` 里同样的 `loadRegistry().catch(() => null)` 会把「读不到登记表」当成「没有变化」（沿用 `run.state`）。现在返回 `state: 'failed'`，由调用方记为 `update-failed`。

**首期实现（2026-11-17）**：`extractAndCommitSettings` 返回 `SettingsCommitResult`（保留 `created/failed/errors`，新增 `state` + `reasons`），状态由导出的纯函数 `settingsCommitState()` 唯一推导；三处调用方按状态措辞或记日志（连写日志、改写提示、优化工单）。验证：`requestLedger` 53/53（新增 ⑧ 段 17 条）、`evidenceGuard` 15/15（一条接线断言随实现改字面，负向条件未放宽）。

⇒ E 包要做的第一件事是把 `{created, failed, errors}` 换成**有状态的结果**（`skipped / failed / partial / done` + 原因码），并审计全部调用方（改写、章后整理、优化工单）。

## 5. 统一结果状态表（3.6.0 全线共用）

| 状态 | 含义 | 允许的 UI 措辞 | 可重试 | 能否当"无问题" |
| --- | --- | --- | --- | --- |
| `pending` | 已登记、未开始 | 待处理 | — | 否 |
| `running` | 有执行权且未结束 | 进行中 | — | 否 |
| `done` | 全部单元成功 | 已完成 | — | 是（仅限本次范围） |
| `partial` | 部分单元成功 | 部分完成（N/M） | 只重试失败单元 | 否 |
| `failed` | 无产物且有原因 | 失败：<原因码> | 作者手动 | 否 |
| `skipped` | 前置不满足（上下文为空、正文过短、预算耗尽） | 已跳过：<原因> | 补条件后重跑 | **否** |
| `cancelled` | 作者取消 | 已取消 | 可重跑 | 否 |
| `stale` | 输入指纹已变 | 内容已变更，需重新生成 | 重新生成 | 否 |

硬规则：`failed`/`cancelled`/`skipped` 不得渲染成「通过 / 无问题 / 新增 0 条」；`stale` 结果**只读不可应用**（F 包候选同此）。

## 6. 作者成果记录契约草案（A 包核心）

### 6.1 落点

`settingsKV`，键 `${projectId}::artefacts`，值：

```ts
interface ArtefactStore {
  formatVersion: 1
  items: ArtefactRecord[]
}
interface ArtefactRecord {
  id: string                 // 稳定 id（uid），导入时换新并记映射
  kind: 'analysis' | 'reference' | 'review' | 'candidate'
  projectId: string
  // 来源（用于过期判定；不存原文）
  source: {
    tabId?: string
    chapterId?: string
    rowId?: string
    cardId?: string
    range?: [number, number]  // UTF-16 半开区间，按原始字符串计位
    quote?: string            // 短引，≤200 字符
    fingerprint: string       // 强摘要 + 长度（见 15.2）
  }
  // 依赖清单（本次实际读取的内容，不记项目全部内容）
  deps: { kind: 'chapter'|'setting'|'outline'|'reference'|'anchor'; id: string; fingerprint: string }[]
  state: 'draft' | 'kept' | 'excluded'
  stale?: { at: number; reason: 'source-changed'|'dep-changed'|'version-unknown' }
  payload: unknown           // 分析卡 / 参考卡 / 审读摘要 / 候选；结构由各包定义
  createdAt: number
  updatedAt: number
}
```

### 6.2 容量与保留

- 单项目 `artefacts` 值上限 **16 MiB**（序列化后 UTF-8 字节），单条 **256 KiB**；超限拒绝写入并提示清理，**不静默淘汰**。
- 列表默认按 `updatedAt` 倒序；「已排除」保留但可批量清理，清理前显示条数与字节。
- 导出/备份的字节开销计入现有备份体积提示，不新增开关。

### 6.3 版本、迁移与降级

- `formatVersion: 1` 独立于 `ProjectBundle.version`（保持 3）。理由：旧客户端读到未知 settings 键只会原样保存，不会失败；把 bundle 升到 4 反而会让旧客户端直接拒绝整包。
- 读到更高 `formatVersion` ⇒ 只读展示 + 提示「来自更新版本」，不写回。
- 缺失该键 ⇒ 空成果（不是错误），UI 不显示空区块。
- 损坏（JSON 解析失败 / items 非数组）⇒ 保留原值、标不可读、**禁止覆盖写**（与 `loadAtlasSchema` 的 `error` 口径一致）。

### 6.4 导入时的 id 重映射（必须新增）

在 `importProject` 里对该键单独处理（`remapSettingValue` 不认识它）：

- `source.chapterId` → `map`；`rowId` → `rowIdMap`；`cardId` → `cardIdMap`；卷台账 `tabId` → `volMap`；
- 映射不到 ⇒ 保留 `missing:<旧id>`，并把 `state` 降为 `draft`、`stale.reason='version-unknown'`，**不删除记录**；
- 记录 `id` 一律换新（避免跨项目 id 冲突）。

### 6.5 与执行台账、正式数据的边界

| 类别 | 落点 | 谁写 | 进入项目包 |
| --- | --- | --- | --- |
| 执行台账 | `taskHeads` / `taskUnits` | 任务编排 | **否**（本地专属） |
| 作者成果 | `settingsKV::artefacts` | 只有作者点「保存为成果」 | 是 |
| 正式数据 | `chapters` / `tableRows` / `cardRecords` / `formData` | 作者确认后按目标写入 | 是 |

任务成功 ≠ 成果已保存；成果保存以「写入并读回」为准。

## 8. 待确认决策（实施前需主人拍板）

1. **成果落点**：`settingsKV` 单键（本文件建议）vs 新 ObjectStore。前者零迁移、五路径已通；后者结构更干净但需 IDB 升级 + 改五处路径。
2. **是否需要「本机专属」**：成果默认随项目包与云同步走；若希望某些成果（如中间分析草稿）只留本机，需加 `LOCAL_ONLY_META_KEY_PREFIXES` 前缀。
3. **容量上限**：16 MiB / 项目、256 KiB / 条是否合适（参照：自动备份 30 份、单项目图片上限见 `atlas/quota.ts`）。
4. **E 包返回契约变更**：`{created, failed, errors}` → 有状态结果会影响改写、章后整理、优化工单三处调用方，是否允许在本版一并改签名（推荐允许，否则又要长期兼容两套）。
5. **D 包新章绑定**：是否接受「先按 taskId + 临时稿指纹绑定，`createChapterAfter` 返回真实 chapterId 后再确认」的两段式（可行但需要新增草稿 id 通道）。
