# 2.2.0 三功能优先级与依赖分析

> 配套文档：
> - `docs/2.2.0-AI伴写与引用高亮方案.md`（功能 A）
> - `docs/一键拆书-方案规划.md` / `docs/一键拆书-详细设计.md`（功能 B）
> - `docs/2.2.0-全自动AI小说创作工作流方案.md`（功能 C）
>
> 本文档回答一个问题：**这三个功能谁先做、谁后做，后做的能否吃到前者的红利？**
> 状态：决策建议稿（2026-09-17）。未写实现代码。

---

## 1. 结论

**推荐顺序：① 伴写 → ② 拆书（通用管线层）→ ③ 工作流 MVP → ② 拆书（抽取本体）**

一句话理由：**② 和 ③ 之间存在真实的强依赖（共用同一套"AI 草稿 → 审阅 → 落库"管线），而 ① 与两者零耦合且体量最小。**

---

## 2. 依赖矩阵（A=伴写 / B=拆书 / C=工作流）

| 依赖方向 | 是否成立 | 说明 |
|---|---|---|
| **B → C（拆书让工作流更容易）** | ✅ **强依赖（核心结论）** | 见 §3，三项共享件几乎完全重合 |
| C → B | ❌ 反向无效 | C 是消费设定，B 是产出设定，C 的产物无法帮 B |
| A → B / A → C | ⚠️ 极弱（可选增强） | 仅共享 `chat` 调用层；`aiInlineSuggest` 可作 C 逐章草稿的细粒度生成原语，非必需 |
| B → A / C → A | ❌ 无 | A 只依赖编辑器叠层与模型通道 |
| A 占用 B/C 资源 | ❌ 无 | A 改 `NovelEditor`，B/C 改 `lib/`，文件不交叉 |

**结论：唯一存在实质依赖关系的，是 B → C 这一对。** 你问的"先开发 B 是否让 A 更容易"——严格说不是 A，而是 **先开发 B 会让 C 明显更容易**。

---

## 3. 为什么 B → C 是强依赖（代码级证据）

C 方案缺的两块是「生成型入口」与「编排器」。核对 `src/` 与 B 的详细设计后，发现 **C 需要的三样通用件，B 的详细设计里已经写好了**：

| 共享件 | B（拆书）中的落点 | C（工作流）中的对应需求 | 复用结论 |
|---|---|---|---|
| **草稿审阅与落库** | `DraftRow` 类型：含 `status:'new'\|'conflict'`、`conflictFields`、`sourceQuotes`、`confidence`；§8 草稿预览 UI | C 的 ①设定奠基 / ②大纲生成两个**人工闸门**，需要"生成 → 预览 → 勾选 → 写库" | 同一套模型，B 建好 C 直接用 |
| **进度状态机 + 中止 + 断点** | `pipeline.ts`（§2.4 状态机 + 进度 + 中止） | C 的 `runWorkflow(seed,{onStage,signal})`：跨阶段、跨章、可中断、可续跑 | 泛化 `pipeline.ts` 即可，C 不必重写 |
| **字段映射表** | `map.ts`：抽取 JSON → 各表行对象（char-main/geography/nations/relations/…） | C 的 Bible 生成：生成 JSON → 各表行对象（方向相反、映射表相同） | **同一张 schema ↔ 目标表映射表，互为镜像** |

此外，C 的 ③ 节点骨架也已存在：`autoContinue.ts` 里的 `ChapterDraft`、`DraftDecision = 'accept'|'rewrite'|'abort'`、`ContinueCallbacks`、`runAutoContinue` —— 正好就是"逐章生成 + 每章人审循环"的现成形状。

### 3.1 反向的代价（为什么不要 C 先做）

若 C 先做，C 会**临时自建**一套草稿审阅器与状态机；等 B 进场时，B 也需要同一套东西 → 要么 B 复用它（那 C 当初就该抽成通用件），要么两边实现分叉后统一重构。**净浪费一轮返工。**

---

## 4. 意外收获：C 的"生成型入口"比预期更省钱

核对代码时发现两个此前未纳入考虑的现成模块，可直接补上 C 的 ① 环节：

| 现有模块 | 真实符号 | 对 C 的价值 |
|---|---|---|
| `src/lib/interview.ts` | `deriveTopics` / `buildInterviewSystem` / `runInterviewTurn` / `filledToText` / `InterviewSpec` | **"由字段表 → 一问一答采访 → 填出草稿文本"** 已经是通用件（已被酒馆 `tavern/interview.ts` 二次复用）。C 的"想法 → Bible"可以是它的特化：把话题从"字段"换成"故事要素" |
| `src/lib/draftMaterial.ts` | `prepareDraftMaterial` / `DraftSource` / `WebVerdict='searched'\|'failed'\|'delegated'\|'off'` | 草稿素材装配（含联网检索与来源标注、可关闭）。C 的设定奠基可直接复用，且天然带"来源可追溯" |

**含义**：C 的"生成型入口"不是从零写，而是 **`interview.ts` 特化 + `aiTasks.ts` 新增 `aiGenerateBible` / `aiGenerateOutline`**。这进一步压低了 C 的成本，也强化了"B 先做"的性价比（等 B 把审阅器与状态机备好，C 就只剩"入口特化 + 编排胶水"）。

---

## 5. 为什么 ① 伴写应该排最前

| 理由 | 说明 |
|---|---|
| **零依赖** | 只依赖 `chat` 与 `NovelEditor` 叠层，不吃 B/C 的任何产出 |
| **风险隔离** | 唯一未知数是"textarea 透明背景 + ghost 叠层渲染 + Tab 键冲突"，且全部落在编辑器组件内，**风险不会传导给 B/C** |
| **验证成本低** | 上述未知数几小时内可实机证伪；结论（叠层可行性/键位）对后续两个功能无影响 |
| **即刻自用价值** | 日常码字立刻受益；B/C 是长周期工程，早期无产出 |
| **文件不交叉** | A 动 `components/NovelEditor.tsx`，B 动 `lib/bookbreak/*`，C 动 `lib/aiWorkflow.ts`，无合并冲突 |

---

## 6. 关键手法：把 B 切成 B1 / B2

直接按"一键拆书"整体开发，会立刻撞上它那 5 个未决开放问题（百万字抽取质量、worldbase/power 单条多要素落点、prompt 列名漂移断言、角色分级判定、geo 建图）。**建议切分，先躲开不确定性**：

| 切片 | 内容 | 定位 |
|---|---|---|
| **B1 通用管线层** | 草稿类型 + 审阅/落库 + 进度状态机 + 字段映射表 + 预览 UI 骨架（**不接真实抽取**，先用假数据跑通） | C 的地基，也是 B 自己的地基。**优先做** |
| **B2 抽取本体** | 切分 `split.ts` / 两遍抽取 `extract.ts` / 对齐 `align.ts` / 校验 `validate.ts` | 体量大、依赖原文质量，**可后置**，且不影响 B1 与 C |

这样 2.2 的路径变成：**A → B1 → C(MVP) → B2**。B2 的五个开放问题可以留到 2.2 中后期实测拍板。

---

## 7. 两种取向下的变体排期

| 若你的目标是… | 推荐顺序 | 说明 |
|---|---|---|
| **日常自用效率优先**（默认可行） | **A → B1 → C → B2** | A 立刻见效，B1 一次投入两处受益，C 省力收尾 |
| **对外较亮眼的成果优先** | **B1 → C(MVP) → A → B2** | C 是"从一句话到成稿"的门面，但需接受 A 延后，且 C 的 MVP 仍要等 B1 |
| ~~C → B~~ | ❌ 不推荐 | 会造成 §3.1 的返工 |

## 8. 风险与开放问题

| # | 项 | 影响 | 处置 |
|---|---|---|---|
| 1 | 伴写 Tab 键与编辑器缩进冲突 | 影响 A | 实机验证优先，方案已列 P0（备选 `→` 采纳） |
| 2 | textarea 背景透明 + 亮/暗主题串色 | 影响 A | 实机验证优先，P0 |
| 3 | B1 用假数据跑通后，接真实抽取时类型不匹配 | 影响 B1→B2 衔接 | B1 阶段严格按 §2 的 `DraftRow`/`ChunkResult` 类型落地，不临时造类型 |
| 4 | C 的"生成型入口"产出质量不足（想法→Bible 太泛） | 影响 C | 复用 `interview.ts` 的多轮采访形态而非一次性生成，提升可控性 |
| 5 | 拆书 5 个开放问题（百万字质量等） | 影响 B2 | 已通过 B1/B2 切分隔离，B2 再拍板 |
