# 3.3.1 · §12 中文标点自动配对：代码侧审查（2026-10-30）

> **这份文件不是 §12 的验收结论。**
> 规划 §12.5 明确要求「真实输入法下的**事件序列日志 + 录屏**，不接受只靠 CDP `insertText` 模拟」。
> 本机没有可用的人工输入法矩阵（搜狗 / 微软拼音 / 微信 / 百度 / 手心），所以这里做的是**能做的那一半**：
> 把现有实现逐条对照 §12.4 的五个彻查方向审一遍，指出还剩哪几处只能靠真实输入法定论，
> 并给出一套**不改产品代码**的取证方法（控制台片段 + 判读脚本）。
>
> 结论只有一句：**§12 仍未完成，但不再是「一行没查」**；剩下的缺口从「不知道查什么」变成「打三组字、导一份日志」。

---

## 一、现有实现（先看清它做了什么）

| 位置 | 行为 |
|---|---|
| `src/lib/editor/punctPair.ts` | 纯函数：左标点补右（`planPunctPair`）、右标点兜底（`planPunctPairFromClose`）、按光标版（`…AtCaret`）、以及「在自己造的那对引号中间再按一次 ⇒ 跳出去」（`closeOrStepOver`） |
| `src/components/editor/NovelEditor.tsx` `onChange` | `ev.isComposing` ⇒ **只 `onContentChange(next)`，不碰 DOM、不改光标**；非组合态才判 `InputEvent.data` |
| 同上 `onCompositionEnd` | 组合结束后按**光标**再判一次（有些输入法不额外发提交 `input`） |
| 光标落点 | 两条路径都 `requestAnimationFrame(() => setSelectionRange(plan.caret))` |

三条边界写在文件头并且确实生效：只认中文左标点（英文引号不碰）、后面已有右标点就不补、只处理「恰好 1 个字符」的输入。

## 二、§12.4 五个方向，逐条对照

| 方向 | 现有代码的实际行为 | 判断 |
|---|---|---|
| **1. 组合态里回写受控 `value`** | 组合态分支只调用 `onContentChange(next)`，而 `next` 就是 `textarea.value` 本身 ⇒ React 比较后**不会重写 DOM**；也没有 `setSelectionRange`。真正会改 DOM 的只有「提交之后」那条路径 | 代码侧**已规避**；「输入法会不会因此被打断」需真实 IME 观测 |
| **2. `compositionend` 后立刻 `setSelectionRange`** | 现在是 `requestAnimationFrame` 里设，比同步设晚一帧；但**没有任何证据**说明这一帧足够输入法收尾 | ⚠️ **未解决**（见风险 A） |
| **3. 是否本来就该「什么都不做」** | 现状是「应用补 + 兜底」两条路径都在 | ⚠️ **无法用代码定论**（见风险 C） |
| **4. 输入法设置差异（中英文标点、全半角、智能引号）** | 判据只认字面字符，不读任何设置；作者用英文标点时 `data` 是 `"`，`CN_PUNCT_PAIRS` 里没有 ⇒ 不插手 | 设计上**不猜意图**，符合规划「应用侧不宜按字符猜意图」 |
| **5. 兼容矩阵** | 无 | ❌ 未做（需要真实输入法） |

## 三、还剩三处风险（按可疑度排序）

### 风险 A：`compositionend` 之后的那一帧，够不够输入法收尾
`onCompositionEnd` 里补完标点后，在 `requestAnimationFrame` 里把光标挪到两个标点之间。
若某个输入法在 `compositionend` 之后**还会再插一次字符**（例如把缓冲里的尾巴补上屏），
它就会落到我们挪动后的光标处 —— 表现和 3.2.1 那个「`““”` 越打越多」的老 bug 同类。
现在的代码有「后面已有右标点就不补 / 在自己那对里就跳出去」两道幂等，但**没有任何一条能证明**在真实输入法下不会出现第三个字符。
**怎么定论**：录一段「`，` + `“`」的事件序列，看 `compositionend` 之后有没有 `input` 落在 `app:setSelectionRange` 之后。

### 风险 B：取消组合后会被补一个右标点
`planPunctPairAtCaret` 只按「光标前是不是中文左标点」判，**不区分这次组合到底提交了内容没有**。
所以：作者打了 `“` → 开始用输入法打字 → 按 Esc 取消（或点击别处），`compositionend` 触发、光标仍停在 `“` 后面
⇒ 会被补上一个 `”`。这不破坏文本，但属于「作者没要求却变了」。
**要不要改**取决于真实输入法是否会在取消时也发 `compositionend`（多数会）。若确认会，最小改法是
`onCompositionStart` 记下 `value`，`onCompositionEnd` 里「值没变就不补」。
**现在不改**：没有证据就动这条链路，容易把已经工作的补全弄坏（3.2.1 就是这么坏的）。

### 风险 C：「应用层该不该补」这个更大的判断
3.2.0 的起因是「微信会补、搜狗不补」。如果实测发现**主流输入法都已自带补全**，
按规划 §12.5 就该**移除兜底与补全两条路径**，只保证「不吞字、不重复、不改写」。
反过来，只要还有一家不补，应用层补就是必要的。
**这不是代码问题，是矩阵问题**：五家 × 三条序列，缺一家就不能下结论。

## 四、取证怎么做（主人这边，约 5 分钟）

1. 打开应用进正文编辑器（任意一章，**用示范项目或临时项目，别用真实稿子**）。
2. F12 打开控制台，整段粘贴并回车：

```js
(() => {
  const ta = document.querySelector('textarea.novel-textarea')
  if (!ta) return '先打开正文编辑器再运行'
  const log = []
  const snap = () => ({
    before: ta.value.slice(Math.max(0, ta.selectionStart - 6), ta.selectionStart),
    after: ta.value.slice(ta.selectionStart, ta.selectionStart + 6),
    caret: ta.selectionStart,
  })
  const push = (type, extra = {}) => log.push({ t: Math.round(performance.now()), type, ...snap(), ...extra })
  for (const type of ['compositionstart', 'compositionupdate', 'compositionend', 'input', 'beforeinput']) {
    ta.addEventListener(type, e => push(type, { data: e.data ?? null, isComposing: e.isComposing ?? null }), true)
  }
  const orig = HTMLTextAreaElement.prototype.setSelectionRange
  HTMLTextAreaElement.prototype.setSelectionRange = function (start, end, dir) {
    if (this === ta) push('app:setSelectionRange', { to: start })
    return orig.call(this, start, end, dir)
  }
  window.__imePunctStop = () => {
    HTMLTextAreaElement.prototype.setSelectionRange = orig
    const text = JSON.stringify(log)
    console.log(text)
    copy(text)
    return `已复制 ${log.length} 条事件到剪贴板`
  }
  return '开始记录。请依次打三组：①「，」再打引号 ②汉字后打引号 ③「《」再打书名，然后运行 __imePunctStop()'
})()
```

3. 按提示打三组字（**用你自己的输入法，别切英文**），再运行 `__imePunctStop()` —— 事件序列已复制到剪贴板。
4. 粘进一个文件（例如 `.workbuddy/tmp/ime-punct-搜狗.json`），然后：

```bash
node scripts/verify/ime-punct-analyze.mjs .workbuddy/tmp/ime-punct-搜狗.json
```

输出会给三条硬判据（组合期间有没有动光标 / 有没有出现 `““` `””` / 组合结束后紧跟的是什么事件），
加上两条记录项（应用补了几次、录到几次左标点）。

> 分析器本身有自测：`node scripts/verify/ime-punct-analyze.mjs`（无参数）会用两份合成日志证明
> 「干净日志全绿、坏日志被抓」。它**只是判读工具，不产生证据**。

## 四点五、已录到的第一份真实数据（微软 / 微信输入法，2026-10-30）

用 `scripts/verify/ime-punct-collect.mjs`（**带窗口的真实浏览器**，不是 CDP 模拟）在示范项目正文里录到 37 条事件，
覆盖「`，`+引号」「`《`+书名」「单个 `“`」三种情形。判读结果：

| 判据 | 结果 |
|---|---|
| 组合期间应用是否移动光标 | **0 次**（风险 A 在这两家输入法上未出现） |
| 是否出现 `““` / `””` | **0 处** |
| 组合结束后紧跟的事件 | `beforeinput`（3 次）—— 不是 `input` |
| 应用补标点命中次数 | 2 次（第 3 组单个 `“`、后来那个 `【`） |

**最关键的发现**：微软 / 微信上屏时，`compositionupdate` 的 `data` 直接就是 `“”`（**一次两个字符**），
所以 `planPunctPair` 的 `data.length !== 1` 这道边界把它们挡在外面 —— 应用**不插手**，这才是「没问题」的真正原因。
而当输入法只上屏一个 `“` 时（第 3 组），应用补上 `”` 并把光标放到中间，也正确。

> 顺带解释了为什么 `onCompositionEnd` 那条路径不是多余的：这两家组合结束后紧跟的是 `beforeinput`，
> 若某些版本不发提交 `input`，只靠 `onChange` 就会漏补。

**推论（尚待验证）**：搜狗的问题大概率出在「上屏字符的个数/时机与我们假设的不同」——
可能是组合期间就上屏、或多个右引号、或 `compositionend` 之后再补一个字符。
这三种都能落进现有判据的缝里，但**得先有那条序列**才能定位。

### 拿到搜狗样本的两条路

1. **找一台装了搜狗的机器**（或让反馈的用户）双击打开 `docs/tools/ime-quote-probe.html`，
   按页面上的三步打三个引号，点「导出记录」把 JSON 发回来。
   —— 单文件、不联网、不上传，只记录输入事件；**不需要装 Node 或任何环境**。
2. 在那台机器上跑 `node scripts/verify/ime-punct-collect.mjs`（能连应用，能看到应用侧的补标点动作）。

拿到 JSON 后我这边做两件事：先用 `ime-punct-analyze.mjs` 判读，再把那条序列**写成固定样本回放到
`planPunctPair*` 的判据里**（不按输入法品牌分支）—— 序列能过，才算真修好。
