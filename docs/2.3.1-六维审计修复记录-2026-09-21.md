## 二、修复的 4 项

### 🔴 P0-1 · `src/lib/db/core.ts` 关同步时「空 store 被整个跳过」→ 删掉的记录复活

**现场**：`mirrorCloudCacheToLocal()` 里 `if (!list.length) continue` 排在 `if (overwrite) { … }` **之前**。

**为什么是 P0**：`list` 为空 = 这个 store 在云端被**整片清空**了 —— 恰恰是最需要执行「删本地多余记录」的那一份。
跳过的后果：本地旧记录一条不删 ⇒ 关同步后立刻复活；**更糟**的是下次开同步时 `seedFromLocal` 会把它当本地数据
**播种回云端**，删除被彻底撤销。注释（142-145 行）描述的正是这个后果，而长度判断让它只在「非空 store」上生效。

**修法**：把长度判断移进 overwrite 分支内部（`if (list.length) bulkPut(…)`），让 `mirrorDeleteExtra(store, list)`
对空列表也执行 —— 它会算出 `keep = ∅`，从而删光本地该 store。兜底路径（`overwrite=false`）保持原有的长度判断（那里绝不能删）。

### 🔴 P0-2 · `src/lib/syncCore.ts` 「云端没有这条记录」分支未查墓碑 → 第二条复活路径

**现场**：`mergeCaches` 里两支不对称 ——「本地没有、云端有」那一支查了墓碑（`isDeleted`），
而「**云端没有、本地有**」这一支**完全没有墓碑判断**，无条件 `arr.push(lo)`。

**为什么是 P0**：云模式下**本机数据文件是「开启同步那一刻」的冻结快照**（此后读写都走 memory cache）。
于是「开着同步删掉某条 → 不关同步直接关窗重启」时，陈旧本地文件里那条还在：
合并遇到 `lo` 有、`sv` 无 ⇒ 旧实现无条件采纳 `lo` ⇒ 删除被撤销并回推云端（自锁）。

**修法**：判据与另一支对齐 —— `localHasContent && isDeleted(s, k) && (b === undefined || eqRecord(lo, b))` → 跳过。

### 🔴 P1 · `src/lib/syncCore.ts` 拉取失败仍清空 cache → 兜底链条被无声抵消

**现场**：`ensureInit` 的 catch 之后无条件 `cache = {}` / `rev = 0`。
而此后 `fallbackHandler(snapshotOf(cache))` 会拿到**空快照** ⇒ `mirrorCloudCacheToLocal({}, false)` 什么都不写 ⇒
「闩锁期把 cache 镜像回本地、保住未推送改动」这条兜底**存在的唯一目的**被上游清空动作抵消，且无声。

**修法**：catch 内直接 `return`（保留旧 cache），并移除不可达的 `cache = {}` / `rev = 0`。
理由：清空只应发生在「本次会话从未成功拉取过」时 —— 而那种情况下 cache 本来就是空的，所以原来的清空
**只对"曾经成功拉取过"的情况生效**，恰好是最不该清的那一种。项目红线也是「绝不返回空库，否则 push 覆盖云端」。

### P2 · `src/lib/desktop.ts` 注释与事实不符（顺带发现过时表述）

原注释称「与**便携版**一致」且「`tests/cloudStoreWrapper.test.ts` 会比对它与 db/core.ts 用的一致性」。
- 「便携版」组件（`portable.ts`）**早已删除** → 表述过时；
- 经核实，该测试**并未引用** `KEY_PATHS` → 所谓的护栏**不存在**。

**修法**：按事实改写注释，指明真正的第二份副本在 `tests/mock-memory.ts`，且**目前没有测试钉住二者一致**。

## 五、过程教训（值得固化）

### 🔴 补丁器「报成功」不等于「全落盘」，且它对同文件的多条规则会只落最后一条

本轮用 skill 的 `patch-delim.mjs` 打 4 条规则（跨 2 文件、每文件 2 条）。它报告
「✅ 已落盘 2 个文件 / 4 处替换」，但**实际每个文件只落了最后一条**：
`core.ts` 的第 1 条（空 list 走删除镜像）与 `syncCore.ts` 的第 1 条（墓碑）**都没生效**，
而文件里旧写法原封不动 —— 若只看它那行绿色输出，会以为改完了。

**处置**：改为自写脚本（按文件聚合 + 每条规则断言命中 1 次 + **落盘后回读断言**）补齐缺失的两条。

**纪律**：任何批量改写工具，**落盘后必须回读 grep 复核**（本项目红线：凡报成功都须核对），
不要相信工具自己的成功摘要。

### 🔴 验证「删掉的代码是否真的不可达」要按行号定位，别按记忆

`syncCore.ts` 里另有 `cache = {}` 出现在 `configure()`（换目录→作废缓存，语义正确）与两个正常分支。
最初用「`cache = {}` + `rev = 0` 相邻」的正则去查，命中了 915 行的 `configure()` —— **差点误判成"死代码没删干净"**。
→ 定位到具体行号再判上下文。
