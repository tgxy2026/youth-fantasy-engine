## 一、🔴 教训：查证救了一次误删

`audit-dead` 报的 A 类（外部 0 引用 **且** 同文件 0 引用）当时有 5 个。
按字面意思，这 5 个「没有任何人用」= 可以删。**但逐个查证后发现只有 1 个真该删。**

全库 grep（含 `docs/`）后，项目自己的审计文档就写着答案：

> 🔴 **能力缺口（保留 export，绝不降级）**：`pruneGhostFreeChars` / `pruneGhostFreeSessions` 及它们依赖的
> `auditFreeChars` / `auditFreeSessions` —— 自由模式的孤儿索引清理**没有接 UI**，而剧本模式的同类
> `pruneGhostSessions` 已接。这是「索引与分条必须成对」体系唯一自救工具，属红线点名的
> **能力缺口**类别 → **白名单保护** 　　（`docs/2.1.2-审计修复记录-2026-09-17.md`）

也就是说：**它们是「有实现、有测试、没接产品入口」的能力缺口，被明确判定为「保留」。**
而自动闸只看「有没有人引用」，看不出「是不是刻意留着的」——**长得跟死代码一模一样**。

同一个坑里还有第二个发现：`pruneGhostSessions`（剧本版）**不在** A 类里，因为它被
`tests/tavernStore.test.ts:79` 调用着 —— 属 C 类「只为测试而活」。而自由版两个连测试都没有。

> ✅ **处置**：这些**一行都没删**，而是反过来给工具加了白名单（见 §三）。
> 如果当时按 A 类字面执行，就会**删掉两个能力缺口**，而且没人会立刻发现。

## 三、工具改进：`audit-dead.mjs` 新增保留白名单

```js
const KEEP = {
  'src/lib/tavern/store.ts:pruneGhostFreeChars':  '能力缺口：…（理由）',
  'src/lib/tavern/store.ts:pruneGhostFreeSessions': '同上',
  'src/lib/promptSettings.ts:promptText':          '预留 API：…（理由）',
}
const isKept = r => Object.prototype.hasOwnProperty.call(KEEP, `${r.file}:${r.name}`)
const kept = rows.filter(r => r.extUse === 0 && r.selfUse === 0 && isKept(r))
const dead = rows.filter(r => r.extUse === 0 && r.selfUse === 0 && !isKept(r))
```

报告里单列 **A2. 白名单保留**（附理由），与 A 类分开 —— 这样下轮审计不会再拿它们当死代码提案。

**登记纪律**（写进脚本注释）：**必须写清「为什么保留」**；写不出理由的就不该进这张表 —— 那就该删。

> 这正对上项目红线「审计四条」的第 ② 条：**门面/保留项靠白名单认，不靠启发式**。
> 此前 `audit-dead` 缺这一层，于是每轮都会重复提案删掉同样的东西。

## 四、「多余 export」226 个的全画像

定义（B 类）：**外部 0 引用，但文件内部在用** —— 即 `export` 关键字多余，符号本身不是垃圾。

### 4.1 按类型

| 类型 | 数量 | 性质 |
|---|---:|---|
| `type` / `interface` | **156** | 类型编译期擦除、不进产物、不影响 tree-shaking。导出它们是「单一类型源 + 将来复用」的正常姿势 |
| `value`（函数 / 常量） | **70** | 进产物（虽会被 tree-shaking 摇掉），但会让人误判「这是公开 API」。**只有这部分值得看** |

### 4.4 分档判断（我的建议）

| 档 | 数量 | 建议 |
|---|---:|---|
| `type` / `interface` | 156 | **不动**。零成本，且是有意的「单一类型源」；改掉只有 churn 没收益 |
| 表驱动数据条目（`paramGuide` 的 20 个 `GUIDE_*`、`interview` 的 5 个 `*_LABELS`、`split.ts` 的 3 个 `DEFAULT_*`…） | ~30 | **不动**。它们**同文件内成组使用**，去掉 `export` 是形式主义 |
| 工具函数（`ai.ts` 的 `isProviderUsable`/`getActiveProvider`、`nameGen.ts` 的 5 个 `genXxxName`、`store.ts` 的 `auditFree*`…） | ~40 | **可收口**（但仍属低优先）—— 它们是「重构后遗留的公开 API 幻觉」。⚠️ 其中 `auditFree*` 属能力缺口，**别动** |
| **A 类真死代码** | **0** | 已清零 |

**结论：226 个里没有一个是 bug，不处理也不会出问题。** 它们是「设计冗余」，
优先级明显低于功能开发；真要处理也只值得挑那 ~40 个工具函数。

### 4.5 实证（抽样验证闸准不准）

抽 6 个实测，`audit-dead` 判断**全部准确**，包括：

- `setStoreOps`（`db/core.ts`）—— 注释声称「不导出就无法在不跑浏览器的前提下锁住它们」，
  但**单测实际并不引用它** → 属「注释承诺了用途、实际没人用」，已记为待办；
- `splitJournalSection` —— `tests/tavernRoundEnd.test.ts:5` 只在**注释**里提到它，
  闸的「语料净化」规则正确地**没把它算成引用**（这条规则是 2026-09-19 加固的）。
