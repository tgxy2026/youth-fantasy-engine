## 二、本轮已做的接线（#1 `canSemanticRead`）

**问题**：写侧有 `canSemanticWrite`，读侧却直接读 `f.permissions.aiRead` —— 同一件事两套口径。

**改法**：`src/lib/templates/semanticView.ts` 的读取闸 `if (!f.permissions.aiRead)` → `if (!canSemanticRead(f))`。

**为什么只改这一处（其余 4 处刻意保留）**：已写进 `fieldPolicy.ts` 的函数注释 ——

| 位置 | 为什么不替换 |
|---|---|
| `templates/render.ts:54` | 构造字段投影（`aiReadable`/`aiWritable` 都取裸值），它不是闸；只换一个会造成不对称 |
| `templates/defAdapter.ts:39,43` | `key → 原始值` 适配器，返回裸值是职责 |
| `templates/consumers.ts:195,235` | 规则表要在裸值上**再叠** `meaningStatus !== 'pending'`，且必须**保留规则本身**（召回闸靠"规则存在但不可读"判旧块失效） |
| `templates/migrate.ts:307` | 迁移指纹记裸值，口径一变就会误判"模板变过" |

**验证**：`tests/semanticView.test.ts` 新增 ⑬ 四条 ——
未开放读取 ⇒ 值不进视图 / 如实标 `not-ai-readable` / 文案点名是哪个字段 / **源码闸**：读取闸必须走 helper。
（此前这条行为**完全没有测试**，属于顺带补上的空档。79 通过 / 0 失败。）

## 三、`failureReceipt` 为什么不能"顺手接"（留给专项）

看起来最该接，但落点有两个坑，必须一次定清楚：

1. **不能挂在 candidate 上**：`revisionCommit.reconcileCrash` 见到 `receipt.ok === false` 会建议
   `suggestedStatus: 'discarded'` —— 也就是说"写盘失败"会被当成"候选作废"。而磁盘满 / 只读是**可重试**失败，
   重试成功才是常态；一旦标成作废，作者的候选就白丢了。
   （`applyCandidate` 里那句注释"这里**不写回执**"正是这个意思。）
2. **挂在 job 上要有读者**：`RevisionJob.receipt` 目前**没有任何读侧**。只写不读 = 又造一个零引用。
   要做就得同时给 `CandidatePanel` 加一行"上次尝试失败：<原因>"，并定义刷新后怎么读回。

**建议的专项口径**（若主人同意再做）：
`RevisionJob` 增可选 `lastFailure?: { at, code, reason }` → `applyCandidate` 增**可选** dep `recordFailure`
（不传则行为与现在逐字一致）→ `candidateRunner` 落库 → 面板读 `listProjectRevisionJobs` 显示。
风险点：动的是刚加固过的候选关键路径，必须同步跑 `revision-reliability` 16 项探针。

## 四、`linkCheckToCandidate` 为什么不能"顺手接"

它的作用是把"这份候选来自哪份检查报告"记到 `candidate.checkPayloadIds`。
但**没有任何路径会"从检查项生成候选"** —— 候选的唯一生产入口是 `candidateIntake.recordRewriteCandidate`
（整章改写），那里根本没有 checkPayload。所以现在接线只能接成"永远传空"。

**要做**＝先做功能「在检查报告里对某条点『按此改写』→ 生成候选」；那是新能力，不是接线。
