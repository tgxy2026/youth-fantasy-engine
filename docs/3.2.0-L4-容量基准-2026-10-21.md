# 3.2.0 · L4 容量基准：1000 条 × 60 自定义字段（2026-10-21）

> 出处：`docs/3.2.0-W0-开工复核报告-2026-10-19.md` §4.1 L4「1000 条 × 60 字段容量重测」。
> 结论先说：**测量已补上，但这个规模目前不达标** —— 打开一张 1000×60 的表要 17 秒，
> 改一个单元格后保存要 25 秒、输入一次要 3.2 秒。修掉了一处 O(n²) 布局抖动，
> 剩下的瓶颈是「整表无虚拟化 + 每次状态变化全表重渲染」，属架构层，另立决策项。

指标定义：
- **打开**：点击「种族生物」→ 1000 行全部进 DOM（含 IDB 读取、75 列渲染、单元格控件挂载）。
- **输入**：改第一行「容量字段01」的值 → 两帧后（React 提交 + 浏览器绘制）。
- **保存**：点「保存」→ 轮询数据库直到该字段真的变成新值。🔴 不能用页面上的「已保存」当信号 ——
  桌面 / 网页版外壳本身就常驻这四个字（本次踩过，第一版因此误报成功）。
- **筛选 / 清空**：表头「名称」输入 `条目1000` → 只剩 1 行；清空 → 恢复 1000 行。
- **切回**：切到「物品资源」再切回「种族生物」，重新挂载并重读整表。

## 二、修复：单元格高度的 O(n²) 布局抖动

### 2.1 问题

`CellTextarea`（表格文本单元格）原来每个组件一个 `useEffect`：

```ts
ta.style.height = 'auto'
ta.style.height = Math.min(ta.scrollHeight, 78) + 'px'
```

每个单元格「写 → 读 → 写」都会强制同步布局；5 千个 textarea 就是 5 千次级联重排。
100 行 × 60 字段（5,000 个 textarea）实测：

| 指标 | 修复前 |
|---|---|
| 打开（100×60） | **37,919 ms** |
| 清空筛选（恢复 100 行） | **32,968 ms** |
| 最长长任务 | 36,296 ms |

### 2.2 改法（`src/components/sheets/tableSheetShared.tsx`）

同一帧内所有待测单元格攒进一个 `Set`，用 `requestAnimationFrame` 批处理：
先全部写 `height='auto'`，再一次性读 `scrollHeight`，最后一次性写回（仍封顶 78px）。
视觉结果与逐个数完全一致，但整帧只付一次布局成本；卸载时把元素从待处理集合摘掉。

### 2.3 效果（100 行 × 60 字段）

| 指标 | 修复前 | 修复后 | 倍数 |
|---|---|---|---|
| 打开 | 37,919 ms | **2,334 ms** | 16× |
| 清空筛选 | 32,968 ms | **1,641 ms** | 20× |
| 最长长任务 | 36,296 ms | 823 ms | 44× |

## 四、判定与原因

**L4 判定：不通过（边界不可用）。** 依据：

1. 打开一张表 17 秒、输入一个字卡 3.2 秒 —— 这不是「慢一点」，是编辑手感断裂。
2. 保存时整表重渲染数轮，用户点击到落盘可见要 25 秒；期间界面无反馈。
3. 清空筛选要 14 秒，等于每次从「查一个条目」回到全表都要等一次首屏。

根因不在数据层：IDB 读取整表仅 **21 ms**（2.53 MB）。成本全在渲染：
- **无虚拟化**：1000 行 × 75 列全部真实挂载，50,000 个 textarea + 10,000 个数字框 + 10,000 个下拉；
- **状态在顶层**：改一个单元格的草稿会让整张表重新协调（输入 3.2 秒即此项）；
- 保存路径连续更新 `saving / rows / drafts / saved`，触发多轮全表重渲染。

本次已把「每个单元格各自强制布局」的 O(n²) 段摘掉；剩下的两项都属结构层，不是再调一个循环能解决的。

## 五、下一步选项（需主人拍板，未擅自开工）

| 方案 | 做法 | 收益 | 代价 / 风险 |
|---|---|---|---|
| **A. 行级渲染隔离** | 让未改动行在草稿变化时不重渲染（稳定回调 + 行级草稿订阅） | 输入从 3.2s → 预期 < 100ms；保存同步下降 | 中等重构，需逐项核对 20 余个 model 回调不产生闭包陈旧 |
| **B. 虚拟化** | 只渲染视口附近的行（变高行需测高或固定行高） | 打开 / 清空筛选从十几秒 → 亚秒级；堆与 DOM 大幅下降 | 大改：树形层级、行定位、拖拽平移、冻结表头都要重做，回归面广 |
| **C. 分页** | 每页 50~100 行 | 实现最简单，立刻可用 | 改变现有「一屏全表」的使用习惯；需产品决策 |

建议顺序：**A（先救编辑手感）→ 观察 → B 或 C（再救首屏）**。
在 A/B/C 任一落地前，本项维持「L4 不通过」，不能作为发布门槛的已验项。

## 六、顺带记录

- 「页面文本包含『已保存』」不能当保存成功信号：应用外壳常驻该文案。任何保存类实机脚本都应
  以**数据库回读**为准（本脚本已改）。
- 大表下 Playwright 的 `locator.click()` 会因主线程长时间占用而等不到可操作性，30 秒超时；
  量应用本身时用 DOM `click()` 更稳（本次已在脚本中说明）。
- 1000×60 的数据只有 2.53 MB —— 「容量」问题不在存储，在渲染。这条对后续设计很重要：
  不要为「大数据」去优化压缩 / 分片，先把 DOM 数量降下来。
