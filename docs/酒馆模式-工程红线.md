## 1. 导出文档（B5）

- `src/lib/tavern/exportDoc.ts`：**先建中立 DocModel，再渲染 md / html**。
  两种格式各自去读一遍会话，等于把「谁是说话人 / 隐藏消息怎么办 / 行怎么分类」写两遍 ——
  本项目对「两处各写一份必然漂移」已踩过多次（TavernMessage、paramGuide）。

- 行分类 `classifyTavernLine` 与界面**共用**：`TavernMessage.tsx` 只剩样式映射（`KIND_CLASS`）。

  只转义行首 `#` / `>` / `1.`，正文里的 `* _ \`` 一律不动（那是作者的正文，替它转义等于篡改）。

- 三页共用 `TavernExportDialog`，页面只传 `build` 回调 + 摘要文案 + 元信息项的叫法。

## 2. 头像（C3 轻量部分）

- `FreeCharacter.avatar` / `TavernProfile.avatar` 都是 dataURL，**必须先压缩再入库**：
  `src/lib/imageAvatar.ts` 的 `readAvatarFile` —— 居中裁方（`fitSquare`，不拉伸）→ canvas 缩到
  `AVATAR_SIZE = 256` → WebP（不支持回落 JPEG）；解码失败再回落原图（仍受 `AVATAR_MAX_INPUT_BYTES = 4MB` 约束）。
- 🔴 **压缩是硬要求不是优化**：桌面版整库一个 JSON、云同步载荷也是整库，2MB 原图 base64 后约 2.7MB。
  实测：**104KB PNG → 落库 15KB WebP**。
- 渲染统一 `Avatar`（有图用图、没图名字首字；首字用 `Array.from` 取，防 emoji 被切半）；
  设置统一 `AvatarPicker`（选完立刻清空 `input.value`，否则同一张图选第二次不触发 change）。
- 🔴 **图片规格说明的唯一真源**是 `AVATAR_HINT_SPEC`（imageAvatar.ts）—— 两处调用点不许各写一份，
  规格与实现不一致比没有说明更坏（作者会按错的比例裁图）。
- 头像改动走**显式保存**（与卡片其它字段一致），不是偷偷落库 —— 实机专门验了这条。
- 接入点：角色卡编辑区 / 卡片列表 / 自由对话气泡（多角色必挂、单角色仅设过才挂）/ 在场者一览 /
  记忆页签（仅设过才占位）/ 新建对话选角列表 / 「我的档案」。
- 老库兼容：`mergeDeep` 会把默认值里的新键照抄进去，所以 `TavernProfile.avatar` 自动补 `''`，不用写迁移。

## 5. 本场变量（C2 第二步）

- 集合：`VAR_KEYS` / `VAR_DEFS`（types.ts）—— **只有五个**：好感 / 信任 / 剧情进度 / 心情 / 当前地点。
  作者只能**逐项关闭**（`settings.vars.off`），不开放自定义：变量要进提示词，自定义数值没有语义
  （模型不知道「金钱 320」算多算少），开放自定义等于让作者去写协议。
- 存储：`FreeSession.vars`（**会话级**）。设置：`settings.vars = { enabled, off[], maxStep }`，默认 **开 / ±5**。
- 🔴 **数值不由模型每轮输出**（2026-09-15 改）：改在**整理记忆时**单开一次结构化小调用
  （`extractSessionVars`，只输出一行 `〔数值〕…`），算完写回会话、显示在角色状态栏。
  旧做法是每轮在回复末尾要一行记账 —— 实测遵守率极低（真模型探针三次跑 1/6、0/6、0/6），
  作者只会以为「数值功能坏了」。单开一次「只干这一件事」的调用反而干净（探针复测 3/3 准）。
- 🔴 **当前值仍每轮进 system**（`buildVarStateBlock`，挂在 protocol **之后**的 `tail` 层）：
  关掉总开关时返回空串 —— 顺带满足「空层不占额度」。
  地点必须每轮在上下文里，否则整场戏会瞬移（实测：宿舍楼道一步跨到食堂）。
- 🔴 **抽取解析严格到宁可不认**（`parseVarsFromText`，不再要求那一行在末尾）：
  ① 认以 `〔数值〕` 开头的那一行；② 每项必须是白名单变量（中文名或英文键）；
  ③ 数值必须带符号（`±N`）或直接赋值（`N`）。
  解出 0 个操作 → **一个字段都不动**。数值改错比不改更坏。
  `〔数值〕无变化` 是**认得出**的写法：剥行、不产生操作（与"认不出"必须区别对待）。
- **唯一写入关口**是 `applyVarOps`：单步幅度先按 `maxStep` 夹取、再按 0–100 夹取；
  文本变量的长度截断**也只在这里**做（解析侧不各截一次，免得两处规则漂移）。
- 🔴 **重说**（`userText === null`）：先 `undoLastVarChanges` 退回上一次变化，再应用这一轮的新变化 ——
  数值不该停在"那个已经被丢掉的回复"上（实测 53 → 50 → +1 = 51）。
- 🔴 **顺序**：先解变量、**再**跑输出后处理（`postRules` 会把半角括号转全角、去 markdown 记号，
  万一动到那一行就再也解析不出来了）。
- 认不出数值行时只标记 `varParseFailed` 供界面提示，**正文原样保留**。
- 回归：`tests/tavernVars.test.ts`（62 条，含"认不出时一个字都不动""重说撤回""关掉开关后数值行原样保留"）。
- 待做：（已补齐，见 §6。）

## 7. 剧本（自由对话专用）

**六栏**：名称 / 情境 / 开场白 / 你的位置 / 这一场的目标 / 不要发生 ——
＝ SillyTavern 的 `scenario` + `first_mes`，另加「目标 / 边界」两栏（调研结论见设计方案讨论稿 §1）。

- 🔴 **归属：全局 `db.getMeta`**（`tavern.scriptIndex` + `tavern.script.<id>`）—— 与角色卡同性质（玩法模板），
  **不绑某一本书**，换项目照样可用。
- 🔴🔴 **会话里存快照，不存引用**：`FreeSession.scriptId` 只作溯源，真正进上下文的是
  `FreeSession.script`（`snapshotOf()` 那一刻的六栏）。只存引用的话，作者改一次剧本，
  **所有历史会话的设定都会被悄悄改写** —— 这类问题几乎反推不到原因。
- 🔴 **注入边界**：情境 / 你的位置 / 目标 / 不要发生 → 进 `buildSystemPrompt` 的
  **「〖这一场〗」层**（排在设定层之后、记忆之前，空则整层不出现）；
  **名称与开场白不进 system** —— 名称是给人看的，开场白走**消息通道**（对话第一条）。
  开场白塞进 system 会让模型以为用户已经说过这句，还会白占每轮的常驻额度。
- 「六栏全空」＝ `isEmptySnapshot` ＝ 整层不出现（与其他层同一条「空的不占额度」纪律）。

  （留空 / 引用一份）；状态栏的场景行在没有 `scene` 时回落成 `scriptSceneLine()`（剧本名 + 情境首句）。
- AI 起草沿用背景设定那一套：`draftScript` + `parseScriptDraft`（复用 `parsePlainObject`，容错围栏 / 裹解释）；
  `mergeScriptDraft` 保证**AI 空着的栏不覆盖作者已写的**。空 seed 或模型乱答一律抛错，绝不写半截。
- 界面共用一份表单 `TavernScriptFields`（页签与「新建对话 → ＋ 新建剧本」弹窗），
  别各写一份（改一处忘一处的老问题）。

## 8. 仓库纪律（2026-09-14 事故）

🔴 **本仓库禁用 `git stash`。** 事故当口正是一条 `git stash push` 被中断（SIGTERM），
随后发现 `.git/refs/` 整个目录消失、`objects/pack/*.pack` 两个包文件被移入回收站、
`9f780fa` 之后 **7 个提交的松散对象被永久删除**（未进回收站，无法找回）。
**代码内容零丢失**（工作区文件未受影响），丢的是那 7 个提交对象本身。

**取证与恢复流程（本次实际走通的路）**

1. `git` 报 `not a git repository` / `bad object HEAD` 时，先 `ls .git`：**查 `refs/` 与
   `objects/pack/*.pack` 是否还在**。
2. 回收站元数据 `$I*` 是二进制（8B 头 + 8B 大小 + 8B FILETIME + 4B 路径长 + UTF-16LE 原始路径），
   解析它就能知道**哪个文件的原路径**何时被删 → 本仓库的两个 pack 就在里面（`$R*` 是同名内容）。
3. 拷回 pack → `git verify-pack -v <idx>` 应报 ok；再逐个 `git rev-list --count <sha>` 找出
   **祖先链完整**的最新提交（本次 = `9f780fa`）。
4. 写回 `.git/refs/heads/main`；**`.git/index` 会指向已消失的 blob** → `git reset` 也会失败，
   必须 `rm .git/index && git read-tree HEAD` 重建。
5. 用工作区内容补一个「重建」提交，把丢失的提交内容合并回来（提交消息里写清丢了哪几个）。

**已做防护**：历史 bundle + 源码快照在 `G:/AI软件/novel-studio-git备份/`
（bundle `verify` 报 `records a complete history`，可独立克隆）。

⚠️ bundle 路径含中文时 `git bundle create` 会因无法建 `.lock` 而失败 →
**先建在纯英文路径，再用 `cp` 拷回来**（bash 的 cp 认中文路径，git 不认）。

⚠️ 这台机器上 `sort -n` / `sort -r` 有时会解析到 Windows 的 `sort.exe`（报「系统找不到指定的文件」）→
**用 node 脚本代替带参数的 sort**。

⚠️ 界面实机脚本里**别用「数 `六、` 的个数」判编号重复**：扮演协议正文自己带一节
「## 六、作者视角」，计数永远 ≥ 2（本轮假失败一轮）。要查重号就直接查那个标题字符串。
同理，断言「某段文本不含 X」时**必须把范围限定到那个 `<pre>` / 那个容器** ——
扫整个 `main` 会把页面上另一处**合法**的同名内容算进来（本轮又栽一次）。

## 10. 联网检索与 AI 起草（2026-09-15）

【需求】一句话想法 → AI 按模板（角色卡四章 / 剧本六栏 / 背景设定）填好；**能联网就联网查**，
不能就退回「模型已有知识 + 粘贴素材」，并且**每次都要如实告诉作者用的是哪一种**。

- 🔴 **三条素材路由**（`webSearch.ts` 的 `SearchSettings.mode`）：
  · `off`（默认）—— 不联网，只用模型已有知识 + 作者粘贴的素材。零配置，永远可用。
  · `model` —— 让**模型自己**去查（适用于自带联网的模型/中转）。⚠️ 我们看不到这一步，
    `note` 里必须如实写「是否真联网取决于你选的模型」——**不许替它吹牛**。
  · `api` —— 由**我们**查：把标题/网址/摘要喂给模型。引擎三选：**博查**（要密钥，开箱可用）/ **SearXNG**（自建，免费无限量）/ 自定义接口。
- 🔴 **请求由谁发出决定能接哪些接口**（详见 §15）：
  · **桌面版**：走主进程代发（`electron/main.cjs` 的 `net:fetch`）→ 不受同源策略限制，
    **任何返回 JSON 的搜索接口都能接**。请求不出本机。
  · **便携版**：是单文件 HTML、跑在系统浏览器里，**没有主进程** → 只能直连，
    因此只认自带 `Access-Control-Allow-Origin` 的接口：2026-09-15 实测 **博查可**
    （响应带 `ACAO: *` + `Allow-Headers: *` + `OPTIONS`）；智谱的 `web_search` 没有 ACAO
    （只有 `Vary: Origin`），会被拦 —— 界面上因此写明「便携版请用博查」。
- 🔴 **联网与模型无关**：`api` 档是我们查好、把结果当**文本**喂进去，模型只是在读文本 ——
  所以本地 Ollama 这种「自己不会联网」的模型照样能用。界面上写明了这一点，别让它被误解成
  「模型得支持联网才行」。
- 🔴 **来源必须一路带回界面**：`DraftSource{ mode, label, used, error?, note? }` 由
  `prepareDraftMaterial` 统一裁决，三个页面（角色卡 / 剧本 / 背景设定）只负责显示
  （`TavernDraftBits.tsx` 的 `SearchPlanLine` 事前预告 + `DraftSourceLine` 事后回执）。
  **界面不许自己重判**「有没有 key、查没查成」—— 两份判定必然漂移，表现就是「说联网了其实没查成」。
- 🔴 **查失败不中断起草**：用模型已有知识照常生成，但把 `error` 显示出来。
  「静默退化成模型瞎编」是最坏的结果 —— 作者会以为 AI 太笨，而不是知道网络不通。
- 检索结果的提取是**通用遍历**（`harvestItems`）：不认识具体接口形状，只找「有标题 + 有链接/摘要」
  的条目，并去重、按 `topK` 截断。这样换接口不用改代码（博查与智谱的形状都能认出来）。
- 角色卡的起草模板落在 `draft.ts`（此前没有）；剧本与背景设定的模板留在各自模块，
  只把「素材 + 检索 + 来源」这一层抽出来共用（`prepareDraftMaterial`）。
- 🔴 角色卡起草的**示例对话必须遵守协议输出格式**（对白纯文本 / 除对白外一律（ ）/ 「Ta」）——
  写在起草提示词里。理由：模型会照第 4 章的写法模仿，起草时格式写错，之后每轮对话都会跟着错。
- 合并语义统一：**AI 空着的栏不覆盖作者已写的**（`mergeCardDraft` / `mergeScriptDraft`）。

## 11. 对话引导（访谈式创建，2026-09-15）

【需求】原创内容常常「有点感觉说不清」—— 不要逼作者写出一句完整描述，而是**按模板提纲被问着走**，
最后汇总成草稿。**角色卡与剧本都要**；**从零创建与补完已有都要**。

- 两条硬规则（老大明确要求）：**一次只问 1–3 个相关联的问题**（一次抛整张问卷等于把人劝退）；
  **按提纲话题顺序推进**，一个话题聊得差不多再进下一个，并要**先接住作者上一句**再推进。
- 🔴 **每轮都让模型顺带输出 `filled`**（到目前为止从对话里提炼出的字段，增量合并）——
  「生成草稿」不是回头重新总结一遍对话（那样会丢细节），而是把一路攒下的东西交出去。
  字段名走**白名单**（`EMPTY_CARD_DRAFT` / `EMPTY_SCRIPT_FIELDS` 的键），模型自己发明的栏名一律丢掉。
- 提纲：`CARD_TOPICS`（8 个话题覆盖 13 栏，顺序＝先定人→再定形→后定边界）、
  `SCRIPT_TOPICS`（5 个话题覆盖 6 栏，先「这一场在哪」再「你是谁」）。
  ⚠️ 提纲的 `fields` 必须**恰好覆盖模板全部栏**——漏一栏就会永远问不到它（剧本的「名称」就漏过一次，
  由 `tests/tavernDraft.test.ts` 的覆盖断言钉住）。
- 界面（`TavernInterviewDialog.tsx`）右侧实时摊开「已收集 N / 总共 M 栏」与已提炼内容 ——
  访谈式创建最让人不安的就是「聊了半天不知道聊出什么」，摊开来作者能当场发现记错的栏。
- 「补完已有」＝把现有内容当起点交给它（`existing`），并要求**保留已经写好的部分、只补缺**。
- 入口：角色卡页「AI 起草 / 对话引导」两个按钮（`TavernCardDraftDialog` + `TavernInterviewDialog`）；
  剧本页工具条「对话引导」。三处共用 `TavernDraftBits` 的素材/来源组件。

## 15. 搜索源扩到「任意 JSON 接口」（B+C，2026-09-15）

【目标】让「搜索源」不再受浏览器同源策略限制，从而支持**免费可持续**的自建搜索
（SearXNG / Jina / Exa 这类无 key、GET 取 JSON 的服务），且与用哪个模型无关。

### B：接口地址支持 `{query}` 占位符（GET）

- `buildSearchRequest(settings, query, count)` 是**纯函数**（构造与发送分开，可脱离网络单测）：
  **地址里含 `{query}` 就用 GET**，否则 POST JSON `{ query, count }`。
  一份配置覆盖两类接口，不需要再加「方法」下拉框让作者去猜。
- `{count}` 也替换；检索词一律 `encodeURIComponent`（**不编码接口会收到乱码**）。
- 🔴 选了 SearXNG 却给了一个没有 `{query}` 的地址 → **当场报错**，
  而不是 POST 过去再报「没返回结果」（后者的排查成本高得多）。
- SearXNG 预设地址：`http://127.0.0.1:8888/search?q={query}&format=json&language=zh-CN`。
  ⚠️ **三个前提缺一不可**（界面提示里也写了）：
  ① `search.formats` 要包含 `json` —— 官方默认**只有 html**，不加接口直接 **403**；
  ② `limiter: false` —— 开着时它只放行「像浏览器」的请求，我们的调用被判成机器人回 **429**
     （实测：开启状态下 25 次普通客户端请求全部 429）；
  ③ 端口与自己的映射一致。默认取 **8888** 而不是 8080：官方 docker 文档示例就是 `-p 8888:8080`，
     且 8080 极易被占（2026-09-15 本机就被 Steam 的 `steamwebhelper.exe` 占着）。
- 本机实例落在 `G:/AI软件/searxng/`（compose + config），自启路径与 open-webui 相同
  （Docker Desktop 登录自启 + 容器 `restart: unless-stopped`），只绑 `127.0.0.1:8888`。

### C：桌面版由主进程代发请求（`net:fetch`）

- 链路：`webSearch` → `window.electronNet.fetch`（preload 注入）→ `ipcMain.handle('net:fetch')`
  → 主进程 `fetch`。**主进程没有同源策略**，于是 CORS 这道坎在桌面版直接消失。
- 🔴 `netFetch` **永不抛**，失败一律返回 `{ok:false,error}` 由上层如实上报
  （Electron 会把跨 IPC 的异常重新包装、原始信息丢失，与 `sync:readFile` 同一个坑）。
- 🔴 它是通用 HTTP 客户端，**边界必须收窄**：只允许 http/https（拒绝 `file:` —— 否则等于给渲染进程
  开了读本地文件的口子）；剔除 `cookie/referer/origin/host/content-length`；限时 30s；
  响应超 2MB **流式中止**（不要先全读进内存再判）；跟随重定向后校验最终 URL 协议。
- **覆盖范围**：只有**桌面（Electron）版**有这个能力。便携版是 `vite-plugin-singlefile` 打出的
  单文件 HTML、跑在系统浏览器里，**不存在主进程**，仍受同源策略限制。
  所以 `searchBlockedReason` 里有一条：便携版选了 SearXNG 就提前提示「会被跨域拦」。

### 验证（硬证据）

- 单测 `tests/webSearch.test.ts` **34 条**：请求构造（GET/POST/占位符/中文编码/条数夹取）、
  注入发送器验证通道与**失败不静默**、off 档根本不发请求、可用性提前判断。
  Node 测试环境用 `tests/mock-desktop.ts` 把 `HAS_NET_BRIDGE` 固定为 false（等价便携版）。
- 实机（真 Electron，`playwright _electron`）**12 条**：先起一个**故意不带 ACAO** 的本地桩服务，
  ① 渲染进程直连 → **被拦**（证明这道坎真实存在，不是假想）；
  ② 同一接口改由 `window.electronNet.fetch` → **200 并取回真内容**；
  ③ 真 `webSearch` 模块（`import('/src/lib/webSearch.ts')`）端到端 → `used:true` 2 条；
  ④ `file:` 协议被拒；⑤ 服务端收到的检索词是正确中文。
- 界面（真 Chromium）**11 条**：引擎三档、切 SearXNG 后密钥栏收起、地址默认值带 `{query}`、
  提示含 settings.yml、当前档显示名、文案点明「与模型有没有联网能力无关」。

### 踩坑（下次直接照抄）

- 🔴 **本 shell 带着 `ELECTRON_RUN_AS_NODE=1`**（宿主本身是 Electron 应用）→ `electron.exe` 会被
  当成纯 Node 跑，报 `Cannot read properties of undefined (reading 'whenReady')`。
  用 playwright `_electron.launch` 前必须 `delete env.ELECTRON_RUN_AS_NODE`。
- 🔴 该环境里 Electron 的 GPU 进程起不来（`FATAL: GPU process isn't usable. Goodbye.`）→
  必须带 `--disable-gpu --disable-software-rasterizer --no-sandbox`。
- 🔴 跑 Electron 实机验证**务必传 `--user-data-dir=<临时目录>`**：否则会动到老大真实的
  `AppData\Roaming\...` 数据文件（app 启动可能建示范项目）。
- ⚠️ 断言前先确认导出来自哪个模块：`HAS_NET_BRIDGE` 属于 `desktop.ts`，`webSearch.ts` 只是引用它 ——
  探针写错会得到一条「功能明明生效却断言失败」的假失败。

### 🔴 反馈：这次到底联没联上，必须说清楚

原有的 `DraftSource.used` 曾经把「模型自带联网」档硬写成 `true` —— 界面于是会理直气壮地说
「已用上外部资料」，而模型到底查没查我们**根本看不到**。那句话在最坏的情况下就是纯撒谎。
（老大 2026-09-15 点名要求：生成内容的同时必须说明这次是联网查的还是凭已有知识生成的。）

- 新增 `WebVerdict` 四态：`searched`（我们确实取回了资料）/ `failed`（查了没成）/
  `delegated`（交给模型自己查，**无法验证**）/ `off`（按设置没联网）。
  `model` 档的 `used` 已改为 `false`。
- 判定收敛到纯函数 **`describeSource(source)`**（`draftMaterial.ts`）→ `{tone, headline, detail}`：
  · `searched` → ok：「已联网：<引擎> 取回了外部资料」
  · `failed`   → warn：「本次没有联网 —— 检索没成功」＋「下面这些是模型凭已有知识生成的，不是检索到的资料」＋原因
  · `delegated`→ warn：「本次无法确认是否联网」＋「若所选模型/中转不支持联网，下面这些就是它凭已有知识生成的」
  · `off`      → muted：「本次未联网（按你的设置）」
- 渲染只在 `DraftBits.tsx` 的 `DraftSourceLine`：warn=amber、ok=emerald、muted=中性。
  **界面不许自己猜**「有没有联上」——猜错的表现就是「说联网了其实是凭印象编的」，比不报还坏。
- 起草前的 `SearchPlanLine` 也补了一条：选「模型自带联网」时提前说明「本软件看不到这一步」。
