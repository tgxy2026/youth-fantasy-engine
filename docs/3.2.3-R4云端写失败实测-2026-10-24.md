# 3.2.3 · R4 web-cloud 写失败实测（真实配额 413 + 真实写盘 500）

> 日期：2026-10-24｜执行：可可｜基线 `main` / `49d5d09`
> 目的：补齐方案 §6.1「web-cloud 配置的保存故障」与平台矩阵 `write-failure/web-cloud` 的三个必需子场景。
> 版本号仍 3.2.2；未封装、未发布、未部署。

## 1. 为什么这一格一直是 blocked

之前 web-cloud 只证了 `boot-store` 与 `account-isolation`。`write-failure` 一直空着，原因是
「云端保存失败要真的让服务端拒绝或写不进去」，而方案又明令**不许在产品里留故障开关**。

本轮的做法是：**不加开关，改环境**。

| 故障 | 真实来源 | 做法 |
|---|---|---|
| 配额 413 | 服务端 `PUT /api/data` 自带配额校验 | 只把**本次临时账号**的 `quotaBytes` 调到 512 字节（隔离数据目录里的数据，不是产品逻辑） |
| 写盘 500 | `writeTextAtomic` 的 `rename(tmp → data.json)` | 把真实 `data.json` 换成**空目录**，让 rename 真的失败（EPERM），与桌面探针同一手法 |

服务端日志可作旁证：

```
PUT 413 2ms /api/data
[data] 写入失败 probe-a-… EPERM: operation not permitted, rename '…data.json.…tmp' -> '…data.json'
PUT 500 25ms /api/data
PUT 200 9ms  /api/data          ← 解除挡板后自动重试落盘
```

## 2. 实测结果（探针 28/28）

| 检查 | 实测 |
|---|---|
| `write-failure-seed` | 富整库（项目/卷/章，正文＝原始手稿）经真实 `/api/data` 落地 |
| `write-failure-fixture` | 页面上打开项目、进「正文编辑」，textarea 显示的就是那份原始手稿 |
| `quota-rejected-visible` | 配额调小后保存 ⇒ 底栏真实显示落盘错误，内容含 **HTTP 413** |
| `quota-preserves-draft` | 配额被拒后，编辑器里的草稿**一字未丢** |
| `quota-not-persisted` | 服务端 `data.json` 仍是**原始手稿** —— 没有"半截写进去" |
| `server-error-visible` | 恢复配额、加上挡板后保存 ⇒ 底栏显示 **HTTP 500** |
| `failure-preserves-draft` | 500 之后草稿仍是刚敲的那份 |
| `accepted-vs-persisted` | 目标位置**仍是空目录**，暂存字节**逐字节哈希不变**，正文仍是原始手稿 —— 前后端都没把"发出去"当成"存下了" |
| `retry-readback` | 撤掉挡板后，前端**自动重试**把草稿写进 `data.json`，无需重新输入 |
| `recovery-visible` | 底栏错误消失，不再显示「未写入磁盘」 |

关键点：`accepted-vs-persisted` 与 `retry-readback` 都是**读真实文件**得出的，不是读界面提示。

## 3. 顺带查实的两件事

### 3.1 云端写盘的 store 是**数组**形态

第一轮 `retry-readback` 报了超时，但服务端日志里明明 `PUT 200`。查真实落盘文件才发现：

```jsonc
"stores": { "projects": [ … ], "chapters": [ … ], "meta": [ … ] }
```

**云端/便携保存时写的是数组**，而桌面保存写的是主键→记录对象。两者都是合法 `portable-data`。
第一轮探针用 `stores.chapters[ID]` 取值 ⇒ 在数组上永远 undefined，于是把「已经落盘成功」误判成「一直没落」。

这正好复现了 P0 的同一条教训：**同一个 `kind`，行形态因端而异**。现在探针用 `chapterOf()` 两形态都认，
而不是去改产品让它统一（那是另一个决定）。

### 3.2 前端没透出服务端的具体文案（已记录，未改）

服务端返回的是能直接读的话：

```json
{ "ok": false, "error": "存储空间不足：本次写入后约 2.4 KB，配额 512 B" }
```

但 `fileBackend.ts` 在 `!res.ok` 分支只写了 `写入便携数据文件失败：HTTP 413`。
作者看到「HTTP 413」得自己猜是空间满了；桌面/便携同样是这条路径。

- 影响：**只影响可读性**，不影响数据安全（该拦的都拦住了）。
- 处置：**按红线只记录，未改产品代码**。若要改，属于提示文案专项，等主人点名。

## 4. 取证工具自身的一次假红（已修，值得记）

第一次跑完整验收时 `storage.desktop-save` 报了超时（`reliability-SU3mP6`），但桌面探针单独跑又是 15/15。
翻 IPC 记录发现第 4 次 `store:save` **返回 ok:true 且内容是草稿** —— 也就是说应用真的写成功了，
是**探针自己**把那份成果抹掉了：

```
探针 rmdir(空目录)  ──┐
应用 write→rename   ──┘  两者撞在一起：
探针紧接着判"目标不存在" ⇒ 把 keptFile(旧字节) rename 回去，覆盖了应用刚写好的草稿
```

所以 `retry-readback` 读到的是旧正文 ⇒ 超时 ⇒ 整步判红。**这是探针的竞态，不是产品缺陷。**

修法（桌面与云端两处同改）：撤掉挡板后**先等应用/服务端自己写回来**（最多 15s），
只有它确实没写，才用旧字节兜底。撤掉挡板之后"结果如何"应该由产品回答，不该由探针替它填。

> 这条也提醒一件事：探针越会"帮忙补数据"，越容易把真实结果盖掉。挡板是我们造的，撤掉就该撒手。
