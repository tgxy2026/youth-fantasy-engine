### 1.1 `novel-studio-audit-fix`：三个改写器收敛成两个

| 工具 | 格式 | EOL | 命中数 | `--dry` | 处置 |
|---|---|---|---|---|---|
| `patch-delim.mjs` | **纯文本** `@@@FILE/OLD/NEW/EDIT` | 感知 | 恰好 1 | ❌ | **保留**（免转义，片段内容完全自由） |
| `patch-multi.mjs` | JSON | 自动归一 | 恰好 1 | ❌ | **删除**（已并入下面这个） |
| `apply-many.mjs` | JSON | 自动归一 | **可指定 `count`** | ✅ | **保留并增强** |

`apply-many` 本来就是 `patch-multi` 的超集，只差 EOL 自动归一 —— 而那正是上一轮踩的坑：
CRLF 文件（`memory/*.md`）+ 写 `\n` 的跨行锚点 ⇒ 命中 0、整批白跑。

已并入的实现（`normOf`：**按目标文件自己的 EOL** 把锚点里的 `\n` 转成它）：

```js
const normOf = (src) => {
  const EOL = src.includes('\r\n') ? '\r\n' : '\n'
  return (s) => String(s).split('\r\n').join('\n').split('\n').join(EOL)
}
```

实测（用 CRLF 的 `MEMORY.md`）：

| 用例 | 期望 | 实际 |
|---|---|---|
| 跨行锚点写 `\n`（正例） | 命中 1/1 | ✅ 1/1（旧版会 0/1） |
| 锚点写错（负例） | MISS + 退出码 1 + **不落盘** | ✅ 且文件未被改 |

另继承了 `patch-multi` 的「打印文件前后字符数」。原文件备份在 `.workbuddy/tmp/patch-multi.mjs.bak`。

### 2.2 🔴 最值钱的一条：先读接口，别凭印象估改动面

上一轮我把 `db/core.ts` 的 `put: (store, value: any)` 判断成「要清就得先改 `StoreOps` 接口签名，
会级联 5 个实现，属独立一轮」。

**错了** —— `src/lib/storeOps.ts` 里的接口**早就已经是 `unknown`**：

```ts
put(store: string, value: unknown): Promise<void>
bulkPut(store: string, values: unknown[]): Promise<void>
```

实现处写 `any` 只是偷懒，直接对齐即可，一个接口都不用动。
→ **改动面评估前先读接口定义**，凭印象估会把能做的活推到"下一轮"。

### 2.3 手法

| 场景 | 处理 |
|---|---|
| `cloudOrLocal` 动态分发 | 收成局部 `type OpFn = (...a: unknown[]) => Promise<unknown>`，**断言只留一处**；调用点用 `await` 丢弃（`StoreOps` 的 put/del/bulkPut/bulkDel 本就契约 `Promise<void>`） |
| 同步目录句柄（7 处） | 统一成 `SyncDirHandle = string \| FsaDirHandle`；按 desktopCloudSync 既有的 re-export 惯例对外（`export type { SyncDirHandle }`），调用方不必换 import 源 |
| 三类审查产出 | `type RefineFinding = { level?: string }` 共同形状（自检只按 level 过滤，不为每个 Finding 单写一套） |
| SSE 增量行 | `type SseChunk`，`message?.content` 与 `choices?.[0]?.delta?.content` 字段全可选，取值后仍 `typeof` 把守 |

### 2.4 🔴 收窄暴露的两处真问题

这才是 D7 真正的价值 —— `any` 不只是"懒"，它会把**真实缺陷**藏起来：

**① `handle.requestPermission()` 不在标准 `FileSystemHandle` 类型里**

`createFileTransport` 里这行是 **Chromium 的早期实现**，标准类型里没有这个成员
（换成标准 `FileSystemDirectoryHandle` 后直接报「属性不存在」）。
原先的 `any` 把这个「实现与标准的差异」彻底藏住了。

处理：用**本地最小接口**显式声明成**可选成员**，调用点 `?.` 兜底 ——
既说清「它可能不存在」，也保留「不支持就跳过」的现有行为。

```ts
interface FsaDirHandle {
  requestPermission?(opts: { mode: string }): Promise<unknown>
  getFileHandle(name: string, opts?: { create?: boolean }): Promise<FsaFileHandle>
}
```

> 顺带：标准 `FileSystemDirectoryHandle` 也**匹配不上测试里的假句柄**（缺 `kind` 等成员，
> `tests/syncTransport.test.ts` 报了 5 处）。用本地最小接口两头都对得上。

**② `EDITOR_TAB` 缺两个必填字段，靠 `as any` 混进数组**

`TabDef` 必填 `type` 与 `description`，而 `EDITOR_TAB` 只有 id/name/group ——
所以 `Sidebar` 里只能写 `[EDITOR_TAB as any, ...TABS.filter(...)]`，等于把"缺字段"藏了起来。
已补齐为 `TabDef`（`description: ''`）；**先 grep 确认各处只用它的 `.name`**，不会漏出空白。

**③ 附带**：`CloudFileSyncBar` 的目录比对补上 `typeof res.handle === 'string'` 守卫 ——
桌面版行为不变；FSA 分支原本也会判不等，但那是"碰巧"，现在是"有意"。
