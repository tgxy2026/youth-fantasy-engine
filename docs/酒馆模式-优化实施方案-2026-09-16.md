## 二、动手前必须知道的三处「源码实情」

这三点清单里看不出来，但直接决定方案怎么写：

### 发现 1 🔴 自由对话里「故事的世界设定」根本没进 system
- `TavernStory.setting`（上限 2400 字，`story.ts:39`）**只在剧本编辑页被读**（`TavernScript.tsx:115`），
  `engine.buildFreeSystem()` 全文没有引用它 —— `getStory()` 在 `src/lib/tavern/` 下**零调用**。
- 现在自由对话真正注入的固定层只有两块：**角色卡**（`setting`，含第 1 章「角色与设定的关系」）
  与 **剧本快照**（`scene` = `scriptToText(session.script)`）。
- 影响：#5 要拆的「故事」这一项，**目前量出来会是 0 字**。
  → **✅ D1 已定：补上「把故事设定注入 system」**（见 #5 步骤 1）。

### 发现 2 ✅ #13 的根因已定位（输入框失焦）
- `TavernFree.tsx:1226` 输入框 `disabled={streaming}`；`send()` 一进来就把 `streaming` 置 true（`:521`）。
- 生成期间整个 textarea 被 disable → 浏览器**主动移走焦点**；`setInput('')`（`:520`）清空内容；
  生成结束后 `streaming` 回落但**没有人把焦点还回去** → 就是你遇到的「每轮都要再点一次」。
- 修复方向明确（见 #13 步骤），但要先定「生成期间能不能继续打字」→ **见待拍板 Q4**。

### 发现 3 ⚠️ #3 的「改名 / 改范围」会撞存储键
- `VAR_DEFS`（`types.ts:532-538`）里 `progress`（剧情进度）、`place`（当前地点）都是**键名**，
  而 `session.vars.values` 是**按这个键存的**。改 `key`＝动存储键，老会话数据会对不上。
- 现值 `好感/信任 = min0 max100 init50`、`剧情进度 = min0 max100 init0`；
  新值要 `−100~100 默认 0`。**旧数据（50 分那批）怎么迁**是个必须拍板的问题 → **见待拍板 Q2/Q3**。

### #4　本场状态改为「每次回复刷新」

**现状**（`vars.ts` 头注释 + `roundEnd.ts:146-179`）：数值**只在整理时算一次**，
`buildVarExtractSystem` 是为此单开的「只输出一行」小调用。

**落点**：`src/lib/tavern/engine.ts` `runFreeTurn`（**614–700 行**）；
`src/lib/tavern/summarize.ts` `extractSessionVars`（**439 行**，已有，可复用）。

**三种实现（择一，见待拍板 Q4 旁的 Q5）**
- **方案 A（推荐）：每轮回复成功后再跑一次小调用**
  `runFreeTurn` 末尾追加：拿本轮的「user + assistant」两条 → `extractSessionVars` →
  `applyVarOps` → `recordVarChanges` → 合并进 `next.vars`（随 `store.saveFreeSession` 一起落库）。
  - 代价：**每轮多一次模型调用**（本地 27B 上是实打实的额外延迟）。
  - 好处：遵守率高（单职能调用，历史已验证「折进主回复」遵守率极低：探针 1/6、0/6、0/6）。
- **方案 B：折进主回复末尾**（协议里再开「〔数值〕记账行」许可）。
  - 代价：历史实测**基本不吐**；且要改协议 → 关联 #7 的版本 bump。
- **方案 C：做成开关**（默认开/关待定），让作者自己平衡「实时性 vs 速度」。

**✅ D3 已拍板：采用方案 A（每轮回复后单跑一次小调用）**

**同步项**
- `roundEnd.ts` 的「② 本场数值」阶段：**保留**（收尾仍兜底算一次，把最后一轮或异常漏掉的补齐）。
- `tests/tavernVars.test.ts:220-221`「这一轮数值一个都没被改」的断言要按新机制改写。
- 右栏 `TavernVarsPanel` 的「这些状态只在点结束对话时结算」文案（`TavernFree.tsx:1311-1314`）→ 必改为
  「每轮回复后自动更新，也可手改」。

**风险**：中高。**性能**是主要顾虑（每轮 +1 次调用），本地 27B 上延迟会明显增加 —— 老大已接受，
但落地时建议在 UI 上给出「正在结算本场数值…」的轻提示，避免像卡住。

### #11　「结束本轮对话」收尾后主动卸载模型缓存（新增设置项）

**现状可行性**
- `provider.ts` / `engine.ts` 只管「解析 provider + chat」，**没有卸载入口**。
- 模型实际由 Ollama 服务托管 → 卸载要走 Ollama HTTP API：`keep_alive: 0`（下次请求后立即释放）
  或 `POST /api/generate`+`keep_alive:0` / `ollama stop <model>`。

**方案（分两步，先落实再挂设置）**
1. **调研 + 打通卸载通道**：在 `src/lib/ai.ts` 附近新增 `unloadOllamaModel(provider)`：
   对 `provider.kind === 'ollama'`（或 baseUrl 指向本地 127.0.0.1:11434）时，发一次带 `keep_alive:0` 的
   空生成请求 / 调 `ollama stop`；非本地或非 ollama 一律**静默跳过**（不报错、不拦收尾）。
2. **挂设置项**：在控制面板「通用设置」或「自由对话」段加开关
   `unloadAfterRoundEnd` —— **✅ D4 已定：默认关**（用户自己去开）。
3. **接线（顺序是硬约束，D4 明确要求）**：
   `TavernFree.runRoundEnd`（`TavernFree.tsx:341-424`）里的三步
   **①记忆+日记 → ②数值 → ③设定审查** **全部跑完之后**才对 `res` 做处理，
   **卸载必须排在最后** —— 即「`await runRoundEnd(...)` 完整返回、`store.saveFreeSession` 落库完成之后」才发卸载指令。
   🔴 绝不在中途卸载：设定审查与记忆整理都还要调模型，提前卸会让收尾半途失败。
   卸载失败只 warn（**绝不能因为卸载失败把收尾判成失败**）。
4. UI：给出「下次对话将重新加载模型（首句会更慢）」的说明。

**同步项**：`settings.ts` 新增字段 + `DEFAULT_TAVERN_SETTINGS` + `upgradeLegacyDefaults`（老库补默认值）；
`TavernControl.tsx` 加 ToggleField；`tests/tavernSettings.test.ts` 若有设置项计数断言需同步。

**风险**：中。**冷启动延迟**需向用户明示；非 Ollama 后端（云端）此处无意义 → 只有本地 Ollama 才生效。
