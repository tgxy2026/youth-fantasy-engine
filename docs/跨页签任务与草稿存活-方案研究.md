# 跨页签「任务与草稿存活」方案研究

> 背景：社区反馈 —— 在 A 页签使用 AI 功能（典型例子是「一键拆书」），切到 B 页签整理设定后，
> A 页签的 AI 流程被**打断或结果消失，拿不到、也存不下**；编辑类数据同理。
> 定位：**本轮只做研究与方案探讨，不动源码**（主人哥哥 2026-09-30 定）。
> 报告日期：2026-09-30 ｜ 涉及版本：**2.6.3**（主人哥哥拍板：不单独立版本）
>
> ✅ **决策已定版（2026-09-30，主人哥哥拍板五项）**：① 并发＝**真并行**；② 切页签＝**轻提示**（不阻断）；
> ③ 结果回填＝**回到发起页签自动显示**；④ keep-alive **先不做**（只要问题能解决即可）；
> ⑤ **不独立版本，仍旧 2.6.3**。 → 定版方案与实施计划见 **第五节**、决策原文见 **第六节**。

## 一、结论速览

1. **现象属实，而且是架构级的**，不是某一个页签的孤立 bug。左侧共 **54 个页签**（`schema.ts` 的 `TABS`），
   切页签的统一行为＝**旧页签组件整体卸载**，绝大多数长任务的状态与结果都住在组件内部，组件一没就全丢。
2. **根因一句话**：`App.tsx` 用的是**条件渲染**（`renderContent()` 同一时刻只返回**一个**页签的组件），
   切页签 ≠ 「隐藏」，而是**卸载**。见 `src/App.tsx:370`（`renderContent`）、`:428`（`switch (tab.type)`）、
   `:496`（全项目唯一一处挂载点，只渲染当前页签）。
3. **病根其实分两种**（这一步最容易被漏掉，也是为什么用户描述是"打断**或者**消失"）：
   - **A 类「被主动中止」**：组件在卸载清理里 **abort 了请求** → 任务当场被杀，进度归零。
   - **B 类「静默丢弃」**：**没写**卸载清理 → 请求在后台**继续跑到把额度烧完**，结果却写进
     **已卸载组件的 `setState`**（React no-op）→ 额度白烧、结果蒸发、界面空手而归。
4. 项目里**已经有两个成熟范式**可以直接复用，不必从零发明：
   - `src/lib/creativeSession.ts` ——「创意写作」早已踩过同一个坑并解决：**模块级单例 store，
     任务跑在 store 里，与组件是否挂载无关**（文件头 1–17 行写明了理由，就是这条反馈）。
   - 「离开页签即落库」—— `FormSheet` / `TableSheet` / `CharacterSheet` / `OutlineSheet` / `WorldSetSheet`
     都在卸载清理里冲刷未保存草稿（同样是这条反馈的历史修复）。
5. ✅ **定版方向（2026-09-30 拍板）**：分两条线推进——
   - **编辑草稿线**：沿用既有范式**补齐遗漏页签**即可，成本低；
   - **长任务线**：把散落在各面板的长任务**统一上提到一个模块级「任务中心」**（＝把 `creativeSession`
     的做法一般化），再配一个**全局任务指示器**（并入 `DataDock`），让「有几个任务在跑、点哪儿回去看」一目了然。
   - **并发＝真并行**；**切页签轻提示**；**结果回填发起页签**；**不采用 keep-alive**；**并入 2.6.3**。

## 二、核实过程与证据

### 2.1 渲染方式：条件渲染 + 单点挂载（根因）

| 事实 | 证据 |
|---|---|
| 同一时刻**只有一个页签在 DOM 里** | `src/App.tsx:496` `{renderContent()}` —— Suspense 内唯一子节点 |
| 分支是 `if / switch`，切页签即换组件 | `src/App.tsx:370-452`（`if (activeTab === 'xxx') return <Xxx/>` … `switch (tab.type)`） |
| 部分页签还额外用 `key` 强制重挂 | `src/App.tsx:433` `<FormSheet key={tab.id} …>`、`:435` `<TableSheet key={tab.id} …>` |
| 项目**没有** keep-alive / 标签缓存机制 | 全仓库检索 `useSyncExternalStore` 仅 3 处（`ai.ts` / `useAIReady.ts` / `creativeSession.ts`），无任何"保留挂载"实现 |

> 结论：切页签 = 组件卸载。**凡是"住在组件里的东西"，都会在这一刻死掉或失联。**
> 项目其实**早就知道**这件事——`creativeSession.ts:5-7`、`FormSheet.tsx:62-63`、`useTableSheetModel.ts:14-15`
> 三处注释都在复述同一个坑。只是**没有系统性解决**，而是"哪里报了修哪里"。

### 2.2 两种失败模式（核实到的确切证据）

对全部带 `AbortController` 的面板逐个核对了**卸载清理**：

| 面板 / 功能 | 卸载时是否 abort | 结果去向 | 失败模式 |
|---|---|---|---|
| `PaceAnalysisPanel.tsx:49` 节奏分析 | ✅ **abort** | 组件 state | **A 被中止** |
| `ReaderProbePanel.tsx:52` 读者审问 | ✅ **abort** | 组件 state | **A 被中止** |
| `useJieWenJiModel.ts:86` 颉文姬（章评/续写建议等） | ✅ **abort** | 组件 state | **A 被中止** |
| `BookBreakPanel.tsx` 一键拆书 | ❌ 不 abort | 组件 state（`bundle/resume/summaries`，:52-80） | **B 静默丢弃**（额度白烧） |
| `AIOrganize.tsx:119` 表格 AI 整理 | ❌ 不 abort | `setResult(r)`，组件 state | **B 静默丢弃** |
| `EditorModals.tsx:148` 正文校对（错别字/语病/逻辑） | ❌ 不 abort | `onApply` 回调 | **B 静默丢弃** |
| `AIAssist.tsx:165` 通用 AI 助手 | ❌ 不 abort | `persist()` 写库（:184） | ⚠️ **半安全**：结果会落盘，但流式过程消失、无任何提示 |
| `useFreeTurn.ts:399` / `useFreeRoundEnd.ts:243` 酒馆自由会话 | ❌ 不 abort | 依赖各自的 session | ⚠️ 待核 |
| `usePlotSummary.ts:132` 剧情速览 | ❌ 不 abort | 组件 state | **B 静默丢弃** |

**这就是用户说"打断**或者**消失"的来源**：有的功能是 A 类（真被杀），有的是 B 类（白烧额度）。
后者更隐蔽——用户以为"取消了没事"，其实额度已经消耗。

## 四、候选方案与取舍

### 方案 1｜keep-alive：把"卸载"改成"隐藏"（保留挂载）
不再条件渲染，而是**访问过的页签全部保留挂载**、用 `display:none` / `hidden` 切换可见性。

- ✅ 改动集中在 `App.tsx` 一处；所有面板（含长任务、含未落库草稿）**天然全活**。
- ❌ **与项目多处既定的红线设计直接冲突**：`key={tab.id}` 强制重挂、"切章必清 ghost"、
  "离开页签必落库草稿"（改隐藏后这些卸载副作用不再触发）、大量 `useEffect([])` 的挂载期加载会变成**一次性**
  （再切回来看到的是旧数据，需要额外做"激活时刷新"）。
- ❌ 54 个页签按需累积挂载 → 内存与 DOM 体量随使用时长膨胀；定时器/监听/subscription 全挂在后台。
- ❌ 一个页签的浮层/滚动/焦点行为会互相干扰（项目已有的 z 层与 `DataDock` 单浮层约束更难守）。
- **评价**：最短路径但**副作用面最大**，等于把"卸载"这个语义整个推翻重定义。**不推荐作为主方案。**

### 方案 2｜逐面板上提：把长任务状态搬进模块级 store
按 `creativeSession.ts` 的范式，**每个长任务建一个模块级 store**（状态 + AbortController + 结果 + 订阅）。

- ✅ 与项目**已有范式一致**（creativeSession 就是这么干的，且已跑通）。
- ✅ 不动 `App.tsx` 渲染方式，不影响编辑线既有红线。
- ❌ 要**逐个面板改**（拆书、整理、校对、审计、节奏、读者、颉文姬…）；每个都要写一遍
  `subscribe/getSnapshot/useXxx`，**重复度高、容易漂**。
- ❌ 没有统一的"哪里在看进度"，用户仍不知道"后台到底有没有任务在跑"。
- **评价**：方向对，但只做了"点"没做"面"。

### 方案 3｜统一「任务中心」：把方案 2 一般化成一个通用模式 ⭐推荐
建 `lib/aiTaskCenter.ts`（模块级单例）作为**所有长任务的统一容器**，一个任务 = 一条记录：

```
AiTask = {
  id, ownerTab: TabId,        // 发起它的页签（用于结果回填 + 点回去）
  title, kind,                 // "一键拆书" / "AI 整理"
  startedAt, phase, progress,  // 进度（复用现有 FlowProgress/WorkflowTimeline）
  abort(): void,               // 显式中止（只有用户点才中止）
  resultSlot: string,          // 结果写到的"槽位"（参考 freeDraft 的项目级键）
  status: running|done|failed|aborted,
}
```

- ✅ **一个框架覆盖全部长任务**，不再逐面板重复造 store；面板只负责"提交任务 + 订阅展示"。
- ✅ 配一个**全局任务指示器**：显示"有 N 个任务在跑 / 已完成未查看"，点一下回到 `ownerTab`。
- ✅ **结果回填**：任务完成 → 把结果写进 `ownerTab` 对应的结果槽（可序列化部分，参考 `freeDraft.ts`
  的项目级 `settingsKV`）→ 切回来即见，真正解决"拿不到、存不下"。
- ✅ **不再在切页签时 abort**；中止改为**用户显式动作**（按钮）+ **关闭项目/退出**时中止并落断点
  （拆书已有 `BookBreakResume` 断点机制可复用）。
- ✅ 天然回答"能不能并发"：**能**——多个任务可同时排队/并行，界面每任务一条。
- ❌ 需要一次性的框架设计（约一个模块 + 一个指示器组件 + 逐面板"接线"，接线本身比方案 2 轻）。
- ⚠️ **必须守的红线**：
  - 指示器**不能新开左下角浮层**——项目红线是"左下角只准一个浮层 `DataDock`"。应**并入 `DataDock`**
    或放在**右上/页头**等不冲突位置。
  - 新浮层的层号必须走 `Z.*`（`zLayer.ts`），不得裸写 z-index。
  - `lib` 层**禁止 import components**（importCycles 闸）；需要弹提示就写进 `notice`，由组件取走 toast
    （`creativeSession` 已有此约定）。
  - 任务中心**只做"记录与调度"，不做"反检测/洗 AI 痕迹"**——与产品立场一致（纯属流程存续，不涉合规风险）。

### 方案 4｜最小改动：只在"完成时"落盘 + 提示
不动任务本身，只保证：① 卸载时**不 abort**（让它在后台跑完）；② 完成时把结果写进持久槽位；③ 弹一次 toast。

- ✅ 极小改动，能立刻止住"B 类静默丢弃"最痛的部分。
- ❌ 用户切走时**看不到任何"还在跑"的指示**，容易以为没在跑而重复发起、重复烧额度。
- ❌ 不解决 A 类（真被杀）的 3 处。
- **评价**：可作为**过渡**，但不宜作为终态。

### 方案对比

| 维度 | 方案1 keep-alive | 方案2 逐面板 store | **方案3 任务中心** | 方案4 落盘+提示 |
|---|---|---|---|---|
| 改造成本 | 低（1 文件）但连带多 | 高（N 面板重复） | 中（1 框架 + N 接线） | 极低 |
| 覆盖长任务 | ✅ | ✅ | ✅ | ⚠️ 部分 |
| 覆盖编辑草稿 | ✅ | ❌ | ❌（另有既有范式） | ❌ |
| 与现有红线冲突 | 🔴 多处 | 无 | 无（需守浮层/z 层/bl 导出约束） | 无 |
| 后台可见性 | 无 | 无 | ✅ 全局指示器 | 无 |
| 结果回填 | ✅ | 需各自实现 | ✅ 统一 | ✅ |
| 内存/DOM 膨胀 | 🔴 明显 | 无 | 无 | 无 |
| 推荐度 | ✗ | △ | ⭐ | △（过渡） |

## 五、定版方案与实施计划（依 2026-09-30 拍板细化）

> 定版＝**方案 ③ 统一 AI 任务中心**（不采用 keep-alive）。原则不变：
> **先止住"额度白烧"与"结果蒸发"，再建框架，最后推广收口。**
> 决策带来的三个硬约束：**真并行**（→ 任务中心**不做全局队列**，是"登记簿"不是"调度器"）；
> **轻提示**（→ 只能 toast，禁原生弹窗、禁阻断切页签）；**结果回填发起页签**（→ 每个任务带 `ownerTab` + 结果槽位）。

> 目标：**用「一键拆书」验证整条链路** —— 起任务 → 切页签（有提示）→ 后台继续 → 回来结果与断点都还在 → 能继续审阅写入。

### 阶段三 · 收口
