# 一键续写正文 + 设定补完 功能方案（草案 v1）

> 定位：纯前端功能设计，**假设 AI 模型通道已就绪**（不讨论模型选型 / CORS / key / 成本）。
> 范围：在编辑器内提供「一键续写下一章」+「续写后自动抽取并补登设定」。
> 红线：本方案只涉及功能开发，**不升版本号、不封装、不碰服务器**。

---

## 1. 目标

1. 编辑器内「一键续写」：基于项目全量上下文，自动生成下一章正文（可预览、可编辑、可丢弃）。
2. 续写落盘后**自动扫描新章**，抽取其中出现的设定实体（人物 / 功法 / 物品 / 地点 / 伏笔…），与已登记设定做判重后**补登**到对应设定表。
3. 用户介入度可配置：从「点一下确认落盘」到「零干预连写」分档。

---

## 2. 现有地基（直接复用，不重写）

| 模块 | 现成能力 | 方案里的角色 |
|------|----------|--------------|
| `src/lib/ai.ts` | `chat()` 统一入口；`requireActiveProvider()` / `getActiveProvider()` 读取**项目内当前配置的模型**；自带流式、`stripThink`、网页版走 `/api/ai` 反代 | 模型调用底座（本方案不重造） |
| `src/lib/aiContext.ts` | `buildProjectContext({ focusChapterId, budget })` 把全项目设定+角色+伏笔+大纲按优先级裁剪打包，支持焦点章节召回 | **一致性保障核心**：保证模型"记得住"长篇前文 |
| `src/lib/aiTasks.ts` | `aiContinuationAdvice()`（现有，只给方向不给正文）；`aiExtractSettingEntities()`（抽实体）；`aiPleasureCheck()`（爽点/毒点体检） | 方向推导、设定抽取、质量闸门（现成） |
| `src/lib/db.ts` | `saveChapter(c)`（upsert，自动记码字增量+时光机快照）；`saveTableRow(row)`（upsert） | 落盘原语 |
| `src/lib/chapterSeq.ts` | `sortChapters(vols, chs)`——章节顺序**唯一权威**，全派生不落库 | 新章只追加数据，排序交给它，绝不手填卷/章号 |
| `src/lib/settingLedger.ts` | `classify(entities, reg)`——三档判重（`registered` 已登记 / `duplicate` 疑似重复 / `new` 待补登）；`commitEntities(items, chapterTitle)`——把勾选项写表 | 设定补完闭环（大半已现成） |

**结论**：最难的三件事（调用配置模型、组装长篇上下文、抽实体+判重补登）早就是成品。缺口只有一个——「生成正文」任务函数 + 把现成积木串起来的编排层 + UI。

## 3. 需新增的最小模块（4 块）

### 3.1 `aiGenerateBody()` —— 生成正文任务函数（核心缺口）

```ts
// 接口签名草案（非实现）
interface GenerateBodyInput {
  context: ProjectContextResult      // 来自 buildProjectContext
  prevChapter?: Chapter             // 上一章，用于衔接 voice/钩子
  outlineCard?: OutlineCard         // 本章细纲卡（含「本章爽点/章末钩子」字段）
  intent?: string                   // 可选：续写意图（如「推进第二卷中州之约」）
  targetWords?: number              // 可选：目标字数，默认取项目习惯值
}
async function aiGenerateBody(input: GenerateBodyInput): Promise<string>  // 返回 markdown 正文
```

- 系统提示词骨架：身份（网文续写助手）→ 约束（严格贴合已写章第一人称 voice、维持爽文节奏、章末留钩子）→ 输入区（世界观简报 + 角色档案 + 伏笔状态 + 上一章末 200 字 + 本章细纲）→ 输出区（只输出正文，不输出解说）。
- 复用 `composeSystemPrompt()` + `chat()`，**不碰底层 HTTP**。
- 流式输出（拿到 `chat` 的 `onToken` 回调直接灌预览区）。

### 3.2 编排器 `useAutoContinue`（hook / service）

伪流程（L1 单章）：
```
focusChapterId = 当前章 ?? 最新章
ctx = await buildProjectContext({ focusChapterId, budget: 'high' })
prev = await getChapter(focusChapterId)
outline = await getOutlineCard(focusChapterId)        // 可选
body = await aiGenerateBody({ ctx, prevChapter: prev, outlineCard: outline, intent, targetWords })
// → 流式灌入预览区，用户可编辑
// → 用户点「保存」：
newChapter = buildNewChapter({ after: focusChapterId, content: body })   // 复用现有「新建章」store action，只填 content/归属卷
await saveChapter(newChapter)                          // seq 由 sortChapters 派生
// 设定补完：
entities = await aiExtractSettingEntities(body, ctx)
items = settingLedger.classify(entities, await getEntityRegistry())
// → 展示补登清单（registered 跳过 / duplicate 标黄 / new 勾选）
// → 用户勾选后：
await settingLedger.commitEntities(selectedNewItems, newChapter.title)
```

- **新章 id / 归属卷**：复用现有「新建章」store action（已含 id 生成、归属当前卷逻辑），AI 只往里塞 `content`，顺序交给 `chapterSeq.sortChapters`。
- **提取与补登是异步链**：落盘后触发，不阻塞正文预览。

### 3.3 UI：一键续写按钮 + 预览/补登面板

- 按钮复用现有 `Button` 体系（`variant="primary"`，不复造）。位置：编辑器工具栏或章节侧栏「下一章」旁。
- 预览区：流式渲染 AI 正文，提供「保存 / 编辑后保存 / 丢弃」三态。
- 补登清单：表格列出 `classify` 结果，三色状态，`new` 项默认勾选、`duplicate` 需用户拍板、`registered` 不可勾。
- autopilot（L3）额外：进度条 + 「停止」按钮（随时中断）。

### 3.4 设定补完闭环（已大半现成，几乎免写）

`aiExtractSettingEntities` → `settingLedger.classify` → 展示 → `settingLedger.commitEntities`。
设计沿用既有原则：**AI 只抽候选，判重交给 `normName`/`rowFingerprint.norm` 确定性比对**，绝不让模型自判"有没有登记过"（它老把已登记的说成没有）。`commitEntities` 只填名称+一句话描述+首次出场章，其余字段留空给作者补。

## 4. 自动化程度矩阵（可自动化到什么程度）

| 级别 | 名称 | 自动化范围 | 用户必须介入的点 | 适用场景 |
|------|------|-----------|------------------|----------|
| **L0** | 纯手动 | 无（维持现状：AI 只给方向，人写） | 全部 | 精修、关键转折章 |
| **L1** | 一键单章（**推荐默认**） | 生成 1 章正文 + 自动抽设定 + 自动判重 | ①是否落盘（可编辑后落）②补登勾选（duplicate 需拍板） | 日常推进、填补更新 |
| **L2** | 多章连写 | 循环跑 L1 共 N 章，每章把新章设为下一焦点，带上下文连贯 | ①给 N ②中途可暂停 ③末章强制复核 | 冲榜、存稿、批量铺设定 |
| **L3** | autopilot | 零干预连写 + 自动补登，每章插 `aiPleasureCheck()` 做质量闸门 | 仅「启动」「停止」；末审建议保留 | 灵感草稿、世界观铺陈（非最终稿） |

**自动化边界（必须说清的坑）**：
- L2/L3 的质量**强依赖模型能力**。本地小模型（如 0.6B 档）连单章都勉强，连写十章基本糊弄；联网 14B+ 或 deepseek-v3 档才稳。现有 `isProviderUsable()` 只校验「配置填全没」，**不校验能力够不够**——这层需在 UI 加一句提示（"当前模型可能不适合自动连写"）。
- L3 长 autopilot 易跑偏人设/伏笔：建议**硬上限（如 ≤3 章）+ 每章 `aiPleasureCheck` 闸门 + 末章强制人工复核**。
- 成本/时延：联网连写是实打实 token 钱 + 每章数秒～数十秒，UI 必须明示。

## 5. 用户在最低限度下需要提供什么

**最低限度：什么都不用给——点「一键续写」即可。** 理由：

| 信息项 | 不提供时的默认行为 |
|--------|-------------------|
| 续写起点章 | 自动取「当前正在看的章」或「最新章」 |
| 续写方向 | 无则 `aiContinuationAdvice` 据前文自推 |
| 续写长度 | 默认 1 章（L1）；L2 给 N |
| 设定补完 | 默认开，`classify` 自动判重，不重复 |
| 风格锚 | 自动贴已写章 voice（上下文已含前文） |

**想提高质量可补（全非必须）**：
1. **本章细纲卡**（已有「本章爽点 / 章末钩子」字段）——质量提升最明显的一手料。
2. **续写意图**（"推进第二卷中州之约" / "引出新势力"）——定向不跑偏。
3. **风格锚样本**（指定参考某几章）。
4. **连写章数 N**（仅 L2/L3）。
5. **是否允许自动补登无歧义新实体**（关掉则 new 项也需手勾，更保守）。

### 5.1 创建任务面板控件（必填/可选，成组放置）

| 控件 | 类型 | 取值 | 默认 | 说明 |
|------|------|------|------|------|
| 续写章节数 | 步进/滑块 | 1–5 | 1 | 对应 L1 单章 / L2 多章 |
| 每章目标字数（汉字） | 步进/滑块 | 2000–8000 | 4000 | 用 `countWords` 校验「汉字数量」，非字符数 |
| **已有设定更新策略** | 单选 | 见下 | **B 候选确认** | **#2 坑收敛：交给用户在创建任务时选，不内置单一默认策略** |
| 情节概要 | 可选 textarea | 自由文本 | 空 | 不填则 AI 据前文自由发挥 |

**已有设定更新策略**三选项（决定新章内容触碰「已登记设定」字段时怎么办）：

- **A. 仅新增，不碰已有**（最稳）：新发现的设定照常补登（`new`/`duplicate` 走 `classify`）；但对**已登记设定的字段**（修为、关系、性格、状态等）一律不改写。适合"世界观已定型，别乱动"。
- **B. 候选确认（推荐默认）**：AI 抽出"对已有设定的修改建议"列成 diff（如 `陈渊 修为：凝气三层 → 凝气四层`），弹列表让用户勾选采纳后再写回。兼顾自动与可控。
- **C. 自动更新**（最激进）：AI 直接覆盖已有设定字段。最省事但风险最高——弱模型会编造"更新"把你好不容易搭的世界观搞崩，且覆盖后不可逆（除非靠时光机快照回滚）。

> **与自动化级别的联动**：L3 全自动下，只有选 C 才能真·零干预；选 B 会在 diff 处挂起等待确认，实质降级为半自动。故 L3 + C 的组合需额外醒目提示"覆盖不可逆，确定？"。

## 6. 落地红线（踩过的坑，强制遵守）

1. **上下文必须走 `buildProjectContext`**，续写任务不自写 prompt 抓数据——否则长篇必失准。
2. **新章只追加数据，seq 交给 `sortChapters`**，绝不手填卷/章号（防「跨卷排序」翻车）。
3. **设定补完走 `classify` 判重 + `commitEntities`**，AI 只抽候选；确定性比对用 `normName`，不靠模型自判。
4. **写回用 `saveChapter` / `saveTableRow` 的 upsert，禁裸 `replaceOne`**（replaceOne 数据隐患已在记要中点名）。
5. 网页版 CORS 已自动走 `/api/ai` 反代，无需新处理；桌面/便携直连，key 只存本地不传服务器（现有设计）。

## 10. 数据正确性保证（落盘机理，开发前确认）

用户核心疑虑：点「AI 创作」后内容会不会填错表、填错字段、章节串行/覆盖、命名乱掉、保存失败。逐条对应现有底层原语的硬保障：

| 顾虑 | 保障机理 | 代码依据 |
|------|----------|----------|
| **正文误进设定表** | 正文是纯字符串，只进 `Chapter.content`；设定是**另一条独立结构化通道**（`aiExtractSettingEntities` → 带 `type` 的实体），两路物理隔离，AI 无法把正文糊进设定表 | `aiGenerateBody` 返回 string；设定走 `classify` |
| **填错表（人物落到地点表）** | 设定按 `type` 路由到固定映射 `TABLE_TARGET` / `TIER_TAB`；**未知 type 直接进 `failed` 列表、不写入**，绝不乱投 | `commitEntities` 的 `if (!tabId){ failed.push(...); continue }` |
| **填错字段（属性被 AI 乱填）** | `commitEntities` **只写 名称 / 一句话描述 / 首次出场 / 自动编号**，其余字段一律留空给作者；人物也只探测式填 姓名/身份定位/首次出场/状态（`cardFieldPath` 探查，不硬编码） | `settingLedger.ts:173` 实现 |
| **章节串行 / 覆盖** | 每章独立 `uid()`；`saveChapter` 按 **id upsert**，绝不会写到别的章；故事顺序由隐藏 `order` 字段派生，**永不解析章节标题**——AI 把章名叫"第5章"但实为第12章也不影响时序 | `db.ts:506` upsert；`chapterSeq.ts:4` 注释 |
| **设定命名串 / 重复** | 名称经 `normName` 归一化（去标点空白大小写）判重；已登记者（首见名）标 `registered` 跳过，AI 再抽到也只标记不新建 | `settingLedger.ts:49` / `classify` |
| **AI 以为保存了其实没存** | 落盘是确定性 `ops.put` **DB 事务**，与 AI 无关；`await` 成功才认，失败内容留在预览区可重试 | `db.ts:508` |
| **写错后无法挽回** | `saveChapter` 内容变化超阈值（>200 字或 >5 分钟）自动建**时光机快照**，可回滚 | `db.ts:513-520` |

**设定补登的二次保险**：`classify` 出清单后**必须用户勾选**才调用 `commitEntities`；`registered` 跳过、`duplicate` 需拍板、`new` 默认勾——AI 不能静默写设定。

**唯一需用户拍板的开放项——章节标题来源**：
- 现有约定：章节**顺序与标题解耦**（标题只是显示标签），故"命名对错"不影响故事时序。
- 建议：AI 续写后**提议一个标题**（从正文抽/生成短标题），用户可改，**兜底「未命名章节」**；绝不靠解析标题推顺序。
- 待确认：是否允许 AI 自动采纳标题（不留"未命名"），还是强制用户过目。

## 11. v1 实测反馈与修复（2026-08-30 第二轮）

作者本地实测后提出 4 项，逐条处置：

### 11.1 无概要时 AI 一上来就跑偏 → 根因：上一章正文根本没进提示词
- **根因**：`runAutoContinue` 里 `lastBody` 初值为空字符串，第一章的 `prevTail` 因此是空的，AI 只拿到设定资料、拿不到任何"上一章结尾"，等于开新篇。
- **修复**：循环开始前从 `sortChapters` 结果取**库里真实的最后一章**，用其 `content` 尾部 1200 字 + 标题作为 `prevTail`；系统提示第 2 条升级为硬约束"必须从上一章结尾的下一刻写起，不得跳场景/另起新线/大跨度时间跳跃"；未填概要时 user 段显式写"严格沿既有走向延续，聚焦未解决的冲突与悬念，不要凭空引入新地图/新势力/新金手指"。

### 11.2 偶发「只保存了几个标点」→ 根因：stripThink 过度剥离 + 无落库校验
- **根因链**：① `stripThink` 对**未闭合 `<think>`** 的兜底是「从标签起全部丢弃」（`ai.ts:154`），而 v1 写法 `body += cont; body = stripThink(body)` 对**累加体反复剥离**——某次增量带了未闭合标签，先前攒的正文会被整段砍掉，只剩残余标点；② `stripThink` 内 `cleaned || raw.trim()` 只在结果**完全为空**时兜底，剩几个标点则原样返回；③ `countWords` 几个标点 = 0，`selfRefine` 因 `<200` 直接跳过，随后**毫无校验地 `createChapterAfter` 落库**。
- **修复**：① 剥离只作用于**单次返回**（`ask()` 封装），增量单独 strip 后再拼；② 新增**落库硬闸门** `minValidWords(target)=clamp(target*0.2, 200, 600)`，不达标一律丢弃重生成、绝不落库；③ 首次返回 <50 汉字自动静默重试一次；④ 修正/压缩后**二次闸门**再校验一次；⑤ `askSoft` 区分「用户取消」与「模型异常」，取消向上抛不再吞成空串。

### 11.3 每章初稿加入作者裁决（采纳 / 重写 / 中止）
- 流程改为：生成初稿 → 字数校准 → **弹窗裁决** → 采纳后才做编辑自检、修正、设定补登 → 下一章。
- `onChapterDraft(draft) => 'accept' | 'rewrite' | 'abort'` 回调；同章最多 `MAX_DRAFT_ATTEMPTS = 8` 稿（重写与异常重生成共用上限）。
- **重写不产生垃圾数据**：裁决发生在落库之前，弃稿只是丢弃内存字符串，数据库无任何写入。
- 「章节数循环」语义不变，只是每轮中间插入一次裁决；选 `abort` 则整个任务结束。
- 「停止」按钮同时 `resolve('abort')` 解除裁决弹窗挂起（与设定补登弹窗同款处理），杜绝转圈不止。

### 11.4 字数从「只补不压」升级为「区间双向校准」
- **根因**：v1 只有"不足则补"（阈值 0.85），没有"超了则压"，模型写飞就一路飞（要 4000 出 6000+）。
- **修复**：引入 `WORD_TOLERANCE = 300`，目标区间 `[target-300, target+300]`。
  - 系统提示写死区间，并明确"过长与过短同样不合格"，要求模型先估算场景数再分配篇幅。
  - `enforceWordRange()`：偏短 → 分幕补写（≤4 轮，告知精确缺口，无效增量即停止空转）；偏长 → 编辑式压缩（≤2 轮，要求保留全部情节线只删冗余描写）。
  - **压缩安全阀**：压缩结果低于下限 85% 视为模型偷懒/截断，保留原文（宁可超字也不丢情节）。
  - 编辑修正后再跑一轮轻量校准（各 1 轮），因改写会改变长度。
  - **改写安全阀**：`aiRewritePassage` 结果不足原文 60% 汉字数则弃用改写、保留原文。
- 日志与裁决弹窗均显示实际汉字数与目标偏差（如 `4120 汉字，+120`），达标/超差用色区分。
