# 3.7.0 投稿合集与浏览量 · 开发方案

> **状态：待评审，未动一行代码。**
> 版本建议 **3.7.0**：这是新功能（合集 + 浏览量），按项目惯例功能进 minor；3.6.2 的可观测性收尾不并入。
> 本方案依据的是**实际读过的代码**，关键处标了文件与行号，便于评审时逐条核对。
> 参考了主流平台的合集形态，但**不照抄参数**（各平台上限是它们自己的容量决定的），只取结构取舍。

---

## 1. 目标与「不做什么」

### 要做

1. **合集**：作者能把已发布的多篇投稿归到一个合集里，读者在合集内按 **第 1 篇 → 最新篇** 顺序连续阅读。
2. **浏览量**：每篇投稿显示被打开阅读的次数；合集页显示合集总量。

### 明确不做（本版）

| 不做 | 理由 |
| --- | --- |
| 订阅 / 追更提醒 | 需要通知通道（站内信/邮件），是另一个子系统；先把「能读完一个故事」解决 |
| 合集封面图上传 | 涉及对象存储配额与审核；先用文字封面（标题 + 首篇摘要），后续版本再谈 |
| 跨作者共建合集 | 权限模型会翻倍（谁能踢谁、谁改顺序），连载场景不需要 |
| 合集在广场列表里单独成一个「分区」 | 广场当前是单流时间线，加分区要重做信息架构；先做成详情页入口 + 卡片角标 |
| 阅读进度记忆（读到第几篇） | 需要按账号存阅读位置；与「浏览量去重」共用一套记录，P2 再做 |

| 存储是**一次写操作 = 一次整文件读改写**（Node 单线程即互斥） | `server/lib/communityStore.mjs` 第 1-20 行 |
| 容量闸：`maxPosts: 5000`，满了返回 503 而非删旧 | `server/lib/communityStore.mjs` 第 21-30 行 |
| 启动完整性检查只强制 posts.json，其余文件缺失按默认初始化 | `server/lib/communityDocStore.mjs` 第 75-93、115-135 行 |
| 前端投稿摘要类型 `CommunityPostSummary` 含 `counts`，卡片底部渲染 up/down/comments | `src/lib/community/types.ts` 第 13-27 行、`src/components/community/FeedPanel.tsx` 第 450-458 行 |

**这两条现状直接决定了方案走向：**

- 存储是「整文件读改写」⇒ **浏览量绝不能每次浏览都落盘**，否则一次热门投稿就能把 `posts.json` 反复全量读写。
- 启动检查只认 posts ⇒ 新增 `collections.json` 是安全的，不会把老库判成损坏。

## 3. 参考平台形态与取舍

| 平台 | 合集形态 | 顺序 | 值得学的 | 不照搬的 |
| --- | --- | --- | --- | --- |
| 知乎专栏 | 文章归入专栏，文章页显示「收录于专栏」，专栏页是目录 | 发布时间倒序 | 「收录于」这行提示，让读者立刻知道这是系列的一环 | 倒序：小说从最新往回读会毁掉阅读体验 |
| B 站合集 | 视频合集，可拖动排序，合集内自动「上一条/下一条」 | 手动序为主 | **连贯播放**（看完自动到下一篇）+ 合集总量 | 播放器式的自动连播，文字阅读要读者自己决定 |
| 小红书合集 | 笔记合集，封面 + 名称 + 网格 | 时间倒序 | 合集入口足够显眼（详情页顶部） | 只做展示不做目录，读者找不到「从哪开始」 |
| Medium Series / Substack | series 内按发布顺序，正文底部「上一篇/下一篇」 | 正序 | **正序 + 上下篇**，最适合连载 | 无目录页，长篇会迷路 |
| 起点 / 晋江作品页 | 按卷组织，章节目录，显示阅读量与更新时间 | 正序 | **目录 + 阅读量 + 最近更新**三件套 | 卷中卷的层级，本社区体量用不上 |

**结论（组合出的一套）**：

> 知乎的「收录于」提示 + B 站的「合集总量」 + Medium 的「正序上下篇」 + 起点的「目录页」。
> 顺序**默认正序**（第 1 篇在前），这是与社交平台最大的不同 —— 因为这里是连载小说，不是动态流。

## 4. 五个核心设计决策（含「为什么」）

### 4.1 关系只存一侧：`post.collectionId`，合集**不存** `postIds[]`

- 存法：帖子记「我在哪个合集」，合集不记「我有哪些帖子」。
- 为什么：现有存储是整文件读改写，**两处存同一关系就必然有一次写失败导致不一致**（帖子说在 A，合集里没有它）。
  单向存 + 反查排序，只有一个写点，坏不了。
- 代价：合集页要遍历 `posts` 过滤 `collectionId`。5000 篇的量级下是内存遍历，可接受（列表接口本来就在遍历）。

### 4.2 合集内默认**正序**，且顺序与「广场时间线」解耦

- 广场仍是「新的在前」；合集内是「第 1 篇在前」。
- 为什么：读者进合集是为了**从头读一个故事**。社交平台的倒序逻辑在这里会让人从大结局开始看。
- 排序两种模式：`chronological`（按首次发布时间正序，默认）/ `manual`（作者拖动排序）。手动序用整数 `collectionOrder`，重排时整段重写（篇数上限 200，代价可控）。

### 4.3 浏览量**不实时落盘**：内存脏计数 + 定时合并

- 读详情时内存 `+1` 并标记脏；每 **30 秒**或脏计数累计 **200 次**时，合并写一次 `posts.json`。
- 为什么：`posts.json` 是整文件读改写。一篇热门投稿若每次浏览都写，等于每次浏览都重写 5000 篇的 JSON —— I/O 会被放大几个数量级，而且会和其他写操作抢同一把锁。
- 代价（如实写）：**进程被强杀时，最多丢 30 秒的浏览计数**。浏览量丢几条不影响任何判断，这个取舍是划算的。
- 另有一条硬约束：**合并写失败不能影响读**。写失败只记日志、保留脏计数、下次再试。

### 4.4 浏览量的口径（写死，避免以后各说各话）

| 规则 | 取值 | 理由 |
| --- | --- | --- |
| 计数时机 | **只有详情页 GET 成功**时计一次 | 列表曝光不算浏览，否则滚动一遍就涨几百 |
| 同人去重 | 同一账号对同一篇，**24 小时内只计一次** | 防 F5 刷量；跨天再读算新一次（合理） |
| 未登录访客 | 按「IP+UA 的哈希」24 小时一次，**不保存原始 IP** | 网页版有游客；存哈希只为去重，不可反查 |
| 作者本人 | **不计** | 自己反复打开不该涨自己的数 |
| 合集总量 | 各篇之和，标注为「合计浏览」 | 同一读者读 10 篇会算 10 次 —— 这是「篇次」不是「人数」，措辞必须区分，不能叫「读者数」 |

### 4.5 下架 / 撤回的帖子**保留**合集归属

- 帖子被撤回或未过审：公开目录**过滤掉**它，但 `collectionId` 不删。
- 为什么：恢复后要自动归位。若下架时清空归属，作者恢复一篇就得重新挂一次，且顺序丢失。
- 副作用：目录里会出现「第 3 篇 → 第 5 篇」的跳号。**这是对的** —— 它如实反映有一篇不可见，而不是假装连续。

### 4.6 合集本身**不单独走审核**，但标题/简介要过内容过滤

- 为什么：合集只是「分组」，不产生新正文；单独审核会让「建一个合集」变成需要等待的操作，体验很差。
- 但合集标题与简介是**公开可见文本**，必须走与投稿正文同一个 `screenContent()`。
- 兜底：合集可被举报，管理员可下架合集（下架合集 = 公开页 404，帖子本身不受影响）。

## 5. 数据模型

### 5.1 新文件 `collections.json`

```jsonc
{
  "version": 1,
  "items": {
    "col_ab12cd34ef56": {
      "id": "col_ab12cd34ef56",
      "uid": "u_xxx",              // 内部关联，公开接口永不返回
      "title": "归墟（连载）",
      "intro": "一个关于渡口与玉佩的故事。",
      "orderMode": "chronological", // chronological | manual
      "status": "active",           // active | hidden（管理员下架）
      "createdAt": 1763700000000,
      "updatedAt": 1763700000000
    }
  }
}
```

> 注意：**没有 `postIds`**（见 4.1）。

### 5.2 帖子对象扩展（向后兼容）

在 `server/lib/communityApi.mjs:613` 的 post 对象上增加三个字段，读取时缺省：

```js
collectionId: '',        // '' = 未归集
collectionOrder: 0,      // manual 模式下用
views: 0,                // 浏览量（去重后）
```

> 老数据读出来是 `undefined` ⇒ 在 `publicPost()` 里统一 `|| ''` / `|| 0` 兜底，**不做数据迁移脚本**（5000 篇全量重写风险大于收益）。

### 5.3 对外 DTO 扩展

```ts
// 列表与详情共用
interface CommunityPostSummary {
  // ...现有字段不变
  views: number
  collection?: {
    id: string
    title: string
    /** 在合集里的序号（从 1 开始，含不可见篇目的真实位置） */
    index: number
    /** 合集内可见篇数 */
    total: number
  }
}

// 详情额外带导航
interface CommunityPostDetail {
  collectionNav?: { prevId: string | null; nextId: string | null }
}

// 合集页
interface CommunityCollectionPage {
  id: string
  title: string
  intro: string
  postCount: number
  totalViews: number
  updatedAt: number
  isMine?: boolean
  items: Array<Pick<CommunityPostSummary, 'id' | 'title' | 'excerpt' | 'views' | 'createdAt' | 'counts'>>
}
```

## 6. 接口契约

全部挂在现有 `/api/community/**` 下，鉴权沿用现有 Cookie / Bearer（见 `server/lib/communityApi.mjs:3`）。

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/collections/:id` | 公开 | 合集页：信息 + 可见篇目（按顺序）+ 合计浏览；`status=hidden` 时对非作者/非管理员 404 |
| GET | `/my/collections` | 登录 | 我的合集列表（含每集篇数、草稿数） |
| POST | `/collections` | 登录 | 建合集：`{ title, intro?, orderMode? }` |
| PATCH | `/collections/:id` | 作者 | 改标题/简介/排序模式 |
| DELETE | `/collections/:id` | 作者 | 删合集：**先把所有帖子的 collectionId 清空**，再删记录（同一把锁内完成） |
| POST | `/collections/:id/posts` | 作者 | 加入：`{ postId, order? }`；校验帖子属于本人 |
| DELETE | `/collections/:id/posts/:postId` | 作者 | 移出（collectionId 置空） |
| PUT | `/collections/:id/order` | 作者 | 手动排序：`{ postIds: string[] }`，整段重写 `collectionOrder` |

**投稿创建接口的小改动**：`POST /posts` 的 body 可带 `collectionId`，服务端校验「该合集属于本人」后才写入；不合法就**忽略**而不是报错（草稿不应因为合集没了就存不下来）。

## 7. 浏览量实现细节

```
读详情 GET → 判断是否计数
  ├─ 已登录且 uid === post.uid            → 不计（作者本人）
  ├─ viewer 有 uid：查 viewSeen[key] 24h   → 命中则不计数
  ├─ 游客：hash(ip + ua) 查 24h            → 命中则不计数
  └─ 否则：内存 viewsDirty[postId]++ ，写一条 seen 记录
                                    ↓
             每 30s 或累计 200 次脏计数 → 合并进 posts.json（一次读改写）
```

- `viewSeen` 记录放内存（环形，上限 20000 条），**不落盘**：进程重启后去重窗口重置，代价是"重启当天可能多算一次"，可接受。
- 合并写失败：保留脏计数，记录日志，下次重试。**绝不因为计数失败让读者看到错误页**。
- 优雅关闭（SIGTERM）时强制 flush 一次（`server/index.mjs` 已有退出钩子的话挂上去）。
- 防刷：沿用现有 `ratelimit`，对「详情 GET」按 uid/IP 限速（例如 60 次/分钟），超限直接返回 429 不计数。

## 8. 权限 · 审核 · 配额

| 项 | 规则 |
| --- | --- |
| 谁能建合集 | 已登录 + 有投稿权限（与发帖同一套资格判断） |
| 谁能加帖 | 只有合集作者，且帖子必须是**自己的** |
| 上限 | 每人 **20** 个合集；每合集 **200** 篇；标题 40 字；简介 200 字 |
| 内容过滤 | 标题/简介走 `screenContent()`；命中就拒绝建/改，并说明原因 |
| 公开可见 | 合集内**至少一篇已发布**才公开；全被下架/撤回时合集页对读者 404（作者仍可见） |
| 举报 | 新增举报对象类型 `collection`，复用现有 reports 表 |
| 管理员 | 可把 `status` 置 `hidden`；不删数据，可恢复 |

## 11. 分期建议

| 期 | 内容 | 价值 |
| --- | --- | --- |
| **P0** | 浏览量（含缓冲合并 + 去重 + 卡片/详情显示） | 独立可发，用户马上能感知；技术风险集中在一处 |

## 12. 验收清单

### 单测（服务端，沿用现有 `server` 测试风格）

- [ ] 建合集：标题超长 / 简介超长 / 命中内容过滤 → 拒绝且原因可读
- [ ] 配额：第 21 个合集 → 拒绝；第 201 篇 → 拒绝
- [ ] 权限：A 把 B 的帖子加进自己的合集 → 403；A 改 B 的合集 → 403
- [ ] 顺序：`chronological` 下按首次发布时间正序；`manual` 下按 `collectionOrder`
- [ ] 下架：帖子撤回后合集页不含它，且**序号跳号**（不是紧邻）
- [ ] 删合集：篇目的 `collectionId` 全部清空，帖子本身还在
- [ ] 浏览量：同账号 24h 内两次 GET 只 +1；跨 24h +1；作者本人不计
- [ ] 浏览量缓冲：连续 250 次浏览后合并一次，磁盘上数值正确；合并失败时接口仍 200
- [ ] 游客去重：同 IP+UA 24h 一次；不同 UA 各计一次
- [ ] 备份：`collections.json` 在备份清单里（遗漏会静默丢合集）

### 真机（Playwright，沿用 `scripts/verify/` 风格）

- [ ] 详情页「上一篇/下一篇」按目录顺序跳转，到头不显示该侧
- [ ] 合集页目录点击能到对应篇目
- [ ] 卡片与详情的浏览数一致（同一时刻取一次）

## 13. 风险与不变量（红线）

1. **浏览量绝不能变成每次浏览都写盘** —— 否则热门投稿会把整库 I/O 放大到不可用。合并写失败也要让阅读正常。
2. **合集归属只存一侧** —— 双写必然不一致，且现有存储没有事务。
3. **公开接口永不返回 uid / 登录名 / 原始 IP** —— `publicPost()` 白名单继续守住；合集 DTO 同理。
4. **下架不清归属** —— 清了就再也恢复不回去，而且是静默的。
5. **「合计浏览」不能叫「读者数」** —— 篇次 ≠ 人数，措辞错就是误导。
6. **删除合集前必须先解绑篇目** —— 否则帖子指向一个不存在的合集，合集页会出现空壳。
