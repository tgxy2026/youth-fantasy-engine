## 1. 目标与不做什么

**目标**：让引擎具备「把外部 Agent 软件接入为**可选模型后端**」的能力，且可复用到后续更多 Agent 软件，为长篇创作补上「整库级、多步、人在回路」的新作业形态。

**原则**（沿用 3.4.2 规划 §1，按 3.4.3 语境收敛）：

- 以现有调用链为唯一事实来源，不新建平行 AI 系统；3.4.2 已落地的 `aiCore/protocols/` 骨架能复用就复用，不能复用先说明原因（见 §6.E）。
- 核心创作流程**离线可用、不依赖 AI、不依赖任何 Agent 软件**；Agent 后端永远是可选项，未配置时行为与 3.4.2 逐字一致。
- 合规优先于省额度。订阅额度的使用方式以厂商**当期**条款为准，条款风险由主人在知情前提下决策，规划不替主人承担该判断。
- 外部 Agent **默认只读**；需要回写时走引擎既有的「导出项目包 → 导入」通道或产出独立建议文件，禁止外部进程直接写库。
- 不承诺模型质量、额度稳定性或厂商条款长期不变；联网资料只作设计参考，不作质量证据。
- 不把 3.4.2 的多协议能力包装或伪装成订阅额度来源。

**本版明确不做**：

- 不做服务端 AI 代理 / 认证方案（网页形态的 Agent 后端须另立专项）。
- 不做 Bedrock Converse、厂商私有协议（沿用 3.4.2 的暂缓结论）。
- 不做 embedding 旁路的协议统一（3.4.2 已明确列为未覆盖）。
- 不做任何反检测、TLS 指纹伪装、住宅 IP 池、账号轮换（红线）。

## 5. 范式差异：为什么是双轨并存，不是替换

### 5.1 现状 API 模式实现了什么

| 类别 | 代表 | 对后端的硬要求 |
| --- | --- | --- |
| A 同步结构化 JSON（最脆弱） | 六大审读诊断、取名、敏感词复核、整理、拆书、实体抽取、章后变化、全书设定汇总、细纲对照、答疑、酒馆结构化小任务 | 一次性返回**完整、可解析、无过程文本**的字符串；关推理低温；可取消；长输出依赖流式防超时 |
| B 长文本批处理 | 设定圣经、大纲、整章改写、逐章连写、分块校对、续写计划 | SSE 首 token 清总超时、空闲判停滞、中断保留已收片段、重复发起 |
| C 多轮对话 | 酒馆、AI 助手、对话引导、创意访谈 | 完整 `messages` 历史、每轮重组 system、采样参数透传 |
| D 旁路 / 自动静默 | embedding 语义索引与召回、模型清单与卸载；伴写 ghost、连写流水线、写后设定侦测补登、章后整理、酒馆轮次结束自动链 | 无人值守 + 静默 + 低延迟；embedding 与模型清单**完全不经过 `chat()`** |

能力探测（15s 硬超时）与市场雷达（`webSearch` + `chat()` 两段式）都**走 `chat()`**，不属于旁路，也不是无人值守自动链路。

### 5.2 接口模式下的可用性分组

| 分组 | 代表功能 | 判据 / 原因 |
| --- | --- | --- |
| 🟢 **原样可用** | 六大审读、取名、敏感词、整理、大纲、灵感融合、答疑、设定圣经、拆书、分块校对 | 手动单轮、允许等待；需逐项实测，不静态断言 |
| 🟡 **需适配** | 酒馆多轮、对话引导、AI 助手、逐章连写、能力探测、市场雷达 | ACP 是 session 语义，须把 `messages` 数组、五层 system、采样参数逐轮映射；中断与重复调用语义不同 |
| 🔴 **用不了** | 伴写 ghost（1~3s）、一键连写流水线（每章 3~8 次无人值守）、写后自动设定侦测、章后整理、酒馆轮次自动总结 / 变量刷新 | 撞两道墙：ACP 交互式需人确认；官方禁止自动化循环。且这类调用正是封号遥测的触发特征 |
| 🔴 **彻底失效** | 语义索引 / 召回 / 知识库重建、模型清单与卸载 | 走独立旁路、不经 `chat()`，Agent 亦不提供 embedding / tags 端点，**改适配层也捞不回来** |
| 🟢 **新增能力** | 见 §5.3 | 结构上 API 模式做不到 |

**核心判断**：**接口模式不是「更强的同一个东西」**。API 模式是「文本进／文本出、无状态、可重复调用」的同步函数；Agent 模式是「有状态、带工具、人可介入」的长任务。功能增减是范式差异，不是缺陷。因此正确形态是**双轨并存**：保底轨继续由 API 模式承担，Agent 轨承接新增能力。

### 5.3 接口模式带来的新增能力

1. **整库级跨章任务**：不受 8000~12000 字资料窗口硬闸限制，可做全书伏笔闭环、人物线一致性、全书设定汇总。
2. **多步自主工作流**：Agent 自行拆解、检索、执行、回读校验，不靠引擎侧循环拼装。
3. **直接产出文件 / 项目包**：产出独立建议文件、章节稿或可导入包，回写走既有导入通道。
4. **人在回路审核**：Plan → diff → Review 的产物机制，作者先审再落库；与「AI 只辅助」红线契合。
5. **Agent 自带工具与联网**：可承接市场雷达这类「检索 + 总结」两段式任务；现有实现是 `webSearch` + `chat()`，Agent 轨只做能力增强，**不宣称替代全部检索通道**。
6. **多 Agent 编排 / 任务级断点**：长任务可暂停、恢复、留痕。

## 6. 方案设计：后端轨（与协议层正交）

> 本节为**设计意图**，不是已实现结构。所有模块落点、命名与依赖方向须在 P0 结构核查后确定，避免违反 `ai.ts` 门面 / `aiCore` 叶子分层与三段禁互 import 的架构红线。

### 6.A 后端轨契约（🔴 3.4.3 最关键的工程判断）

3.4.2 的 `ChatDriver` 契约是：`chat(config, messages, opts) → Promise<DriverResult>`，一次逻辑调用、一次响应体、一次用量。**Agent 不满足这三个「一次」**：它是 session、有中间过程文本、可能要人确认、可能暂停恢复、产出的是文件而非字符串。

因此：

- 🔴 **禁止**把 Agent 后端伪装成第六个 `WireProtocol`，也禁止在 `ChatDriver.chat()` 里用「循环轮询直到 Agent 结束」把它压成同步函数 —— 会把超时 / 取消 / 用量 / 失败降级四条契约全部扭曲，且「过程文本混进 JSON」正是 A 类任务静默失效的形态。
- **建议**新增一层**后端轨**抽象（命名与落点 P0 定），至少表达：session 生命周期（创建 / 发送 / 取消 / 暂停恢复 / 关闭）、过程事件流（plan / tool / diff / message）、产物（文件 / 建议集）、能力声明（复用 `DriverCapabilities`）、额度口径。
- 后端轨与协议轨**正交**：协议轨负责「跟一个 HTTP 端点怎么说话」，后端轨负责「跟一个有状态 Agent 怎么共事」。两者各自可插拔，不互相继承。
- driver 只做适配，不碰提示词、不做内容改写、不缓存作品正文；避免与 `injectUserSystemPrompt` 的兜底注入语义打架。

### 6.B 能力声明与三轨路由

以 3.4.2 已落地的 `DriverCapabilities` 为**唯一**路由依据，不另立能力表：

| 轨 | 承担 | 规则 |
| --- | --- | --- |
| 保底轨 | 现有 AI 功能全量 | 未配置 Agent 后端时与 **3.4.2** 逐字一致；配置后仍默认走原通道 |
| 需适配轨 | 能力不足的任务 | 按能力声明降级或**跳过并留痕**，禁止静默返回空；不得把「解析失败」写成「审了没问题」 |
| 增强轨 | §5.3 新增能力 | 仅手动触发、显式选择；产出独立文件或走导入通道 |

🔴 `unattended` 在官方条款禁止时一律 `false`，且**用条款约束而非技术手段**保证；`quota` 按真实口径记账，不许把订阅调用报成按量。降级与拒绝必须**可观测**：写进调用归属与用量账本，界面如实提示「本次未执行 / 由何原因跳过」。

### 6.C 只读边界与数据一致性

- 桌面 / 便携为「整库单 JSON + 防抖 + 原子写 + 同源 Web Locks」，**外部进程直接写会打穿一致性** ⇒ 默认只读。
- 网页游客数据在浏览器 IndexedDB，外部进程读不到；网页云端须另走服务器 API + 认证，本版不覆盖。
- 需要回写时：产出独立建议文件，或走既有「导出项目包 → 导入」通道；导入后必须按既有判据重建资料索引（`lib/kbRestoreIndex.ts`）。
- 新增持久数据（后端配置、能力声明、任务留痕）须明确：旧数据默认值、迁移、回退、删除、同步、导出与恢复策略；🔴 **改数据结构必问「写入侧改了吗」**。

### 6.D 形态边界

网页版一律禁用本机 / 局域网端点（P9）；三形态判定以 `platform.ts` 为准（`WEB` 优先）。独立 IDB（`-vec` / `-kb`）不进 `lib/db` 门面，删项目连带清。

### 6.E 与 3.4.2 协议层的关系（一张表说清）

| 维度 | 3.4.2 已落地 | 3.4.3 要做 |
| --- | --- | --- |
| 协议 driver | ✅ 五个 + 注册表 | 不动；最多按需要新增协议 |
| 能力声明 | ✅ `DriverCapabilities` | 复用，作为三轨路由唯一依据 |
| 兼容降级 | ✅ 协议内 `fetchWithWireDegrade()` | 补**能力级**降级（跳过并留痕），两层不混 |
| 配置界面 | ✅ 模型设置 + 协议下拉 + 网页未验证徽标 | 若 P4 授权，新增后端配置区；不挤进现有协议下拉 |
| 用量账本 | ✅ 按协议解析 | 补订阅 / 按量口径区分，不改写既有来源标签 |
| 审计登记 | ✅ 六维 + 契约 | 新后端能力逐项进验收与审计覆盖 |

## 7. 实施顺序与决策门

| 阶段 | 内容 | 出口判据（做不到标 blocked，不硬闯） |

| **P3 官方 ACP 可行性验证** | 仅当主人选 B：以官方未修改运行时 + 一次性账号，验证「交互式派一个整库长任务 → 产出文件 → 引擎导入」闭环 | 记录真实交互与产物；明确哪些功能退化；账号状态如实记录；**不跑无人值守循环** |
| **P4 集成与增强轨** | 按 P1–P3 结论决定是否产品化；若做，补配置界面、用途路由、用量账本、帮助文案与审计登记 | 三道门禁 + 完整六维取证 `complete`；新增能力逐项验收；如实列出未覆盖。**须另行授权** |

## 8. 完成标准与验收

- 核心判据：**未配置 Agent 后端时，现有 AI 功能全量的行为与 3.4.2 逐字一致**（同一夹具前后对照）；配置后，§5.2 标注「原样可用」的功能逐项实测，标注「用不了 / 彻底失效」的链路不得静默报错或伪装成功。
- 能力不符时必须留痕且界面如实提示；禁止把解析失败写成「审了没问题」。
- 外部 Agent 无写库路径；回写只走既有导入通道；导入后索引重建验证。
- 三道门禁全绿（`tsc --noEmit` / `eslint src tests --max-warnings 0` / 全量单测）；全量审计 `complete`（先 `scripts/verify/contracts-evidence.mjs` 再 `scripts/audit/run.mjs --probes --evidence`）；有失败须留证据，不抹去。
- 三形态分别记录覆盖与未覆盖：网页版本机端点禁用属**预期**，不得写成缺陷或写成已支持。
- 若升版本号：4 处同步（`package.json` / `package-lock.json` 头部两处 / `src/lib/help/registry.ts` / `README.md`）+ `tests/helpCenter.test.ts` 门禁；`package-lock.json` 逐处核对未误伤第三方依赖版本。
- 新增测试登记 `tests/run-batches.sh`；夹具内 `src/...` 字面量须真实存在；注释与文档的 `docs/` 路径跑 `check-doc-refs --source` / `--inuse`。

## 9. 风险台账

| 风险 | 后果 | 处置 |
| --- | --- | --- |
| 🔴 订阅额度经网关使用违反 Section 6，2026-02 起有**社区停权案例** | Antigravity / Gemini CLI 账号停权（共用额度池互相连坐）；不波及整个 Google 账号 | 若主人仍选 A，须用一次性账号、书面知悉；默认推荐 B 或 C；**本版不实现任何规避检测** |
| 🔴 引擎「一键连写流水线」＝长循环 + 高频调用，正是遥测触发特征 | 与 Agent 轨组合时风险最高 | 该链路**不路由**到订阅额度后端；能力声明 `unattended=false` 用条款约束硬闸 |
| 🟠 官方口径曾自相矛盾、条款随时可变 | 方案前提失效 | P0 重新取证；规划不把条款快照当长期保证 |
| 🟠 ACP 语义是「编辑器↔编码 Agent」，引擎不是编辑器 | client 侧需自建，交互模型可能不匹配 | P3 先做可行性验证，不通过即记录 blocked，不强推产品化 |
| 🟠 Agent 返回带过程文本 / 工具调用记录 | A 类 JSON 解析判 invalid，功能静默返回空 | 需适配轨跳过并留痕；不靠「宽松解析再猜一次」掩盖 |
| 🟠 外部进程写库打穿整库单 JSON 一致性 | 丢稿 / 串项目 | 默认只读 + 导入通道回写 |
| 🟠 **把 Agent 压成 `ChatDriver`**（3.4.3 新增） | 超时 / 取消 / 用量 / 降级四条契约全被扭曲；过程文本混进 JSON 静默失效 | §6.A 独立后端轨；P0 结构核查时把这条列为硬闸 |
| 🟡 旁路基建（embedding / 模型清单）不经过 `chat()` | 语义索引、召回、知识库重建整条失效 | 保持原通道不动，明确列为接口模式未覆盖 |
| 🟡 用量账本口径失真（订阅 vs 按量） | 统计与复盘失真 | `quota` 纳入能力声明，按真实口径记录 |
| 🟡 3.4.2 的 `protocol` / locality 拆分被后端轨绕开 | 本地判定、采样下发、能力缓存按 pid 比对错配 | 后端轨不得改写 `AIProvider` 的 `type` 存储键与 `protocol` 语义；沿用 `protocolOf()` |

## 10. 版本边界与未覆盖（如实）
