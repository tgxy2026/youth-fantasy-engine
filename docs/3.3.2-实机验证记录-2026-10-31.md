## 1. 已执行并抽出的缺陷（本轮修复）

| 编号 | 严重度 | 现象 | 根因 | 状态 |
|---|---|---|---|---|
| **L1** | 🔴 阻断 | 首次上传成功后，面板永久显示「本机基于第 0 版」，并在下一轮自动同步被判成**假冲突**（"云端与本机各有改动"） | 提交成功只清了墓碑，**没有回写绑定**的 `baseRevision` / `lastSyncedAt`。`afterCommit` 当时写成 `deps.tombstones ? ... : undefined`，没有墓碑存储时连回写也不执行 | ✅ 已修（`nextBindingAfterCommit` + `syncController.onCommitted` + `syncBoot` 接线，单测 44+17） |
| **L2** | 🔴 阻断 | 打开「云端同步」面板后，服务端在数十秒内收到 **17688 次** `GET /api/v2/projects/:pid`（日志一度 16 万行） | 组件内 `const store = createSettingBindingStore()` 每次 render 产生新对象 ⇒ `load` 每次新引用 ⇒ `useEffect([open, load])` 每 render 重跑 ⇒ `load` 里 setState ⇒ 再 render | ✅ 已修（`useMemo` 稳定 store + `load` 重入保护） |
| **L3** | 🔴 阻断 | 同上，页面加载阶段也出现 4503 次 GET | 同步启动写在 `WebDataBar` 里且 cleanup 调 `stopAutoSync`：该组件被反复卸载重挂 ⇒「挂载即启动（立刻跑一轮）→ 卸载即停止」死循环 | ✅ 已修（改为应用级只启动一次，`useRef` 兜底；不再在组件卸载时停） |
| **L4** | 🟡 高 | **拉取功能全线不可用**：`planApply` 一律判「云端清单格式无法识别」 | 服务端返回 `{ ok, revision, manifest, current }`，客户端 `fetchManifest` 直接把外层当清单 ⇒ `objects === undefined` | ✅ 已修（解包 `manifest` 并合入 `revision`，新增契约单测 8 条） |

## 5. 一条验证手段的限制（如实记录）

**内置浏览器对同一构建产物存在强缓存，`?v=` 与 Ctrl+Shift+R 均未能切换到新 JS。**

证据：源码与 `dist` 产物里都能 grep 到临时标记（`未同步v2`），
但页面始终渲染旧文案。因此 **L5 的修复只做了代码层验证（纯函数 + 8 条单测），
没有拿到"界面上确实显示已同步"的截图证据**。

这不等于"L5 已验收"。下一轮在**真实浏览器（Edge profile）或桌面安装包**上复验一次即可闭环。

## 6. 另外一条环境观察（不是产品缺陷，但会影响验证）

在旧的 `127.0.0.1` origin 上，此前失败的队列任务残留在 IndexedDB 里，
导致新任务一直领不到（同项目串行）。换到全新 origin（`localhost`）后上传一次成功、
`baseRevision` 正常推进到 1。

⇒ 真实用户升级后如果长期卡在"排队中"，值得优先怀疑**本机残留的旧队列任务**；
建议后续在 `prepareQueue` 里加"超过 N 次尝试且本机无改动 ⇒ 直接丢弃并如实告知"。

## 8. 本轮新发现并修复的缺陷

| 编号 | 级别 | 现象 | 根因 | 处置 |
|---|---|---|---|---|
| **L6** | 🟡 中 | 章节树「新建章节」下拉菜单在窄面板里**右半边被裁**，只看到「新建最…」「新建自…」 | 菜单用 `left-0` 展开，而按钮在标题栏最右侧 | ✅ 改右对齐 + 限宽 + 卷名截断；实机复验两项完整可见 |
| **L7** | 🔴 高 | 给上传加了「跳过云端已有对象」后，编译/单测全绿但**线上行为毫无变化** | 补丁打在 `sync／syncClient.ts` 的 `createSyncClient()` 上，而**该函数没有任何调用方**；应用实际装配在 `app/syncBoot.ts` + `sync/syncController.ts` | ✅ 改接 `syncController` 并透传到上传器；`createSyncClient` 加显式「未接线」警告注释 |
| **L8** | 🔴 高 | 重建 dist、重启服务后，页面仍运行**旧版 JS** | 服务端 `renderIndex()` 把 `dist/index.html` 缓存进内存且 `if (!indexCache)` **永不失效** ⇒ 一直返回旧 HTML（引用已被删掉的旧 JS 文件名），浏览器于是用 HTTP 缓存里的旧 JS | ✅ 改为按 `mtime` 失效；顺带修掉我第一版引入的重复声明 |
| **L9** | 🟡 中 | 一次推送把同一个对象 PUT 了 5 次（11 个分片里 5 个是空数组，哈希相同） | 上传循环没有按哈希去重 | ✅ 单次推送内按哈希去重；跳过的对象也推进进度 |
| **L10** | 🟡 中 | 每次同步都**重传整本书**（改动一个字 = 40 MiB 含图作品再上行一次） | 上传器不检查云端是否已有该对象 | ✅ 用「基线版本清单」里的哈希跳过重传；服务端回 `OBJECT_MISSING` 时自动补传一轮 |

### L8 是最值得记的一条

它同时解释了两件事：

1. 第一轮把「页面还是旧文案」误判成浏览器强缓存（真实原因是服务端一直给旧 HTML）；
2. **真实部署也会踩**：只要进程不重启，覆盖 dist 之后用户拿到的永远是上一版——
   JS 文件名已变、旧文件已被删，运气好是旧界面，运气差是白屏。

修完后不需要重启服务端：重建 dist ⇒ 下一次请求自动读到新 HTML（本轮就是这样验的）。
