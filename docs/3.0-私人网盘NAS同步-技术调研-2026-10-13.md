# 私人网盘 / NAS 同步能力 — 技术调研与可行性评估

> 调研日期：2026-10-13
> 起因：用户提出「希望能对接私人网盘或 NAS 做同步」
> 现状基线：3.0.2（本项目已有「云盘文件中转同步」，见 §一）

---

## 一、现状盘点：今天已经能做到什么

在讨论新增协议之前，先说清**现在的能力边界**——这决定了「需求是真的没满足，还是用户没发现已有入口」。

### 1.1 已有机制：云盘文件中转同步

| 项 | 事实 | 源码位置 |
|---|---|---|
| 机制 | 用户选定**本机一个同步目录**，软件把整库加密写成 `青春幻想引擎-同步数据.yfe`，由**网盘客户端**负责跨设备搬运 | `src/lib/sync/syncTransport.ts` · `createFileTransport` |
| 支持网盘 | 任何把「本机目录」同步到云的产品：OneDrive / 百度网盘 / 坚果云 / WPS 云盘 / 阿里云盘 / 群晖 Drive / 极空间…… | UI 文案 `CloudFileSyncBar.tsx` |
| 凭据 | **不需要** —— 两块设备指同一目录即互通 | `DEFAULT_CLOUD_KEY` 内置常量 |
| 加密 | AES-GCM，密钥为**公开源码常量**（等价混淆，防明文扫描，不抗蓄意破解） | `syncTransport.ts:50` |
| 冲突 | rev 三路合并 + 墓碑防复活 | `syncCore.ts` · `syncTombstone.ts` |
| 服务器 | **零依赖**，全程不过自建服务器 | 2026-09-15 服务器同步已下线 |

### 1.2 已满足的场景

- ✅ **家里 NAS + 装了同步客户端**（群晖 Drive / 威联通 Qsync / 极空间客户端）→ 选它的本地目录即可，**今天就能用**
- ✅ **Nextcloud / ownCloud 桌面客户端** 同理会往本机映射目录
- ✅ **坚果云 / OneDrive / 百度网盘** 等主流云盘

### 1.3 未被满足的场景（用户真正想要的）

- ❌ **NAS 没装同步客户端**，只想填个「WebDAV 地址 + 账号密码」就直接同步
- ❌ **纯 WebDAV 服务**（群晖 WebDAV Server 套件、坚果云 WebDAV、Alist/rclone 暴露的 WebDAV）
- ❌ **对象存储**（MinIO / Cloudflare R2 / 阿里云 OSS —— 自建 NAS 玩家常用）
- ❌ **不想在本机常驻一个第三方同步客户端**（很多 NAS 用户反感「为了同步还得装一套客户端」）

**结论**：需求成立，且缺口明确——不是「没有同步」，而是**「只有文件目录中转这一条路，没有直连协议」**。

## 二、候选协议调研

### 2.1 协议对比总表

| 协议 | NAS 支持度 | 国内云盘 | 认证 | 传输 | 本项目落地难度 | 结论 |
|---|---|---|---|---|---|---|
| **WebDAV** | ★★★★★ 群晖/威联通/华硕/铁威马/极空间/飞牛全原生 | 坚果云唯一主流支持 | Basic / Digest | HTTP(S) | **低**（主进程已能发 HTTP） | ⭐ **首选** |
| **S3 兼容** | ★★★☆ MinIO/TrueNAS/部分 NAS | 阿里OSS/腾讯COS/七牛 | AK/SK 签名 | HTTP(S) | **中**（需写 SigV4 签名） | ⭐ 次选 |
| **SMB/CIFS** | ★★★★★ Windows 共享事实标准 | — | NTLM/Kerberos | TCP 445 | **高**（445 被封 + 需原生实现） | ❌ 不建议 |
| **SFTP** | ★★★★ 群晖/威联通/TrueNAS | — | SSH 密钥/密码 | TCP 22 | **高**（SSH 协议栈极重） | ❌ 不建议 |
| **Syncthing** | ★★★☆ 需装 Syncthing 本体 | — | 设备 ID 配对 | P2P TLS | **中高**（需内嵌/联动二进制） | ⚠️ 另案 |
| **rclone 联动** | ★★★★★ 万能转接器 | 70+ 存储 | 各自 | 各自 | **中**（需用户自装 rclone） | ⚠️ 另案 |
| **FTP/FTPS** | ★★★ 老 NAS 常带 | — | 明文/FTPS | TCP 21 | 中 | ❌ 安全差 |

### 2.2 各协议关键事实（已联网核实）

**WebDAV**
- 基于 HTTP，**天生适互联网访问**；群晖默认端口 5005(HTTP)/5006(HTTPS)，Nextcloud 走 `/remote.php/dav/files/<user>/`，坚果云走 `https://dav.jianguoyun.com/dav/`
- 群晖/威联通/华硕/铁威马/极空间/飞牛 **全部原生支持**；国内公有云仅**坚果云**支持（百度/腾讯/华为企业盘均未开放）
- 群晖与绿联的 WebDAV **建议用 `/home/` 路径**（某些配置下仅 `/home/` 有写权限）—— 实践中必须支持「远程路径」输入
- 坚果云需在「账户信息 → 安全选项 → 第三方应用管理」**生成应用密码**（非登录密码）—— UI 必须提示这一点

**SMB/CIFS**
- **国内 ISP 大面积封 445 端口**（历史勒索病毒原因），外网访问须改高位端口（4445/16445 等）
- **Windows 客户端难以把 445 换成其他端口**（实测会错走 WebDAV 协议）
- Electron/Node 无原生 SMB 客户端，须引 `@marsaud/smb2` 等三方库 —— **与项目「零依赖」政策冲突**
- **判定：不作为首选**，局域网内用户仍可用「挂载为本地盘 + 目录中转」绕过

**SFTP**
- 须实现完整 SSH 协议栈（密钥交换/加密/MAC），Node 侧唯一现实路径是 `ssh2` 三方库 —— **同样违反零依赖**
- 群晖/威联通开 SFTP 容易，但**落地成本全在客户端协议栈**，性价比低

**S3 兼容**
- 单签名算法（AWS SigV4）+ 少量 REST 动作（PUT/GET/HEAD/DELETE/LIST）即可覆盖需求，**可纯手写、无依赖**
- MinIO（自建 NAS 首选）、Cloudflare R2（10GB 免费）、阿里 OSS / 腾讯 COS 均兼容
- **是 WebDAV 之外唯一的「高价值 + 可零依赖落地」选项**

**Syncthing**
- P2P 去中心化、TLS 1.3 端到端加密，有完整 **REST API**（`X-API-Key` 认证，`/rest/db/status`、`/rest/db/scan`、`/rest/events` 长轮询）
- 但**应用不能替用户装 Syncthing**，最多检测「本地 8384 端口是否在跑」并借用其 API —— 用户门槛高
- **判定：可作为「高级玩法」提示，不做为一等公民**

**rclone 联动**
- rclone 支持 70+ 存储，可 `serve webdav` 把任意网盘转成 WebDAV 端点
- 思路：用户在 NAS 或本机跑 `rclone serve webdav`，本项目**用 WebDAV 协议连它** → 等于**间接支持了 70+ 网盘**
- **判定：不额外开发，靠 WebDAV 自然覆盖**，在帮助文档里写一句即可

## 三、可行性评估（针对本项目架构）

### 3.1 现有架构对新增协议友好度：★★★★★

`syncTransport.ts` 顶部写着：

> 「只做一件事：把「字节怎么落地 / 怎么读回来」与加密、载荷结构、rev 三路合并解耦。」

这正是**扩展点上佳**的架构：

```
        ┌─────────────────────────────────────────────┐
        │  syncCore.ts（加密 / 载荷 / rev 合并 / 墓碑） │  ← 完全复用，一行不改
        └────────────────┬────────────────────────────┘
                         │ SyncTransport 接口（pull / push / startWatch / stopWatch）
        ┌────────────────┼────────────────┬───────────────┐
        │                │                │               │
   FileTransport    IdleTransport   （新增）WebDAV    （可选）S3
   已有·在用          已有·占位        Transport        Transport
```

**新增一个协议 = 实现一个 `SyncTransport`**，加密/冲突/备份/恢复全部白拿。

### 3.2 落地路径（WebDAV）

| 步骤 | 做什么 | 位置 | 依赖 |
|---|---|---|---|
| ① 主进程加 IPC | `webdav:propfind` / `webdav:put` / `webdav:get` / `webdav:mkcol`，用 Node `http/https` 手写 | `electron/main.cjs` | 无（Node 内置） |
| ② preload 暴露 | `window.electronStore.webdavXxx()` | `electron/preload.cjs` | 无 |
| ③ 渲染层实现 | 新建 `createWebdavTransport()`，实现 `SyncTransport` | `src/lib/sync/webdavTransport.ts` | 无 |
| ④ UI 加一档 | 云盘同步页加「直连 WebDAV」选项 + 地址/账号/密码/远程路径四个输入 | `CloudFileSyncBar.tsx` | 无 |
| ⑤ 配置持久化 | 凭据存 `settingsKV`（**需决定是否入备份**，见 §四） | `lib/db` | 无 |

**总代码量预估**：主进程 ~200 行、渲染层 ~250 行、UI ~150 行。**零新增 npm 依赖**，完全符合项目零依赖政策。

### 3.3 关键技术风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **CORS** | 渲染进程直连 WebDAV 会被同源策略拦 | **必须走主进程**（Node http 不受 CORS 约束）—— 这正是现有 `net:fetch` 的既有范式 |
| **自签名证书** | NAS HTTPS 常用自签，Node 会拒 | 提供「忽略证书校验」开关（默认关），并在 UI 警告 |
| **Basic Auth** | 部分服务需 Digest | 先做 Basic（覆盖 95%），Digest 按需加 |
| **路径语义** | 群晖要 `/home/`、Nextcloud 要完整前缀 | 提供「远程路径」输入 + 「测试连接」按钮 |
| **大文件** | 整库 JSON 可能几十 MB | 复用现有 `.yfe` 单文件策略，WebDAV PUT 单次上传；超限再考虑分片 |

## 四、需要用户（主人）决策的点

1. **先做 WebDAV，还是 WebDAV + S3 一起做？**
   - WebDAV 覆盖 NAS 与坚果云，是**性价比最高的一档**
   - S3 覆盖自建对象存储玩家，但需手写 SigV4，工作量约是 WebDAV 的 1.5 倍
2. **凭据是否随备份走？**
   - 存进整库 JSON 会**随备份/云同步扩散**，密码泄漏面变大
   - 建议存 `settingsKV` 但**排除出备份**（与 `kbInBackup` 同一套机制）
3. **是否明说「不加密传输」？**
   - HTTP（非 HTTPS）的 WebDAV 是明文，须在 UI 显著提示，与现有「密钥是公开常量」的披露口径一致
4. **要不要做「测试连接」按钮？**（强烈建议做，NAS 路径千奇百怪，没有它用户会反复失败）

## 五、结论与建议

### ✅ 结论：**可实现，且架构上是最省力的一类新增**

- 现有 `SyncTransport` 抽象天然支持多协议，加密/冲突/备份全部复用
- WebDAV **零依赖可实现**（Node 内置 http/https），不破坏项目零依赖政策
- 覆盖了用户核心诉求：**群晖/威联通/极空间/飞牛 + 坚果云，填地址密码即用**
- SMB/SFTP 因**封端口 + 需三方库**，明确不建议立项

### 📋 建议实施顺序

| 优先级 | 内容 | 理由 |
|---|---|---|
| **P1** | WebDAV 直连同步 | 覆盖 90% NAS 用户，零依赖，工作量最小 |
| P2 | 「测试连接」+ 完整错误提示 | 决定功能可用性的关键体验 |
| P3 | S3 兼容（MinIO/R2） | 覆盖自建存储玩家，工作量中等 |
| — | Syncthing / rclone | **不做**，靠 WebDAV + 文档提示自然覆盖 |

### 💡 一句话给用户

> NAS 用户**今天**就能用：装个群晖 Drive / 极空间客户端，在云盘同步里选它的本地目录即可。
> 如果想要「填个 WebDAV 地址就直接同步」，**这个可以做**，而且不需要引入任何新依赖。
