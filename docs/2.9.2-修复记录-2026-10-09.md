## 1. ① 投稿前自检落库（P1-③）

- `lib/checkLog.ts`：`CheckEngine` 加 `'manuscript'`；新增 `manuscriptLogged(scope, obs)`。

- `components/ManuscriptCheckPanel.tsx`：点「跑结构与伏笔」时顺手落一条台账并刷新趋势。

**三个刻意的设计**（都写进了源码注释）：不做缓存（纯统计算得快）／不区分 `error`（观察项不是「问题」，`notable` 计 `warn` 只为让趋势有增减可算）／`scope` 用**章节 id**（趋势要「这一章比上次」，不是全书混算）。
且**只在作者显式点按钮时落库** —— 行文指纹本身随渲染即时算，跟着渲染走会变成每切一章写一次盘。

## 2. ② 优化工单按问题类型聚合（P2-①）

- `lib/optimizeTicket.ts`：新增 `TicketIssueGroup` + `groupByIssue(items)`。

按类型视图**只做汇总、不提供勾选**（底部写明「执行改写仍在按章视图」）。

## 3. ③ `dataHealth` 提示（P1-② · 方案 C）

**为什么不是「挂插槽」**：原报告估"小改动"，核实后发现「设定变更」页由通用 `TableSheet` 渲染，而**它没有页顶插槽能力**（会影响所有表格页）；且 `dataHealth` 是**全库扫描**，常驻区块会随页面渲染反复跑。

- `components/ChangelogHealthNote.tsx` 🆕：进出该页时静默跑一次 `runDataHealthCheck()`，**仅 `error` 级**才渲染一行提示；带模块级缓存（按「项目 + `project.updatedAt`」失效 + 5 分钟 TTL）。
- `App.tsx`：`case 'table'` 中对 `tab.id === 'changelog'` 包一层。

三条口径都落实：**不常驻区块**（无冲突时页面与改动前**一字不差**）／**静默跑**（失败不弹错）／**只报数不判定**（给条数 + 去处，逐条上下文仍在检查工具页）。

🎯 **实测**：dataHealth 全库扫描 **11 ms** —— 方案 §3 担心的性能问题**不存在**（缓存仍保留，只防大项目）。

## 4. ④ 节奏与章末钩子落库 + 同模型趋势（P2-②）

### 改动（3 源码 + 1 测试）

| 文件 | 改动 |
|---|---|
| `lib/checkLog.ts` | `CheckEngine` 加 `'pace'`；`CheckSnapshot` 加 `model?: string`；`logSnapshot(..., model?)`；新增 `paceLogged(scope, report, model?)`；`trendOf(engine, scope, model?)` 支持**同模型过滤** |

| `components/PaceAnalysisPanel.tsx` | 真跑完落台账；新增趋势行与刷新 effect |
| `tests/checkLog.test.ts` | +7 条（含 4 条核心判据） |

### 四条口径（🔴 与实施方案原设想有两处不同，已按实现更正文档）

1. **记 `provider.model`，不记 `provider.name`** —— 后者是作者可随手改的显示名，一改名就把趋势线截断。
2. **趋势只比同模型**：`trendOf(..., model)` 传了就只留 `model` 相同的快照。
   `model` 缺失的快照**直接排除**（原设想是"单独标注不参与对比"⇒ 趋势行是极简一行塞不下说明；且 `pace` 是本版新引擎，不存在"老快照"）。
3. 🔴 **不做缓存**（与原设想相反）：这是一次**显式 AI 调用**，本就该每次真跑；缓存只对「同数据版本内重复调用」有意义。
4. **先 `await` 写盘再 `return`** —— 任务转 `done` 时订阅趋势的 effect 才读得到刚落的这条（顺序反了永远落后一轮）。

### 观察类不染红绿

`total` ＝「本次观察到的结构点数」＝ 爆点处数 ＋（章末无钩子时 1）：
每条爆点 → `info`（title 用「段位 · 类型」，段位是本地拿引文定位算的）；章末无钩子 → `warn`（**客观结构事实，不是评分**）。
界面用 `neutral` 形态且单位说成「**个观察点**」—— 爆点变多不等于变好、变少也可能是这本该收束，染红会把「观察」误读成「问题」。

### 验证

- 🔴 **换模型 ⇒ 趋势断线重新开始**（同模型仍有上一条、新模型 `prev` 为 null）：单测 + 实机各验一次；
- 同模型连跑两次 ⇒ 出现「比上轮 多/少 N 个观察点」；本地 4B 实测 **54.1 s／次**（首跑含模型加载）。

## 6. 本轮新坑（3 个，都已固化）

### 坑 A · `.workbuddy/tools/apply-many.mjs` 是旧版，**不认 `--dry`**

写了 `--dry` 它照样落盘，导致随后那次「正式落盘」因锚点已被替换而整批 FAIL。
⇒ 已用 skill 版（支持 `--dry` + EOL 自动归一）覆盖 `tools/` 版，实测生效。
🔴 **教训**：跑 `--dry` 要看输出里有没有「**未写盘**」，别默认它一定生效。

### 坑 B · 🔴🔴 `page.evaluate` 里 import 的模块与 React 用的**不是同一个实例**

实机 ④ 段最初用 `page.evaluate` 直接写 AI provider 配置，结果 **4 条断言全挂**，而界面上
**既不报错、也没有任何提示** —— 唯一线索是「按钮 `disabled` + 面板内显示『需先接入 AI 模型』」。

根因：vite dev server 给模块 URL 带了 `?t=` 版本戳 ⇒ 同一文件两个 URL ⇒ **两份模块状态**；
`evaluate` 侧写配置触发的「AI 就绪」广播，React 侧**收不到**。
⇒ **正解：写完配置后 `page.reload()`**（UI 侧重新初始化，从同一个 IDB 读到配置）。
已写进 `ui-292-verify.mjs` ④ 段的注释与断言（`④ reload 后模型就绪、按钮可点`）。

### 坑 C · **二态断言只跑一边 ＝ 没验证**（⑤ 段踩过）

第一轮实机只在本机（本地模型）跑 ⇒ 那条「酒馆云端灰显」断言在「0 项灰显」时**也通过** ——
等于什么都没验证。改法：实机**主动切云端预设**再验一次（新增断言「云端形态：正好 3 项灰显」）；
酒馆那边改不了当前模型 ⇒ 改用**源码断言**钉住「6 处两态 + 同一组件 + 父组件统一传参」。
