# 3.2.0 · W3 候选链路 实机验收结论（2026-10-21）

> 环境：dev `localhost:5199` + 真 Edge（持久化 profile）+ 示范项目「吞天神脉（示范）」21 章
> 方式：Playwright 驱动真实渲染、真实 IndexedDB、真实 AI 通道（非模拟）
> 版本：`v3.2.0`（页面标题已确认）

## 一、为什么这一轮必须实机

核查发现：候选的存储、应用内核、审阅界面三块都在，但**没有任何地方创建一份候选** ——
`listProjectCandidates` 只被面板读、`saveCandidate` 只被"保存状态变更"调用。
于是「创作轨迹 → 候选审阅」实际恒空，而空态文案写着"跑一次整章改写后，产出的稿子会先放在这里"。
那是**承诺了没交付**。本轮补生产入口（`revision/candidateIntake`）后，必须真跑一遍才算数。

## 三、实机抓到并修掉的缺陷：成功提示跟着列表项一起消失

**现象**：第一轮应用成功后，面板变成"还没有待审阅的候选"，**一句结果都没有**。
作者无法判断到底应用成功了没有，只能去正文里数字数。

**原因**：结果提示（`note`）渲染在对应条目的 `<li>` 里，而应用成功后 `load()` 会把这条
从待审阅列表移走 —— 提示跟着条目一起消失。放弃同理。

**修法**：提示提到列表外面（面板内容区顶部），并留注释说明为什么不能挂在条目上。
第二轮实机确认修复：顶部显示 `已应用（新增 0 / 删去 4 / 改动 95）`，同时列表已空。

> 这类缺陷单测抓不到（渲染位置的语义），只能真点一次。

## 四、崩溃恢复实测（发布门槛 2 的"中断恢复"）

**做法**：不是模拟返回码，而是用 CDP `Page.crash` **真让渲染进程崩溃** ——
点「应用到正文」后 15ms 崩。

| 阶段 | 实测 |
|---|---|
| 崩后重开，候选状态 | **`上次中断`**（`status=applying`：意图已落盘、回执未写） |
| 是否谎报"已应用" | ❌ 没有 —— 状态如实是"上次中断" |
| 再点应用 | **`已应用（新增 0 / 删去 0 / 改动 106）`** |
| 正文是否半截 | ❌ 没有 —— 3550 → **3444**，整段替换 |
| 是否要人工核对（needs-reconcile） | ❌ 不用 —— 崩在"意图已写、正文未写"这一段，重开直接补写即可 |

**结论**：中断恢复在真机上按设计工作 —— 状态不谎报、正文不半截、重开后能继续。

**未命中的分支（如实标注）**：
- `resumed`（"上次已经写过，这次只补回了回执"）：需要崩在"正文已写、回执未写"的毫秒级窗口，本次 15ms 落在写盘之前。
- `needs-reconcile`（正文既非改前也非改后）：需要外部改动正文制造不一致。
这两个分支由单测覆盖（`candidateApply` 30 条 + `candidateRunner` 29 条），**未在真机复现，不写成"已验证"**。
