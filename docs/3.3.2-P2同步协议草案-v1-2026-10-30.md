# 3.3.2 · P2 同步协议草案 v1

编写日期：2026-10-30（香港时间）
依据：规划 R3 §6（协议与不丢稿）、§7（冲突与删除）＋ P0 盘点 §7–§11（T1/T2/T3/T5 结论）
性质：**草案**，未实现、未联调、未在真实服务器验证。写作目的是把 P0 查出来的三处硬约束（删除标记缺失、图片内嵌、旧 blob 写无版本）落成确定的字段，供 P2 实现。

---

## 1. 一句话模型

> 一次同步 = 把「一本作品」打成一个**不可变快照**（manifest + 内容对象），以**基线 revision** 做条件提交；服务端原子发布并回一个 revision；客户端只认与本次操作 ID 匹配的回执。

不做：实时协作、段落级合并、整库覆盖、跨账号共享。

---

## 2. 命名空间与身份

| 层 | 标识 | 生成方 | 备注 |
|---|---|---|---|
| 账号 | `accountId` | 服务端（注册时） | 客户端自报的账号一律不信 |
| 服务数据世代 | `dataEpoch` | 服务端 | 迁移/恢复即升；旧基线在旧世代全部失效（§8） |
| 作品（云端） | `cloudProjectId` | 服务端，客户端提供幂等键 | 与本地 `localProjectId` 靠绑定记录映射，不靠名称 |
| 版本 | `revision` | 服务端，单调递增 | 时间戳只用于展示 |
| 快照 | `snapshotId` = manifest 的 SHA-256 | 客户端计算 | 同内容同 id，可去重 |
| 操作 | `opId` | 客户端（安全随机 UUID） | 幂等键，服务端保留 ≥ 30 天 |

🔴 `localProjectId` 与 `cloudProjectId` 必须分开存：同一本作品在不同设备上本地 id 不同，靠绑定表关联；复制项目/U 盘克隆默认产生新身份（规划 §3.3）。

## 3. 快照结构

### 3.1 manifest（提交的唯一真源）

```jsonc
{
  "protocol": 1,
  "accountId": "acc_x",            // 服务端校验，忽略客户端填的值
  "cloudProjectId": "prj_y",
  "opId": "uuid-v4",
  "baseRevision": 42,              // 0 = 首次提交
  "createdAt": 1761800000000,      // 仅展示
  "project": { "name": "…", "genre": "…", "projectType": "full" },
  "counts": { "chapters": 300, "volumes": 3, "tableRows": 812, "cardRecords": 96 },
  "objects": [
    { "kind": "chapters",     "hash": "sha256:…", "bytes": 1834221, "records": 300 },
    { "kind": "volumes",      "hash": "sha256:…", "bytes": 2140,    "records": 3 },
    { "kind": "tableRows",    "hash": "sha256:…", "bytes": 912330,  "records": 812 },
    { "kind": "cardRecords",  "hash": "sha256:…", "bytes": 288100,  "records": 96 },
    { "kind": "formData",     "hash": "sha256:…", "bytes": 40211,   "records": 12 },
    { "kind": "settings",     "hash": "sha256:…", "bytes": 3120,    "records": 9 },
    { "kind": "dailyStats",   "hash": "sha256:…", "bytes": 5100,    "records": 120 },
    { "kind": "aiRuns",       "hash": "sha256:…", "bytes": 88012,   "records": 44 },
    { "kind": "tavernReports","hash": "sha256:…", "bytes": 22014,   "records": 6 },
    { "kind": "snapshots",    "hash": "sha256:…", "bytes": 640022,  "records": 18 }
  ],
  "assets": [                       // 图片走内容寻址（见 §4），与记录分开
    { "hash": "sha256:…", "bytes": 204800, "mime": "image/webp", "refs": 1 }
  ],
  "tombstones": [                   // 见 §5，这是 ProjectBundle 现在缺的东西
    { "kind": "chapters", "id": "ch_17", "deletedAt": 1761799000000 },
    { "kind": "tableRows", "id": "row_88", "deletedAt": 1761799100000 }
  ]
}
```

要点：

1. `objects` 是按 kind 分片的**内容哈希**，不是「整库 JSON 的哈希」—— 桌面与便携的整库不是同一集合（盘点 §10），不能拿整库做判据。
2. 每个 object 单独一个内容文件（可 gzip），单文件失败可单独重传。
3. `counts` 与 `records` 是给人看和做守恒断言的，不参与一致性判定（盘点/规划都明确：禁止只比记录总数）。
4. `project` 只带展示用字段，完整项目行在 `projects` object 里。

### 3.2 内容对象规范

| 项 | 规则 |
|---|---|
| 序列化 | 记录按主键字典序排序，字段按声明顺序，UTF-8，无多余空白 |
| 哈希 | `sha256:` 前缀 + 小写十六进制，对**压缩前**字节计算（压缩算法可换而哈希不变） |
| 分片粒度 | 一个 kind 一个对象；单对象 > 8 MiB 时按记录数二分（仍按 kind 标注） |
| 主键 | 与 `KEY_FIELD` 一致（`formData` = 剥过前缀的 `tabId`，`settings` = 剥过前缀的 `key`） |
| 禁止项 | 不含 `backups` / `backupPayloads` / `revisionPayloads` / `vecRows` / `kbDocs` / `kbBodies` / `worlds` / `tavern.*` |

🔴 前缀剥离必须与 `exportProject()` 完全一致，否则导入回来键对不上（盘点 §7.0）。

## 4. 图片：内容寻址，不内嵌（D8 采纳方案）

现状：立绘与图鉴图是记录里的 dataURL（盘点 §4）。直接内嵌会让典型含图项目达到 40 MiB 级，且「改一个字」要重传全部图片。

```
上传：记录里仍然保留 atlasImage / portrait 的元信息（mime/width/height/bytes），
     dataUrl 换成 assetRef = "sha256:…"；原 dataUrl 解码后作为独立对象上传。
下载：先取 manifest → 取对象 → 取缺失的 assets → 校验哈希 → 原子替换本地记录里的 assetRef 回 dataUrl。
```

约束：

- **本地数据格式不变**（仍是 dataURL），只在**同步载荷**里做引用化 —— 否则要动存储层与全部读取路径，风险远大于收益。
- 上传前 `assetRef` 由本地 dataURL 计算；下载后必须校验 `bytes` 与哈希，不符即视为附件损坏（X09）。
- 服务端对象按 `accountId` 隔离；哈希相同不跨账号复用（防存在性侧信道）。
- 首版不做图片增量压缩/转码，只做去重。

## 5. 删除：墓碑（D7 采纳方案）

`ProjectBundle` 目前**没有任何删除标记**（盘点 §7.1），整项目覆盖上传会让「B 端删的章在 A 端复活」。

规则：

1. 客户端在生成快照时，把**自上次成功提交以来**删除的记录写成 `tombstones`（kind + id + deletedAt）。
2. 服务端在发布新 revision 时把墓碑并入该项目的墓碑集（不是替换），保留 30 天。
3. 下载应用时：先按 `objects` 落记录，再按**当前有效墓碑集**删除本地对应记录；本地若有比墓碑更新的修改，进冲突（§7）。
4. 墓碑过期后（>30 天）：设备若其 `lastKnownRevision` 早于过期点，**拒绝直接应用**，要求全量重建（规划 §7 的「人工决定」）。
5. 章级 `trash` 不进快照（盘点 §7.1）：本机回收站保留，跨设备删除只认墓碑。

## 6. 提交与回执

### 6.1 服务端接口（草案）

| 方法 | 路径 | 作用 | 条件 |
|---|---|---|---|
| `POST` | `/api/v2/projects` | 绑定/创建云端作品（幂等：`localProjectId` + `opId`） | 登录 |
| `GET` | `/api/v2/projects` | 列出云端作品（名、revision、大小、更新时间） | 登录 |
| `GET` | `/api/v2/projects/:id/manifest?rev=` | 取 manifest（缺省最新） | 登录 + 归属校验 |
| `POST` | `/api/v2/projects/:id/objects` | 上传内容对象（先暂存） | 登录 + 归属 + 配额 |
| `POST` | `/api/v2/projects/:id/commit` | 条件提交，原子发布 | 登录 + `baseRevision` 匹配 |
| `GET` | `/api/v2/projects/:id/ops/:opId` | 查回执（超时后用） | 登录 |
| `DELETE` | `/api/v2/projects/:id` | 删除（写墓碑 + 进回收站 30 天） | 登录 + 显式确认 |

### 6.2 提交事务（服务端）

```
1. 鉴权 → 取 accountId（不信 body）
2. 校验 manifest：protocol 版本、对象齐备（全部 objects 已暂存且哈希对得上）、配额
3. 加**项目级锁**（跨进程：文件锁或 DB 行锁）
4. 在锁内比对 baseRevision == 当前 revision
   · 不等 ⇒ 409 + 当前 manifest 摘要（不求全量）
5. 原子写：revision+1、manifest 指针、对象引用计数、墓碑集、opId→revision 幂等记录（同一事务）
6. 提交事务 → 返回 { revision, snapshotId }
```

🔴 第 5 步必须是**一个事务**：单文件 rename 不等于跨文件事务（规划 §6.2 第 3 条明确要求取证）。

### 6.3 客户端回执判定

| 情况 | 处理 |
|---|---|
| 200 + `revision` | 核对 `opId`、`accountId`、`cloudProjectId`、本地快照代次 → 只确认匹配的那一代 |
| 超时/网络断 | **不判失败**：先用 `opId` 查回执；查不到再以同 `opId` 重试 |
| 409 基线不符 | 停止覆盖，拉远端 manifest + 共同基线，进冲突（§7） |
| 413 配额不足 | 暂停该项目同步，保留本地待同步与云端旧版本 |
| 401/403 | 停止重试，保留草稿并按账号隔离，提示重新登录 |

## 7. 冲突（首版一律人工）

触发：`409` 且本地有未提交修改；或下载应用前发现有本地草稿/在途写入。

产物：三个可恢复版本 —— 本地快照、云端快照、共同基线（能取到时）。界面展示来源设备、最近确认时间、差异章节/设定清单。

可选动作：保留云端 / 保留本地（先创建可恢复版本，再以当前 revision 条件提交）/ 另存为新作品 / 导出。

🔴 不做「本地优先」「时间优先」静默决胜；不做文本自动合并。

---

## 8. 旧路径门禁（数据世代）

盘点 §11 查明旧客户端有 4 条写路径，其中 blob 写/删**无版本保护**。门禁设计：

| 路径 | 门禁 |
|---|---|
| `PUT/POST /api/data` | 迁移完成后，`dataEpoch >= 2` 的账号一律 `409 { code: 'LEGACY_WRITE_BLOCKED' }` + 升级提示 |
| `PUT/POST /api/blob` | 同上；且旧 blob 与本协议对象**分目录存放**，避免新旧互相覆盖 |
| `DELETE /api/blob` | 同上；删除旧 blob 不得影响新对象引用计数 |
| `POST /api/auth/*` | 不拦登录，但登录后旧写路径仍被前三条挡住 |

旧客户端拿到 409 后必须能：只读打开 + 导出 + 看到升级提示（需旧版本配合；做不到就在服务端返回可读文案）。

⚠️ `dataEpoch` 一旦提升不可回退；回滚流程见规划 §8（先冻结写入、导出增量、验证逆向转换）。

## 9. 客户端状态机（与规划 §3.1 对齐）

```
未启用 → 本地已保存待上传 → 上传中 → 云端已确认(revision)
                              ↘ 待重试(退避) ↘ 冲突 ↘ 需要登录 ↘ 空间不足 ↘ 版本不兼容
```

- 「本地已保存」与「云端已确认」是两个独立事实，界面不得合并显示。
- 队列持久化在本地库（不进整库 JSON，单独立表），带 `accountId` + `serviceUrl` + `cloudProjectId` + `opId` + 基线 + 快照引用。
- 同项目串行、跨项目有限并发；多进程/多窗口用项目级锁（物理根锁，便携同一 U 盘同理）。

## 10. 错误码映射（不假设不存在的状态码）

| 客户端语义 | HTTP | code |
|---|---|---|
| 未登录/会话失效 | 401 | `SESSION_EXPIRED` |
| 无权限（非本人作品） | 403 | `FORBIDDEN` |
| 基线不符（冲突） | **409** | `BASELINE_MISMATCH` |
| 旧版写入被拒 | **409** | `LEGACY_WRITE_BLOCKED` |
| 配额不足 | **413** | `QUOTA_EXCEEDED`（现有实现已用 413） |
| 协议版本不支持 | 409 | `PROTOCOL_UNSUPPORTED` |
| 对象缺失/哈希不符 | 400 | `OBJECT_INVALID` |
| 需要前置条件（可选） | 428 | `PRECONDITION_REQUIRED` |

🔴 规划里提到「不能假设现有接口返回 412」—— 已核：现有实现用 **409 + ETag**，没有 412（盘点 §11）。

## 11. 必须验证后才能算数（P2 出口条件）

原型已跑（隔离目录 `.workbuddy/tmp/proto-p0-t6/`，Node v22.22.2，证据 `result.json`）。四条验证结果：

| 编号 | 验证项 | 结果 | 说明 |
|---|---|---|---|
| V1 | 两进程同时提交同一项目，只有一个成功 | ✅ 通过 | 两个子进程同基线 `0` 并发提交：1 个 `PUBLISHED`(rev 1)、1 个 `BASELINE_MISMATCH`(rev 1)，最终 revision=1 |
| V2 | 提交成功后、回执返回前断电 | ✅ 通过 | 子进程在状态发布后 SIGKILL；状态 revision=1；客户端以同 `opId` 重试得 `IDEMPOTENT_REPLAY` rev 1，**未产生 rev 2** |
| V3 | 同 opId 重放不重复发布 | ✅ 通过 | 同上，快照 id 一致 |
| V4 | 40 MiB 快照在 1.7 GB 服务器上的峰值内存 | ⚠️ **必须改设计** | 40.1 MiB 载荷 → RSS 峰值增量 **220.4 MiB（5.49×）**；10.1 MiB → 56.5 MiB（5.61×）。按 1.2 GB 安全余量算，**并发 5 个 40 MiB 上传即触顶** |
| V5 | 旧客户端在 `dataEpoch=2` 后所有写路径被拒 | ⏳ 未做（需服务端改造） | 门禁尚未实现，见 §8 |
| V6 | 墓碑应用后 A 端删的章不会在 B 端复活 | ⏳ 未做（需客户端状态机） | 见 §5 |

V4 的结论（必须写进实现）：

1. UI 层同时只允许**一个**项目在提交（全局串行），不要按项目并发就以为安全；
2. 服务端在 `/api/v2/.../objects` 上必须**流式落盘**，不能沿用 `readBody()` 的全量缓冲；
3. 若首版不做流式，则单对象上限必须压到 **8 MiB**（`MAX_BODY` 同理），并在超过时返回 413 而不是硬吃内存。

原型附带发现：失败尝试会在 `projects/<pid>/<rev>.json` 留下孤儿 manifest。因为 revision 指针在 `state.json`，孤儿不影响正确性；但建议把 manifest 文件名改成 `<snapshotId>.json`，避免重试时覆盖他人写入。

## 12. 未定项（本草案不替主人拍板）

1. 服务端存储实现（SQLite/Postgres vs 纯文件 + 锁）—— 决定 V1/V2 的可行边界。
2. 单对象分片阈值（暂定 8 MiB）需实测。
3. 对象是否 gzip、是否允许 zstd —— 影响哈希口径（本草案按「压缩前」算）。
4. 历史与回收站的 30 天是否与墓碑 30 天对齐。
5. 网页版是否复用同一 v2 接口（建议复用，但需按浏览器条件单独验证离线队列）。
