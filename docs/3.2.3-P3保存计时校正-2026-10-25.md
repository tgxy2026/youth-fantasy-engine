# 3.2.3 · P3：保存计时里的探针开销（计量 v5，2026-10-25 18:30）

> 承接 [P3 滚动口径校正](3.2.3-P3滚动口径校正-2026-10-25.md)。上一批把「large 保存 450ms」当作最大热点，
> 这轮先按承诺只做分段测量。结论又是同一类问题：**450ms 里大部分是探针自己的轮询**，不是产品保存。

## 1. 分段诊断（一次性脚本 `.workbuddy/tmp/save-split.cjs`，不入库）

large 夹具，页面内计时：输入一个字 → 点「保存全部」→ 等 IDB 事务提交 → 等界面「已保存」。

| 段 | 5 次实测 |
|---|---|
| 点保存 → **IDB 事务提交**（含结构化克隆） | 13.2 / 45.2 / 42.1 / 42.9 / 41.3 ms |
| 点保存 → 界面出现「已保存」 | 23.8 / 52.4 / 52.4 / 49.9 / 48.5 ms |
| 一次 `getAll('tableRows')`（1000 行 × 74 列） | **16.0 ms** |

而正式 `measure` 量到的 save P95 是 **450.2 ms**。差在哪：

- 旧轮询每 25ms 调一次 `readStores()` —— **开库 + `getAll(tableRows)` + `getAll(projects)` + 关库**，
  large 一次约 40ms，加上 25ms 的 sleep，命中前往往要跑 5~9 轮；
- 于是「产品 45ms 的保存」被量成「450ms」。

🔴 顺带记一笔：诊断脚本第一版直接给 textarea 赋 `value` 再 dispatch `input`，React 不认（受控组件），
表格一直显示「无未保存的改动」、连保存按钮都不出现。必须用**原生 setter**
（`Object.getOwnPropertyDescriptor(HTMLTextAreaElement.prototype,'value').set.call(el, v)`）再 dispatch。

## 2. 改了什么（计量 v5）

| 位置 | 改法 |
|---|---|
| save 的确认轮询 | 不再 `readStores()`，改成**按主键读单条**（`get('tableRows', id)`，约 2~5ms），间隔 15ms |
| 整表回读 | 保留，但只在**所有样本跑完后做一次**、且**不计时**；它继续作为持久化断言（`complete persisted records only contain intended change` + reload 回读） |
| 计量版本 | 4 → **5**（口径变化 ⇒ v4 基线不再可比，有意） |

## 3. v5 正式基线

单独跑（不与单测并发），游客真后端 + 生产构建 + 1600×950/DPR1/100% 缩放 + 护眼主题，
证据 `.workbuddy/tmp/table-performance-wxNB1r/`；每夹具 **69 / 69** 功能检查通过。

| 夹具 | 打开 P50/P95 | 输入 P95 | **保存 P50/P95** | 筛选 P95 | 清筛选 P95 | 滚动 P50/P95 |
|---|---|---|---|---|---|---|
| medium | 176.4 / 191.6 | 39.7 | **59.9 / 60.1** | 148.7 | 139.9 | 26.1 / 32.1 |
| large | 186.4 / 199.2 | 40.0 | **59.9 / 60.1** | 168.3 | 140.2 | 25.0 / 32.6 |

**七项绝对阈值全过**，每夹具 69/69。

## 4. 怎么读这组数字（别误读成「优化了 7 倍」）

- 产品的保存链路没改一行：13~45ms 本来就是这个水平；变的是**计量不再把探针开销算进去**。
- 保存样本现在几乎恒为 60ms，是**轮询粒度（15ms）与产品耗时叠加**的结果 ——
  分辨率约一个轮询间隔，不要拿它去比较 10ms 级的差异。
- 界面上作者真正看到的是「已保存」出现（~50ms），与 60ms 的差值就是最后一次轮询的等待。

## 5. 三次口径修正的共同教训

| 批 | 当时的数字 | 真实情况 | 根因 |
|---|---|---|---|
| v3→v4 | 滚动 113/205ms | 23.6/24.4ms | 步长不是真实滚轮量 + Playwright 往返 |
| v4→v5 | 保存 450ms | 60ms | 探针每轮 `getAll` 整表回读 |

⇒ 写性能指标时，必须把「**作者在等什么**」和「**探针自己在花什么**」分开；
凡是探针为了让断言成立而做的读取，都不该计入作者的等待时间，但**断言不能省**（改成事后做一次）。

## 7. 边界与下一步

- 保存计时仍含 Playwright 的点击开销（actionability 检查），只是被压到几十毫秒级；
  真机手感仍以「已保存」出现时间为准，未在实体设备上验。
- 真正还没解决的产品侧热点：**单行挂载 ≈5ms**（滚动每步新挂 1~3 行）、**打开 190ms**（16 行 × 74 列首次挂载）。
  这两个都需要降「单行成本」，方向是减少每行里控件初始化的工作量（不是行级订阅，已证伪）。
- 便携正式基线仍未采；P0 其余余项（冷启动、远端定位、tree/mixed 交互、A/B 交错、longbook、100 行批量保存）未做。
- 计量 v5 使 v4 基线（`SsoRuQ`）不再可比 —— 有意，历史数据只作并列对照。
