## 三、D7：同步层 `any` 收窄

### 3.1 实测规模比文档记的更大

文档记「52 处（`syncCore` 32 / `db` 12 / `syncTransport` 8）」；按**剥掉注释与字符串后**的
词元口径重数，实为 **112 处 / 9 个文件**（`syncCore` 69、`db/core` 16、`desktopCloudSync` 9、
`syncTransport` 8、`autoContinue` 4、`ai` 2、`CloudFileSyncBar` 2、`Sidebar` 1、`materialRef` 1）。
差异来自计数口径，**以本轮的实测口径为准**（它可复现，见闸的输出）。

### 3.2 手法：先把 `any` 收进**一处声明**，再逐个边界显式收窄

`syncCore.ts` 新增三个通用类型（`src/lib/syncCore.ts` 顶部）：

```ts
export type SyncRow    = Record<string, unknown>   // 一条已落库记录：同步层只按主键(id/key)比对搬运
export type SyncStores = Record<string, SyncRow[]> // store → 记录数组（快照/缓存/备份统一是它）
type   SyncPayload     = SyncStores & { __cloudBackup?: CloudBackup }
```

于是 `Record<string, any[]>`（26 处）一次性变成 `SyncStores`；读字段从此得 `unknown`，
**迫使调用点说清「我凭什么认为它是这个形状」** —— 这正是要的摩擦力。具体收窄手法：

| 场景 | 处理 | 理由 |
|---|---|---|
| `(x: any) => x[kf] === key` | 去掉标注（`x` 自动推出 `SyncRow`） | 比较 `unknown === unknown` 合法，不需要 `any` |
| `new Map<any, any>()` | `new Map<unknown, SyncRow>()` | 键是主键（运行时是字符串），值为记录 |
| `value: any`（`keyOf`/`put`） | `value: unknown` + 函数内 `as SyncRow` 断言 | `StoreOps` 的入参本就跨域，断言点集中在一处 |
| `(globalThis as any).crypto` ×7 | 抽到**叶子模块** `src/lib/webcrypto.ts` 的 `webcrypto()` | 见 §3.4 |
| `aesDecrypt(...): Promise<any>` | `Promise<SyncPayload>` | 解密出来的就是载荷本身 |
| `(string \| number)[]`（墓碑） | 放宽成 `readonly unknown[]` | 函数内部本来就做 `String(k)`，`unknown` 才是真实契约 |
| `as T[]` / `as T \| undefined`（`getAll` 等） | `as unknown as T[]` | **边界断言**：cache 里存的是各业务域记录，与 `StoreOps` 泛型签名对齐只能靠它 |

### 3.3 行为等价的**可证明性**（本轮最要紧的一条纪律）

类型标注在编译期被擦除 ⇒ **只改类型不可能改行为**。本轮把这句话做成了可执行证据：
用 esbuild 把改前/改后的文件都剥掉类型再逐行 diff，**剩下的差异就是真实运行时代码变化**。

`src/lib/db/core.ts`：剥类型后 **300 行 → 300 行，diff 为空** —— 纯类型改动，零运行时差异。

`src/lib/syncCore.ts`：剥类型后 657 → 665 行，**只有 6 处运行时差异，全部有意为之**：

| # | 差异 | 说明 |
|---|---|---|
| 1 | 新增 `function webcrypto()` | 新的取用器 |
| 2 | `(globalThis.crypto && globalThis.crypto.subtle)` → `globalThis.crypto?.subtle` | 语义完全等价 |
| 3–5 | `globalThis.crypto.subtle.X` → `webcrypto().subtle.X`（`deriveKey`/`encrypt`/`decrypt`） | 失败形态由 `TypeError` 变成明确的 `Error`（更好，且原路径本就不可达：调用点都由 `hasSubtle` 把守） |
| 6 | `put` 里多一个局部别名 `const rec = value` | 纯别名 |

`src/lib/syncTransport.ts`：仅 2 处（新增 import + `sha256Hex` 走 `webcrypto()`）。

### 3.4 顺手做对的两件事

- **抽出 `src/lib/webcrypto.ts`（叶子模块）**：`syncCore` 已经 import 了 `syncTransport`
  （用它的 `createIdleTransport`），若 `syncTransport` 反过来 import `syncCore` 取这个函数，
  就凑成 `syncCore ↔ syncTransport` 环。故按项目固有playbook「**抽出共享件到第三文件**」落地。
  闸已验证：`importCycles` 仍 **9 passed / 0 failed**。
- **把 `多余 export` 拉回原值**：`audit-dead.mjs` 报 `SyncPayload` / `CryptoApi` / `CryptoHost`
  进了「B. 多余 export」（外部 0 引用）。三者本就只在本文件内用 → **去掉 `export`**，
  清单从 230 **回到 227**。这条不能省：那个清单一旦失控，真正的死代码就再也看不出来了。

### 3.5 留下的存量（如实记账，不假装清零）

| 文件 | 剩余 | 为什么这轮不动 |

## 四、阶段 5：结构护栏闸（`tests/structureGates.test.ts`）

文档称这一步「**性价比最高**」，因为「项目 90 条红线已经证明踩过的坑会重踩，只有闸能防住」。
本闸纯静态、不 import 业务代码，故无 mock 依赖，毫秒级跑完。**六条规则**：

| # | 规则 | 判据 | 现状 |
|---|---|---|---|
| ① | 单文件行数 | 硬上限 **1200**（失败）／软上限 **800**（仅告警） | ✅ `src/lib/tavern/protocol.ts` 1449 等 4 个「鲸鱼」进冻结账本，**只准降不准升** |
| ② | 分层方向 | 真正的闸在 `importCycles`；本闸只钉住「新数据目录必须登记进 `NO_UI_DIRS`」 | ✅ 已登记 `src/lib/` + `src/data/` |
| ③-a | `src/data/**` 无运行时代码 | 不得有运行时 `import`（`import type` 允许） | ✅ 现仅 1 条 `import type` |
| ③-b | `src/lib/**` 无纯数据文件 | 无 `function`/`=>`/`class` 且 > 200 行 → 报错 | ✅ `seedData.ts` 有 12 处工厂函数，不误伤 |

### 4.1 两处「刻意不做过火」的判定

- **④ 的作用域只限 AI 链路。** 红线原文是「解析统一 `aiParse.ts`」，但它的语境是
  「把**模型返回的文本**变成结构化数据」。把加解密 / 传输解码 / 桌面 JSON 文件读取也一起禁掉是过头的
  —— `aiParse` 的「剥代码块 / 切最外层大括号」对它们没有意义。具名例外两条，都写了理由：
  `aiParse.ts`（它就是唯一合法出口）、`ai.ts`（SSE **行解析器**，解析的是传输信封不是模型正文）。
- **⑥ 用账本而不是全局禁 `any`。** 存量里有**真正无法静态描述**的边界（preload 桥 / Node `require` /
  动态 `StoreOps` 分发）。一次性清零不现实，还会逼出更差的写法（`as unknown as X` 满天飞）。
  账本把增长变成一次显式决定 —— 这就是摩擦力。

## 六、本轮踩到 / 复用的坑

- ⚠️ **两个工具并行写同一份临时文件会互相污染**：`typeonly-diff.mjs` 用固定的
  `typeonly-a.txt` / `typeonly-b.txt`，两条命令并行跑时后者读到前者的产物，
  于是 db/core 那次的 diff 输出的是 syncTransport 的结果（**差点据此下错结论**）。
  → 临时文件带 label，或串行跑。（与「同一消息多个 Edit 互相覆盖」同源：**共享中介必须串行**。）
- 🔴 **`Record<string, unknown>` 与 `interface` 的赋值关系**：`interface Foo` 没有隐式索引签名，
  故 `Foo` **不可**赋给 `Record<string, unknown>`；但 `SyncRow[]` ← `Foo[]` 是可行的
  （元素位置是协变，`Foo → unknown` 永远成立）。本轮的 `SyncStores` 恰好只在**数组元素**位置用它，
  所以能干净落地 —— 换一处用法就要重新推一遍。
- ✅ **「先量化、再动手」又一次是对的**：`webcrypto` 抽成叶子模块是**在动手前**先查了
  `syncCore → syncTransport` 这个既有方向才定的，否则会当场造出一个新的环。
