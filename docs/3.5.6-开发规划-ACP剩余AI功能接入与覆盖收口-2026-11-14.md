## 开发顺序与验收

灵感启发专项覆盖三处按钮：「灵感夹 → 融合为情节卡」「随机取名生成器 → AI 取名」「AI 辅助规划」。融合只提交作者选择的灵感与确认的参考资料，校验来源编号和卡片字段后走原画布写入；AI 取名保留类别、风格和候选复制；辅助规划验证多轮上下文、切项目、取消和资料附带范围。三处均须在未配置 API 模型时完成 ACP 正向验收。

1. 先接现有契约最稳定的手动任务。以整章改写、表格拆分、批量摘要、检查报告和手册问答覆盖纯文本、结构化、批量与证据四条链。
2. 接入画布、拆书和创意写作流水线，核验中断续跑时的阶段、项目和输入版本。用合成作品验多章、长文本、重复任务、额度不足、候选冲突及保存失败。3.6.0 的拆书与创意写作新产品流程仍由其版本规划负责。
3. 完成联网检索桥接、审核本地性验证，并检查 3.5.5 外部能力阻塞项。使用官方组件与假 Agent 分别验证；组件未提供能力时如实显示未支持原因和回退入口，由用户主动切换模式。
4. 复核每个可见入口的 ACP 状态、资料确认、结果去向和模式提示。对最终 Windows x64 安装候选复跑三模式、IPC 门禁、取消、崩溃、恢复、无系统 Node.js、覆盖升级和回退；同时核对 API、MCP、便携和网页。

当期 ACP 覆盖矩阵为每一项保留具体入口、任务标识、组件能力、证据及交付状态。任何新增 AI 调用入口须登记至当前可用、已排期、外部能力阻塞或模式专属之一。禁用原因应明确到入口或组件能力。

### 覆盖验收与阻塞判定

- 验收清单逐项记录入口或自动触发点、共用函数、后续子调用、版本、任务标识、数据来源和结果去向。通过零 API 配置的正向录制核对实际请求，并测试 API/MCP 切换、取消迟到、用户改稿、旧选项失效和跨项目结果。单测或文档勾选不作为官方组件实测证据。
- 两版收口时，所有能接入的现有 AI 功能须有同一候选的可用证据。外部能力阻塞须写明组件版本、所需能力、缺失证据、当前替代入口及恢复条件。耗时、拆分难度或尚未测试不能作为「明确无法支持」的依据，仍须列为开发或验收待办。
- 对现有 Antigravity 文本会话，真实向量与经证明的本地审稿分别有 3.5.5 和 3.5.6 的独立能力验收。不可用时标注具体限制，关键词降级、本地 API 审核或模式专属服务分别留有入口与提示。工具权限和三模式互斥继续验收。
