## P0 · 三模式上下文预算

前置修复已落地（`c0a2db4`）：酒馆 16 个调用点改走 `resolveTavernChatProvider`，ACP 分支直接返回 `provider: null`，不再读取 API 模型窗口或系统提示词；`checkTavernReady` 在 ACP 快照可用时直接就绪。剧情推演、自由对话与推演报告已在零 API 配置下通过假 Agent 的业务入口测试（`tests/tavernAcpChat.test.ts` 第 10 节）。下列按实际 ACP 模型配置窗口、长文本装配及 MCP 取材能力仍待实现。

| 模式 | 模型窗口由谁决定 | 3.5.6 预算职责 |
| --- | --- | --- |
| API | 云端由模型服务决定，引擎按模型配置估算；本地 Ollama 支持实际传入 `num_ctx`。 | 沿用每模型 `contextWindow`、请求词元估算、输出预留、酒馆和正文额度。保留用途路由、自动推荐与手调值。 |

### MCP · 由客户端决定取材量

- 先核对桌面随包 MCP、实时只读桥和便携桥。主 MCP 桥（`scripts/mcp/yfe-agent.mjs`）的部分列表已有 `offset` / `limit`（上限 100），单章读取返回完整正文；桌面只读桥（`scripts/agent-host/readonly-tools.mjs`）当前没有分页，列表一次性全量返回。保留旧工具的入参与响应语义；对长章节和大批设定提供可选范围读取，返回稳定位置、下一段游标和数据版本。跨多次调用拼接期间内容变更时提示重新读取，避免混合不同版本。
- 更新开发者规范，说明先用目录、摘要或搜索定位，再按章、段落或分页取材。提供单次返回的字符或字节目标、实际大小和后续读取位置，结合工具现有硬上限；外部客户端可以逐次调小或调大读取量。排序、授权和同一资料的分段边界由宿主确定。单次返回目标的默认值只适用于主动选用分段的请求。
- 客户端若知道所用模型及剩余上下文，可将其换算成读取目标。客户端身份、模型名称和调用方传入的数值均不作为权限依据。引擎不读取外部账号配置，也不从连接或握手推断模型容量。真实客户端验收记录实际模型与测试条件，从工具日志核对每次返回和续读位置。

### ACP · 按 Agent 与实际模型装配

1. **确定有效容量。** 先核对会话实际选中的模型标识，包括「使用 Agent 默认设置」解析后的模型。优先采用适配器可验证的会话能力，包括已提供的上下文窗口、单次输入和输出上限；其次使用可追溯到同一模型版本和服务的官方资料作为预算估算。设置页允许为当前 Agent 和模型手填窗口估算、发送预算上限及输出预留，显示自动值、手填值及本次生效值。手填值可以主动调小，在服务上限未知时可提高本地估算，但不能越过已确认的服务或宿主上限。缺少窗口依据时显示「实际窗口未知」，只有该模型没有可用数据且没有手填估算时才采用保守预算，并说明兜底来源。以上均为实现目标而非现状：会话选项目前只有模型与推理档位两个下拉（运行方式 `runAs` 另有独立入口），`acp:configure` 白名单只有 `model` / `thinking` / `runAs`，`acp-client.mjs` 也没有窗口或预算字段。
2. **隔离配置与冻结请求。** 以适配器和实际模型标识保存预算配置；服务或账号能影响模型标识、额度时再按可安全区分的作用域隔离。只有可验证的推理档位差异才影响预留。模型、账号或组件变动后重新核对有效容量，旧请求保留已确认的资料清单和预算快照，仍按现有 ACP 代次、项目与草稿规则拒绝过期发送或采纳。无法识别当前默认模型时，单独显示「默认模型未识别」，不套用上次选中模型的配置。
3. **统一算当前请求，按任务分配。** 复用 `requestBudget.ts` 的估算与资料清单，预算以实际打包后的提示词为准，计入系统说明、输出格式、当前指令、设定、正文和历史，并预留回复、安全余量及可估算的 Agent 开销。词元估计、字符数、UTF-8 字节数分开计算。正文续写与审校优先保留当前指令、选区或正文锚点、已确认的关键设定，按相关性扩展摘要和前文；酒馆按角色、固定世界书、动态词条、当前回合和对话历史分配，并计入数值结算等子调用；批量和长结构化任务按单章、场景或可校验的结构边界分配，分批保留进度及合并规则。用户继续可收紧任务资料范围，预算变大时只扩展已选资料的装配量。当前 `requestBudget.ts` 是按 API provider 的 `window` 装配的通用实现（`planRequestBudget` / `buildMaterialManifest` / `describeBudget` 可直接复用），尚无任何 ACP 专用预算装配。
4. **打通正文与酒馆的容量来源。** 正文手动续写当前按 `effectiveWindowOf(provider)` 取窗口：ACP 路径 `provider` 为 `null`，落到 `src/lib/ai/modelCapacity.ts` 的 32K 兜底（`FALLBACK_WINDOW = 32768`），API 路径取真实模型窗口；正文基础资料额度仍走 `writerBudgetFor('jiewenji-continue')`，诊断等入口按 kind 直接取共享额度。酒馆侧的前置修复已于 3.5.5 落地：16 处注入点改走 `resolveTavernChatProvider`，ACP 分支不再执行 `resolveTavernProvider`，零 API 配置不会在调用 Agent 前报错，已有 API 模型配置也不再影响世界书额度（`src/lib/tavern/quotas.ts` 对非数字窗口统一按 32K 固定档）。因此 3.5.6 要做的是统一容量来源，而不是再清理残留的 API 读取：让正文续写、酒馆主回复与子调用都读取当前模式下所选 Agent 与实际模型的有效预算，兼容既有手调资料额度，保留酒馆控制面板、会话的手调上限、记忆和筛选规则；就绪状态、界面额度和实际发送使用同一套解析结果。
5. **长上下文受限时有可用路径。** 运行层目前有 256 KiB 输入（`scripts/agent-host/acp-runtime.mjs`）、512 KiB 文本输出、1 MiB 单帧、30 秒请求超时和 180 秒生成等待（`scripts/agent-host/acp-client.mjs`）。3.5.5 发布版另引入常驻宿主与空闲 10 分钟回收（`LIVE_IDLE_MS`）、传输报废重建判据 `isFailed()`，以及**仅限编辑器伴写**的会话池：`reuseKey` 按项目 + 章节拼接，同一 key 最多复用 `POOL_MAX_USES = 6` 次，其余任务仍是每任务新建独立会话。先记录单次请求实际受哪项约束。优先按资料边界分批带入，提供可追踪的摘要、证据引用与跨批合并。若评估提高传输上限，按适配器和组件版本实测消息大小、稳定性、内存和取消后再启用。跨轮依赖 Agent 记忆仍须先验证会话复用与历史容量，且只能限定在上述有界会话池，不得推广到跨任务、跨模型或跨账号；可识别的超限明确报出裁剪或拆批选项，发给 Agent 的范围扩大后按现有授权重新确认；截断或未完整结束的输出不进入采纳与落库。

## 开发顺序与验收

灵感启发专项覆盖三处按钮：「灵感夹 → 融合为情节卡」「随机取名生成器 → AI 取名」「AI 辅助规划」。融合只提交作者选择的灵感与确认的参考资料，校验来源编号和卡片字段后走原画布写入；AI 取名保留类别、风格和候选复制；辅助规划验证多轮上下文、切项目、取消和资料附带范围。三处均须在未配置 API 模型时完成 ACP 正向验收。

1. 先落地上下文专项；酒馆残留的 API 模型依赖已由 3.5.5 的 `c0a2db4` 修复，专项内改为复验该修复并统一正文／酒馆的容量来源。用正文续写、酒馆主回复与子调用验证 ACP 预算，用 MCP 长章节验证分段读取。随后以整章改写、表格拆分、批量摘要、检查报告和手册问答覆盖纯文本、结构化、批量与证据四条链。
2. 接入画布、拆书和创意写作流水线，核验中断续跑时的阶段、项目和输入版本。用合成作品验多章、长文本、重复任务、额度不足、候选冲突及保存失败。边界：3.5.6 只把**现有**一键拆书与创意写作入口接到 ACP 并做覆盖收口；[3.6.0 规划](3.6.0-开发规划-拆书分析与创意写作闭环-2026-11-13.md) 的六个工作包（分析卡、创作参考、审读记录、章节保存恢复、剧情候选等）仍由其定义与验收，且 A–F 首先走现有 API 任务路径，ACP／MCP 须在结构化契约、权限与真实验证完成后单独接线，不因 3.5.6 提前计入。
3. 完成联网检索桥接、审核本地性验证，并检查 3.5.5 外部能力阻塞项（真实向量接口、Windows 隔离方式安装实测、ACP 协议异常样本归因）。使用官方组件与假 Agent 分别验证；组件未提供能力时如实显示未支持原因和回退入口，由用户主动切换模式。
4. 复核每个可见入口的 ACP 状态、资料确认、结果去向和模式提示。对最终 Windows x64 安装候选复跑三模式、IPC 门禁、取消、崩溃、恢复、无系统 Node.js、覆盖升级和回退；同时核对 API、MCP、便携和网页。验收记录沿用 3.5.5 的安装包指纹与 `runAs` 运行方式记账口径。

当期 ACP 覆盖矩阵以本文「功能归属矩阵」为索引，逐项在验收清单登记具体入口、任务标识、组件能力、证据及交付状态（条目级记录含共用函数、后续子调用、版本、数据来源与结果去向），不以文档勾选代替实测证据。任务标识以 `acpBridge.ts` 与桌面 IPC 白名单为准，新增标识须同步两处。任何新增 AI 调用入口须登记至当前可用、已排期、外部能力阻塞或模式专属之一。禁用原因应明确到入口或组件能力。

### 覆盖验收与阻塞判定

- 验收清单逐项记录入口或自动触发点、共用函数、后续子调用、版本、任务标识、数据来源和结果去向。通过零 API 配置的正向录制核对实际请求，并测试 API/MCP 切换、取消迟到、用户改稿、旧选项失效和跨项目结果。单测或文档勾选不作为官方组件实测证据。
- 3.5.5 / 3.5.6 两版收口时，所有能接入的现有 AI 功能须有同一候选的可用证据。外部能力阻塞须写明组件版本、所需能力、缺失证据、当前替代入口及恢复条件。耗时、拆分难度或尚未测试不能作为「明确无法支持」的依据，仍须列为开发或验收待办。
- 对现有 Antigravity 文本会话，真实向量与经证明的本地审稿分别有 3.5.5 和 3.5.6 的独立能力验收。3.5.5 侧已交付能力探测与关键词降级，正式向量接口仍无证据，按外部能力阻塞记账；3.5.6 继续条件验证。不可用时标注具体限制，关键词降级、本地 API 审核或模式专属服务分别留有入口与提示。工具权限和三模式互斥继续验收。
