## 〇、先立规矩：两个模式必须分开说

酒馆模式是**两条相对独立的线**，数据归属、记忆结构、上下文构建全都不一样。
任何规划都必须分别标注「剧情模式」与「自由对话」，绝不能一句「酒馆」带过。

| 维度 | 剧情模式（`tavern-plot`） | 自由对话（`tavern-free`） |
|---|---|---|
| 类型 | `TavernSession`（types.ts:146） | `FreeSession`（types.ts:411） |
| 引擎入口 | `runPlotTurn`（engine.ts:296） | `runFreeTurn`（engine.ts:719） |
| **数据归属** | **随当前小说项目**（项目级 `settingsKV`） | **全局**（`getMeta`，不绑项目） |
| 叙事锚点 | 有（`anchorChapterId`，锁定到某一章） | **无** |
| 记忆 | 会话级单份 `session.memory?: string`（六栏文本） | **按角色分条**（`getMemory(charId)`，`FreeMemory`） |
| 上下文构建 | ✅ `buildProjectContext()`（**含语义召回**） | ❌ **不用**项目上下文，纯角色卡 + 故事 + 剧本 |
| 角色来源 | `cast: TavernCast[]`（引用项目角色表） | `charIds: string[]`（引用全局角色卡 `FreeCharacter`） |
| 世界观来源 | 项目资料 + `tavern.world` | `TavernStory`（故事层，全局） |
| 检查点/分支 | ✅ 已有（`checkpoints`/`branchSession`） | ❌ 无 |
| 变量 | 无（用会话记忆里的关系状态） | ✅ `vars`（5 项，每轮自动刷新） |
| 收尾 | 无 | ✅ `runRoundEnd`（三笔事务） |

**两条推论（决定了整份规划的形状）**：

1. 剧情模式**已经站在项目数据之上**，所以「记忆/召回」类能力它多半已经享用；
   它真正缺的是**世界书的精细触发**。
2. 自由对话是**全局玩法模板**，拿不到项目上下文，所以「向量召回」对它要**新搭一条链路**
   （不是改造现有 `aiContext` 调用），但**底层的 `semantic/*` 模块完全可以复用**。

#### 差距（对照 ST World Info）

| ST 能力 | 咱们现状 | 差距性质 |
|---|---|---|
| 每条目**独立关键词** | 只能整份一把关键词 | 数据结构要扩 |
| **递归激活**（A 命中后触发 B） | 无 | 逻辑要新写 |
| **概率触发**（触发%） | 无 | 字段要扩 |
| **插入位置**（角色定义前/后、@深度） | 只有固定层位 | 逻辑要扩 |
| **可选过滤器**（AND ANY / NOT ANY） | 无 | 逻辑要扩 |
| **包含组**（同组互斥随机） | 无 | 字段要扩 |
| **实时可见「哪些条目被激活」** | 无 | 界面要扩 |

#### 改造方案（**不新建模块，全部落在 `world.ts`**）

**第 1 步 · 数据结构扩字段（向后兼容）**

```ts
// world.ts —— WorldSection 扩字段，全部可选，老数据原样可读
export type WorldSection = {
  id: string
  title: string
  body: string
  // ↓↓↓ 新增（全部可选，缺省 = 维持旧行为）
  keys?: string[]        // 该条目自己的关键词；为空 = 跟随整份 keywords
  prob?: number          // 触发概率 0-100，缺省 100
  order?: number         // 插入排序，值大者更靠后（更靠近对话）
  recursive?: boolean    // 本条命中后，是否允许再触发其他条目（默认 true）
}
```
> 🔴 **不新增顶层字段**，只在 `sections[]` 的元素里加可选属性 —— 老库读进来 `keys` 是
> `undefined`，`shouldInjectWorld` 行为与现在完全一致（等价性红线）。

**第 2 步 · 把「整份判定」改成「逐条判定」**

- 保留 `shouldInjectWorld`（对外契约不变，仍是「整份开会话层的闸」）。
- 新增 `pickSections(w, haystack, deps)`：逐条判 `keys`/`prob`，返回命中的 `WorldSection[]`。
- 新增 `renderPicked(sections, maxChars)`：按 `order` 排序后拼接，超限按 `order` **从小到大**丢。
- 递归：`pickSections` 内部跑**最多 2 轮**（第一轮直接命中，第二轮用「第一轮命中的正文」再扫一遍），
  用 `visited: Set<id>` 防环。**上限 2 轮是硬约束**，否则会像 ST 那样偶发失控。
- 正文里「哪些事项已经说完」的纪律照旧走 `authorBlock()`。

**第 3 步 · 调用点改造（两模式共改）**

- `engine.ts:150`：`shouldInjectWorld(...) ? worldToText(...)` 换成
  `const picked = pickSections(...); const worldText = renderPicked(picked)`。
- 自由模式当前**没有**世界书注入 —— 但 `story.ts` 提供了故事层设定。
  **本项只在剧情模式生效**；自由模式是否也要世界书，见下方「开放问题」。

**第 4 步 · 界面改造（`TavernWorld.tsx` 就地扩，不新页签）**

- 每个 `section` 卡片里加：关键词输入、概率滑杆、排序数字、递归开关（折叠在「高级」里）。
- 预览区（`TavernWorld.tsx:298` 已有 `worldToText(w)` 预览）改为**显示当前命中哪些条目**，
  就地复用现有预览块，不新开面板。

#### 风险

| 风险 | 处置 |
|---|---|
| 递归失控 → 注入量爆炸 | 硬限 2 轮 + `WORLD_MAX_CHARS` 总量闸 + `visited` 防环 |
| 老数据行为漂移 | 全部字段可选 + 缺省即旧行为 + 单测跑「无新字段 == 旧结果」等价断言 |
| 逐条判定性能 | `sections` 上限本就 3–6 节，无性能问题 |

#### 验证

- 单测：`tests/tavernWorld.test.ts`（若不存在则新建测试文件，**这是测试不是功能**）
  - 无新字段 ⇒ 注入结果与旧实现逐字一致（等价性）
  - 递归 A→B 命中、A→B→A 不死循环
  - `prob=0` 从不注入、`prob=100` 必注入
- 实机：`novel-studio-ui-livecheck` 走「背景设定」页，改关键词后看预览变化

**自由对话要新增的只是一条「查询文本从哪来」的接线**：

1. **扩 `VecKind`**：`store.ts:22` 加 `'tavern'`（对话消息类）。
   向量库隔离性照旧（`novel-studio-vec` 独立 IDB，不进整库 JSON）。
2. **给自由会话建索引**：复用 `indexOneDoc`，把已完成会话的 assistant 消息切块入库。
   - 触发点挂在 `saveFreeSession` 之后（**不 await**，与 `saveChapterWithAi` 的既有做法一致）。
   - 通过控制面板开关控制（默认关，与语义检索既有默认一致）。
3. **查询文本**：自由模式没有 `focusChapterId`，用**最近 N 条消息**拼查询串
   （`keywordHaystackMessages` 已有同款取材口径，直接复用同一函数）。
4. **注入点**：`runFreeTurn` 组装 system 时，在记忆层之后加一段〖相关对话召回〗。
   - 走 `buildSemanticRecallBlock` 的**同构包装**：新写一个 `tavernRecallBlock`，
     但内部仍调 `recallRelevant` —— **不重写检索**，只写「查询从哪来、结果怎么渲染」。
5. **S/D 过滤**：`recallRelevant` 已支持 `hideSecretRows`，自由模式传 `true`（角色视角）。

> 🔴 **不做的**：不给自由模式的「记忆六栏」上加向量 —— 六栏是**结构化**记忆，
> 已经有 `summarize.ts` 的总结式压缩，再叠一层语义召回是重复。只召回**原始对话消息**。

| 风险 | 处置 |
|---|---|
| 自由模式是全局的 ⇒ 索引库如何分区？ | 按 `sessionId` 作为 `refId`，跨项目天然无冲突（本来就是全局） |

> ⚠️ **注意**：这原本是**老大 2026-09-14 明确决定的**「不做多候选」。本轮要改变这条既定决策，
> 需老大重新拍板（见「开放问题」）。

#### 改造方案（**扩字段 + 扩 MessageOps，不新建组件**）

1. **`TavernMessage` 加两个字段（可选）**：
   ```ts
   /** 本条的多个候选文本（含当前选中那份）。长度 ≤1 时界面不显示翻页 */
   variants?: string[]
   /** 当前选中的候选下标；缺省 0 */
   variantIdx?: number
   ```
2. **重说改为「生成并追加候选」**：
   - 现状：`reroll()` 调 `runPlotTurn(session, null)` ⇒ 新回复**替换**旧的那条。
   - 改后：拿回新文本后 `variants.push(newText)`，`variantIdx = variants.length - 1`，`content` 同步。
   - 保留原 `reroll` 语义作为「重新生成一个候选」，**不破坏既有调用**。
3. **翻页回归**：`MessageOps` 加 `onPrevVariant / onNextVariant / variantCount / variantIdx`。
   - `TavernMessageBody` 工具条里，`canReroll` 那一行的左侧加 `‹ 2/3 ›` 计数控件。
   - **两模式共用同一组件**，所以剧情模式与自由对话**同时获得 swipe**，无需分别改。
4. **与记忆/水位线的交互**（🔴 关键）：
   - `store.rewindAfterReroll` 已处理「水位线指向被替换消息」的情形。
   - 改成候选后，**切换候选不等于替换消息 id**，所以水位线不用动 —— 但要重算
     `session.memory`（因为选中候选变了，已总结内容需重判）。**处置：切换候选时若水位线 ≤ 该条，清记忆**。
   - 这条规则必须写进 `store.ts` 的注释与单测。

#### 风险

| 风险 | 处置 |
|---|---|
| 候选翻页时模型上下文变乱 | 只有**未被总结进记忆**的候选可切换；已总结的清记忆（同 reroll 逻辑） |
| 存储膨胀 | 每消息候选上限 3–5 个；候选只存文本，不存元数据 |
| 老数据 | 两字段可选，`variants` 缺省 ⇒ 按单候选渲染，与现在完全一致 |

#### 验证

- 单测：`variants` 往返、切换候选后 `content` 同步、清记忆规则
- 实机：生成 → 重说 → 翻页三条候选，确认正文与记忆都跟着变

#### 改造方案（**复用现有 Canvas 管线，只补 chunk 读写**）

ST 的 v2 卡是把 JSON 塞进 PNG 的 `tEXt` chunk（关键字 `chara`，base64）。读写各一个函数即可：

1. **读**：`pngCardToJson(arrayBuffer)` —— 解析 PNG chunk 链，找到 `tEXt`/`iTXt` 且 keyword
   为 `chara`/`ccv3` 的块，base64 解码 → 现有 `parseCardFile` 复用（**导入口径不变**）。
2. **写**：`jsonToPngCard(json, avatarPngBytes)` —— 先用 Canvas 把现有 `avatar`（dataURL）
   画成 PNG（`canvas.toBlob('image/png')`，**复用已有 Canvas 能力，不引库**），
   再在 chunk 链里插入 `tEXt` 块。
3. **界面**：`TavernCardList.tsx` 现有三个按钮旁**再加两个**（「导入 PNG 卡」「导出 PNG 卡」）——
   **不加页签、不加弹窗**，就是两个按钮。

  云端走各家 REST；**差异全部收敛在 adapter 层**，上层调用点一份。
- **ComfyUI 工作流占位符**（ST 实测）：`%prompt% %negative_prompt% %model% %sampler% %steps%`
  `%scale% %width% %height% %seed% %char_avatar% %user_avatar%` —— 工作流 JSON 里没写的占位符，ST 就控制不了那项。
- **生成模式**（ST 共 12 种，可先取子集）：手动自由输入 / 消息配图 / 场景描述 / 角色立绘 / 面部特写 / 背景。
- **默认关闭**：未配置 source 时整段不出现（与知识库挂载同一口径）。

### 5.2 ST 群聊（Group Chat）机制对照 —— 「人多会不会让 AI 弄不清」（2026-10-05 追加调研）

主人问：ST 支持创建群聊，我们「开始会话前选择多个角色」也是同类功能，**ST 是怎么处理多角色混乱的**？
以下是读 ST 官方文档 + 源码（`public/scripts/group-chats.js`）得到的事实，以及本项目的对照。

#### ST 的五个机制

| 机制 | ST 的做法 | 我们的对应 |
|---|---|---|
| **生成模式**（**最关键**） | `SWAP`（默认）：**每轮只把「当前说话者」的角色卡放进上下文**；`APPEND`/`APPEND_DISABLED`（= Join）：把所有成员的卡合并成一份 | ❌ 我们**全员卡注入** —— 对应 ST 的 Join |
| **激活策略** | 4 种：Natural（按语境）/ List（轮流）/ Manual（手选）/ Pooled（随机） | ✅ 剧情＝按语境（Natural）；自由＝**轮换 autoSpeaker**（List，还支持点头像手选） |
| **话痨度** | `Talkativeness` 0–100%，默认 50%，控制「没被点名时开口的概率」 | ✅ 已有：`TALK_BANDS` + `talkativityOf`，写进 `buildMultiCharRule` 的「发言分量」 |
| **静音** | `muted` 成员可临时排除，不参与生成 | ✅ 已有：`silent` 角色（在场不出声）+ 运行时静音 |
| **强制发言** | `Force Talk` 可指定某角色开口 | ✅ 已有：「用户点名某个角色时，那个角色必须接话」 |

#### 🔴 关键结论：我们的架构**应该**走 Join，不是 SWAP

ST 官方文档对 Join 的警告是「角色会对自己困惑、人格融合」—— 那是因为 **ST 的模型每轮只演一个人**，
把别人的卡塞进去，等于往一个「单角色演员」脑子里灌别人的设定。

而本项目的多人同场是「**AI 分饰全部、一次只让一个说话**」（`buildMultiCharRule`），
模型本来就需要认识所有人 ⇒ **Join 才是对的**，代价是人数**线性吃上下文**。

#### 本轮据此做的改动（已实施）

上限从 3 提到 **`MAX_AI_CAST = 6`**，并把散落三处的数字抽成**单一真源**（`lib/tavern/types.ts`）：

| 位置 | 原值 | 现值 |
|---|---|---|
| 剧情 `TavernPlotSetup` 的 `MAX_SLOTS` / `MAX_AI_ROLES` | 4 / 3 | `MAX_CAST_SLOTS`(8) / `MAX_AI_CAST`(6) |
| 自由 `TavernFreeSetup` 的 `MAX_SLOTS` | 3 | `MAX_CAST_SLOTS`(8) |
| `store.planFreeSessionCast` 的 `slice(0, 3)` | 3 | `MAX_AI_CAST`(6) |

🔴 **为什么必须抽常量**：三处各写一个数字时，改一处漏一处会**静默丢角色** ——
自由侧原先界面允许 3 个、store 也截 3 个「恰好一致」；一旦只改界面不改 store，
就会出现「选了 5 个只存 3 个，界面还显示 5 个」。

**给作者的实用建议（写进界面文案）**：用不上的角色挂到「**在场不出声**」——
Ta 依然在场、可被提到、记忆照算，只是不占发言，也就不吃 AI 名额。
