# 3.2.0 · 发布门槛 §13.2 容量实测：500 章 / 百万字 / 200 载荷（2026-10-21）

> 依据：方案 §13.2「500 章/百万字量级、200 个候选载荷 → 列表惰性加载、内存、首屏与保存延迟；数据读取和渲染分别测量」。
> 🔴 与 `docs/3.2.0-L4-容量基准-2026-10-21.md` 的「1000 条 × 60 字段表格」**不是同一件事**（那个是自设更高标准，不构成发布门槛）。
> 脚本：`.workbuddy/tools/bench-release-500ch.cjs`（本机，不入库）｜原始数据 `.workbuddy/tmp/release-capacity-500ch.json`

## 一、测法

| 项 | 口径 |
|---|---|
| 应用 | 真 dev server（Vite `http://localhost:5199/`），不是构建产物 |
| 浏览器 | Edge（headless，`--disable-gpu --enable-precise-memory-info`），viewport 1600×950 |
| 隔离 | `browser.newContext()` 的**独立 IndexedDB**；示范项目里种数据，**不碰主人真实书库** |
| 数据 | 500 章 × 2000 字 = **1,015,000 字符（100 万字）**；**200 条** `revisionPayloads`（kind=report） |
| 卷 | 新建的示范项目自带 0 卷 ⇒ 自动建「第一卷 容量基准」并挂载（否则章节成孤儿，界面不显示） |
| 建数据成本 | 写 500 章 **19ms**、写 200 载荷 **10ms** |

## 二、结果

| 指标 | 实测 | 判定 |
|---|---|---|
| IDB 读全部 500 章（含 100 万字正文） | **8–11 ms** | ✅ 读取不是瓶颈 |
| 首屏：刷新 → 回项目列表 → 点开项目 → 工作面板可见 | **1.85 s** | ✅ 可接受 |
| 「正文编辑」页（500 章侧栏 + 编辑器）打开 | **264 ms** | ✅ 很快 —— 章节列表**有虚拟化**，只渲染可见行 |
| JS 堆（500 章 + 200 载荷） | **70 MB** | ✅ 合理 |
| 单章写盘（IDB put） | **1 ms** | ✅ |
| 切到第 250 章 | 未量到 | ⚪ 方法问题：列表虚拟化，第 250 章不在 DOM 里，需先滚动定位（不是缺陷） |

**结论：§13.2 的容量门槛（500 章/百万字/200 载荷）达标。**
章节列表的虚拟化是它与「1000×60 表格」的关键差别 —— 后者没有虚拟化才会 17 秒。

## 三、踩点（下一端别重复）

1. **「章节总表」不是正文列表**：它聚合的是「各卷章节台账」（`tableRows` 里的章节记录表），
   读 `chapters` 正文库的那个页签叫 **「正文编辑」**（侧栏里"正文写作"是**分组标题**，不是页签）。
2. **判据要查 `document.body.innerText`**：章节列表不在 `<aside>` 里，查 aside 会一直等不到、误判成"渲染不出来"
   （第一版因此白等了 90–120 秒）。
3. **Playwright 的 `waitForFunction(fn, arg, options)`**：`{ timeout }` 必须放**第三个参数**；
   放第二个会被当成 `arg`，超时仍是默认 30s（我因此连错两次）。
4. **刷新后应用回到项目列表**（设计如此）：要先点「打开项目」再测页内指标。
5. **备份提醒弹窗会遮住页面**（"稍后再说"）：进页签前先关，否则截图和判据都被挡。
6. 新建示范项目**自带 0 卷**：种章节必须自己建卷并挂 `volumeId`，否则章节是孤儿、界面不显示。
7. 章节 `status` 是**中文枚举**（'草稿'/'完稿'…），写 `'draft'` 类型不符。
