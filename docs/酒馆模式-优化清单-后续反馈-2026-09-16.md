## 二、逐条明细

### #5　回合结算时文字先显→消失→重算→再显；希望结算全程后台化
- **情况描述**：AI 回复后，文字先出来；随后文字消失、进入本场数值结算（好感/信任等刷新），结算跑完文字才重新出现。希望改成——状态结算**不影响文字回复**：AI 做状态运算/处理时全程在后台跑，只把结果输出到对应位置（右栏数值面板），文字回复保持常驻、不闪、不丢。
- **归类**：酒馆模式 · 自由对话 · 回合结算 UX / 前后台分离
- **建议优先级**：P1（"文字消失"易被误认成消息丢失，观感上是 bug）
- **状态**：待修复
- **待核实 / 处理方向（占位、不展开）**：文字为何消失需查——可能结算期间 `session` 被覆盖 / `streamText` 被清空，或 `refreshSessionVars` 是 await 阻塞、返回的新会话重渲染导致正文短暂消失。改法方向：把数值刷新改为**不阻塞正文**——后台 fire-and-forget 或并行，结果落库后只增量更新右栏、不动 `messages`。

### #6（更新）　信任/精神会变但不稳定；需说清影响因素与提示词判定
- **情况描述**：实测几轮后，信任和精神**突然变化了**——说明给 AI 的提示词确实能起作用，只是**触发不稳定 / 判定条件不明**。你要求后续说清：这两项数值各自的**影响因素**是什么、提示词**如何教 AI 判断**它们的变化。（地点部分按你先前意见不修——只认客观描述里的地点，避免对话干扰误判。）
- **归类**：酒馆模式 · 自由对话 · 本场数值（信任/精神）· 抽取准确性 / 提示词
- **建议优先级**：P1（你反复提及，需给出可解释的判定逻辑）
- **状态**：待核实
- **待核实 / 处理方向（占位、不展开）**：
  - `VAR_DEFS` 中 trust/spirit 的 kind 与抽取规则；`buildVarExtractSystem` 是否给足判定依据；模型对这两项的增量判定是否过保守（±maxStep 夹取后归零）。
  - 解析 / 写入路径是否对这两项有偏向（如只认好感类关键词）。
  - 落地时需在文档/提示词注释里**显式写明信任、精神各自的触发因素**，便于你审阅。

### #7　楚楠×苏念对话"指节泛白"类动作描写高频复现；需查是否角色卡设定导致
- **情况描述**：用楚楠角色与苏念对话时，描述人物动作细节的文本里反复出现"指节因为用力而微微泛白"这类描写。你**不是禁止**这种描写，而是觉得出现频率偏高、让人出戏；希望核实——是不是楚楠（或苏念）的角色卡里有对应设定，导致 AI 把"这件事"当成标签反复拿出来说。
- **归类**：酒馆模式 · 自由对话 · 角色卡设定副作用 / 描写重复
- **建议优先级**：P2
- **状态**：待核实
- **待核实 / 处理方向（占位、不展开）**：
  - 查楚楠角色卡 **description / 示例对话 / 标签**里是否有"指节泛白、用力、紧张、手"等字样——这类"高频+具体身体部位描写"往往是卡内 sample 或设定把某个细节写死，模型当成恒定特征反复发作。
  - 对比：用**其他角色**对话时是否也出现同类描写？若只有楚楠触发，基本坐实是楚楠卡问题；若通用，需查全局系统提示。
  - 本步只定位成因、不动卡；确认后归入"角色卡调优"单独处理。

### #9　角色卡补充"喜好/爱好"设定点（2.2 内核，"性格"下、"在乎什么"上）
- **情况描述**：你发现现有角色卡 schema 没有覆盖"人物的喜好或爱好"这个重要设定点。后续需要加进去——落点明确：放在 **2.2 内核** 下面，字段层级为 **「性格」之后、「在乎什么」之前**（即 性格 → 喜好/爱好 → 在乎什么 的排序）。
- **归类**：酒馆模式 · 角色卡 schema 扩展 / 设定完善（功能需求，非 bug）
- **建议优先级**：P2
- **状态**：待实施
- **待核实 / 处理方向（占位、不展开）**：
  - "2.2 内核"具体指哪一层（角色卡数据结构的字段分区？还是某 seed/模板版本标记？）动手时需核实——可能是 `FreeCharacter` 的某个分组字段或 seed 模板的章节序。
  - 确认现有"性格""在乎什么"字段的位置（编辑器 UI + types + seed），新字段插在二者之间，并同步到类型定义、编辑器 UI、seed 示例。
  - 与 #7 可能联动：若"指节泛白"源于卡内缺"爱好/放松方式"等设定，补全"喜好/爱好"或能稀释模型对单一紧张描写的偏好（假设，先不实锤）。

### #10（含美观）　本场状态面板：进度条换行到数值下方、固定窗格内完整可见、整体更美观
- **情况描述**：好感/信任/精神三个数值后边带了进度条，但本场状态显示窗格高度有限，信任、精神的进度条被挤到视口下方，必须拖滚动条才能看到。希望：把进度条**改到对应数值的下一行显示**（数值一行、进度条紧随其下），并整体调整为**所有信息（五项数值 + 各自进度条 + 备注）都能在固定窗格内完整显示、不再滚动**；重新设计后还要**整体更美观**（间距、对齐、进度条样式、信息层级都顺眼）。
- **归类**：酒馆模式 · 自由对话 · 本场状态面板（`TavernVarsPanel`）· 布局 + 视觉优化
- **建议优先级**：P1
- **状态**：待实施（与 #11、#12 同改 `VarRow` 渲染，建议合并实施）
- **待核实 / 处理方向（占位、不展开）**：当前 `VarRow` 里进度条渲染位置需查（#4 加的是值输入 + 备注输入两行；进度条本体可能是 `VAR_SCALE` / `renderVarValues` 既有渲染）；改为"数值一行、进度条下一行"的纵向堆叠，并让面板内容按窗格高度自适应、消除溢出滚动。

### #11　进度条语义重做：以 0 为中心、双向填充、正负异色
- **情况描述**：好感/信任/精神进度条目前填充从 **-100 开始**（左端 -100、右端 +100，0 不在正中）。你希望改成：
  1. **以 0 为中点**——进度条分左右两半，0 在中心。
  2. **正向（值 > 0，往好的方向发展）**：向**右侧**填充（或缩短左侧），代表良性发展。
  3. **负向（值 < 0，往坏的方向发展）**：向**左侧**延伸（或缩短右侧），代表恶化。
  4. **正负填充颜色不同**：>0 用"好"的色、<0 用"坏"的色（从零变大=好，从零变小=坏）。
- **归类**：酒馆模式 · 自由对话 · 本场状态面板 · 进度条视觉语义（与 #10 合并实施）
- **建议优先级**：P1
- **状态**：待实施
- **待核实 / 处理方向（占位、不展开）**：把"从 -100 起算的单色横条"改为"以 0 居中、双向、双色"的对称条；需确认当前进度条渲染所在函数并改造。

### #12　本场状态面板："心情""地点"去掉蓝色填充状态、只留可编辑文本框
- **情况描述**：在"本场状态"栏里，"心情"和"地点"现在有两样东西——一个可编辑文本框，外加一个**蓝色填充状态**（AI 抽取到的当前判定值高亮展示块）。你觉得那个蓝色状态变化**不需要显示**，只要把内容**直接写进可编辑文本框**即可，不要另起一个蓝色填充态。
- **归类**：酒馆模式 · 自由对话 · 本场状态面板（`TavernVarsPanel` 的 text 类型字段：心情/地点）· 展示简化
- **建议优先级**：P1
- **状态**：待实施（与 #10/#11 同改 `VarRow`）
- **待核实 / 处理方向（占位、不展开）**：定位"蓝色填充状态"渲染段（大概率是 `VarRow` 对 text 类字段额外渲染的派生展示块或 `renderVarValues` 特殊高亮），移除该块，只留 `<input>`（AI 抽取到的值直接回填文本框）。

### #13　自由对话 / 剧情推演：加"一键回到底部"按钮（仅非底部时显示）
- **情况描述**：用户在自由对话或剧情推演窗口里常往前滚动翻看历史消息；想回到最新消息时，只能手动拖滑条或一直往下滚，很麻烦。希望加一个**「一键回到底部」按钮**——并且**只在当前视图不在最底部时才显示**（滚到底部后自动隐藏）。
- **归类**：酒馆模式 · 自由对话 + 剧情推演 · 消息列表 · 滚动交互 UX
- **建议优先级**：P2
- **状态**：待实施
- **待核实 / 处理方向（占位、不展开）**：查两处消息列表容器（自由对话对话区、剧情推演会话区），实现滚动监听：`scrollTop + clientHeight < scrollHeight - 阈值` 时显示按钮，点击 `scrollTo({top: scrollHeight})` 回底；到底后自动隐藏。两个场景可抽公共"回底部"浮层组件复用。

### #14（偶发·低优先）　人物对话与括号内客观描写偶发同行、区分不明显
- **情况描述**：偶尔仍会出现"人物直接对话"和"客观描写（括号内的动作/旁白）"写在同一行的情况，导致括号里的内容和人物台词没有明显分行区分。你明确说这是**偶发现象、不严重**。
- **归类**：酒馆模式 · 自由对话 / 剧情推演 · 输出格式 · 对话与描写分行约束
- **建议优先级**：P3
- **状态**：待评估
- **待核实 / 处理方向（占位、不展开）**：查 system 提示是否已有"对话与客观描写须分行"约束及模型输出换行处理；偶发说明约束有时被忽略。因不严重，仅可在汇总时做轻量提示词强化，不单列大改。

### #15（条件性）　合理范围丰富 AI 颜文字/emoji 字库（易则做、难则弃并说明）
- **情况描述**：你希望在合理范围内给 AI 丰富一下"颜文字和 emoji 表情"的字库——你觉得这些发出来能提升沉浸感和体验感。约束明确：**如果只需简单改动就能实现，就做；如果不好处理，就说明原因、放弃开发**（不要硬上）。
- **归类**：酒馆模式 · 自由对话 / 剧情推演 · 输出风格 · 颜文字/emoji 字库
- **建议优先级**：待评估（实现成本低则做，否则放弃并说明）
- **状态**：待评估
- **待核实 / 处理方向（占位、不展开）**：动手时先查当前 emoji/颜文字控制方式——若是 system 提示里挂了一份"可用表情清单"，扩充字库=改提示词清单（简单，照做）；若涉及渲染层解析/替换或 token 限制导致不稳定，则说明原因、放弃。颜文字风格需按角色调性（楚楠偏冷、苏念偏活泼），不能一股脑全塞。

### #16（需修复）　结束对话后结算状态写错卡：写进用户卡、没写进 AI 角色卡
- **情况描述**：多轮对话后选"结束对话"，生成的人物记忆日记、设定变更识别都准确、没问题；但**结算过后的本场状态（好感/信任/精神等数值）没有落到 AI 模型扮演的角色卡里，反而落到了用户扮演的角色卡里**。你明确说这个有问题，要查明原因并修复。
- **归类**：酒馆模式 · 自由对话 · 回合结算（`roundEnd`）· 状态落库 · 角色 id 错配（疑似 #4 实现的边界 bug）
- **建议优先级**：P0（数据写错卡，属功能正确性，需优先修）
- **状态**：待修复
- **待核实 / 处理方向（占位、不展开）**：高度怀疑是 #4 埋的隐患——结算落库用了 `session.charIds[0]` 当 primary，但实际 `charIds` 顺序里**用户扮演的角色排在前**，于是数值写进用户卡。需查 `roundEnd.ts` 里 `primaryCharId` 取值链路：`session.charIds` 顺序约定、哪个是 AI 模型扮演、哪个是用户；以及 `saveFreeChar` 写入目标是否为"AI 角色卡"。修复方向：primary 必须指向 **AI 模型扮演**的角色（而非盲取 charIds[0]），或显式区分 user/ai 角色 id。
