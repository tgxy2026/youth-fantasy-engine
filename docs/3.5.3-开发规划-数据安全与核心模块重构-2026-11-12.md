## 一、版本目标与边界

在保持现有用户体验、数据格式和接口兼容的前提下，优先收紧项目数据读取失败的处理，整理异步保存归属，再逐步拆分同步、社区存储和大型界面模型，降低后续修改和回归的风险。以完整可验证的工作包交付，不以文件行数或拆分数量作为目标。

本版不默认引入新社区功能、不迁移生产存储到 SQLite、不更换同步加密或数据协议。异地备份、生产告警配置、生产迁移、部署、打包、推送及发布须另行获得明确授权。隔离环境使用合成数据，不访问真实用户资料或模型。

3.5.2 最新交接顶部记录正式发布与 449/449 回归；交接下半部和旧开发规划包含发布前快照，不能混用为当前状态。上述测试为历史证据，本次规划未重跑；生产状态及其后变化未现场核实。三端矩阵、真实设备、同等资源负载和断电等仍不可据此宣称已覆盖。

补充盘点：状态文件缺失但项目目录、历史 manifest 或墓碑仍存在，以及世代文件缺失但已有数据，都不能直接认定为首次初始化。覆盖提交、删除、恢复、永久清理、历史列表及迁移入口；区分合法缺失与损坏，检查合法 JSON 的结构、类型、世代和账户归属。验证异常时不改变版本指针、幂等记录或其他数据，并检查锁释放和重试。恢复扫描历史版本时不得将损坏静默当作普通缺项。

**验收：**故障注入覆盖上述情形及恢复后重试；证明失败时原文件和其他项目未被更改，正常新建、读取、提交、恢复及旧格式行为保持预期；运行现有项目存储及迁移专项 `scripts/verify/project-store-332.mjs`、`scripts/verify/migrate-v2-332.mjs` 和相关服务流程。先确认适用的实际运行方式并记录命令与环境。

服务自检入口为 `npm run test:server`；`node scripts/verify/run-all-332.mjs project` 只筛选名称匹配的脚本，不能代替恢复、清理、迁移专项或全量服务自检。接口测试应验证授权和错误码，确认旧客户端不会将错误当作成功。

### P1-A：异步保存归属

1. 梳理角色卡、正文编辑器和表格保存入口、卸载/切换、自动及手动保存，明确操作启动时的项目、记录、账号/存储上下文和草稿版本。
2. 以已有所有权工具为基础，先在一个代表性路径提炼最小公共接口并验证，再逐条迁移；不要在首次异步操作之后才捕获归属，不让迟到结果覆盖新记录、新账号或新输入。
3. 明确失败和冲突时的提示、重试与未保存草稿保留规则，保持现有离开保护与写入协调。

**验收：**隔离浏览器和存储中覆盖保存期间切项目/记录/账号、组件卸载、失败重试、先后回执倒序、提交后继续输入；核对持久化结果及草稿而非仅检查提示。复用 `scripts/verify/frontend-character-save.mjs`、`frontend-async-record-owner.mjs` 等适用专项，并补缺失场景。

先盘点 `writeOwner.ts`、`ownedOperation.ts`、记录操作和表单租约等既有机制及其边界，复用已有能力，避免引入相互冲突的归属机制。

### P1-B：同步核心分层

先固定当前输入输出与副作用，再从 `syncCore.ts` 提取可单独验证的合并规则；随后视依赖情况拆分编码兼容、恢复、传输和调度。保持公开接口、冲突决议、本地专属数据、删除墓碑及历史载荷的行为；禁止借重构更换加密方式或改变协议。

**验收：**以旧版兼容样本及合成快照覆盖本地/远端增删改、冲突、空载荷、网络失败重试、备份恢复、重复同步和账号切换；比较重构前后结果并运行 `tests/syncGuards.test.ts`、`tests/syncRestore.test.ts`、`tests/cloudStoreWrapper.test.ts` 所属测试入口。敏感信息不得进入样本或日志。

另核对公开导出、监听器注册与注销、重复初始化、并发推送和卸载清理；通过旧格式夹具与受影响的新旧客户端组合验证兼容。

### P1-C：社区存储边界

围绕现有 JSON 实现分离文件访问、缓存和业务操作，保持 `createCommunityStore` 对外行为与磁盘格式。保留核心文件缺失拒绝、评论初始化标记、写失败清缓存、协作锁、匿名映射及密钥失败关闭；备份恢复仍按停写与现有操作规程执行。必要时为未来存储方案定义最小接口，不实现生产迁移。

**验收：**社区评论、匿名代号、备份恢复及锁竞争专项在最终源码上通过；注入缺失、损坏、写失败、恢复及重启场景，核对数据和映射。兼容性测试须覆盖已有 JSON 与现有备份；不能把协作锁描述为强制互斥或把单文件 rename 描述为断电持久性。

核对恢复预览、公开与待审版本指针、匿名映射和评论计数，检查备份工具与存储接口使用的规则一致。

### P2：界面模型与服务端路由

在 P0/P1 稳定后，按用户行为而非行数拆分编辑器和表格中可独立验证的职责；保留集中协调生命周期的入口。服务端按认证、项目、社区等领域逐步提取路由，保持鉴权、同源检查、顺序、状态码和响应契约。

路由回归覆盖游客、登录、跨账号和管理员身份，检查路径匹配、请求大小限制及异常响应，确保公共防护在拆分后仍生效。

**验收：**针对受影响的真实交互及服务接口开展隔离回归；盘点源码文本断言，迁移时说明原保障与替代行为测试。若某一拆分不能在本版安全完成，明确标记未完成及影响，不以删除测试代替验收。

## 四、实施顺序与工作方式

1. 重新核对基线、环境、历史证据及工作区；为涉及模块建立当前行为和故障基线。
2. 完成 P0 盘点、复现、修复及专项；随后完成 P1-A、P1-B、P1-C，逐包审查、验证并记录结果。
3. 在依赖稳定后推进 P2；发现新的安全问题时先确定影响与修复范围，必要时调整顺序。
4. 最终按实际改动重跑全量、专项和适用端到端验证，记录源码版本、命令、环境、结果及未覆盖项。源码变化后旧证据只作历史参考。

## 五、统一验收与发布边界

- 基础门禁：`npm run verify`、`npm run test:server` 及受影响专项通过；分别记录测试任务数、专项断言数、失败、未运行与跳过原因，不混用统计单位。`npm run verify` 不包含全部服务端或浏览器专项。最终源码执行 `npm run build`；这不是桌面或便携正式产物验收。
- 行为验收：以隔离数据覆盖关键持久化、同步冲突、备份恢复及对应 UI 流程；验证失败不破坏原数据，新输入不被旧回执覆盖。功能不适用的端须注明原因。
- 范围验收：列出网页、桌面、便携版的适用性与逐项证据；浏览器模拟不等于真实设备，开发态不等于正式安装包。真实设备、断电、跨设备、生产规模容量等未验证项单列，不推断通过。
- 安全及运维：生产匿名密钥与社区数据须同时间点恢复；异地副本、外部告警及恢复演练是否实际启用需现场核实。测试锁和停写协议的覆盖范围要如实记录。
- 兼容与回退：开发前保存合成旧版 JSON、备份与同步载荷夹具；明确并验证受影响的新旧客户端与服务端组合。回退分别评估代码、已写入数据和配置兼容性，提供停止条件与隔离恢复演练，不能假定回退代码即回退数据。
- 证据矩阵：逐包列出场景、实际端与环境、执行命令、源码指纹、通过/失败/未运行、日志位置及限制；失败、超时、零断言或缺设备均不能记作通过。故障注入核对操作前后数据内容及关联记录，而非只观察退出码。
- 完成判定：规划内工作包全部完成且相应证据通过，才能称开发与测试验收完成；如存在未完成或阻塞，明确列出，不能以历史回归或局部测试替代。发布、部署、封装和生产变更另需明确授权。

## 六、交付记录模板

每个工作包记录：基线与最终提交或源码指纹、变更范围、兼容性影响、测试命令与结果、故障注入结果、未覆盖项目及回退方法。阶段完成后更新项目工作日志与交接；不得清理已有恢复证据或覆盖用户改动。
