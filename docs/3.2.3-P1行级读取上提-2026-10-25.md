# 3.2.3 · 大表热点取证与两处「逐行读取」上提（2026-10-25 16:20）

> 承接 [P0 大表生产基线](3.2.3-P0大表生产基线-2026-10-25.md) 的「新增技术债线索」那段：
> 当时只有代码层面的怀疑（`TableRefSelect` 每行读整表），**没有调用计数证据**，large 也一直打不开。
> 这一轮先补取证工具，再按证据修两处逐行读取。**P0 仍未完成、P1 的虚拟化部分仍未开工。**

## 1. 新增取证工具：`scripts/verify/table-hotpath.mjs`

在**存储边界**上数「一次打开到底读了多少」，而不是靠猜：

| 做法 | 说明 |
|---|---|
| 埋点位置 | `IDBObjectStore.prototype`（getAll/get/count/openCursor/getAllKeys）**和** `IDBIndex.prototype` 同名方法 |
| 只统计应用请求 | 不改应用行为、不注入延迟；探针自检一次 `index('tabId').getAll()` 确认补丁在链路上（`selfTest.delta === 1`） |
| 归因 | 每次调用**同步**取栈并按签名聚合（同一读取键可能有很多调用方，只留前 3 条样本会看到「碰巧第一个」就下错结论） |
| 不改已冻结的测量实现 | `table-performance.mjs` / `table-metrics.mjs` / 夹具模块一字未动 —— 它们参与 `measurementHash`，改了就让 compare 判「实现不兼容」 |

🔴 两个自伤的坑（都写在脚本注释里）：
1. **`IDBObjectStore.getAllFromIndex` 在标准里已移除**：应用走的是 `store.index('tabId').getAll()`，
   请求对象是 **IDBIndex**。只挂 ObjectStore 会把 `tableRows` 数成 0 —— 看起来像「根本没读」，其实全在另一侧。
2. **栈必须在调用那一刻同步取**：放在 `success` 回调里取到的只是事件派发的栈（`<anonymous>:42:51`），
   第一版就这么白跑了一轮。

## 2. 修前实测（游客真后端 + 生产构建 + 300 行 × 74 列）

| 指标 | 数值 |
|---|---|
| 打开耗时 | 13.3 ~ 13.9 s |
| IDB 请求总数 | **1,217** |
| `tableRows` 读取 | **304 次 / 读回 90,300 行**（放大 **301 倍**） |
| `settingsKV` 读取 | **913 次**（≈3 / 行） |
| DOM 节点 / 挂载行 | 125,340 / 300 |

归因（按调用签名聚合）：

- **301 × `getTableRows`** ← `TableRefSelect` 每行的 `useEffect`：一行一次整表读取。
- **900 × `getCustomOptions`** ← `CustomSelect` 每行的 `useEffect`：300 行 × 3 个内置下拉。

## 3. 两处改动

| 位置 | 改法 | 口径是否变化 |
|---|---|---|
| `useTableRefOptions.ts`（新增 hook）+ `TableSheetRow` + `TableRefSelect.options` | 跨表引用候选值在**表格级按列读一次**，用 `refOptions[col.name]` 传进每行；控件收到 `options` 就不再自己读 | 同一 `getTableRows`、同一去重 + `localeCompare('zh')`，完全一致 |
| `useTableSheetModel.customOpts` 暴露 + `CustomSelect.payload` | 内置下拉的自定义选项由模型读一次、逐行传下去；控件收到 `payload` 就不自己读、也不各挂广播监听（广播仍由模型统一监听后重算） | 同一 `getCustomOptions`；增删改选项仍靠 `CUSTOM_OPTIONS_EVENT` 回到模型刷新 |

🔴 **首帧必须是「空数组/空载荷」，不能是 `undefined`**：`undefined` 在控件语义里是「没人给我，我自己读」——
第一版就这么漏了，300 行在 model 读回来之前各自又读了一遍（实测 306 次，等于白改）。

结构护栏：`useTableSheetModel.ts` 本来就贴着 1200 行硬上限，这次没有再往里塞（先塞到 1241 被闸 ① 拦下），
逻辑抽到 `useTableRefOptions.ts`，主文件 1199 行、`structureGates` 33/33 通过。

## 4. 修后实测

| 指标 | 修前 | 修后 | 变化 |
|---|---|---|---|
| IDB 请求总数 | 1,217 | **19** | −98.4% |
| `tableRows` 读取次数 | 304 | **6** | −98% |
| `tableRows` 读回行数 | 90,300 | **900** | −99%（放大 301→3 倍，即 3 个引用列各读一次） |
| `settingsKV` 读取 | 913 | **13** | −98.6% |
| 打开耗时（medium） | 13.3~13.9 s | **12.7 s** | **仅 −8%** |
| DOM 节点 | 125,340 | 125,340 | 不变 |
| 堆占用 | 142 MB | 115 MB | −19% |

**结论必须如实写清**：这轮消掉的是「读取放大」这一整类病理（1000 行时原本是 100 万行读回、内存抖动剧烈），
但 **medium 的首屏仍要 12.7 秒** —— 瓶颈已经不在存储，而在**把 300×74 = 22,200 个单元格全量挂进 DOM**。
这正好是方案里 P2（只挂视口附近的行）的活，不属于本轮。

large（1000×74）现在**能打开**了（此前 180 s 等不到首个编辑器，工具判失败）：

| large | 数值 |
|---|---|
| 打开耗时 | **254.7 s**（4 分 15 秒） |
| `tableRows` 读取 | 6 次 / 读回 3,000 行（放大 3 倍） |
| IDB 请求总数 | 19 |

⇒ 存储侧已不再是 large 的瓶颈，**74,000 个单元格的渲染**才是。large 的正式基线仍不能记（254 s 不是可接受基线，
且工具默认 180 s 超时会判失败）；要不要给 large 单独放宽超时、还是等 P2 之后一起测，需要一次明确决定。

## 6. 边界

- **不是 P2**：没有虚拟化、没有行级草稿隔离、没改 `TableSheetRow` 的订阅方式；medium 12.7 s / large 254 s 仍不可接受。
- **没有动基线**：`table-performance.mjs`、`table-metrics.mjs`、夹具模块未改，P0 已记录的 small/medium 基线仍可比。
- `getTableRows` 在**其它页面**（正文检索面板、设定检索、故事线）仍是逐处读取，本轮没动（不在大表主路径上）。
- 真实输入法与实体设备、安装包验收仍未做；大表 P0 的「冷启动 / 筛选 / 远端定位 / 连续滚动 / tree·mixed 交互 /
  A-B 交错 / longbook 正文 / 阈值冻结」仍缺。
