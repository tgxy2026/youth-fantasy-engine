## 1. 这轮修的是什么

方案 §5.1 记录的三处病灶，全部落在「模型给的东西能不能进正文」这条链上：

| 病灶 | 现场后果 |
|---|---|
| 提示词允许逻辑层「把修改建议写进 fix，它同样会被替换到 quote 的位置」 | **一句建议被当成正文写进稿子** |
| 同一文件把 `fix` / `建议` / `suggestion` 归成同一个字段 | 解析层无法区分「能替换」与「只是建议」 |
| 请求侧 `output: 'json-object'`，提示词却要求顶层数组 | 协议自相矛盾，模型两种都可能给 |
| 替换时 `at` 失效就无条件 `indexOf` 回退 | 同一句出现多次 ⇒ **必定改错位置** |
| 解析不出结果时返回空数组 | 界面亮绿「未发现问题 ✓」，实际那段根本没读懂 |

契约语义（按方案 §5.2）：

1. 只有 `kind: "replacement"` 允许改正文；`suggestion` 只展示、可复制。
2. `replacement` 必须非空、且不同于 `quote`；不满足则**降级为建议**（问题不丢，也不许替换）。
3. 旧格式（顶层数组 / `fix` / `建议` / `suggestion` 别名）仍可解析，**缺 kind 一律按建议**，不靠关键词猜。
4. 整块解析失败、条目格式非法、引文定位不到 —— 三者都如实计数并展示，且都会阻止「未发现 ✓」。
5. 应用时核对位置：`at` 逐字对上才用；否则只有全文唯一命中才允许定位；多义/找不到直接拒绝并说明。
6. 替换后两块结果一起重锚定，**相交范围标记失效**（`stale`，可看不可改），不再拿旧下标套新正文。
