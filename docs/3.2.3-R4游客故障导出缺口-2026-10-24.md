# 3.2.3 R4：游客模式"保存失败期间的导出"缺口

> 日期：2026-10-24｜执行：可可｜基线 `main` / `85cd7ac`
> 性质：**只记录，不改代码**（等主人拍板）。结论是代码级判读，未做浏览器实测 —— 下文逐条给出依据路径。
> 不涉及封装/发布/部署；版本号仍 3.2.2。

## 1. 为什么查这件事

方案 §7 与 §6.1 给 `write-failure` 这一格的描述是：
**「区分内存接受与持久化确认，失败不清 dirty / 不刷新 / 可导出」**。
游客（`web-guest`）的探针目前已经验到「不清 dirty、不刷新、可重试、重启回读」，
唯独**「失败时可导出」**没有证据 —— 所以矩阵里 `write-failure/web-guest` 一直没被点亮，
只在 `boot-store/web-guest` 点亮过一格（1/26 → 桌面取证后 3/26）。

## 2. 查证结论：导出入口存在，但**带不走未保存的草稿**

| 入口 | 代码 | 在游客模式下的实际行为 |
|---|---|---|
| 数据坞「导出全部数据」（游客视图） | `DataDock.tsx:49` → `storageBar:'guest'` → `GuestDataBar`（`Guest.tsx`） | **有这入口**，走 `exportGuestData()`（浏览器下载，整库 JSON，格式与便携/桌面一致） |
| 其取数来源 | `guestData.ts:55 guestDataObject()` → `collectAll()` → 对 16 个 store 逐个 `ops.getAll` | **全部从 IndexedDB 读**。保存失败时 IDB 里是旧正文 ⇒ 导出的包里**不含编辑器里的新草稿** |
| 项目中心「导出 JSON 备份」 | `ProjectHub.tsx:222` → `db.exportProject()` → `projects.ts:280-289` 同样走 `ops.get/getAll` | 同上，导的是库里那份 |
| 便携/桌面为什么能带草稿 | 它们的整库导出读的是**内存整库**（`portableDataJSONReport` / `exportDesktopData`） | 游客没有"内存整库"这一层，数据源就是 IDB |

所以准确的缺口是：**不是"不能导出"，而是"导出的备份不含未落盘的草稿"**。
游客模式下 IDB 写失败时，新草稿只活在页面内存 —— 能导出的是旧稿；刷新/关标签即丢。
这一条是**代码级判读**，未做浏览器实测（见第 5 节如何转成实测）。

## 3. 影响判断

| 维度 | 判断 |
|---|---|
| 严重度 | 中。仅影响「游客模式 + IndexedDB 写入失败/配额满」这一交叉场景；已有重试与草稿保留，刷新才丢 |
| 与已验能力的关系 | **不推翻**游客 14/14：那 14 项验的是"不清 dirty / 不刷新 / 可重试 / 重启回读"，全部成立 |
| 对矩阵的影响 | `write-failure/web-guest` 继续**不点亮**。理由不再是"没跑"，而是"该格要求的『可导出』在产品里拿不到未保存草稿" |
| 是否该冒充已验 | 绝不。方案 §7 的口径是「某个子场景有证据不能代表整个单元通过」，反向同理：缺一个子场景就不能算过 |

## 3.1 想把它变成实测，需要改探针一步

在 `web-guest-save-probe.cjs` 的 quota 段里（故障仍生效时）点 `GuestDataBar` 的导出，接住下载的 JSON，
断言 `stores.chapters[CH].content === 旧正文`（＝确认草稿不在包里）。**我没有加**，原因：
该探针的每条 case 都是"通过了才算过"，把"确认缺口"写成 case 会让报告读起来像"缺口是预期行为"，
在主人拍板 A/B/C 之前容易误导。等定方案再决定它作为「回归（修复后应包含草稿）」还是「现状固化」。

## 4. 三个可选处置（等主人选，我不擅自开工）

| 方案 | 做法 | 代价/风险 |
|---|---|---|
| **A. 明确写进帮助与红条**（最小） | 游客保存失败的提示里加一句「本模式暂不支持导出未保存草稿，请勿关闭页面，排除问题后重试」 | 只改文案，几分钟；但用户确实仍可能丢稿 |
| **B. 加「导出当前草稿」按钮**（中） | 编辑器加一个只导出当前章正文的降级出口（不碰整库、不碰备份） | 改 UI + 导出逻辑，需回归；收益是丢稿风险大降 |
| **C. 给游客补整库导出**（大） | 让 `exportPortableData` 在游客下也可用（从 idbOps 聚合） | 与"游客数据只在浏览器"的定位冲突，且备份载荷在 IDB 里读全库成本高；不建议为凑矩阵做 |

我的建议：**A 立刻做、B 看主人是否愿意接受一个新按钮**、C 不做。
但按红线「待优化只记录、未点名禁动代码」，这里只登记，不动手。

## 5. 与其它待办的关系

- 矩阵 `write-failure/web-guest` 的 3 个必需子场景里，前两个（`accepted-vs-persisted`、`failure-preserves-draft`、`retry-readback`）都有实测；
  缺的是描述句里的"可导出"。要么补能力（B/C），要么**把该格的验收口径写清楚**（"本格不要求游客可导出"）——后者需要主人拍板改 policy 描述。
- 桌面侧同格已验（真实的故障期导出 + 恢复重启），所以 `write-failure/desktop` 已点亮，不冲突。
- `web-cloud` 的临时账号隔离运行仍未做（下一批），与本文无关。
