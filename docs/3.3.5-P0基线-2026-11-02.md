## 2. 存储后端与事务/恢复窗口盘点（A1–A3）

### 2.1 三大存储后端语义对比
| 存储后端 | 平台 | 底层驱动 | 写入机制 | 事务与原子性语义 |
|---|---|---|---|---|
| **IndexedDB** | Web / 浏览器 | `idb`（`src/lib/db/core.ts`） | IDB 事务 | 单 object store 事务内具备原子性；跨 store（如 `chapters` 与 `meta`）依赖多 store 事务，但在标签页意外强关/崩溃时缺乏持久化同步保证。多标签并发无排他锁。 |
| **FileBackend-Desktop** | 桌面安装版 (Windows) | Electron IPC / 专用数据文件 | 内存 ops + 节流 `flushDesktop` (`src/lib/app/desktop.ts`) | 支持 `putStrict` 确认落盘；但章节正文落库与检查点保存分属两个独立写入，非跨实体单次文件事务。 |
| **FileBackend-Portable** | 便携版 (Node.js) | 本地 HTTP 服务器 + JSON 数据文件 | 内存 ops + 节流 `flushPortable` (`src/lib/storage/fileBackend.ts`) | 与 Desktop 类似，依赖轮询 flush 确认落盘，章节与检查点跨 step 写入存在断裂窗口。 |

### 2.2 创意写作连写恢复窗口分析（A1/A2）
- **核心调用链**：
  `runCreativeWriting` (`aiWorkflow.ts`)  
  $\rightarrow$ `autoContinueDraft` (`autoContinue.ts`)  
  $\rightarrow$ `onChapterSaved` (章落库)  
  $\rightarrow$ `opts.onCheckpoint` (`creativeSession.ts`)  
  $\rightarrow$ `persistNow` + `flushCreativeCheckpoint`
- **最坏故障窗口**：
  新章节正文在 `autoContinueDraft` 内部成功落库后，到 `onCheckpoint` 中的检查点被持久化到磁盘并完成 `flushCreativeCheckpoint` 之间。
  - 若在此窗口发生异常、进程终止（SIGKILL/强杀）或断电：章节表中已存在新章，但会话 `meta` 中的断点（`doneChapters` 与 `evidence`）仍停留在上一章。
  - **现有恢复判据**：
    `validateResumeForStart` 调用 `verifyResumeEvidence(resume.evidence, chapters, resume.doneChapters)`：
    - `legacy`：旧记录无证据，阻止并要求人工核对；
    - `count`：已完成章数与证据条数不匹配，阻止；
    - `missing`：断点中记录的章在书库中已被删除，明确阻止并说明；
    - `changed`：断点中记录的章正文指纹与书库现有正文不一致，明确阻止并说明（禁止静默跳过或覆盖）；
    - `ok`：全部已记录章节存在且指纹吻合，允许续跑。
- **事务与宣传口径结论**：
  当前任何后端均不能证明章节落库与检查点落盘具备跨实体原子提交能力。**严禁宣传 exactly-once**，UI 和文档必须如实明确提示：在极端崩溃或断电情况下，系统优先保护已写入章节，恢复时可能需要重新确认或重写最后一章。

### 2.3 同步并发与冲突拦截现状（A3）
- 现有机制：`captureStorageWriteOwner` 与 `contextEpoch`（`src/lib/storage/contextEpoch.ts`）。
- 冲突保护：切项目或远端版本推进时，存储写所有者会抛出 `StorageWriteConflictError` 或拦截写入。
- 3.3.5 目标：在受控双标签/双实例下，验证 AI 候选生成确认期间本地编辑、远端版本推进、读写失败时的冲突回退，确保旧请求不静默覆盖新编辑。

| **CreativeRewrite** (整章改写) | `src/components/creative/CreativeRewriteSection.tsx` | 创意写作页整章改写/续写 | 仅送 `title`、`body`、`prevTail`，未接通全量设定与细纲 | 已接 `RevisionCandidate` 存储、字数校验与时光机快照 | ⚠️ **次优**：虽有候选机制，但位于独立创意写作面板，远离正文编辑器与 `ChapterContextPanel` 资料抽屉。 |
| **JieWenJi 续写** (颉文姬续写) | `src/components/jiewenji/JieWenJiEdit.tsx` + `NovelEditor.tsx` | **正文编辑器内当前章末尾续写** | 已调 `buildProjectContext` + `getContinuationSources`（细纲、角色、前文、文风档） | 当前直接以「建议段」插入编辑器正文，尚未规范化接入 `RevisionCandidate` 条件提交 | ✅ **首选**：直接位于主创作工作区（`NovelEditor`），与 `ChapterContextPanel` 处于同一焦点章视图，是「本章计划 + 已确认设定 + 邻近正文 $\rightarrow$ 本章候选」的最天然闭环。 |

### 3.2 选定纵切入口与调用链
- **选定入口**：正文编辑器 · 颉文姬续写（`NovelEditor` $\rightarrow$ `JieWenJiEdit` / `useJieWenJiModel`）
- **完整调用链**：
  1. `NovelEditor` 传入当前章节上下文（`chapterId`, `chapterTitle`, `bodyText`）；
  2. `ChapterContextPanel` 提供绑定细纲与本章固定资料（保持旧固定不自动发送原则，展示为可选来源）；
  3. `useJieWenJiModel.runContinuation` 触发装配：
     - 调用 `getContinuationSources` 提取邻近前文与章节摘要；
     - 调用 `buildProjectContext` 装配已确认设定资料；
     - 接入 `requestBudget.ts` / `contextAssembler.ts` 生成冻结的 `MaterialManifest`（发送清单快照），计算字符与 token 估算预算；
  4. 提示词分层重构：
     - 提示词稳定 ID：`continue-passage`（`src/lib/aiTasks/jieWenJi.ts`）；
     - 分层结构：系统角色与不可绕过的纪律 $\rightarrow$ 作者明确续写指令 $\rightarrow$ 隔离包裹的作品资料（计划、设定、前文） $\rightarrow$ 去 AI 味规则；
  5. 模型请求与候选生成：
     - 调用受控模型/假模型端点；支持中途取消、超时提示；
  6. 候选确认与条件应用：
     - 产物先登记为 `RevisionCandidate`；
     - UI 展示发送材料清单对照与候选内容；
     - 作者点击「确认应用」时，通过 `applyCandidate` 进行基准指纹（`beforeText`）核对；若期间正文有新编辑，拒绝静默覆盖并提示保留草稿。

## 4. 提示词与稳定 ID / 覆写矩阵（Package C）

### 4.1 纵切相关提示词登记现状
- **注册机制**：`src/lib/ai/promptSettings.ts` 中的 `registerPrompt`；集中在 `PROMPT_ORDER`（`src/lib/ai/aiTasks.ts`）。
- **稳定 ID**：`continue-passage`
  - 组别：`正文写作`
  - 名称：`续写正文`
  - 变量：`P_continue_passage`
  - 说明：接着本章末尾往下续写一段正文，交作者取舍。
- **关联纪律规则**：
  - 去 AI 味规则：`deAiGenerateRule('full')`（`src/lib/ai/deAiStyle.ts`）
  - 文风指纹：`activeFingerprintNote()`
  - 提示词隔离边界：`authorBlock(fence, text)` 与 `newAuthorFence()`（`src/lib/ai/promptGuard.ts`）
- **兼容性承诺**：
  旧用户在 `settingsKV` 中对 `continue-passage` 的自定义全局覆写在升级后继续有效；新增模板变量（如章节计划、结构边界）均设置安全默认回退值，旧覆写不包含新变量时仍能平稳运行。

### 5.1 各环境保存与备份能力现状
| 平台 / 运行环境 | 保存状态语义 (`lastSavedAt`) | 自动备份机制 | 手动备份机制 | 导出机制 | 还原机制 |
|---|---|---|---|---|---|
| **桌面版 (Windows)** | 内存排队 $\rightarrow$ 800ms 防抖 $\rightarrow$ `flushDesktop` 落盘确认 | 5分钟滚动 (最多30份) + 每日备份 (最多30份) | 支持即时备份，存至 `backups` 与 `backupPayloads` | 导出独立备份文件 (`.json`)、项目迁移包、TXT/MD/DOCX/EPUB | `restoreBackup`（覆盖当前项目，重映射 ID，保留快照，独立还原知识库） |

### 5.2 现状缺口与安全规则（待 P1 强化）
1. **时间戳混淆**：此前部分面板将定时器触发时间等同于落盘时间；P1 必须明确区分「进行中」、「上次成功保存」、「上次成功备份」与「落盘失败」。
2. **知识库独立步骤容错**：`db/backups.ts` 中 `bundle.knowledgeBase` 还原为独立步，失败只报 `console.warn`；P1 须将部分成功与缺失内容明确汇报给调用方。
3. **覆盖前预备份**：执行覆盖还原前，必须在本地先建立一份可回读的自恢复临时备份，若预备份失败则中止覆盖。
