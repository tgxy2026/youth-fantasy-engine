## 二、批次 1 · 酒馆 timeout 与 onToken（13 处 / 10 文件）

### 2.1 问题回顾

`summarize`(×4) / `revise` / `report` / `world` / `story` / `script` / `draft` / `import` / `daily` / `interview`
这 13 处 AI 调用**硬编码 `timeoutMs: CHAT_TIMEOUT_MS`（180 秒常量）**，而酒馆控制面板明明提供了
「请求超时」设置（`TavernSettings.common.timeoutSec`，默认 300 秒）—— **用户调了完全不起作用**。

且 `engine.ts` 主对话用的是 `timeoutMsOf(st)` ⇒ 同项目两套口径。

### 2.2 修法（最小侵入）

```ts
// 之前
timeoutMs: CHAT_TIMEOUT_MS,
// 之后
timeoutMs: timeoutMsOf(await getTavernSettings()),
```

- `timeoutMsOf(s) = Math.max(5, s.common.timeoutSec) * 1000`（酒馆设置的真源，`settings.ts:796`）
- `getTavernSettings()` 自带 try/catch（读失败回默认值），无缓存但走 IDB（毫秒级），而这些是**低频任务**（整理记忆 / 报告 / 导入），多读一次无感
- 同时从各文件的 `from '../ai'` import 里删掉 `CHAT_TIMEOUT_MS`（否则 ESLint 报未使用）

### 2.3 🔴 有意**不**加 `onToken`（与子代理建议不同）

子代理建议「透传 `onToken: () => {}` 以开启流式、在首 token 清总超时」。**本轮采纳其另一半（timeoutMs），但未采纳 onToken**，理由：

1. `chat.ts:157` 是 `stream: !!o.onToken` ⇒ 传 `onToken` 会把**传输形态**从「非流式」改成「流式」；
2. 项目历史记录过**第三方中转站跑不通**（见长期记忆），流式对中转站兼容性更敏感 ⇒ 属于「为省时间而扩大兼容面风险」；
3. 核心缺陷是「绕过用户可调设置」，改 `timeoutMs` 即已解决；非流式下用户可把 `timeoutSec` 调到 600/900，足够覆盖后台任务；
4. 若将来确实需要「首 token 后无限延长」，应作为**独立一项**做，并配套中转站兼容测试。

### 2.4 顺带判定：**主应用侧不改**

`src/lib/aiTasks/**` 等 21 个文件也在用 `CHAT_TIMEOUT_MS`，但它们：
- **没有**用户可调超时设置（`timeoutSec` 仅存在于酒馆控制面板）⇒ 不存在「声明与实现不一致」；
- 且其调用形态是 `onToken: opts?.onToken`（**透传**）⇒ 调用方给了就走流式保活 ✅

⇒ **判定不改**（并记录：若将来给主应用也加「请求超时」设置，这批要一并改）。

### 2.5 实弹验证路径（待人工）

本次仅做静态验证（tsc / lint / 157 单测）。**行为**验证需实弹：

1. 酒馆控制面板把「请求超时」设为 **30 秒**（远小于 180）；
2. 用本地慢模型（如 27B）触发「整理本场记忆」；
3. 若在 ~30 秒触发超时提示 ⇒ 说明用户设置**已生效**（修复前无论如何都要等到 180 秒）。

## 三、批次 2 · 安全面 + 叠类清理

### 3.1 `will-navigate`（`electron/main.cjs`）

原先只设了 `setWindowOpenHandler`（拦 `target="_blank"` 新窗口），**同窗口导航无人管** ——
正文/设定里若出现不带 `target` 的外链，一点就把主窗口导航离开应用、且无返回路径。

```js
const APP_ORIGIN = (() => {
  const u = process.env.ELECTRON_START_URL
  if (u) { try { return new URL(u).origin } catch { /* 非法 URL 退回 file:// 口径 */ } }
  return 'file://'
})()
win.webContents.on('will-navigate', (e, url) => {
  if (url.startsWith(APP_ORIGIN) || url.startsWith('file://')) return
  e.preventDefault()
  shell.openExternal(url).catch(() => {})
})
```

### 3.2 同步文件路径收窄（`electron/main.cjs`）

原先 `sync:readFile` / `sync:writeFile` 直接吃渲染层传来的**任意路径**（等于把「任意文件读写」原语暴露出去）。
现做**零契约成本**收窄：

```js
const assertSyncPath = (p) => {
  const s = typeof p === 'string' ? p : ''
  if (!s || !path.isAbsolute(s) || !s.toLowerCase().endsWith('.yfe')) {
    throw new Error('同步文件路径非法：只接受绝对路径且以 .yfe 结尾')
  }
  return s
}
```

- 依据：云同步载体**恒为 `*.yfe`**（`syncTransport.ts` 的 `CLOUD_FILE_NAME = '青春幻想引擎-同步数据.yfe'` 与 `<sha256>.yfe`）
- 原子写的三处路径（正文件 / `.tmp` / `.bak`）全部改走 `safe` 变量
- **未做**「限定在同步目录下」：主进程并不知道同步目录（由渲染层保存）⇒ 那需要新增 IPC 契约 + 时序处理，风险大于收益（详见 §五·待办）

## 四、批次 3 · 巨型组件拆分：**评估后判定不拆**

### 4.1 实测数据（内聚信号）

| 组件 | 行数 | 组件自身 useState | useMemo | useCallback | useEffect |
|---|---|---|---|---|---|
| `TavernScript.tsx` | 896 | **9** | 1 | 2 | 2 |
| `NovelEditor.tsx` | 838 | 0 | 0 | 0 | 0 |
| `TavernFree.tsx` | 812 | 0 | 0 | 0 | 0 |

### 4.2 判定与理由

**`NovelEditor` / `TavernFree`：不拆。** 它们**组件自身 0 个 hook** —— 逻辑早已抽进
`useNovelEditorModel` / `useTavernFreeModel`（项目既有惯例）⇒ 剩下的几乎纯 JSX。
再拆只是「把一段 JSX 挪到另一个文件」，**收益仅组织性，代价是 props 传参样板**。

**`TavernScript`：也不拆。** 虽然它有 9 个 useState（逻辑与视图混杂），但：
1. 这 9 个状态（`storyDirty` / `scriptDirty` / `saving` / `drafting` / `seed` / `refs` / `interviewOpen` / `importOpen` / `storyCharCount`）
   被三栏 JSX（树列表 / 六栏编辑 / AI 起草）**深度引用** ⇒ 抽 hook 后需返回 20+ 字段，**props 链变长，可读性未必提升**；
2. 项目**无 React 测试基建**（无 vitest/RTL，只有自建 build-test + DOM 桩）⇒ 纯搬移的**行为等价无法静态证明**，
   只能靠实机回归；而收益只是组织性 —— **风险/收益不划算**；
3. 它**该拆的部分已经拆过了**：两个弹窗早已独立成 `TavernScriptImportDialog.tsx` / `TavernScriptDialog.tsx`
   （见 `audit-coverage` 清单），剩下的三栏是「页面级布局 + 紧耦合选中态」，属**内聚紧密**的典型。

### 4.3 何时才该拆（触发条件，供下轮判）

满足**任一**即值得单独立项：
- 某个巨型组件**又要新增一大块独立功能**（此时顺手拆出那块，语义边界清晰）；
- 组件出现**行为缺陷**且根因是「多处状态互扰」（此时拆是修 bug 的手段，不是为了行数）；
- 项目引入 **React 测试基建**（拆完能配单测，行为等价可自动验）。

⚠️ 反例提醒：**不要按行数摊派**。896 行但内聚紧密的组件，拆完可能更难读。
