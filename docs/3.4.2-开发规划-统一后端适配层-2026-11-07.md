## 1. 目标与原则

**目标**：两条开发线，共用一套「能力声明 + 可插拔 driver」骨架——

- **开发线一**：让引擎具备「把外部 Agent 软件接入为可选模型后端」的能力，且可复用到后续更多 Agent 软件，为长篇创作补上「整库级、多步、人在回路」的新作业形态。
- **开发线二**（追加）：把 API 模式从仅 `ollama` 原生 / OpenAI 兼容两种**线协议**，拓展到主流协议族，让更多平台与厂商官方原生端点**不经中转直接接入**。

两条线都必须在**不破坏现有 AI 功能全量**的前提下完成（口径见 §2.1：43 是登记提示词条数，不是功能数）。

**原则**：

- 以现有调用链为唯一事实来源，不新建平行 AI 系统；能复用就复用，不能复用先说明原因。
- 核心创作流程**离线可用、不依赖 AI、不依赖任何 Agent 软件**；Agent 后端永远是可选项，未配置时行为与 3.4.1 逐字一致。
- 合规优先于省额度。订阅额度的使用方式以厂商当期条款为准，条款风险由主人在知情前提下决策，规划不替主人承担该判断。
- 外部 Agent **默认只读**；需要回写时走引擎既有的「导出项目包 → 导入」通道或产出独立建议文件，禁止外部进程直接写库。
- 协议适配与 Agent 适配共用骨架；新增协议不得改变既有 provider 的默认行为、存储键与解析键名。
- 开发线二是纯引擎内、纯合规能力，**不与订阅额度条款绑定**；不得用它包装或伪装订阅额度来源。
- 不承诺模型质量、额度稳定性或厂商协议长期不变；联网资料只作设计参考，不作质量证据。

🔴 **口径澄清（复核修正）**：**43 是 `registerPrompt` 登记的提示词条数，不是 AI 功能数**。实际功能明显更多：仅 `src/lib/aiTasks/` 就导出 38 个 `ai*` 函数，另有酒馆约 15 处、模板补全 / 对话引导 / 使用答疑 / AI 助手 / 创意访谈、能力探测、市场雷达，以及伴写 / 连写 / 设定侦测等自动链路。本文后续统一表述为「**现有 AI 功能全量**」，不再用 43 指代功能数量。

**盘点口径的一处待核对**：此前会话口径中的「6 组系统提示词」，代码里**未找到字面注册表**；可确认的只有 43 条登记提示词 + 8 个板块分组。若该口径来自某份盘点文档，开发前须核对来源，不据此新增结构。

**结论**：只要对面提供 OpenAI 兼容端点并支持 SSE、`messages` 数组、可取消、可忽略不认的字段，**引擎零产品代码改动即可接入**。接线不是难点——但这句话只覆盖「已有 OpenAI 兼容端点」的情形；厂商**原生端点**必须新增协议适配，正是开发线二要解决的问题。

### 2.3 四条技术路线对比

| 路线 | 用上订阅额度 | 合规 | 引擎改动 | 功能覆盖 | 形态 |
|---|---|---|---|---|---|
| **A 本地兼容网关** | 能 | 🔴 违规 · 有社区停权报道 | 零（填 `baseUrl`） | 现有 AI 功能近乎全可用 | 桌面 / 便携 |
| **B 官方 ACP 交互式** | 能 | 🟢 合规 | 需适配层 | 手动派长任务可用；自动链路全废 | 桌面 / 便携 |
| **C 官方 AI Studio / Gemini Enterprise key** | 不能（按量计费） | 🟢 合规 | 零 | 全功能 | **三形态** |
| **D 只读 MCP 数据桥** | 不能（不解决额度） | 🟢 合规 | 零产品代码 | 只做数据互通 | 桌面 / 便携 |

**关键判断**：A 与 C 是同一个技术方案（唯一差别是额度来源）；B 是另一套协议。想「用已付额度 + 不冒账号风险」只剩 B，而 B 是「人派任务给 Agent」而非「引擎调模型」。三者取舍不由架构决定，由主人在 §0 拍板。

**形态边界**：任何本机端点只覆盖桌面 / 便携；网页版依 P9 定案一律禁用（**仅限本机 / 局域网端点**）。联网 API 在网页形态可用，但是**浏览器直连厂商**（静态核对服务端未见 AI 代理端点），密钥为用户自带、浏览器可见；新增协议须逐家实测 CORS 预检，详见 §4.F.3。若未来要覆盖网页形态的 Agent 后端，须另立服务端 + 认证方案，本版不做。

### 2.5 主流线协议现状（2026-11-07 联网核对，开发线二依据）

三大协议家族 + 现有两条，关键差异落在**鉴权、system 位置、消息容器、SSE 事件族、结构化输出**五处：

| 协议族 | 端点 | 鉴权 | 系统提示 | 消息容器 / 助手角色 | 流式 | 结构化输出 | 引擎现状 |
|---|---|---|---|---|---|---|---|
| OpenAI Chat Completions | `/chat/completions` | Bearer | `messages` 内 `system` / `developer` | `messages` / `assistant` | 同端点 `stream:true`，`[DONE]` 收尾 | `response_format` | ✅ 已有 |
| Ollama 原生 | `/api/chat` | 通常无 | `messages` 内 `system` | `messages` / `assistant` | 每行裸 JSON、`done:true` 收尾 | `format` | ✅ 已有 |
| OpenAI Responses | `/v1/responses` | Bearer | 顶层 `instructions` | `input` items / `output` | 具名事件 `response.output_text.delta` → `response.completed` | `text.format` | ❌ 无 |
| Anthropic Messages | `/v1/messages` | `x-api-key` + `anthropic-version` | **顶层 `system`** | `messages` / `assistant` | 具名事件 `message_start` → `content_block_delta` → `message_stop` | `output_config.format`（旧 `output_format` 已被取代） | ❌ 无 |
| Google Gemini generateContent | `/v1beta/models/{model}:generateContent` | `x-goog-api-key` 或 OAuth2 | **顶层 `systemInstruction`** | `contents` parts / 角色 **`model`** | **独立端点** `:streamGenerateContent?alt=sse`，**无** `[DONE]` | `generationConfig.responseMimeType` / `responseFormat`（`responseSchema` 已弃用） | ❌ 无 |
| Amazon Bedrock Converse | AWS SDK 操作名（非 HTTP 路径） | SigV4 / AWS 凭证 | 顶层 `system` | `messages` / `assistant` | 独立操作 `ConverseStream` | `outputConfig.textFormat` | ❌ 不在首批 |

**三个必须说清的判断**：

1. 「OpenAI 格式」本身不是单一格式：Chat Completions 与 Responses 是两套，前者仍被广泛支持、长期可用，不因新增 Responses 而废弃。
2. Gemini 的助手角色叫 `model` 而非 `assistant`，且无 `system` 角色；流式走**独立端点**、无结束哨兵——这三点若照抄 OpenAI 分支会静默失败。
3. 各家结构化输出字段近年都在改名（第三方资料提及 Anthropic `output_format` → `output_config.format`、Gemini `responseSchema` → `responseFormat`）。🔴 **本表字段名系第三方整理、未经官方文档逐条取证**，§11 已列厂商官方入口；**开工须以厂商当期官方文档为准**，不照抄本表实现。
4. **浏览器直连各家 CORS 策略不同**：Anthropic 需 `anthropic-dangerous-direct-browser-access: true` 头、Gemini 原生支持 CORS、OpenAI 各家口径不一且资料互相矛盾。网页形态能否用新协议**必须实测预检**，不静态断言可用。

**开发线二的价值**：让路线 C 从「必须找 OpenAI 兼容中转端点」变成「厂商官方原生端点直连」，减少中转依赖、提高可用性与模型能力覆盖（尤其 Gemini 官方通道，直接对应主人最初的 Gemini 3.8 Flash 诉求）；同时让「协议层」与「后端层」解耦，后续接更多 Agent 软件时不必再改协议解析。

## 3. 功能影响矩阵（回答「哪些能用、哪些不能用、新增什么」）

### 3.1 现状：API 模式实现了什么

三大类 + 旁路 + 自动链路：

| 类别 | 代表 | 对后端的硬要求 |
|---|---|---|
| A 同步结构化 JSON（最脆弱） | 六大审读诊断、取名、敏感词复核、整理、拆书、实体抽取、章后变化、全书设定汇总、细纲对照、答疑、酒馆 12 处结构化小任务 | 一次性返回**完整、可解析、无过程文本**的字符串；关推理低温；可取消；长输出还依赖流式防超时。能力探测虽同为小 JSON，但受 15s 硬超时约束，单列见 §3.2 |
| B 长文本批处理 | 设定圣经、大纲、整章改写、逐章连写、分块校对、续写计划 | SSE 首 token 清总超时、空闲判停滞、中断保留已收片段、重复发起（字数校准 3~8 次 / 空结果重试 / 兼容降级） |
| C 多轮对话 | 酒馆 15 处、AI 助手、对话引导、创意访谈 | 完整 `messages` 历史数组、每轮重组 system、`think:false`、采样参数透传、独立模型解析 |
| D 旁路 / 自动静默 | embedding 语义索引与召回、模型清单与卸载；伴写 ghost（停笔 800ms）、连写流水线、写后设定侦测补登、章后整理、酒馆轮次结束自动链 | 无人值守 + 静默 + 低延迟；embedding 与模型清单**完全不经过 chat()** |

**两项曾误归入旁路的功能（复核修正）**：**能力探测**（`src/lib/ai/capabilityTest.ts`，手动点确认 → `chat()` 小 JSON、15s 硬超时）与**市场雷达**（`src/components/dialogs/MarketRadarDialog.tsx` 手动发起 → `webSearch` 检索 + `chat()` 总结）都**走 `chat()`**，不属于旁路，也不是无人值守自动链路。

### 3.2 接口模式下的可用性

| 分组 | 代表功能 | 接口模式 | 判据 / 原因 |
|---|---|---|---|
| 🟢 **原样可用** | 六大审读、取名、敏感词、整理、大纲、灵感融合、答疑、设定圣经、拆书、分块校对 | 可用 | 手动单轮、允许等待；端点能吐同步字符串即可。需逐项实测，不静态断言 |
| 🟡 **需适配** | 酒馆多轮、对话引导、AI 助手、逐章连写、**能力探测**、**市场雷达** | 需映射层 | ACP 是 session 语义，须把 `messages` 数组、五层 system、采样参数逐轮映射；中断与重复调用语义不同。能力探测受 15s 硬超时约束、市场雷达是「检索 + 总结」两段式，均需单独验证，不属「彻底失效」 |
| 🔴 **用不了** | 伴写 ghost（1~3s）、一键连写流水线（每章 3~8 次无人值守）、写后自动设定侦测、章后整理、酒馆轮次自动总结 / 变量刷新 | 不可用 | 撞两道墙：ACP 交互式需人确认；官方禁止自动化循环。且这类调用正是封号遥测的触发特征 |
| 🔴 **彻底失效** | 语义索引 / 召回 / 知识库重建、模型清单与卸载 | 不可用 | 这些走独立旁路、不经 `chat()`，Agent 亦不提供 embedding / tags 端点，**改适配层也捞不回来**。能力探测与市场雷达已移至「需适配」（复核修正） |
| 🟢 **新增能力** | 见 §3.3 | 新增 | 结构上 API 模式做不到；市场雷达类「检索 + 总结」在 Agent 轨反而可能增强（与 §3.3 第 5 条一致） |

**核心判断**：**接口模式不是「更强的同一个东西」**。API 模式是「文本进／文本出、无状态、可重复调用」的同步函数；Agent 模式是「有状态、带工具、人可介入」的长任务。功能增减是范式差异，不是缺陷。因此正确形态是**双轨并存，不是替换**：保底轨继续由 API 模式承担，Agent 轨承接新增能力。

### 3.3 接口模式带来的新增能力

1. **整库级跨章任务**：不再受 8000~12000 字资料窗口硬闸限制，可做全书伏笔闭环、人物线一致性、全书设定汇总。
2. **多步自主工作流**：Agent 自行拆解、检索、执行、回读校验，不靠引擎侧循环拼装。
3. **直接产出文件 / 项目包**：产出独立建议文件、章节稿或可导入包，回写走既有导入通道。
4. **人在回路审核**：Plan → diff → Review 的产物机制，作者先审再落库；与「AI 只辅助」红线契合。
5. **Agent 自带工具与联网**：终端、浏览器、MCP 工具，可承接市场雷达这类「检索 + 总结」两段式任务（与 §3.2「需适配」一致）；现有实现是 `webSearch` + `chat()`，Agent 轨只做能力增强，**不宣称替代全部检索通道**。
6. **多 Agent 编排 / 任务级断点**：长任务可暂停、恢复、留痕。

## 4. 方案设计：统一后端适配层（两条开发线共用骨架）

> 本节为**设计意图**，不是已实现结构。所有模块的落点、命名与依赖方向须在 P0 结构核查后确定，避免违反 `ai.ts` 门面 / `aiCore` 叶子分层与三段禁互 import 的架构红线。

**两条线，一套骨架**：开发线一（§4.A~4.E）解决「后端是谁」——本地模型 / 联网 API / Agent 软件；开发线二（§4.F）解决「用什么线协议说话」——Ollama 原生 / OpenAI 兼容 / Anthropic Messages / Gemini generateContent / Responses。两者正交组合，共用 §4.A 的能力声明与 §4.B 的 driver 注册；**一个后端 = 一个协议 driver + 一组能力声明**，现有 AI 功能侧始终不动。

### 4.A 能力声明契约

每个 driver 声明自身能力，作为路由唯一依据：

| 字段 | 含义 | 缺失时 |
|---|---|---|
| `stream` | 能否 SSE 逐块输出 | 长文任务不路由到该 driver，或显式降级并留痕 |
| `structured` | 能否保证纯净结构化输出 | A 类 JSON 任务不路由 |
| `cancel` | 能否中途取消并保留片段 | 长任务不可中断须在界面写明 |
| `multiTurn` | 能否接受外部 `messages` 历史 | C 类多轮任务不路由 |
| `embedding` | 是否提供 embedding 端点 | D 类语义链路保持原状，不由 Agent 轨接管 |
| `latency` | 首响应量级 | 伴写等低延迟链路不路由 |
| `unattended` | 是否允许无人值守循环 | 🔴 官方条款禁止时一律 `false`，且**用条款约束而非技术手段**保证 |
| `quota` | 额度口径（订阅 / 按量 / 本地） | 用量账本按真实口径记录，不许把订阅调用报成按量 |

### 4.B 可插拔 driver

- 一个**后端（协议族或 Agent 软件）**对应一个 driver；新增后端 = 新增 driver + 能力声明，**现有 AI 功能侧不动**。
- 首个 driver 以 Antigravity 为验证对象；抽象层不得写死任何 Antigravity 专属字段。
- driver 只做协议适配，不碰提示词、不做内容改写、不缓存作品正文；避免与 `injectUserSystemPrompt` 的兜底注入语义打架。
- 配置沿用现有模型设置入口；新增配置项须同步 `AIProvider` 类型、持久化、能力缓存按 pid 比对、用途路由。

### 4.C 三轨路由与降级

| 轨 | 承担 | 规则 |
|---|---|---|
| 保底轨 | 现有 AI 功能全量 | 未配置 Agent 后端、且未配置新协议时与 3.4.1 逐字一致；配置后仍默认走原通道 |
| 需适配轨 | 能力不足的任务 | 按能力声明降级或**跳过并留痕**，禁止静默返回空；不得把「解析失败」写成「审了没问题」 |
| 增强轨 | §3.3 新增能力 | 仅手动触发、显式选择；产出独立文件或走导入通道 |

降级与拒绝必须**可观测**：写进调用归属与用量账本，界面如实提示「本次未执行 / 由何原因跳过」，不伪造绿灯。

### 4.D 只读边界与数据一致性

- 桌面 / 便携为「整库单 JSON + 防抖 + 原子写 + 同源 Web Locks」，**外部进程直接写会打穿一致性** ⇒ 默认只读。
- 网页游客数据在浏览器 IndexedDB，外部进程读不到；网页云端须另走服务器 API + 认证，本版不覆盖。
- 需要回写时：产出独立建议文件，或走既有「导出项目包 → 导入」通道；导入后必须按既有判据重建资料索引。
- 新增持久数据（driver 配置、能力声明、任务留痕）须明确：旧数据默认值、迁移、回退、删除、同步、导出与恢复策略；🔴 改数据结构必问「写入侧改了吗」。

### 4.E 形态边界

网页版一律禁用本机 / 局域网端点（P9）；适配层三形态判定以 `platform.ts` 为准（`WEB` 优先）。桌面包实机验证须带 `--no-sandbox --user-data-dir=<临时>`。

### 4.F 开发线二：多协议接入层（2026-11-07 主人追加）

#### 4.F.1 先拆语义，再扩协议（🔴 最关键的一步）

`AIProviderType` 目前**一个字段兼任两个正交语义**：线协议 + 本地/联网。静态核对全库约 **24 处** `type === 'ollama'`，其中约一半判「本地 / 联网」（`src/lib/aiCore/localModelPolicy.ts`、`src/lib/ai/modelCapacity.ts`、`src/lib/aiCore/session.ts`、`src/lib/app/diagnostics.ts`、`src/lib/semantic/settings.ts`、`src/components/settings/AIConfigPanel.tsx`、`src/components/app/WelcomeAISetup.tsx`），另一半判「线协议」（`src/lib/aiCore/chat.ts` 分发与用量来源、`src/lib/aiCore/transport.ts` SSE、`src/lib/semantic/embed.ts` 端点选择、`src/lib/ai/modelSampling.ts` 采样六项下发、`src/components/tavern/TavernControlModes.tsx` 控件）。后者甚至明确注释「判据是 `type === 'ollama'`，**不是本地**」。

- **禁止**直接把 `'anthropic' | 'gemini' | 'responses'` 塞进原联合类型了事——会把新协议误判成联网（碰巧对）或把 Ollama 本地判定、采样下发、用量解析通道带偏；更糟的是「碰巧对」不会报错，属于静默失明。
- **建议**拆成两个正交维度：`protocol`（线协议枚举）与既有 `local` / `baseUrl` 判定的 locality；旧数据反序列化时按原 `type` 映射出默认值。
- 🔴 **列名＝存储键**：既有 `type` 存储键不改，只做显示名与反序列化默认值；🔴 **改数据结构必问「写入侧改了吗」**：新增字段须同步 `providerFromPreset()`、`headersForPresetSwitch()` 与配置界面保存路径。
- 新 driver 落在 `aiCore` 叶子层，不引入循环依赖；`src/lib/ai.ts` 门面显式再导出，禁 `export *`。

#### 4.F.2 协议 driver 契约（在 §4.A 能力声明之上追加）

| 字段 | 含义 | 缺失 / 差异时 |
|---|---|---|
| `auth` | 鉴权方式（Bearer / `x-api-key`+版本头 / `x-goog-api-key` / 无） | 配置界面按协议显示必填项，不混用 `apiKey` 语义 |
| `systemSlot` | `messages` 内 / 顶层 `system` / `systemInstruction` / `instructions` | 映射层统一处理，提示词内容**逐字不变** |
| `assistantRole` | `assistant` / `model` | 多轮历史映射，酒馆 15 处不受影响 |
| `streamEvents` | 事件族与结束判据（含「无哨兵、靠连接关闭」） | 受控假端点逐协议验证，未知事件优雅忽略 |
| `streamEndpoint` | 同端点 / 独立端点 | 独立端点须单独实现取消与超时语义 |
| `structuredField` | 各家结构化输出字段名 | 不得擅自强下发，见下条 |
| `usageShape` | 用量字段位置 | 按协议解析，账本口径不变 |

🔴 **结构化输出沿用现有能力闸**：现网默认 `wireFormat='none'`（JSON 靠提示词文字约束），只有端点能力被确认才下发 `response_format` / `format` / `output_config` / `responseMimeType`（**具体字段名以厂商当期官方文档为准，§2.5 表仅第三方整理**）。新协议**不得**借「支持新格式」之名悄悄改变现有调用点的请求体与既有 JSON schema 契约。

#### 4.F.3 兼容性硬约束

- 旧配置（3.4.1 保存的 provider）反序列化后行为**逐字一致**；未配置新协议时全链路与 3.4.1 一致。
- 既有兼容重试三级降级（full → noToggle → bare）、流式失败转非流式重试、Ollama `format` 400 撤字段等行为**按协议分别实现，不得串味**。
- `signal` 取消、`onToken` 流式、首 token 清总超时、空闲 120s 停滞判定、`partialText` 保留，五条契约逐协议对齐。
- 能力探测 15s 硬超时、`protocol` 标签与能力缓存按 pid 比对须同步；用途路由 `aiRouting.ts` 不因协议变化改变分工语义。
- embedding 旁路 `src/lib/semantic/embed.ts` 有自己独立的 `'ollama' | 'openai'` 类型，**首批保持原通道不动**，明确列为未覆盖；不为了「统一」把它硬塞进新协议层。
- 网页端本机端点禁用（P9）与三形态判定不受影响；新增协议不扩大任何 AI 发送范围，沿用既有明确选择与清单。
- 🔴 **网页形态浏览器直连边界（复核补漏）**：`src/lib/aiCore/transport.ts` 的 `fetchWithTimeout` 直接 `fetch(url)`，静态核对服务端未见 AI 代理端点 ⇒ 网页版是**浏览器直连厂商**。由此两条硬约束：① 新协议须**逐家实测 CORS 预检**（Anthropic 需 `anthropic-dangerous-direct-browser-access: true` 头、Gemini 原生支持 CORS、OpenAI 口径不一），未通过即在网页形态标**不支持**、如实留痕，不伪装可用；② 沿用「**密钥为用户自带、浏览器可见**」的既有边界，界面须明确提示，🔴 **本版不新增服务端 AI 代理**（那属 §2.3 的形态扩展，须另立认证方案与授权）。
- 🔴 **版本升级判据（复核补漏）**：本版若升 3.4.2，须按既有 **4 处**同步——`package.json`、`package-lock.json` 头部两处、`src/lib/help/registry.ts` 的 `SUPPORTED_APP_VERSION`、`README.md`；`tests/helpCenter.test.ts` 有「手册版本 ≥ 包版本」门禁，漏改必红。🔴 `package-lock.json` 批量替换须逐处核对，**勿误伤同名第三方依赖版本号**（3.4.1 曾误改 `temp-file@3.4.0`，会破坏 `npm ci` 校验）。

#### 4.F.4 首批范围建议（P0 决策第 4 项）

| 优先级 | 协议族 | 理由 | 备注 |
|---|---|---|---|
| 1 | Anthropic Messages | 生态最广、Claude 系主流；系统提示在顶层，差异典型可验证骨架 | 需 `anthropic-version` 版本头 |
| 2 | Google Gemini generateContent | 直接对齐路线 C 官方 key 与主人最初的 Gemini 3.8 Flash 诉求 | 官方另有 OpenAI 兼容端点可作降级对照 |
| 3 | OpenAI Responses | 新能力优先落地，但 Chat Completions 仍完全支持，收益递减 | 不做「弃旧换新」 |
| 暂缓 | Amazon Bedrock Converse 及厂商私有协议 | SigV4 / 云凭证复杂度高，与创作场景收益不匹配 | 只登记，不排期 |

#### 4.F.5 验收（开发线二独立判据）

- 每个新协议至少一条**端到端纵切**：连通性测试 → 结构化 JSON 任务 → 流式长文 → 中途取消 → 用量解析 → 失败降级，逐项留证据。
- 现有 AI 功能按 §3.1 三类各抽样：提示词内容与解析键名**不因协议变化而改变**，同一夹具前后对照（43 仅指登记提示词条数，不是抽样数）。
- 受控假端点注入：未知 SSE 事件、中途 error、无结束哨兵、结构化字段 400 —— 解析失败不得静默当成功，不得把「空」写成「审了没问题」。
- 网页形态逐协议记录 CORS 预检实测结果（通过 / 阻塞 / 未运行）；密钥暴露提示文案实机可见；未通过者不得在界面显示为可用。
- 三道门禁 + 全量审计 `complete`；新增用例登记 `tests/run-batches.sh`，夹具内 `src/...` 字面量须真实存在。
- 官方协议字段以**当期厂商文档**为准，不把 §2.5 的联网快照当实现依据；文档引用跑 `check-doc-refs --inuse` / `--source`。
