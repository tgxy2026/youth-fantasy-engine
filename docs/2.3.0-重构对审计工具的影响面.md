# 2.3.0 结构优化 · 对「六维审计工具」的影响面盘点

> 起因：老大布置 2.3.0 定向重构时特别提醒——**「如果影响到了我们之前写好的六维审计工具，记得要同步进行修改」**。
> 本文是该提醒的落实：逐支排查哪些工具依赖了「会随重构变化的假设」，并把它们改成**结构无关**。
> 盘点日期：2026-09-19　｜　状态：已完成加固 + 已验证

---

## 一、为什么要专门盘这一遍

六维审计工具（`skill: novel-studio-audit-fix` 的 `assets/` 下 14 支脚本）**是"看代码结构"的工具，因此它们自己就写死了大量关于代码结构的假设**。

这是最容易出事的地方，理由是：

| 风险特征 | 说明 |
|---|---|
| **失效不报错** | 脚本里的路径/清单对不上时，绝大多数**不会崩**——只会**少匹配 / 多匹配**，输出一个"看起来很正常"的错误数字 |
| **反向迷惑** | 最坏的一种失效是「把该排除的算进来」：`audit-prompt` 一旦漏排除出厂数据，会凭空多报 22 条假资产、token 合计从 1.3 万虚报成 10 万，而报告里**看不出任何异常** |
| **复跑对比失效** | 重构的可信度全靠「改前改后跑同一支扫描器比数字」。工具自己错了 ⇒ 这张对比表全废 |
| **越晚发现越贵** | 重构做完才发现工具失效，就无法区分「结构真的变好了」与「工具看不见了」 |

**结论：加固必须做在动手之前**（本次即按此顺序执行）。历史已经证明过这一点——`audit-dead.mjs` 的 v1 有系统性 bug，曾把 42 个类型误报成死代码（虚报 49、真实 7）。

### 2.1 受影响的（🔴 需要同步修改）

| # | 位置 | 原假设 | 为什么会被本次重构打破 | 处置 |

### 2.3 ⚠️ 盘点中发现的一处**事实更正**

原计划（`docs/2.3.0-项目重构必要性评估.md` 的 D3）表述为「数据文件混居 `src/lib` 共 14,868 行」。逐文件核对后**不准确**：

| 文件 | 行数 | 真实性质 | 处置 |
|---|---|---|---|
| `seedContent.ts` | 7,658 | ✅ 纯数据（章节正文） | **搬** → `src/data/` |
| `materialData.ts` | 5,725 | ✅ 纯数据（素材库，文件头自己写着"本文件只有数据，不含逻辑"） | **搬** → `src/data/` |
| `seedData.ts` | 1,485 | ❌ **是代码**——`createDemoProject()` 工厂，import 了 `db` / `types` / `schema` / `id` / `textStats` / `date` | **留在 `src/lib/`** |

⇒ 真正搬迁的是 **13,383 行**，不是 14,868 行。`seedData.ts` 被 11 个测试文件 + `App.tsx` + `ProjectHub.tsx` 引用，若照原计划一起搬会误伤一大片。

**教训**：**按文件名判断"这是不是数据文件"不可靠，必须打开看内容**（是否含函数/import 逻辑模块）。

## 三、加固原则（写进工具，防再犯）

本次三处修改遵循同一条原则：

> 🔴 **工具里不要出现「完整源码路径」作为判断依据；能用「文件名」或「目录清单 + 登记」就不要用路径拼接。**

理由：路径会随重构漂移，而**漂移不报错**。文件名与显式清单则会在重构时表现为"一眼能看出的需要修改"。

配套要求（已写进脚本注释）：

| 场景 | 要求 |
|---|---|
| 要排除「某几份出厂数据」 | 按 **basename** 匹配 |
| 要判断「某目录属于哪一层」 | 抽出**目录白名单常量**，并在注释里写明「新增平级目录必须登记」 |
| 新增 `src/` 下的平级目录 | 同步检查 `audit-graph.mjs` 的 `NO_UI_DIRS` 与 `tests/importCycles.test.ts` 的 `NO_UI_DIRS`（**两处**） |

## 四、验证方式（含负面对照）

改动只碰工具、不碰产品代码，因此验证目标是「**工具在搬家后仍给出正确结论**」，分三步：

1. **正向**：搬家后复跑八支扫描器，与 `.workbuddy/tmp/*-baseline.txt` 逐节对比 —— 除"数据文件路径改显 `src/data/`"这一预期变化外，**数字不应有其它变动**。重点看 `audit-prompt` P1 的**合计 token**（应仍在 1.3 万量级，若跳到 10 万即加固失败）。
2. **负面对照**：把 `audit-prompt.mjs` 临时改回**路径写法**（`'lib/seedContent.ts'`）复跑一次，确认 P1 合计 token **确实会跳到 10 万** —— 这证明加固不是"恰好没触发"，而是真的在起作用。
3. **回归**：`tsc --noEmit` / `eslint src` / `tests/run-all.mjs` 三方基线与改动前逐项一致。

> 负面对照是这套流水线的一贯要求（见 SKILL「修复后必须做负面对照测试证明用例有效」）——**没有负面对照的"通过"不算通过**。

## 五、结论

- 六维审计工具共 **14 支脚本**，其中 **3 支**含会被本次重构打破的结构假设（`audit-prompt` / `audit-graph` / `audit-scan`），另 **1 个项目自带闸**（`tests/importCycles.test.ts`）同类。
- 已全部改为结构无关写法，并**先于搬家落地**，避免出现"重构做完才发现工具看不见了"的窗口期。
- 其余 11 支脚本与 3 个相关 skill **不受影响**（已逐条核实，非默认假设）。
- 顺带更正了原评估里的一处事实：`seedData.ts` 是代码不是数据，搬迁量应为 **13,383 行**。
