# 一键拆书 · 方案规划（基于调研 + 项目实情）

> 文档状态：规划稿（仅调研与方案，不含开发实现）
> 适用版本：novel-studio 2.1.3（当前桌面版）
> 目标：把「输入现成小说文本 → 模型分析正文 → 回填到项目各设定模块」做成可落地功能
> 红线（来自项目既有约定）：本地优先、零联网、绝不静默覆盖用户已锁定设定、复用现有 AI 层与 schema

---

## 0. 背景与范围

### 0.1 用户诉求
- 输入：现成小说文本（txt 粘贴 / 上传 / 已分章节的正文）
- 处理：调用模型分析正文内容
- 输出：把分析产物填写到 novel-studio 的世界设定、角色卡、关系、地理、势力、大纲、素材等模块

### 0.2 范围边界（本规划锁定）
- ✅ 做「结构化抽取 + 回填草稿」，不做「问书/剧情问答」（那是长期可选项，见 §5.3）
- ✅ 输出定位为**草稿 + 人工校对**，不是自动覆盖
- ✅ 本地模型优先（Ollama + Qwen3.8-27B uncensored），契合「商业机密不联网」红线
- ❌ 不引入独立知识图谱数据库（你们已有固定 schema，开放图谱是过度设计）

### 0.3 关键发现：项目现状已消化大部分工程难点
| 拆书难点 | novel-studio 现有能力 | 结论 |
|---|---|---|
| 实体对齐（别名合并） | 角色卡「别称」字段：正文出现别称时系统识别为同一人物；地理位置/势力/关系大量用跨表引用列 `cr()` 根治同名异写 | **难度降一档**：抽取层只需产出 canonical 名 + 别称列表，归并借力已有机制 |
| 长文本结构化输出 | `aiChatJson`（结构化 JSON）、`aiParse`（唯一解析入口，禁裸 `JSON.parse`）、`paramGuide` 共享采样参数 | 直接复用，不必新写解析层 |
| 设定回填 | StoreOps 适配层 + 三存储后端，所有模块走统一写入 | 草稿走同一写入通道，预览即所见 |
| 模型调用 | 本地 Ollama 已接（27B q6_K ≈22GB 权重 + 32K KV cache ≈8GB，RTX 5090 32GB 可跑） | 本地零 token 成本，零联网 |

## 1. 现有可复用能力盘点

| 能力 | 位置 | 拆书怎么用 |
|---|---|---|
| `aiChatJson(...)` 结构化输出 | `src/lib/ai.ts:701` | 让模型返回固定 schema 的 JSON（人物/地点/势力/关系/要素数组） |
| `parsePlainObject` / `parseObjectArray` | `src/lib/aiParse.ts`（全项目唯一解析入口） | 剥代码块、切最外层、兜底解析，**禁止裸 `JSON.parse`** |
| `paramGuide` 采样参数 | `src/lib/tavern/paramGuide.ts` | `contextBudget:24000`、`numCtx:32768`、`repeat_last_n:512`、`frequency_penalty:0.1` 等可直接复用到抽取任务（结构化抽取建议温度 0.3） |
| 角色卡 / 关系 / 地理 / 势力 schema | `src/lib/schema.ts` | 抽取产物的目标落点（字段名见 §4 映射表） |
| `cr()` 跨表引用列 | `schema.ts` | 角色「所属势力」「地理位置」、地理「势力归属」「所属地图」等自动联动、根治同名异写 |
| StoreOps 写入 | `src/lib/storeOps.ts` | 草稿写入走统一通道 |

## 2. 整体技术路线（Pipeline）

```
[输入] 小说文本(txt/粘贴/分章)
   │
   ▼
[① 切分] 按章节优先；无章节则固定 token 块 + 重叠
   │
   ▼
[② 抽取] 逐块两遍抽取：候选实体(人物/地点/势力/事件/关系/世界观要素) + 原文出处
   │
   ▼
[③ 实体对齐] 别名合并成 canonical 名（借力「别称」字段 + 跨表引用列）
   │
   ▼
[④ schema 映射] 聚合为草稿：角色卡 / 地理 / 势力 / 关系 / 世界设定 / 力量体系 / 大纲
   │
   ▼
[⑤ 校验] 原文引用核对 + 冲突检测 + 置信度评分
   │
   ▼
[⑥ 预览 + 人工校对 + 写入] 草稿绝不自动覆盖；冲突走跨表引用列
```

> 与 GraphRAG 的区别：GraphRAG 多出「社区检测 + 全局归纳」是为多跳问答设计的；你们是「填固定设定表」，不需要这一步。下文 §3.2 详列替代路径。

## 3. 各能力模块的多路径方案

> 规则：凡存在 ≥2 条可行路径，全部列出（含优缺点与适用场景），标注**我的推荐默认**；最终选型留到开发阶段结合实际研判。§8 汇总成「待研判清单」。

### 3.1 文本输入与切分

| 路径 | 思路 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 按章节切分（推荐默认）** | 解析「第X章」标题/分隔符，整章为单元 | 语义边界天然对齐剧情；便于回填「首次出场章节」 | 需章节格式规整；无章节文本失效 | 绝大多数网文（已分章） |
| **B. 固定 token 块 + 重叠** | 约 1200 token/块，块间重叠 ~100 token 防截断 | 对任意文本鲁棒；实现简单 | 可能切断人物对话/场景；需后处理拼接 | 无章节的纯文本/散文 |
| **C. 语义切分** | 按空行/场景切换/视角切换切 | 比 B 更贴剧情 | 需额外小模型判断边界；成本高 | 精抽场景级要素时 |

**推荐**：A 为主、B 兜底（无章节时）。C 留中期。
**开发待定**：章节标题正则的容错度（「第1章」「第一章」「Ch.1」混用如何处理）。

### 3.2 抽取引擎（核心）

| 路径 | 思路 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 轻量自研 schema-aligned 两遍抽取（推荐默认）** | 自写 prompt：第一遍逐块抽候选，第二遍校验+合并；输出直接对齐你们列名 | 输出即草稿、零转换损耗；本地零成本；最贴合固定 schema | 需自己写校验循环；精度依赖 prompt 质量 | MVP 首选 |
| **B. GraphRAG 全栈** | Microsoft 框架：TextUnit→实体/关系抽取→社区检测→社区摘要 | 多跳问答强；生态成熟 | 重（需图数据库/索引）；社区摘要对「填表」是浪费；本地部署重 | 仅当长期要做「问书」 |
| **C. LightRAG** | 3 步、增量、索引成本≈GraphRAG 的 1/100、支持 Ollama、MIT | 比 B 轻；支持本地 | 仍建开放图谱，与你们固定 schema 有转换鸿沟 | 想做轻量 RAG 时 |
| **D. 借鉴 novel-characters skill** | 两遍抽取+别名合并→`cast.json`+角色卡+关系图 HTML，带确定性脚本校验 | 开源可直接研读其 prompt 与别名合并范式 | 仅覆盖角色，需扩到地点/势力/世界观 | 作为 A 的起步模板 |

**推荐**：A（以 D 的 prompt/别名合并范式作起步参考）。B/C 仅作为长期「问书」底层候选。
**开发待定**：抽取是「一次大 prompt 全量」还是「逐块 + 聚合」——受本地 27B 上下文（numCtx 32768）约束，**逐块 + 聚合更稳**，推荐后者。

### 3.3 实体对齐 / 别名合并（公认最难）

| 路径 | 思路 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. LLM 投票 + 确定性校验（推荐默认）** | 让模型对每个候选判断「是否与已见实体为同一人」，附原文证据；确定性脚本做精确串匹配防篡改 | 可解释、可控；契合你们「别称」字段 | 需多轮；长文本易漏 | MVP |
| **B. 向量相似度聚类** | embedding 后按余弦相似度聚合别名 | 全自动；对长文本友好 | 需 embedding 模型；阈值难调；同形异义误并 | 配合 A |
| **C. 混合（A + B + 冲突阻断）** | LLM 初筛 → 向量校验 → 相似名阻断（AI Reader 经验）+ 跨人物冲突检测 | 精度最高（AI Reader 实测迭代方向） | 工程量大 | 中期增强 |
| **D. 直接借力 schema** | 抽取层只产出 canonical + 别称列表，归并交给角色卡「别称」字段 + `cr()` 引用列 | 几乎零额外工程 | 仅覆盖已建模块；自由文本别称仍可能漏 | 与 A 组合 |

**推荐**：A + D 组合起步（D 已消化大半难度）；B/C 进中期。
**关键经验（来自 AI Reader V2）**：canonical 选名规则、相似名阻断、跨人物冲突检测，是精度天花板所在，值得投入。

### 3.4 schema 映射与聚合

| 路径 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **A. 直接字段映射（推荐默认）** | 抽出来的 JSON 字段名直接对应 schema 列名，聚合成草稿对象 | 零中间层；预览即所见；人工校对成本低 | 需严格约束 prompt 输出键名 |
| **B. 中间开放图谱 → 转表** | 先建实体-关系图，再投影到各表 | 灵活、可做图查询 | 转换损耗大；与固定 schema 摩擦；MVP 过度设计 |

**推荐**：A。B 仅在长期做 RAG 时复用其图结构。

### 3.5 校验与质量控制

| 路径 | 思路 | 说明 |
|---|---|---|
| **A. 原文引用核对（推荐默认）** | 每条抽取带「出处章节 + 原文片段」，校验时精确串匹配防模型编造引语 | 防幻觉第一道闸 |
| **B. 六层神经符号校验（中期）** | 形态过滤/后缀方向修正/多源投票/传递性验证/层级合并/LLM 反思（AI Reader 范式） | 精度显著提升，工程量大 |
| **C. 冲突检测** | 同一字段多块给出矛盾值 → 标红待人工定夺 | 防「关系失忆」「设定漂移」 |

**推荐**：MVP 做 A + C 基础版；B 进中期。

### 3.6 预览 / 校对 / 写入（含冲突处理）

| 路径 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **A. 草稿预览 + 逐条人工校对 + 选择性写入（推荐默认）** | 弹出草稿面板，每条可改/弃/合并；写入走 StoreOps | 安全、可控；契合「绝不覆盖」红线 | 人工成本高 |
| **B. 自动合并** | 抽取结果直接合并进现有设定 | 快 | **违反红线**（静默覆盖已锁定设定）；不可取 |

**冲突处理原则**（固定）：
- 已有设定 ≠ 抽取结果 → 不覆盖，标「新增/冲突」两态，人工选
- 同名异写 → 借 `cr()` 引用列 + 「别称」字段归并
- 置信度低 → 默认进「建议」区，不进草稿主表

### 3.7 模型部署与调用

| 路径 | 思路 | 说明 |
|---|---|---|
| **A. 本地 Ollama 优先（推荐默认）** | 复用现有 Qwen3.8-27B uncensored（27B q6_K）；结构化抽取温度 0.3；采样参数照搬 `paramGuide` | 零联网、零成本、契合商业机密红线 |
| **B. 云端可选** | 用户自备 API Key 走云端大模型 | 精度更高但联网；默认关闭，需用户主动开启 |

**红线**：导入的小说文本**绝不联网**；云端模式需用户显式开启且提示风险。
**实测经验（AI Reader）**：7B 以下模型抽取准确率明显崩；你们 27B 在本地档位够用，但需强 prompt + 校验循环。

### 3.8 断点续跑 / 增量

| 路径 | 思路 | 说明 |
|---|---|---|
| **A. 章节级断点续跑（中期推荐）** | 已抽章节记 checkpoint；中断后从断点续 | zaomeng 已验证必要 |
| **B. 增量抽取** | 新增章节只抽增量，与已有草稿合并（走别名归并） | 长篇持续创作刚需 |

**MVP 可不做**（一次性抽完即止）；中期补 A，长期补 B。

## 5. 分阶段路线（按推荐落实）

### 5.1 短期 · MVP（建议 1–2 个迭代）
**目标**：跑通「分章文本 → 本地 27B 两遍抽取 → 别名归并 → 草稿预览 → 人工写入」最小闭环。
**范围**：
- 输入：分章 txt 粘贴/上传（路径 3.1-A）
- 抽取：自研两遍抽取（3.2-A/D），复用 `aiChatJson`+`aiParse`+`paramGuide`
- 对齐：LLM 投票 + 借力「别称」字段（3.3-A/D）
- 映射：直接字段映射（3.4-A），覆盖 §4.1–4.5（角色/地理/势力/关系/世界设定/力量体系）
- 校验：原文引用核对 + 基础冲突检测（3.5-A + 3.5-C 基础版）
- 写入：草稿预览 + 选择性写入（3.6-A），绝不覆盖
- 模型：本地 Ollama 优先（3.7-A）
**交付**：拆书入口（工作面板或独立页签）+ 草稿预览面板 + 写入确认
**验收**：用《吞天神脉》示范文本跑通；角色卡/地理/势力/关系回填草稿可预览、可写入、不覆盖已有设定
**不做**：图谱、RAG、增量、置信度评分 UI

### 5.2 中期 · 增强
- 抽取精度：六层神经符号校验（3.5-B）、混合实体对齐（3.3-C）
- 断点续跑（3.8-A）、置信度评分 UI
- 大纲抽取：分卷/章节细纲/伏笔台账回填（§4.6）
- 设定集导出（对标 AI Reader 设定集）
- 语义切分（3.1-C）覆盖无章节文本
- 冲突检测 UI 强化（多块矛盾值标红）

### 5.3 长期 · 深化（可选）
- **问书 / 剧情问答**：在抽取层之上叠加 LightRAG/GraphRAG 做 RAG 检索，与拆书抽取**分层解耦**（抽取产结构化设定，RAG 另做检索）
- 多模型对照（本地 27B vs 云端大模型，结果 diff）
- 可视化关系图谱自动生成（借 `faction-rels` / `relations` 数据）
- 增量抽取（3.8-B）支持长篇持续创作

## 6. 工程风险与缓解

| 风险 | 缓解 |
|---|---|
| LLM 抽取不可靠（Harvard Story Ribbons 实测 naive 抽取差） | 校验循环 + 原文引用 + 结果定位「草稿需校对」 |
| 实体对齐最难 | 借力「别称」字段 + `cr()` 引用列（已消化大半）；剩余走 3.3-A/C |
| 本地 27B 能力天花板 | 强 prompt + 校验；小模型不行（AI Reader 实测 7B 以下崩）；云端可选但默认关 |
| 长文本窗口 | 逐块 + 重叠 + 聚合；numCtx 32768 已够 |
| 写入安全 | 草稿预览 + 冲突处理；绝不静默覆盖（红线） |
| 隐私 | 本地 Ollama 优先；导入文本不联网 |
| prompt 与实现漂移 | 输出键名锁定 schema 列名；必要时加测试断言（仿 `tests/paramGuide.test.ts`） |

## 8. 进入开发阶段的待研判决策清单

> 以下选型在开发时结合实际研判，本规划只列候选与推荐默认。

1. **切分策略**：推荐 A（按章）+ B（无章兜底）；章节正则容错度待定
2. **抽取引擎**：推荐 A（自研两遍）+ D（借 novel-characters prompt）；是否逐块聚合（推荐是，受 numCtx 约束）
3. **实体对齐**：推荐 A+D 起步；中期是否上 B/C 混合
4. **schema 映射**：推荐 A（直接字段映射）
5. **校验深度**：MVP 做 A+C 基础；中期是否上 B（六层）
6. **写入方式**：仅 A（草稿+人工），B（自动合并）禁用
7. **模型**：默认本地 Ollama；云端是否作为可选开关
8. **覆盖模块顺序**：MVP 先角色/地理/势力/关系/世界设定/力量体系；大纲进中期
9. **入口位置**：工作面板新增页签 vs 独立入口（UX 待定）
10. **置信度呈现**：MVP 是否做评分 UI（推荐中期再做）
