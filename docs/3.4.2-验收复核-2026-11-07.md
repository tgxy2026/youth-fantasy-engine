### 4.1 CORS 实测记录（本轮新增证据，如实）

| 端点 | 浏览器直连（Playwright + Edge，无代理） | Node OPTIONS（经本机代理） | 判定 |
| --- | --- | --- | --- |
| `api.anthropic.com/v1/messages` | `Failed to fetch`（757 ms） | HTTP **403**，无 CORS 响应头 | **blocked**（可达但预检不通过 / 无法判定） |
| `generativelanguage.googleapis.com` | `Failed to fetch`（超时 ~168 s） | HTTP **000**（连接超时） | **blocked**（网络不可达） |
| `api.openai.com/v1` | `Failed to fetch`（~21 s） | HTTP **000**（连接超时） | **blocked**（网络不可达） |

🔴 结论边界：`Failed to fetch` **不能区分**「CORS 拒绝」与「网络不可达」，因此**不得宣称任何一家「浏览器可用」或「被 CORS 拒绝」**。本机直连环境不具备判定条件，需在可直连（或代理可透传）的环境重跑。

## 5. 偏差（须修或须明确接受）

### D-1 新三协议缺「兼容降级 / 流式失败转非流式」

- **规划原文**（§4.F.3）：「既有兼容重试三级降级（full → noToggle → bare）、流式失败转非流式重试、Ollama `format` 400 撤字段等行为**按协议分别实现，不得串味**。」
- **现状**：`openaiChat.ts` 与 `ollama.ts` 各自实现；`anthropic.ts` / `gemini.ts` / `openaiResponses.ts` **只发一次请求**，400 直接抛错，流式解析失败不重试。
- **影响**（不夸大）：三家官方端点对合法请求不会 400；但下列真实场景会退化 —— ① Responses 推理模型对 `temperature ≠ 1` 直接 400（本引擎会下发作者设置的采样温度）；② 走兼容网关时 SSE 格式不标准，只能报错、不会退非流式；③ 作者给 Anthropic 填 1.5 温度（其范围 0–1）→ 400，无兜底。
- **建议修法**（最小）：仅对「400 且报错文案含 temperature / 采样 / unsupported parameter」做**一次**去采样重发（`bare`）；流式解析失败时退一次非流式（与 `openaiChat` 同口径计数，不叠加）。补受控注入用例：结构化字段 400、流式畸形分片。

### D-2（已修，留档）协议切换时 `local` 被继承

- `043ec8a` 前：从 Ollama 切回 OpenAI 兼容会保留 `local=true`，联网模型顶「本地」标记进入本地预设组，且 `precheck` 跳过密钥校验。
- 现状：`protocolSwitchPatch()` 已复位，单测 1 条 + 浏览器探针 1 项锁住。**不构成遗留偏差**。

### D-3 网页形态未按 CORS 结果标注协议可用性

- **规划原文**（§4.F.3 / §7）：「未通过即在网页形态标**不支持**、如实留痕，不伪装可用。」
- **现状**：三家协议在网页形态与 DeepSeek 等既有联网预设一样可选、可保存，界面无「网页形态未验证」标注；只有 FAQ 文章与请求失败文案提到 CORS。
- **判定**：既未「伪装可用」（有 FAQ 声明），也未「明确标不支持」——属**未落实**。修法二选一：① 网页形态给三家协议加一行「网页形态未验证 CORS」提示；② 实测通过前在网页形态隐藏该三个预设。
