> - **内部/包名**：`youth-fantasy-engine`（小写连字符，npm 合法，决定 `userData` 目录名）。
> - **安装目录/exe**：`YouthFantasyEngine`（驼峰，仅 Programs 文件夹与 exe 文件名可见）。

## 3. 老用户数据迁移方案（核心 · D4）

### 3.1 旧数据物理位置（由旧 app 生成，name=novel-studio）
- `userData` = `%APPDATA%\novel-studio`
  - `novel-studio-data.json`（整库 JSON，含 `app:'novel-studio'` 与各 `kind`）
  - `IndexedDB/file__0.indexeddb.leveldb/`（含主库 `novel-studio` + `novel-studio-vec` + `novel-studio-kb` 三个 IDB）
  - `Local Storage` / `Session Storage` / `Preferences`（Chromium profile，按 origin 索引，与 app 名无关）
  - `data-location.json`（若用户设过自定义数据路径 → 真实数据可能在别处，迁移须读它定位）

### 3.2 首启迁移向导流程
1. 新 app 首次启动（新 `userData=%APPDATA%\youth-fantasy-engine` 为空），探测旧目录 `%APPDATA%\novel-studio` 是否存续。
2. 存在 → 弹「发现旧版（novel-studio）数据，是否导入到 Youth Fantasy Engine？」；不存在 → 全新用户，正常走。
3. 用户点「导入」→ 执行 3.3–3.5。
4. 完成后提示「导入成功，现在可以卸载旧版了」，并提供「卸载旧版」入口（见 3.6）。
5. 「设置 → 数据」保留「重新导入旧版数据」按钮（幂等，防手滑 / 多 PC）。

### 3.3 整库 JSON 文件 remap
- 读旧 `novel-studio-data.json`（或 `data-location.json` 指向的路径）。
- 遍历结构：每个信封 `app` 字段 → `youth-fantasy-engine`；每个 `kind` 命中下表即改写：
  - `novel-studio-trajectory` → `youth-fantasy-engine-trajectory`
  - `novel-studio-trajectory-book` → `youth-fantasy-engine-trajectory-book`
  - `novel-studio.tavern-preset` → `youth-fantasy-engine.tavern-preset`
- 写出新 `youth-fantasy-engine-data.json` 到新 `userData`。
- ⚠️ `generator.app='青春幻想引擎'`（中文显示串）**不改**。

### 3.4 IDB 导出重导（最难点 · D2 的代价）
> LevelDB 文件名按内容寻址，**不能简单改名**；必须「开旧库 → 读全部 store/记录 → 写新库」。
1. 把旧 `IndexedDB/` 整目录**复制**到新 `userData/IndexedDB/`（新库为空，直接覆盖，让新 app 能按旧名打开旧库）。
2. 在渲染进程（IndexedDB API 可用）逐个处理：
   - 开旧库 `novel-studio` → 读全部 store/记录 → 开新库 `youth-fantasy-engine`（触发 `db/core.ts` 的 `onupgradeneeded` 建表）→ 批量 `put`。
   - 同法处理 `novel-studio-vec` → `youth-fantasy-engine-vec`（`semantic/store.ts`）、`novel-studio-kb` → `youth-fantasy-engine-kb`（`knowledgeBase.ts`）。
   - **复用现有 `openDB` 函数**保证新库 schema 与源码一致。
3. `indexedDB.deleteDatabase('novel-studio' / '-vec' / '-kb')` 清旧库，回收 LevelDB 文件。
4. 若个别记录写入失败（schema 漂移）→ 记日志、跳过、汇总到导入报告，不中断整体。

### 3.5 Chromium profile 复制
- `Local Storage` / `Session Storage` / `Preferences` 按文件整体复制到新 `userData`（与 app 名无关，安全）。

### 3.6 卸载旧版引导
- 改 `appId` 后新旧是**两个独立 Windows 产品**：新安装器**不会**自动卸载旧版，控制面板会出现两条，直到旧版被卸。
- 导入完成后提供「卸载旧版」按钮：经旧 `appId=cn.novelstudio.yfe` 的注册表 `Uninstall` 键定位旧卸载器并拉起；找不到则引导用户去「设置 → 应用 → 青春幻想引擎（旧）」手动卸载。
- 发布文案明确写「请先卸载旧版 novel-studio，再安装 Youth Fantasy Engine；首次启动会自动导入旧数据」。

### 3.7 幂等与重导
- 新 `userData` 已有数据 → 导入前询问「覆盖 / 合并 / 跳过」。
- 「设置 → 数据 → 重新导入」可随时再跑（多 PC / 手滑场景）。

### 9.5 功能边界（不主动阉割）

- **明确不启用**：所有「云端同步 / 云盘同步 / 在线更新检查 / 需后端服务器的联网功能」一律禁用（便携版离线自包含，本就不含这些）。
- **仅当"便携版实在无法启用"才禁用 / 阉割**，须逐一评估并形成清单：
  - 依赖系统级安装的能力（桌面版安装 / 卸载、系统托盘、原生文件对话框）→ 便携版用 Web 等价实现或禁用。
  - 需常驻后台 / 开机自启的能力 → 禁用。
  - 其余纯本地能力（本地 Ollama、书稿编辑、世界观、时间线、关系图、AI 创意写作、酒馆本地对话等）**全部保留**。
- 动手前须产出「功能对照表」（桌面端功能 → 便携版状态 ✅保留 / ⚠️降级 / ❌禁用 + 禁用理由），经主人哥哥确认后再实施。

### 9.6 与 3.0 重命名的耦合

### 9.8 风险与纪律
| 风险 | 说明 | 处置 |

### 10.3 对方实现路径与具体功能（逐项固化 · 开工时的参照）

> 以下「对方实现路径 / 具体功能」来自 StoryForge 仓库 README 原文（2026-10-10 抓取）；「本项目结合点」是咱们开工时的对接方向，**不是最终设计**。

#### #1 候选→采纳 + 版本保护（Harness 运行账本）
- **对方实现路径**：一次正式 AI 任务 = `Agent Skill + 运行契约(Run Contract)` 定义任务约定 → `Harness` 记录约定 / 实际输入 / 候选 / 版本 / 检查点 / 结果 → `模型适配器` 生成候选并返回原始响应 → `正式创作采纳`：作者确认 → 校验 → `adopt()` **事务写入并回读** → 持久化「运行账本」（事件 / 检查点 / 验收回执）。
- **具体功能**
  - 候选机制：AI 先产出**候选**，作者确认后才写回正式作品，**不自动落库**。
  - 校验与写回：`FIELD_REGISTRY`（字段登记）+ `AdoptionSchema`（采纳模式：identity / required / fkChecks）+ `adopt()` —— 按模式校验后才进入正式作品。
  - 版本保护（有回归反例钉住）：**正文或上游设定变化后，旧候选不得覆盖作者编辑**。
  - 恢复：章后候选中断后可从检查点恢复，**已有候选无需再次调用模型**。
  - 可检查：上下文装配结果、运行证据、验收回执均可查。
- **本项目结合点**：已有 `previewCommit`（`lib/flow/commit.ts`）+ 创意写作候选 + 创作轨迹 / 证据包 ⇒ 在既有 preview 与轨迹上扩展统一运行账本与版本保护，**不另起炉灶**。

#### #2 上下文网关（按需分层召回 + 规模门）
- **对方实现路径**：`CONTEXT_SOURCES` 登记「AI 可从哪些来源读取」（作品设定 / 角色 / 大纲 / 正文 / 记忆等）→ `assembleContext()` 按任务装配上下文 → 作用域内读取本地数据（IndexedDB / 文件与媒资存储，由 `PROJECT_TABLES` 治理生命周期）→ 原文溯源。
- **具体功能**
  - 按需读取（非全量塞上下文）+ 原文溯源。
  - 分层召回：**远 / 中 / 近**证据；长篇规模门测试覆盖 **10 万 / 30 万 / 100 万字符**三档。
  - 缺失检查：必需证据缺失时**停止生成**，不硬写；精确编辑目标不能退化为「截取前缀」。
  - 上下文查看：作者可检查本次任务实际装配的上下文。
- **本项目结合点**：已有 `aiDataSources`（AI 读哪些数据的单一源）+ 语义检索 + 知识库 ⇒ 在其上加「远中近分层 + 规模门 + 缺失即停」，**复用既有检索**，不新建一套。

#### #3 章后整理 + 未来影响分析
- **对方实现路径**：每章写完后，把本章带来的变化作为**独立 AI 任务**走同一条 Harness 链（候选 → 作者确认 → `adopt()` 写回）；检查点可恢复。
- **具体功能**
  - 整理本章带来的**事实、人物状态、关系、伏笔**变化；作者确认需保留的内容，为下一章准备依据。
  - 未来影响分析：上游（已写正文 / 设定）变化使旧的「未来计划」失效 —— 「未来演化边界」：已写历史保持稳定，上游变化令旧未来计划失效。
  - 中断恢复：章后候选中断后可恢复，已有候选不重复调用模型。
- **本项目结合点**：已有设定变更 / 伏笔追踪 / 知情权限 / 改写后设定同步 ⇒ 章后整理做成挂在既有能力上的**统一入口闭环**，不新建孤立页面。

#### #4 一致性审计（显式触发 + 失效机制）
- **对方实现路径**：**显式触发**（按任务配置或作者触发），非后台自动跑；结果随正文变化失效。
- **具体功能**
  - 一致性审计：跨章核对事实 / 状态 / 伏笔 / 关系等冲突。
  - 失效机制：正文改动后审计结果**标记为未知、需重跑**，**不自动重试**（避免拿旧报告给新稿盖章）。
  - 保障边界：版本 / 作用域 / 结构 / 状态转换 / 写回规则由**确定性代码**检查；语义层面（隐喻、潜台词、未登记伏笔、文学效果）仍需模型 + 作者判断。
- **本项目结合点**：基于现有 `dataHealth` + 优化工单升级为「按章审计 + 正文指纹失效」，沿用方案 C 的「不常驻 / 静默跑 / 只报数」口径。

#### #5 提示词透明化 / 提示词库 / 创作规则
- **对方实现路径**：提示词库 + 创作规则 + 补充要求；作者可查看与调整任务提示词，并可检查实际装配结果。
- **具体功能**
  - 提示词**全透明可改**：内置任务提示词可见、可覆盖。
  - 创作规则：作者写自己的写作要求。
  - 上下文查看：可检查本次任务实际装配的上下文与运行证据。
  - AI 对话副驾：对话式辅助。
- **本项目结合点**：已有自定义系统提示词 + `PROMPT_ORDER`（还原注册序）⇒ 提示词库基于 `PROMPT_ORDER` 暴露并可覆盖，**保留内置默认且可复位**。

#### #6 AI 消耗统计
- **对方实现路径**：云端请求只发「当前任务所需内容」；消耗统计可观察。
- **具体功能**
  - 消耗统计：可查看调用情况；建议先用小任务验证再扩大篇幅。
  - 费用提示：API 费用由服务商收取；本地模型取决于设备与模型能力（不绑某家云服务）。
  - Key 安全：API Key 默认仅本次会话，勾选「在本机记住」才写入 localStorage。
- **本项目结合点**：咱们是桌面版，Key 存储走既有配置（**不照抄 localStorage 方案**）；统计落到每次调用记模型 / token / 耗时，按日 · 按项目汇总。

#### #7 作品版本冻结 + 版本历史
- **对方实现路径**（以短篇为典型）：创作要求与故事设计先确认 → 逐章生成 / 编辑 / 采纳 → **完成检查**（读实际正文长度、章节卡、正文完整性，显示与目标字数偏差）→ 审校（问题带章节与证据，重写针对具体章节，**审校记录绑定本次手稿内容指纹**，正文改动后需重新审校）→ 缺失章节 / 待处理候选 / 未解决严重问题**阻止发布** → 通过后新增**冻结作品版本**，后续修订保留原版 → 导出 Markdown / TXT / JSON。
- **具体功能**：完成检查、内容指纹绑定、发布闸门、冻结版本、版本历史、自动保存、完整备份。
- **本项目结合点**：已有整库备份 / 导出 + 创作轨迹 + 投稿前自检 ⇒ 版本冻结做成「定稿快照」，与既有备份 / 导出共用 `StoreOps` 数据契约。

#### #8 世界引擎（版本封存 / 跨作品引用）
- **对方实现路径**：长篇 / 短篇**由作者选择派生**（或）从零构建 → 世界草稿 → 确认并**封存** → 世界版本 → 具体产品配置并制作 → 发布作品并游玩。
- **具体功能**
  - 带来源的**语义快照**；**不可变世界版本**；按产品需求读取。
  - 同一世界可供多个作品引用；每次制作都知道用了哪一版设定。
  - 边界：原作品后续修改**不会**自动同步到派生世界；游戏进度也不自动改写共享世界。
  - 世界只保存**可版本化的语义内容**；互动产品引用冻结版本，各有自己的媒资 / 发布 / 运行数据。
- **本项目结合点**：世界快照封存可与 §9 便携版 `PortableData` 数据契约共用；派生必须**显式动作**、不自动同步（与对方一致）。

#### #11 跑团互动（#9 / #10 不开发，仅保留此项）
- **对方实现路径**：跑团 → 作品库 / 游玩；互动产品各自拥有**规则、角色知识、事件、存档与演出状态**；引用**冻结的世界版本**；完整项目备份包含剧本 / 产品媒资 / 存档。
- **具体功能**（以内置《雾港》为样本）
  - 《雾港：失潮钟声》：**18 个叙事节点、158 个节拍、三条结局**，17 项原版背景 / 立绘 / CG；可选视觉小说或文字冒险。
  - 文字冒险：可**观察、交谈、取证**；视觉小说：逐句阅读、选择分支并保存舞台进度。
  - 存档：首次开始创建**独立世界与产品发布**；「继续游玩」恢复进度，「从头开始」另建存档。

## 12. 内部自查优化项：酒馆「数值档位」未注入扮演侧

> 🧭 路线图：第 2 批 **W2-4**（与 §13 F1 / F2 打包）。

### 12.1 现状（已核实，含源码位置）

- ✅ **数值每轮进扮演上下文**：`buildVarStateBlock`（`src/lib/tavern/vars.ts:289`）挂在 system 的 **tail 层**（协议之后），注入点 `src/lib/tavern/engine.ts:718`（自由模式）。实际喂给模型的形如：
  `〖本场数值〗你此刻的状态：好感 45 · 信任 -10 · 精神 0 · 心情 … · 地点 …` ＋ 备注 ＋ 目标 ＋ 「这是给你把握分寸用的状态，不要把它抄进正文。」
- 🔴 **但「档位行为指引」只进抽取侧**：`VAR_BANDS`（`types.ts:689`）为三项数值各写了 5 档（**名字 + `effect` 行为指引**，例：好感 −60~−20「反感」＝ 刻意保持距离、对方越热络越往后退；60~100「亲密依赖」＝ 会主动分享、会说软话、会依赖对方）。这些 `effect` **只在数值抽取提示词** `buildVarExtractSystem`（`vars.ts:355-365`）里注入，用途是让「记账员」判断现在落在哪一档、该往哪走；**扮演侧零命中**（`bandOf` / `bandsOf` 仅被界面 `TavernVarsPanel` 与 `paramGuide` 使用）。

### 12.2 问题

- 扮演侧拿到的是**裸数 + 备注**，「数值 → 言行」的翻译**全靠模型自己领会**：本地小模型这一层领会得比较飘 —— 「低好感应主动疏远」「高好感应会依赖」都不是硬约束。
- 现成的档位文案只喂给了记账侧，演戏侧没吃到。

### 12.3 建议改法（最小改动 · 开工时再细化）

- 在 `buildVarStateBlock` 内用 `bandOf(key, value)` 取当前档位，把**档位名 + effect** 并进那一块（每轮注入）。
- 🔴 边界与纪律：
  - 只对**数值项**做 —— 文本项（`mood` / `place`）无档位，`bandsOf()` 返回 null；
  - 只渲染**启用中**的 keys（`varsEnabledKeys`），关掉就一个字都不加；
  - **只输出当前档位一行**，不要把整张五档表塞进扮演侧（每轮都注入、额度敏感；全表只在抽取侧给）；
  - 保留「不要把它抄进正文」尾句；
  - 与界面 `TavernVarsPanel` 的档位显示保持一致（共用同一份 `VAR_BANDS`）。
- 🔒 **不扩范围**：本项只做「数值 → 言行的翻译更硬」，**不改亲密内容的解锁逻辑** —— 亲密与否仍由角色卡 `conduct.rating`（尺度）/ `bottomLine`（底线）/ `paceLock`（进度锁）把关；进度锁随关系推进改写走既有设定更新通道（`CARD_FIELDS` 的 `conduct.paceLock`）。

### 12.4 建议优先级与验收

- 优先级：**P2**（建议；待主人拍板）。
- 验收：补 `buildVarStateBlock` 输出单测（数值项带档位 / 文本项不带 / 关开关时为空）；过 tsc / eslint / 全量单测 / `structureGates`；实机（真 Chromium）确认注入文案正确且未撑爆上下文额度。

## 14. 内部自查优化项：模型「拒答」无感知、无反馈（2026-10-10）

> 🧭 路线图：第 1 批 **W1-3**（与 #1 / #2 / #6 同族打包）。
> 来源：2026-10-10 主人提问「线上模型拒绝生成成人向 / 暴力向等平台不允许的内容时，项目能否给用户反馈」触发的**源码自查**（非 §10 调研项，属本项目自己查出的问题）。
> 状态：**✅ 已完成**（随 W1-3 落地；拒答识别与反馈已实现）。
> ⚠️ 与 §10.3 **#1（候选→采纳）/ #2（缺失即停）/ #6（调用可观察）** 属**同一族**（AI 可控性与可观察），建议一并排期。

### 14.1 现状（已核实，含源码位置）

结论：**项目没有任何「模型拒答 / 被拦截」的识别，更谈不上反馈。** 逐条证据：

- 🔴 **不读 `finish_reason`**：`openaiChat`（`src/lib/aiCore/chat.ts`）只取 `choices[0].message.content` / `delta.content`；**全仓 grep 零命中 `finish_reason`** ⇒ `content_filter`（被内容过滤截断）与 `length`（超长截断）都拿不到，无法区分「正常写完」与「被拦腰斩断」。
- 🔴 **拒答正文被当正文用**：若模型以 **HTTP 200 + 一段拒答文字**（"抱歉，我无法……""作为 AI……"）回应，`content` **非空** ⇒ 被当正常产出原样返回。**续写 / 伴写无任何拦截**（伴写会把它当 ghost 建议透出）；整章改写只有「字数与期望相差过大」的 `isSuspectRewrite`（`creativeSession.ts:772`）能**偶然**兜住，并非针对拒答。
- ⚠️ **安全类错误被误判成配置问题**：`describeApiError()`（`src/lib/aiCore/transport.ts:238`）**只按 HTTP 状态码给建议** —— `400` →「模型名不在该账户已开通的清单里，也可能是参数不被接受」、`403` →「密钥无权访问」。而多数平台把**内容政策拒绝**也走 400 / 403 ⇒ 作者会被引向**错误**的排查方向（去查模型名 / 密钥，其实是内容被拒）。
- ⚠️ **空内容兜底报错也指向配置**：`'API 未返回内容，请确认模型名称正确且账户有额度。'`（`chat.ts:368`）、`'…流式响应体无法解析…'`（`chat.ts:362`）、Ollama 两处（`chat.ts:215` / `:226`）—— 全部假设是「配置 / 兼容」问题，未考虑「模型拒绝 / 被平台拦截」。
- ⚠️ **伴写连理由都不展示**：`useNovelEditorGhost.ts:193-200` —— 空串 → 静默不显示；抛错 → 只累加 `ghostFail`，**连续 N 次失败**才弹一句通用 toast（`'AI 伴写已连续失败 N 次，已自动停用…'`），**模型原话 / 理由一律不展示**。
- **全仓无「拒答话术」识别**：`protocolLegacy` / 角色卡里"不说'作为 AI''我无法'"是**生产侧约束**（防旁白腔），**不是消费侧识别**。
- ⚠️ **相邻但不同（不能替代本项）**：`aiReviewSensitive`（敏感词复核，`src/lib/aiTasks/suggest.ts:98`）是**对作者文本的事前合规复核**（本地词库命中 → AI 判风险），**不感知模型拒答本身**。

### 14.2 目标行为

- **正常生成** → 一切照旧，**零改动、零打扰**（呼应 §10.5「不因新项动摇既有功能」）。
- **模型拒答 / 被拦截** → 明确告诉作者三件事：① 这是「内容被平台拒绝」，**不是本地配置错**；② 尽可能附上**平台原话 / 理由**；③ 给出**可行动作**（改掉触发的敏感点重试 / 换本地模型 / 换平台）。

### 14.3 判据分层（由强到弱，任一命中即判「拒答」；开工时细化）

| 层 | 判据 | 说明 |
|---|---|---|
| ① 结构化（最强） | `finish_reason === 'content_filter'`；或平台 `error.code` / `type` 命中安全类（如 `content_policy_violation` / `data_inspection_failed` / `sensitive`…） | 需按平台维护一份**安全类码表**（与 §10.3 的「平台差异」同思路） |
| ② HTTP 状态 | 400 / 403 / 422 **且**响应体含安全类关键词（而非「模型名 / 参数」） | 从 `describeApiError` **分流**到「内容被拒」分支，不再一律归因配置 |
| ③ 文本启发式（兜底） | `content` 非空但整段是**拒答模板**（"抱歉…无法…" / "作为 AI…" / "I can't…"）**且明显短于任务期望长度** | ⚠️ 必然有误报 / 漏报 ⇒ **只提示，不自动丢弃、不上锁破坏性动作**（沿用 `isSuspectRewrite` 的克制口径） |

🔴 **边界**：只做「**如实反馈 + 让作者自己决定**」，**不做任何"绕过 / 反检测 / 洗提示词"**（项目红线）。

### 14.4 落点（最小改动，开工时细化）

- **解析层**：`aiCore/chat.ts` 读取 `finish_reason` 与 `error` 字段，向上返回**结构化「拒答信号」**（而不是只 `throw` 一句话被上层丢成通用错误）。
- **翻译层**：`aiCore/transport.ts` 的 `describeApiError()` 增「内容被拒」分支 + 安全类码表；调用方据此给出针对性建议。
- **呈现层**：统一一个「AI 请求被拒」提示（Toast / 行内提示），三处消费 —— 伴写（`useNovelEditorGhost`）、续写 / 改写（`jiWenJi` / `chapterRewrite` / `creativeSession`）、酒馆自由对话。
- **复用**：与 §10.3 #6「调用可观察」共用同一条**调用结果账本**（拒答也记一笔，便于作者复盘「哪段内容老被拒」）。

### 14.5 验收

- **单测**：`finish_reason = content_filter` / 安全类 400 / 拒答模板文本 → 三路均判定为「拒答」并给建议；正常 200 生成 → 判为正常、不打扰。
- **负面对照**：注入一条会拒答的输入 → 断言弹出「被拒」提示（红）→ 还原后 sha256 **逐字节一致**（沿用 `apply-many` + `count` 断言纪律）。
- **实机**：真 Chromium 下用云端模型跑一次触发拒答的续写 / 伴写，确认提示文案出现、且**原有正常生成路径不受影响**。

### 14.6 优先级建议

- **P1**（底座能力，不阻塞主线）：与 **§10.3 #1 候选→采纳 / #2 缺失即停 / #6 调用可观察** 属同一族 —— 「AI 可控性与可观察」，建议**打包排期**；单独做也成立。
