## 3. 老用户数据迁移方案（核心 · D4）

### 3.1 旧数据物理位置（由旧 app 生成，name=novel-studio）
- `userData` = `%APPDATA%\novel-studio`
  - `novel-studio-data.json`（整库 JSON，含 `app:'novel-studio'` 与各 `kind`）
  - `IndexedDB/file__0.indexeddb.leveldb/`（含主库 `novel-studio` + `novel-studio-vec` + `novel-studio-kb` 三个 IDB）
  - `Local Storage` / `Session Storage` / `Preferences`（Chromium profile，按 origin 索引，与 app 名无关）
  - `data-location.json`（若用户设过自定义数据路径 → 真实数据可能在别处，迁移须读它定位）

### 3.2 首启迁移向导流程
1. 新 app 首次启动（新 `userData=%APPDATA%\youth-fantasy-engine` 为空），探测旧目录 `%APPDATA%\novel-studio` 是否存续。
2. 存在 → 弹「发现旧版（novel-studio）数据，是否导入到 Youth Fantasy Engine？」；不存在 → 全新用户，正常走。
3. 用户点「导入」→ 执行 3.3–3.5。
4. 完成后提示「导入成功，现在可以卸载旧版了」，并提供「卸载旧版」入口（见 3.6）。
5. 「设置 → 数据」保留「重新导入旧版数据」按钮（幂等，防手滑 / 多 PC）。

### 3.3 整库 JSON 文件 remap
- 读旧 `novel-studio-data.json`（或 `data-location.json` 指向的路径）。
- 遍历结构：每个信封 `app` 字段 → `youth-fantasy-engine`；每个 `kind` 命中下表即改写：
  - `novel-studio-trajectory` → `youth-fantasy-engine-trajectory`
  - `novel-studio-trajectory-book` → `youth-fantasy-engine-trajectory-book`
  - `novel-studio.tavern-preset` → `youth-fantasy-engine.tavern-preset`
- 写出新 `youth-fantasy-engine-data.json` 到新 `userData`。
- ⚠️ `generator.app='青春幻想引擎'`（中文显示串）**不改**。

### 3.4 IDB 导出重导（最难点 · D2 的代价）
> LevelDB 文件名按内容寻址，**不能简单改名**；必须「开旧库 → 读全部 store/记录 → 写新库」。
1. 把旧 `IndexedDB/` 整目录**复制**到新 `userData/IndexedDB/`（新库为空，直接覆盖，让新 app 能按旧名打开旧库）。
2. 在渲染进程（IndexedDB API 可用）逐个处理：
   - 开旧库 `novel-studio` → 读全部 store/记录 → 开新库 `youth-fantasy-engine`（触发 `db/core.ts` 的 `onupgradeneeded` 建表）→ 批量 `put`。
   - 同法处理 `novel-studio-vec` → `youth-fantasy-engine-vec`（`semantic/store.ts`）、`novel-studio-kb` → `youth-fantasy-engine-kb`（`knowledgeBase.ts`）。
   - **复用现有 `openDB` 函数**保证新库 schema 与源码一致。
3. `indexedDB.deleteDatabase('novel-studio' / '-vec' / '-kb')` 清旧库，回收 LevelDB 文件。
4. 若个别记录写入失败（schema 漂移）→ 记日志、跳过、汇总到导入报告，不中断整体。

### 3.5 Chromium profile 复制
- `Local Storage` / `Session Storage` / `Preferences` 按文件整体复制到新 `userData`（与 app 名无关，安全）。

### 3.6 卸载旧版引导
- 改 `appId` 后新旧是**两个独立 Windows 产品**：新安装器**不会**自动卸载旧版，控制面板会出现两条，直到旧版被卸。
- 导入完成后提供「卸载旧版」按钮：经旧 `appId=cn.novelstudio.yfe` 的注册表 `Uninstall` 键定位旧卸载器并拉起；找不到则引导用户去「设置 → 应用 → 青春幻想引擎（旧）」手动卸载。
- 发布文案明确写「请先卸载旧版 novel-studio，再安装 Youth Fantasy Engine；首次启动会自动导入旧数据」。

### 3.7 幂等与重导
- 新 `userData` 已有数据 → 导入前询问「覆盖 / 合并 / 跳过」。
- 「设置 → 数据 → 重新导入」可随时再跑（多 PC / 手滑场景）。

## 4. 风险与纪律

| 风险 | 说明 | 处置 |
|------|------|------|
| 🔴 IDB remap 失败 | LevelDB 不能改名，须导出重导；schema 漂移会丢记录 | 复用现有 openDB；失败记录进报告不中断；封装前真机跑通 |
| 🔴 反向校验漏接 | `storeOps.ts:65` / `desktop.ts:635` 只认 `novel-studio` → 旧记录（含旧备份文件）被拒 | **不保留运行时兼容**：`storeOps`/`desktop` 校验只认新值；旧值仅在导入向导内部被识别并 remap（§3.3/3.4）。⚠️ 3.1+ 移除向导旧值识别，旧数据务必在 3.0 导入 |
| 🔴 `build-desktop.mjs` 常量未拆 | 设 executableName 后 `APP_NAME` 硬编码致主 exe 元数据补写静默跳过 | 必须拆 `EXE_FILENAME` + `DISPLAY_NAME`（10-08 上午纪律） |
| 🔴 旧备份文件兼容 | 用户手导旧 `.json` 备份，`app` 仍是旧值 | 备份导入路径同样走导入向导 remap（不保留运行时向后兼容）；3.1+ 旧值识别移除后此路径失效 |
| ⚠️ 双产品并存 | appId 改 → 新旧同列控制面板，直到旧版卸载 | 发布文案 + 向导「卸载旧版」按钮引导 |
| ⚠️ `data-location.json` 自定义路径 | 真实数据可能不在默认 userData | 迁移先读旧 `data-location.json` 定位 |

## 6. 已决结论（2026-10-08 17:49 拍板）

- **主库真相源（最稳妥双保险）**：迁移向导**二者皆迁、不丢任何数据**——① `novel-studio` IndexedDB 作为运行时 live 真相源优先搬迁；② `novel-studio-data.json` 整库一并改名 + `app` 字段 remap 作可携/兜底副本。目标 userData 已存在数据则**跳过避免双写覆盖**。⚠️ 二者精确冗余关系 3.0 开工前读 `db/core.ts` + `electron/main.cjs` 实测确认后再细化步骤。
- **英文品牌呈现面（仅关于页 + 仓库）**：`Youth Fantasy Engine`（官方简称 `YFE`）**只进**关于页英文品牌行（可带 `(YFE)` 角标）+ README 标题 + Gitee 仓库介绍三处；窗口标题 / 菜单 / NSIS 版权元数据**保持中文「青春幻想引擎」现状，不强加英文**（呼应中文软件定位）。
- **向后兼容窗口（不保留）**：3.0 起 `storeOps`/`desktop` **只认新值 `youth-fantasy-engine`**，旧 `app:'novel-studio'` 值不保留运行时兼容。导入向导**内部**容错旧值、仅把旧数据 remap 成新值后落新库。
  - 🔴 **兼容性声明（须写进发版说明 + 关于页/向导）**：旧版软件数据**仅能在 3.0 完成兼容导入**；3.1 及之后版本将移除旧值识别代码，届时导入旧数据可能导致未知错误。老用户务必在 3.0 一次性完成迁移。

## 9. 恢复 U 盘便携版（3.0 维护开发）· 规格定稿

> 提出：2026-10-08 ｜ 规格定稿：2026-10-09（主人哥哥口述详细要求）
> 性质：3.0 并行交付产物，与 §1–§2 重命名同步处理。**不沿用 2.1.0 砍掉的单文件 HTML 路线**，按"效果优先"重建。

### 9.1 历史背景（已查实，非推测）
- 便携版（U 盘单文件 HTML）在 **1.0–2.0** 持续交付：`vite-plugin-singlefile` 把 JS/CSS/资源内联进 `novel-studio.html`，双击即在浏览器运行；数据走 File System Access API（FSA）序列化到 U 盘 JSON 文件；`src/lib/portable.ts`（PORTABLE 引擎：800ms 防抖写盘 + 原子写）+ `src/components/Portable.tsx`（Gate + Badge）+ `vite.config.portable.ts` + `scripts/make-portable.mjs` + `portable-assets/`（START.bat + 使用说明.txt）+ `build:portable` 脚本配套。
- **2.1.0（2026-09-15）按决策「放弃网页版与便携版」整体砍掉**上述 FSA 路线文件；`StoreOps` / `PortableData` / `normalizePortableData` 因是三端共享数据契约被保留（现仍在 `src/lib`，供桌面版整库 JSON 与外部备份导入复用）。
- ⚠️ **关键事实**：原便携版依赖的 `vite-plugin-singlefile` 已于 **2.9.0 作为死依赖移除**（全仓零引用）。
- 🔴 **本次 3.0 新路线与老单文件 FSA 路线解耦**（依据见 9.3）：用户要求"数据在脚本同文件夹内"，FSA 方案无法满足（FSA 仅在 Chromium、需用户手势、跨机权限重置），故不原样复活旧文件，按文件存储新方案重建。

### 9.2 目标定位与交付形态（主人哥哥定稿）
- **交付时序：跟随 3.0 一起推出**（进 3.0 首批，与桌面版同发）。
- **形态：可装载到任意存储媒介（U 盘 / 移动硬盘 / 本地硬盘）的自包含目录**，内含三要素：
  1. **一键启动脚本**：`启动.bat`（Windows）/ `启动.sh`（macOS·Linux），双击即启动。
  2. **源代码 / 运行产物**：应用前端 + 一个轻量本地服务进程（见 9.3）。
  3. **项目数据存储目录**：与脚本、源代码同目录（建议 `./data`），项目数据文件就地存放。
- **启动效果**：点击一键启动脚本 → 自动拉起本地服务 → 自动打开默认浏览器窗口进入项目页面。无需安装、不写注册表、不留 `%APPDATA%` 痕迹、跨机随盘走。

### 9.3 技术路线与架构推断（主人哥哥不限定，按"效果优先"）
- 🔴 **关键推断：用户要求"项目数据跟脚本、源代码在『同一个文件夹内』" ⇒ 必须用文件存储，不能用浏览器 IndexedDB**（IndexedDB 落在浏览器 profile，不在应用目录，跨机/跨浏览器不跟随 U 盘）。
- **推荐路线**：构建前端静态产物 + 一个极简 **Node 本地服务**（`server.js`：静态托管前端 + 数据读写 API + 自动开浏览器），由启动脚本 `node server.js` 拉起；浏览器仅作客户端，数据经服务落盘到 `./data`。
  - 启动脚本职责：探测可用端口（默认 `127.0.0.1`，避免冲突）→ 起服务 → 调起默认浏览器到 `http://127.0.0.1:PORT` → 监听退出清理。
- **不沿用**老单文件 HTML + `vite-plugin-singlefile` 路线（理由：FSA 不满足同目录数据诉求 + 插件已移除）。
- 备选增强（可选，非基线）：用 pkg/nexe 把 Node 运行时编译进单 exe，免去"目标机需装 Node"；但主人哥哥要求"含源代码"，故基线为"源码 + 启动脚本 + 目标机有 Node"，单 exe 打包作可选增强。

### 9.4 数据契约与桌面版兼容（核心约束）
- 便携版数据**必须与桌面版完全兼容、可互导**。
- 复用桌面版 `StoreOps` / `PortableData` / `normalizePortableData` 数据契约（§2.2 已保留在 `src/lib`）。
- **数据文件命名：跟随 3.0 最新重命名要求**——整库 JSON 命名为 `youth-fantasy-engine-data.json`（对应 §1 整库 JSON 文件名映射），落盘于 `./data`；旧 `青春幻想引擎-同步数据.yfe` 命名废弃（便携版本就不含云同步，去"同步"语义）。
- ⚠️ 互通机制：便携版（文件存储）与桌面版（运行时 IndexedDB、整库导出才是 JSON）**不直接读对方库**，靠「整库 JSON 导入导出」这一个共同格式互通——桌面版「设置→数据」导出 JSON；便携版同格式读写 / 导入导出。
- 数据随应用目录走，不写 `%APPDATA%`、不写注册表。

### 9.5 功能边界（不主动阉割）
- **原则：不进行主动阉割，尽量保留桌面端绝大多数功能。**
- **明确不启用**：所有「云端同步 / 云盘同步 / 在线更新检查 / 需后端服务器的联网功能」一律禁用（便携版离线自包含，本就不含这些）。
- **仅当"便携版实在无法启用"才禁用 / 阉割**，须逐一评估并形成清单：
  - 依赖系统级安装的能力（桌面版安装 / 卸载、系统托盘、原生文件对话框）→ 便携版用 Web 等价实现或禁用。
  - 需常驻后台 / 开机自启的能力 → 禁用。
  - 其余纯本地能力（本地 Ollama、书稿编辑、世界观、时间线、关系图、AI 创意写作、酒馆本地对话等）**全部保留**。
- 动手前须产出「功能对照表」（桌面端功能 → 便携版状态 ✅保留 / ⚠️降级 / ❌禁用 + 禁用理由），经主人哥哥确认后再实施。

### 9.6 与 3.0 重命名的耦合
- 同 §2 / §9.4：便携版内部 `app:` 键、整库 JSON 文件名、标题 / 关于页英文副标题一律走新品牌 `youth-fantasy-engine` / `Youth Fantasy Engine`，不出现 `novel-studio`。
- 注意：便携版走文件存储，**不涉及 IDB 库名**（`-vec` / `-kb` 等 IDB 名仅桌面版运行时用），但向量 / 知识库数据仍以 JSON 形式随整库落 `./data`。

### 9.7 重建清单（相对 2.1.0 砍版）
- **不原样复活**（老 FSA 语义）：`portable.ts`(FSA 引擎) / `vite.config.portable.ts` / `make-portable.mjs` / `Portable.tsx`(FSA Gate) / `portable-assets/START.bat`。
- **新建**：
  - `portable/server.js`（或 `scripts/portable-server.mjs`）：Node 静态托管 + 数据 API + 自动开浏览器。
  - `portable/启动.bat` + `portable/启动.sh`：一键启动。
  - `portable/使用说明.txt`：装载 / 启动 / 数据备份与迁移说明。
  - `package.json` 加 `start:portable` 脚本。
  - 前端加「便携模式」识别（启动参数 / env 告知前端走文件存储适配层）。
- **复用 / 抽象**：`StoreOps` / `PortableData` / `normalizePortableData`（数据契约）；AI 层、schema、tab 注册表、StoreOps 门面。**须先抽象 `StorageBackend` 接口**（桌面=IDB 实现、便携=File 实现），否则双端无法共用 StoreOps。

### 9.8 风险与纪律
| 风险 | 说明 | 处置 |
|------|------|------|
| 🔴 存储后端抽象缺失 | 现状桌面版直接依赖 IndexedDB/Electron，便携版要文件存储 | 先抽象 `StorageBackend` 接口（IDB + File 两套实现），可单测后再接前端 |
| ⚠️ 端口冲突 | 多实例 / 多 U 盘同插 | 启动脚本探测可用端口、写 `./data/.port` 锁防多开 |
| ⚠️ 浏览器自动打开失败 | 无默认浏览器 / headless 环境 | 启动脚本打印 URL，兜底手动打开 |
| ⚠️ 目标机无 Node | 基线"需目标机有 Node" | 备选 pkg 单 exe；或文档注明需装 Node |
| ⚠️ 数据文件体积 / 写盘安全 | U 盘小文件 IO 性能、断电损坏 | 沿用桌面整库 JSON + 防抖 + 原子写（先写 .tmp 再 rename） |
