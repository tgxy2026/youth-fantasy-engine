## 一、目标（§10.3 #8 原文口径）

1. 带来源的**语义快照**；
2. **不可变世界版本**；
3. 同一世界可供**多个作品引用**，每次制作都知道用了哪一版设定；
4. 边界：**原作品后续修改不会自动同步到派生世界**；世界只保存**可版本化的语义内容**。

🔴 结合点（§10.3 #8 末原文）：*「与 §9 数据契约可共用」* —— 世界包与备份 / 导出走**同一套 StoreOps 契约**，不另造序列化。
🔴 落地纪律（§10.5）：*「详细落地方案在开发时设计……结合本项目既有能力落地，不照抄」*。

## 二、术语对齐（先消歧，免得与既有概念打架）

| 方案用词 | 本项目对应物 | 说明 |
|---|---|---|
| 世界 | 一个项目里「世界构建」内容的集合 | 世界设定 `worldbase` ＋ 力量体系 `power` ＋ 世界构建组 7 表（`nations`/`geography`/`races`/`items`/`history`/`terms`/`misc-settings`）＋ 各表的**子世界条目**（`<tabId>-sub`，C10 · 2.4.2） |
| 语义快照 | **世界包（WorldPack）** | 只含可版本化的语义内容；**不含**章节正文 / 角色卡 / 对话 / 向量索引 |
| 封存＝不可变版本 | 世界包下的 `versions[]` | 一旦封存不再改写（与 W3-1「定稿」同款语义） |
| 跨作品引用 | 另一项目**显式导入**某份世界包 | 导入即派生：独立、留溯源、不自动同步 |

## 三、现状盘点（源码级侦察结论）

| 能力 | 现状 | 位置 |
|---|---|---|
| 世界数据存储 | ✅ 全在项目内：`tableRows`（按 `tabId`）＋ `cardRecords` | `db/core.ts` |
| 子世界结构（C10） | ✅ 母级 ＋ 子项两段；AI 只喂「母级 ＋ 活跃子世界」 | `worldSets.ts` / `aiContext.ts` |
| 整库备份 / 导出 | ✅ `backups` ＋ `backupPayloads`，`kind` 化（W3-1 加 `frozen`） | `db/backups.ts` |
| 「冻结」的既有模式 | ✅ **不新建表** —— 就是一份 `kind='frozen'` 的备份 | `db/backups.ts:156` 注释 |
| 同步范围 | ✅ `SYNC_STORES` 15 个 store；`backups`/`backupPayloads` 是**本地专属** | `syncCore.ts:25` / `LOCAL_ONLY_STORES` |
| 可移植存储抽象 | ✅ `StoreOps`（桌面 / 便携 / 云端多实现） | `storeOps.ts` / `desktop.ts` / `desktopCloudSync.ts` |
| **世界包 / 版本 / 跨作品引用** | ❌ **全仓零命中** | —— |

**结论**：世界「内容」已经完整；缺的是**抽包 → 封存 → 跨作品引用**这条链。

## 四、设计

### 4.1 世界包契约（`src/lib/worldPack.ts` · 新增）

```ts
export interface WorldPack {
  schema: 1
  id: string                 // 世界包 id（稳定）
  name: string
  origin: { projectId: string; projectName: string; at: number }  // 来源（方案要求「带来源」）
  tables: Record<string, unknown[]>   // tabId → 行（仅世界相关表，含 <tabId>-sub）
  fingerprint: string        // 内容指纹（沿用 W3-1 `bookFingerprint` 的思路）
}
```

- 抽包范围＝**决策点 D2**；
- 序列化走既有 `StoreOps` / 备份同源的 JSON 形态（结合点要求）。

### 4.2 封存（不可变版本）

- 一个世界包可**多次封存**，每次产出一个不可变 `version`（`{ v: number; at: number; fingerprint: string }`）；
- 存放位置＝**决策点 D1**（三候选见第五节）；
- 🔴 封存后不再改写；后续编辑只动「草稿」，要生效须**再封一次**。

### 4.3 跨作品引用（显式派生）

- 目标项目执行「引入世界」→ 选某份世界包的**某个版本** → 复制其内容进本项目的世界表；
- 记**溯源**（引自哪个包、哪一版、何时）→ 在页头常显；
- 🔴 **不自动同步**（方案边界）：源项目改了世界，引用方**不跟着变**；要更新须再显式引入一次（届时提示差异，＝决策点 D3）。

### 4.4 UI

- 入口形态＝**决策点 D4**；
- 版本列表复用 W3-1 `BookVersionPanel` 的呈现范式。

## 五、决策点（请主人拍板）

### D1 · 世界包与版本放在哪里？

| 选项 | 优点 | 代价 |
|---|---|---|
| **A** 主库新 store `worlds`（进 `SYNC_STORES`） | 随项目同步、随备份走；实现最省 | 世界**跟着宿主项目**跑；「跨作品」仍是显式导入 |
| **B** 独立 IDB 库（如 `novel-studio-worlds`） | 天然跨项目 | 🔴 按既有红线，独立库**不进整库 JSON / 同步 / 备份** ⇒ 换机须手动搬世界包文件 |
| **C** 落成文件（用户选目录） | 可分享、可进 Git | 新增文件 IO 与路径闸；与「只存语义内容」的定位打架 |

**可可推荐 A**：与既有同步 / 备份契约同源、实现最省；跨设备交给「导出世界包 `.json`」这条明路。

### D2 · 一个世界包含哪些表？

- **A**（最小）：世界设定 `worldbase` ＋ 力量体系 `power`
- **B**（推荐）：A ＋ 世界构建组 7 表（`nations`/`geography`/`races`/`items`/`history`/`terms`/`misc-settings`）＋ 子世界条目
- **C**（最全）：B ＋ 大纲类（`outline` / `chapterMaster`）

**可可推荐 B**：`C` 会把「这本书的情节」误当「世界」，与「世界只存可版本化语义内容」冲突。

### D3 · 引入后在目标项目里能否编辑？

- **A**（推荐）：**可自由编辑**，但页头常显「引自 …（v3）」，再次引入时提示差异；
- **B**：**只读**，要改必须回源项目再引入。

**可可推荐 A**：贴合网文作者「拿来做底稿再本土化」的真实用法；「不自动同步」的边界仍由「引用＝快照复制」保证。

### D4 · 入口形态

- **A**（推荐）：世界构建组下新增页签「世界库」；
- **B**：挂在「世界设定」页头的按钮（不新增页签）。

**可可推荐 A**：世界库是**跨作品**的，塞进某张项目内表会让「它属于哪个项目」更绕；新页签另需四处同步（`TabType` / `TABS` / `App.renderContent` / `FEATURE_TIER`）。

## 六、分步实施（拍板后执行）

- **W4-1a**：`worldPack.ts`（抽包 / 指纹 / 序列化）＋ 单测（抽包范围、指纹稳定、**不含正文**）
- **W4-1b**：封存与版本列表（含 UI）＋ StoreOps 对接 ＋ 单测
- **W4-1c**：跨作品引入（显式派生 ＋ 溯源显示 ＋ 差异提示）＋ 实机验证

## 七、验收

- tsc / eslint / 全量单测 / `structureGates`；
- 实机：抽包 → 封存 → 另开项目引入 → 页头显示溯源 → 源项目改世界后**引用方不变**（负面对照）；
- 🔴 新增 store 须同步：`SYNC_STORES` / `LOCAL_ONLY_STORES`（若选 B）/ 备份范围 / 删除项目清理 / 迁移。

## 八、不扩范围

- 不做短篇 / 剧本 / 漫画（§10.3 #9 明确不开发）；
- 不做「游戏进度改写共享世界」（方案边界）；
- 不引入在线世界市场 / 云共享。
