# 2.2.0 全自动 AI 小说创作工作流 · 落地方案

> 范围：把项目内已零散存在的 AI 能力串联成「从一句话想法 → 成稿」的全自动（可人机协同）创作工作流。
> 本文为**方案级**文档，不写实现代码。开发前按本方案逐条推进。
> 关联：2.2 三大功能之二（另两个见 `docs/2.2.0-AI伴写与引用高亮方案.md` 与 `docs/一键拆书-方案规划.md` / `docs/一键拆书-详细设计.md`）。
> 红线前提：沿用「AI 辅助、人不退场」定位（旧「只辅助不生成正文」断言已删，commit `0158375`）；全程本地模型（Ollama + Qwen3.8-27B），零外发。

---

## 0. 目标与范围

1. **自动串联**：用户仅提供「一句话想法 / 一句话简介」，AI 在引导下自动完成 设定奠基 → 大纲 → 逐章正文 → 审校闭环 → 导出。
2. **可人机协同**：关键闸门（设定奠基、大纲）需用户确认后才进入自动连写——人定方向，AI 跑量。
3. **不重造框架**：直接复用现有 `aiTasks` / `autoContinue` / `aiContext` 能力，只补「生成型入口 + 编排器」两块最小代码。

## 1. 业界成熟方案调研结论（提炼）

调研覆盖 7 个开源项目（LangGraph-based-Novel、NovaTale、AI_Gen_Novel、EditorHouse、langbooks、AI_NovelGenerator、novel-ai-agent、opennovel、autonovel、quill）及 IBM / Stanford(SuperWriter) 论文。

### 1.1 通用 6 阶段管线（所有方案高度一致）
```
种子意图 → ①设定奠基(Bible) → ②大纲(Outline) → ③逐章草稿(Draft)
        → ④审校/自评(Critic) → ⑤修订闭环(Revise Loop) → ⑥导出(Export)
```

### 1.2 四个决定质量的关键机制
| 机制 | 说明 | 开源痛点 |
|---|---|---|
| **多智能体分工** | Planner / Writer / Editor / Critic 各司其职 | 单 LLM 视角单一、风格漂移 |
| **Critic / Reflect 自评闭环** | 写完打分 → 低于阈值退回修订，循环至达标 | 这是质量分水岭（IBM Perceive-Think-Act-Reflect） |
| **上下文压缩** | 用「最近 N 章摘要」代替全文注入 | 长文 recall 衰减、人设/伏笔遗忘 |
| **连续性硬约束** | 伏笔/持有物/既定事实写成 JSON 强制注入 | 软 bible 在长文易崩、产生"穿越 bug" |

### 1.3 对我们最重要的两点判断
1. **长文一致性崩塌是开源方案的通病**（LangGraph-based-Novel 自承"长文中可能出现幻觉"）。而我们的**结构化 schema（角色卡 / 地理风物 / 国家势力 / 人物关系 / 世界设定 / 力量体系 / 大纲 / 素材资料）+ 伏笔闭环看板 + 连续性校验** 把"软 bible"变成了"硬约束"——这是我们的**天生差异优势**，应作为工作流的核心一致性保障。
2. **框架非必需**：有方案明确指出"几个脚本或 Node 循环就够了"，无需引入 LangGraph/ADK。我们已有 `autoContinue.ts` 这类纯逻辑编排先例，照此扩展即可。

## 3. 目标工作流设计（novel-studio native）

```
[种子] 一句话想法
   │
   ▼
① 设定奠基  aiGenerateBible(seed) ──▶ 落到现有 schema（角色卡/地理/势力/世界/力量/大纲/关系）
   │                                        ↑ 人工确认闸门 ①
   ▼
② 大纲生成  aiGenerateOutline(bible) ──▶ 分卷分章大纲 + 伏笔台账初稿
   │                                        ↑ 人工确认闸门 ②
   ▼
③ 逐章草稿  for each chapter:
   │    注入 = buildProjectContext(设定) + getRecentChapterTexts(最近N章) + 本章细纲 + 伏笔约束
   │    生成 = runAutoContinue(...)（复用一键续写+设定补完）
   │    → aiChapterSummary 压缩 → 喂下一章
   ▼
④ 审校闭环  per chapter（Critic 组合）:
   │    aiOocCheck + aiContinuityAudit + aiProofread/aiEditorDiagnosis + aiStyleCheck + aiPleasureCheck
   │    → 加权评分；低于阈值 → aiRewritePassage 修订 → 重评，直到达标或达最大轮次
   ▼
⑤ 伏笔回收  aiForeshadowReview 持续更新伏笔台账（埋设/回收状态）
   ▼
⑥ 导出      复用现有导出（TXT / Markdown / EPUB / DOCX / 平台粘贴版）
```

**人机协同闸门**：闸门①（设定奠基）与闸门②（大纲）必须用户确认后才进入自动连写——既保"人不退场"，又让 AI 在确认后放心跑量。闸门之后每章的 Critic 闭环可全自动，用户随时可介入改稿。

## 4. 核心机制设计

### 4.1 上下文注入（复用 `buildProjectContext` + `getRecentChapterTexts`）
- **设定层**：`buildProjectContext({ budget: 4000 })` 注入角色/世界/势力等硬约束（取代开源的"软 bible"）。
- **前文层**：`getRecentChapterTexts(N=3~5)` 注入最近几章正文/摘要，解决长文 recall 衰减。
- **约束层**：从伏笔台账 + 连续性校验提取"既定事实/未回收伏笔"作为强制约束，注入 system（钉末尾）。
- **作者保护**：`authorBlock()` 封装已有正文，绝不清洗作者原文（沿用既有红线）。

### 4.2 自评闭环（Critic 组合，质量分水岭）
- 每章生成后跑 **5 项审校** 取加权分（逻辑/人设/情节/节奏/文风/爽点）。
- 评分 < 阈值（建议 0.7）→ `aiRewritePassage` 修订 → 重评；最多 2~3 轮， Plateau 即停。
- 复用 `aiOocCheck`（人设漂移）、`aiContinuityAudit`（穿越 bug）、`aiStyleCheck`（文风漂移）—— 这三项正好对应开源最头疼的"一致性崩塌"。

### 4.3 状态持久化（run-state）
- 工作流运行状态（当前阶段、已生成章、各章评分、伏笔台账版本）存入现有 StoreOps 存储（与项目数据同生命周期），支持**断点续跑 / 中断恢复**。
- 不引入新数据库；复用 `db` / `StoreOps` 既有机制（与一键拆书、酒馆模式一致）。

### 4.4 本地模型零外发
- 全部走 `requireActiveProvider()`，仅本地 Ollama；无任何外部网络请求（商业机密红线）。

## 5. 与「一键拆书」「伴写」的关系（同一 schema 双向闭环）

| 功能 | 方向 | 与自动工作流的关系 |
|---|---|---|
| **一键拆书**（规划中） | 外部文本 → 项目 schema（import） | 工作流是反向：schema → 文本（generation）。两者共用同一 schema，互为补充 |
| **AI 伴写**（规划中） | 实时一句话 ghost 续写 | 工作流③「逐章草稿」阶段的实时辅助层；连写时也可调起伴写 |
| **自动创作工作流**（本方案） | 想法 → schema → 成稿 | 三者中枢，把拆书产出的设定与伴写的实时能力串成完整管线 |

> 一句话：**拆书沉淀设定，工作流消耗设定产出正文，伴写在写作现场补刀**。三者围绕固定 schema 形成闭环。

## 7. 实施分期（MVP → 增强 → 可选）

- **阶段一（MVP · 可落地验证）**：
  - 种子 → `aiGenerateBible` → **人工确认** → `aiGenerateOutline` → **人工确认** → 逐章 `runAutoContinue` + `aiChapterSummary` → 单轮 Critic（`aiOocCheck` + `aiContinuityAudit`）→ 导出。
  - 核心验证：本地 27B 能否稳定产出"不崩人设/不穿越"的成稿。
- **阶段二（增强）**：
  - 多轮 Critic 闭环（5 项加权评分 + `aiRewritePassage` 修订）；伏笔台账自动更新（`aiForeshadowReview`）；`aiStyleCheck` 文风漂移防控；断点续跑 UI。
- **阶段三（可选）**：
  - 节奏曲线（`aiPleasureCheck` 张力争）；并行多方案对比；去 AI 味（humanize）；与「伴写」实时联动；长卷分线叙事编排。

## 8. 风险与开放问题（待拍板）

1. **本地 27B 长文质量上限**：百万字级连写，27B 的设定洞察力可能弱于云端大模型 → 建议 MVP 先在 5~10 万字中篇验证，再决定是否放开长篇。
2. **Bible/Outline 生成质量依赖 seed 丰富度**：一句话太薄时生成设定可能空洞 → 闸门①/②的人工确认正是兜底；可加"追问补全"引导。
3. **自动连写算力/时长**：逐章多轮 Critic 耗时显著 → 需明确的"停止/暂停/恢复"与进度反馈，避免卡死感。
4. **与既有 UX 协调**：删了"只辅助"红线后，需确保自动工作流不与"AI 入口 disabled 当无模型"等既有红线冲突（仍保留无模型时禁用）。
5. **伏笔台账自动更新的准确率**：`aiForeshadowReview` 误标会影响连续性约束 → 阶段二再接，MVP 先用手动/半自动。
