## 二、修复的 8 项

### 🔴 P0-1 · `src/lib/db/core.ts` · 兜底镜像把「本机删过」的记录补回，并顺手清掉墓碑 → 第三条「删了会复活」路径

**现场**：`mirrorCloudCacheToLocal(cache, overwrite=false)`（异常兜底路径）里，`missing` 只按「本地有没有」判定：

```ts
const missing = list.filter(r => !have.has(String(r[kp] ?? '')))
if (missing.length) tasks.push(desktopLocalStore.bulkPut(store, missing).catch(() => {}))
```

**为什么是 P0**（三步走完就彻底复活）：
1. 云端闩锁（`isUnavailable()`）期间，包装层把 `del` 切到**本地库**（`core.ts:254`）→ 记录从本机删掉，**墓碑记下**；
2. 关窗/异常触发兜底镜像，参数 `overwrite=false`，而 `cache` 是**闩锁前的旧数据** —— 它里面还有那条 → 本地没有 → 进 `missing` → `bulkPut` 补回；
3. 🔴 而 `desktopLocalStore.bulkPut` 会**顺手 `clearDeleted()`** 抹掉同 key 的墓碑（`desktop.ts:484`）。
⇒ 记录回来了、墓碑没了 → 下次开同步 `seedFromLocal` 把它当本地数据**播种回云端**，删除被彻底撤销。

这与既有防线（`overwrite=true` 的 `mirrorDeleteExtra` + 注释 144-149 行）防的是**同一个病**，只是这条兜底路径漏了判据 —— 也是本家族**第三条**路径
（09-21 那轮修的是前两条：空 store 被跳过、`mergeCaches` 的「云端没有」分支未查墓碑）。

**修法**：`missing` 除「本地有没有」外，再剔除被墓碑标记的（判据用墓碑，不用「本地有没有」—— 闩锁期的删除只落在本地库 + 墓碑里，旧 cache 并不知情）：

```ts
const missing = list.filter(r => {
  const k = (r as Record<string, unknown>)[kp]
  if (isDeleted(store, k)) return false       // 🔴 本机删过 → 不能补回（会清墓碑 ⇒ 复活）
  return !have.has(String(k ?? ''))
})
```

### P1-1 · `src/lib/db/backups.ts` · 恢复备份会把该项目的快照**清空且不复原**

**现场**：`restoreBackup()` 的收尾里

```ts
const snapKeys = (await ops.getAllByIndex<Snapshot>('snapshots', 'projectId', targetPid)).map(s => s.id)
…
if (snapKeys.length) await ops.bulkDel('snapshots', snapKeys)
```

**为什么是 P1（实为数据丢失）**：三条事实叠起来 = 「恢复一次备份，时光机全没」：
1. 本函数的写入段只恢复 `volumes/chapters/formData/tableRows/cardRecords` —— **没有任何快照写入**；
2. 自动备份恒定 `includeSnapshots:false`（A3 的决策：自动备份不带快照）⇒ bundle 里本来就没有快照；
3. 这行是**无条件全删** —— 对比紧邻的 `dailyStats` / `settingsKV` 用的都是 `stale* = 差集`，**只有快照这行是全删**，不对称本身就是线索。

**修法**：删掉这行（连同已无用的 `snapKeys` 与其 `Snapshot` 类型 import），并写明"恢复备份的语义是还原，不是把备份没覆盖的也清掉"。
（手动导出包带快照时走 `importProject`，那条路会按新 `chapterId` 重映射写入，不受影响。）

### P1-2 · `src/lib/syncCore.ts` · `sameStores` 主键取错 → `formData` 恒判「不一致」→ 同步乒乓

**现场**：`sameStores()` 里手写 `r?.id ?? r?.key` 取主键，而本文件别处（830/842/852/861/878/890）**一律用 `KEY_FIELD[store] ?? 'id'`**。

**为什么是 P1**：`formData` 的主键是 **`tabId`**（`KEY_FIELD.formData`，第 36 行），既没有 `id` 也没有 `key`
⇒ 每条都被映射成 `undefined` ⇒ Map 互相覆盖只剩最后一条 ⇒ `formData ≥2 条` 时该函数**恒返回 false**
⇒ `backgroundPull` 恒判 drifted ⇒ `schedulePush`。两端都持有 formData 时会形成「收到即回推」的同步乒乓、rev 持续自增。

**修法**：改用 `const kf = KEY_FIELD[k] ?? 'id'` 取主键。

### P1-3 · `electron/main.cjs` · 原子写的 tmp 名不唯一 → 可能把半截内容搬成正文件

**现场**：`writeAtomicSync`（关窗同步写）与 `writeAtomic`（防抖异步写）共用 `file + '.tmp'`。

**为什么是 P1**：关窗时防抖中的 `store:save` 仍在途，`store:save-sync` 又进来写**同一个 tmp**；
两次写交错后 `rename` 可能搬走写了一半的内容 —— **恰好破坏这两个函数本来要防的「截断 JSON」**。

**修法**：tmp 名带 pid + 递增序号（`tmpNameOf(file)`），并在失败时清理残留。同进程内不会重名，跨进程靠 pid 区分。

### P1-4 · `src/lib/syncCore.ts` · 检索密钥随云盘同步外流，与 UI 承诺矛盾

**现场**：`SearchSettingsPanel` 密钥栏写着「存在本机数据文件里，**不会上传到任何服务器**」，
但 `app.search`（含 `apiKey`）住在全局 meta，而同步排除表只挡了 AI 那三个键（`EXCLUDED_META_KEYS`）。

**为什么是 P1**：这是**产品承诺 ↔ 实现不一致**（口径问题属于本项目的红线区）。
同步是整条 key-value 写出，没法只排除某个字段。

**修法**：把 `app.search` 加进 `EXCLUDED_META_KEYS` —— 与 `aiProviders` 完全同构：整条本地专属，换设备需重填一次。
（选"改实现"而不是"改文案"：承诺方向是对的，实现该跟上。）

### P1-5 · `src/lib/schema.ts` · 创意写作承诺「更新已有设定」，默认策略只新增

**现场**：功能说明写「每章写完都会抽取本章设定、补登新增设定、**更新已有设定**」；
而默认策略是 `add-only`（`creativeSession.ts:110`），面板自己也写「已登记的设定一律不动」。

**修法**：改为「按所选策略补登（**默认只新增，不动已登记的条目**）」。

### P1-6 · `src/components/CloudFileSyncBar.tsx` · 「全程不经过任何服务器」

**现场**：帮助弹窗写「由 OneDrive / WPS 云盘 / 百度网盘 / 坚果云 等客户端负责跨设备搬运，**全程不经过任何服务器**」。

**为什么是 P1**：文件是加密后交给用户网盘客户端上传的 —— **确实经过了服务商服务器**，只是不经本软件自建服务器。

**修法**：改为「本软件不经过任何自建服务器（文件由你所选的网盘客户端上传到该服务商）」。

### P1-7 · `src/lib/tavern/varsRefresh.ts` · 每轮数值刷新失败**完全无痕**

**现场**：`catch { return session }`，而文件头注释写明「**失败一律静默**：数值是锦上添花，绝不能让它的失败把这一轮对话弄没」。

**判断**：静默本身是**有意设计**（不打断对话），不是 bug —— 但"完全无痕"让排查无从下手
（数值一直不动时，分不清是"这几轮真没变化"还是"每轮都在失败"）。
**最小改进**：补一行 `console.warn`（与 `useTavernCardModel.ts:538` 的写法同构），**不弹 toast**（它每轮都跑，弹窗会盖住对话）。

### P1-8 · `src/lib/tavern/cardFile.ts` · 关系状态「导出带、导入丢」→ 往返一次全部归零

**现场**：`toCardFile` / `toCardBundle` 都用 `const { id, createdAt, updatedAt, seededFrom, ...rest } = c` 导出，
`rest` **包含 `vars`**；而 `normalizeCard` 返回的对象只列 `storyId/name/avatar/world/profile/conduct/examples/importedFrom`
—— **从不读 `cardRaw.vars`**（批量通道 `parseCardBundle` 复用同一函数，同样丢）。

**为什么是 P1**：`vars` 是「关系状态」（好感 / 信任 / 精神 / 心情 / 地点 + 每项备注），是角色卡里**最有价值的那部分进度**。
导出 → 导入往返一次（或换设备搬卡）全部归零，而且**没有任何提示** —— 作者只会觉得"状态怎么没了"。

**结论**（老大 2026-09-22 拍板）：**随卡跨设备** ⇒ 导出带、导入也必须读。两侧要么都带、要么都不带，不能一边带一边丢。

**修法**：新增 `normalizeVars()` 并在 `normalizeCard` 里接上。校验取宽松尺度（与本文件其余部分一致）：
只认 `VAR_KEYS` 里的键，数值项收有限数字、文本项收非空字符串，`notes` 同理，其余一律丢弃；
一个可用字段都没有时返回 `undefined`（不给卡硬塞一个空的 `vars`）。
落库链路 `createFreeChar` → `normalizeCardMarkup` 全程用 `...` 展开，已确认不丢字段。

**这是向后兼容的加法**（旧文件没有该字段 → 直接走 `undefined` 分支），故 `FORMAT_VERSION` **不需要升版**。

**测试**：`tests/tavernCardFile.test.ts` 新增 6 条往返对称断言（单卡 / 批量 / 非法键丢弃 / 旧文件兼容），**50 → 56**。

## 六、方法论收获

1. **🔴「删了会复活」是一个家族，不是一条路径。** 上一轮（09-21）修了两条，这一轮又挖出第三条
   （兜底镜像的 `missing` 补回 + `bulkPut` 清墓碑）。**修这类问题时要把"同一个病的所有路径"一次找齐**，
   否则每轮审计都只会捞出漏网的那一条。
2. **交叉验证真的能提信心。** 扫描器 `audit-content` 的 C3「AI 续写 / 一键续写」术语不一致，
   与子代理④独立报出的 `AIConfigPanel.tsx:218` 指向同一处 —— 两条独立线索撞在一起，采信度远高于单条。
3. **"不对称"本身就是最强的线索。** P1-1 里 `dailyStats`/`settingsKV` 用差集、只有 `snapshots` 全删；
   P1-2 里全文件都用 `KEY_FIELD`、只有 `sameStores` 手写 `id ?? key` —— 两处都是"周围同类写法不一致"暴露的问题。
4. **静默 ≠ 一定是 bug。** `varsRefresh` 的静默是**有意设计**（不打断对话）。判"不改"并把理由写下来，
   和修 bug 一样重要 —— 否则下轮会有人再来提一遍。

### 新工具 `ui-btn-size-audit.mjs`（已沉淀进 skill）

遍历 53 个真页签，约 **1.7 分钟**。过程中踩了四个坑（详规写在 skill）：

1. 单页版**看不见纯图标键** —— 而真实违规恰恰出在纯图标键上；
2. 🔴🔴 **「同一行」不能用 `top` 绝对值判** —— 这是**循环依赖**：
   删除键 h=32 比编辑键 h=24 高 8px，`items-center` 下它的 top 反而**小 4px**（实测 570 vs 574），
   按 `round(top/4)` 分行就把这对"同排不同高"分到了两行 —— **恰好在最该报的地方永久失明**。
   正解：**垂直中心聚类**（`|cyA − cyB| ≤ min(hA,hB)/2`）；
3. 遍历侧栏必须**排除折叠开关** —— 分组标题与卷标题**都是 `<button>`**，点它们只做折叠，
   组内页签随折叠从 DOM 消失。不排除时 64 个可点项里 **53 个"找不到"**，
   脚本一路 `continue` 到底、最后打印「✅ 没有发现」——**假绿比误报危险得多**。
   判据：`!b.querySelector('svg.lucide-chevron-down')`；
4. **负面对照前要确认目标控件真的渲染了** —— 「模型设置」页在空 provider 时只显示两个"添加"大按钮，
   编辑/删除键根本不渲染 ⇒ 注入违规也检不出来。
