## 二、本轮已落地：酒馆超时防回归闸

### 2.1 为什么补这条闸

`docs/2.9.0-未做五项推进记录` §2 把酒馆 13 处硬编码 `CHAT_TIMEOUT_MS`（180s）改成了
`timeoutMsOf(await getTavernSettings())`，但当时只跑了 tsc/lint/单测 —— **没有任何东西守住「别再改回去」**。
本轮补 `tests/tavernTimeout.test.ts`（**纯静态、零 IO**，归 A 批结构闸）填这个空。

### 2.2 断言内容（7 条）

| # | 断言 | 为什么要守 |
|---|---|---|
| ① | `src/lib/tavern/**` 不含 `CHAT_TIMEOUT_MS` | 那是主应用常量；酒馆必须走设置 |
| ② | 每一处 `timeoutMs:` 的值都以 `timeoutMsOf(` 开头 | 防有人写死数字／写回常量 |
| ③ | `timeoutMs` 接入点 ≥ 13（当前 **16**） | 防「被整段删掉」而无人察觉 |
| ④ | 能定位 `timeoutMsOf` 实现，且语义 = `Math.max(5, s.common.timeoutSec) * 1000` | 下限 5s 被去掉会让 `0` 值直接失效 |

**为什么用「读源码」而不是「跑函数」**：本闸刻意归 A 批（纯静态扫描，18s 那一批），
不 `import` `settings.ts` ⇒ 不拉 `db`／IDB。行为侧的「默认 300 秒」由 `tavernSettings.test.ts` 守。

### 2.3 负面对照（实测）

| 操作 | 结果 |
|---|---|
| 把 `daily.ts:234` 改回 `timeoutMs: CHAT_TIMEOUT_MS` | **① ② 双双报红** → 5 通过 / 2 失败，exit 1 |
| `git checkout` 还原 → 复跑 | **7 通过 / 0 失败**，exit 0 |
| A 批整体 | **14 / 14 通过 · 14s**（原 13 + 本闸） |

### 2.4 ⚠️ 这条闸**不能**替代实弹验证

它只证明「代码走的是设置」，**不证明**「设置真的对模型生效」。实弹口径（待做）：
把酒馆「请求超时」设成 **30 秒**，用慢模型触发「整理本场记忆」—— 若约 30 秒即超时（修复前无论
如何都要等满 180 秒），才算真验证。⚠️ 需真模型（本地 Ollama 或云端），属人工/联网作业。

## 三、主应用「请求超时」设置 · 实施方案（待拍板）

### 3.1 现状（实测）

| 位置 | 现状 |
|---|---|
| `aiCore/core.ts:56` | `export const CHAT_TIMEOUT_MS = 180_000` |
| `aiCore/chat.ts:135` | 已是 `timeoutMs: opts.timeoutMs ?? CHAT_TIMEOUT_MS` ⇒ **只差调用点传值** |
| `aiCore/template.ts` | 159 / 186 两处引用常量 |
| `aiTasks/**` | **16 个文件**引用（audit 7 / jieWenJi 10 / creative 3 / extract 3 / suggest 3 …） |
| 酒馆 | 已有 `common.timeoutSec`（默认 300），但**只管酒馆内任务** |
| 主应用 | **无任何用户可调超时** ⇒ 慢模型跑长任务只能干等/失败 |

### 3.2 建议改法（最小侵入，5 步）

1. **存储**：`db.meta` 新增键 `aiRequestTimeoutSec`（与既有 `aiProviders` / `aiActiveProviderId`
   同层，见 `aiCore/session.ts` —— 全局共享、**不跟项目**）。默认 **300**，范围 **30–3600**。
   - 不加 DB 列、不改 schema、零迁移（老库读不到即用默认）。
2. **读入口**：`aiCore/session.ts` 增 `getAiRequestTimeoutSec()` 与派生的 `aiTimeoutMs()`，
   内存缓存口径与 `aiProviders` 一致（模块级缓存须比对，换库失效）。
3. **UI**：`AIConfigPanel.tsx` 加一个 `NumberField`（该文件**已 import**，且第 587 行有
   `contextWindow` 的现成写法可照抄）。文案建议：**「请求超时（秒）· 结构化任务的等待上限」**
   ＋ 说明「只影响主应用任务；酒馆模式另有「请求超时」设置」。
4. **调用点**：`aiTasks/**` 与 `aiCore/template.ts` 的 `CHAT_TIMEOUT_MS` → `await aiTimeoutMs()`。
   - ⚠️ **长文任务已走流式**（首字节到达即清总超时，见 `aiTasks/stream.ts` 注释）⇒ 改这个对它们
     **无实际影响**；真正受益的是**非流式的结构化任务**（JSON 抽取／审核／汇总这类）。
5. **保留 `CHAT_TIMEOUT_MS`** 作为兜底默认 —— `chat.ts` 的 `opts.timeoutMs ?? CHAT_TIMEOUT_MS` **不动**。

### 3.3 风险与对策

| 风险 | 对策 |
|---|---|
| 用户设太小 ⇒ 误杀慢模型 | 下限 30s ＋ `NumberField` 失焦钳回 ＋ `onClamped` 弹提示 |
| 与酒馆 `timeoutSec` 并存让人困惑 | 界面文案**显式写清**两者作用域不同 |
| `aiTasks` 调用点是否都在 async 上下文 | 逐文件确认（这些函数本就 `async`，预期无结构影响） |
| 提高超时后用户点了「停止」 | 无影响：`isCancelled` 判据与超时无关 |

### 3.4 验证口径（实施时执行）

- `tsc --noEmit` / `eslint src tests` / `bash tests/run-batches.sh all`（158 入口）
- **新增闸**：断言 `aiTasks/**` 不再直接使用 `CHAT_TIMEOUT_MS`（`chat()` 的兜底除外），
  与 `tavernTimeout` 同风格、同批（A 批）
- **实机**：设置改 30s，用**慢响应假端点**触发一个**非流式**结构化任务 ⇒ 应约 30s 报超时；
  改回 300s ⇒ 能跑完。（仓库已有 `.workbuddy/tmp/fake-openai-*.mjs` 可复用，但 tmp 会被清理，
  实施时应固定放进 `.workbuddy/tools/`。）

### 3.5 工作量与风险评级

**中等**：1 处存储 + 1 处读入口 + 1 个 UI 控件 + ~50 处调用点替换 + 1 条新闸 + 实机验证。
**风险低**：不改数据结构、不改 AI 提示词链路、不动酒馆；全部改动在「传参」层。
**可秒回滚**：不涉及迁移，回滚＝撤销该批提交。

## 四、另两项「不做」的理由（复核，免下轮重复提案）

### 4.1 同步目录「前缀限定」

- 现状已收紧到「**绝对路径 + `.yfe` 结尾**」（2026-10-07 六维审计批次 B），攻击面已很小。
- 再严需「限定在同步目录下」，但**主进程不知道同步目录**（目录由渲染层保存）⇒ 必须新增
  `sync:setDir` IPC ＋ 处理「尚未推送 / 重启恢复」的时序；且 fail-closed 会**误拒合法写入**。
- 结论：**风险 > 收益**，与「云同步重构」一并做。

### 4.2 酒馆 `onToken` 流式保活

- 本轮**有意不加** `onToken`：`chat.ts` 是 `stream: !!o.onToken` ⇒ 传了会把**传输形态**从非流式
  改成流式，对第三方中转站兼容风险大（项目历史记过「中转站跑不通」）。
- 而核心缺陷是「绕过用户可调设置」，改 `timeoutMs` 已解决；非流式下把 `timeoutSec` 调到 600
  已足够覆盖后台任务。
- 结论：**立项待定**。若要做，须独立立项 + 中转站兼容测试 + 实弹验证。

### 4.3 `TavernScript` 抽 hook

- 实测：`NovelEditor`(838) / `TavernFree`(812) 组件自身 **0 个 hook**（逻辑早在
  `useNovelEditorModel` / `useTavernFreeModel`）⇒ 已是薄组件，再拆只增 props 样板。
- `TavernScript`(896) 有 9 个 `useState`，但**被三栏 JSX 深度引用** ⇒ 抽 hook 要返回 20+ 字段；
  且项目**无 React 测试基建** ⇒ 纯搬移的行为等价**无法静态证明**。它该拆的部分（两个弹窗）
  早已独立成文件。
- 结论：**不拆**（触发条件见 §一）。⚠️ **不要按行数摊派**。
