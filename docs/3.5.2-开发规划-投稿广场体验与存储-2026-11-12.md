# 3.5.2 开发规划：投稿广场体验与存储优化

> 日期：2026-11-12｜状态：规划讨论稿，未实施。基线：3.5.1 已发布，当前源码 `6e6eef1`。本文不代表问题已经修复或通过验收。

## 一、版本定位

投稿广场是青春幻想引擎内供用户分享作品片段、交流与反馈的轻量社区。3.5.2 聚焦已有的浏览、投稿、审核、评论和管理流程，目标是交互便捷、反馈清楚、社区数据可保护和恢复。

不以扩大功能数量为目标。本版暂不规划私信、关注、复杂通知、多层评论或多服务器集群；是否引入新存储由隔离压测结果和后续决策确定。便携版当前不支持投稿广场，保持既有产品边界；网页及桌面按各自可用能力验收。

## 二、调研基线与限制

2026-11-12 约 08:16 对服务器作只读检查：服务 active，首页社区接口和健康检查返回 200；磁盘 40 GB、已用约 8.1 GB，内存 1.7 GiB、可用约 1.3 GiB；社区目录约 40 KB，投稿记录 3、评论 1、投票 3（含示例及非公开状态，不能视作公开用户内容数量）。这是低负载瞬时快照，不代表峰值容量或稳定性。

已检查的 `/opt/yfe/backups` 中，最近完整数据归档为 11 月 10 日，未在该归档中发现 community 目录；已查看的 root 定时任务和 systemd 定时器没有明确的社区备份任务。尚未排除其他路径、其他账号任务或云端备份，不能据此断言完全没有备份。应优先核对实际策略与恢复能力。

源码现状：社区使用单进程、多个 JSON 文件；每次修改同步读改写整个对应文件，临时文件加 rename 提供单文件原子替换。列表、评论等有遍历和排序；投稿上限 5,000、评论上限 50,000 是保护阈值，未经容量压测，不能作为性能承诺。多个文件各自原子写不构成跨文件事务，也不应假定具备断电持久性或多进程写入安全。

## 三、工作项与验收

### P0-1 评论分页和数量正确性

**现象：**服务端提供评论游标分页；前端仅读取第一页且未提供后续加载。发表成功后前端以已加载评论数量更新显示总数，多页时可能不准确。

**实施：**接入下一页加载、加载中/失败重试/到底状态；明确评论总数口径，以服务端确认的总数或可靠更新方式呈现，不用当前页长度充当总数。切换帖子、返回列表和并发加载时隔离请求归属，避免旧回执混入当前页面。

**验收：**隔离数据覆盖 0、1、20、21 条及多页，以及相同时间戳时的稳定排序；加载失败重试、切换帖子期间迟到响应不得串项或重复。明确分页期间新增、删除及审核状态变化的处理：已有游标按稳定排序加载，较新的内容通过刷新获得；不承诺动态列表天然是冻结快照。以已公开评论数为总数口径，待审、被拒和已删除评论不计入；列表、详情和发评后显示一致。计数与权威记录不一致时不得让前端凭已加载数量掩盖，应先修复或可解释地重算。桌面和窄屏可操作。

### P0-2 评论提交和网络重试

**风险：**服务端按令牌去重，前端每次尝试生成新令牌；服务端已写入但响应丢失后重试，可能重复。此为代码路径推断，先用隔离故障注入复现。

**实施：**同一份待确认提交重试复用令牌；区分已确认、失败、结果未确认。保存用户继续输入的新内容；账号、帖子或正文变化时不能把旧回执应用到新上下文。检查限流发生在去重之前的边界，避免合法重试被误判；不承诺跨设备无条件去重。

**验收：**模拟请求未到达、写入后响应丢失、连续点击、切换账号/帖子和用户继续输入；同一意图最多生成一条，后续新评论仍可正常提交，未确认结果有可理解的恢复路径。明确令牌的账号、帖子、正文及展示方式归属；重复令牌与不同内容冲突时不能静默返回旧评论。检查令牌跨页面刷新、登录失效与服务重启的实际有效期；如未提供持久恢复，不得宣称刷新或跨设备后仍保证去重。去重查询须先验证权限、目标可访问及归属，不能借此绕开频率限制或泄漏他人记录。

### P0-3 备份、恢复与一致性

**实施：**先盘点现有外部、主机和云备份及权限；确认覆盖 community 数据及其他关联数据。设计备份频率、保留期、访问权限、备份失败告警与异地副本；建立跨文件一致性快照或可验证的等效机制，并在隔离环境执行恢复演练。恢复前验证文件结构、记录数量和关键关联；不可用损坏文件静默覆盖现有数据。生产备份、计划任务和恢复均另行明确授权。

梳理评论及计数、投票及计数、审核及审计等跨文件写入；注入每一步失败、进程中止和重启，设计一致性检查、修复或可恢复机制。先复现并量化风险，再选事务、日志或其他方案；不得把原子 rename 等同于跨文件事务或断电不丢数据。

**补充风险：**现有 `mutate()` 直接修改缓存对象后再写文件；若写入失败，缓存可能保留未成功落盘的变更，须在隔离故障注入中验证读回和重试行为。异步读取请求正文的处理链也需要复核：等待期间投稿可能被下架、删除或更改，写入前应重新检查目标及权限，不能用过期对象覆盖较新的记录。文件缺失目前会走默认空数据，需区分首次初始化与已有社区文件意外丢失的场景，避免在未知状态下用空数据继续写入。以上是代码风险线索，实施前先复现，不预设已发生线上事故。

恢复与迁移必须考虑帖子和评论中的账号引用及匿名/昵称映射：明确 community 与账号数据的一致性边界、恢复顺序、授权作用域和孤儿引用处理；恢复旧快照不能悄悄重新公开已下架/删除内容，不能让不同时间点的账号或审核状态错配。备份应最小权限、加密保护并验证可解密；校验清单和演练输出不得包含正文、凭据或个人信息。恢复方案需说明停写、快照时点、恢复后新写入如何处理，以及失败时回退至何处；清理与覆盖均须事先有可核验的备份。

**验收：**隔离演练证明备份包含发布与非公开记录、评论、投票、审核/举报/申诉、档案、排行和状态等需要恢复的数据；恢复后的可见性、关联与计数正确；模拟损坏、写失败、空间不足和中途退出时保留原始证据、明确报错且可恢复。记录备份新鲜度、恢复步骤和结果，明确实际 RPO/RTO；具体目标待结合运行条件确定。

### P1-1 浏览、投稿和互动体验复核

按「浏览 → 阅读 → 返回 → 投稿/预览 → 提交 → 查看审核 → 修改或申诉 → 互动」走完整流程。复核列表返回位置、标签筛选、加载/空状态、弱网反馈与小屏布局；确认匿名/昵称切换、旧版继续展示、审核原因和下一步在适当位置可理解。

保持现有草稿和账号隔离、提交幂等、匿名边界、审核状态与作者资料不回退；新增改动前先用隔离账号和示例数据复现问题，不记录真实用户正文。新投稿已有本机草稿，编辑态与评论草稿保护须按实际流程检查，不假设其已具备相同能力。

补充检查：正文按 Unicode 码点计数，但评论输入框存在浏览器 `maxLength`（UTF-16 单位）与展示计数口径差异，应以中英文、emoji 和组合字符验证输入限制是否与服务端一致；检查回帖提交中用户继续输入、关闭/切换帖子、切换账号及迟到响应的内容归属。分别验证详情读取失败与评论读取失败的提示和重试，避免把网络失败误报为投稿不存在。

**验收：**游客、普通账号、管理员按权限完成适用流程；网络失败和刷新后输入保留规则准确可见；发布与审核状态不误导；键盘、常见桌面宽度和移动窄屏可完成主要操作。具体视觉问题以复现截图和验收记录为准。

### P1-2 轻量监测与容量保护

设计只包含聚合指标的监测：文件体积、记录数量、磁盘余量、进程内存、请求延迟、写入错误、备份结果与时间；避免记录正文、私密账号标识或密钥。明确提醒阈值、接收方式和负责人；不得自动删除用户内容来释放空间。

**验收：**在隔离环境模拟容量接近上限、写盘失败和备份失败，告警可发现、恢复后状态可消除；服务端限制保留准确提示。阈值为待定参数，不把缺少告警等同于无故障。

### P1-3 隔离容量与性能评估

在独立数据目录及服务上，用合成内容分别测试**当前量级、增长量级、接近保护上限**，记录数据大小、并发数、机器配置、p50/p95/p99 延迟、内存、事件循环阻塞、失败率、备份和恢复耗时；包含列表、详情、分页、投稿、评论、投票和排行，并验证正确性。具体规模及合格阈值由实际用户预期和服务器预算确定；未确定前不宣称支持某用户数。

结果满足预期则保留 JSON 并补强；出现明确瓶颈或一致性要求超出其能力时，形成 SQLite 等单机方案的独立决策：列出迁移映射、完整性校验、停写或一致快照、失败回滚、备份恢复及资源开销。数据库迁移不自动纳入本版，需按结果和风险决策。

压测前登记数据构成（含多版本投稿、不同状态、举报/申诉、投票和排行）、并发读写组合、预热与持续时间、机器限制和基线；不得连接生产、真实模型或真实账号。分别报告服务端延迟与端到端体验，记录内存/磁盘峰值与正确性，不根据空载 ping 推算并发容量。兼容性验证须覆盖旧版客户端与新版服务端的混用、权限与响应字段；若接口调整，先定义向后兼容及回滚策略。

## 四、实施顺序与里程碑

1. **基线与复现**：核实当前功能和已有备份；隔离复现分页、重试和跨文件中断风险，保存可重复证据。
2. **互动修复**：完成 P0-1、P0-2，补充必要的失败注入及浏览器验证。
3. **数据保护方案**：完成 P0-3 的设计、隔离备份恢复与故障演练；生产配置另行授权后实施。
4. **体验和容量评估**：完成 P1 交互复核、监测方案和压测，依据结果决定存储路线。
5. **版本验收**：全量回归、审计和适用端测试；更新版本记录、使用说明与已知边界。具体实施中按里程碑更新工作日志及交接记录。

## 五、总体验收与边界

- 修复项须有修前复现、修后回归及失败路径证据；数据写入必须验证账号、帖子和请求归属。
- 用户可完成浏览、投稿、互动和管理；管理员可完成审核、举报及已有申诉流程。权限、匿名、草稿和审计边界保持正确。
- 社区数据的备份、恢复及一致性有隔离演练证据，容量和性能以测试配置和结果说明，不以静态分析替代真实多设备、断电或生产压力测试。
- 三端实际交付与运行矩阵、真实模型及真实多设备等未覆盖项单独列明；本轮不读取或修改真实作品、账号及社区正文，不自动清理生产数据。
- 3.5.1 之后仅网页版已包含的致谢名单与「关于打赏」位置调整，下一次桌面与便携构建时核对并同步。
- 本文为规划；开发、真实数据操作、生产部署、封装、发布和清理不因本文件自动执行。

## 六、待讨论决策

1. 社区预期的活跃用户和同时在线范围，作为压测规模及延迟目标依据。
2. 现有外部备份位置、恢复责任人、允许的数据丢失窗口与恢复时间。
3. 审核结果展示和失败反馈的具体文案；是否确需额外交流功能，以用户反馈决定。
4. 存储路线在压测和故障演练后决定；新数据库、生产迁移和切换方式另行确定。
5. 动态评论分页遇到新内容时的提示与刷新方式；未确认提交在刷新后是否需要可恢复，以及保存多久。
6. 备份对社区与账号数据的一致性范围、访问权限、加密密钥保管及误删/下架状态恢复策略；生产执行需要明确操作窗口与负责人。
