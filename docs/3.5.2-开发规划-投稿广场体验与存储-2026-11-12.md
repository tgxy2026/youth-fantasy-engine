## 一、版本定位与范围

投稿广场是引擎内的轻量交流社区。3.5.2 以已有浏览、投稿、审核、评论和管理功能好用为目标，同时增强服务端数据保护。暂不增加私信、关注、复杂通知、多层评论或多服务器集群；是否迁移存储根据隔离压测和后续决策确定。网页和桌面按适用能力验收；便携版维持当前不支持广场的边界。

开发提交 `275a7ec` 与 `16b777f` 已在本地；工作区另有他人的 3.4.3 / 3.5.0 / 3.5.1 文档归档变动，继续原样保留。

## 三、P0：复核问题与修复结果

### 本次复核定案：P0-R1 / R2 / R3 已修复

三项均先复现、再修改，并以最终源码重跑专项、演练与全量。**修复不等于未覆盖边界已消失**，见每项「边界」。

**P0-R1：评论文件缺失的可证明性。** 修前 `coreFileProblems` 只看 `counts.comments > 0`；仅有帖子、公开计数为 0 且缺 `comments.json` 时，检查与备份仍成功（隔离样本 `.workbuddy/tmp/acceptance-r3-vXcOaJ/`），无法区分「从未写入评论」与「待审/已删评论文件丢失」。

修复：新增 `server/lib/communityFiles.mjs` 与 `<community>/.yfe-community-meta.json`，持久记录 `commentsInitialized`。语义为：真空目录首次启动写 `false`；`comments.json` 存在时写/补 `true`；标记 `true` 而文件缺失 → `COMMENTS_FILE_LOST` 拒绝；标记 `false` 且帖子计数为 0 → 历史空社区允许；无标记但有帖子 → `COMMENTS_FILE_UNVERIFIED` 拒绝；标记 `false` 但计数 > 0 → `COMMENTS_METADATA_CONFLICT` 拒绝；`posts.json` 缺失但目录还有其他社区文件 → 拒绝。`inspectCommunity`、`createBackup`、服务启动共用同一判定。人工核对后可用 `node server/community-backup.mjs adopt-empty-comments --data <dir> --confirm-adopt-empty` 补空并持久记录，命令在 `comments.json` 已存在、标记为 `true` 或缺少 `posts.json` 时拒绝。

验证：`.workbuddy/tmp/352-repro3/r1-repro.mjs` **25/25**（`r1-result.json`）；`tests/communityBackup.test.ts` 覆盖从未有评论、仅待审后丢失、曾初始化后丢失、元信息缺失、标记/计数冲突、仅剩 `true` 标记（不得降级为首次使用）、采纳被拒与重启；`communityBackup` **124/124**、`communityComments` **45/45**。

边界：标记只证明「本工具/本版本是否写过评论文件」，不重建历史事实；无标记旧社区会被停止而不是静默补空，需人工核对；采纳命令只是把人工结论落盘，不是数据恢复或丢失证明；标记写失败不阻断已有可读数据，但下次启动仍会按保守规则拒绝不可证明状态。

**P0-R2：恢复差异必须覆盖评论状态、正文与可见性。** 修前 `diffVisibility` 对评论只比较 ID；同一条评论当前 `removed`、备份 `visible` 时变化清单为空，恢复会重新公开已删除内容。复现脚本 `.workbuddy/tmp/review-352-r3.mjs`，并用隔离备份/恢复补全风险验证。

修复：`diffVisibility` 双向比较帖子的可见性、版本/正文/展示指纹与当前独有记录；评论比较同 ID 的 `status`、`body`、`display`，并报告当前/备份独有评论；举报、申诉、档案、排行、投票按状态/内容指纹统计变化，审计统计当前独有记录。恢复预览默认因 `VISIBILITY_CHANGES` 拒绝，只有显式 `--accept-visibility-changes` 才执行一次恢复；预览不输出正文、uid、昵称或登录名；拒绝时 live 不变，接受后按备份恢复但保留恢复前副本。

验证：`tests/communityBackup.test.ts` 的 R2 用例覆盖评论状态、正文、展示方式、备份独有评论、举报/档案/审计变化、差异脱敏、默认拒绝且 live 不变、显式接受后按备份恢复；隔离演练 **26/26** 覆盖下架稿不复活、待审评论不可见、举报/申诉/排行保留。

边界：这是「差异检测 + 人工确认」，不是自动合规判断或字段级三方合并；接受恢复仍会以备份旧值覆盖当前审核/编辑，操作人必须核对预览；没有墓碑文件，物理删除的「不复活」只能靠默认拒绝与人工判断。

**P0-R3：停写确认与前后状态比较不是锁。** 修前 `--confirm-stopped` 只是人工确认，`stat` 只能发现检测窗口内的变化；并行 4/4 只证明特定交错被拒绝，不证明跨进程排他。

修复：新增 `server/lib/communityLock.mjs`，在社区目录旁创建 `<community>.backup.lock`（`openSync(..., 'wx')` 独占创建）。服务启动发现残留锁即拒绝；运行中每次 `mutate` 检查锁，命中返回 `COMMUNITY_BACKUP_LOCKED`，HTTP 写入返回 503 `BACKUP_IN_PROGRESS`，读取仍可用；`createBackup` / `restoreBackup` 外层获取锁并在 `finally` 释放，冲突返回 `LOCKED` 且不产生正式备份目录；崩溃残留锁必须由操作人执行 `node server/community-backup.mjs unlock --data <dir> --confirm-stale` 清理。`--confirm-stopped` 仍保留，作为人工停机确认，不被锁替代。

验证：`.workbuddy/tmp/352-repro3/r3-two-process.mjs` **3/3**（两进程并发只有一个成功、另一个明确 `LOCKED`、失败方不产生正式目录，`r3-two-process-result.json`）；`communityBackup` 覆盖两进程竞争、写入期间锁阻断、残留锁拒绝/确认清理、锁路径不可写失败关闭；`communityComments` 覆盖锁存在时 API 写入 503、读取 200、锁未写入、释放后可写。

边界：这是**协作式文件锁**，只约束遵守该协议的进程；旧版本、外部脚本或不检查锁的写入者仍可能绕过，单靠锁无法证明「所有写入进程已停止」。写入请求在锁检查后、落盘前仍有被备份窗口切入的间隙，因此锁不能替代停服务与人工确认。残留锁需人工确认，锁不提供断电/网络文件系统/多主机语义，也未替代 fsync。生产使用仍须停写窗口、运维授权与启动前检查，不能宣传为已自动保障。

### P0 修复的边界

- 一致性边界是「人工停写确认 + 读写前后文件状态复核 + 协作式锁」；不是强制锁、不是热备、不是跨文件事务、不是断电持久性证明。
- 锁只约束遵守协议的进程；旧版本或外部写入者可绕过，「所有写入已停止」仍需运维确认。残留锁必须人工核对后清理。
- 恢复仍要求停写；备份目录权限、加密、异地副本、定时任务与告警均未在生产启用。
- `atomic.mjs` 未加 fsync；单文件 rename 只证明不会读到半个文件，不证明断电后一定落盘。

## 六、建议的直接方案与授权边界

- **容量与监测：**按推荐方案作为计划默认：日活 100、并发 10（不是当前数据或性能承诺）；在同等资源隔离机用 1/5/10 并发测 30 分钟，目标读取 p95 ≤ 500 ms、写入 p95 ≤ 1 s、错误率 < 1%，业务正确性 100%。采集磁盘、备份新鲜度、失败率及事件循环延迟；阈值先用磁盘使用 70% 提醒/85% 紧急、备份超 26 小时提醒作为建议，经过演练再定。S3 已接近这些性能目标，不能声称已达标。
- **备份：**先确认是否存在外部备份。按推荐方案作为计划默认：每日一次经停写协调的一致快照、本机保留 14 份、加密异地副本、每日检查结果、每月至少一次隔离恢复演练；暂定 RPO 24 小时、RTO 4 小时，实际取决于维护窗口、人手、容量和验证。负责人建议由服务运维承担，密钥独立存放并先验证恢复；这些是计划默认，不是已批准或已启用措施。当前工具默认保留删除行为须审计，生产实施不可自行清理旧备份。
- **恢复：**默认禁止复活已删/下架/撤回内容；按 P0-R2 优先保留当前审核状态，无法保证时停止并人工核对。恢复前停写、创建并验证当前副本，明确数据时间点和回退流程。
