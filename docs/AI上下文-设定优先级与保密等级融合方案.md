# AI 上下文 · 设定优先级 与 保密等级 · 融合方案

> 性质：**设计决策文档**（方案级，未写实现代码）。
> 缘起：2.2 后两项（一键拆书 / 全自动工作流）都会大量产出设定，必须先定"长篇有限预算下，哪些设定优先喂给 AI"。
> 前置阅读：`docs/AI上下文与保密等级-现状摸底.md`（现状与全部代码位置）。
> 结论先行：**不并存，也不等同 —— 把「保密等级」语义升维为「信息档位」，单字段扇出两条独立输出。**

---

## 一、问题定义

长篇小说写到中后期，设定量会线性增长，但上下文预算是固定的（当前 `buildProjectContext` 默认 12000 字符）。于是产生三个必须回答的问题：

1. 哪些设定应该**优先**给 AI？
2. 哪些是**有预算才给**？
3. 哪些**不需要给**？

同时，作者已经在 9 个页签里标了「保密等级 S/A/B/C」。两者是并存，还是融合？

---

## 二、为什么"并存"是坏选项

| # | 问题 | 说明 |
|---|---|---|
| 1 | **组合矛盾** | 两字段会产生 4×4=16 种组合，其中大半无意义（S 绝密 + 低优先？C 琐碎 + 必带？）。作者填了之后系统无法给出连贯行为 |
| 2 | **心智负担翻倍** | 9 张表、每条记录要判断两件事。写小说的人不会认真维护两套分级 |
| 3 | **已有现实证据** | 现状：9 张表的 `保密等级` 默认值几乎全是 `C`，且**全库没有任何逻辑读它** —— 说明单靠"多给一个字段"并不会让它被用起来 |
| 4 | **真实需求是少数派** | 需要"高保密 + 低重要"或"低保密 + 高重要"的条目占比很低（估 <5%）。为少数派开一个全局字段不划算 |

**结论：字段数量应当收敛，而不是扩张。**

---

## 三、为什么"等级直接当优先级"也是错的

最直觉的做法是"把 S 当最高优先级"。但这会在三处翻车：

| 反例 | 按"S=最高优先"的后果 | 正确做法 |
|---|---|---|
| S 级「世界终极真相」 | 在**角色视角**下被优先塞进去 → **直接剧透**，恰好反了 | 角色视角：**排除** |
| S 级「主角最终结局」（在写第 21 章时） | 优先占掉 12000 预算，挤掉"本章出场角色的当前状态" | 对**局部续写**任务价值有限，应让位给局部相关设定 |
| C 级「本章新出现的镇名」 | 排在最后 → 被丢；但本章立刻就要用 | C 级也可能有**时序相关性**，靠时间轴救 |

**根因**：「保密等级」与「预算优先级」在语义上**正交**（一个是"谁能看"，一个是"值不值得占预算"），只是多数情况下答案绑定。

## 四、设计方案：单字段 · 双输出

### 4.1 语义升维

字段名保持 `保密等级`（不破坏 9 页签与既有数据），**语义**从"保密"升维为：

> **信息档位** —— 决定「谁看得到」与「预算优先」。原描述里其实已经写了"保密/**重要度**分级"，本方案只是把后半句真正实现。

### 4.2 默认映射表（唯一真源）

| 档 | 展示文案 | 角色视角可见 | 作者/导演视角预算 | 角色视角预算 |
|---|---|---|---|---|
| **S** | S · 绝密（剧透管控） | ❌ 排除 | **P0 必带** | —（不适用） |
| **A** | A · 重要（主线关键） | ✅ 可见 | P1 优先 | **P0 最高** |
| **B** | B · 次要（支线） | ✅ 可见 | P2 常规 | P1 |
| **C** | C · 琐碎（日常） | ✅ 可见 | P3 最先丢 | P2 最先丢 |

**关键洞察：S 是唯一的"双面特例"**（可见性最低、预算最高）；A/B/C 两个维度**同向**。所以一个字段完全够用，不需要第二个字段。

⚠️ 注意「角色视角预算」一列：S 被排除后 **A 顶上为第一优先**，排序需按视角重排，不是简单套同一张数值表。

### 4.3 稀疏覆盖（可选，1 个字段）

只有作者明确知道"这条不符合默认映射"时才覆盖。建议**只给预算优先加覆盖**：

- 新字段（可选）：`预算覆盖` —— 选项：跟随等级 / 高 / 中 / 低 / 不入AI
- **不给可见性加覆盖**：那条已有更精确的机制（`secrets` 表的「知情者」逐条精确 + `AUTHOR_SIDE_FIELDS` 列级），重复造轮子只会产生两套互相打架的真相

## 五、第三维度：时序加权（本方案的增量核心）

"重要性"不是常量，它**随写到的章节位置变化**：

| 例子 | 现在不重要 | 什么时候重要 |
|---|---|---|
| 伏笔「计划回收位置 = 第 35 章」 | 在写第 21 章时 | 第 32~38 章附近 |
| 角色「活跃卷 = 卷五」 | 在写卷三时 | 卷五 |
| 角色「首次出场 = 第 40 章」 | 现在**根本不该出现**（人物还没登场） | 第 40 章之后 |

好消息：**驱动这一维度的字段和基础设施都已经存在**：

- `anchorChapterId`（时序锚点，已在 `buildProjectContext` 里实现，用于章节召回与裁剪）
- 角色卡 `活跃卷与出场频率` / `首次出场`
- 伏笔 `计划回收位置`
- 知情权限 `计划揭晓章节` / `何时知道（章节）`

**加权规则草案**（P2 阶段落地）：

1. 角色卡 `活跃卷` 命中当前卷 → ×1.0；未命中 → ×0.6
2. `首次出场` 晚于当前章 → 降级到 P3（人还没登场）
3. 伏笔 `计划回收位置` 落在当前章 ±3 章 → 直接提到 P0
4. 其余保持默认映射

## 六、与既有机制的分工（不重复造轮子）

现状里"可见性"已经有三个粒度、而"预算"只有表级 —— 本方案补的正是**行级预算**这个空洞：

| 需求 | 用什么 | 粒度 | 现状 |
|---|---|---|---|
| 整张表不给 | `viewMode:'character-view'` + `AUTHOR_SIDE_TABS` | 表级 | ✅ 已有 |
| 整列不给 | `AUTHOR_SIDE_FIELDS`（≈40 字段名） | 列级 | ✅ 已有 |
| 单条不给（粗） | **保密等级 S** | 行级 | 🔴 待接 |
| 单条不给（精） | `secrets.知情者` | 行级 | ✅ 已有（仅 secrets 表） |
| 行间谁先塞 | **保密等级 + 时序加权** | 行级 | 🔴 待接 |
| 表间谁先塞 | `PRIORITY`（硬编码 25 表） | 表级 | ✅ 已有 |

## 七、直接回答三个问题

### 7.1 优先给（P0 / P1）

- 作品定位 / 世界设定 / 力量体系 —— 一致性之根（`PRIORITY` 前三位）
- 全书总纲 —— 走向的唯一真源
- **主要角色**（尤其当前卷活跃者）+ **人物关系**（活跃角色之间）
- **当前章细纲 / 上一章结尾 / 本章相关章节召回**
- **等级 A 及以上的条目**
- **当前章 ±3 章内要回收的伏笔**（时序加权后提为 P0）

### 7.2 有预算才给（P2）

- 次要角色 / NPC —— 当前卷不出场的
- 国家势力 / 地理风物 / 种族生物 / 物品资源 —— 当前卷未涉及的
- 历史事件（远期）、名词术语（本卷未引用过的）
- **等级 B**

### 7.3 不需要给（P3 / 排除）

- `progress` 写作进度 —— **已是硬排除**（纯码字流水，对模型是噪音）
- `changelog` 设定变更 —— 运营台账，对生成几无价值
- `ideas` 灵感素材 —— 除非当前功能就是"灵感辅助"
- **角色视角下的所有 S 级**
- 等级 C 且与本章无关的条目

## 八、实施分期

### P0 · 最小改造（只动一个函数 + 两处调用）

| 项 | 内容 |
|---|---|
| 新增 | `rankOf(row, tab)` 纯函数 —— 读 `保密等级` → 数值（S=0 / A=1 / B=2 / C=3 / 空=2） |
| 修改 | `renderCards`（`aiContext.ts:220`）与 `renderTable`（`:232`）的 `recs.slice(0, cap)` → **稳定排序后** `slice(0, cap)` |
| 🔴 约束 | 排序必须**稳定**（同等级保持录入顺序）。否则 prompt 顺序每次可能不同 → 本地模型 prefix cache 失效（变慢）+ 输出抖动 |
| 测试 | 新增 `tests/contextRank.test.ts`：排序正确性 + **同级稳定性** + 空等级兜底 |
| 不改 | schema、既有数据、UI —— 九张表已填的 S/A/B/C **立刻生效** |

### P1 · 让保密等级第一次真的"保密"

- 角色视角下**过滤掉 S 级行**（`RenderOpts` 增加 `hideSecretRows`，与 `hideAuthorFields` 同层）
- 效果：S 级条目从"只在表/列级被保护"补上"行级保护"

### P2 · 时序加权

- 引入 `activeVolumeId` / `currentChapterIndex`，按 §5 规则对 P0 排序加权
- 需要解析「卷五」「第 35 章」这类自由文本字段 —— 有不确定性，故放最后

### P3 · 可选（长期）

- 段级超预算时改为**降级**而非整段丢弃（先丢 C 级行，而不是丢整张表）—— 涉及 `push` 重构，改动较大

## 九、风险与开放问题

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **标注质量决定效果**：默认值现在是 `C`（=最先丢），作者不标等于没标 | ① 默认值 `C` → `B`（中性，需 migration，只影响新条目）；② 或给"未分级"一个视觉提示 |
| 2 | **S 级在作者侧功能（续写/工作流）该带吗** | 建议**带**（续写需要知道走向），但要在提示词里加元信息标注，如 `〖以下为作者已知走向，不得写入正文〗`，否则模型可能把结局直接写出来 |
| 3 | **排序稳定性** | 同级必须保持录入序（见 P0 约束） |
| 4 | **等级 ≠ 重要性** | 如"主角的公开身份"是 A 级重要但零保密 —— 靠 §4.3 稀疏覆盖解决 |
| 5 | **大表排序开销** | 纯内存 sort，千行级可忽略 |

### 12.4 实机对照实测（真 Chromium + 本地模型）

**为什么必须构造场景**：示范项目每张表的行数都远小于 `ROW_CAP`，无论怎么排都"全带得进去"，排序在它身上看不出任何差异。故脚本主动灌 **60 条 C 级噪音行**（order 排在真实行之前），复现"写到几十万字时、先录入的琐碎条目按录入序占满 cap"这一真实场景。

| 指标 | 改造前（模拟旧 `slice(0,cap)`） | 改造后 |
|---|---|---|
| terms 真实条目保留 | **0 / 32** | **30 / 32** |
| 其中 S/A 关键条目 | **0 / 15** | **15 / 15** |
| 被挤出的条目 | 全部 | 仅 2 条 C 档 |

**生成层**（同一问题、两份上下文）：问「把十万柄剑与十万条命熔成铁、糊死神族之门的那件事，正式名称叫什么？」（答案 = S 级条目「焊门」）

| 模型 | 改造前上下文 | 改造后上下文 |
|---|---|---|
| qwen3:4b | 「资料未提及」 | 「正式名称叫：焊门。」 |
| **Qwen3.8-27B（作者日常）** | 「资料未提及」 | 「焊门」 |

两个模型均 **9/9 全过**。核心结论：**改造前的失败模式是"AI 拿到的全是无关琐事、真正相关的设定一条都没有"**，模型只能答「资料未提及」—— 这正是长文一致性崩掉的起点。

### 12.5 已知边界（诚实记录）

- 本次收益是**行级**的（表内排序）。**表间顺序仍由 `PRIORITY` 硬编码决定**，本次未动。
- 收益大小取决于"表内行数是否超过 `ROW_CAP`"。示范项目当前规模下（每表 1~32 行）**无差异**；它要到长篇中后期（单表上百行）才自然显现 —— 所以本轮的实测数据来自**主动构造的挤压场景**，不是示范项目的自然状态。
- 尚未做的：**P1 角色视角按等级过滤 S 级行**（保密等级目前只影响"顺序"，还不影响"可见性"）；P2 时序加权。
