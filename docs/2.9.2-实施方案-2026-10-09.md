## 1. ① 文风体检 + 投稿前自检落库（P1-③）

### 现状（源码实证）

- 引擎在 `src/lib/manuscriptCheck.ts`：`analyzeStyle()` → `StyleFingerprint`、`analyzePacing()` → `PacingReport`、
  `toObservations(fp)` → `Observation[]`、`buildCheckReportText()`。
- 展示在 `src/components/ManuscriptCheckPanel.tsx`。
- 结果**只在组件 `useState` 里** —— 切页签即重跑、关软件即蒸发。

### 台账已就绪（2.9.1 建的 `lib/checkLog.ts`）

```ts
export type CheckEngine = 'continuity' | 'foreshadow'          // ← 要扩
export interface CheckSnapshot { ts; engine; scope; total; error; warn; info; titles[] }
export async function trendOf(engine, scope = 'global'): Promise<CheckTrend | null>
```

`CheckSnapshot` 是**通用结构**（统计值 ＋ 前 12 条标题），不绑业务 ⇒ 扩展无需改表结构。

### 改法

1. `CheckEngine` 增加 `'style' | 'manuscript'`；
2. 新增两个包装：`styleLogged(text)` / `manuscriptLogged(text)` —— 与既有 `continuityLogged()` / `foreshadowLogged()` 同范式（跑引擎 → 记快照 → 共用 `revisionOf()` 缓存）；
3. `ManuscriptCheckPanel` 顶部加 `<CheckTrendNote engine="manuscript" />`（该组件 2.9.1 已在 `AuditModals.tsx` 里落地，可复用或提到公共处）；
4. 统计口径：`total/warn/info` 取 `Observation[]` 的计数（`Observation` 已带级别）。

### 验收

- 连续跑两次（同数据版本）→ **第二次不新增台账**（缓存生效，沿用 2.9.1 的可观测判据）；
- 改动数据后再跑 → 台账 +1，趋势行显示「比上轮多/少 N 条」；
- `tests/checkLog.test.ts` 扩 4~6 条；面板交互进实机脚本。

**预估**：源码 3 文件 ＋ 测试 1 文件。

## 2. ② 优化工单「按问题类型聚合」视图（P2-①）

### 现状（源码实证）

```ts
// lib/optimizeTicket.ts
export function sortAndDedup(items) {
  return uniq.sort((a, b) =>
    a.chapterNo - b.chapterNo                                   // ← 章序优先
    || SEVERITY_ORDER[a.severity] - SEVERITY_ORDER[b.severity]
    || SOURCE_ORDER.indexOf(a.source) - SOURCE_ORDER.indexOf(b.source)
    || a.title.localeCompare(b.title))
}
export function groupByChapter(items): TicketChapterGroup[]
```

→ 当前只有**按章**一个视角。它服务的是「按章合并改写」这个执行流，**不该动**。
缺的是另一个问题：**哪类问题在全书里最普遍**（跨章聚合）。

### 改法（纯增量，不动既有排序）

1. 新增 `groupByIssue(items)`：

```ts
export interface TicketIssueGroup {
  key: string          // `${source}::${title}`
  source: TicketSource
  severity: IssueSeverity
  title: string
  chapters: { id: string; no: number; title: string }[]   // 出现在哪些章
  count: number
  action: ChapterRewriteAction | 'manual'
}
export function groupByIssue(items: TicketItem[]): TicketIssueGroup[]
```

2. **排序口径（可可的建议，规则要一句话能说清）**：
   **先按严重度分档**（`warn` 先于 `info`）→ **档内按出现章数降序** → 章数相同按标题。
   🔴 **刻意不引入加权公式**（如「严重度 × 频次」）—— 加权会让作者无法预判顺序，而「分档 + 频次」一眼就懂。
3. 界面：`OptimizeTicketPanel` 加「**按章 / 按类型**」视图切换；按类型视图里点击某组 → 跳/筛到该章。

### 验收

- 同标题跨 3 章的 warn 排在只出现 1 章的 warn 前面；
- 切换视图不丢勾选状态（若有勾选）；
- 既有「按章」视图**逐字不变**（回归断言）。

**预估**：源码 2 文件；`tests/optimizeTicket.test.ts` 扩 5~8 条。

## 3. ③ `dataHealth` 挂「设定变更」页（P1-②）— 🔴 需先选落点

### 现状（源码实证）

- `runDataHealthCheck()` 在 `src/lib/dataHealth.ts`，返回 `{ issues, scannedTables, tavernGhosts? }`；
  已把 `GEO_MAPS_TAB` 显式并入扫描面（因为《地理风物》的「所属地图」引用它）。
- 当前唯一产品入口：`src/components/CheckTools.tsx:142`（「检查工具」页）。
- 目标落点「设定变更」＝ `schemaTabs/part3.ts:64`，`type: 'table'`。

### 🔴 真正的障碍

「设定变更」是**通用表格页**，在 `App.renderContent` 里由：

```tsx
return <TableSheet key={tab.id} tab={tab} onNavigate={navigate} ctx={visCtx} ... />
```

渲染。而 **`TableSheet` 目前没有「页顶插槽 / 自定义区块」能力**（已 grep 确认无 `topSlot`/`children` 之类）。
⇒ 原报告把这项估成「小改动」是**低估了**，此处更正。

### 三个可选落点（请主人拍板）

| 方案 | 做法 | 代价 | 影响面 |
|---|---|---|---|
| **A · 给 `TableSheet` 加通用页顶插槽** | 加 `topSlot?: ReactNode` prop；`App.renderContent` 对 `changelog` 传一个只读提示条 | 中（动通用组件，**所有表格页都受影响**，需全量回归） | 大但一劳永逸，将来别的页也能用 |
| **B · 只给 changelog 包一层专用壳** | `App.renderContent` 对 `tabId === 'changelog'` 返回 `<ChangeLogShell><TableSheet/></ChangeLogShell>` | 小（局部） | 局部；但引入「按 tabId 特判」，不够优雅 |
| **C · 不硬挂页面，改成「有高危才提示」** | 页面不常驻区块；改为在**进出该页时**静默跑一次，仅当有 `error` 级问题时出一行提示条 | 小 | 局部；且避免「每次渲染都跑扫描」的性能问题 |

**🔴 可可的推荐：C**（若不介意 `TableSheet` 改动则 A）。
理由：这项的真实价值是「改设定时别忘了看数据健康」，而 **dataHealth 是全库扫描**——方案 A/B 都会让它随页面渲染反复跑（需额外做缓存），
C 天然规避了这点，且提示只在「真有问题」时出现，不打扰。

### 验收

- 造一条断链 → 进「设定变更」页出现提示；修好后不再出现；
- 无问题时**页面与现在逐字一致**（无空区块）；
- 扫描耗时有实测数字（写进文档）。

**预估**：视方案 1~3 文件。

## 4. ④ AI 类结果落库语义（P2-②）

### 涉及哪两个

| 功能 | 引擎 | 是否需模型 | 结果形态 |
|---|---|---|---|
| 节奏与章末钩子 | `lib/paceAnalysis.ts` | 是 | 段位分布 + 钩子有无（**含量化值**） |
| 读者视角审问 | `lib/readerProbe.ts`（`ReaderProbeResult`） | 是 | AI 的观察文字 + 段号定位 |

### 可可的判断（结论先给）

🔴 **建议只落库「节奏与章末钩子」，「读者视角审问」维持不落库。**
理由：趋势的前提是**同一把尺子重复量**。节奏有程序算的量化值（爆点落在前/中/后、章末有无钩子），跨章可比；
读者审问产出的是**开放式观察文字**，它的价值在「当场读一遍的启发」，同一章两次跑本来就会不一样，做趋势没有意义。

### 若落库节奏 → 需要定的口径

1. `CheckSnapshot` 增加**可选**字段 `model?: string`（记录生成时用的模型名）；
2. `trendOf()` 只在该 engine 的**同 model** 快照间算趋势；
   `model` 缺失的老快照单独标注「模型未记录，不参与对比」，**不混算**；
3. 记录点：`PaceAnalysisPanel` 真跑完时（沿用 `revisionOf()` 缓存，与 ① 同范式）。

### 验收

- 换模型后再跑 → 趋势行明确显示「上一次是 X 模型，不参与对比」；
- 同模型连跑两次 → 第二次不新增台账（缓存）。

**预估**：源码 2 文件。

## 5. ~~⑤ D2 地图元信息 → 行程对账（P1-①）~~ — ❌ **已放弃（2026-10-09 拍板）**

> 下面保留原始分析**仅供存档**（防止下一轮有人再把它当新点子提出来）。**本版不实施，也不需要再做数据探查。**

### 现状（源码实证）

- **A2 已落地**（2.9.1）：`lib/continuityCheck.ts` 第 12 节「行程时间存疑」——
  读《地理风物》的「距离与行程时间」自由文本，经 `parseTravelDays()` 解析；**解析不出返回 `null`，调用方跳过**。
- **`geomaps`**（`schema.ts:57` 的 `GEO_MAPS_TAB`，**不在 TABS**）字段：
  `编号 / 名称 / 每格公里（枚举 ['1','10']）/ 说明 / cH('底图模式') / cH('底图')`。
- 《地理风物》另有隐藏列 `cH('地图格子')`（`gx,gy;gx,gy;…` 坐标串）。

### 原报告的设想与它的缺口

报告写「若要支撑 A2 的行程对账，把 geomaps 的元信息（名称 / 每格公里）纳入可读范围」。
但**「每格公里」× 格距只能算出「距离」，算不出「天数」**（没有速度基准）⇒ 无法替代「距离与行程时间」这一列。

**因此可可把这项重新定义为两件不同的事：**

| 子项 | 内容 | 判断 |
|---|---|---|
| ⑤-a | 把地图元信息**塞进 AI 上下文**（供模型写作时参考） | ❌ **建议不做**：「每格公里」对生成正文几乎无用，却要占 prompt 预算 |
| ⑤-b | 新增第 15 类检查：**用「地图距离 ÷ 登记天数」算日均行进，超出常识区间就提示** | ✅ 有价值，但**前提是数据齐备** |

### 🔴 ⑤-b 的前提未验证 ⇒ 先做「数据可用率探查」

要算距离，需要同时存在：① 两地点都在《地理风物》有**地图格子**（隐藏列）；② 其「所属地图」能在 `geomaps.名称` 里对上；③ 该地图有**每格公里**。
这三条**任何一条缺失，这项检查就形同虚设**。

**第 0 步（约半小时，不改源码）**：写一个只读探查脚本，对**真实项目数据**统计：
- 《地理风物》里「地图格子」非空的行数 / 总行数；
- 这些行的「所属地图」能对上 `geomaps` 的比例；
- 能算出「格距 → 公里」的**相邻章地点对**有多少组。

**据探查结果决定**：
- 可用对数 ≥ 20 ⇒ 值得做 ⑤-b（定常识区间时再讨论阈值）；
- 可用对数 < 5 ⇒ **本版不做**，只把探查结论写进文档（免得下一轮再提）。

### 验收（若做）

- 造一组「10 公里却登记 30 天」→ 报 `info`；
- 日期/格距/每格公里任一缺失 → **跳过**（沿用 A2 的「宁可不报」口径，有负向断言）；
- **只提示、绝不改数据**（契约断言）。

**预估**：探查 0.5h；若做，源码 2 文件（`continuityCheck` + 一个 `geomapDist` 只读源）。
