## WEB-01 数据自动备份（**暂缓**）

- **状态**：主人 2026-10-18 明确「先不着急，等大面积铺开使用之后再讨论」。
- **现状**：`/opt/yfe/data` 是全部云端用户数据的**唯一副本**，没有任何自动备份。
- **风险**：单盘故障 / 误删 / 勒索软件 = 所有打赏用户的稿子一起消失，且无法恢复。
- **启动条件**：正式对外发码、用户量上来之后。
- **候选方案**（届时选一个）：
  1. 每日 `tar czf` 打包到 `/opt/yfe/backups`，保留 7 份 + 每周 1 份共 4 周（本机双份，防误删不防盘坏）；
  2. 同上 + `rclone` 同步到主人自己的网盘（防盘坏，推荐）；
  3. 华为云 OBS 对象存储（防盘坏 + 异地，有少量费用）。
- **注意**：备份文件含用户明文稿件，落盘前应确认权限（`600`）与存放位置，不要放进 web 目录。

## WEB-02 多标签页 / 多设备并发覆盖（**部分完成**）

- **现象**：同一账号在两个标签页或两台设备同时编辑，后保存的会覆盖先保存的，**先写的内容静默丢失**。
- **根因**：前端是「整库读入内存 → 改动 → 全量写回」，没有任何版本号或冲突检测。
  桌面版靠单进程独占文件天然规避，网页版没有这层保护。
- **已完成（2026-10-18）· 同浏览器多标签页**：
  `src/lib/app/tabGuard.ts` 用 `BroadcastChannel` 探测第二个窗口，命中后在页面顶部浮一条提示
  「检测到另一个窗口也在用这个账号，同时编辑会互相覆盖」。
  设计取舍：**只提示、不拦写** —— 强行禁止会让「开两个窗口对照看」的正当用法没法用；
  实现上用原生 DOM 而非 React 组件（`App.tsx` 有四处 early-return 各自渲染横幅，逐个加容易漏），
  且非网页版第一行即返回，桌面 / 便携零影响。
- **仍未解决 · 跨设备 / 跨浏览器**：需要服务端 `revision` + `If-Match`，冲突时返回 409 并提示用户，
  要动前端整条保存链路。
- **优先级**：跨设备部分为中低（单人单设备不会触发）。

## WEB-04 存储改增量同步

- **现状**：整库 JSON 全量 `PUT`，800 ms 防抖。
- **影响**：稿子大（含备份载荷 / 向量）时每次保存都要上传整库，公网慢、浪费流量。
- **方案**：按 store 分片（`GET/PUT /api/store/:name`），前端只提交「脏 store 集合」；
  服务端按 store 落盘。这是当初评估过的最大一块改造。
- **优先级**：低（当前用户量下不明显）。真要做时注意：`portableStore` 的脏标记目前是整库级。

## WEB-08 会话过期后的体验（**高**） ✅ **已完成**（2026-10-18）

- **现象**：登录会话 30 天后失效。此时用户仍在编辑，下一次保存的 `PUT /api/data` 会拿到 **401**，
  而 `fileBackend` 只把它记进 `lastError`，界面显示「保存出错」——**不告诉用户要重新登录**。
  更糟的是这期间写的内容只存在于内存，用户以为存上了，实际一直没落盘。
- **修复**：`fileBackend` 识别 401 ⇒ 明确提示「登录已过期，请重新登录」并引导去 `/login`；
  或在服务端返回体里带 `code: 'SESSION_EXPIRED'` 让前端分流（与配额超限 413 同等对待）。
- **优先级**：高。第一个账号到期就会踩到，且现象像「数据丢了」。

- **实现**：fileBackend 识别 401：GET 401 ⇒ 直接回登录页（不锁写盘、不弹「数据读取失败」红条）；PUT 401 ⇒ 文案改为「登录已过期：未保存的改动有丢失风险，请立即重新登录」。服务端 401 统一带 code: SESSION_EXPIRED。

## WEB-10 服务存活监控（**中**） ✅ **已完成**（2026-10-18）

- **现状**：`yfe-web` 挂了没人知道（systemd 会重启，但反复挂就成黑洞）。服务器整体失联同样无人知。
- **目标**（二选一或都做）：
  1. 本机 crontab：每 5 分钟 `curl /api/ping`，连续 2 次失败记日志 + 重启服务；
  2. 外部免费监控（UptimeRobot 类）探测 `http://115.120.232.153/api/ping`，挂了发邮件。

- **实现**：server/scripts/healthcheck.sh + crontab */5；连续两次 ping 失败才重启（单次抖动不重启），重启后仍失败则打 journal 到日志等人看。

## WEB-13 磁盘用量监控（**中**） ✅ **已完成**（2026-10-18）

- **算术**：40 GB 系统盘，每人 200 MB ⇒ 约 180 个满配额用户就写满，且系统本身要占十几个 GB，
  实际警戒线更早。满了之后**所有用户都无法保存**，且 journald/临时文件也会开始报错。
- **目标**：crontab 每日记录 `df -h /` 与 `/opt/yfe/data` 体积；超过 70% 记警告日志，90% 通知主人。

- **实现**：server/scripts/diskcheck.sh + crontab 每日：记录磁盘用量/用户数据体积/账号数；≥70% 警告、≥90% 严重；日志自限 500 行。
