## WEB-02 多标签页 / 多设备并发覆盖 —— ✅ **已完成**（2026-10-18，单会话方案）

- **现象**：同一账号在两个标签页或两台设备同时编辑，后保存的会覆盖先保存的，**先写的内容静默丢失**。
- **根因**：前端是「整库读入内存 → 改动 → 全量写回」，没有任何版本号或冲突检测。  
  桌面版靠单进程独占文件天然规避，网页版没有这层保护。
- **最终方案（主人 2026-10-18 拍板）：不允许多端登录，从根上消除。**  
  原计划做的「服务端 revision + If-Match」需要动整条保存链路、且只能做到「冲突时提示」；  
  而这里真正要的只是「别两个人同时写」——**单会话更简单也更彻底**。
- **实现**：
  - 用户表增加 `session: { token, at }`，每次登录/注册都覆盖它 ⇒ 旧设备下一个请求即失效；
  - `authCheck()` 返回精确 reason（`NO_TOKEN` / `EXPIRED` / `NO_USER` / `REPLACED`），  
    401 的 `code` 取 `SESSION_EXPIRED` 或 `SESSION_REPLACED`；
  - 前端 `fileBackend` 据此说两句不同的话（「登录已过期」/「账号已在别处登录」）；
  - 登出（`/api/auth/logout` 与 `/logout`）都会抹掉活跃会话，退出即彻底失效。
- **同浏览器多标签页不受影响**（共用一个 Cookie，不会自己踢自己）—— 这条单独由  
  `lib/app/tabGuard.ts` 做提示。
- **实测**：设备 B 登录后，设备 A 的 `GET /api/auth/me` 与 `PUT /api/data` 均返回  
  401 + `SESSION_REPLACED`；设备 B 读写正常；退出后旧 Cookie 401。
- **取舍**：用户在两台设备间切换时必须重新登录（这是「单会话」的固有代价，换来的是永不丢稿）。

## WEB-04 存储改增量同步

- **现状**：整库 JSON 全量 `PUT`，800 ms 防抖。
- **影响**：稿子大（含备份载荷 / 向量）时每次保存都要上传整库，公网慢、浪费流量。
- **方案**：按 store 分片（`GET/PUT /api/store/:name`），前端只提交「脏 store 集合」；  
  服务端按 store 落盘。这是当初评估过的最大一块改造。
- **优先级**：低（当前用户量下不明显）。真要做时注意：`portableStore` 的脏标记目前是整库级。

## WEB-06 账号自救能力 —— ✅ **已完成**（2026-10-18，凭邀请码重置）

- **方案**：不引入邮件服务，用**注册时那张邀请码**当找回凭证（主人 2026-10-18 提出）。  
  理由：邀请码由站主亲手发放、与账号一对一绑定、8 位十六进制猜不动，对「打赏用户」这个量级零成本。
- **流程**：登录页「忘记密码？」→ `/reset` → 填**用户名 + 邀请码 + 新密码** → 重置成功。
- **实现**：
  - `users.resetPasswordByInvite(name, invite, hash)`：**用户名与邀请码必须同时匹配**，  
    两者任一不满足都返回同一句「用户名或邀请码不正确」（不透露哪个字段错，防用户名枚举）；
  - 重置后 `delete u.session` ⇒ **其他设备的登录全部退出**（来重置往往意味着怀疑账号被盗）；
  - 只改 `pwd` 一个字段 ⇒ **作品与设定零改动**；
  - 限流 5 次/10 分钟/IP（重置是暴力试邀请码的主要入口）；服务端记日志便于站主审计。
  - 已登录用户访问 `/reset` 直接回工作台（避免困惑分支）。
- **实测**：错误邀请码被拒、正确邀请码重置成功、旧密码失效、新密码可登、  
  **重置前写入的「我的小说」项目原样读回**、旧 Cookie 401。
- **遗留**：连邀请码也忘的用户只能联系站主人工核实（页面已写明这条路）。

## 备份档位调整（WEB-02 衍生，2026-10-18 已完成）

- **问题**：每份备份是**整包全量快照**。按桌面档位（自动 30 份 + 每日 30 份）算，  
  一个 100 万字项目（约 3 MB 文本）会占掉约 **180 MB**，而账号配额总共 200 MB  
  —— 用户自己的书只占 3 MB，其余全被备份历史吃掉。
- **调整（仅网页版，桌面 / 便携维持原档）**：
  - 自动备份间隔 5 分钟 → **15 分钟**（云端每份都是整库上传，5 分钟一次太浪费带宽与配额）；
  - 自动备份保留 30 份 → **10 份**；每日备份 30 份 → **7 份**（约 51 MB）。
- 实现：`db.maxAutoBackups()` / `db.maxDailyBackups()` 按平台取值；`sync/backup.ts` 的  
  定时器间隔同样按平台切换；备份界面文案与分组标题同步显示实际档位。

## WEB-08 会话过期后的体验（**高**） ✅ **已完成**（2026-10-18）

- **现象**：登录会话 30 天后失效。此时用户仍在编辑，下一次保存的 `PUT /api/data` 会拿到 **401**，  
  而 `fileBackend` 只把它记进 `lastError`，界面显示「保存出错」——**不告诉用户要重新登录**。  
  更糟的是这期间写的内容只存在于内存，用户以为存上了，实际一直没落盘。
- **修复**：`fileBackend` 识别 401 ⇒ 明确提示「登录已过期，请重新登录」并引导去 `/login`；  
  或在服务端返回体里带 `code: 'SESSION_EXPIRED'` 让前端分流（与配额超限 413 同等对待）。
- **优先级**：高。第一个账号到期就会踩到，且现象像「数据丢了」。
- **实现**：fileBackend 识别 401：GET 401 ⇒ 直接回登录页（不锁写盘、不弹「数据读取失败」红条）；PUT 401 ⇒ 文案改为「登录已过期：未保存的改动有丢失风险，请立即重新登录」。服务端 401 统一带 code: SESSION_EXPIRED。

## 网页版构建专项审计（2026-10-18，主人要求对 3.1.2 之后的网页版改动单独审一遍）

### 修掉的 5 处

| # | 问题                                                                                                         | 严重度  | 修法                                       |
| - | ---------------------------------------------------------------------------------------------------------- | ---- | ---------------------------------------- |
| 1 | **统计日志用 UTC 日期**：`toISOString().slice(0,10)` 与按本地日期取数的汇总脚本错配，**本地 0–8 点的活动永远汇总不进去**（静默丢数据）                 | 🔴 高 | 改 `todayLocal()` 取本地日期                   |
| 2 | **`PUT /api/data` 不校验 `kind`**：只查 `stores` 存在，畸形/截断的载荷会被当成合法数据写进用户库                                        | 🟡 中 | 补 `kind === 'portable-data'` 校验，与导入链路同口径 |
| 3 | **`/api/auth/me` 每次都 `usageOf()`**：递归遍历整个用户目录（data.json + 全部外置 blob），重度用户几千文件时是几百毫秒同步 IO，而页面加载 + 底部胶囊每次都要调 | 🟡 中 | 直接返回记录值（由 PUT / blob 写入时维护），取消遍历         |
| 4 | **写盘锁横幅在网页版说「便携数据文件」**，主操作是「复制数据文件路径」——云端没有本地路径可复制                                                         | 🟡 中 | WEB 分支改「云端数据」+ 主操作换「导出全部数据」              |

### 已知但**不修**（记录在案）

- **200 MB 整库读进内存**：`GET /api/data` 会把整库 JSON 读成 Node 字符串，峰值约等于库大小。  
  当前用户库远小于配额，1.7 G 内存可承受；真要修得上流式或分片（同 WEB-04）。

  跨设备已由单会话根治。
