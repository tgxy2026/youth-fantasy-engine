二、P0（新增 · 建议优先处理）

P0-1「切页签前落库」守卫是死代码 —— 未保存的表格 / 表单 / 角色卡改动静默丢弃

src/App.tsx:346,348,354 · src/components/TableSheet.tsx:206,279-290 · FormSheet.tsx:52-70 · CharacterSheet.tsx:83-107

触发：在任一表格 / 表单 / 角色卡页签里改了内容，不点保存直接点侧栏切到别的页签。

根因：这三个组件都写了「切页签前把上一页未保存草稿落库」的守卫，但 App 给它们加了 key={tab.id} —— 切页签时组件整体重挂，useRef 初值直接就是新的 tab.id，守卫条件永不成立。

// App.tsx:346 / 348 / 354
return <TableSheet key={tab.id} tab={tab} … />

// TableSheet.tsx:281-283（永不进入的分支）
const prevId = tabIdRef.current        // 重挂后 = 新 tab.id
if (prevId !== tab.id && …)            // 恒假

影响：内存态草稿随卸载消失，作者无从察觉（既无提示也无脏标记残留）。注释自己写着「之前会静默丢弃」，说明这个守卫就是为修它而加的 —— 但 key 把它废掉了。

🔬 验尸结论：成立（已核对 App.tsx 三处 key={tab.id} 与 TableSheet.tsx:206 的 useRef(tab.id)）。

建议：把冲刷放进卸载清理 useEffect(() => () => { if (dirtyRef.current) void save(dataRef.current) }, [])；或去掉 key 并保留 [tab.id] 分支。

P0-2transientUnavailable 是单向闩锁 —— 一次网络抖动后，编辑进本地、再被云端旧快照回滚

src/lib/syncCore.ts:429,485,527,574,591,716 · desktop.ts:427 · db.ts:466 · App.tsx:87

触发：任何一次同步 push 返回 status 0（网盘客户端正占用同步目录 / 目录暂不可写 —— 注释自认常见）。

根因：该标志置位后几乎没有自愈路径。置位点 3 处（:429 / :527 / :574），复位只有 2 处：:422（ensureInit 的 pull 成功分支）与 :699（configure()，即换目录 / 重开同步才会走）。而 ensureInit 被 initPromise 记忆化 —— 正常使用中永远不再执行；backgroundPull 又因该标志直接 return，于是它锁死了自己。

// syncCore.ts:485  拉取被自己挡住 → 无法靠成功 pull 自愈
if (!code || authFailed || transientUnavailable) return

// syncCore.ts:591  push 也放弃，只调 fallback
if (authFailed || transientUnavailable) { fallbackHandler?.(snapshotOf(cache)); return }

// syncCore.ts:716  包装层据此把读写全切到本地库
isCloudUnavailable: () => authFailed || transientUnavailable || Date.now() < rateLimitedUntil

影响链（静默数据回滚）：① 包装层把读写切到本地库（db.ts:466），此后编辑只进本地、不再进 cache；② 关窗 / 最小化触发的 unload flush 会调镜像，而 desktop.ts:427 的 bulkPut 是主键无条件覆盖、无新旧判定 → 用云端旧快照盖掉本地刚写的新记录；③ 紧接着 App.tsx:87 的 flushDesktopSync() 把它写盘。磁盘上不可逆丢失，切回前台还会看到界面「跳回旧版」。

🔬 验尸结论：主体成立，一处修正 —— 子代理称「唯一复位点在 :422」不准确，configure()（:699）也复位。但这不改变结论：正常轮询期间确实无自愈路径。

建议：① backgroundPull 在闩锁期仍周期性试拉一次（成功即复位）；② 镜像改为「只补本地缺失主键、绝不覆盖已存在主键」，或按 updatedAt 判新旧。

五、🔬 验尸修正（子代理报错、被判掉的部分）

四路子代理共 31 条，逐条回源码复核后修正 2 条。这一步不做，报告就会带着错结论进入修复轮：

降级「日记保留」的「天 / 条」不是 bug —— 语义等价

子代理原报：P1「一处说条、一处说天，用户会按天理解而实际是场」

验尸：日记是一天一条 —— daily.ts:77 提示词写「一天一条，最多 N 条」，summarize.ts:56 写「每条一行，格式 - MM-DD：一句话」。因此「保留 N 条」与「保留 N 天」等价，不存在行为偏差。

→ 降级为 P2「表述口径可统一」（统一成"条"更好读，但不影响行为）。若不复核，会白改一处并可能改错常量语义。

剔除TavernVarsPanel.tsx:96 的 Enter 未挡 IME —— 误报

子代理原报：P2「96 行与 121 行都未挡 isComposing」

验尸：96 行是数值输入（inputMode={isNumKind ? 'numeric' : undefined}，走数字键盘），不产生 IME composing 状态；121 行是文本备注框（placeholder 明写「模型会读取 / 改写」，可输中文）→ 只有 121 行成立。

→ 剔除 96 行，保留 121 行。

修正P0-2 的「唯一复位点」表述不准

验尸：子代理称 transientUnavailable 只有 :422 一个复位点；实测 configure()（:699）也复位。核心结论（正常轮询期间无自愈路径）不变，但修复方案要据此写准。
