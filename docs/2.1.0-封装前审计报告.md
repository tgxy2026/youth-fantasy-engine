## 三、存储 / 同步层深度审计

### ✅ P0-2 已修复（本次）

**位置**：`db.ts` 启动恢复云盘同步处

原实现 `applyDesktopCloudFromPersisted()` 返回 true 就直接把 `ops` 切到云盘存储，
**没有「云端是否真的有数据」的判定** —— 而显式开启那条路 `enableDesktopCloudSync` 是有守卫的。

**后果**：同步目录里的 `.yfe` 被删掉、或还没从网盘客户端下载完时，读到的 `rev=0` + 空 stores
被当成「空库」切过去 → 界面瞬间变成空项目 → 触发示范项目播种 → **反写覆盖云端快照**。

**修法**：切换前先 `pullDesktopSnapshot()`，空则保持本地存储；拉取失败同样不切。
与 `enableDesktopCloudSync` 的空快照守卫同构。提交 `8b24f1f`。

### 🔴 P0-1 未修复（历史遗留，需你决策）

**位置**：`db.ts:365-375`（`makeCloudStoreWrapper.cloudOrLocal`）+ `syncCore.ts:540-543`（`flushNow`）

**问题**：云盘同步开启期间（`ops = desktopCloudFileStore`）所有写入只落在云端实例的**内存 cache**；
推送失败时不回写本地数据文件，**关窗即丢稿**。

**证据**：

```ts
// db.ts —— 只有「操作前就已不可用」才落本地
if (isUnavailable()) return (local as any)[op](...args)
const r = await (cloud as any)[op](...args)
return isUnavailable() ? (local as any)[op](...args) : r   // ← 操作成功但之后不可用：不补写本地

// syncCore.ts —— 不可用时直接 return，无重试、无本地兜底
if (authFailed || transientUnavailable) return
```

`desktop.ts` 的 `flushDesktopSync()` 写的是 `desktopStore.data`，云模式下不含这批编辑 → 双向皆无。

**触发条件**：已开启云盘同步 → 断网 / 网盘客户端占用文件 / 目录不可写 → 用户最后一次编辑 → 关窗。

**为什么建议先不动**：修复要改 `syncCore` 的 flush 语义（推送失败时把 cache 镜像写入 local），
属**同步核心**改动，必须配双设备实测才能确认不引入新的合并问题。
在封装前动它，风险大于收益。

**建议**：列入下个迭代的第一项，或本轮封装后立即处理。
