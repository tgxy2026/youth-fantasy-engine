# 酒馆「上下文窗口长度」设置 · 核实报告（2026-10-07）

> 触发：主人实测「酒馆控制面板里的『上下文窗口长度』不会根据选定模型自动切换」。
> 结论：**现象成立**（有前置条件）；且**界面上那句文案承诺得比实现更宽**，这才是真正该修的点。

---

## 一、结论

| 问题 | 判定 |
|---|---|
| 「换模型时窗口不自动切换」 | ✅ **成立**：只在「模型配置里**手填过**该模型窗口」+「指纹变了（确实换了模型）」+「自动调整开关开着」三条同时满足时才跟随；缺任一条就纹丝不动 |
| 界面文案「换模型时会自动带过来」 | 🔴 **承诺过宽**（无条件的说法，实现是有条件的） ⇒ 这是**文案与实现不一致**，属本轮最该修的点 |
| 该设置本身是否有用 | ✅ 有 —— 本地模型下它是 `num_ctx`（**显存安全阀**），不能简单删掉 |

## 二、机制全貌（读源码所得，非推断）

### 2.1 存在**两份**手填的「窗口」

| 位置 | 字段 | 真实作用 |
|---|---|---|
| 模型配置页（模型设置 → 模型配置） | `provider.contextWindow` | **全项目真源**（2026-10-03 定案）。决定上下文预算、记忆档、系统提示词的窗口假设 |
| 酒馆控制面板 | `common.numCtx` | ① 本地时作为 `num_ctx` 发给 Ollama（`params.ts` 的 `toOllamaOptions`：`num_ctx: p.numCtx`）—— **显存占用由它决定**；② 本地时也参与预算推算 |

两者**语义高度重叠**，只是一份用于"发给模型"，一份用于"内部推算"。

### 2.2 跟随模型的那条链（有条件）

`modelCapacity.adviseCapacity()`（`modelCapacity.ts:398-432`）：
```
userWindow = windowSource === 'user' ? windowTokens : 0     // 只有**手填**才算
effectiveCtx = userWindow || current.numCtx                 // 手填 > 面板现值
numCtxFromUserWindow = userWindow > 0
```

写回只发生在（`tavern/settings.ts` 的 `syncTuningWithModel()`，以及
`useTavernControlModel.ts` 的 `onDefaultModelChange`）：

```
if (cap.numCtxFromUserWindow && rec.numCtx && rec.numCtx !== st.common.numCtx) {
  nextCommon.numCtx = rec.numCtx
}
```

⇒ **未在模型配置里手填** ⇒ `numCtxFromUserWindow = false` ⇒ **不写回，面板值永远不变**。

再加两道闸（`syncTuningWithModel` 的判定链，由 `shouldApplyTuning` 纯函数守）：
① `autoTuneByModel === false` 不动；② 指纹相同（**没换模型**）不动 —— 后者是"用户手调的值不被改回去"的保证。

⚠️ 还有一处容易踩：`syncTuningWithModel()` 取的模型是
`st.common.defaultProviderId || activeId`（**酒馆面板里指定的那个优先**），
不是"模型配置页的当前模型"。若酒馆单独指定了模型，两条链看的根本不是同一个对象。

### 2.3 界面上其实**没有**显示派生值

`TavernControlBasics.tsx:100` 那个框绑的是 `c.numCtx`（用户手填值），
**不是** `cap.windowTokens`（按模型算出来的值）。
所以即使模型配置已填 262144、`adviseCapacity` 也算对了，只要没人把值写回 `common.numCtx`，
**面板照旧显示旧数字** —— 这条与 2.2 叠加，就是主人看到的现象。

## 三、两处真正的问题

### 🔴 P1 · 文案承诺过宽（建议必改）

`TavernControlBasics.tsx:93-95` 本地分支写着：

> 「默认取「模型配置 → 上下文窗口」里填的值：那里填多少，这里就是多少（**换模型时会自动带过来**）。」

「换模型时会自动带过来」是**无条件语气**，而实现有 2.2 的三个前置条件。
未手填窗口的作者会被这句话误导，以为改模型配置就够了。

### 🔴 P2 · 同一概念两份手填值（建议按主人方向收敛）

主人给的判断是对的：**要么自动跟随，要么去掉、直接继承**。
两份手填值本身就让"哪个说了算"说不清。

## 四、方案对比

### 方案 A（不推荐）· 面板值无条件跟随所选模型

- 做法：换模型时一律把 `numCtx` 重算并写回。
- ❌ **本地会踩显存安全阀**：若"跟随"的是模型标称窗口（而非作者手填），256K 直接拉爆显存。
  项目里「本地绝不放宽」（`modelCapacity.ts:15`）这条原则是刻意留的。
- ❌ 还会冲掉作者刻意调小的值（面板手调的意义消失）。

### 方案 B（推荐）· 去掉手填入口，改为只读派生 + 未填时沿用旧值

1. **面板那个框改为只读展示**，值取 `cap.windowTokens`（已等于「手填 > 面板现值」，语义正确）；
   旁边给一句「来自『模型配置 → 上下文窗口』」＋「去填」的引导。
2. **数据层保留 `common.numCtx` 字段**，但**不再由面板直接编辑** ——
   - 模型配置**已填** ⇒ 由现有 `sync` 写回（行为与今天一致）；
   - 模型配置**未填** ⇒ 沿用 `common.numCtx` 的旧值（**老用户零回退**）。
3. **文案重写**：把"换模型时会自动带过来"改成条件明确的两句（见下）。

**为什么是这个方案**：
- ✅ 零迁移（不动老数据、不动 `params.ts`）、零行为回退（老用户照旧生效）；
- ✅ 消除"两份手填值谁说了算"的歧义，方向与 2026-10-03「模型配置窗口＝真源」的定案**一致**；
- ✅ 保住本地显存安全阀（未填时沿用旧值，而不是按标称放量）；
- ✅ 保留"想去更大窗口"的路径 —— 去模型配置填（那里本来就是必填项）。

**改哪个文件**：`TavernControlBasics.tsx`（UI + 文案）＋ `useTavernControlModel.ts` 的
`cap` 暴露（把 `windowTokens` 与 `windowSource` 传给面板）；`tavern/settings.ts` 与
`params.ts` **可不动**。

### 文案改写建议（本地分支）

> 窗口取「模型配置 → 上下文窗口」里填的值；**那里没填时，沿用这里上次的值（当前 X）**。
> 它决定本地模型一次能装多少内容，调大会同步抬高「上下文预算」，显存占用也跟着涨。
> 想去更大窗口 ⇒ 去「工作面板 → 模型设置 → 模型配置」把该模型的窗口填上。
