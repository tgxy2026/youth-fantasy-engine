# 3.3.2 · 阶段性审查（2026-10-30）

审查范围：本轮为 3.3.2 写的全部代码 —— P0 盘点结论、P1 认证与会话、P2 项目版本服务（存储/HTTP/快照/上传/应用/门禁/迁移）。
审查方式：逐模块读代码 + 用**真实旧数据形态**跑端到端（而不是只跑自己造的理想数据）+ 对每条断言问「它真的在验我想验的东西吗」。

结论：**发现 5 个问题，全部已修**；另有 4 条记录在案、未擅自改动。

## 一、已修问题

### S1（严重）旧令牌迁移用了占位哈希 ⇒ 升级后全员掉线

| 项 | 内容 |
|---|---|
| 现象 | 3.3.1 的登录态在新版服务端上会被判为无效，用户升级后集体被踢下线 |
| 根因 | `sessions.migrateLegacySession` 用 djb2 造了个 `stub_xxx` 当 `tokenHash`；而认证时算的是 **HMAC-SHA256(令牌, SECRET)** ⇒ 两边永远对不上 |
| 为什么没被测出来 | 当时的端到端是**手工塞了一条用真 HMAC 算的行**，绕过了迁移函数本身 —— 测试验的是我以为的路径，不是真实路径 |
| 修法 | 迁移只补空 `sessionList`，**保留旧 `session` 字段**；由 `users.checkSession` 在旧令牌第一次到来时「就地转正」：用调用方算好的真 HMAC 摘要建会话、删旧字段。删掉了整个 stub 哈希实现 |
| 证据 | 新增 `scripts/verify/legacy-token-332.mjs`（**9/9**）：真 `.secret` + 真 3 段令牌 + 真 users.json 旧形态 |

### S1b（严重，同一个 bug 的第二层）转正后会话被自己覆盖成空

修 S1 的过程中，端到端仍然失败：`/api/auth/me` 200 但设备列表里没有这台设备。
根因是 `checkSession` 里 `touch(list, …)` 用的是**转正前**的空数组，随后 `else` 分支把 `u.sessionList = list` 写回 —— 把刚转正的会话抹掉。
修法：引入 `cur` 跟踪当前会话表，转正后替换它，后续 touch/prune 都基于 `cur`。

> 这两个 bug 的教训是同一条：**用自己造的「理想输入」测，测不到升级路径**。

### S2（中）历史版本的「年龄」取自客户端字段

| 项 | 内容 |
|---|---|
| 现象 | `pruneRevisions` 按 manifest 里的 `createdAt` 判新旧 |
| 风险 | 那个字段是客户端填的。乱填一个很旧的时间就能让清理逻辑把**别人的历史**判成过期 |
| 修法 | `listRevisions` 的 `at` 改取**文件 mtime**（服务端事实），提交时的清理也据此判断 |

### S3（中）配额信任 manifest 声明的字节数

| 项 | 内容 |
|---|---|
| 现象 | 提交时按 `manifest.objects[].bytes` 求和判配额 |
| 风险 | 客户端谎报 `bytes: 1` 而实际传 40 MiB ⇒ 配额形同虚设（`stageObject` 只限单对象 64 MiB） |
| 修法 | 改为按磁盘真实大小 `statSync` 累加，同一哈希只算一次。**声明值只用于进度显示，不参与记账** |
| 证据 | `project-api-332` 第 10 条：真传 5 MiB（配额 4 MiB）、manifest 谎报 `bytes:1` ⇒ 必须 413 |

### S4（低）已删除的作品在列表里看不出已删

删除会写 `deletedAt` 到索引，但 `GET /api/v2/projects` 没把它返回 —— 客户端无法区分「云端有这本」和「云端只有一本墓碑」。
修法：列表项补 `deleted` / `deletedAt`。

### S5（低）静态 `/logout` 一次请求调用两次鉴权

`authCheck` 带 `touch` 副作用（可能落盘），调两次等于一次请求写两遍 `users.json`。改为只调一次。

## 二、记录在案、未修（都有明确理由）

| 编号 | 问题 | 为什么不现在修 |
|---|---|---|
| O1 | 对象库只增不减：历史清理只删 manifest，不删内容对象 | 内容寻址对象可能仍被其他版本引用；没有引用计数就删＝赌命。需要与配额计量一起做（P2-6） |
| O2 | `desktopAuth` 的一次性授权码存内存表 | 单进程部署下正确；**一旦上 cluster/PM2 多实例就会失效**（授权码可能落到另一个进程）。这条必须写进部署约束，而不是靠"应该没事" |
| O3 | 迁移脚本与客户端 `buildProjectSnapshot` 不是逐字节同源 | 排序规则若分歧，客户端首次提交会多一个 revision —— 不是数据错误。真正同源需要共享一份实现（跨 TS/DOM 与 Node 两种环境） |
| O4 | 回收站没有 UI 与过期清理任务 | 删除 30 天保留的数据结构已在，但「恢复」入口与「到期物理删」都属 P4/P6 |

## 四、给自己留的判据（下一轮审查照这个查）

1. **每条端到端都必须用「旧版本真实产物」当输入**，不能只用自己造的理想数据。S1 就是这么漏掉的。
2. **凡是客户端能填的字段，都不能直接当服务端的判定依据**（时间、字节数、数量）。S2/S3 同源。
3. **凡是「修完还失败」的，先怀疑自己的第二次改动引入了新错误**，而不是回头改测试。S1b 就是这样。
4. **测试断言要能失败**：写完先问「它在我把实现改错时会不会红」。
