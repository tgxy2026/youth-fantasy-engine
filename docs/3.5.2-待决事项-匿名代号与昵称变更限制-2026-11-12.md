### 2. 昵称冷却：可直接实施的规则

1. 服务端保存独立的 `nicknameChangedAt` 毫秒时间戳；首次成功设置和成功更换均写服务端当前时间。滚动期满条件为 `serverNow >= nicknameChangedAt + 7*24*60*60*1000`，与客户端时区无关。客户端收到 `serverNow`、`nicknameNextChangeAt` 后显示剩余时间，计时仅供提示；校时变化或进入页面时重新取服务端状态，不自行提前认定可修改。
2. 在同一个受保护的 profile 读改写操作内比较当前值、校验冷却并写入；现有 `mutate()` 是**单进程同步**读改写，不是跨进程 CAS，也不是数据库事务。上线假设为单实例和协作式备份锁；旧服务或绕过协议的并发写入不能由此保证，必须通过部署约束和隔离并发测试验证。
3. 先规范化并做格式校验，再比较与已保存值：相同昵称返回成功但不更新时间戳；不同昵称且未到期返回 `NICKNAME_COOLDOWN`、可读提示和剩余秒数，不写昵称、不重置冷却。校验失败、写盘失败、重复提交均不得消耗次数。其他展示设置不改 `nicknameChangedAt`。
4. 对升级前已有昵称而没有独立变更时间的账号，**无法从通用 `updatedAt` 可靠推算改名时刻**。迁移时标记“历史时间未知”，允许一次按当前规则修改，成功后进入冷却；未设置昵称的账号首次成功创建后立即进入冷却。开发验收时明示该兼容方案，禁止伪造历史修改时间。时间戳存在但格式损坏、处于不可解释的未来时，不能按“未知历史”放行，应提示并交运维修复。
5. 现有 profile PUT 允许昵称、排行授权等字段同包更新，而关闭排行会先写另一文件。冷却/格式失败必须在任何排行或展示设置副作用前完成；对混合请求和中途写盘失败明确全成功、拒绝或部分失败的响应，不声称现有 JSON 跨文件原子。至少验证失败后不会误删排行、清空输入或让客户端错误提示保存成功。
6. 审计记录只包含必要的动作、时间、内部操作者与结果，避免记录昵称正文或泄露到公开响应。改名会改变选择昵称展示的历史投稿、评论与排行，界面应事先说明；不能用 profile 的 `updatedAt` 显示为“昵称修改时间”。

### 3. 每周代号：时间、碰撞和历史稳定性

1. 代号以 `(账号, 内容归属周)` 计算，周以北京时间周一 00:00 开始；同账号同归属周在投稿、评论、排行使用相同映射，排行归属周按第 1 节已确认的榜单区间开始日期计算。展示为 `代号（匿名用户）`，昵称模式不附代号；示例帖使用固定的示例标识，不与真人占用名额。
2. **不能用当前已发布版本的 `v.createdAt` 直接充当帖子永久归属周**：当前代码在编辑时新建版本，审核通过后 `publishedVersionId` 指向新版本；跨周编辑会改变版本时间，导致旧帖代号变化。为投稿持久化一次性 `anonWeekKey`，从帖子原始 `post.createdAt` 计算并冻结；评论按 `comment.createdAt` 冻结或可验证派生。待审、申诉、下架再恢复、重新发布、展示方式切换和跨周编辑均不得重置归属周。旧记录采用原始创建时间迁移；缺失/非法/未来时间不得静默用当前周替代，应先隔离报告并人工处理。
3. “按各内容创建周”意味着**同一讨论串跨周时，同一人的旧帖和新评论可以使用不同代号**；原文“讨论串内始终一致”不成立。`byAuthor` 仍会提示评论者是作者，因此会形成跨周关联。界面应说明“每个内容沿用所属周代号，跨周可能不同”，不能保证同一讨论串永远一致。
4. 同周不同账号不能仅靠 `HMAC % 1672` 保证不同；应对 `(weekKey, uid)` 的分配结果做持久化，映射和周内占用约束同一次提交。固定序号需从 `-02` 开始，**两位是最小显示宽度而非上限**，超过 99 时扩展位数并设置明确容量上限/耗尽错误；无论碰撞或容量不足，不能静默复用他人代号。分配顺序、重复请求、故障重试和单实例并发应保持幂等；不能把这种机制描述为跨进程强事务。
5. 旧公开内容和排行榜不能依赖访客 GET 首次访问顺序分配，否则读操作会写盘、不同访问顺序可能改变名字，并与停写备份冲突。发布前在隔离环境对现有记录按稳定次序建立映射、核对后停写迁移；新内容在经鉴权的业务写入/发布流程中分配，**先确认映射持久化成功再公开内容**，失败时不公开；映射成功、业务写入失败可能留下未使用映射，重试复用并保留，不能当作跨文件原子提交。匿名名称解析相关的公开读取只查询映射，不因分配代号而新增写盘。排行历史区间按已确认的榜单开始周口径生成，预分配范围在开发设计中明确；缺失映射应返回明确的受控错误或暂停该功能，不默默生成不稳定名字。
6. 按周占用表不能只保留最近 N 周而同时承诺历史帖子代号稳定：仍被历史内容、历史排行或恢复快照引用的映射及其版本必须保留。只有有证据确认已无引用且不再需要恢复的条目才可按明确的保留策略处理；不得自动清理未知引用。预估词表/映射增长，避免无限增长和全表重写，达到阈值时告警，不主动删除用户内容。
7. `anonHandles.json` 如作为新核心文件，须同步 `communityStore`、备份固定清单 `COMMUNITY_FILES`、清单版本/校验、旧备份兼容、恢复差异、锁、异常中断与回滚。映射关系属于敏感数据，不可进入公开 API、日志或前端；原有的备份工具**不会自动包含**新增文件，必须真实验证。
8. 使用独立密钥的 HMAC 可降低从公开代号直接推算账号的风险，但**不能保证不可逆、唯一或匿名性**；不得复用会话签名密钥。密钥由运维单独管理并加密备份，密钥与社区备份独立保管，同时在恢复演练中验证两者匹配；丢失、轮换、跨环境/回滚时不得悄然生成不同代号。词表版本和映射版本冻结并随备份记录，不得把密钥明文写进仓库、清单或日志。

### 4. 隐私和用户可见说明

- 代号是公开的**周内可关联展示名**，不输出 uid、登录名、密钥或内部映射；跨周更换只能降低直接关联，**不保证跨周无法关联或身份无法推断**。正文、同一讨论串中的“作者”标记、昵称、排行数值/时间、截图和公开历史都可能建立关联；跨周碰撞也可能偶然出现相同代号。
- 月榜跨多个自然周，采用区间开始周后，榜单可能与当前周的帖子显示不同代号；不同榜单切换、旧内容新增代号、改昵称影响旧内容等均需在设置、手册和更新说明如实解释。不能用“完全匿名”“跨周自然断开”作保证。
- `commentDisplay` 当前未单独传给 `FeedPanel`，实现时应补齐并覆盖切换设置、旧数据默认值和提交展示，避免用户选择匿名而沿用另一开关的结果。

### 5. 备份恢复、上线顺序与验收

- 恢复差异应覆盖昵称及其冷却时间、周映射、词表/密钥版本；映射缺失、损坏或版本不匹配时默认拒绝上线/恢复，避免把缺失当空表重新分配。对“保留现有冷却”与“恢复备份昵称”可能冲突，不能简单取最大时间戳后宣称安全：先预览差异、保留恢复前副本；需明确审批恢复时间点及昵称/冷却策略，必要时人工核对。已删除、下架、撤回内容仍遵守当前默认拒绝可见性变化的恢复规则。
- 推荐顺序：固定词表来源 → 本机合成数据验证 → 停写迁移/回滚演练并生成备份 → 服务端与网页一起发布 → 新旧客户端及缓存验证 → 持续观察。现有 `X-YFE-Account-Context` 只保护发送该头的新网页配合新服务端，旧客户端/旧服务不受保护，不能误认为冷却或身份保护已覆盖所有混用版本。
- 必测：首次/历史昵称、相同昵称、7×24 小时边界、非法/未来时间、并发与写盘失败、混合 profile 请求；同周碰撞及超过 99 个同名、映射成功而内容写入失败后的重试、重启与备份恢复、旧记录缺失时间、周日跨周、跨周编辑/审核/撤回再发布、同串跨周评论、排行三周期、示例帖、昵称伪装及 Unicode 变体、词表/密钥版本变化和丢失、权限与公开数据不含 uid/映射、网页/桌面/旧版混用、窄屏及匿名代号解析的公开读接口不新增写盘。当前首次 `GET /profile` 会初始化档案，不能把现状误写成“所有 GET 都不写盘”。故障演练只用隔离数据，性能与真实设备分别记录，不以单次脚本通过代替完整验收。

## 一、社区昵称：按钮语义 + 每 7 天只能改一次

### 主人原话要点

1. **没创建过昵称时**：这里显示「保存」按钮（现状如此，没问题）。
2. **已经保存过昵称、后续想改**：按钮变成「**修改**」，点它去更新社区昵称。
3. **更新有限制：每 7 天只允许变更一次。**
4. ✅ **首次创建也计入冷却**（D1）；✅ **界面要有冷却期提示**（D2）。

### 当前代码事实（只读取证，未改动）

| 位置 | 现状 |
|---|---|
| `src/components/community/SettingsPanel.tsx` | 昵称区永远渲染一个「保存」按钮 → `saveNickname()`；`profile.nickname` 为空表示从未创建；提示语只写「昵称与登录名完全分离，匿名展示时不会输出登录名」，**没有冷却期说明** |
| `server/lib/communityApi.mjs` · `PUT /api/community/profile` | 只要带 `nickname` 就 `validateNickname()` 后写入，**没有任何时间/冷却校验** |
| `server/lib/communityRules.mjs` · `validateNickname()` | 只校验长度（1–16）、不可见字符、保留名「匿名用户」、官方/管理身份字样 |

### 仍待决（不影响开工，但实现前最好问一句）

1. **冷却的计时口径**：自然日（北京时间 00:00 分界）还是滚动 7×24 小时；项目里 `todayKeyCn()` / `periodRange()` 已有中国日口径可复用。
2. **超限的表现**：按钮置灰＋倒计时提示，还是仍可点、由服务端返回明确错误码；提示要不要显示「还剩 X 天」。
3. **冷却期提示放哪**：输入框 hint、按钮下方、还是「保存/修改」按钮旁的说明块（D2 只说「相应位置」，未指定）。
4. **管理员是否可豁免**（改名涉及冒名/投诉处理时），以及是否留审计日志。
5. 「修改」按钮的交互形态：直接沿用现有输入框就地改，还是点「修改」后才进入可编辑态（未创建时仍是「保存」）。
6. 「提交相同昵称」算不算消耗一次变更额度。

### 技术注意点（可可补充，非主人要求）

- 7 天限制**必须落在服务端**（`PUT /api/community/profile`），项目红线一贯是「前端隐藏按钮不算权限控制」；只在前端置灰可被绕过。D2 的提示文案只是告知，不能当控制手段。
- 需要新增独立字段如 `nicknameChangedAt`（**首建与修改都写**，对应 D1），**不能复用 `updatedAt`** —— 改一次排行开关就会把它刷掉，导致冷却被绕过。

- 昵称是动态解析的，加冷却能顺带减少「旧内容展示名整体漂移」的频率；但如果要求历史内容锁定旧昵称，就得改成快照存储，属于另一档设计，不在本次想法里。

## 三、匿名代号库选型建议（可可的建议，供参考，**不是定案**）

### 选型原则（比具体词表更重要）

1. **中性、无身份暗示**：不指向性别 / 年龄 / 地域 / 职业 / 身份等级，避免读者把代号当成真人特征往上投射。
2. **无等级与稀缺感**：不要「至尊 / 黄金 / 稀有」这类词，否则代号变成攀比，或让人觉得被系统评了级。
3. **无时效性**：不用当下网络热词、流行角色名、梗 —— 两年后尴尬，还有版权与粉圈风险。
4. **不撞真人名 / 作品名 / 品牌**，词表可人工审校一遍。
5. **容量可扩展**：组合式或可叠序号，避免几百个账号就开始碰撞。
6. **字数固定、中文优先（2–4 字）**：窄屏列表、评论行、排行栏都放得下。
7. **可版本化**：换词表时老用户代号不能变，否则「按账号固定 / 允许关联」的承诺会被打断。
8. **一眼能和「昵称」区分**：固定格式 + 「（匿名用户）」后缀，避免用户以为是自己设的。

### 候选方案对比

| 方案 | 示例 | 优点 | 风险 |
|---|---|---|---|
| A 自然意象单词 | 晚风 / 青苔 / 薄雾 / 槐序 | 贴合小说社区气质、亲切、好读 | 词表容量小（几百），早期就碰撞；部分词带情绪色彩 |
| **B 双词组合（状态/颜色 + 中性物）** | 静水·青砚 / 晚灯·北窗 / 远山·素笺 | **容量大**（60–80 × 60–80 ≈ 数千组合），碰撞低；中性无身份指向；文艺但不指人 | 要维护两张小词表、风格需统一审校 |
| C 中性序号 | 匿名作者 #0142 | 零联想、无限扩展、最中性、最易实现 | 冷冰冰像工号，「区分谁是谁」的亲切感弱 |
| D 星象 / 节气 | 观星者·霜降 / 廿四·惊蛰 | 有文化感、稳定 | 24 / 28 个太少，必须叠序号；部分带季节联想 |
| E 笔墨 / 书页意象 | 未命名的稿纸 / 第 37 页 | 贴合写作主题 | 偏长，容易和作品标题混淆 |

### 我的推荐：**B 为主 + C 做兜底**

> 形如 `静水·青砚（匿名用户）`；万一组合撞了，加一个短序号 `静水·青砚-07（匿名用户）`。

理由：

- 两张 60–80 词的小表就能给出数千组合，再叠序号近乎无限，**比单表方案更晚才会碰撞**；
- 组合词中性、无等级、无时效，也不会撞真人名/品牌；
- 比纯序号有人味、比水果/动物更有「小说创作社区」的调性，且不会萌化或性别化；
- 词表可以版本化冻结：`v1` 表只服务已分配的账号，将来加词走 `v2` 新账号，**老用户代号永不变**；
- 生成接口（D5）可以先只实现「从词表按 uid 稳定取组合」这一步，词表内容后填，完全不阻塞其它开发。

### 明确不建议

- **水果 / 食物**（主人的举例只是示意）：词表小、容易撞用户自己起的昵称、带可爱/性别化联想。
- **动物**：容易萌化，且部分动物已有网络梗含义。
- **网络热梗 / 影视角色名**：时效性、版权、粉圈争议。
- **带评价或等级色彩**的词，以及任何像「官方 / 管理员」的词。

### 生成接口怎么预留（D5 的工程要点，不代表已开工）

- 服务端单一纯函数 `anonHandleOf(uid, salt, dictVersion) → string`；**前端只拿 `displayName` 字符串**，不参与生成、不拿词表。
- **不可逆**：`HMAC(uid, 服务端盐)` → 取模映射到词表；盐只放服务端配置，绝不下发（允许关联 ≠ 允许反推 uid）。
- **稳定**：盐 + 词表都带版本号；换盐/换表前必须冻结旧映射或迁移，否则老账号代号全变。
- **碰撞**：要么允许多账号同代号并加短序号，要么维护 `uid → handle` 映射表（更稳，但要随账号一起备份）。
- **防冒充**：`validateNickname()` 里禁止匹配代号格式，沿用现有禁止「匿名用户」的做法。
- **三处共用**：投稿 / 评论 / 排行都走 `displayNameOf()`，改一处即可全量生效。
- **旧内容**：动态解析 ⇒ 上线即生效，旧投稿会突然多出代号，需在 3.5.2 更新说明里说明。

### 每周轮换的工程要点与关键分歧（D9，未开发）

- 周标识必须**服务端统一计算**（ISO 周或项目已有的中国周口径），绝不能按客户端本地时钟 —— 否则同一用户在不同设备/时区看到不同代号，讨论就乱了。
- 派生方式建议 `HMAC(uid + weekKey, 服务端盐) % 词表长度`：**允许周内关联，但不允许从代号反推 uid**；盐与词表都带版本号，换盐/加词前要冻结旧映射或迁移。
- 🔴 **最关键的一个分歧（14:56 已定案：取 B，见第七节）**：代号到底按哪个周算？
  - **A 按当前周显示**：所有历史内容每周一起换 → 上周的帖子本周再看，作者代号变了，**同一条讨论串前后会不一致**。
  - **B 按内容创建周固定**：老帖子保留它创建那周的代号，同一作者跨周投稿会显示不同代号 → **讨论串内始终一致，跨周自然断开关联**，正好是 D9 想要的「避免完全绑定」。
  - **可可推荐 B**：它同时满足了「区分谁是谁」和「不完全绑定」，且不会把已有讨论搅乱。但主人原话「每周刷新一次」也可能指 A，故不擅自定，列为开工前必问项。
- 其它待决：周切换瞬间正在阅读/评论的用户看到代号变化要不要提示；周口径用自然周（周一 00:00）还是滚动 7 天；昵称若与异兽名撞车（比如用户叫「麒麟」）是否需要在 `validateNickname()` 里排除词表 —— 目前代号带「（匿名用户）」后缀，视觉上已能区分，倾向不禁止，待定。
- 旧内容兼容：`displayName` 是动态解析的，上线后旧投稿/评论会突然多出代号；若选 B，旧内容按其创建周补一个周标识即可，需要在 3.5.2 更新说明里写明「匿名代号每周轮换」。

### D10 冷却期提示要写清什么（供 UI 文案参考）

不只是挂一句「有冷却期」，建议把三件事说透：① **首次创建后 7 天内不能修改**（D1 的直接后果，刚建完打错字也得等）；② 每次改名后 **7 天内不能再改**；③ 当前是否可改、以及**还剩几天**。服务端仍是唯一裁判，前端文案只做告知。
