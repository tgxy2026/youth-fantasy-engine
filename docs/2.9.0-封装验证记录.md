## 二、🔴 本轮发现并修复的阻塞性问题：builder 26 的「解包改名」EPERM

### 2.1 现象

第一批把 `electron-builder` 升到 **26.15.3** 后，封装在解包 Electron 这一步**必然失败**：

```
⨯ EPERM: operation not permitted,
  rename '…\desktop-out-2.9.0-*\win-unpacked.tmp' -> '…\desktop-out-2.9.0-*\win-unpacked'
    at extractArchive (app-builder-lib/…/util/electronGet.js:249)
```

连跑两次**完全一致**（不是间歇性），重跑无效。

### 2.2 根因（独立探针实证，非推测）

写探针直接调 `app-builder-lib` 的 `extractArchive(zip, target)`：

```
RESULT: 失败 -> EPERM
=> 同进程延迟 5s 后改名【成功】 ⇒ 是【外部瞬时占用】（安全软件扫描）
```

⇒ **解包本身是成功的，只有紧跟其后的 `fs.rename(tmpDir, dir)` 失败**；同一进程隔 5 秒再改名就成功
⇒ 是**外部瞬时句柄占用**（实时防护扫描刚写出的 ~200MB 新文件），**不是权限问题、也不是句柄未释放**。

🔴 **为什么旧版（builder 24.13.3）不撞**：24 的 `extractArchive` 是**直接解到目标目录**；
26 新引入「锁 + 解到 `.tmp` + `rm` 目标 + `rename`」的并发安全写法（源码注释：
"rm + mkdir happen AFTER acquiring the lock so no concurrent caller can clear our tmpDir mid-extraction"），
正好撞上本机那个扫描窗口。

### 2.3 修复：改用 `electronDist` 指向「**已解包**的 Electron 目录」

读 `app-builder-lib/out/electron/ElectronFramework.js` 的 `unpack()` 可知，`electronDist` 有三条分支：

| electronDist 指向 | 行为 | 是否撞 EPERM |
|---|---|---|
| `.zip` 文件 | `extractArchive` | ❌ 撞 |
| **含 zip 的目录** | `extractArchive` | ❌ 撞 |
| **不含 zip 的目录** | `emptyDir` + **`copyDir`** | ✅ **不撞**（无 rename） |

⇒ `scripts/build-desktop.mjs` 新增 `ensureUnpackedElectronDist()`：
把 `node_modules/electron/dist`（本身就是已解包的 Electron，73 个文件、无 zip 混入）
逐文件复制到 `release/eb-cache/electron-unpacked/electron-v<版本>-win32-x64/`，
再以 `-c.electronDist=<该目录>` 传给 electron-builder。

**为什么要剔两个文件**：自定义 `electronDist` 时 `cleanupAfterUnpack(..., isFullCleanup=false)`
**不会**替咱删 `resources/default_app.asar` 与 `version`（默认流程会删）⇒ 缓存里预先删掉，
产物才与既有发布版逐项一致。（`LICENSE → LICENSE.electron.txt` 的改名两种情况都做，无需处理。）

**缓存键**：目录名带版本号 + `stamp-<版本>.txt`，换 Electron 版本即换目录，**不会陈旧**。

### 2.4 连带踩到的坑：`fs.cpSync` 在本机被 shim 掐断

第一版修复用 `fs.cpSync` 复制 200MB ⇒ 脚本在打印 `[3/3] …` 之后**零输出直接退出码 127**。
探针定位：日志停在 `3 cpSync begin`，无任何异常 ⇒ **cpSync 被本机 shim 拦下并静默杀进程**。
⇒ 改为自写的 `copyDirDeep()`（`readdirSync` + `copyFileSync` 递归，`copyFileSync` 在脚本里已被验证可用）。

### 2.5 修复后完整流程（三步，与 skill 记录一致）

| 步 | 动作 | 结果 |
|---|---|---|
| ① | `node scripts/build-desktop.mjs` | 出 `win-unpacked` + 首次 NSIS；主 exe 元数据缺失 ⇒ **设计性退出码 2** |

## 三、⚠️ 验证环境的两条注意（与产品无关，但会误导判断）

### 3.1 `ELECTRON_RUN_AS_NODE=1` 被注入

本代理环境的 shell 里带着 `ELECTRON_RUN_AS_NODE=1` ⇒ **任何 Electron 启动都会退化成纯 Node**，表现为：

- 开发版 `electron .` → `TypeError: Cannot read properties of undefined (reading 'whenReady')`
- 封装版带参数启动 → **`<exe路径>: bad option: --smoke-test`**（👈 这其实是 **Node** 在拒绝未知参数，不是应用报的）
- 进程起得来但**没有窗口、没有 GPU/渲染子进程、userData 不被写入**

**解法**：启动时剥掉它 —— `env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS <exe> …`。

### 3.2 代理进程上下文里 Chromium 沙箱起不来

剥掉上一条后 Electron 真正启动，但 GPU 进程立刻崩：

```
ERROR:gpu_process_host.cc(1002) GPU process exited unexpectedly: exit_code=-1073741819  (0xC0000005)
FATAL:gpu_data_manager_impl_private.cc(449) GPU process isn't usable. Goodbye.
```

**解法**：`--no-sandbox` 即可跑通（随后 `SMOKE_OK` + 窗口正常）。
这是**代理进程上下文**的限制，主人哥哥双击运行时是正常交互会话，不受影响。
