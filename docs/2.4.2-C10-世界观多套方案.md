# 2.4.2 · C10 世界观 · 力量体系「多套卡片化」方案

> 状态：**待主人哥哥拍板**（第四节的四个问题定了才开工）。
> 规划原文见 `docs/2.4.0-版本规划.md` §四 C10；本方案基于**源码实测**，与规划有出入处已标注。

---

## 一、一句话结论

**把「世界设定」「力量体系」从 `type: 'form'`（单表单，一份数据）改成 `type: 'card'`（多条记录）——
一张卡就是一套，卡名即套名。**

这么做有三个硬理由（都是查源码查出来的，不是设计偏好）：

1. **UI 层几乎免费**：`App.tsx` 对 `type: 'card'` 的分发是 `group === '大纲规划' ? OutlineSheet : CharacterSheet`。
   这两张表在 `开书定位` 组 ⇒ 自动走 `CharacterSheet`；而 `CharacterSheet` **已经**做过单位名词参数化
   （`const noun = isCharTab ? '角色' : '设定'`，`isCharTab = tab.group === '角色管理'`），
   所以「新建角色 / 删除角色卡」这类错话不会出现 —— 2.3.0 加「其他设定」时已经踩过并修好了。
2. **落库逻辑已经按 type 分发**：`lib/flow/commit.ts`（AI 整理 / 拆书草稿写入）有完整三分支
   `form / card / table`，`aiContext.sectionOf` 同样三分支。改 type ⇒ 这些路径**自动**改走卡片分支。
3. **有现成先例**：「其他设定」(`misc-settings`) 2026-09-20 就是从表格改成卡片型的，
   迁移函数 `migrateMiscSettingsToCards` 可以逐行照抄（复用原 id ⇒ 幂等）。

**顺带捡一个收益**：酒馆推演报告的 `TARGETABLE` 白名单（`lib/tavern/report.ts:27`）曾经把这两张表列进去，
审计 P1-5 又摘掉了，原因是——

> 它们是 `type: 'form'` 的**单表单**页签，压根没有「哪一条记录」的概念。模型指对了也只会切个页签、
> 指不到任何东西，等于给作者一个点过去发现没反应的链接。

改 card 后这个理由消失，两张表可以加回白名单，酒馆诊断里「问题出在世界设定 / 力量体系」就能**点过去定位到那一套**。

## 三、核心设计

### 3.1 数据模型：一张卡 = 一套

```
cardRecords（已有 store，不动结构）
  ├─ { tabId:'worldbase', name:'苍澜大陆',        data:{'一、世界总览::世界名称':'苍澜大陆', …}, order:0 }
  ├─ { tabId:'worldbase', name:'主神空间',        data:{…}, order:1 }
  ├─ { tabId:'power',     name:'玄脉体系',        data:{…}, order:0 }
  └─ { tabId:'power',     name:'异火阶序',        data:{…}, order:1 }
```

- **卡名 = 套名**（作者自己起，如「苍澜大陆」/「主神空间」/「现实世界线」）
- 老库那一份 formData ⇒ 迁成**第一张卡**，卡名取 `世界名称` / `体系名称` 字段值（空则「默认」）
- 「套」之间**完全独立**（各自一套完整字段），不需要「继承 / 覆盖」这种复杂关系 —— 无限流每卷一个世界，
  本来就该各写各的

### 3.2 「当前套」＝ AI 的收敛锚点（🔴 老大点名的风险点）

规划原文：

> 🔴 **产品风险（老大点名）**：套数一多，设定之间容易互相冲突，**会让 AI 判断混乱** ——
> 必须在 UI 上**显式提醒用户**，并考虑「AI 上下文里同时只喂当前章所属的那一套」这类收敛策略

本方案的落地：

**① 记一个「当前套」**（每张表各一个）：
- 存 `settingsKV`，key = `worldActiveSet::${projectId}::${tabId}`，值 = 卡的 id
- 选 `settingsKV` 而不是 `meta`：它在同步清单里（跨设备一致，「我在写第三卷」这件事不该换台机器就丢）
- 卡被删 / 找不到 ⇒ 回退到第一张卡（不报错、不空白）

**② AI 上下文只喂当前套**：
`aiContext.sectionOf` 对**多套表**取当前套那一张再渲染，段首加一行标注：
```
【世界设定】（当前使用：苍澜大陆；本项目另有 2 套，未发送）
```
> ⚠️ 明确写出「另有 N 套未发送」，别让作者以为 AI 读过全部 —— 这与既有的
> 「按预算裁剪并注明被略过」是同一个诚实口径（`BY_BUDGET`）。

**③ UI 显式提醒**（规划要求）：
- 该表 **≥2 套**时，页签顶部显示黄条：「本项目有 N 套世界设定，AI 只会读**当前**这一套（苍澜大陆）。
  写别的世界线时记得切换。」
- 条数 > 2 时文案升级（「套数越多，越容易写串」）—— 这是**提醒**不是限制，不阻止作者建第 4 套
- 「当前套」切换器放在 `CharacterSheet` 顶栏（与「隐藏已退场」同排），标签写「AI 使用中」而不是「当前选中」，
  点明它影响的是 AI 读什么，而不只是界面高亮

**④ 写入也锚在当前套**（🔴 容易漏的一处）：
`flow/commit.ts` 的卡片分支现在是「按名字**全表**查 ⇒ 未命中新建卡」。多套之后必须改成
**只在当前套内查找 + 新建也落到当前套**；否则 AI 整理一次设定就会凭空多出「第三套」，
而作者完全看不出来（新卡排在列表末尾，且名字可能只差一个字）。

### 3.3 🔴 补充排查：四个「不看源码根本想不到」的连锁点

`type` 一改，下面这几处**不会报错、只会静默变样**。这是本方案里最需要注意的部分。

#### ① 「全书级设定汇总」会整条链路失明（= 功能回归）
`lib/flow/formMap.ts` 的四个函数全部以 `type === 'form'` 为判据，而它服务的是
**拆书 / 创意写作流程末尾的「汇总全书级设定」**（`lib/aiTasks/formSummary.ts` + `lib/bookbreak/run.ts`）：

| 函数 | 改动后会怎样 |
|---|---|
| `summaryFormTabs()` | 返回的表清单里**不再有** `worldbase` / `power` |
| `formFieldSpecs()` | `if (tab?.type !== 'form') continue` ⇒ 这两张表一个字段都取不到 |
| `formFieldsPrompt()` | 给模型的字段清单少了这两张表 ⇒ 模型**不会填**它们 |
| `formFieldNames()` | `if (tab?.type !== 'form') return out` ⇒ **返回空集** |

**表现**：拆完一本书，作者发现作品定位、全书总纲、写作规范都填好了，**世界设定与力量体系却是空的** ——
而且不报任何错。单测也未必抓得到（它测的是函数逻辑，不是「清单里有没有这两张表」）。

**对策**：把判据从「type 是 form」放宽成「**有 modules 的页签**」——
```
isFormLikeTab(tab) = (tab.type === 'form' || tab.type === 'card') && tab.modules?.length
```
多套表在多一条通道里按**当前套**处理（见 ②）。

#### ② AI 汇总会把世界设定「每次新建一张卡」（必然发生的静默 bug）
`formDraftRows` 生成的草稿行 `name = tab.name`（就是「世界设定」三个字），而 `commit.ts` 的卡片分支是
**按 `row.name` 在全表查卡 ⇒ 查不到就新建**。

作者的卡叫「苍澜大陆」⇒ 查「世界设定」查不到 ⇒ **新建一张名为「世界设定」的卡**。
汇总跑几次就多几张，且新卡排在列表末尾 —— **作者完全看不出它是哪来的**。

**对策**（推荐第一种）：
- **A（推荐）**：`commit.ts` 对多套表**特判** —— 直接写回「当前套」那张卡的 `data`，不参与「按名查卡 / 新建」。
  内聚在 commit 一处，不动调用方签名。
- B：让 `formDraftRows` 把 `name` 填成当前套的卡名 ⇒ 能走既有的「命中则更新」分支；
  但 `formDraftRows` 是同步函数，要 async 化并牵动 `formSummary.ts` / `bookbreak/run.ts` 两个调用方。

#### ③ 设定集导出的字段会丢模块分组（可接受的演进，但要写明）
| | form 分支（现在） | card 分支（改后） |
|---|---|---|
| 结构 | `## 表名` → `### 模块名` → `- **字段名**：值` | `## 表名` → `### 卡名` → `- **字段名**：值` |
| 字段顺序 | **schema 顺序** | data 的键序 |
| 模块名 | 有 | **丢** |

多套必须有「套名」这一层，所以结构演进是对的；但**丢模块分组**会让设定集变难读
（世界设定有 6 个模块，扁平后 29 个字段连成一片）。
**建议顺手优化**：card 导出时若该页签有 `modules`，仍按 schema 顺序输出并在字段名前带上模块名
（`- **一、世界总览 · 世界名称**：…`），改动很小但可读性差别很大。⚠️ 改完要跑既有导出测试确认不红。

#### ④ 全文检索：**顺带**能补一个能力（不是回归）
`SettingSearch` 的卡片白名单是 `角色管理 / 世界构建 / 创作管理`，而原注释已写明
「表单型：每个已填字段一条（**不进入本检索**）」⇒ 这两张表**现在本来就搜不到**，
所以不改也不会变差。但改 card 后只要把 `开书定位` 加进白名单，作者就能「搜一个设定名 → 直接打开那一套」，
**属于顺手捡到的能力**（与 §一 的酒馆白名单是同一类收益）。

### 3.4 分期

| 期 | 内容 | 说明 |
|---|---|---|
| **第一期（本次）** | 卡片化 + 多套 + 当前套 + AI 只喂当前套 + 黄条提醒 + 迁移 | 解决「一个项目只能建一套」这个原始需求 |
| 第二期（可选，暂不做） | 卷/章 → 套的归属映射（AI 按当前章自动选套）；「跨套通用设定」层 | 归属映射要新增数据模型 + 一大套 UI，工量与收益不成比例；先看第一期实际用起来缺不缺 |

## 五、逐文件改动清单（第一期）

### A. schema（`src/lib/schema.ts`）

| 位置 | 改动 |
|---|---|
| `:175` | `worldbase`：`type: 'form'` → `'card'`；`description` 补一句「一张卡＝一套，可建多套」 |
| `:223` | `power`：同上 |
| 两表 `tips` | 各加一条：「📌 本项目可以建多套（无限流 / 同人文）。**AI 只会读当前那一套**，写别的世界线时记得切换。」 |

> ⚠️ `modules` / `fields` **一个字都不动** —— 字段键 `模块::字段` 在两种类型下通用（见现状核查 #5）。

### B. 迁移（`src/lib/db/migrations.ts` + `idbMigrations.ts` 不需要）

新增 `migrateWorldFormsToCards()`（照抄 `migrateMiscSettingsToCards` 的幂等手法）：

```
for (const tabId of ['worldbase', 'power']) {
  const rec = await ops.get('formData', `${pid}::${tabId}`)
  if (!rec || 没有非空字段) continue
  卡名 = data[`一、世界总览::世界名称`]（power 用 `一、体系总览::体系名称`）.trim() || '默认'
  await ops.put('cardRecords', { id: rec.id 复用（幂等关键）, projectId: pid, tabId, name, data: rec.data, order: 0 })
  await ops.del('formData', `${pid}::${tabId}`)      // 🔴 先 put 后 del
  写「当前套」= 这张卡的 id
}
```

- 位置：`runMigrations` 末尾、`migrateMiscSettingsToCards` 之后（两者互不相干）
- **不需要 IDB 版本升级**（不新增 store / 索引）
- 幂等性：跑第二遍时 formData 已删 ⇒ 直接跳过；即便卡被删过又重新跑，`id` 复用也只会覆盖

### C. 当前套读写（新文件 `src/lib/worldSets.ts`）

```
WORLD_SET_TABS = ['worldbase', 'power']          // 单一判据（新增多套表只往这里加名字）
isWorldSetTab(tabId)
getActiveSetId(tabId) / setActiveSetId(tabId, cardId)     // settingsKV，key 含 pid
pickActiveSet(tabId, cards)  →  当前套那张（找不到就第一张；空表返回 undefined）
```

> 🔴 判据做成**单一常量 + 单一函数**（与 C2 的 `LOCAL_ONLY_STORES` 同款）——
> 「哪些表是多套表」这个判断会散落在 AI 上下文、UI 提醒、写入锚点三处，
> 写死三遍必然漂移（C2 那次 6 处硬编码的教训）。

### D. AI 上下文（`src/lib/aiContext.ts`）

| 位置 | 改动 |
|---|---|
| `sectionOf` 的 card 分支 | 多套表先 `pickActiveSet` 再 `renderCards`；段首加「（当前使用：X；另有 N 套未发送）」 |
| `renderCards` | 加一个可选参数传「已略过套数」用于标注；**不改**它既有的保密等级排序与 cap 逻辑 |

### E. 读取点修正（`src/lib/ai.ts:746`）

`db.getFormData('worldbase'/'power')` → 读当前套卡的 `data`（AI 取名要拿世界名称/体系名称）。
这是**唯一**绕过 `aiContext` 的独立读取点。

### F. 写入锚点（`src/lib/flow/commit.ts`）

**两处都要改**（第 173 行与第 288 行各有一条 form/card 分发）：

## 八、建议的开工顺序

```
① schema 改 type（2 行）→ 立刻跑全量闸 + vite build（先看连锁红在哪）
② worldSets.ts（单一判据 + 当前套读写）+ 单测
③ migrateWorldFormsToCards + 幂等测试
④ flow/formMap.ts 判据放宽 + flow/commit.ts 写入锚点  ← 🔴 与 ① 强耦合，必须这轮一起改完
⑤ aiContext 只喂当前套 + lib/ai.ts 读取点修正
⑥ CharacterSheet UI（黄条 / 切换器 / 名词特化）
⑦ 种子改卡片 + 示范项目实机（首启向导路径）
⑧ exporter 模块分组（可选）+ SettingSearch 白名单（可选）
⑨ 酒馆 TARGETABLE 加回 + 注释更新
⑩ 真跑一次「全书级设定汇总」+ 实机脚本 + 记录
```

**为什么 ① 要单独先做并单独提交**：
`type` 一改，所有按 type 分支的地方都会变（本次排查出 20 处，其中 4 处是静默变样）。
单独跑一遍全量闸 + `vite build`，能最快暴露「还有哪些地方假设了它是 form」——
比混在后续改动里排查便宜得多（那时红了你分不清是新改的还是旧假设）。

**为什么 ④ 必须紧跟 ①（不能拖到最后）**：
`formMap` / `commit` 的问题**不会让任何测试变红**，只会让「拆完整本书后世界设定是空的」
和「每汇总一次多一张卡」。这类问题越晚发现，排查成本越高（要重跑一轮完整流程）。

**为什么 ⑩ 要真跑一次汇总**：
这是唯一能验证 ④ 的路径。单测能钉住「清单里有这两张表」，但「草稿落到了当前套、没有新建野卡」
最好用实机确认一次（库里的卡数前后对比）。
