## 一、结论：母级不动，子级外挂

**主人哥哥的设计口径**（原文）：

> 无限流小说最顶层一定有一个统一的世界观和力量体系，在这个统一的世界观和力量体系之下，
> 主角可能在不同的世界或者不同的剧本里发生不同的故事，对应的世界和故事还有一套独立的
> 世界观或力量体系。所以项目的母级世界观还是只能有一个，就是全书籍的一个世界观或者力量体系
> 设定。**这个设定一定会喂给 AI**。但在这个母级世界观下面，可以建立多项子世界观 / 子力量体系，
> 给它们的列表里增加一个开关（正在活跃 / 已经完结），用来对应当前的故事剧情是否聚焦于这一个
> 子世界观。**只有处于活跃状态的子项才会作为内容提供给 AI**。

落地一句话：**母级继续用现在的 `type: 'form'`（零迁移、零改动）；子级外挂在 `cardRecords` 上，
用一个不在 `TABS` 里的 tabId 存放，活跃状态记在 `settingsKV`。**

### 与 v1 的关键差别（都是「风险」层面的差别）

| | v1（全部卡片化） | **v2（母子结构）** |
|---|---|---|
| 母级存储 | 改成卡片（要走迁移） | **不动**（还是那份 `formData`） |
| `type` 是否改 | 改 ⇒ **波及约 20 处按 type 分支的代码** | **不改** ⇒ 一处都不波及 |
| 老数据迁移 | 必须做（formData → 卡） | **不需要**（母级原地不动） |
| 四个静默连锁点 | 全部要处理（`formMap` / `commit` / 导出 / 检索） | **全部不存在**（见 §六） |
| 多套语义 | 单选（AI 只读"当前套"） | **多个可同时活跃**（更贴无限流的双线并行） |
| 历史保留 | 卡留着（不喂 AI） | 子级标「已完结」（不喂 AI）—— **语义更准** |
| 工量 | schema + 迁移 + 4 处链路 + UI | 存储 + AI 一段 + UI（§五） |

## 三、数据模型

```
母级（全书唯一，永远喂 AI —— 与现在完全一样）
  formData[`${pid}::worldbase`]        ← 原地不动
  formData[`${pid}::power`]            ← 原地不动

子级（多项，可开关）
  cardRecords
    { id, projectId, tabId:'worldbase-sub', name:'主神空间', data:{'一、世界总览::世界名称':'主神空间', …}, order:0 }
    { id, projectId, tabId:'worldbase-sub', name:'三国乱世', data:{…}, order:1 }
    { id, projectId, tabId:'power-sub',     name:'轮回者等级 F~S', data:{…}, order:0 }

活跃状态（与内容解耦）
  settingsKV[`worldSubActive::${pid}::worldbase`] = ['<子项id>', '<子项id>', …]
  settingsKV[`worldSubActive::${pid}::power`]     = […]
```

### 三个关键决定

**① 子级用「不在 TABS 里」的 tabId**（`worldbase-sub` / `power-sub`）
- 好处：不会被 `App` 当页签渲染、不会被 `formMap` 当表单汇总、不会被酒馆 `TARGETABLE` 误收录
  —— **天然与所有现存链路隔离**，这也是 v2 没有连锁点的根本原因
- 代价：需要自己写存取函数（§五 A），不能白拿 `CharacterSheet` 的 UI（但那本来也不合适：子级是「开关列表」不是「卡片目录」）

**② 活跃状态放 `settingsKV`（不放卡片身上）**
- 放卡片身上要改 `cardRecords` 结构 + 迁移 ⇒ 违背 v2「零迁移」的初衷
- `settingsKV` 在同步清单里 ⇒ 「第三卷在写哪个副本」这件事跨设备一致（合理）
- ⚠️ 两个必须处理的边角（§六 风险 ①）：
  - **删子项时同步清活跃列表**
  - **读取时过滤掉已不存在的 id**（防御：设备 A 删了、设备 B 的列表还没同步）

**③ 子级与母级共用同一套字段**（同一个 `tab.modules`）
- 无限流里这是对的：母级写「主神空间规则 + 统一等级 F~S」，每个副本子级写自己的「世界名称 / 底层法则 / 局部力量体系」
- 好处：AI 渲染与表单 UI 都能直接复用同一套 schema 渲染，**不用第二套字段映射**
- 🔴 代价要说清：母级与子级**会出现同名字段**（如都叫「世界名称」），所以 UI 上必须**始终标明当前在编辑哪一层**
  （母级 / 子级名），否则作者会填错层 —— 这是本项最容易踩的体验坑（§六 风险 ②）

## 四、AI 上下文（只有活跃子级才发）

### 渲染样例

```
【世界设定 · 全书统一】          ← 母级，永远出现（即使一个字没填也保留表头，作者才知道该填）
世界名称：苍澜大陆
世界核心规则：天地灵气为万物修行之源…

【世界设定 · 子世界（活跃 2 / 共 4）】
▸ 主神空间
世界名称：主神空间
底层法则：……

▸ 三国乱世
世界名称：三国乱世
……

（另有 2 个子世界已完结，未发送）
```

### 三条规则

1. **母级恒在**：即使母级为空也保留表头（与现在「空表返回空串」不同 —— 这里要显式出现，
   因为它是"全书统一"那一层，缺了作者没法察觉）；
2. **只发活跃子级**；一个活跃的都没有时，**只显示一行**「（尚未启用任何子世界）」，
   不把已完结的发出去；
3. 🔴 **必须写明「另有 N 个已完结，未发送」** —— 与既有的 `BY_BUDGET`（按预算裁剪并注明被略过）
   同一个诚实口径。不写的话，作者会以为 AI 读过全部子世界。

### 实现落点

`lib/aiContext.ts` 的 `sectionOf()`，form 分支加一层判断：

```
if (tab.type === 'form') {
  const main = renderForm(tab, await db.getFormData(tab.id), o)
  const sub  = isWorldSetTab(tab.id) ? await renderActiveSubSets(tab) : ''
  return [main, sub].filter(Boolean).join('\n\n')
}
```

- `renderActiveSubSets(tab)` 复用 **`renderForm(tab, sub.data, o)`** 渲染每个子项（键格式相同，见 §二 #5），
  外面套一层子项标题 ⇒ 与母级渲染口径**完全一致**，不会出现「母级按模块顺序、子级按字典序」这种偏差
- 判据走 `worldSets.isWorldSetTab()`（**单一常量**，见 §五 A）—— 不要在 aiContext 里写死表名
- **保密等级（`isPrunedForAI`）沿用**：子项 data 里若有 D 级标记，`renderForm` 已有过滤 ✅

## 六、v1 的四个静默连锁点，v2 为什么一个都不存在

v1（改 `type`）排查出四个「不报错只变样」的坑。v2 因为**母级仍是 form 型**，四处全部消失：

| v1 的坑 | v2 为什么没有 |
|---|---|
| `flow/formMap.ts` 四个函数按 `type === 'form'` 取表 ⇒ 「全书级设定汇总」失明 | 母级**还是 form 型**，`summaryFormTabs()` 照旧包含这两张表 ✅ |
| `flow/commit.ts` 汇总草稿按表名查卡 ⇒ 每次新建野卡 | 汇总仍写 `formData`（走 form 分支）⇒ **不经过卡片分支** ✅ |
| 设定集导出丢模块分组 | 母级走 form 分支（模块分组照旧）；子级是**新增**一段，不影响母级 ✅ |
| 全文检索白名单不含 `开书定位` | 与现在完全一致（本来就不检索 form 型）✅ 不改 |

**唯一新增的链路是「子级」**，而它用独立 tabId 与所有现存链路天然隔离（§三 ①）。

## 八、风险与对策

### ① 活跃列表与子项的「一致性」（最需要盯的一处）
- **删子项** ⇒ 必须同步从活跃列表移除（否则残留 id）
- **云端删了、本机列表还在** ⇒ 读取时按「实际存在的子项」过滤（`splitActive` 负责，纯函数可测）
- 不做「自动清理」写成副作用 —— 清理只在**删除动作**里做，读取只做**防御性过滤**

### ② 填错层（母级 vs 子级）—— 体验上的第一风险
同名字段（两边都有「世界名称」）⇒ 作者可能在子级里填全书设定。
- 对策：右列头部**始终**显示 `【母级】全书统一` / `【子世界】XXX`；左列母级项加 `全书` 徽标；
  两层的字段区加**不同底色左边框**（母级 amber / 子级 ink），让"我现在在哪一层"一眼可见

### ③ AI 上下文变长
活跃子项都发 ⇒ 活跃 5 个就相当于 5 份世界设定。
- 对策：活跃 ≥3 给黄条（§5.2）；**不设硬上限**（作者自己控，工具只提醒）——
  与规划里「超过 2~3 套显式提醒」的口径一致

### ④ 「子世界不会被 AI 汇总」要讲清
拆书 / 创意写作末尾的「全书级设定汇总」只写**母级**（因为它按 form 型取表）。
- 这是**设计如此**（子世界是作者按剧情手维护的），但必须在 UI 帮助里写明，
  否则作者会问「为什么拆完书子世界是空的」
- 将来若要让汇总写子级，需要新增一条「汇总写到哪个子世界」的策略 —— **本批不做**

### ⑤ 结构闸 / 行数
新面板 `WorldSetSheet` 控制 ≤300 行；抽取后 `FormSheet` 反而变小 ✅

## 九、验收标准

**单测（新增 `tests/worldSets.test.ts`）**
- `isWorldSetTab` / `subTabIdOf`：只认这两张表，返回值稳定
- `splitActive`：活跃 id 存在 → 取到；**id 已不存在 → 静默过滤**（不抛错、不返回 undefined 项）
- 活跃列表读写：`setSubActive(on/off)` 幂等；删子项后列表不含它

**AI 渲染（可在单测里直接测纯渲染函数）**
- 母级空 ⇒ **仍出现**「世界设定 · 全书统一」表头
- 子级：只渲染活跃的；已完结的**不出现在正文**，只在末尾计数里出现
- 一个活跃都没有 ⇒ 出现「（尚未启用任何子世界）」
- 🔴 **单世界用户零变化**：没有子项时，渲染结果与 2.4.2 之前**一字不差**（回归保护）

### 实现中补的三个决定

1. **新建子世界默认「活跃」** —— 作者刚建就是要写它；默认给「已完结」的话，他会填半天却发现 AI 根本没读（提示条还写着"没有活跃子世界"）。
2. 🔴 **离开页签时把未保存草稿落库**（`FormSheet` 的 `tabIdRef` 范式，本组件也必须做）——
   实机抓到：在子世界填了内容 → 直接点左侧别的页签 → 回来发现是空的。
3. **母级项与子项的名字按钮都加 `title`** —— 对作者是 hover 提示（"这一层永远发给 AI"），对脚本是**唯一可靠的定位锚**
   （按文本找 `/全书/` 会先命中左侧导航的「全书总纲」页签）。
