# 2.8.3 · 「自定义系统提示词」注入覆盖面补全（2026-10-06）

## 一、起因：承诺与实现不一致

「模型设置 → 模型配置 → 自定义系统提示词」的界面文案承诺的是
**「对所有调用此模型的功能追加一段总体指令」**，但代码里注入只靠**每个调用点自觉**多写一行
`composeSystemPrompt(...)` —— 盘点后发现有 **18 处没接**：

| 类别 | 处数 | 具体 |
|---|---|---|
| 酒馆模式**整个目录** | 15 | 剧情对话 / 自由对话 / 润色·代写 / 日常推进 / 轮末结算 / 记忆总结 / 冷启动档案 / 变量抽取 / 角色卡草稿 / 小说卡转换 / 修订建议 / 世界书 / 剧本 / 故事 / 复盘 / 访谈 |
| 字数校准 | 1 | `lib/wordRange.ts` 的 `ask` / `askSoft` —— 正文续写、整章改写的**补足篇幅与压缩** |
| 全局对话引导 | 1 | `aiCore/template.ts` 的 `aiChatJson`（经 `AITemplateFill` 的 `callChat`） |
| 访谈（全局侧） | 1 | `lib/interview.ts` 的 `runInterviewTurn` |

判定它是**漏接而非有意排除**的依据：`lib/tavern/` 目录对 `systemPrompt` 一词**零提及**，
没有任何注释说「酒馆不适用」；且 `tests/` 对 `composeSystemPrompt` 的覆盖面**零断言**。

根因不是谁偷懒，而是这件事的设计本身是**抄写型代码**——新增功能时漏一处，
表现只是「填了没感觉」，不报错、不崩溃、没有任何测试会红。

## 二、改法：把注入从「自觉」改为「兜底」

### 1. 注入下沉到 `chat()`（核心）

`aiCore/core.ts` 新增：

- `USER_SYSTEM_MARK` —— 注入块的固定开头，**同时充当去重标记**；
- `injectUserSystemPrompt(messages, provider)` —— 兜底注入，四条分支：
  - provider 没填 → **原样返回同一个数组引用**（最热路径零开销）；
  - 已有 system 且含标记 → 原样返回（**不重复注入**）；
  - 有 system 但没标记 → 追加到**第一条** system 尾部；
  - 一条 system 都没有 → 在**最前面**补一条（作者提示词必须留在最高指令层，不能被降级成 user）。

`aiCore/chat.ts` 的 `chat()` 里调用它（`skipUserSystem` 可显式跳过）。

⇒ **从此新增 AI 功能只要走 `chat()` 就自动接入**，不再依赖谁记得手写那一行。
原有 34 处显式调用**一字未改**：它们拼出的内容带标记，兜底会跳过，行为完全不变。

### 2. 结构闸 ⑩：把承诺钉死

`tests/structureGates.test.ts` 新增第 ⑩ 条，两条断言：

- **⑩-a** `aiCore/chat.ts` 必须仍调用 `injectUserSystemPrompt(` —— 这个支点被拆掉＝承诺静默作废；
- **⑩-b** 除 `aiCore/chat.ts` 外，`src/lib/**` 不得出现**在拼对话端点地址**的代码
  （判据：同一行既有 `/api/chat`｜`/chat/completions`、又有模板串插值 `${`）
  —— 绕开 `chat()` 就必然绕开注入。

⚠️ 判据刻意收紧过一轮：初版只匹配端点路径，把 `transport.ts` 的 baseUrl 归一
（`base.endsWith('/chat/completions')`，纯字符串处理）误报成违规。
**闸的假阳性一多就没人信它了**，故加「同时含 `${`」把「提字符串」与「拼请求」分开。

### 3. 酒馆：独立开关，默认关

主人拍板：酒馆的 system 是「扮演协议 + 世界书 + 记忆 + 档案」一整套，
而作者那段自定义提示词是**给正文与设定类功能写的总体指令**（人称 / 文风 / 禁忌），
无脑灌进来可能与「AI 分饰全员、一次只让一个人说话」的协议打架 —— 故**默认不接**。

- `TavernCommonSettings` 新增 `injectSystemPrompt: boolean`（默认 `false`）；
- 开关落在酒馆控制面板「一、通用设置」→「通用补充要求」下方；
- 🔴 实现位置＝`resolveTavernProvider`：关闭时**直接剥掉 `provider.systemPrompt`**。

为什么卡在模型解析这一层，而不是给 15 个调用点各传一个 opts：
逐处改就得各自拿到设置对象，**漏一处就是一个静默缺口**；而它们**全都**先走
`resolveTavernProvider` ⇒ 一处改动覆盖全部，**以后新加的酒馆 AI 功能也自动跟随**。
开销：只有模型配置里**真填了**提示词时才读设置，没填直接返回、零额外读盘。

### 4. 界面文案：说清「全局」并给出正确去处

`AIConfigPanel` 的「自定义系统提示词」：

- 标题改为「自定义系统提示词（可选 · 全局生效）」；
- 说明文字改用琥珀色警示，写明：这是**全局**的、对所有调用该模型的 AI 功能一并生效
  （酒馆默认不接，可在酒馆控制面板单独开启）；
  **只想调某一个具体功能，请到「模型设置 → AI 提示词」改那个功能自己的提示词，不要写在这里**。

## 三、关于「先发系统提示词、让模型回一句、再发工作指令」的评估

主人问：改成两次往返（先 system → 模型确认 → 再发工作指令）能否**完全保证**系统提示词生效？

**结论：不建议改，维持现状。** 理由：

1. **定位不对**：问题的性质是「有没有送到」和「会不会打架」，不是「送了几次」。
   兼容性上 system 角色本身已是最高指令层，`messages` 顺序也始终是 system 在前、user 在后。
2. **换不来服从度**：模型回一句「好的」并不会让它之后更遵守；反而会——
   凭空多一条无意义 assistant 消息**污染上下文**（酒馆每轮都跑，成本翻倍且吃预算），
   并可能被模型当成 few-shot 范例去**模仿这种确认式回复**。
3. **真正影响生效的是两件事**：①**内容冲突**（自定义提示词与功能格式铁律打架）；
   ②**位置权重**。而当前把自定义提示词放在 system **尾部**，恰恰已是最优位置（近因优势）。
4. **诚实的边界**：能 100% 保证的是「**注入到位**」（本次已用兜底 + 闸锁死）；
   无法 100% 保证的是「**模型服从**」——那取决于模型本身，加一轮往返也买不到。

⇒ 保持现在的单次请求结构；把力气花在本次做的「覆盖面补齐 + 机制兜底」上。
