## 四、存储 / 同步层的严重问题（本轮已修 —— 第二次封装前）

> 这一节原本是「待商量」，老大看过之后要求一并修掉（版本号不变，重新封装）。修完补了常驻回归闸：`tests/syncGuards.test.ts`（7 条）。

### P0 · 更换同步目录到空目录会写入一份空快照 ✅ 已修

- 链路：`CloudFileSyncBar.pickDir` → `enableDesktopCloudSync(handle)` → `enableDesktopCloud()` 里 `cloud.configure()` **先把单例 cache 清空** → 拉新目录快照（空）→ 走 `seedDesktopFromLocal((s) => ops.getAll(s))`；而「同步本来就开着、只是换目录」时 `ops` 正指向**同一个被清空的单例** → 读回来全空 → 写成 rev=1 落到新目录；空推守卫比较的 `baseCache` 也被清零 → 不拦。
- 修法：新增 `captureSyncData()`，在 `enableDesktopCloud()` **之前**把参与同步的 store 抓一份快照，播种改用这份快照（不再读「此刻的 ops」）。

### P1 · 空推守卫会被「12 个空数组」骗过去 ✅ 已修

- `liveStores()` 会把每个 store 都放成键（哪怕是空数组）→ `Object.keys(...).length === 0` 恒不成立，空载荷照样能推上云端。
- 修法：新增 `totalRecords()`，守卫与 `restoreFromCloudBackup` 的空判都改成**按记录总数**判。

### P1 · 关闭云同步会丢掉未推送的改动 ✅ 已修（同批）

- `disableDesktopCloud()` 直接清 cache 与 code，防抖窗口内的改动（或离线期推送失败的改动）随之消失，`ops` 切回更旧的本地快照。
- 修法：`flushNow` 已是推送入口；本轮把它接上 `clearDesktopCloudEnabledFlag()` 的诚实标记，并保证异常时 `onFallback` 落本地（见下面「推不上去」那条）。

### P1 · 云端载荷解密失败会被静默覆盖 ✅ 已修

- 外层 JSON 合法、`enc` 段损坏时，409 分支的 `decryptObj` 抛错 → 旧实现把 `serverCache` 置 null 继续，于是用本地 cache 以 serverRev 覆盖 —— 那份加密载荷**只有云端有**，覆盖后连 `.corrupt` 都没留。
- 修法：`decryptObj` 失败时 `setStatus(error)` 并**直接抛错**，不再重试。闸：`syncGuards` §②断言「只尝试了一次」。

### P1 · IPC 写同步文件失败被吞，状态永远停在「同步中」 ✅ 已修

- 主进程 `sync:writeFile` 失败时返回 `{ok:false}` 而不抛；`nodeWrite` 不看返回值 → 写后回读 rev 不匹配走 409 → 重试 5 次后 `pushNow` **返回** `{conflict:true}`（不抛）→ `flushNow` 只对抛错设 error → 状态卡在 syncing。
- 修法：①`nodeWrite` 检查 IPC 返回值并抛错；拿不到 fs 后端也如实抛（原先静默 return）；②`flushNow` 处理 `{conflict:true}` → 置 error。闸：`syncGuards` §③。

### P1 · 启动时云端为空仍显示「已开启」 ✅ 已修

- `applyDesktopCloudFromPersisted()` 配好了 code/transport/watch，`db.ts` 拉快照为空（或抛错）就 return 保持本地 ops，但 `ENABLED_KEY` 没清 → 界面显示「已开启（待命）」而实际一条都没同步。
- 修法：新增 `clearDesktopCloudEnabledFlag()`（**保留**目录偏好），启动的两条空/失败分支都调它。

### P2 · 导出 / 换位置 / 恢复默认位置没走「锁写盘」 ✅ 已修

- 锁写盘期间内存里是空库/残缺数据：导出会造出一个**看起来正常**的空备份；换位置会把空数据写成新位置的一份有效文件。
- 修法：三个入口都先判 `writeLocked` 并明确拒绝（提示按顶部红条解除锁定）。**导入数据文件不拦** —— 拿一个校验通过的文件覆盖，正是锁写盘的恢复手段；顺带修了它在锁定期 `flushDesktop()` 直接 false、导入的数据根本落不了盘的 bug（现在会先显式解锁）。

### P2 · 删项目时快照清理挂错前提 ✅ 已修

- `const snapKeys = chapterIds.size ? ... : []` —— 章节全在回收站时该项目的快照一份都不删，成了界面看不到、却持续进云载荷的孤儿。改成按 `projectId` **无条件**查（顺带删掉那次无用的 `chapters` 全表预读）。

### P2 · 两套同步可以指向同一目录 ✅ 已修（软校验）

- ①「改数据文件位置」＝明文 JSON（含 apiKey 明文）；②「云盘文件同步」＝加密 `.yfe`。代码层原先没有任何校验阻止两者指向同一目录：明文库会被网盘客户端一起传上云，且两边互相覆盖。
- 修法：选云盘目录时比对「数据文件所在目录」，命中就用 `confirmDialog` 明确警告（默认建议另选空目录，用户坚持才继续）。新增 `getDesktopDataFilePath()`（走既有的 `store:path` IPC）。

### 本轮判定不改（留待需要时再谈）

- 自动保存路径（`NovelEditor` 的 394/415/443）不逐次同步台账：台账是**粗粒度视图**，每次自动保存都跑一遍「全表扫 + 孤儿行清理」代价太大；字数在手动保存/重排/新建章时自然刷新。
- `deleteTableRow` 只删台账行、不删正文（反向幽灵）、`deleteVolume` 不清该卷 tab 的设置 —— 语义含糊（台账行 vs 正文谁是主体），改动面大，先记录。
  唯一顺手修掉的是「批量重生成摘要」那条：摘要变了台账的「一句话事件」却没更新（用户会以为重生成没生效），已补 `syncChapterMaster`。
