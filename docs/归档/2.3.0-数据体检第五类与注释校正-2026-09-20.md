## 一、第 2 项：`setStoreOps` 注释校正（**改注释，不补测试**）

### 查清的事实

`src/lib/db/core.ts` 里那句话的主语被误读了：

```ts
// 🔬 导出仅供单测（tests/cloudStoreWrapper.test.ts）：本函数是纯工厂、无副作用，
// 且「backups 落本地 / 敏感 meta 不上云 / 云端不可用回退本地」三条语义都只在这里，
// 不导出就无法在不跑浏览器的前提下锁住它们（与 setStoreOps 同理）。   ← 这句
export function makeCloudStoreWrapper(...)
```

- **`makeCloudStoreWrapper`** 的导出理由**成立**：它确实被 `tests/cloudStoreWrapper.test.ts` 引用。
- 括号里的「**（与 setStoreOps 同理）**」是**错的类比**：`setStoreOps` 在 `src/` + `tests/` 全库
  **零消费者**（只被 `enableDesktopCloudSync` / `disableDesktopCloudSync` 在**同模块内**调用，
  另有 `db.ts` 门面再导出但无人经它使用）。

### 它真正的导出理由

`db/core.ts` 顶部约定：

> `ops` 与 `currentProjectId` 是**可重新赋值**的模块级单例 …… **故它们必须 export** ——
> 兄弟业务域只读、不写（对 import 进来的绑定赋值是编译错误）；ESM 活绑定保证换值后各处都读到新值。

`setStoreOps` 是 `ops` 这个「必须 export 的活绑定」的**唯一写入口** —— 与"为了单测"毫无关系。

### 处置：为什么**不**补测试

不是疏漏，是**正向断言写不出来**：

1. 它唯一的可观测出口 `isDesktopCloudSyncActive()` 在测试环境**恒为 false**
   （`desktopCloudFileStore` 是模块内部引用，测试拿不到），硬写只能得到**恒真的假 PASS**；
2. 它本身只是一行赋值（`ops = o`），类型一致性 `tsc` 已经保证；
3. 真正有风险的是**两个调用方**（`enable`/`disableDesktopCloudSync` 里「先 flush + 镜像再切」的
   顺序 —— 那里有 P1-1 丢数据的血泪注释），而那需要**真实桌面环境**才跑得起来。

故：删掉错误类比、在 `setStoreOps` 上把理由写准、并写明「为何没有单测」。

> 📌 同时纠正我上一轮的表述偏差：我当时说的是「`setStoreOps` 声称『不导出就无法…』」，
> 其实那句话是 **`makeCloudStoreWrapper` 的注释**，`setStoreOps` 只是被顺手类比。事实判断
> （`setStoreOps` 无测试）没错，但归错了主语。

### 2.2 老大定调：只接检测，不接清理

理由写在代码注释里，核心是**破坏性操作的风险**：

> 幽灵的成因常常是「**这一侧读失败 / 同步竞态**」而不是真的缺失 —— 盲目删索引会把**还能恢复**的
> 条目永久抹掉。这与项目红线「**读数据失败必须锁写盘**」是同一类风险。

所以本轮交付「看得见」，不交付「一键删」。清理入口待后续版本单独设计（需带安全前置）。

### 2.3 两个关键设计

#### ① 检查必须**追加在最后**（issue id 稳定性）

issue id 是 `H${n}` 递增的，而本页的「**忽略**」把 id **持久化**在 `healthIgnoredIds` 里。
把新检查插进表格循环**中间**，会让作者此前忽略的 id **错位到别的条目上** ——
表现是「我忽略了 A，结果 B 被藏起来」，且**不报任何错**（静默失效）。

已写测试钉死（见 2.5 的第 ③ 组），负面对照实测复现：`H1 → H4`，幽灵占了 `H1,H2,H3`。

#### ② 用**动态** `import('./tavern/store')` —— 但理由与原先想的不同

一开始写的理由是「静态 import 会把整套酒馆存储层无条件打进主包」。**实测推翻了它**：

| | `index`（主包） | `CheckTools` chunk | `store` chunk |
|---|---|---|---|
| 动态 import（现方案） | 1356.10 kB | 22.79 kB | 11.35 kB |
| 静态 import（对照） | 1356.11 kB | 22.40 kB | 11.37 kB |

**改成静态也不会进主包** —— 因为 `CheckTools` 自身就是懒加载 chunk，而 `tavern/store` 早已被
`Tavern*` 组件引用成独立 chunk。注释已改成诚实的**防御性**论证：

> `check-tools` 在 FEATURE_TIER 里是 **locked**（永远在），酒馆那套全是 **optional**（默认不勾）；
> 一个 locked 模块不该在**模块图**里强依赖 optional 模块。哪天有人把 CheckTools 收回主包 /
> 改 manualChunks，静态 import 就会把酒馆存储层拖给每个项目的每个用户，动态 import 天然免疫。

（对照脚本已跑完并删除；结论与数据记在此处，避免下轮重复做。）

### 2.6 为什么第 5 类用 `warn` 而不是 `error`

`error` 在 UI 上是「冲突」徽标、排在最前。幽灵条目**不影响已有内容的正确性**（只是列表里有几条点开是空的），
而且**当下无法通过改数据修复**，用 `warn`（「注意」）更贴切。已用断言钉住，防止后人"顺手"改成 error。

## 三、本轮最有价值的东西：**两次「实测推翻推理」**

### 案例 A：动态 import 的理由（体积）

推理说「静态 import 会把酒馆拖进主包」，实验说「**不会**」（差 <0.5 kB）。
若不实测，这个错误理由会被抄进代码注释、再被后人当依据引用。**已改成防御性论证 + 实测数据。**

### 案例 B：实机脚本的「还原」（`写回 ≠ 还原`）

第一版脚本的还原逻辑是「把**读到的值**写回」。但还原时读到的正是**注入后**的值 ——
等于**把幽灵原样留在库里**。日志里那句 `[还原] … 还原后=1` 就是它。而**断言全绿**，
只有 `[注入] 原值条数="absent"`（键本不存在）与 `后=1` 这对数字露了馅。

改成**按 ghostId 过滤**后，用独立只读探针复核：`tavern.charIndex` 键**不存在** ✓ 彻底干净。

> 教训：**实机脚本的 `还原` 必须写成"幂等的状态修正"（按标记过滤/删除），不能写成"写回读到的值"** ——
> 后者在"读-改-写"结构下天然把改动当成基线。
