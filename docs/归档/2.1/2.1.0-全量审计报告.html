2 · P0 · 必修（数据安全）

P0桌面版"读不到数据文件"被当成"空库"，随后首次写盘覆盖真实数据

位置
electron/main.cjs:41-47 · src/lib/desktop.ts:147-156 · src/App.tsx:163-167
触发
主进程读数据文件抛异常（被云盘客户端 / 杀软短暂占用导致 EACCES/EBUSY、权限变更、文件被截断）
影响
不可逆数据丢失。用户辛苦写的数据文件被一个空库覆盖。

证据链（三段全部可复核）：

// ① electron/main.cjs:41-47 —— 所有异常都被吞成 null，没有区分"文件不存在"与"读失败"
function readDataFileSync() {
  try { return fs.readFileSync(dataFile(), 'utf-8') }
  catch { return null }          // ← 读失败与"首次使用"返回同一个值
}
// 主进程 store:load 恒返回 { error: null }（因为上面不抛），desktop.ts 的 r.error 分支永远进不去

// ② src/lib/desktop.ts:147-156 —— 拿到 null 后 data 保持空库，且连 lastError 都不设
if (r.error) { lastError = '读取本地数据文件失败：' + r.error }
else if (r.text && r.text.trim()) { /* 解析 */ }
// 两条都不满足 → data 仍是空 → finally { inited = true }

// ③ src/App.tsx:163-167 —— 见到"没有项目"就自动播种示范项目
if (!last) {
  const existing = await db.getAllProjects().catch(() => [])
  if (existing.length === 0) { await createDemoProject() }   // 数据变更 → dirty → 800ms 后写盘
}

项目在 desktop.ts:154 的注释里明确承诺过「将以空库启动，原文件不会被覆盖」——但这个保护从未实现：没有任何写盘锁定，播种示范项目就会触发 flushDesktop() → store:save 原子写，把原文件覆盖掉。主进程的原子写（writeAtomicSync）只防"写了一半"，不防"用空数据写"。

修法（择一，建议 A）：

  • A（推荐）：主进程返回时区分三态——不存在 / 读取失败 / 成功；读取失败或 JSON 解析失败时，渲染层进入只读锁定态：禁止任何写盘，界面顶部常驻红色横幅「数据文件读取失败，已暂停写入以免覆盖，请检查文件是否被占用」，并给「重试读取 / 手动选择文件」入口。
  • B（兜底）：写入前先 store:load 比对——若磁盘上存在非空文件而内存是空库，拒绝写入。

AI 层

P1剧情模式的"会话级记忆"是一条从未接通的死链

位置
tavern/types.ts:149-154 · tavern/engine.ts:157 · TavernPlot.tsx:604-607,726 · TavernUsageDialog.tsx:58
证据
全仓 grep：session.memory 有 4 处读、1 处类型定义、0 处写；summarizeMemory 唯一调用点是 TavernFree.tsx:339；store.ts 的检查点/回滚/分支对 memory、watermark 的搬运全是空转；inheritMemoryFrom 无写入者也无消费者。
影响
① 剧情 system 的「长期记忆」层永远为空 → 长推演无法跨轮记忆；② 「本场记忆（N 字）」面板因 {session.memory && …} 恒假而整块不渲染；③ 检查点文案宣称"消息与本场记忆一起还原"是空承诺；④ 用量明细里该项恒为 0。

这条经两路独立审计交叉验证一致。方案文档里只有消费端与容器（types.ts:151-154 写着"本场推演的六栏记忆（会话级）"），生产端从未建成——即不是"显示 0"，而是整条管线缺一半。

修法（二选一，推荐 A）：

  • A：补 summarizePlotMemory（可复用自由模式的 summarizeMemory，把 source 换成剧情 messages），在 runPlotTurn 后按阈值写入 session.memory + 推进 watermark。这样检查点/回滚的记忆语义同时被激活，inheritMemoryFrom 也有了落点。
  • B：若判定剧情模式不该有会话记忆（毕竟底下就是小说正文），则应摘干净：删 UI 面板、删检查点文案里的"记忆"字样、删三个死字段，别让作者以为它在工作。

P1变量行未剥离 + 「无变化」被误报为"格式没对上"

位置
tavern/engine.ts:685-700（调用方）与 tavern/vars.ts:106-114（解析器）
影响
模型完全按我们自己的提示词写 〔数值〕无变化（vars.ts:258 要求的写法）时，界面会弹「数值行格式没对上」的错误提示，而格式其实是对的——作者会去改一句没坏的提示词。

解析器其实已经写好了正确逻辑：vars.ts:106 注释「认得出，把行剥掉」，并返回已剥离的 parsed.text。问题在调用方没用上：

// engine.ts:687-699
if (parsed.ops.length > 0) {
  const applied = applyVarOps(...)
  if (applied.changes.length > 0) {   // ← 只有这里才 reply = parsed.text
    reply = parsed.text; ...
  }
} else if (parsed.rawLine) {
  varParseFailed = true               // ← 「无变化」也落这里 → 误报，且那行留在正文
}

还有一个未覆盖的隐含分支：ops 非空但夹取后无实际变化（applied.changes.length === 0）时，两个分支都不进——那一行既留在正文里，也不报错。

修法：只要 parsed.rawLine 非空（即确实识别出标记行）就采用 reply = parsed.text；仅当"认不出"（ops.length === 0 && parsed.text === reply）时才置 varParseFailed。

数据安全

P1恢复备份是"先清空、再写回"，中途失败项目变半空

位置
db.ts:1374-1401（批量删除）→ db.ts:1404+（逐条写回）
影响
删与写之间无事务、无回滚。写入中途失败（IndexedDB 配额、云模式 413 / 断网、用户关窗）→ 项目数据半空且原数据已删。

附带发现：恢复会清掉该项目的全部 snapshots（时光机），而 ProjectBundle（db.ts:917-933）本就不含快照、永不再生 → 用户的手动存档在恢复后全部消失且无任何提示。
说明：删除孤儿快照本身是合理的（恢复时所有 id 都重新生成，旧快照指向的章节已不存在），缺的是告知。

修法：先写入临时 projectId，全部成功后再切换引用；或把快照一并纳入 bundle。同时在恢复确认弹窗里如实写明"此项目的时光机存档将被清除"。

P1桌面版关窗时的同步写盘失败被吞掉

位置
desktop.ts:197-206 + electron/main.cjs:95-102
证据
主进程 store:save-sync 失败时返回 { ok:false, error } 而不抛异常；渲染层 api().saveSync(JSON.stringify(data)) 的返回值没有检查，随后无条件 dirty = false。
影响
关窗时写盘失败（只读目录、盘满、文件被占用）→ 数据丢失且无提示；desktop.ts:204 注释声称"失败保留 dirty 供下次启动补救"与代码不符。

修法：检查返回值，ok !== true 时不改 dirty，并把失败原因通过 lastError 上报给启动 toast。

P1启动切换到云同步时，不判断"远端是否为空"

位置
db.ts:444-451、db.ts:484-493
影响
云盘客户端尚未把 .yfe 同步下来 / 被其它设备删除 / 文件为 0 字节时，直接切到云端 → 本地明明有全量数据却显示空书架；此后一次写入即以近空载荷覆盖云端文件，其它设备的有效数据被清掉。

修法：启动即 pull；远端为空而本地非空时，先播种本地数据再切换；失败则回退本地并提示。

P1地图编辑器画布尺寸走了 getBoundingClientRect() → 右下被裁掉约 8%

位置
GeoMapEditor.tsx:216（写入点 :766-768）
证据
const r = el.getBoundingClientRect() → setVp({w: Math.round(r.width), …}) → <svg viewBox={0 0 vp.w vp.h} width={vp.w} height={vp.h}>。而 <html> 有 108% 界面缩放，rect 返回的是缩放后视口像素，却被当成 CSS px 属性写入。
影响
画布容器 800 CSS px 时读出 864 → svg 溢出 64px，被 overflow-hidden（:754）永久裁掉右侧；fitView 以 vp.w/2 居中，于是"居中"永远偏右下。

对照：同型画布 PlotCanvas.tsx:107 用的是 clientWidth/clientHeight（CSS px，不受 zoom 影响）——两种口径并存，进一步说明这处是偏离。

修法：改用 el.clientWidth / el.clientHeight；同步修正 :371 兜底分支的单位。

P1三处拖拽位移未按界面缩放换算，拖动比光标快 8%

位置
TableSheet.tsx:257（列宽）· PlotCanvas.tsx:235（卡片）· useSvgPanZoom.ts:115（画布）
证据
位移取 ev.clientX - startX（视口像素）却直接加到 CSS px 尺寸上：Math.round(startW + dx)。正确范式就在同仓——useResizable.ts:53-54 先除以 zoom：const z = Number(document.documentElement.style.zoom) || 1; const dx = (ev.clientX - startX.current) / z。
影响

修法：三处统一 dx / (Number(document.documentElement.style.zoom) || 1)，或抽成一个共享 hook。
