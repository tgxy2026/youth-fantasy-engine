## 二、创意写作：产出目标前移到起点

**要求**：开口就分清「大纲规划」还是「正文创作」，不要跑到闸门②才让作者选。

**改动前**：起点只有「从一句话创作 / 接着已有内容写」；跑到闸门②才出现三个按钮 —— 「放弃本次创作 / 只保存大纲（不写正文）/ 保存大纲并开始连写」。
**问题**：把"目标决策"塞进了"确认动作"里 —— 作者在最该只是"看一眼、点确认"的位置上被要求做产品级选择。

**改动后**：

| 层 | 改动 |
|---|---|
| `creativeSession.ts` | 新增 `CreativeTarget = 'outline' \| 'full'`，进 `CreativeInputs.target`（默认 `full`）；`onOutlineGate` 的 Promise 类型从 `boolean \| 'outline-only'` 收窄为 `boolean` |
| `aiWorkflow.ts` | `CreativeWritingOptions` 加 `target`；`outline` 阶段改为 `const outlineOnly = (opts.target ?? 'full') === 'outline'` → `ctx.skipRest('（已选择：只做大纲规划）')`；闸门只判 `true/false` |
| `CreativeWritingPanel.tsx` | 起点下方新增「这一次要产出什么」：`只做大纲规划` / `大纲 + 正文` |

**界面随目标联动**（不是单纯多两个按钮）：
- 「只做大纲规划」时：**「每章目标字数」收起**（不写正文，问字数没意义）、**「连写设置」整块收起**（去 AI 味儿 / 设定补完 / 逐章确认都只服务于连写）、章数标签从「连写章数」变「**规划章数**」、开始按钮文案变「**开始规划**」、底部说明改口说"本次只做大纲规划：确认后即收工"。
- 闸门②只剩 `放弃本次创作` / `确认大纲（不写正文）`（或 `保存大纲并开始连写`）—— **不再提供「只保存大纲」**。
- 帮助文案同步改写。

**只对起点生效**：「接着已有内容写」永远是写正文（它的定义就是续写），代码里 `target` 只在 `mode === 'scratch'` 时取值。

## 三、新增「整章改写」（润色 / 扩写 / 精简 / 改写）

**背景（老大原话）**：示范项目第 21 章只有 2202 字，而一章的目标体量约 4000 字；颉文姬里虽然润色 / 扩写都有，但**那是面向一段的**，项目里缺一个"对大段文字做润色 / 改写 / 扩写"的接口。

**为什么不能直接复用颉文姬的「选区改稿」**（三条都是硬的）：
1. 它的产出是「**建议段**」—— 写法是"把改稿写到原文下方"。整章改写用它，正文会变成原文 + 改稿两倍篇幅，作者没法读。
2. 它是 **JSON 输出**（`{rewritten, notes}`）。把 4000 字正文塞进 JSON 字符串，引号 / 换行转义极易解析失败 —— 这个坑项目里踩过（表现为"只输出个别标点"，见 `aiParse.ts` 的注释）。
3. 它的定位是"局部修改"，不是"重写一章"。

**所以新增一条独立链路**（走**纯文本流式**输出）：

| 层 | 文件 | 职责 |
|---|---|---|
| 任务 | `lib/aiTasks.ts` → `aiRewriteChapter()` | 拼提示词（动作规则 + 原文 + 上一章结尾 + 作者要求 + 目标字数）、调模型、清洗输出 |
| 清洗 | `aiTasks.ts` → `cleanChapterOutput()` | 纯函数：剥 markdown 围栏 / 「好的，以下是…」开场 / CRLF 归一 |
| 落库 | `lib/chapterRewrite.ts` | `listRewriteCandidates()`（选章列表）+ `applyChapterRewrite()`（写回） |
| 状态 | `lib/creativeSession.ts` → `RewriteState` | 与创作共用同一 store：**切页签不丢结果** |
| 界面 | `CreativeWritingPanel` 底部「整章改写」区块 | 选章下拉（带字数）→ 动作 → 目标字数 → 补充要求 → 开始 → **预览** → 替换 / 丢弃 |

**四种动作**（`CHAPTER_REWRITE_META`）：润色（不要目标字数 —— 改了字数就不是润色了）/ 扩写 / 精简 / 改写。

**🔴 三条安全边界**（都写进了代码注释与单测）：
1. **结果只在内存** —— 作者点「替换该章正文」之前绝不写库。这是与"创作"的根本区别：创作产出新章，改写要**覆盖**旧正文。
2. **写前显式存快照** —— `db.saveChapter` 自己也会按阈值存（>5 分钟 或 字数差 >200），但"5 分钟内连改两次且字数接近"两条都不满足，旧稿就永久丢了。所以 `applyChapterRewrite` 里**再显式存一份**，界面提示指向「时光机 · 本章版本历史」。
3. **只动三个字段** —— content / wordCount / updatedAt。标题、状态、卷属、排序一律不碰（改写是"改文字"，不是"挪动章节"）；并同步该章在**章节台账**里的「字数」，否则章节总表停在旧值上。

**其它**：
- 走**纯文本流式**（长度上千字，非流式必撞总超时墙）。
- 上一章结尾随请求一起送（约 1200 字）—— 保证改写后仍接得上。
- 提示词登记进「模型设置 → AI 提示词」（`chapter-rewrite`，分组「正文写作」）。
- `aiDataSources` 同步新增 `chapter-rewrite` 条目（红线：AI 会读哪些数据以它为准）。

## 四、核查：接着已有内容续写时，纲要会不会跟着推进？

**结论：分三层，只有一层会。**

| 纲要载体 | 续写 9 章后 | 依据 |
|---|---|---|
| **各卷「章节台账」表**（章节总表的实体） | ✅ **自动跟上** —— 第 22~30 章会自动出现，含「章节号 / 章节标题 / 一句话事件 / 字数」 | `autoContinue.ts:349-351`：每存一章都 `db.saveChapter(ch)` + `syncChapterMaster(ch, chapterSeqOf(...))`；`chapterMaster.ts#syncChapterMaster` 写入这四列；「一句话事件」取 `ch.summary`，而续写每章都会生成约 1/10 的压缩摘要（`aiChapterSummary`） |
| **《章节细纲》卡** | ❌ **不会新增** | `chapterMaster.ts#backfillOutlineEvent` 的红线写着「匹配不上就什么都不做，**绝不新建细纲卡**」—— 它只在卡已存在且字段为空时回填 |
| **《分卷大纲》/《全书总纲》** | ❌ **完全不动** | 续写链路里没有任何写这两个页签的代码 |

**所以"规划到 21 章、再续写 9 章"的实际后果是**：台账层面 22~30 章齐了（作者能看到"写到哪了"），但**第 22 章起没有细纲**，于是连写阶段 `outlineFor(22)` 返回 `undefined` → **静默退化成"自由发挥"**。界面目前没有任何地方告诉作者这件事，只在结果里说"写完 N 章"。

**这是真缺口，但不是 bug**（"绝不新建细纲卡"当年是刻意定的：凭空建一张"有计划但内容是正文摘要"的卡，等于把"没有计划"变成"假的计划"）。

**三个可选做法**（建议 **B**，请老大定）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 只讲清楚 | 面板显示「细纲覆盖：第 1~21 章；从第 22 章起将自由发挥（不贴大纲）」 | 零风险、零调用；但作者仍得自己补细纲 |
| **B. 续写前补细纲（建议）** | 「接着已有内容写」处加一个按钮：按已有《章节细纲》的风格 + 全书总纲，**一次性生成第 22~30 章的细纲草稿** → 走现有草稿勾选通道 → 作者确认后落库 → 再开始连写 | 多一次模型调用（一次生成 N 章，不是每章一次）；要新增一条"往下续排细纲"的任务与入口 |
| C. 续写后补记 | 扩展现有 `backfillOutlineEvent`：缺卡时按章建卡，内容用正文摘要 | 语义会从"计划"变成"事后补记"，与"细纲是计划"的定位冲突 —— 不推荐 |

26 项检查 25 通过；唯一未过的是「提示 toast 指向时光机」——**断言时序问题**（toast 约 3 秒淡出，
脚本 3.5 秒后才抓）。该文案已改由 `creativeModes` 的文本断言锁住，实机脚本也放宽为不误报。

### 本轮实机抓到的三个真问题（都不是猜的）

1. **🔴 任务跑完没把 `running` 置回 false** —— AI 层 86 秒就跑完，界面却**永远**停在「正在改写…」，
   预览与「替换该章正文」都不出现，12 分钟后脚本超时才暴露。
   **定位手法**：写一个绕过 UI、直接 `page.evaluate` 调 `aiRewriteChapter` 的诊断脚本，打印
   `firstTokenMs / 总耗时 / 输出长度` —— 实测 `887ms / 86s / 3494 字`，一步排除"模型慢"，锁定 UI 状态层。
2. **上下文取样方向写反** —— 提示词写的是「上一章**结尾**」，代码却是 `slice(0, 1200)`（取到开头）。
   已改 `slice(-1200)`。
3. **模型偶发只返回 1 个字** —— 同一 prompt 前后实测三次分别返回 3494 / 4271 / 4563 字，
   说明不是 prompt 问题；但**异常短的结果原本可以一键「替换」**，等于一次点击就能把作者正文换成
   一个字（只剩快照能救）。已加锁：**原文 > 600 字符且结果 < 35% ⇒ 标 `suspect`、禁用「替换」并说明原因**。
