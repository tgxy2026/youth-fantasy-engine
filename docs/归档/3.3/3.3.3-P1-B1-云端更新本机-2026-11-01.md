## 1. 原来缺什么（逐条对照规划 §7）

| 规划要求 | 原状 | 本包做法 |
|---|---|---|
| 确认框写「替换为第 N 版」，并锁住该 rev | 确认框显示 `cloudRevision ?? '?'`，下载时**不传 rev** ⇒ 取最新 | 确认前要求 `cloudRevision` 已探测成功；`rev: pinned + expectedRevision: pinned`，下载到的版本不等于 pinned ⇒ `CLOUD_ADVANCED` 中止 |

| 期间暂停该项目自动推送 | 无 | 覆盖全程 `stopAutoSync()`；未完成操作记录还会让 `autoSyncTick` 跳过**该项目**（连 revision 都不查） |
| 备份完成与首次写入之间持久化操作记录 | 无 | `meta` 里 `syncPullOp::<projectId>`：`prepared → backup-done → writing → written`；覆盖 / 基线 / 记录三步都完成才删 |
| 启动发现中断要阻止自动推送并提供核验/恢复 | 无 | 面板顶部常驻提示：阶段 + 备份 id；两个入口「从这份备份恢复本机」「当前内容我已核对」 |
| 写成功才推进基线；部分失败要分开报 | 基线写失败与覆盖失败同一句 toast | 分别报告：内容已更新但基线未写入 ⇒ **保留记录**、自动同步停着；`WRITE` 失败 ⇒ 记录留作核对 |
| 换项目晚回执不能改新项目 | `restoreBundleToProject` 用传入的 localProjectId，但调用方没有二次核对 | 写前复检 `getCurrentProjectId() === pid` |

## 3. 为什么操作记录放 `meta` 而不是 `settingsKV`

`settingsKV` 是**项目级、会随项目包与云端快照走**的数据。把"这台机器上的一次覆盖"写进去，
另一台设备会看到"上次更新没走完"，而那条备份根本不在它机器上；更糟的是它会挡住那台设备的自动推送。
`meta` + `LOCAL_ONLY_META_KEY_PREFIXES` 是项目里已有的"本机专属键"通道（模板迁移/个人模板库同款），
判据只在 `sensitiveMeta.ts` 一处，云同步与数据文件导出自动排除。

## 4. 失败语义（代码里逐条对应）

| 结局码 | 本机内容 | 记录 | 自动同步 |
|---|---|---|---|
| `CLOUD_ADVANCED` | 未动 | 清除 | 恢复 |
| `DOWNLOAD` | 未动 | 清除 | 恢复 |
| `BACKUP`（建备份失败 / 记录写失败） | 未动 | 清除 | 恢复 |
| `STALE_TARGET` | 未动（备份已建，随结果返回 id） | 清除 | 恢复 |
| `WRITE` | 可能写了一半 | **保留**（phase=writing） | **挡住** |
| 成功但基线写入失败 | 已更新 | **保留**（phase=written） | **挡住** |
| 成功 | 已更新 | 删除 | 恢复 |

🔴 「从备份恢复」不推进同步基线：恢复的是**这次更新之前**的本机内容，它的基线本来就是
`fromBaseRevision`；硬把基线改到新版本会让下一轮把旧内容当成"已同步"而永远不上传。
「当前内容我已核对」才推进到 `confirmedRevision`（写入中断过时用 danger 确认，并提示先逐章核对）。
