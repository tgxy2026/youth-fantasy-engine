## 2. 外置 sidecar 与独立库

| 位置 | 布局 | 物理通道 | 现状 | 3.3.2 处置 |
|---|---|---|---|---|
| `backupPayloads` | `per-id` | 桌面 IPC `payload:*`／便携 `/api/blob` | 大块备份载荷独立成文件 | 不上传（本地专属） |
| `vecRows` | `whole` | 便携：整库 JSON 内 | 语义向量，随 U 盘携带 | **不上传**，作品可读后本机重建 |
| `kbDocs` | `whole` | 同上 | 知识库文档 | 不上传；`kbInBackup` 默认关 |
| `kbBodies` | `whole` | 同上 | 知识库正文 | 同上 |

桌面版不走 sidecar：向量与知识库放在**两个独立 IndexedDB 库**（`-vec` / `-kb`），刻意不进整库 JSON（`storeOps.ts` 头部说明）。⇒ 一个必须记住的后果：**桌面与便携的「整库」并不是同一集合**，任何以「整库 JSON 相等」为判据的同步校验在三端都站不住。

## 4. 关键发现：项目里没有独立附件通道，图片内嵌在记录中

| 事实 | 证据 | 对同步的影响 |
|---|---|---|
| 立绘存为已压缩 dataURL，直接躺在 `cardRecords.portrait` / `portrait2` | `src/lib/types.ts:206-241`，注释明确「整库就是一个 JSON、云同步载荷也是整库」 | 快照体积由图片决定，不由文本决定 |
| 图鉴主图存为 `atlasImage{dataUrl,mime,width,height,bytes}`，在 `TableRow` 顶层 | `src/lib/types.ts:248`、`src/lib/atlas/types.ts:95` | 同上；`bytes` 字段可直接用于容量估算 |
| 没有独立的图片/blob store，`/api/blob` 只服务 sidecar 的 4 个 store | `src/lib/storage/fileBackend.ts:483-523` | 规划 §5「附件按哈希同步」在首版**退化为**「记录内 dataURL 随主体一起走」 |

三个直接结论：

1. 「附件与主体构成一致版本」这件事**在首版天然成立**（同一条记录、同一个哈希），比规划里设想的附件清单简单；但**不代表**以后引入独立附件时还能成立，清单机制仍要留。
2. 规划 §13.2 的「3 秒防抖 + 最多 30 秒一次快照」是按**典型 10 MiB 项目**写的；含立绘与图鉴图的项目可能远超此值 —— 必须用真实含图项目实测，不能沿用文本项目的直觉。
3. 快照哈希必须覆盖内嵌 dataURL 原文（含 base64 大小写与换行），否则「图片被换但文本没动」会被判成无差异而漏同步。

| 形态 | 主库载体 | 大对象 | 鉴权/冲突 | 与 3.3.2 的关系 |

## 6. 结论：不能沿用「整库上传」

按本盘点，现有整库同步把下列内容一起搬走，因此**不能**直接复用为 3.3.2 的同步载荷：

1. 本地备份与备份载荷（`backups` / `backupPayloads`）—— 体积最大、且是恢复证据；
2. 在途改写载荷（`revisionPayloads`）—— 属于某台设备的中断现场；
3. 敏感配置（AI 密钥、检索密钥）—— 现有排除表已挡，但**新增键**必须走同一判据；
4. 本机专属迁移日志与个人模板库 —— 换机无意义甚至有害；
5. 全库向量与知识库 —— 可重建，且桌面根本不在整库里；
6. 其他作品 —— 用户只关联了一本，不能连带上传；
7. 回收站/历史 —— 语义上属于「账号云端」，但保留期与容量政策未定（规划 §13.4）。

⇒ 首版按规划 §6.1 走**项目级不可变快照**：只打包被选中的作品及其项目级记录，排除上表 1–5，第 6–7 按「关联范围」与「历史策略」单独定。

## 7. T1 核实结论（N1–N4 已查实）

### 7.0 先看这个：项目范围的载荷**已经存在**

`src/lib/db/projects.ts` 的 `exportProject()` 就是一份成熟的「项目级载荷」实现，字段与 `ProjectBundle` 一一对应：

- 按 `projectId` 过滤：`volumes` / `chapters` / `tableRows` / `cardRecords` / `dailyStats` / `tavernReports` / `aiRuns` / `snapshots`（走索引）；
- 按键前缀过滤并**剥掉项目前缀**：`formData`（`pid::tabId` → `tabId`）、`settings`（`pid::key` → `key`）、`customOptions`（`customOption::pid::` → `key`）；
- 出口再挡一道敏感键：`isSensitiveSettingKey()`；
- `snapshots` **只带 AI 来源的**（注释给了理由：全带会让 300 章的书备份 JSON 胀到 20MB+）；
- 参考资料按开关（`kbInBackup`，默认关）。

⇒ 3.3.2 的项目快照应当**复用这套过滤与剥离逻辑**，而不是另写一份。另写必然漂移，而漂移方向一定是「把别的作品的数据带出去」或「导入回来键前缀串台」。

### 7.1 T1-1 `trash`（原 N1）：项目级，但**不进快照**

证据：`TrashItem extends Chapter`（`db/chapters.ts:193`）⇒ 天然带 `projectId`；删项目时 `projects.ts:142` 按 `projectId` 批量清理；导出项目**刻意不带** trash（`projects.ts:561` 注释）。

结论与理由：
- 回收站是**本机**的误删兜底，跨设备价值低（另一台机器上那章本来就还在）；
- 若把 trash 随快照上传，会在云端制造一份「已删章节副本」，与墓碑语义打架；
- ⇒ 跨设备删除靠**墓碑**表达（`sync/syncTombstone.ts` 已有此机制），trash 留本机。
- 🔴 但必须补一条现在没有的东西：`ProjectBundle` **不含任何删除标记**。整项目覆盖上传时，B 端删掉的章节在 A 端会「活着回来」。首版必须为章节/卷/表格行/角色卡各带删除墓碑，否则 S07 验收过不去。

### 7.2 T1-2 `aiRuns` / `dailyStats`（原 N2）：都进快照

- `aiRuns` 已在 `ProjectBundle` 契约内（`projects.ts:225/323`），排除会造成「导出有、同步没有」的不一致；它是账本、体积小。
- `dailyStats` 记的是**每日净增量**（`db/meta.ts:41-58`，键 `pid::date`），本质不可重算 —— 排除会让换设备后《写作进度》和 AI 轨迹（`ai/trajectory.ts`）凭空少一段。体积一天一条，忽略不计。
- 唯一例外仍是 `revisionJobs`（在途任务，§1 第 11 项）：不进快照。

### 7.3 T1-3 `worlds`（原 N3）：全局，且**不是唯一的全局内容**

`db/worlds.ts` 头部写得很明确：「`worlds` 不是项目级数据 —— 世界可被多个作品引用，不建 `projectId` 索引、删项目时不清理，随整库同步/备份走」。

顺这条线还查到一个**规划里没提的同类问题**：酒馆自由模式的角色、会话、记忆、日记、问候全在**全局 meta**（键前缀 `tavern.` / `tavern.free.*`，见 `tavern/store.ts:45-52`、`tavern/script.ts:43-46`）。它们既不在项目包里，也不在任何作品名下。

⇒ 首版结论：
- 作品快照**不打包** `worlds` 与 `tavern.free.*`，避免把「跨作品资产」按某一本作品的身份搬走；
- 但必须在界面上**如实告知**：账号同步只覆盖被关联的作品，世界库与酒馆自由模式记忆仍只在本机（或另立「账号级全局库」通道）。
- 若将来做全局库通道，`worlds` 与 `tavern.*` 要一起做 —— 它们都是「同一账号、跨作品」的语义。

### 7.4 T1-4 `settingsKV`（原 N4）：键表已枚举

项目级设置（写入统一走 `setSetting()`，存储键带 `pid::` 前缀）：

| 键 | 用途 |
|---|---|
| `plotCanvas` | 剧情画布 |
| `calendars` / `calendarName` | 历法规则与名称（唯一入口 `CalendarRuleModal`） |
| `healthIgnoredIds` | 数据体检忽略项 |
| `nameFavorites` | 取名收藏 |
| `goalTotal` / `goalDeadline` / `goalDaily` | 写作目标 |
| `customSensitiveWords` | 自定义敏感词 |
| `customOption::<pid>::…` | 自定义下拉选项（人物状态等），**另一套前缀** |
| `<pid>::kbInBackup` | 知识库随包开关（默认关） |

⇒ 全部随作品走，但**导入/导出时必须剥前缀**（`exportProject` 已这么做），否则新项目 id 与旧键前缀对不上，读出来是空。

## 8. T2 体积账（已实测）：10 MiB 门槛对含图项目不成立

### 8.1 文本侧（有实测口径）

| 数据 | 实测 |
|---|---|
| `src/data/seedContent.ts`（示范项目 20 章正文） | 104,099 字符，其中汉字 77,830，UTF-8 **288,265 字节 ≈ 0.27 MiB** |
| 折合单章 | ≈ 3,900 汉字/章 |
| 外推 300 章 | ≈ 117 万汉字 ≈ **3.5 MiB** 纯文本（JSON 转义后约 +15%） |

### 8.2 图片侧（按管线硬上限推算，不是实测样本）

| 来源 | 单张上限 | 说明 |
|---|---|---|
| 立绘 `portrait` / `portrait2` | **200 KB**（512×910 WebP q0.9，超限阶梯降到 0.82/0.74） | 源码注释原话：「30 个角色 ≈ 6MB」—— 那是**单张**立绘时代的口径；现在每角色可放两张 ⇒ 60 张 ≈ **12 MiB** |
| 图鉴主图 `atlasImage` | **200 KB/张**；项目总上限 32 MiB | 🔴 32 MiB 墙**只对网页云端账号生效**，桌面/便携/游客无此限制（`atlas/quota.ts` 头部 2026-10-18 拍板） |

两个容易漏的换算：

1. **dataURL 是 base64**：压缩后 200 KB 的图，落进 JSON 约 **267 KB** 字符串（×4/3）。所以「图鉴 32 MiB 上限」对应的 JSON 占用约 **42.7 MiB**。
2. 桌面/便携没有 32 MiB 墙 ⇒ 图片侧**没有有效上界**，只受用户耐心限制。

### 8.3 实测：合成含图样本 45.69 MiB，图片占 68.4%

样本口径（`.workbuddy/tmp/proto-p0-t5/measure-project-size.mjs`，结果 `result-n5.json`）：300 章 × 3,900 字真实中文正文（取自 `seedContent.ts`）＋ 3 卷 ＋ 812 表格行（其中 100 行带图鉴主图）＋ 30 角色卡各 2 张立绘 ＋ 18 份 AI 快照 ＋ 120 天统计。图片用**与压缩管线等长**的 200 KB 占位（长度真实，可压缩性最差）。

| 口径 | 字节 | 相对 10 MiB 门槛 |
|---|---|---|
| 项目快照（内嵌图片，现状方案） | **45.69 MiB**（gzip 32.82） | **4.57×** ❌ |
| 其中图片原始字节 | 31.25 MiB（占 68.4%） | — |
| 图片改内容哈希引用后（D8 方案） | **4.02 MiB**（gzip 1.40） | **0.40×** ✅ |

分段占用（内嵌方案）：

| store | 体积 | 说明 |
|---|---|---|
| `tableRows` | 26.44 MiB | 图鉴主图 |
| `cardRecords` | 15.76 MiB | 立绘（每人两张） |
| `chapters` | 3.28 MiB | 30 万字正文 |
| `snapshots` | 0.20 MiB | 只含 AI 快照（与 `exportProject` 口径一致） |
| 其余 | < 0.02 MiB | — |

结论（两条都很硬）：

1. **gzip 救不了**：45.69 → 32.82 MiB，只省 28%，因为图片本身已压缩。
2. **图片引用化把快照压到 4.02 MiB**，比门槛低 60%，且后续「只改文字」的提交只需传这 4 MiB（gzip 1.4 MiB）。⇒ **D8（图片抽内容哈希 blob）不是优化，是让 10 MiB / 30 秒门槛成立的前提**。

## 10. T3 结论：向量/知识库的等价性只在「导出/导入」这一层成立

| 维度 | 桌面安装版 | 便携版 | 网页云端 |
|---|---|---|---|
| 主库 | IndexedDB `youth-fantasy-engine`（v14） | 整库 JSON（`fileVersion=2`） | 服务器 `userdata` 整库 JSON |
| 语义向量 | 独立 IDB **`youth-fantasy-engine-vec`**（v1，`semantic/store.ts:129`） | 整库内 `vecRows`（`whole` 布局，`vec` 转 base64） | 待核 |
| 知识库 | 独立 IDB **`youth-fantasy-engine-kb`**（`search/knowledgeBase.ts:62`） | 整库内 `kbDocs` / `kbBodies`（`whole`） | 待核 |
| 是否进整库 JSON | ❌ 不进（`storeOps.ts` 头部明说刻意独立） | ✅ 进（U 盘必须自包含） | 取决于 blobs |

原 N6 的答案：**内容等价、物理位置不等价**。等价性由「导出/导入」的转换层保证（`portableVecKb.ts` 负责 base64 与拆并），而不是由「整库 JSON 相同」保证。

三条直接后果：

1. 任何「比对整库 JSON 是否一致」的同步校验，在桌面与便携之间**必然误判**（桌面缺这三个 store）。
2. 首版不同步向量与知识库 ⇒ 换机后（含桌面→桌面）语义检索需重建。这不是退化，是既有行为（桌面整库导出本来也不带它们）；但界面必须说清，否则用户会以为「同步完了检索却没结果」是 bug。
3. 桌面与便携的「项目大小」统计口径也会差一块（便携把向量算进整库，桌面不算）。

## 11. T5 结论：旧客户端写入路径只有 4 条，但其中 2 条无版本保护

服务端可写端点全清单（`server/index.mjs` 471–585 行）：

| # | 路径 | 方法 | 保护 | 门禁要点 |
|---|---|---|---|---|
| 1 | `/api/data` | PUT / POST | 登录 + `kind==='portable-data'` + `If-Match` ETag + 配额 | **整库覆盖写**，迁移后必须按数据世代拒绝 |
| 2 | `/api/blob?store&id` | PUT / POST | 登录 + store 白名单 | 🔴 **无 ETag、无版本** ⇒ 并发写是「最后到达者赢」，静默覆盖 |
| 3 | `/api/blob?store&id` | DELETE | 登录 + store 白名单 | 🔴 同样无版本；删除与并发写可互相踩 |
| 4 | `/api/auth/*` | POST | — | 会话创建口；旧客户端可登录后立刻走 1–3，故门禁不能只挡新协议 |

补充事实（供 P2 设计参考）：

- blob store 白名单＝`backupPayloads` / `vecRows` / `kbDocs` / `kbBodies`（`server/lib/userdata.mjs:25`）—— 只有这 4 个，**没有通用文件上传口**，这是好事。
- `DEFAULT_QUOTA = 200 MiB`，可用 `YFE_QUOTA` 覆盖（`server/lib/config.mjs:18`）；`MAX_BODY = 配额 + 8 MiB`（同文件 25 行）。
- 🔴 `readBody()` 把整个请求体**缓冲在内存**（`server/lib/http.mjs:27-45`）。服务器是 2C/1.7 GB + 2 GB swap（`server/provision-swap.sh`）。
  实测（`.workbuddy/tmp/proto-p0-t6`，Node v22.22.2）：40.1 MiB 载荷 → RSS 峰值 +220.4 MiB（**5.49×**）；10.1 MiB → +56.5 MiB（5.61×）。按 1.2 GB 安全余量，**5 个并发 40 MiB 上传就触顶**。⇒ P2 必须流式落盘或把单对象压到 8 MiB，不能假设「配额内就能安全传」。

原 N8 的答案：路径已穷举为 4 条，其中 1 条有 ETag、2 条没有、1 条是会话入口。旧版门禁要同时处理「已登录的旧客户端」和「无版本的 blob 写」。
