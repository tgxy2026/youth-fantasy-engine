## 2. 关键发现：「章有、检查点无」在文件后端结构上不存在

桌面与便携都把**全部 store 放在同一个整库 JSON**：

- 写入路径：`ops 变更 → 800ms 防抖 → tmp 文件 → rename 原子替换`（`src/lib/storage/fileBackend.ts`、`electron/main.cjs`）；
- 创意连写的每章检查点：`onChapterSaved → onCheckpoint → persistNow(meta) → flushCreativeCheckpoint()`，
  而 `flushCreativeCheckpoint` 会**强制把整库落盘**（`src/lib/creative/serialPersist.ts`）。

因此磁盘上只可能出现两种状态：**旧快照（章节与检查点都旧）** 或 **新快照（两者都新）**；
`IndexedDB` 那种「章节先落、检查点后落」的分库窗口在整库 JSON 上不成立。

本机实测 10 次强杀，**每次都满足 `chapters.length === resume.doneChapters`**，没有一次出现两者不一致。

🔴 这不代表「不会丢数据」：最坏情况是**最后一章整体丢失**（旧快照），恢复时重写该章。
这是既有 R-1 降级语义（「最坏重写最后一章」），本轮未改变它，也没有观测到重复建章。

## 6. 复现注意

- 桌面跑法必须清环境变量：`env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS`，否则 `_electron.launch` 直接失败。
- 强杀后 Chromium 会在 profile 留下 `SingletonLock` 等文件；脚本已清理，否则下一次启动报 `Target closed`。
- 桌面数据文件在 `--user-data-dir` 下（会覆盖 `app.getPath('userData')`），不是 `appData/<name>/`。
- 便携服务把整库读进内存：**改完数据文件必须重启服务**，否则新页面仍读到旧内存。
