## 0. 一句话结论

| 议题 | 结论 |
|---|---|
| **① 同一对实体多条关系** | **可行，且属「稍作改动」**：把判重键从 `(A,B)` 扩成 `(A,B,关系类型)`，图谱补「平行边分离 + 独立着色」。**手动加行本来就不判重**，受限的只是 AI 侧。 |
| **② 自定义关系类型的画布配色** | 现有「名称哈希 → 色板」会**撞色**（16 色板 + 生日悖论，5 个以上自定义类型几乎必撞）。改为「按本图出现集合**确定性分配**」，保证同图内**互不同色**；两图收敛到**同一色彩模块**。 |
| **③ 等比时间轴被拉长** | 采用「**空档封顶 + 断裂符**」（axis break）：密集段保持等比、稀疏段压缩并**显式标注**被压缩的真实跨度；自动检测长空档并提示。 |

## 1. 现状勘察（事实，非推测）

### 1.1 两张关系表的身份与判重

| 环节 | 代码位置 | 现在怎么认「同一条」 | 后果 |
|---|---|---|---|
| **手动新增行** | `useTableSheetModel.addRow`（`:393`） | **完全不判重**，`uid()` 建行直接落库 | 手输可加任意多行，含完全重复 |
| **AI 整理** | `aiScope.ORGANIZE_KEYS`（`:120`）= `relations:['人物A','人物B']`、`faction-rels:['势力A','势力B']` | `(A,B)` 值组合 | 同一对只产出**一条**，类型不同也被吃掉 |
| **无序对比较** | `aiScope.isUnorderedPairTab`（`:143`） | `A-B` 与 `B-A` **同一条** | 反向也判重 |
| **拆书 / 写入项目** | `bookbreak/relations.ts`（`:141`）`dedupKeys:[first,second]` → `flow/commit.ts`（`:97`） | 同上 | 同上 |
| **表格导入** | `tableIO.ts`（`:287`）→ `organizeKeyColumns` | 同上 | 同上 |

> 🔴 **关键结论**：需求「支持在同一对之间加一种以上关系」在**手动侧已经成立**（能加），在 **AI 侧被 `(A,B)` 判重挡死**。所以改动重心 = **放开 AI 侧的判重键**，而**不是**改数据格式。

### 1.2 图谱侧的边绘制

| 事实 | 代码 | 影响 |
|---|---|---|
| 一条表行 = 一条边 | `RelationGraph.tsx:144` / `FactionGraph.tsx:105` | 同一对多条行 = 多条边 |
| 弯曲方向由 `A→B` 顺序决定 | `graphGrouping.curvedEdge`（法向 `(-dy,dx)`） | `A-B` 与 `B-A` **自然分居两侧**；但**同方向**的两条边**完全重叠** |
| 边色 = 关系类型 | `edgeColor` / `relColor`（各自一套色板 + 哈希兜底） | 见 §3 撞色问题 |
| 边线型 = 关系性质 | `edgeDash`（敌对/恩怨虚线、竞争点线） | 第二编码，可复用 |

### 1.3 时间线的间距

| 事实 | 代码 | 影响 |
|---|---|---|
| 相邻时间点**等距** `SLOT_W=240` | `HistoryTimeline.tsx:65` / `StoryTimeline.tsx:65` | 长空档不拉长（现有优点） |
| 相邻两点间**按时间比例插值** | `storyDate.interpolateX`（`:197`） | 局部区间标得准 |
| 设计意图 | `interpolateX` 注释原文 | 「三千年 vs 三天」在纯比例轴上会把晚近挤成一团 —— **这正是当初不做等比的原因** |

> 🔴 「等比」的价值（看清真实时间跨度）与它的代价（长空档被拉爆）是**同一个机制的两面**，必须在等比模式下正面解决空档。

## 2. 议题①：同一对实体多条关系

### 2.1 判重键扩展（核心改动）

```
relations       判重列：['人物A','人物B']       →  ['人物A','人物B','关系类型']
faction-rels    判重列：['势力A','势力B']       →  ['势力A','势力B','关系类型']
```

落点共 **3 处**（口径单一源，改一处即可，其余复用）：

| 文件 | 改什么 |
|---|---|
| `src/lib/aiScope.ts` | `ORGANIZE_KEYS` 两条各加 `'关系类型'` |
| `src/lib/bookbreak/relations.ts` | `dedupKeys` 追加 `keyColsOf(tab)` 之后的类型列 |
| 其余（`flow/commit.ts` / `tableIO.ts` / `organizeRows.ts`） | **零改动**（都调 `organizeKeyColumns`） |

**兼容性**：老数据行本就是 `(A,B,类型)`，只是判重口径放宽 ⇒ **不会凭空多出任何行**。风险仅一处：过去「同对同类型」的重复行若手动存在，现在仍各自独立（本就可删，无回归）。

### 2.2 「视角 / 方向」——待决策 D1

需求原文提到「**A 的视角里 B 跟他的关系，可能不同于 B 的视角里 A 跟他的关系**」。有两种建模：

#### 方案 甲 · 无序对 + 类型（推荐，改动最小）
- 身份 = `{A,B}` 无序 + 类型 ⇒ 同一对可并存 **盟友 / 宿敌 / 提防 …** 多种。
- **「A 视 B」与「B 视 A」**：用户写两行，**类型不同**时都能存活；图谱按 A/B 顺序把它们画到**弧线两侧**，视觉上已能读出不对称。
- **不区分**「同一类型但视角相反」（例：`A视B为盟友` 与 `B视A为盟友`）—— 而这种情况在语义上**本就是同一种双向关系**，判重吃掉反而正确。
- 老数据零风险；不新增列。

#### 方案 乙 · 有向对 + 类型（能力最全，改动较大）
- 身份 = `A→B` 有序 + 类型 ⇒ 连「同类型、不同视角」都能并存；渲染加**箭头**表明主体。
- 代价：需要把「人物A = 主体视角方」的语义写进列说明 / 表头 / AI 提示词；`isUnorderedPairTab` 的去重语义要改成有序（波及 4 处判重 + AI 提示词），老库里若有「A-B 与 B-A 同义」的手输行会被视作两条。

> **可可建议：先取甲。** 甲已覆盖主人描述的、实际会遇到的不对称场景（不对称 ⇒ 类型必然不同），且「老数据零破坏 + 不新增列 + 只动 1 处键」。若日后确需「同类型双向」，再补一列「方向」升级为乙，届时是**叠加**不是返工。

### 2.3 渲染：平行边分离（两图通用）

新增公共纯函数（进 `graphGrouping.ts`，可单测）：

```
edgeCurveRatios(k: number): number[]
// k=1 → [0.16]（保持现在的轻微弧形）
// k=2 → [-0.20, +0.20]
// k=3 → [-0.26, 0, +0.26]
// k>=4 → 在 [-0.30,+0.30] 上等分
```

渲染时：
1. 边按**无序对**分组（`pairKey = sort(a,b).join()`）；
2. 组内按 `(类型, id)` **确定排序**（同一份数据每次渲染弧线位置一致 —— 与「确定性布局」红线同源）；
3. 第 i 条取 `edgeCurveRatios(k)[i]` 作 `curveRatio` ⇒ 平行边**扇形铺开**；
4. 标签取该边自己的 `curveMidpoint` ⇒ 自动错位，不再叠字；
5. `edgeDash` 线型照旧。

**顺带修正**：节点度数若继续按「行数」累加，会给「一对多关系」的人物虚增权重 ⇒ 改按**不同邻居数**计（`degree = 邻居集合大小`），更贴近「这人交际面广不广」。

### 2.4 表格 / 其它消费方

| 消费方 | 是否受影响 | 处理 |
|---|---|---|
| `TableRelationGroups`（按人分文件夹） | 否 | 同对的 N 条关系**都列在该人卡片下**，天然正确（见 §1.1 分组代码 `:562`） |
| `useTableSheetModel` 分组（`:555`） | 否 | 同上 |
| `search.ts` / `SettingSearch` / `settingLedger` / `continuityCheck` | 否 | 只按 A/B 列取值，与条数无关 |
| AI 整理提示词 `organizeHint('relations')` | **文案微调** | 从「已有关系不会重复生成」→「同一对可登记多种关系（按类型区分），**同对同类型**才不重复生成」 |

## 3. 议题②：自定义关系类型的画布配色

### 3.1 现状问题（可复现）

```
edgeColor(t): 内置 8 类走精调色；否则 h = hash(t) % 16 取 EXTRA_PALETTE
```
- **撞色**：16 色板，**5 个以上自定义类型就大概率有两两同色**（生日悖论）。
- **与内置撞**：自定义色可能恰好等于某内置类型的颜色 ⇒ 图上两条边同色不同义。
- **两图各一套**：`RelationGraph`（8 内置 + 16 扩展）与 `FactionGraph`（5 内置 + 12 扩展）**彼此独立**，同一「敌对」在两张图里颜色不同，视觉语言不统一。

### 3.2 方案：确定性分配（保证同图内不撞色）

新建 `src/lib/relationColors.ts`（纯函数，可单测）：

```
allocateTypeColors(types: string[], preset: Record<string,string>, palette: string[])
  → Map<string,string>
```
规则：
1. **内置类型**取精调色，并**占用**该色槽；
2. **自定义类型**按「本图出现顺序」（= 行的稳定序）依次取**未被占用**的色板槽；
3. 色板扩容至 ~20 色、色相均匀分布（覆盖红橙黄绿青蓝紫粉棕灰）；
4. 色板用尽才回绕（并有测试兜底：回绕时相邻仍异色）。

**代价（需主知晓）**：某自定义类型的颜色会**随「同图里还有哪些类型」微调**。可接受 —— 换来的是「同图内**绝不两两撞色**」，而同一份数据每次打开顺序稳定 ⇒ **同图内颜色稳定**。
> 若主人更看重「全局绝对固定」（不随同图变化），可退回哈希法，但**必须接受偶发撞色**（D2 二选一）。

### 3.3 顺带统一

- `RelationGraph` 的 `TYPE_COLORS` 与 `FactionGraph` 的 `REL_COLORS` 收敛到同一模块的同名 `PRESET`（两表类型词表不同，各保留自己的内置表，但**扩展色板与分配算法共用**）。
- 图例徽标「自定义」保留；再加一档：**同图内颜色实际撞车时**（极端情况）自动打散。

## 4. 议题③：等比时间轴「防拉长」

### 4.1 问题形式化

等比轴 `x = f(时间)`，线性比例。当 `最大空档 / 中位空档` 很大（例：主线密集在 1 年，中间夹一段「三千年前」的传说事件），整条轴被这一个空档撑到几十倍长 —— 密集段挤成一坨，正是 §1.3 里 `interpolateX` 注释所担心的「三千年 vs 三天」。

### 4.2 方案（推荐）：空档封顶 + 断裂符（axis break）

统计学制图的标准解，**诚实且可读**：

1. 计算相邻不同时间键之间的**真实间隔** `gaps[]`；
2. 取 `cap = max(median(gaps) × K, minPositiveGap)`，`K` 初定 **6**（可配置）；
3. 渲染位置 = **累计「封顶后的间隔」** 再整体缩放到目标宽度；
4. 被压缩的空档（`gap > cap`）在轴上画 **断裂符 ⟋⟋**（双斜线），并在该处标注**真实跨度**（如「≈ 3000 年」）；
5. **自动检测 + 提示**：若 `maxGap / medianGap > 8`，横轴顶部出提示条「已压缩 N 处超长空档」，并给一个「按真实比例查看」的切换（真等比、可横向滚动）。

**优点**：密集段严格等比（该看清的看清）；稀疏段压缩但**明示**（不撒谎）；一个开关回到真等比。

### 4.3 备选（供对比，不推荐单用）

| 方案 | 做法 | 硬伤 |
|---|---|---|
| **乙 · 对数/根号压缩** | `x = sign·log(1+|Δt|)` | 违背「等比」的本意（等时间不再等距），且负/零年处理啰嗦 |
| **丙 · 迷你导航图** | 真等比 + 整体缩略图 + 视窗拖动 | 不解决「整体很长」，只是把导航成本转给用户 |
| **丁 · 双模式并列** | 等距/等比两个 Tab，等比就是纯比例 | 纯比例必然拉爆 ⇒ 不符合要求 |

### 4.4 落地骨架

- 新增纯函数入 `storyDate.ts`：`cappedPositions(keys: number[], opts) → { x: number[]; breaks: {afterIndex, realSpan}[] }`（**可单测**，含「无空档退化 = 纯等比」「单空档」「全同键」等用例）。
- 两个时间线组件加「间距」切换（等距 / 等比），**默认仍等距**（零回归）；等比走上述封顶算法。
- 断裂符 + 跨度标注 + 「真实比例查看」开关。
- ⚠️ 前置：补**跨历法**单测（`calValue*1e10 + tk` 权重在不同历法混排时的单调性），这是等比模式正确性的地基。

## 5. 改动范围与风险

| 层 | 文件 | 改法 |
|---|---|---|
| 判重键 | `aiScope.ts`、`bookbreak/relations.ts` | 加 `关系类型`（+ 提示词文案） |
| 配色 | 🆕 `relationColors.ts`、`RelationGraph.tsx`、`FactionGraph.tsx` | 抽公共分配算法 |
| 平行边 | `graphGrouping.ts`（新增 `edgeCurveRatios` + 分组）、两图渲染 | 扇形铺开 |
| 时间轴等比 | `storyDate.ts`（新增 `cappedPositions`）、两时间线组件 | 加间距切换 + 断裂符 |
| 测试 | 🆕 `tests/relationMulti.test.ts`、`tests/timelineScale.test.ts` | 判重/分配/封顶 |
| 文案 | `TableSheet.tsx` 帮助、`schema.ts` 表 description/tips、`aiScope.organizeHint` | 口径同步 |

**风险**：
- 🟡 判重键放宽 → AI 整理可能产出更多行（**这是需求本身**），需在预览面板文案里讲清「同对同类型不重复」。
- 🟡 等比轴改动 `storyDate` 核心函数，**必须**先补跨历法单测再动（红线）。
- 🟢 平行边分离是纯渲染增量，可回退。

**验收（沿用四关 + 实机）**：`tsc` / `eslint` / `run-all`（现 130 入口）/ `vite build` + 真 Chromium 实机（含：手输两条同对关系 → 图上看两条不同色弧线；AI 整理产出同对多类型；等比轴长空档显示断裂符）。

## 附：为什么改 3 处就够（口径单一源的证明）

```
aiScope.ORGANIZE_KEYS ──┐
                        ├─→ organizeKeyColumns(tab) ──┬─→ tableIO 导入判重
isUnorderedPairTab ─────┘                              └─→ organizeRows AI 整理判重
bookbreak/relations.ts 的 dedupKeys ──→ flow/commit.ts 写入项目判重
```
判重列的**唯一真源**是 `aiScope.ORGANIZE_KEYS`；`bookbreak` 那条是拆书链路的显式副本（须同步改）。其余全部复用，不重复实现 —— 与本项目「候选值注入只有一处真源」的既有纪律一致。
