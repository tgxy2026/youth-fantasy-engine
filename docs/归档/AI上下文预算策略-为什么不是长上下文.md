# AI 上下文预算策略：我们为什么用 1~2 万字符，而不是模型的 256K

> 缘起：老大问 —— 现在很多模型号称支持几十万字上下文，为什么项目里各功能的上下文预算只有一两万字符？
> 结论先行：**不是我们保守，而是三个独立的硬约束；其中第一条（显存）在本地部署下就是物理天花板。**

---

## 一、先把三个数字摆出来

| 项 | 值 |
|---|---|
| 本地模型标称上下文 | **262144**（256K tokens） |
| 项目实际使用的 `numCtx` | **32768**（酒馆模式可配；主流程走 Ollama 全局设置） |
| 各功能发给模型的正文字符预算 | **2000 ~ 12000 字符**（≈1.3K ~ 8K tokens） |

差距 100 倍以上。你的疑问完全合理。但把三个约束摊开看，就知道这不是"没利用上"，而是"用不了"。

---

## 二、约束一：显存 —— 本地部署的物理天花板（决定性）

KV cache（键值缓存）的显存占用随上下文长度**线性增长**。本机模型实测参数：**65 层 / 4 个 KV 头 / head_dim 256**。

| 上下文 | KV cache (FP16) | 加上模型本身 23GB | 单卡 5090（32GB） |
|---|---|---|---|
| 8K | 2.2 GB | 25.2 GB | ✅ 余量充足 |
| **32K** | **8.7 GB** | **31.7 GB** | ✅ **刚好塞下 —— 这就是 `numCtx=32768` 的由来** |
| 64K | 17.4 GB | 40.4 GB | ❌ 溢出 |
| 128K | 34.9 GB | 57.9 GB | ❌ 远超 |
| **256K（模型标称）** | **69.8 GB** | **92.8 GB** | ❌ 不可能 |

**结论**：在单张 5090 上，这个 27B 模型的**物理可用上下文上限就是 32K 左右**。
"标称 256K"是模型**架构容量**（要靠多卡或大显存机器才跑得起来），不是本机的可运行配置。

（理论上可以把 KV cache offload 到你的 64GB 内存 —— Ollama 确实会这么做 —— 但每 token 都要过 PCIe，速度掉一个量级。对"伴写要停笔即出"这种场景不可接受。）

---

## 三、约束二：有效上下文 ≠ 标称上下文（业界共识，不是我们保守）

来自 RULER（NVIDIA）/ NIAH-2 / MRCR v2 / FLenQA / Chroma 等基准的实证结论：

1. **有效上下文通常只有标称的 30~65%**；而**多针检索**（同时整合多个信息点）比单针检索低 **15~40 个百分点** —— 单针成绩严重高估实际能力，因为生产场景都是"多针"。
2. ⭐ **"长度本身就是税"**（Levy, Jacoby & Goldberg，ACL 2024 杰出论文，FLenQA 基准）：
   固定推理逻辑、只增加**无关填充** —— 从 250 token 涨到 **3000 token**，准确率就从 **0.92 掉到 0.68**。
   **注意是三千，不是三十万** —— 远低于任何模型的标称窗口。
3. **Context rot（上下文腐烂）**：Chroma 测了 18 个模型，**全部**随输入变长而质量下降；其中"纯长度"这一项就占约 **7.9% 的损耗底线**（还没算无关内容的干扰）。
4. **Lost in the middle**：信息放在上下文中段时召回率明显下降（U 形曲线：首尾好、中间差）—— 所以"重要的往后塞"也不可靠，得**结构化管理**。

⚠️ 对照我们的数字：**12000 字符 ≈ 8000 tokens，早已进入退化区间**。继续往上堆，边际收益是负的。

---

## 四、约束三：延迟与成本

**延迟**：prefill 的计算量随上下文显著增长。我们踩过一次真实的坑 —— 27B 要同时扛"加载进显存 + prefill 一万二千字 + 出首个 token"，**被 180 秒总超时掐死**。这就是红线"自己驱动 `runAutoContinue` 必须传 `onBodyToken`（开流式）"的由来：流式让首字一出来就清掉总超时。

**成本**：云 API 按 token 计费，且每轮对话都要重传历史 → 累计成本随轮次增长（O(n²)）。另外 Anthropic / Google 对超过 200K 的请求**按 2 倍单价计费**，而且是**请求内全部 token 都翻倍** —— 是个价格悬崖。

---

## 五、所以我们的策略是"精准选材"，不是"堆长度"

| 机制 | 作用 |
|---|---|
| `PRIORITY` 表级顺序 | 决定"先给谁"（世界/主角 → 结构性大纲 → 运营台账） |
| 「保密等级」行级排序 | 决定"同一张表里谁先给"（S→A→B→C） |
| `AUTHOR_SIDE_TABS` / `AUTHOR_SIDE_FIELDS` | 防剧透，同时省 token |
| `ROW_CAP` / `CELL_CAP`（+ 长文本字段 600） | 防单表/单字段吃光预算 |
| 分功能预算档 | 按任务"需要多少"给，而不是"能给多少" |
| `dropped` 声明 | 装不下的**如实告知模型**，而非静默丢弃 |
| `buildInlineBriefing`（伴写专用） | 只带 4 类最相关设定、关掉章节目录 |

一句话：**在 8000 token 里放进最相关的 8000 token，效果优于在 200K 里放进 20 万 token 的混合内容。**

## 六、但确实有"该用长上下文"的场景 —— 按需扩容

| 场景 | 频率 | 策略 |
|---|---|---|
| 伴写 | 极高（每次停笔） | **保持极小**（前文 2000 + 设定 900）—— 延迟就是手感 |
| 逐章续写 | 中 | 保持 12000（设定 + 上章结尾 1200 字 + 最近 3 章摘要） |
| **一键拆书（全书抽取）** | 低（一次性） | ✅ **这才是长上下文的主场**：一次性喂大批章节，慢一点无妨 |
| **全书一致性审计** | 低（一次性） | ✅ 同上 |
| 深度校对 / 全书诊断 | 低 | 可考虑"深度模式" |

### 当前各功能预算档位（实测值）

| 功能 | 预算（字符） |
|---|---|
| 伴写 · 设定切片 | 900（+ 前文 2000） |
| 灵感工具 | 3000 |
| AI 助手 | 4000 |
| 编辑器弹窗 | 6000 |
| 检查工具 / 颉文姬 | 8000 |
| AI 整理 | 9000 |
| 一致性校验 / 写作面板 / 默认 | 12000 |

### 可考虑的改进（待老大拍板）

1. **给"低频一次性大任务"加「深度模式」开关** —— 预算提到 24000~32000。代价是更慢，且要先确认显存余量（32K 时已占 31.7/32GB，很紧张）。
2. ✅ **按模型能力自适应** —— **已落地**，见 §6.1；各参数推荐值一并跟着模型走，见 §6.2。
3. **超长任务改"分章批处理 + 结果汇总"** —— 比一次性塞满更稳，也符合拆书的分期设计。

### 6.1 已落地：按模型能力自适应（2026-09-17）

**先讲一个之前没人注意到的缺口**：

| 参数 | 是什么 | 对云端模型 |
|---|---|---|
| `numCtx: 32768` | Ollama 专有字段（`num_ctx`）—— 本地 KV cache 分配 | **完全无效**（会被 OpenAI 兼容端的采样白名单丢弃） |
| `contextBudget: 24000` | 字符预算（设定 + 记忆 + 对话历史） | **有效**，但它原本是**按 numCtx 32768 反推出来的** |

也就是说：**接上云端 256K 窗口的模型，用户仍被"本地显存算出来的数"锁死**，而且界面上毫无提示。

**修正**（`src/lib/modelCapacity.ts` + 酒馆控制面板）：

1. **区分本地 / 云端**：`type==='ollama'` 或 `local===true` → 本地；其余 → 云端。
2. **本地绝不放宽**：numCtx 是显存安全阀，不随模型标称值放大 —— 标称 256K 而单卡跑不到，放大了只会崩。
3. **云端按「窗口 × 有效系数」**：
   - 窗口来源优先级：用户手填 `provider.contextWindow` → 内置预设识别 → 保守兜底 32768
   - 有效系数 **0.4**（依据：RULER 实测有效上下文仅标称 30~65%，且酒馆是典型"多针"场景）
   - 建议预算 = 窗口 × 0.4 − 回复预留 8192
4. **界面如实告知**：云端时把 numCtx 的说明换成"此参数对云端无效"，并给出按窗口算出的建议预算。

**内置预设**（只收录能确认的）：Qwen3.5/3.6 → 256K · Qwen3 → 128K · DeepSeek-V3 → 128K · DeepSeek-R1 → 96K · GLM-4.5/4.6 → 200K · Kimi-K2 → 256K · GPT-4.1 → 1M · GPT-4o → 128K · Claude → 200K · Gemini → 1M。认不出就走保守兜底，并**如实标注"未识别、可手填"**（不假装知道）。

**实测**（接硅基流动 `Qwen/Qwen3.5-35B-A3B`，真 Chromium 驱动）：

| 项 | 值 |
|---|---|
| 识别窗口 | 262144 |
| 建议预算 | **96665 字符**（本地默认 24000 → **解锁约 4 倍**） |
| numCtx 提示 | 已改为"只对本地生效，设了也不生效" |
| 断言 | 9/9 全过 |

⚠️ **成本提醒**：云端按 token 计费，而酒馆是**多轮**场景（每轮都要重发历史）。预算从 24000 提到 96665，每轮输入 token 约翻 4 倍 —— 请按你所用平台的单价自行评估，建议先在一次对话里试，不要直接全线放开。

### 6.2 已落地：推荐值跟着模型走（2026-09-17 · 本轮）

§6.1 只解决了「上下文预算」**一项**。但老大指出：面板上还有一批数值同样是按本地设备定的 ——
「上下文窗口长度」「记忆软上限 / 硬上限 / 长期摘要上限 / 日记保留」的取值范围与推荐，
全都出自"本地 5090 + 27B q6_K"这一套前提。换个模型，用户没有任何依据知道该调到多少。

#### 关键洞察：这些数是一条链，不是五个孤岛

```
当前模型（窗口大小）
   ↓  窗口 × 有效系数 0.4 − 回复预留
上下文预算 B
   ↓  按出厂配比缩放（24000 → 软 2000 / 硬 3000 / 长期 500 / 日记 7）
记忆档四项
```

所以「记忆档跟着模型变」**不需要单独的模型识别逻辑** —— 跟着**预算**走即可，而预算已经跟着模型走。
副产品：**手工把预算改小，记忆推荐会同步收紧**（不是只有"放大"一条路）。

#### 配比为什么是这几个数

直接以**出厂值反推**，不另拍一套（出厂值是当初在本地 27B 上调好的，换模型只该改"总量"，内在配比不该漂）：

| 项 | 比例 | 依据 |
|---|---|---|
| 记忆硬上限 | 预算 × 12.5% | 24000 → 3000（出厂） |
| 记忆软上限 | 预算 × 8.3% | 24000 → 2000（出厂） |
| 长期摘要上限 | 硬上限 ÷ 6 | 3000 → 500（出厂） |
| 日记保留 | `round(7 × √(预算 ÷ 24000))` | **开方** —— 它数的是"生活痕迹几条"，与窗口大小相关性弱；线性放大会让云端模型存下几十条日记、反过来挤占对话历史 |

三项记忆上限**线性**缩放，日记保留**开方**缩放。推出来的值一律对齐输入框步长，并 clamp 到静态范围
（`hardLimit` 先算，软上限以它为顶 —— 软上限高于硬上限等于没有上限）。

#### 第二件事：输入框的上限也是按本地定的

`contextBudget` 的静态上限是 **100000**。接 1M 窗口的模型时建议值是 41 万 —— **根本填不进去**，
输入框会把它默默夹回 100000，界面上没有任何提示。

新增 `scaleGuide(guide, suggested)`：按需把上限抬到 `max(静态上限, 建议值 × 1.5)`。
抬法刻意保守 —— **只延长最后一段的上界**，不动 min/step、不动任何分段边界、不动那个唯一的推荐段，
于是 `paramGuide` 的三条不变量（分段首尾相接 / 完整覆盖 [min,max] / 恰好一个推荐段）仍然成立。
**本地、或建议值没超静态上限时原样返回同一对象**（有单测锁住"不改行为"）。

#### 界面

- **模型能力条**（通用设置顶部，见截图）：一行摘要 + 一段人话解释 + **「采用推荐值（N）」** 一键写入六项
- **每项标题右侧**多一个「建议 N」徽标：与当前值不同 → 琥珀色 `↺`（可点采用）；相同 → 灰字 `✓`
- 云端时「上下文窗口长度」**不给推荐值** —— `num_ctx` 对云端无效，瞎推就是误导

#### 实测（真 Chromium 驱动 dev server · **46/46 全过**）

| 场景 | 能力条摘要 | 预算建议 | 记忆档（软/硬/长期/日记） | 预算输入框上限 |
|---|---|---|---|---|
| 本地 Ollama 32768 | `本地 Ollama · 窗口 32768 词元 · 预算 24000 字` | 24000（不擅改用户值） | 2000 / 3000 / 500 / 7 | 100000（不动） |
| 云端 Qwen3.5-35B（256K） | `云端 · 识别为 Qwen3.5/3.6 系列（256K） · 窗口 262144 词元 · 建议预算 96665 字（约占窗口 37%）` | **96665** | **8100 / 12100 / 2000 / 14** | **144998**（动态放宽） |

切模型**不需要刷新页面**，六项推荐值同时换一套；点「采用推荐值」后按钮变「已是推荐值」，
点保存后用 `getTavernSettings()` 实读确认已落库。把预算手工改回 24000，记忆四项推荐同步回落到出厂档 ——
这条"预算 → 记忆档"的传导链有独立断言（⚠️ 首版断言曾写成"切回本地就回到出厂档"，是**错的**：
记忆档跟预算走、不跟本地/云端走，产品行为一直是对的）。

### 6.3 已落地：模型配置页可手填窗口（2026-09-17 晚）

§6.1 的窗口识别靠**内置预设表**（正则匹配模型名）。认不出的模型只能吃保守兜底 32768 ——
对自建 / 冷门模型，这会把预算压到 1.2 万，白白浪费窗口。所以补上**手填入口**。

- **入口**：「灵感工具 → 灵感启发 → 模型配置 → 编辑」里的「上下文窗口（tokens）· 选填」
- **实时提示**（`lookupWindow()`，与酒馆面板共用**同一份**预设表，不会两处说法不一）：

| 情况 | 界面提示 |
|---|---|
| 留空 + 能识别 | `留空 = 按模型名识别为 262144 tokens（Qwen3.5/3.6 系列（256K））。识别得不对就手填覆盖。` |
| 留空 + 认不出 | `未识别到该模型名 —— 留空会按保守值 32768 tokens 估算，建议手填真实值。` |
| 已手填 | `已手填 500000 tokens：酒馆控制面板会按它算上下文预算与记忆档的建议值。` |
| **本地模型** | 输入框**禁用**：`本地部署不读这一项 —— 本地窗口由显存决定，请在酒馆控制面板调「上下文窗口长度（num_ctx）」。` |

- 反向也通了：酒馆面板**认不出模型**时（`windowSource === 'fallback'`）会指向这个入口。

**为什么本地要"禁用"而不是"隐藏"**：`num_ctx` 由显存决定，这一项对本地**完全无效**。
留着禁用 + 说明原因，比让字段凭空消失更少困惑 —— 用户知道"有这个东西、以及为什么用不了"。

#### 实测（真 Chromium · **23/23 全过**，含端到端）

| 断言组 | 关键结论 |
|---|---|
| 字段与提示 | 未识别 → 如实说按 32768 兜底并建议手填；**不假装知道**（不提任何具体模型系列） |
| 可识别 | 显示 `识别为 262144 tokens（Qwen3.5/3.6 系列（256K））`，字段仍可填（允许覆盖） |
| 本地 | 输入框 disabled + 说明指向酒馆面板的 num_ctx |
| **端到端** | 手填 500000 → 保存 → 酒馆面板能力条变成 `云端 · 你填写的窗口 · 窗口 500000 词元 · 建议预算 191808 字（约占窗口 38%）`，记忆档同步重算（日记保留 7 → **20**） |

端到端那一条是关键：它证明配置页填的数**真的被 `modelCapacity` 读到了**，而不是只存了个字段。

### 6.4 修订：窗口改为必填、识别表退休（2026-10-04 · 2.8.0）

§6.1 的「窗口来源优先级：手填 → 内置预设识别 → 保守兜底」在 2.8.0 调整为**必填**：

| 项 | 旧 | 新 |
|---|---|---|
| 模型配置 → 上下文窗口 | 选填，留空按模型名猜 | **必填**：留空 / < 2000 / > 2M 都保存不了，界面直给原因 |
| 换算提示 | 填小了只在兜底时"不采纳" | 填 128（疑似 128K）→ 琥珀条 + 一键「按 ×1024 换算为 131072」，**保存前就拦住** |
| 预设识别表 | 推荐路径 | **降级为老数据兜底**（老库里的模型没这个字段时不让预算一夜塌成 32K），**不再补数值** |
| 云端有效系数 | 0.4 | **0.6**（作者反馈"取值与赋值过于保守"；128K → 70,464 字） |
| 本地分支 | 只回落不放大 | **按手填窗口主动放大** = 窗口 × 出厂配比 0.732（出厂 32K ⇒ 24,000，默认行为不变） |
| 记忆三项静态上界 | 1 万 / 2 万 / 2000 | **20 万 / 40 万 / 4 万**（否则 1M 窗口算出的 6.8 万硬上限会被夹回去） |

**为什么不再维护预设表**：各家发布节奏不一致（同一模型不同版本窗口能差一倍），
本地 / 自建 / 冷门模型永远认不出 —— 维护成本高、收益低，还容易给出"看着可信其实过时"的值。
让作者按自己的部署填一次（**1K = 1024 tokens**），是唯一不会错的做法。

校验落在 `modelCapacity.checkContextWindow()`：模型配置页的实时提示与保存拦截**共用它**，
单测锁住"通过的值一定被 `adviseCapacity` 采纳为用户窗口"（校验与算法不许各说各话）。

## 七、一句话回答

> **256K 是模型的「架构容量」，不是它能「可靠推理」的长度，更不是我们单卡显存跑得动的长度。**
>
> 实测：32GB 显存下，这个 27B 模型的物理上限就是 **32K 上下文**（再多就得 offload 到内存、速度掉一个量级）；
> 而业界实证表明，**有效上下文通常只有标称的 30~65%**，且**三千 token 就开始因「长度税」掉准确率**。
>
