## 4. 发现的问题（详细）

### ISSUE-01【高】`yfe_host_info` 不反映运行模式，模式关闭后仍报「连接可用」

**现象 / 复现步骤**

1. Agent 模式 + 「Agent 写入连接」开启，调 `yfe_host_info` → `{available:true, enabled:true, scope:{projects:[21 项动作]}, note:""}`。
2. 主人在引擎设置页**关闭 Agent 模式**（切回 API）。
3. 再调 `yfe_host_info` → **仍是** `available:true, enabled:true`、完整 21 项授权、`note:""`。
4. 同一时刻调 `yfe_list_projects` / `yfe_list_check_reports` / `yfe_read_plot_canvas` / `yfe_read_check_report` → 全部 `{ok:false, code:"MODE_BLOCKED", error:"当前模式不允许 Agent 调用。"}`。

**实际 vs 预期**

- 实际：`MODE_BLOCKED` 正确拒绝了业务调用，但 `host_info` 显示一切正常。
- 预期：连接状态查询应能反映「当前运行模式不允许 Agent 调用」，或至少给出 `mode` / `phase` / `reason`，让第三方不必靠业务调用失败反推。

**证据（现场文件元数据，未读取任何文件内容）**

| 文件 | LastWriteTime | 说明 |
|---|---|---|
| `agent-host.json` | 2026-11-10 09:05:56 | **未变**，故 `enabled` 仍为 true |
| `connection-mode.json` | 2026-11-10 09:32:53 | 模式切换写入点 |
| `agent-host-requests.json` | 2026-11-10 09:30:37 | 最后一次成功写入 |

**根因定位（只读代码核对，未改代码）**

- `scripts/mcp/yfe-agent.mjs:683-690`：`yfe_host_info` **完全由桥本地从 host 文件组装**，直接返回 `available / port / enabled / scope / note`，不请求宿主、不查 `modeGate`，因此天然看不到运行模式。
- `scripts/agent-host/core.mjs:331-337`：`status()` 同样只有 `running / enabled / port / bridgeFile / scope / clients / ...`，**无 `mode` 字段**。
- `scripts/agent-host/core.mjs:427-438`：`handleCall` 每次业务调用执行 `modeGate.acquire('agent','agent-host')`，失败即 `MODE_BLOCKED`。
- `electron/main.cjs:816-828`：`agentStatusFromMode()` **已经**组装了 `connectionMode:{phase, mode, busy, reason}` 并供页面 IPC 使用 —— 即数据存在，只是没有透传到 MCP 的 `yfe_host_info` / 宿主 `status()`。
- `src/lib/agentHost/host.ts:41`：页面侧 `AgentHostStatus.connectionMode` 类型定义已存在。

**影响**

- 第三方 Agent 依据 `host_info` 判定「可连」后批量发起业务调用，会全部失败；虽能靠 `MODE_BLOCKED` 分支识别，但**无法自助判断是模式切换、连接关闭、令牌失效还是宿主故障**，容易误判并盲目重试。
- 适配规范 §2 只写了「API 模式时宿主返回 MODE_BLOCKED」，未要求状态查询暴露模式，也未给出该场景的客户端处理指引。

**建议（供下游，不代为实施）**

1. 让 `yfe_host_info`（或宿主 `/api/agent/status`）透传 `connectionMode`，口径复用 `agentStatusFromMode()`；最小改动可只加 `mode` + `phase` + `reason`。
2. 或模式切换时同步更新 host 文件的 `enabled`，使桥本地状态与实际一致（需评估与「用户授权保留」语义的冲突）。
3. 规范 §2 / §4 补充：「`host_info.available/enabled` 仅表示配置与宿主进程状态，不代表当前运行模式允许调用」。
4. 补回归：Agent→API 切换前后，`host_info` 与业务调用结论一致性；以及切回 Agent 后的恢复。

### ISSUE-02【高】工具结果信封不统一，与规范 §4 冲突，已造成第三方客户端崩溃

**规范声明**：`tools/call` 首个文本项成功为 `{ "ok": true, "value": ... }`，失败为 `{ "ok": false, "code": ..., "error": ... }`（`docs/3.4.3-MCP第三方开发者适配规范.md` §4）。

**实测三种形态**

| 工具 | 实际返回 | 是否符合规范 |
|---|---|---|
| `yfe_list_projects` / `yfe_get_project` / `yfe_read_chapter` / 绝大多数工具 | `{ok:true, value:...}` | ✅ |
| `yfe_host_info` | `{available, port, enabled, scope, note}` —— **裸对象，无 `ok` / `value`** | ❌ |
| `yfe_request_status` | `{ok:true, request:{requestId, state:"success", ...}}` —— **有 `ok` 但无 `value`**，数据在 `request` | ❌ |

**真实后果（不是推测）**：隔离轮测试脚本按规范写了 `JSON.stringify(valueOf(resp)).includes('success')`；`valueOf()` 对 `yfe_request_status` 取到 `undefined`，`JSON.stringify(undefined)` 返回 `undefined`，`.includes` 抛 `TypeError`，脚本在 4.4 崩溃、后续 10 项级联中断（前 19 项 PASS 仍有效，续跑脚本从已落盘状态补完 4.4→6.6，未重复写入）。

**影响**：任何按规范统一解析 `result.value` 的第三方客户端都会在 `host_info` 和 `request_status` 上取不到数据或抛异常；失败分支若只检查 `ok` / `code`，对 `host_info` 会误判。

**建议**

1. 统一为 `{ok:true,value:...}`：`host_info` 包一层、`request_status` 至少补 `value` 别名（保留 `request` 兼容）。
2. 若刻意保留例外，须在规范 §4 **逐工具列出例外结构**，并给出客户端解析示例。
3. 补契约测试：68 个工具的成功 / 失败返回都符合声明的信封。
4. 证据：`.workbuddy/tmp/mcp-it-20261110/results.json` 的 `resume.firstRunFatalPreserved` 与 `notes` 里 `yfe_request_status` 的真实响应。

### ISSUE-06【低·规范措辞】「清理该章快照和台账」语义含糊，易误导幂等判断

- 规范 §73 原文：「删除章节进入回收站，但会清理该章快照和台账」。
- **实测**：章节删除→恢复后 `yfe_list_chapter_snapshots` 返回 **0 条**（覆盖前的 A+B 版与初始 A 版两份快照均消失）；但 `yfe_request_status` 对 `real-ch-create-0001-20261110` 仍返回 `state:"success"`，`real-ch-restore-0001-20261110` 亦 `success`。
- **结论**：这里的「台账」指**章节级台账 / 快照索引**，**不是宿主 `requestId` 幂等账本**（后者保留，所以幂等重放仍安全）。
- **影响**：第三方按字面理解会以为幂等账本被清空，进而不敢用同 `requestId` 重放、或反过来以为可以换新 ID 重做，两种都错。
- **建议**：规范改用「章节快照与章节台账」并显式注明「宿主 `requestId` 幂等账本不受影响」；若产品希望恢复后保留历史快照，需另行设计（当前是取舍，不是 bug）。
