## 一、结论先行（TL;DR）

**不建议从零重写。** 但要**大幅做定向重构**——这是两件成本差 5 倍以上、收益却几乎相同的事。

| | 从零重写 | 定向重构（推荐） |
|---|---|---|
| 成本 | 100% | 约 20% |
| 结构收益 | 那 20% 的改善 | **同样的 20%** |
| 功能风险 | 高（行为漂移不可控） | 低（每步可回滚） |
| 工期 | 1–3 个月停更 | 可分多轮，随时可停 |
| 老大的角色 | 唯一测试员，且无法验证"功能没变" | 每轮用 71 个测试 + 实机指纹验收 |

**一句话**：这个项目的结构问题**远小于你的担心**，而重写会把你两年"试错试出来的知识"全部清零——那才是本项目真正值钱的东西。

## 三、为什么"重写"恰好是本案最差的选择

### 3.1 收益侧：重写能拿到的，定向重构也能拿到

重写的全部结构收益 = 消除巨石文件 + 归位目录 + 清掉 1 个循环。
这三件事**都不需要重写**就能做，而且成本低得多。

### 3.2 成本侧：重写会报销掉你真正值钱的资产

| 资产 | 数量 | 重写后的命运 |
|---|---|---|
| 红线与踩坑经验（`MEMORY.md`） | 约 90 条，含 2 次数据事故、1 次 `.git` 清空事故、若干次线上丢数据 | **全部要重新用事故换一遍** |
| 决策文档（`docs/`） | **65 份**，含酒馆工程红线 18 节、AI 上下文预算策略、拆书六阶段设计 | 大半作废，需重新推导 |
| 测试与闸 | 71 个测试入口 + `seed-schema-check` / `feature-deps-check` / `importCycles` / `aiDataSources` / `extractFields` / `bookbreakRelations` | **部分保值**（断言仍是规格），但 import 路径要重接 |
| 出厂数据与示范项目 | 《吞天神脉》三卷 21 章 + 设定库 + 酒馆协议 v1.11 | 需重建校验 |
| 已固化的工作流 | 巨型组件拆分手法、实机指纹比对、分隔符式批量补丁 | 可复用（唯一完整保值的） |

> **核心判断**：本项目的代码是"零基础起步"的，但它的**知识库不是**。这个知识库是 474 次提交、65 份文档、若干次线上事故一点点攒出来的——**它才是这个项目不可替代的部分，代码只是它的载体。** 重写等于把载体换了、内容扔了。

### 3.3 风险侧：重写的失败模式，恰好是你最防不住的那种

从 Bug 清单里可以清楚看到本项目的 bug 类型分布（#001–#034）：

| bug 类型 | 编号 | 发现方式 | 检测延迟 |
|---|---|---|---|
| 数据丢失级（云端/推送/回退） | #008 #009 #011 #023 #025 **#030** | **线上日志考古**（`access.jsonl` 反查） | 数天～数周 |
| 状态/生命周期 | #007 #023 | 用户实测 + 日志指纹 | 数小时～数天 |
| 静默失效（UI 与数据脱节） | #030 #029 | 老大肉眼发现"点开是空的" | 不定 |
| 编译级错误 | — | tsc | 秒级 |

**关键观察**：这个项目**几乎从未出现过"编译不过"的 bug**，出事的全是**编译通过、类型正确、测试全绿、但行为悄悄错了**的那类。

而重写的失败模式恰恰就是这个：`保密等级 D 档` 漏掉一条过滤路径 → 正文悄悄进 prompt；`章节号` 派生规则差一个分支 → 某卷开始跳号；云盘同步的墓碑逻辑漏一个分支 → **已删项目开始复活**（这个你已经真出过一次，#030 幽灵项目）。

**你的验证能力对不上重写的风险等级**：
- 你是唯一的测试员，没有真实用户群体的错误上报
- 重写的中间态**不能上线**（半成品），所以没有"边跑边发现问题"的窗口
- 结果：**漂移会静默积累到很深才被发现，而且发现时你已经分不清哪一版是对的**

### 3.4 机会成本：重写会让"正在work的事"停摆

当前节奏是每月一版、内容创作与修 bug 并行。重写意味着：
- 1–3 个月零新功能、零内容更新
- 更糟的是**心理拐点**：到了第 2 个月，你手上是一个"完成了 80% 的克隆体"，然后面临二选一——继续填坑（再 1 个月）或放弃（2 个月白干）。**两个选项都很差，而且这个抉择点一定会到来。**

## 五、推荐路线：五阶段"绞杀者式"定向重构

**总原则**：每一步**独立可验收、独立可回滚、功能零变化**；71 个测试**全程保持全绿**；每阶段结束单独提交（不封装）。

### 阶段 0 · 结构体检与地图（不改任何代码）
- 产出：完整依赖图 + 债务清单 + 每项的风险与验收方式
- 交付物：本文件 + 一份 `结构地图`（模块归属、分层、中心度 TOP）
- **出口条件**：老大确认优先级排序

### 阶段 1 · 零风险归位（D3 + D6）
- 数据文件搬出 `src/lib` → `src/data/`
- `lib/flow` 与 `lib/bookbreak` 分工写清（或在 README/注释中固化）
- **验收**：tsc 0 错 + eslint 0 + 71 测试全绿 + `vite build` 通过（提醒：删/动门控必跑一次 build）
- **可回滚**：纯路径变更，一个 commit 回退即可

### 阶段 2 · 收口两个巨石（D1 + D2）
- 先用 `dep-cost` 量化依赖热度，**从最外层、最少引用的部分开始切**
- `db.ts` 按 store 域切分，`StoreOps` 接口不变（存储三端行为不变）
- **验收**：实机指纹逐项比对（参照上一轮 15/18/22 项指纹的做法）+ 负面对照
- **可回滚**：分多次提交，每次只切一块

### 阶段 3 · 组件拆分收尾（D4）
- 沿用已验证的拆分 playbook，一个个来，每拆一个跑一次指纹
- **验收**：该组件的实机指纹 + `tests/importCycles` 通过

### 阶段 4 · 清债收尾（D5 + D7）
- 修掉唯一循环依赖（抽第三文件）
- 收紧同步层 `any`
- **验收**：`tests/importCycles` 报 0 环；eslint 仍 0 问题

### 阶段 5 · 立"护栏"，防反弹（强烈建议）
把上面治好的结构**变成自动化闸**，否则三个月后必然重犯：

| 护栏 | 规则 | 落点 |
|---|---|---|
| 单文件行数上限 | 硬上限 1,200 行 / 软上限 800 行 | 新增闸脚本进 `tests/` |
| 分层方向 | 禁止 `lib → components` 反向引用 | 扩展 `tests/importCycles` |
| 目录归属白名单 | 数据文件必须在 `src/data/`，不得落 `lib/` | 新增闸 |
| 禁止裸 `JSON.parse` | 统一走 `aiParse` | 已有闸 |
| 禁止原生弹窗 | 禁 `window.prompt/confirm/alert` | 已有约定，可加闸 |
| 新增 `any` 需注释理由 | eslint 规则 | 扩展 `eslint.config.js` |

> ⚠️ 这一步是**性价比最高的**：项目 90 条红线已经证明"踩过的坑会重踩"，只有闸能防住。

## 六、什么情况下才真该重写（边界条件，如实列出）

不是"永远不该重写"。以下任一成立时，重写才划算：

1. **技术栈要整体更换**——例如 Electron → Tauri、React → 其他框架、Vite → 其他构建。此时重写是不得不做。
2. **要转成多人协作 / 多端同源**（Web + 移动 + 桌面），现有单体结构扛不住。
3. **发现跨模块的根因性数据模型错误**——例如存储键设计从根上错了，导致每个功能都别扭。
   - 📌 本项目最接近这条的是 **"schema 列名即存储键"**（中文列名既是显示标签又是存储键）。它确实有代价，但**已被数据迁移 + 闸兜住**，属于"有代价但可控"，不构成重写理由。
4. **改不动了**——改 A 必坏 B、无人敢动核心。
   - 📌 **本项目明确不符合**：lib→components 反向依赖 0 条、循环仅 1 处、tsc 0 错、71 测试全绿，说明核心是可以安全改动的。

**即便真要重写，正确做法也不是"停机重写"，而是绞杀者模式（Strangler Fig）**：新代码长在旁边，按模块逐个替换、每替换一个就删掉旧的、测试始终全绿。**永远保持一个可运行的版本。**

## 七、给老大的直觉类比

你现在的心情，相当于：

> "这套房子住了两年，有点乱，是不是该拆了重建？"

实际情况是：**这房子的承重墙、水电、地基全是好的**（分层单向、无循环、类型严格、有测试），乱的只是**客厅沙发上堆了东西**（两个巨石文件）和**几个箱子摆错了房间**（数据文件在 lib 里）。

拆了重建的代价不是"花多少钱"，而是**丢掉这两年你试出来的所有居家习惯**——哪面墙该挂什么、哪个插座在哪儿、哪个抽屉一拉就卡。这些都是你住过才懂的，图纸上没有。

写作上的类比更贴切：

> 重写代码 = 把你写了一年的小说**从零重写一遍**，理由是"前几章文风不够统一"。
> 你不可能在保留剧情、伏笔、节奏、爽点的同时重写——那些"试出来的东西"会全部丢掉，你只会得到一部文风统一但**不再是你那本书**的书。

**正确做法**：不改剧情，只做编辑——把两章并作一章（拆巨石）、把插叙理顺（归位目录）、删掉多余的重复段落（清死代码）。**这正好就是 2.3.0 该干的事。**
