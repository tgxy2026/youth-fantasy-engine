## 1. 为什么单开这一条

R2 方案 §6.2 末尾那句是这次工作的全部理由：

> 「对可确定阶段的进程终止安排少量独立进程测试，**不能把内存异常测试写成真实崩溃恢复已验证**。」

`candidateApply.test.ts`（3.2.0 起就在）已经覆盖了同进程内的内存异常：persist 抛错、回读串内容、
applying 的三条恢复分支。但那是**同一个进程里的 throw**，证明不了"进程被强杀之后磁盘上到底剩下什么"。
所以这轮补的是**真实 SIGKILL + 真实文件 + 重启核对**。

## 2. 怎么做的

| 文件 | 作用 |
|---|---|
| `tests/candidateCrashChild.ts`（新，非用例） | 由父进程拉起，按 `YFE_CRASH_STAGE` 在**确定屏障**上 `process.kill(pid,'SIGKILL')`；不用随机等待、不靠概率 |
| `tests/candidateCrash.test.ts`（新，58 条断言） | 五个屏障各跑一次真实崩溃 + 父进程重启核对；临时目录用真实文件当存储（正文 / 候选 JSON / 写入日志） |
| `scripts/verify/reliability.mjs`、`reliability.contracts.json` | `revision.recovery` 契约接入（定向跑该套用例，要求 ≥50 条断言），去掉 pending |

五个屏障与实测结论：

| 屏障 | 崩溃后磁盘 | 重启后行为 | 正文写入次数 |
|---|---|---|---|
| `before-intent`（意图落盘前） | 正文＝改前；候选仍 pending | 正常写入一次 | 1 |
| `after-intent`（意图已落、正文未写） | 正文＝改前；候选 applying＋intent | 正常写入一次（不误判为"已应用"） | 1 |
| `before-write`（正要写正文） | 同上 | 正常写入一次 | 1 |
| `after-write`（正文写完、回执未落） | 正文＝改后；候选 applying＋intent、无 receipt | **只补回执（`resumed=true`），不再写正文** | 1 |
| `before-receipt`（回执构造完、持久化前） | 同上 | 同上 | 1 |

每个屏障同时断言：崩溃后候选**不会**被标成 `discarded`/`stale`（可重试的失败不许丢候选）、
回执与意图 `operationId` 配对、最终候选 `applied`、正文只被写过一次。

另加三条针对 `failureReceipt` 的判据：没有 intent 时返回 `null` 而不是伪造一条；
失败回执是**独立记录**（带 `ok:false` 与原因），不写进 candidate；它不改变候选状态。

## 6. §6.1 便携配置：真实 HTTP 写盘失败（同日追加）

方案 §6.1 对 portable 的要求是「本地 HTTP 失败、连接中断、提交后响应丢失」。
`tests/portableSaveFailure.test.ts` 不伪造 `fetch` —— **起一个真的 `node:http` 服务**（真实 socket），
按场景真的回 500、断 socket、回 401，然后看 `flushPortable()` 与 `getPortableState()` 怎么说话。

便携判定沿用平台矩阵里同一个注入点（`window.__YFE_PORTABLE__ = { apiBase }`，与 `scripts/audit/platform/policy.json` 的 portable profile 一致），
所以这跑的不是"另写一个假后端"，而是生产代码的同一分支。

| 场景 | 核心断言 |
|---|---|
| PUT 500 | `flushPortable()` 为 false；**dirty 仍在**；`lastError` 含 HTTP 500；服务恢复后重试成功、dirty 清掉、服务端确实收到内容 |
| 连接中断（收完请求即断 socket） | false；dirty 保留；有错误说明；重试可成功 |
| **提交后响应丢失**（服务端已收到、回应没回来） | false（不能凭"请求发出去了"算保存）；dirty 保留；重试可成功 |
| 401 + `SESSION_REPLACED` | false；文案说清「账号已在别处登录」而不是笼统的写入失败；dirty 保留 |
| **保存中继续编辑**（PUT 在途时再写一次） | 在途写盘本身成功，但**新改动仍然 dirty**（旧回执不许清新草稿）；再存一次落的是新内容 |
| 状态自洽 | 结束后不在 `saving`；成功后 `lastError` 清空；`lastSavedAt > 0` |

证据：**28 条断言全通过**；`reliability.mjs --profile local` 新增 `storage.portable-save` 契约（要求 ≥20 条）已 passed。

## 7. §6.1 其余三配置：为什么是阻塞而不是"已验"

| 配置 | 方案要求的注入点 | 本轮结论 |
|---|---|---|
| desktop | 测试引导里拦截目标文件写/rename/flush | **阻塞**：写盘在 Electron 主进程经 IPC，Node 夹具里 `@/lib/app/desktop` 被整体打了桩，注不进真实失败 |
| web-cloud | 本地真实 server 的失败/配额/会话替换（限临时账号） | **阻塞**：需要隔离服务 + 临时账号的会话替换流程，本机无这套夹具；且不得用生产账号 |
| web-guest | 目标 IDB 写事务制造 abort / QuotaExceeded | **阻塞**：Node 里没有 IndexedDB 实现，仓库也未装 `fake-indexeddb`；自己写个假 IDB 只能证明假件的行为，属于自欺 |

🔴 因此 `storage.four-profiles` **保持 blocked**，另立 `storage.portable-save` 单列已完成的这一项 ——
方案 §7 的口径就是「某个子场景有证据不能代表整个单元通过」，不拿一项去凑四配置的绿。

这三项与 §6.3（备份/迁移/导入导出：载荷损坏、迁移中断、恢复重试）留给后续批次；
`desktop` 一项最终要与 R4 的封装/真机项合并验收，不在 Node 夹具里假装已经验过。

## 8. §6.3 备份外置数据的迁移、损坏与恢复（同日追加）

`tests/sidecarMigration.test.ts`（34 条断言）补的是**迁移与恢复链路** ——
`sidecar.test.ts` 已锁两种布局语义与单条损坏导出，`backupShards.test.ts` 已锁四片拆分与"哈希不符不写回"，
这里不重复，只补方案 §6.3 点名的五类场景。

| 场景 | 核心断言 |
|---|---|
| 迁移成功 | 载荷 2 份 + 整表 1 份逐条迁出；主 JSON 里外置 store 已摘除、未外置的 chapters 原样保留；**外置内容与源逐字段哈希一致** |
| **目标不可写**（定点让第 2 份载荷写失败） | `failed` 如实记录；**该 store 源数据原样留在主库**（不许删了却没写出去）；另一个 store 照常迁走 |
| **迁移中断**（主数据文件写不下去） | `migrateSidecar` 返回 `ok:false`；外置已写入 ⇒ 下次重启重迁是安全 upsert |
| 重试幂等 | 重跑 `moved` 为空、无 failed、外置文件数不变、内容哈希不变 |
| **多份载荷损坏** | 两份坏 → `issues` 逐条列出（2 条）、`complete=false`、健康那份仍带出且哈希对得上 |
| **主 JSON 与 blobs 同时恢复** | 主 JSON 取 chapters + 外置取回载荷/向量 ⇒ 条数、id、正文、载荷哈希、向量哈希全对；外置里不残留主库数据 |
| **恢复失败后重试** | 第一次 `complete=false` 且写明缺哪条、仍救出健康载荷；故障排除后重试 ⇒ `complete=true`、内容与原始一致 |

同时修了一处**静默**（`src/lib/storage/fileBackend.ts`）：
`migratePortableSidecar()` 原来只看 `r.failed`，不看 `r.ok` —— 大块数据迁出去了、主 JSON 却没写成功时，
只留一行 `console.log`，作者和界面都看不到。现在会写进 `lastError`：
「大块数据已迁出，但主数据文件未写成功（下次启动会自动重试…）」。第 ⑧ 组断言就是这个守卫。

验收：全量 **312/312**（A33 B67 C121 D91，214s）；`local` 档 **10 passed / 4 blocked**（新增 `backup.migration` 契约，≥30 断言）。
