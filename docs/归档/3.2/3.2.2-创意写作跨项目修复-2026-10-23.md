# 3.2.2 · 创意写作跨项目串任务（A 档修复）

> 来源：用户 2026-10-23 反馈 ——「我一个项目在创意写作，切换到另一个项目，创意写作也在进行」
> 口令：2026-10-23 06:52「升 3.2.2，先落地 a 档修复方案」
> 🔴 结论：**反馈成立，且比反馈描述更严重** —— 不只是"还在跑"，是**产出写进了另一个项目**。

---

## 一、病灶链（七环，全部代码可查）

| # | 环节 | 位置 | 事实 |
|---|---|---|---|
| ① | 切项目改全局 | `App.tsx` `db.setCurrentProject(id)` | `currentProjectId` 是**模块级可重赋值单例**（`db/core.ts:6`） |
| ② | 面板重挂 | App 主 return 的 `key={`proj-${projectId}`}` | key 变 ⇒ 整棵子树重建，创意写作在 B **重新挂载** |
| ③ | 挂载即重读会话 | `useCreativeWritingModel.ts:86` → `loadSession(pid)` | pid 变了 ⇒ 走重置分支 |
| ④ | **`running` 没被重置** | `creativeSession.ts` 的 `RUNTIME_RESET` / `SESSION_BLANK` | 两个集合都不含 `running` ⇒ B 的面板照样显示「运行中」 |
| ⑤ | 任务不停 | `abortCtl` 只在 `stopCreativeRun()` 里 abort，唯一调用点是「停止」按钮 | 切项目 / 面板卸载**都不 abort**，A 的 async 继续跑并继续 `set()` 刷进度 |
| ⑥ | **落库跟着新项目走** | `autoContinue.ts` `const pid = db.getCurrentProjectId()`；`db/chapters.ts` `projectId: c.projectId \|\| currentProjectId` | 新章构造时**动态取当前项目** ⇒ 切到 B 后带 `projectId=B` 落库；`getAllVolumes/Chapters` 读的也是 B ⇒ 续写上下文是 B 的内容 |
| ⑦ | 同源污染 | `creativeSession.ts` 三处 `db.getCurrentProjectId()`（运行账本 / 调用账 / 改写候选） | 同样跟着新项目 |

### 为什么之前没被发现

- 面板卸载不 abort 是 3.0 期的**刻意设计**（模块级 store 就是为了"切页签不丢任务"），
  但当时只考虑**同一项目内切页签**，"切项目"这条路径没进判定。
- `App.openProject` 里其实**早有**跨项目清理机制（`resetTaskCenter()`：换项目才清后台任务）——
  **创意写作不走任务中心**（它有自己的 `abortCtl`），所以这套保护对它无效。
- `bindProject()` 的注释写着「有活任务时不动（那次运行自己认的是启动时的项目）」，
  **但实现里没有这个判断** —— 注释承诺了保护，代码没实现。

## 二、修法（A 档：数据安全优先，宁可停）

| 改动 | 位置 | 说明 |
|---|---|---|
| 新增 `runProjectId` | `creativeSession.ts`（模块级） | 记「本次运行认的项目」，`null` = 没有任务在跑 |
| 开跑绑定 | `startCreativeRun` / `startChapterRewrite`（`await bindProject()` 之后） | 记下 `db.getCurrentProjectId()` |
| 收尾清空 | 两个任务的 `finally` | 与 `abortCtl = null` 同处 |
| 新增 `runBelongsTo()` | 同文件（**导出以便单测**） | 判定表：`!active` / `runPid===null` ⇒ 不冲突；否则 `runPid === nextPid` |
| 新增 `abortRunIfProjectChanged(nextPid)` | 同文件 | 冲突则 `stopCreativeRun()` + 置 `running:false` + 如实提示 + 清空绑定 |
| 接线 | `App.openProject`（紧挨 `resetTaskCenter`）、`App.exitProject`（紧挨 `abortAllTasks`） | 放在 `setCurrentProject` **之前** |

### 三个关键设计决定

1. **为什么复用 `stopCreativeRun()` 而不是自己写 abort**：
   它会把**三个挂起的弹窗 Promise 全部 resolve 掉**（闸门 / 初稿裁决 / 候选挑选）。
   漏掉任何一个，编排器都会永远 `await`，按钮一直转圈 —— 这正是既有注释写的坑。

2. **为什么传 `nextPid` 而不是比较"当前项目"**：
   App 里是"先判再切"。若函数内部去读当前项目，切换前它和启动项目**必然相等** ⇒ 永远不触发。
   传目标项目才没有时间窗（切换那一瞬间不会漏掉一章写入）。

3. **为什么"停"而不是"继续跑、写回原项目"**：
   落库全走 `db.*`（隐式取当前项目），要写回原项目得给整条链路加显式 pid 参数（B 档）。
   而**写错项目是不可逆的数据事故** —— 宁可停，并明确告诉作者"产出没有写入任何项目"。
   ⚠️ 反例：只把 `running` 加进重置列表是最坏的做法 —— 界面不转了，但任务还在往错项目写。

## 四、✅ 已实机验证（2026-10-23 07:19 口令，详见 `3.2.2-创意写作跨项目守卫-实机验证-2026-10-23.md`）

用**桌面版 dev + CDP + 90 秒挂起的假模型服务**造出"运行中"的真实现场，三段观测：

| 验证 | 结果 |
|---|---|
| 运行中点「切换项目」 | ✅ 第 **49 秒**中止，A 面板留痕「设定奠基 · 已中止 · 49 秒」+ 给「继续写作」 |
| 切到 B 后面板 | ✅ **不显示「创作中…」**（`running` 已清） |
| B 的数据 | ✅ `0 卷 · 0 章`；库里 B 的 `creativeSession` 是空会话 ⇒ **没写错项目** |
| A 的数据 | ✅ A 的会话键里 `seed` 与 `resume` 都在 |
| 刷新后 B | ✅ 完全干净（证明污染只在内存） |

**遗留两条（已定位，未擅自改，建议补第二刀）**：

- ⚠️ **内存态短暂跨项目**：切到 B 的当下会显示 A 的「已中止 / 继续写作」，刷新即消失。
  根因：`loadSession` 的清理依赖「`hydratedFor !== pid` 才重读」，而 `setCurrentProject` 与 React 挂载的
  先后没有保证，可能被提前返回跳过。修法：`abortRunIfProjectChanged` 里**顺手清 `SESSION_BLANK`**。
- ⚠️ **想法在"填完 1 秒内就点开始"时会丢**（既有 1s 防抖边界，本次新增的"切项目即中止"放大了它）。
  修法：abort 前**先 flush**，且 flush 必须写 `runProjectId` 而不是 `db.getCurrentProjectId()`
  （后者此刻可能已换项目 —— `persistNow` 正是动态读它，同一病根）。

## 五、原计划的真机清单（已被上面的实测覆盖，保留作复核口径）

- ① A 项目点开始创意写作 → 等到出现进度（不必跑完）；
- ② 直接点侧栏回项目首页 → 进入 B 项目；
- ③ 期望：B 的创意写作面板**不再显示运行中**，并有一条提示；
- ④ 回 A 项目检查：正文/大纲里**没有**多出怪章节。

---

## 六、影响面（谁能受益）

- 切项目后**不会再出现"B 项目凭空多出几章"**（这是最严重的那条）；
- 面板不再在 B 里显示「运行中」；
- 唯一代价：切换项目会**停止**正在跑的创意写作（A 档的取舍，已在提示里说明产出未写入）。
