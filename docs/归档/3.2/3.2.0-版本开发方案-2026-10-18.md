## 1. 版本目标与交付范围

**版本主题：让作者使用自己的资料模板，并通过资料准确、结果可信、运行可追溯的 AI 完成创作与可控修订。**

作者能从空白或预设建立自己的资料结构，在项目中填写、搜索、交给 AI 参考或补全；既有 AI 通过稳定的业务语义继续读写这些资料。写作时找到本章资料，把问题变成候选，审阅后应用并支持重启续处理。原计划中的细纲对照、精细影响定位仍为 P1，优先完成模板对现有 AI 的兼容，不以缩减旧能力换取新模板入口。

### 1.1 三个方向的安排

| 原讨论方向 | 3.2 的具体增量 | 本版安排 |
|---|---|---|
| 新增：用户自定义模板 | 统一有效模板、自定义结构、模板复用与升级、AI 读写及用途绑定；旧字段改名与新增字段同一理解规则 | 3.2.0 主线，T0/T1/T2/T3，作为 A/B 共用前置 |
| 规划与正文联动 | 按有效模板展示本章资料；细纲与正文对照、精细影响提示 | A1 必交付；A2、A3 的确定性证据版为 P1，可顺延 3.2.x |
| 可控的多步骤 AI | AI 审读结果进入现有工单、先产出候选后应用、限定范围的重启恢复 | 3.2.0 主线，B1/B2/B3 |
| AI 共用能力深化 | 结果状态、权限、上下文、输出协议、流式运行、调用追踪与质量基准 | Q1–Q8 基础能力为 P0；生成质量深化与长期记忆 Q9 为 P1，详见 §16 |
| 跨作品资料复用 | 世界包封存版本差异查看、选择性更新 | C1/C2 均顺延 3.2.x；本版须保证现有世界包搬运不丢模板定义 |

P0 必交付为 F0、T0/T1/T2/T3、A1、B1/B2/B3，以及 §16 的 Q1–Q7 和 Q8 基础质量守卫、评测基准。Q2/Q3 分别并入 WT2/W3，Q7 的提示词快照并入 F0，不能重复建设。P1 为 A2、A3 的确定性证据版、Q8 生成质量深化及 Q9 记忆深化；A3 的 AI 相关性复核及 C1/C2 留到后续。没有完成 P1 时，P0 仍须能独立完成“模板→资料→工单→候选→审阅应用”的流程，不能依赖未交付的按钮或数据结构。

### 1.2 版本演示场景

1. **P0：** 从空白创建角色模板，只使用名称和作者设计的字段；保存、填写、导出结构，并在另一个项目应用，原项目不随模板库变化而改变。
2. **P0：** 原内置字段改名和新增字段都让 AI 依据当前名称/说明理解并填写；历史别名集中确认，同义改名继续原功能，改义先调整用途。禁止参考的值不进入上下文、索引或召回；只允许填写时仅提供目标定义。改变字段含义或类型后，旧结果不可直接应用。
3. **P0：** 打开第 12 章，看到绑定细纲与当前模板下的角色资料；切到第 13 章后资料随章切换，正文草稿和光标不丢。
4. **P0：** 自定义角色字段经语义映射后，续写、人设审读、拆书/补登与章后整理仍能使用；有些精确状态缺失时只标对应子检查未检。问题进入工单并生成候选，原稿保持不变，审阅应用或关闭后继续处理。
5. **P1：** 细纲计划“隐瞒身份”，正文已公开；展示计划/正文依据，由作者保留变化或登记工单。
6. **P1：** 资料修改后列出后续细纲中的直接提及依据；证据不足时保留范围提醒，不把推测说成确定影响。

### 1.3 本版边界

- 沿用章节、细纲卡、角色卡、设定表、工单、运行账本和快照，不建立平行的场景正文系统。
- 核心手动写作、资料查看与本地检查继续离线可用；AI 功能按已有模型配置启用。
- 本版不引入新的顶级功能组。模板管理入口放在项目管理/功能配置与受支持资料页，工作流交互放在原正文编辑、检查工具和颉文姬内。
- 模板替换 P0 开放国家势力、地理风物、种族生物、物品资源，以及主要/次要/NPC 角色卡七个资料页签。后三类复用同一角色组件和适配层。世界/力量体系、制度、分卷大纲与章节细纲暂用预设模板适配器；它们的模板编辑入口列入 3.2.x。功能页、编辑器、酒馆和跑团页面不套用通用资料模板。
- T3 覆盖当前已经允许字段改名的业务资料入口，包括上述七页签以外的既有表格、表单和卡片字段；统一名称、说明及用途确认不等于开放这些页签的完整模板编辑、增删字段或修改系统规则。字段内部 ID、编号、记录关系与系统元数据约束保持原契约。
- 既有酒馆、跑团、拆书、创意写作流程保持各自职责；B3 的任务恢复覆盖本版核对与修订。Q1 连写自检暂停额外保存当前章的最小待审草稿检查点，不扩为整条旧工作流的重启续跑；其他原流程继续沿用自己的恢复能力。
- 历史章的自动候选仍遵守已有 `HISTORY_ACTIONS`（润色、精简）；需要改变剧情、设定或扩写历史章的问题交由作者手动处理。
- 原存储、模型路由、预算、提示词注册、任务中心、拆书/创意写作执行器、快照与备份继续复用。新增层负责字段解释、规范化读取和确认写回，不把同一功能重写成“自定义模板专用版本”。
- Q1/Q2/Q4–Q7 为共用边界改造，覆盖 §3.11 的原 AI 入口，按入口逐条迁移；不改变不同功能的业务职责。通用调用追踪不等于所有产物持久化；恢复范围按 B3 与上述暂停检查点执行，拆书、酒馆等的全面恢复另行评估。
- 全书历史事实时间线、全部原生服务商协议和全自动语义改稿不纳入 3.2.0。历史审读先明确时间依据和未知项；模型能力采用配置与实测结果，未知接口保持原兼容路径。

## 3. 共用基础 F0：记录定位、版本基准与提交结果

F0 与 T0 一起先落地，供模板和 A/B 共用。章节、记录、字段身份及能力判定以同一个有效模板服务为准。

### 3.1 稳定引用和章节细纲绑定

新增纯类型 `lib/revision/revisionTypes.ts`，业务引用统一形状：

```ts
type RecordRef = {
  kind: 'chapter' | 'outline' | 'card' | 'row' | 'form' | 'sub'
  projectId: string
  tabId: string
  id: string                  // form 使用逻辑页签 ID，其他使用业务记录 ID
  fieldId?: string            // 有效模板中的稳定字段 ID；新引用使用此项
  fieldKey?: string           // 仅兼容旧引用；由模板适配器解释，不能按显示文字猜
}
```

- 章节身份使用 `Chapter.id`，章号只作展示与排序。序章、番外和不计序号的章不得一律按“第 0 章”匹配。
- `resolveChapterOutline()` 首先查显式绑定；没有绑定时仅对“可解析的全局章号唯一匹配”给出建议；多匹配、零匹配或自由章节要求手动选卡。标题包含只能用于展示搜索结果，不能静默建立绑定。
- 手动绑定与固定资料按章存入项目设置键 `chapterContext32:<chapterId>`，值为 `{schema:1, outlineId?, pinnedRefs:RecordRef[], updatedAt}`，不复制细纲/设定正文。
- 切项目、复制项目、导入、恢复及删章时处理引用；项目导入器需同时补齐章 ID、卡 ID、表行 ID 映射。无法映射的引用保留可读名称提示，不能指向别的同名记录。
- 向 `App` 的导航参数增加可选 `recordId`，为 `OutlineSheet` 增加精确目标卡；沿用既有角色卡/表格的行聚焦机制。旧调用签名继续可用。
- 所有字段引用同时带上所在模板 ID 与版本依据；改名/改分组按稳定 ID 跟随，归档或迁移无法映射时显示失效引用。不能因字段显示名称相同就绑定到另一字段。

### 3.2 内容基准

复用 `chapterFingerprint()`；为关联细纲、设定记录和活跃子项选择增加内容摘要。对象字段排序后计算摘要，纯界面布局、分组顺序和主题不参与；T3 统一后的字段名称会提供给 AI，不能再按“仅显示别名”排除。实际提供给 AI 的名称、说明、类型、选项、权限与用途绑定属于语义基准，变更时按实际字段依赖判定失效。

`RevisionBasis` 至少包含项目 ID、项目数据恢复代次 `projectDataEpoch`、目标章指纹、细纲引用及内容摘要、实际送给模型的相关记录摘要、依赖模板的 `templateId/version/semanticDigest`、实际字段/映射依赖摘要、能力判定摘要、卷章顺序摘要、生成参数/提示词版本、采集时间。模板整体版本仅用于识别变化，按 §3.10.4 判断是否影响该任务；不能看到修订号变化就使全部候选作废。不要假设现有 `settingsRev` 已在所有写入点更新；拿不到的真实依赖必须标明。

- 检查报告：目标章、细纲或实际依赖变化后显示“结果已过期”，仍可阅读，禁止直接转成可执行候选。
- 修改候选：应用前重新验证所有实际依赖；影响该任务的变化才拒绝应用，提供针对涉及步骤重新生成或复制文本路径。可证明纯展示变化或无关字段新增时继续使用，不能跳过真实权限收紧。
- 作者认可的计划偏离绑定“该项计划摘要 + 正文指纹”。两者之一变化后重新核对，不永久屏蔽同名问题。
- 基准只保存摘要和引用。候选全文放独立载荷，不能塞入 `AiRun.candidates`。
- 区分“生成依据”和“提交前置条件”：模型/参数/提示词版本固定为运行快照用于追溯，作者后来换模型或编辑提示词不自动使已生成内容过期；正文、已消费资料、权限、相关字段含义/绑定与章序才按实际依赖检查。续跑未完成步骤采用原配置或作者明确选择新配置并重新捕获依据。
- 新条件提交使用持久化修订标识和规范化内容摘要，避免仅靠毫秒时间戳或旧短哈希防覆盖；规范化保留字符串/数字/布尔/空值差异。既有 `chapterFingerprint` 保留兼容，不能把仅适于缓存的散列直接当成唯一提交凭据。
- 同项目恢复/替换导入生成新的 `projectDataEpoch`，相关候选及提交日志即使遇到相同文本/时间戳也需重新核对。普通编辑、无关布局和例行同步不增加该全项目恢复代次；日常失效仍按实际依赖处理。
- Q7 的请求上下文显式携带 `projectId/taskId/stepId/callId`；每次装配直接返回本次 `contextSnapshot`，账本按 ID 关联。弃用全局“最近一次装配/当前运行任务”作为归属依据；原接口可保留兼容包装，但不能参与新链路的审阅依据判定。

共用接口约定如下，接口名可在实现评审时调整，输入输出语义固定：

| 接口 | 输入 | 输出/失败语义 |
|---|---|---|
| `resolveChapterOutline` | 项目 ID、章 ID、当前章序及显式绑定 | 唯一绑定或待选择候选；歧义不能返回伪造的唯一结果 |
| `captureRevisionBasis` | 项目 ID、目标章、细纲及实际上下文依赖 | 只含引用与摘要的基准，缺失依赖另列 |
| `validateRevisionBasis` | 原基准、当前数据 | `{valid, reasons, missingRefs}`；读失败按不可应用处理 |
| `prepareRevision` | 任务 ID、章 ID、选中问题 ID、动作、作者要求、模型参数快照 | 已持久化候选 ID 与状态，生成阶段不写正文 |
| `commitRevisionCandidate` | 项目 ID、候选 ID、作者本次确认 | `{state, snapshotId, persisted, derivedPending, error?}`，已应用返回同一回执 |
| `resumeRevisionJob` | 项目 ID、任务 ID、作者确认续跑 | 只安排未完成且基准有效的步骤；过期步骤单独返回 |

这些接口必须显式携带项目 ID。底层需要新增指定项目的章节/资料读取方法，避免后台任务在 `currentProjectId` 改变后写入另一项目；不能临时切换全局项目指针模拟后台读写。

### 3.3 统一应用协议

计划新增 `prepareRevision()`、`validateRevisionBasis()`、`commitRevisionCandidate()`。现有 `runTicketChapter()` 拆为生成和应用两步；现有手动整章改写在 P0 接入同一条件提交与快照保护，不能留作发布后的可选接线。

应用顺序：

1. 固定目标项目和章节；若编辑器存在该章未保存草稿，先完成草稿冲刷，失败立即停止。
2. 获取该章提交协调权，读取当前记录并校验基准。预写候选/快照载荷和准备日志不占用 IDB 长事务；模型生成阶段不持有写入锁。
3. 建立改前快照，持久化提交意图（唯一 `operationId`、候选 ID、基准、目标正文摘要、快照引用及待派生步骤）。
4. 最终短事务/写入段内再次检查基准，原子写入正文/字数/时间、AI 来源统计、修订标识及本次提交标记；不以旧整章对象覆盖其他字段。提交标记与正文必须在同一主记录持久化中生效。
5. 确认主记录本机持久化，再按 `operationId` 幂等补派生台账、影响提醒和回执。派生更新失败显示“正文已保存，台账待补齐”，仅重试派生步骤；后续人工编辑不得抹除尚未结清的提交标记。
6. 本机保存成功与云同步成功分开显示。远端不可用不能反过来把正文写回旧版。

需要在 `db/chapters.ts` 和存储适配层补“带预期指纹的条件更新”能力：IDB 在同一读写事务中核对并更新；文件后端在本进程记录变更锁中核对并替换。编辑器保存、AI 应用以及同步缓存合并对同一章的更新都必须经过这道条件保护或共享变更协调点。仅在 UI 中先比一次再调用旧 `saveChapter()` 不算实现。

本机条件写入不能代替跨设备并发控制；仍由现有同步冲突副本机制处理远端分叉。模型请求期间允许正常写作，发现基准改变时使候选过期。

文件后端的协调必须覆盖使用同一数据目录的实际写入者：桌面优先由主进程统一执行条件更新与持久化；多个程序实例或便携服务不能只各持一把进程内锁。无法取得目录唯一写入权时提示只读/关闭冲突实例。IDB 后端使用短事务，另以迁移代次阻止其他窗口按旧配置写入，不能持有等待模型、文件 I/O 或用户选择的事务。

取消规则：提交主记录前取消可退出并保留草稿；主记录写入后，取消仅停止下一章和可选后续模型请求，不能中止提交核对或显示“未应用”。应用中关闭/切项目先结清短提交或留可恢复日志；重启先核对结果，不用取消信号回滚已保存正文。

### 3.4 T0：统一有效模板协议（P0）

目标是让页面、AI、搜索、导出和检查读取同一份项目结构。不要直接修改全局 `TABS` 或 `activePack` 来实现某个项目的用户模板。

新增 `lib/templates/`，基础接口为：

```ts
resolveProjectTemplate(projectId, tabId, purpose, recordCategory?)
// => { templateId, version, revision, semanticDigest, fields, groups,
//      semanticBindings, capabilities, diagnostics }
```

`purpose` 至少区分表格、详情、普通搜索、AI 读取、AI 写入、向量索引和导出。字段采用稳定 `id`、原始 `sourceKey`、显示名 `label`、说明、类型、选项、分组、适用类别、归档状态和独立权限。复用图鉴现有六种基础类型；新字段继续使用 `cf_<uid>`，既有 `cf_` 值保持原键。

在此之上提供 `readSemanticView(projectId, recordRef, operation)` 和 `resolveSemanticWrite(projectId, recordRef, slot, candidate)`。前者将自定义结构投影成现有业务能理解的语义，后者把原执行器的输出译回真实字段。投影只在读取时生成，原 `TableRow.data` / `CardRecord.data` 仍是正式内容唯一来源，不另存第二份角色/世界事实库。

- 内置字段由适配器赋予稳定描述 ID，`sourceKey` 继续指向原列名或 `模块名::字段名`；改显示分组、标题不改存储位置。禁止给所有历史资料做一次性全键改写。
- 把 3.1.3 图鉴配置通过适配器接入通用服务，先证明当前输入输出一致再启用新编辑器；已迁移页签以项目模板快照为唯一配置来源，旧图鉴入口成为同一服务的编辑入口，不双向维护两份配置，也不在新 UI 上线前强制搬动全部旧值。
- 尚未开放模板编辑的页签也返回“内置模板适配结果”，业务消费者不自行兜回 `tab.columns`、`tab.modules` 或遍历所有原始值。
- 解析失败或遇到更高格式时，受影响页签/字段只读，停止其 AI 读写与配置修改；其他已解析且获授权资料继续工作，不能把单页异常扩大成全项目 AI 停用。不能退回原始字典把归档或禁止参考的字段发出去。字段级未知类型只隔离该字段；无法解释整个模板结构才隔离该页签。
- 配置缓存按项目 ID、页签 ID、模板修订缓存。切项目、导入、恢复、同步合并后统一失效；后台任务捕获启动时项目 ID 和模板快照，发送前仍执行 §3.8 的当前权限检查。
- 模板存储格式版本、发布版本、项目修订号分别管理。纯布局变化只更新项目修订号；影响 AI 理解/权限/用途的变化改变 `semanticDigest`，再按实际字段/来源依赖使相关报告、索引和候选失效。
- 旧 `fieldAlias` 作为迁移输入接入 T3；迁移后有效字段的 `label` 是界面和 AI 共用的名称，`description` 解释当前含义。新字段与改名字段采用同一规则，不叠加第二层仅供人看的别名。原预设名仅用于内部兼容与迁移说明，不作为覆盖用户含义的提示词约束。隐藏仅影响展示，归档影响常规使用，AI 权限另判。

### 3.5 T1：模板创建、项目采用与复用（P0）

P0 面向七个资料页签，支持从空白或预设复制创建；新增/改名/排序/分组字段，配置六类类型、选项、说明、示例、适用类别、AI 可读可写，预览后采用。可保存为个人模板，也能导入导出仅结构模板包。

“从空白”只保留记录身份和最小名称入口；用户自行设计其余栏目。创建时提供“连接现有 AI 能力”的用途建议，不要求用户复制内置字段名。原预设字段不强制显示或填入 AI 上下文；已有旧值进入可查看、可映射的保留资料，作者可明确选择哪些继续作为 AI 参考。记录 ID、项目归属、保密/弃用策略、自动编号和内部引用等系统元数据仍由系统管理，模板不能删除这些保护。

项目采用模板的**固定快照**。个人模板库发布新版本不修改已有项目；项目可独立编辑成新修订，或查看库版本差异后升级。已发布库版本不可原地覆盖，模板包同 ID/版本但内容摘要不同须报冲突或另存为新模板。

| 数据 | 存放与行为 |
|---|---|
| 项目有效模板 | `settingsKV`：`projectTemplate32:<tabId>`，含完整定义、用途绑定、版本与来源；按指定项目读写，随项目正式备份/导出/同步 |
| 项目模板目录 | `projectTemplate32:index`：启用页签与快照摘要；只用于索引，定义仍以每页签快照为准 |
| 个人模板库 | `meta`：`templateLibrary32:<templateId>:v<version>`；只含定义，默认作为本机个人库，加入云同步排除；分享走显式模板包，不影响项目内快照同步 |
| 迁移暂存 | `meta`：本机项目级迁移日志，保存目标配置和受影响值的恢复引用；不进入日常云同步，恢复未完成前禁止再迁移同一页签 |

初始限制：每页签最多 60 个未归档自定义字段、20 个分组，名称 1–20 字，单字段说明最多 500 字，选项最多 100 项；模板包序列化上限 2 MiB，单项目模板定义合计上限 8 MiB。超限明确拒绝，不能截断定义。角色“名称”使用记录标题元数据；表格从当前模板中唯一绑定一个名称字段，映射不到时要求作者先指定。

上述 8 MiB 包括项目模板、T3 轻量覆盖及发布清单；归档定义也计入字节额度，另限制每页签全部自定义字段定义最多 200 个，避免只限制活跃字段却无限积累归档。包导入先验证完整结构、引用、大小和未知版本，再建立变更计划；规则见 §17.3，不能借导入绕过界面限制。

模板包不带条目正文、角色记忆、图片或密钥；完整项目/图鉴资料包另行承载资料。模板支持分组和现有类型，不含脚本、公式、任意布局代码、新业务页签或自定义执行规则。

### 3.6 模板更换、升级与迁移（P0）

统一通过 `planTemplateChange()` 产出只读计划：字段保留/新增/归档、旧值到新字段映射、类型转换、引用影响、原 AI 能力兼容情况、可修复映射建议和结果失效数量。显示名称相同只能建议映射，不能据此自动合并。提交前优先给出保留功能的映射路径，而非只列“将不可用”。

确认后先验证变更计划的配置/值基准，完成严格持久化备份并建立日志，再写入目标数据和配置；成功后按 §17.2 的发布代次切换有效模板。桌面/便携不能依赖跨文件事务，逐步写入须记录完成项。受影响页签及引用它的派生视图/AI 取材保持迁移维护状态，其他资料继续可用。迁移期间阻止旧编辑草稿、自动保存和已在途 AI 结果回填该页签；它们返回明确冲突，不把旧草稿悄悄冲刷进新结构。

- 默认归档，不删除旧值；删除/合并/类型转换必须有预览。转换失败保留原值并列出条目，未解决前不能报告完整迁移成功。
- 项目复制/导入映射记录 ID、模板引用和字段用途；同模板跨项目可保留字段 ID，异源模板有 ID 冲突时重发并重映射全部值与引用。
- 模板配置与条目值仍通过现有同步分别传输，但采用前必须通过 §17.2 的发布清单校验；即使只是同 ID 字段改义、没有未知键，也不能将旧值按新语义读取。未完成发布的代次不参与日常推送；拉到冲突先保留远端副本，不在本机迁移中间态上自动合并。
- 为 3.1.3 `atlasSchema` 做幂等迁移：复制字段定义、归档项和权限，原 `cf_` 值原地保留；只有作者确认的值转换才写新值。验证 ID、存储字符串和授权等价，不能把按明确旧缺陷过滤后的 AI 输出变化当成迁移失败。最后记录迁移完成，旧配置仅作恢复来源。
- 全库/项目正式备份始终带项目采用的模板快照，无须携带个人模板库；模板定义不属于 B3 可选携带的候选载荷。旧备份无模板快照时启用预设/图鉴兼容适配器。

### 3.7 T2：用途绑定与能力判定（P0）

普通自定义字段不必逐项绑定用途即可手填、搜索、供 AI 参考和补全。专用功能通过“内置语义默认绑定→模板发布者已确认绑定→本项目已确认覆盖”取值，本项目覆盖可明确解除旧绑定，未确认含义的字段不参与默认回退。没有绑定时先提供配置建议或使用通用资料审读，不根据相似名称静默认定含义，也不直接禁用整项 AI。T3 的历史含义确认不同于逐字段用途绑定；确认新名称及含义后，一般 AI 可直接阅读，无需为其配置专用用途。

语义目录优先从现有 `KIND_MAP.slots`、`settingLedger`、表单汇总、人物状态与 `WORLD_CONTEXT_GROUPS` 提取，保留它们现有的业务含义：人物身份、年龄/性别、外貌、性格、动机、能力/境界、技能、装备、背景、势力、地点、关系、首现章，以及势力/地理/物品/种族的已用槽位。未开放模板编辑的大纲和伏笔页由内置适配器声明事件、场景计划、编号/状态。首版不要另发明一套与抽取 JSON 不对应的分类。

用途注册表声明类型、单/多值、只读或可写、必要的状态/单位约束。多个字段可组合提供人物行为等文本依据；名称、状态、上级等标量用途要求唯一且明确的写入目标。不要把“多个原字段合并成一段资料”和“可把修改自动拆回多个字段”混为一谈。

状态值不能只认用户显示文字：绑定状态用途时，把本地选项显式映射到程序状态（如未登场/已登场/已退场）。没有确定映射的自定义状态保留为资料，不参与确定性检查。关闭自动功能不影响字段作为一般资料的使用。

`capabilitiesFor(projectId, tabId, operation)` 返回 `available / partial / unavailable`、使用路径、覆盖子项、缺少证据及修复建议。默认目标是保持操作可运行：只有没有允许使用的资料、没有可写目标或全部必要输入确实缺失时，才停止对应操作；不能按“未绑定一个用途”关闭整个面板。具体约定：

| 功能 | 适配方式 | 缺用途时的行为 |
|---|---|---|
| AI 读取、一般审读 | 同时提供语义摘要与允许参考的扩展字段，保留原标签和证据引用 | 无用途的资料仍进入通用阅读，告知上下文缺项，不整项停用 |
| AI 补全、对话引导 | 复用原动态 `TemplateField` 和 `deriveTopics`，目标按 ID、说明和类型提供 | 有普通自定义字段也能运行；仅无可写字段时停止写入，已有非空值不覆盖 |
| 人设语义检查 | 优先规范化行为/动机；缺映射时按原标签与说明审读全部允许的人物资料 | 返回有证据的观察并声明覆盖范围；只把无法核对的细项记为证据不足，不宣称全面通过 |
| 连续性/退场检查 | 确定性引擎读明确状态/引用；AI 一致性审读可读一般资料 | 只有精确状态子检查缺项；其他确定性检查和 AI 审读继续，不让模型猜测死亡状态补入数据库 |
| 关系图、地图、层级 | 用名称、关系端点、地点/上级的语义读取边界复用原可视化 | 缺精确关联只关闭该图层/连线，AI 仍可阅读允许的关系文字 |
| 拆书、补登、章后整理 | 复用原抽取、判重、证据及草稿审阅，映射已有槽位到真实字段 | 优先作者确认目标或选择“追加至指定资料字段”，只隔离无法安全回写的候选，其他条目继续 |

首次支持七页签时，相关专用消费者必须通过适配器读值；不能模板页面开放了替换，图谱和检查仍从固定中文列名取值。首版不让用户定义新的确定性检查规则或通用关系引擎。

### 3.8 AI 数据和结果的一致处理（P0）

- 直接上下文、对话引导、拆书补登的候选名单、向量索引和召回都用同一个有效字段权限。禁止参考、归档、类别不适用、弃用等字段的已存值不能从另一条链路重新进入模型；允许填写时的目标定义只按下文的独立授权发送。限制同样作用于程序从这些字段生成的摘要、语义投影、缓存、候选名单和诊断复用文本，不能只过滤原字段。
- 语义索引记录项目/来源/模板语义摘要；权限收紧立即屏蔽旧索引，完成清理重建后再使用。召回时再校验当前权限；索引尚未重建须显示状态，不用旧块凑数。
- 通用模板补全输出使用稳定字段 ID；已有拆书/整理等标准抽取协议保留原槽位 JSON，经语义写回适配器解析到字段 ID，避免为模板重写整套解析器。采纳时按**当前项目的当前模板**校验真实目标、类型、选项、类别、可写权限及基准。未知键、无法映射的旧槽位和非法值逐项回报，不能默认套到同名新字段。
- 保持现有 AI 参考与 AI 填写两个权限独立：禁止参考时，其**已存值**不得进入模型或向量；若作者仍允许填写，可发送必要目标定义（名称、类型、说明、选项）以填写空白字段，但不附带已有值。说明含作者不愿发送的资料时，可同时关闭填写。界面解释两类授权，不因迁移擅自关掉旧的允许填写项，更不能打开参考权限。非空字段仍按原补全策略本地锁定。此规则替代上一版“禁读即禁写”的新增限制。
- 字段说明和示例作为用户资料发送，不拼成可覆盖输出协议/权限的系统指令。能力用途不由模型自动授予，提示词修改也不能绕过程序权限。
- 生成新设定与抽取已有事实沿用不同规则：补全可生成候选；拆书/整理不能因字段必填就编造缺失事实，应留空或显示未找到依据。
- 工单、审读报告和章后整理结果保存当时的可读字段标签快照及稳定引用，便于历史阅读；执行时始终用当前有效模板校验。
- 直接上下文、世界摘要、对话引导、索引、召回及缓存统一消费 T0 的用途权限解析；Q2 复用工作区已有索引过滤。收紧权限时先撤销旧块的可用资格，再异步重建；解析权限失败的受影响字段不发送，其他已获授权资料仍可使用。详细规则见 §16.3。
- 每次真正发送及每次重试前，依据材料来源清单重查权限、含义确认及迁移状态；等待期间已变更则重组受影响材料或暂停。已经发出的请求无法撤回，收到结果标明依据变化并禁止自动应用；不承诺抹去服务商已收到的内容。

### 3.9 P0 模板验收与扩展边界

必须同时验证预设项目与空白自定义模板：字段改名/换组数据不丢；归档后仍可恢复；改名后原 AI 能按已确认语义正常工作；多字段组合仍能审读、非可逆回写需要确认；状态确实缺失时只将精确子检查记为未检；禁读值不进入上下文和旧向量但独立授权的空字段填写仍可用；相关模板变更拒绝旧结果、无关布局不误失效；备份与双设备往返保留定义/值；3.1.3 图鉴已有数据、图片、类别及权限迁移一致。

扩展到世界/力量/制度、大纲的编辑入口，以及全新自建资料页签，统一留到 3.2.x。P0 提前提供内置适配器并验证原 AI 行为；A2/A3 通过语义读取和通用字段证据取值，后续开放模板时复用同一链路。

### 3.10 复用优先的语义适配与可回写设计（P0）

#### 3.10.1 三层职责与唯一资料源

1. **模板展示层**决定作者看到哪些字段、怎样分组、字段叫什么。
2. **语义适配层**把字段投影为原功能理解的身份、动机、状态、地点等语义，并保留全部可参考的扩展资料。
3. **原功能执行层**继续调用原上下文组装、模型路由、抽取器、判重器、草稿审阅和提交器；只在取值/落点边界增加适配接口。

原存储键不因展示变化改写；语义视图不反向写成一份隐藏内置角色卡。内容更新、备份、同步仍围绕原记录，不能维护“用户模板一份、系统预设一份”并让两边长期同步。

语义条目至少返回 `{slot, value, sources:[{recordId,fieldId,quote?}], mappingId, transform, writableTarget?, limitations}`；投影内容和原始扩展字段按来源 ID 去重，控制上下文预算，避免把整份资料重复塞入模型。预算不足沿用原裁剪说明。

#### 3.10.2 映射方案与作者负担

- 从预设复制时直接继承已验证的字段用途和状态映射；同义改名经确认后保留用途，排序、换组无需重新配置。实质改变含义时按 T3 更新或解除受影响绑定，不能按稳定字段 ID 自动继承不适用的旧用途。
- 空白/外来模板导入时，先用标签、说明、类型和现有角色目录给**映射建议**；可显式调用已配置模型辅助建议，但不在每次写作前调用，也不把模型置信度当确认。作者一次确认后按模板版本保存，分享时一起带走。
- 不明确的字段仍作为普通扩展资料进入允许的 AI 阅读，不必逐字段完成用途映射才能使用续写、一般审读和补全。
- 提供“兼容现有 AI”检查页，列出每项功能采用哪些字段、可修复映射、仅缺哪些精确子项；给“指定字段”“保留现有用途”“作为补充资料”等操作。
- 模板发布时展示兼容等级，区分自动验证过的映射、作者声明映射、缺失项。接受任意自由模板，但只有通过相关语义与往返验证的模板才能宣称相应专用功能完整兼容。

#### 3.10.3 读取与写入的不对称处理

| 映射类型 | AI/旧引擎如何读取 | 生成结果如何写回 |
|---|---|---|
| 一对一字段，含确认含义不变的改名/换组 | 通过稳定 ID 取值，AI 使用当前名称及说明 | 类型、权限、基准校验后走原保存器；含义改变须先按 T3 调整绑定 |
| 多字段组成一个用途，如行为底线+触发点 | 按字段分别标注来源后合并阅读 | 不自动拆分覆盖；作者指定一个目标或逐项确认 |
| 同一长文本包含多个用途 | 可整体供语义审读；作者可选局部原文作为映射依据 | 没有确定可逆位置时只产候选，由作者选择追加或手动替换 |
| 状态/下拉标签与程序枚举不同 | 使用已确认枚举对照；未知值不强转 | 反向对照唯一才写入，否则留待选择 |
| 单位不同或需简单规范化 | 只允许注册并验证的纯转换，保留原值和单位 | 可逆且精度规则明确才回写；文本和数字混填不能猜算 |
| 没有对应字段的抽取事实 | 放入本次报告的待分配资料，不隐写旧预设列 | 作者选现有可写字段，或明确新建字段后确认；不得自动创造目标 |

首版只支持直接读取、文本聚合、已确认枚举和少量内置可逆转换。用户自写公式/脚本继续不开放。模型可以提出映射或修改候选，不能自行决定一个字段的正式业务含义。

#### 3.10.4 运行结果与失效范围

模板整体 `semanticDigest` 用于目录和索引版本；具体任务还记录**实际依赖的字段/映射摘要**。仅新增不参与该任务的字段或改无关布局，不使全部任务过期；实际读写字段的含义、值、权限、类别或映射变了才拒绝对应旧结果。按字段/来源重建索引，保留原项目范围的全量重建作为显式兜底。

已依赖整套人物资料或全书摘要的检查，新增相关可读资料仍可能改变结论，应标待重审；不能为了减少重跑故意漏记真实依赖。恢复旧任务时先判断是否可以通过同 ID 的等价映射继续，无法证明等价才重生成涉及步骤，不一律重跑整批。

### 3.11 现有 AI 兼容矩阵与接线清单（P0）

下列是本版必须完成的适配清单，适配优先于扩展新模板页签。以现有代码基线的入口和调用链为准，不以函数存在替代运行验证。

| 现有能力 | 主要复用位置 | 必须增加的边界适配及验收 |
|---|---|---|
| AI 新增/补全/对话引导 | `AITemplateFill`、`aiCompleteTemplate`、`deriveTopics`、图鉴类型校验 | 投递动态字段定义，已有值与权限分离；改名仍填对字段，普通字段不绑定也可用 |
| 世界资料摘要与全文上下文 | `buildWorldContext`、`buildProjectContext`、`atlasContext`、预算与保密过滤 | 固定字段选择改语义读取；只投射受影响来源，其他分段和裁剪规则复用；保留扩展资料 |
| AI 伴写/选区改稿/本章续写 | `aiInlineSuggest`、颉文姬编辑与上下文选择器 | 同一资料服务接入，原文本生成、建议段采纳及快捷键行为保留 |
| 逐章连写/创意写作 | `runAutoContinue`、`aiWorkflow`、`creativeSession` | 正文生成流程不重写；章后补登通过映射回真实字段，单条映射不明不终止已完成正文 |
| 一键拆书与设定汇总 | `bookbreak/run`、`flow/fieldMap`/`formMap`/`commit`、`aiExtractSettingEntities` | 保留已验证的标准抽取槽位；增加槽位到模板的翻译和待分配草稿，抽取证据/去重/人工闸门复用 |
| 设定补登/章后整理 | `settingLedger`、`chapterPostProcess`、原 UI 确认 | 人物/关系/状态用适配器取值与回写；未映射条目单独待处理，已映射项正常提交 |
| 主编诊断/人设审读/连续性 AI 检查 | 颉文姬审读与 `aiTasks/audit` | 原审读任务和报告形状尽量复用；传入语义资料和扩展字段、来源/覆盖说明，允许无显式用途的一般语义阅读 |
| 简报/卡文建议/情节推演 | `aiBriefing`、`aiContinuationAdvice`、`PlotCanvas` | 复用简报管线，只换读取边界；角色状态、待办伏笔和扩展资料不因改栏目名消失 |
| 语义检索与参考资料 | `semantic/indexer`/`inject`/`recall`、原知识库 | 字段权限、可读名称、映射来源进入索引；权限收紧屏蔽旧块，知识库独立正文不强行模板化 |
| 酒馆背景提炼/从小说角色转卡/剧情推演 | `tavern/world`、小说角色导入、原项目资料装配 | 只适配小说项目资料输入；酒馆自身角色、记忆、故事/剧本协议保持原实现，不能因模板没绑状态就关闭聊天 |
| AI 工单与本版候选 | `optimizeTicket`、B1/B2/B3 | 依据指向真实字段，按实际依赖验证；一条未检不阻止其他问题审阅应用 |
| 取名、术语去重、反馈分析等辅助 | 各现有专用任务与模型路由 | 用到资料者走读取适配；没有模板依赖者行为不变，不增加无关配置和模型调用 |

开工时为每行登记实际调用方、输入快照、可写目标和测试样本。先在预设模板上做新旧输入等价对照，再验证同义改名、拆分/合并字段、全新字段和确实缺资料五类变化。事实缺失可以报告证据不足；有资料且映射正确时，不能仅因不再使用原字段名而失去功能。

### 3.12 T3：字段改名与新增字段的 AI 理解统一（P0）

#### 3.12.1 目标与数据契约

旧字段改名、图鉴新增字段和自建模板字段统一为“稳定身份 + 当前名称 + 当前说明 + 类型/选项 + 权限 + 已确认用途”。AI 以当前名称和说明理解资料；程序以稳定身份取值和回写。更改名称不改变原存储键，不给旧内容复制一份隐藏预设数据。

- T0 有效字段增加或明确 `defaultLabel`（仅兼容/展示变更来源）、`label`、`description`、`meaningStatus`（confirmed/pending）、`bindingOverrides`（明确保留/替换/解除）及语义依据。具体字段可复用已有模板属性，不强制另建平行结构。
- 新增自定义字段发布时以其名称/说明作为作者声明，默认不绑定未知系统用途。内置字段未改名时继承原定义；旧字段新改名时通过下述确认形成含义声明。
- 读取投影使用当前标签和允许参考的值；回填目标使用稳定字段 ID。标准抽取仍复用原业务槽位 JSON，经当前已确认绑定翻译；已解除的用途必须明确阻断默认绑定回退，不能又从旧 `sourceKey` 推导回来。
- 模型材料不得出现“当前字段叫社会声望，但仍应按修炼境界理解”的隐藏约束。正确保留用途的同义改名可提供一致的语义说明；不同含义的旧名只保存在迁移/诊断信息中，不混进事实正文。

#### 3.12.2 修改入口与含义确认

复用 `FieldAliasButton` 与模板字段编辑器，保存时展示名称、说明、当前用途及受影响功能。区分：

| 作者选择 | 保存行为 | 原功能处理 |
|---|---|---|
| 只是换个叫法，含义不变（如所属势力→效忠组织） | 更新 label，保留可兼容的类型/说明/用途，说明中旧名称相冲突时要求修正 | AI 看到新名称；原势力关联和整理继续按原用途运行 |
| 字段含义也改变（如修炼境界→社会声望） | 编辑说明，检查选项/单位/类型，展示将解除或需替换的用途及现有值 | 社会声望按新义供一般阅读；不再参与境界判断，其他检查继续 |

确认只发生在字段编辑或历史迁移时，不在每次写作/调用前追问。批量同义改名可集中确认；系统可提示疑似含义冲突，不能凭名称或 AI 判断静默替作者决定。

类型/枚举/关系端点等结构能力仍受所在页签限制。T3 在未开放完整模板编辑的页签允许名称、说明和用途覆盖；需要更换不支持的结构时，保存变更计划并明确缺口，不能仅换标签就宣布结构转换成功。系统身份、编号、内部引用的含义不可通过改名替换。

含义改变不自动把“筑基”解释成声望等级，也不清除已有值。预览列出原数据，作者可保留原值作为待整理、明确映射或另建目标字段；保留待整理的值不得进入新义的专用自动判断/回写。一般阅读仅在作者明确允许参考后以“历史待整理值”标注发送；禁读值始终不发送。多义或含糊标签建议填写说明，不将说明填写强制扩展成所有普通字段的必填步骤。

#### 3.12.3 历史别名迁移与存储

1. 项目升级按旧 `fieldAlias::<tabId>` 扫描既有改名，逐字段建立稳定身份和别名来源；与图鉴 `cf_` 定义合并为同一有效结果，同名字段不能自动合并。没有别名的字段继承原定义，不要求全项目人工配置。
2. 首次展示项目级确认清单：旧名、新名、现有说明、当前用途、值样例与影响，支持批量标记“含义不变”和逐项调整含义。确认必须由作者提交，不能因升级默认视为全部已改义。
3. 待确认字段保留界面名称和数据，允许手工编辑；AI 不偷偷回退按旧名解释，也不推断新义。相关字段暂不进入上下文/索引，也不作为 AI 填写目标，说明未确认范围；只有确实依赖这些字段的精确子检查未检，其他授权资料继续可用。确认后再分别恢复其已授权的读/写能力。
4. 已采用模板的页签存入原 `projectTemplate32:<tabId>`；其他既有改名页签使用项目设置 `fieldDefinition32:<tabId>` 保存轻量覆盖（名称/说明/确认/绑定），由 T0 合并解析，不开放完整模板编辑。日后启用完整模板时先原样吸收覆盖，再停止旧覆盖的可写入口。
5. 迁移复用 T1 的备份、日志和幂等步骤。旧别名保留作恢复来源，迁移后原字段按钮写当前定义，不双写旧别名和新定义。未确认/已确认状态、定义及绑定随项目备份、导入、同步；个人模板导出只带已确认的结构，不带值样例。
6. 其他设备/导入包对同一字段的定义或确认产生冲突时保留两份依据，受影响字段暂停 AI 应用，待作者协调；不以最后到达的别名覆盖含义。旧版本不能理解新语义时沿用版本阻写策略，不宣称可以无损向旧客户端降级。

#### 3.12.4 消费入口、缓存与结果失效

T3 覆盖表格、表单与卡片的上下文渲染、`buildWorldContext`、补全/对话引导、拆书/补登/章后整理、语义索引与召回、搜索、导出及世界包。复用 §3.11 接线矩阵；独立酒馆字段不因项目别名变化改义，只有从项目引用或转换资料时遵守当前定义。

- 含义变化时解除受影响的旧用途；专用流程只消费已确认且类型兼容的绑定。未绑定资料仍以新名称/说明进入一般审读，不整项关闭 AI。
- label 变化即更新模型可见依据及相关索引文本；description、绑定、类型等变化按 F0 的实际依赖校验。布局/换组不误失效，无关字段不要求整批重生成。
- 改名或改义后先屏蔽相关旧索引/缓存，后台重建按 Q2 执行；当前字段配置读取失败不能回退成预设名称发送。历史报告保留当时名称快照，应用时检查当前依据；有语义变更的旧候选必须重新生成或人工处理。

#### 3.12.5 专项验收

| ID | 必验场景 | 通过要求 |
|---|---|---|
| T3-01 | 表格/表单/卡片内置字段同义改名，含七页签外原有改名入口 | 直接上下文、摘要、补全及原专用功能使用新名称，值不丢，回写原正确位置 |
| T3-02 | 修炼境界改为社会声望，保留原值与旧选项 | 说明/类型/选项冲突可见；旧境界用途不再生效，新义材料不夹带原含义；待整理值不被自动重解释 |
| T3-03 | 历史项目含别名、图鉴新增字段、重复显示名，尚未确认/批量确认/改义 | 稳定身份区分字段，状态可恢复，未确认值不发给 AI，无别名字段继续可用 |
| T3-04 | 同一业务内容分别使用改名内置字段和新增字段 | 一般 AI 按当前名称/说明得到一致的材料含义；只有已确认绑定决定专用用途，回填不靠名称猜测 |
| T3-05 | 改名/改义前已建索引、已生成报告/候选，另一设备同步新定义 | 旧块不可继续注入，受影响候选过期；无关字段与布局变化不连带作废，冲突有提示 |
| T3-06 | 多次迁移、迁移中断、项目复制/导出/恢复、世界包引用 | 定义/确认/绑定与值一致，无重复迁移或双写；历史版本按当时定义解释，无隐藏旧字段回写 |

T3 为 P0 发布条件。以上均为待实施规格和待执行验收，当前未修改产品代码，不能据本文宣称已统一。

## 4. 方向一 A1：当前章节资料工作区（P0）

### 4.1 作者操作

在正文编辑器现有“本章引用”抽屉内扩展为“本章资料”，包含“细纲 / 关联资料 / 正文引用”三个页内切换项：

- **细纲**：按有效模板分组展示已绑定字段，并通过用途突出事件、人物、场景、伏笔和衔接；预设模板目前有三个场景，组件不能写死三个场景槽。每项可跳到原细纲卡。无细纲时可绑定已有卡，或前往原页面新建。
- **关联资料**：作者搜索并固定角色、地点、伏笔、支线等记录；同时显示来源与当前值。自动命中的正文引用另标为“正文提及”，不等同于作者指定的出场计划。
- **正文引用**：复用现有引用扫描、高亮与计数，补上稳定记录引用；点击定位到具体资料项。

已有设定检索栏继续承担全局查找。右侧只打开一个工作抽屉，颉文姬与资料区通过现有容器切换或收起，避免窄窗叠加多个常驻列。默认不自动展开；切章只刷新内容，不重置正文光标。

### 4.2 规则与复用

- 抽屉是源数据的视图，编辑细纲仍走原 `OutlineSheet`；第一版不在编辑器另建细纲保存表单。
- 从模板用途绑定读取出场人物、伏笔操作等值，只对唯一命中的登记名称/编号提供建议引用；歧义结果要作者选，未绑定的自定义文字仍原样展示，不猜实体关系。
- D 档、停用记录可供作者查看，但进入 AI 上下文仍走既有保密、弃用、角色视角与预算过滤。手动固定不能越过这些过滤。
- 记录改名按 ID 跟随；记录删除显示失效引用和移除按钮；隐藏模块的自定义项目显示具体不可用原因。
- 固定到工作区只代表便于查看，不自动扩大 AI 授权或加入每个请求。调用前按任务选择实际资料；选中后再通过权限/预算过滤，发送清单注明未带入原因。Q4 的“必须材料”指本次明确选用的材料，不把所有固定资料视为必发。
- 规划板的“打开正文”“打开细纲”分别精确定位；不以细纲卡的排序替代正文顺序。

### 4.3 代码落点与验收

新增 `lib/revision/chapterContext.ts`、`components/editor/ChapterContextPanel.tsx`；接入 `NovelEditor.tsx`、`useNovelEditorModel.ts`、`OutlineSheet.tsx`、`App.tsx` 和 `WritingWorkflow.tsx`。编辑器只接容器及状态，不继续堆业务逻辑。

验收：同名章/重复章号不误绑；序章可手绑；切章/切项目不串资料；记录改名与删除正确；未保存草稿不丢；无模型完整可用；在 1280×720、1440×900、1920×1080 及 80%/100%/125% 缩放下保留正文可编辑空间，不绕过 3.1.2 的正文宽度保护。

## 5. 方向一 A2：细纲与实际正文对照（P1，可顺延 3.2.x）

本节以 T0/T2、A1 和 B1/B2/B3 为前置。P0 版本保留普通细纲查看与人工修订，不显示尚未交付的核对操作；相关结果类型可以先预留，但不能把预留类型计为已实现。

### 5.1 操作和输出

在“本章资料”的细纲项下提供“核对正文与细纲”；颉文姬整理完成后提供同一入口。调用前显示会使用本章正文、所绑定细纲和实际选择的资料；长文超过模型能力时使用已有规模门和证据门，不能截取后假称检查全章。

报告以计划项为行，列出：计划原文、完成情况、正文依据、作者处置。完成情况使用“已体现 / 部分体现 / 未找到体现 / 与计划不同 / 证据不足”，不把偏离计划自动定为写作错误。额外列出正文新增但计划未列出的关键变化。

作者可选择“保留这次变化”“加入修订工单”“去编辑细纲”。“保留”只记录本次核对决策；“编辑细纲”跳转原卡，AI 不直接重写已填计划。章后整理仍负责事实、关系等写入，本报告只链接到它，不复制其写入逻辑。

### 5.2 结构化结果和证据门

计划新增 `aiTasks/planCompare.ts`：复用模型路由 `review`、提示词登记与 AI 来源说明。每个结果包含 `planFieldId`、模板版本、`planQuote`、`status`、`bodyQuotes[]`、`reason`、`suggestion?`。计划字段来自模板用途或作者显式勾选的字段，旧 `planFieldKey` 只用于兼容解析；没有计划类用途时可由作者选择参与核对的内容，不擅自把全部备注当成计划。

- 程序按本次有效模板验证计划字段存在、允许参考、计划引文在该字段内；正文引文必须在本次正文快照内逐字命中，段号由本地计算。模板语义或用途变化后报告过期。
- 多处相同引文显示多个位置，作者选择定位；无命中标“未定位”，只能查看或手动处理。
- “未找到体现”属于检查判断，没有正文引文也可以展示，但不能据此自动生成执行指令；作者补充目标位置或明确修改要求后才能进入候选生成。
- 不因模型返回高置信度跳过定位校验；列表最多 20 项，超出时标明结果数量限制。
- 新生成的报告替代当前展示版本；旧版本可在本版任务记录内查看，不能混用两份报告的选中状态。

### 5.3 验收

覆盖按计划完成、部分完成、主动偏离、没有细纲、重复章号、找不到原文、正文改后报告过期、作者确认偏离后再次改稿等场景。报告生成过程对正文与细纲零写入；保留/弃用选择不创建新设定。

## 6. 方向一 A3：有证据的后续影响提示（确定性版 P1；AI 复核后续）

本节依赖模板用途、记录变化事件和稳定引用。未纳入本版时，B2 继续调用已有粗粒度 `futureImpact` 提醒，不要求未实现的 `futureImpact32`，也不显示“已精确分析影响”。

### 6.1 触发范围

在现有正文改写提醒上，补以下“实际变化”事件：作者/AI 修改已写章的正文，修改或删除绑定状态、关系、伏笔等用途的资料，修改世界设定及力量体系条目，切换活跃子项。无用途的自定义字段变化只标为一般资料变化，不猜因果。纯布局/主题不触发；字段含义、类型、权限或用途变化先使旧影响结论过期。

新增叶子模块 `lib/revision/changeEvents.ts`，由相关数据保存器提交前后引用与内容摘要；事件在项目内按记录合并，保存/输入防抖不应产生每个按键一条提醒。覆盖 `db/chapters.ts`、`db/tabs.ts`、`db/worldSets.ts` 等真实写入入口，而不是只在某一个 UI 按钮里接线。

标题或正文改动无法直接判断语义时标“正文发生变化”。作者可以在章后整理中选“这次涉及哪些资料”帮助缩小范围，不能把任意文字润色直接描述成角色事实改变。

### 6.2 两层结果

1. **直接依据（P1）**：检查后续细纲的显式资料关联、通过用途读取的旧名/新名及别称、伏笔编号；显示字段稳定 ID、标签快照与短引文。使用修改前后章序快照处理重排；既有 ID 优先，编号只辅助匹配。
2. **相关性复核（3.2.x）**：作者显式勾选候选后，AI 读取变化前后值及这些未来计划，给“可能冲突 / 可能无关 / 无法判断”和理由。必须引用实际提供的计划及变化，未定位结果不能升级成明确冲突。

送入模型前重新执行现有弃用/保密/角色视角规则。D 档资料与不允许暴露的前后值均不发送，不能因为它们出现在本地变化日志里就绕过过滤；可见性变化本身计入基准失效条件。被过滤的来源只给作者本地提示“这部分未参与 AI 复核”。

没有直接命中时，继续显示已有粗粒度“后续计划建议复核”，明确“尚未定位直接关联”。不能得出“没有影响”。不沿人物关系图自动扩散无限多跳。

### 6.3 提醒模型与处置

项目设置使用 `futureImpact32`：`schema:2`，按 `changeId` 存来源记录、模板语义摘要、前后内容摘要、原因、时间和有限短引文；按目标细纲 ID 存 `targetRef`、`matchedFieldId`、标签快照、引文、目标摘要、关联等级与处置；旧字段键只由适配器解释。

- `changeId` 使用来源引用、变化前后摘要生成，重复保存同一变化不重复新增。
- 每条可跳转来源和目标；可标“已检查，无需修改”或“待修改”；新的变化必须产生新的处置状态。
- 已写章节列为“已有正文需复查”，未写细纲列为“未来计划需复查”，不把所有后续章节都叫尚未开写。
- 原 `futureImpact` 老标记仍可读，显示为“旧版范围提醒”；只有能唯一解析的才绑定 ID，歧义时保持范围提醒，不自动删除旧信息。
- 上限：每项目保留最近 100 个变化事件、最多 500 条目标提醒；每条引文不超过 300 字。触顶先清已处理历史，仍超限则显示汇总与“其余待复查数量”，不能静默丢未处理提醒。

验收：改名可用旧名找到计划；同名角色不会被判成唯一因果；重排后仍定位原细纲；删记录有依据；无模型显示直接提及；同一次变化去重；已处理的旧变化不能屏蔽新变化。

## 7. 方向二 B1：AI 检查结果进入现有工单（P0）

### 7.1 入口与范围

增强现有“全书优化工单”，提供全部/按卷/手选章范围。`buildTicket({chapterIds})` 已有范围参数，先将它接到 UI。默认执行可用的免费本地检查；另勾选“AI 编辑意见 / AI 人设检查 / AI 爽点毒点”。执行前按有效模板判定实际资料和覆盖范围：缺少精确状态映射只影响相应确定性子检查；一般人物资料仍可供 AI 审读。不把“没有预设字段名”当成没有人设资料，也不给整批笼统的“全部通过”。

开始前显示非空目标章数、检查类型、各类型模型、预计请求次数和输入规模估算；不能将字符估算显示成精确价格。每批上限 20 章，AI 默认逐章串行，章内所选检查逐项执行；其他无关任务仍使用现有并行机制。

### 7.2 报告转工单

- 增加 `lib/revision/findingAdapters.ts`，将现有 AI 结果归一到工单扩展结构，保留原报告来源；P1 A2 实现后再登记其适配器，P0 不依赖 A2。
- 原 `aiChapterReview()` 的 `warnings[]` 是文本，不能凭文字猜章节或原文位置。为工单用途新增结构化检查接口 `aiReviewFindings()`，复用现有审读规则、模型路由和提示词管理，返回明确的证据与建议；原审读面板接口继续兼容。
- OOC 已有原文 `evidence`，先做本地定位；设定依据增加 `RecordRef + fieldId + quote + templateBasis`。人设约束优先语义投影，也允许依据可读扩展资料提出有原文证据的观察，所有结论注明依据；禁止固定读原角色卡字段。爽点结果同样适配；没有位置的抽象建议只作人工待办。
- 扩展 `TicketItem`：`originReportId`、`evidence[]`、`basis`、`capabilitySnapshot`、`disposition`、`runnableReason`；P1 A2 使用新增来源 `plan-compare`。归档/迁移后找不到的依据保留可读，但不可执行。
- 默认不勾选执行。按来源、章、严重度筛选；保留按章与按问题类型两种视图。
- 去重键使用“章 ID + 来源 + 定位证据摘要 + 问题类别”；无证据文本才退回旧标题规则。跨来源相似问题显示为同一章的一组，保留各自依据，不让模型自动删除“看起来重复”的问题。
- 既有颉文姬审读/OOC/爽点结果增加“加入工单”入口，复用本次已生成结果，不能偷偷重新调用模型。

### 7.3 执行边界和验收

历史章仍按 `resolveAction()` 限定动作；人物动机、事实或伏笔冲突默认手动处置，必须区分“改措辞”和“改事实”。有证据不等于允许自动改变设定。

验收：只选本地检查零模型调用；指定一卷不检查其他卷；单章失败显示漏检与重试位置，不能报告“全部检查完成无问题”；正文改变后旧报告不能执行；检查途中取消保留已完成报告；未定位问题不能混进自动候选队列。

Q1 的检查状态同时接入逐章连写自检和原审校面板，不能仅修 B1 新入口。Q8 的证据验证复用本节适配器；资料缺失、解析失败、引文无法定位分别显示，成功无问题只能来自有效的空清单。现有流水线的自检失败时保留生成草稿并等待作者选择重试、审阅或明确继续，不能自动显示自检通过并继续无人确认的落库步骤。

## 8. 方向二 B2：先生成修改候选，再审阅应用（P0）

### 8.1 新流程

现有“执行选中”调整为“生成修改候选”。相同章节的问题合成一次请求，生成整章候选，与原稿进行逐行对照。作者逐章选择“应用本章 / 放弃候选 / 修改要求后重生成”。首版按整章应用，避免承诺尚未设计的任意差异块合并。

候选生成对原正文、设定表和章节状态均零写入。生成完成不等于问题已修复；工单只有在正文实际应用成功后才显示“已应用”。没有重新检查前显示“修复效果待复核”。

### 8.2 生成与应用

- `runTicketChapter()` 拆为 `generateTicketCandidate()` 和 `applyTicketCandidate()`；生成继续复用 `aiRewriteChapter()`，应用统一走 F0。
- 每个候选包含目标章、问题 ID 集合、生成要求、基准、候选全文引用、改前内容引用、内容摘要和状态。
- 去除提示词包装、检测空输出与异常字数，沿用 `isSuspectRewrite()`；异常候选可以查看和复制，但应用前需明确复核。长正文超过载荷上限不截断，标明本章无法保存候选，允许导出后手动处理。
- 提交前正文已变则使候选过期，不尝试自动拼接。重复点应用使用候选 ID 和目标摘要判重，不能重复记字数、重复补登或重复快照。
- 最新章应用后沿用已有设定补登策略和执行器，先经语义写回适配；映射不明确的事实进入待分配候选，已映射项仍正常处理。失败回执区分“正文已应用，资料整理失败”和“部分资料待分配”，只重试涉及步骤，不重复改稿。
- AI 设定补登候选的采纳也补基准校验。当前章后整理返回的指纹未贯穿 UI 提交；本版需保存完整报告基准并在 `commitPost` 前验证，防止拿旧抽取结果更新新状态。
- 原专用落点通过 T2 语义写回接口翻译，复用 `KIND_MAP` 等抽取槽位和原保存器；缺少可写目标时提供指定字段/追加至选定字段的候选审阅，不创建隐藏旧列。实际依赖的语义或权限变化才重新核对候选。
- 精细影响分析 A3 未启用时调用已有范围提醒；不能把 A3 作为本章应用成功的必要步骤。
- Q3 同步覆盖原手动改写、票据改写、逐章连写补齐已有末章和章后整理。已有章节/资料更新必须携带生成基准并经条件写入；新增章按锚点、目标卷与 ID 检查冲突。逐条回执只移除真正成功的整理项，失败/待分配项保留原候选与重试入口，不重新调用模型抽取。

### 8.3 中断后的确定性恢复

提交意图必须在改正文前持久化。若应用后、回执写入前崩溃，启动时同时核对 `operationId`、主记录修订与正文摘要：

| 当前内容 | 恢复行为 |
|---|---|
| 主记录有本次提交标记，正文仍与目标相同 | 标为已应用，仅幂等补回执/派生数据；不重复改稿与 AI 字数统计 |
| 主记录有本次提交标记，之后正文又被编辑 | 标为曾应用、后续已变；保留操作历史，不写回旧候选。派生数据按当前修订重建或提示待核对 |
| 无本次提交标记，修订与应用前基准均未变 | 标为待作者重新确认；不自动应用 |
| 无本次提交标记，但正文恰好等于候选目标，或与前后均不同 | 标为需人工核对，不能仅凭相同文本认领一次 AI 提交；不自动回滚、不补记 AI 字数 |

“应用前旧稿”和候选保留在本地载荷中，不能只依靠可能被轮换掉的时光机快照。回滚使用既有版本恢复入口，并说明它会替换该章；整卷应用不提供伪装成原子事务的“一键全卷撤销”。

验收：生成候选前后正文完全一致；双击应用一次生效；生成时手动改稿后拒绝旧候选；快照失败不动正文；写盘失败不显示成功；故障发生在提交各阶段均能按上表恢复；历史章动作限制仍有效。

## 9. 方向二 B3：限定范围的任务与候选持久化（P0）

### 9.1 覆盖范围和状态

P0 覆盖 B1 检查与 B2 候选修订，P1 A2 启用后复用相同存储。复用任务中心的运行状态、提示和中止，不改变已有任务的全局并行策略。新增 `revisionJobRunner` 绑定持久化任务 ID。Q1 连写自检暂停时只额外保存当前章草稿、基准、检查状态及来源会话引用；恢复为“待人工审阅”，不自动续完整连写流程。Q6/Q7 的通用追踪不扩成其他所有原流程的产物恢复。模板迁移使用独立 T1 日志。

任务状态：`queued → running → awaiting-review → completed`，允许进入 `paused / failed / cancelled / interrupted`。候选状态：`pending / stale / applying / applied / discarded / needs-reconcile`。

通用任务中心的执行结束、单步骤 Q1 结果和待审候选状态分层映射，详见 §17.1；模型请求已结束不等于候选已审阅。批次生成完成但仍有 pending/stale 候选时保持 awaiting-review；作者可归档为已结束但未采纳，不能自动计入已修复。

- 启动后将遗留 `running` 标为 `interrupted`；`applying` 按 B2 的提交意图核对。
- “继续”只从尚未完成的章/检查项开始。被中断的单次模型请求重新调用，并提前说明可能再次产生调用量。
- 已完成且基准未变的报告/候选直接恢复；基准变化的单独标过期；不重跑整批。
- “取消”停止后续请求并保留已完成产物，“删除草稿”另设操作；切页签不取消，切项目遵守已有退出处理，任务永远绑定启动时项目 ID。
- 首版允许多个只读检查并行；同章的候选应用按 F0 互斥。同章有另一份候选时提示，应用一份后另一份应失效。
- 同一批次使用单一执行租约/代次，多个窗口不能同时“继续”并重复发送请求；租约丢失或项目删除后的迟到回调不得重新创建任务、载荷或资料。切项目后的回调只更新原项目结果，不向当前编辑器注入文本。
- 恢复时校验记录与实际依赖字段/映射：布局、无关字段变化可继续；相关结构/用途/权限变化时保留产物可读，列出需要重跑的涉及步骤，不重跑整批。

### 9.2 存储设计

采用两个新增 store，避免把正文候选写入整库设置或运行账本：

| store | 记录内容 | 物理布局与生命周期 |
|---|---|---|
| `revisionJobs` | ID、项目 ID、任务类型、范围、参数、状态、步骤计数、基准、报告/候选载荷引用、提交意图与回执 | 小元数据留主库，按项目索引 |
| `revisionPayloads` | 不可变报告、改前文本、候选全文、Q1 暂停草稿及摘要；每次重生成用新载荷 ID | 桌面/便携按 ID 外置，IDB 独立 store；按需读取 |

载荷写入成功并回读摘要一致后才发布元数据引用；元数据写入失败可留下可清理孤儿，不能留下看得见却打不开的“成功候选”。现有 sidecar 的普通写入可能仅告警，新增严格写入路径必须向调用方返回失败，禁止把 `ops.put()` 无异常等同于磁盘成功。

容量初值：每批最多 20 章；每个正文载荷 UTF-8 序列化上限 256 KiB；每项目最多 5 个未结束批次、200 个载荷（包含报告、改前稿、候选和暂停草稿）、总载荷 32 MiB；全库总量 128 MiB。报告超单项上限可按完整条目分块，不截断 JSON 或引文。awaiting-review/paused/interrupted 均计入未结束批次；归档只结束执行，不豁免其仍保留的载荷额度。

容量按实际字节统计并在并行分配时预留，开始单章生成前预留改前稿/候选空间；空间不足不先烧模型额度再放弃保存。已应用/已放弃且未被其他记录引用的载荷保留 30 天；待审、过期、未结清提交和主动导出中的载荷不自动删。清理先核对所有引用，孤儿留出宽限期，避免删除刚写好尚未挂引用的载荷。触顶停止新增并提供导出/清理，不自动丢未审资料。

列表只读元数据；打开某章才加载正文和 diff。量级验收目标为 500 章项目、200 个载荷下列表首屏不预读全部候选，目标交互就绪不超过 300 ms（需注明测试机与测量范围；超标先定位，不能把目标写成结果）。

### 9.3 三端、同步、备份与导入

- 本次修订核对 IDB 为 13，若开工基线不变，新增迁移为 13→14；否则顺延。新安装和升级路径都创建两个 store 与 `projectId` 索引。T0/T1 定义复用现有设置/元数据，不额外预占另一套迁移号，统一由 W2 汇总发布迁移。
- 同步更新 `desktop.KEY_PATHS`、便携主键表、同步 store 清单及主键映射、测试内存后端；两种候选 store 同时列入 `LOCAL_ONLY_STORES`。它们不随日常云同步搬运；已应用正文仍按已有规则同步。界面注明“待处理报告与候选仅保存在本机”。

- 当前 3.1 读取路径未查到完整的未来格式版本拒写保护，因此仅提升版本号不能保证已安装旧程序会自行拒绝新库。3.2 首次升级前保留独立的 3.1 可恢复备份；发布说明明确同一数据目录不支持新旧程序混用，降级须在隔离目录恢复升级前备份。若发布要求旧客户端也强制拒写，需要另发 3.1 兼容补丁；本方案不把这件事冒充已解决。
- 全库导入/导出带齐候选载荷。项目 JSON/迁移包提供“携带未处理报告与候选”，有产物时默认勾选并显示体积；`ProjectBundle` 增加可选的两个字段，旧包缺字段正常读取。
- 项目采用的模板定义、字段用途和正式资料值始终随正式项目备份/同步，不受候选携带开关影响。个人模板库是独立本机资源，模板 ID 缺失不影响项目按内嵌快照打开。
- 自动项目备份默认只备份正式创作数据，不循环复制候选载荷；用户手动导出可携带。该差异需写入帮助说明。

- 导入新项目：重发任务/载荷 ID，映射目标章/卷/卡/行引用，统一设为需重新核对，保留候选可读与复制；不得恢复为运行中，也不自动应用。无法映射的对象标缺失。
- 同项目恢复旧备份：本机已有草稿保留但强制重新校验；已不存在的目标标不可应用。删除项目级联清理这两个 store 的元数据及外置载荷；备份孤儿清理机制扩展到新载荷，先展示可核对清单。

### 10.2 C2：选择性更新（后续候选，独立规格）

使用“上次已引入基线 B、当前项目 L、目标世界版本 R”三方比较：

| 情况 | 默认处置 |
|---|---|
| L=B，R 改变 | 可选更新，默认仍需勾选 |
| R=B，L 改变 | 保留本地 |
| L=R | 无需写入 |
| L 与 R 均不同于 B | 冲突，逐项选择保留本地/采用源字段 |
| 源删除、本地有修改 | 保留并提示，禁止默认删除 |

前置：现有引入重新生成行 ID，只有 `worldImport` 的版本与整体指纹，不能直接靠行 ID 三方比较。为新的引入增加“源行 ID→本地 ID”映射与每字段基线摘要；老项目没有映射时先人工建立或继续整包引入，不用同名自动套用。基线源版本缺失时只能查看两方差异，不能声称可自动合并。

只更新部分字段后，不把项目溯源改成“已完整更新至 vN”；每项分别记录接受基线，其余继续保留原基线。此项预计 8–14 人日，依赖 C1 和额外的数据映射评审，不进入 3.2.0 必交付范围。

C1/C2 顺延不代表可以忽略当前世界包功能。T2 必须为现有抽包、封存、指纹、引入携带“实际用到的字段定义/用途/模板语义依据”，扩展目前部分图鉴字段的搬运方式。引入到异源模板时先预览映射和权限差异，定义冲突未解决时拒绝相关写入，不能覆盖整个目标项目模板。模板定义变化计入新世界包内容指纹，旧包按兼容适配器读取；不把当前项目的模板自动追写到已有不可变版本。

### 16.2 Q1：可区分、可汇总的结果状态（P0）

**实施位置：** 扩展 `ai/aiParse.ts` 的详细解析接口，新增轻量 `TaskResult<T>` 约定；迁移 `aiTasks/*`、逐章连写自检、原审校 UI、整理及 B1。保留原数组/字符串签名作为过渡包装，受影响调用者必须使用详细结果，不能仅新增类型却沿用空数组兜底。

- 解析结果包含 `valid / repaired / invalid`、数据、缺字段/类型错误及是否截断。合法 `[]` 是有效空结果；缺键、非预期对象、残缺 JSON 和无法恢复的文本不是“无问题”。修复后只保留已验证完整条目，丢弃条目记入诊断。
- 执行结果包含 `completed / partial / failed / cancelled / skipped / incomplete`，以及 `coverage`、`issues`、`errorCode`、`retryable`、来源 ID。完整性与数据有效性分别记录，HTTP 200 不直接等于任务完成。
- `coverage` 按章和检查项记录 requested/completed/failed/skipped；摘要显示“完成 X/Y 项，发现 N 条问题”，有缺项时不显示全面通过。评分缺失显示“未评分”，不填 0 分。
- 逐章连写自检对“本次已启用且承诺执行的必选项”发生失败/未完成时暂停后续自动应用；保留草稿，允许作者重试、审阅或明确跳过。启动前已声明资料不足的精确子检查不纳入承诺覆盖，但始终显示未检；一般审读继续，不让自由模板因缺一个用途每章都被迫暂停。运行中才发现材料不足则更新覆盖并要求本次处置，不能伪装完成。用户取消立即传播，不能被 catch 改为空结果继续连写。
- 必选项的 skipped/incomplete/partial 同样不等于通过；“明确跳过”记录本次作者决策和覆盖缺项，不改变原报告。自检暂停按 B3 保存最小草稿检查点，写失败时保留当前内存草稿并提供导出，禁止把未保存草稿显示为可重启恢复。
- 不增加所有功能统一的额外弹窗：原面板显示结果状态；需要自动推进的工作流才增加暂停决策。整理/补登失败保留已生成结果，不为纠正状态再调用一次模型。

**验收：** 合法空数组、无效 JSON、修复部分成功、缺字段、超时、拒答、取消分别有正确状态；三项自检中一项失败不能显示通过；评分解析失败不能展示 0 分健康度；重试只执行失败项。

### 16.3 Q2：权限、索引与召回同源（P0，合入 WT2）

**实施位置：** T0 有效字段解析 → `atlasContext` / `tableRender` / `aiCore/template` → `semantic/indexer` / `store` / `recall` / `inject`，知识库挂载权限与缓存使用相同的任务可用性判据。保留资料类别/角色视角等原有规则，不把项目作者资料的授权套到无关酒馆会话。

1. 复用 R04 的字段过滤，将图鉴特例扩为 T0 结果。每个索引块携带来源引用、内容摘要、权限/模板依据及涉及的字段 ID；多字段混合块不能只删除显示标签而留下禁读值。
2. 权限收紧、归档、类别变化、字段语义改变或来源删除时，先在本地将受影响旧块/缓存标为不可用，再异步重建；关闭软件或重建失败也不能使旧块重新可读。提升权限可等待重建，不读取未经批准的历史缓存。
3. 召回最终注入前再次加载当前权限与来源状态。块中任一字段失效时丢弃该块或从当前授权值重建，不能把旧原文直接注入。没有权限依据的历史块先隔离，完成升级/重建后再使用。
4. 读取权限配置失败时，对无法证明授权的字段停止发送，返回缺项说明；既有公开内置字段和其他权限已确认来源可继续。未知 `cf_*` 不以“自定义字段”兜底泄露其值。
5. 保留可读、可写的独立授权；只写空字段时仅发送必要的目标定义，不发送非空禁读值。模板库、缓存和索引不能成为第二套正式资料源。
6. “有效配置但全部禁读/归档，解析结果为空”必须返回权威空集合，与“非模板资料”及“配置读取失败”分开；禁止把空集合变成 `undefined` 后重新遍历全部旧字段值。
7. 程序派生摘要/缓存携带来源依赖并在复用前复查；无法证明来源授权的旧派生缓存先隔离。作者独立编写的正文、主动选择的附件按其自身来源规则处理，不承诺通过字符串匹配追溯所有历史复制内容，也不因此删除作者正文。

**验收：** 先索引含唯一标记值的字段，再关闭参考权限，在不重建、重建失败、重启和缓存命中四种情况下均不能发送该值；归档、类别改变、全部禁读/归档导致规则为空，以及配置读取失败同样验证。允许写但禁读的空字段仍可补全。

- 装配结果返回 `MaterialManifest`：实际来源引用/读取修订、字段定义及权限依据、包含/裁剪范围、输出协议和预算。直接传给本次调用与 F0，不在生成结束后重新读取最新记录作为“当时依据”。发送前按 §3.8 复核；多次读取跨越了资料变更则重组受影响材料。
- 保持模型窗口、资料预算和输入/输出 token 的单位独立；推理输出预算计入输出预留。本地模型采用实际加载上下文上限，不能仅按模型理论窗口扩大资料。取不到可靠容量时走已声明的保守配置并显示估算来源。

**验收：** 分工模型窗口不同仍各用实际预算；当前指令与必要原文保留；资料超限明确申报；重复来源不多次占预算；历史审查不会把未知状态定为事实冲突；长篇样本记录关键资料覆盖与延迟。

### 16.6 Q5：输出结构、推理需求与能力配置（P0）

**实施位置：** 扩展原 `ChatOptions` 和任务元数据，复用 `modelSampling`、`promptSettings`、`aiParse`；新增能力解析小模块，不新增服务商专用业务生成器。

- 任务分别声明 `output: text | json-object | json-schema`、`reasoning: default | off | required`、schema 版本和输出预算。旧 `json:true` 在兼容包装中保留原默认，逐条迁移后由任务明确决定；不能全局改变旧调用的温度和思考行为。
- provider 能力记录结构输出方式、思考开关、可接受参数及来源（用户配置/隔离验证/未知），同一兼容接口不按模型名字一律认定能力。未知接口先使用原文本约束路径；按作者主动测试或明确配置启用新增协议，不对所有模型自动发送付费探测。
- 抽取/导入可使用低温；大纲/设定允许独立保留推理。端点不支持单次“推理＋结构”时沿用可用路径并说明限制；不默认增加“先构思再整理”的第二次调用。额外调用必须由相应功能显式启用并计入请求估算。
- 本地 `format` 与云端结构格式仅在能力确认后下发。动态补全 schema 与 T0 字段定义同源；拆书/标准抽取使用原业务槽位 schema，再经 T2 目标映射校验。不能把保留的标准槽位键一律当成未知字段 ID 拒绝，也不能据槽位键直接写原列。格式约束不能代替本地授权和语义校验。
- 元数据记录 finish reason、截断、拒答及修复情况；`length` 或未完成流进入 incomplete。截断长文可保留为草稿，未经作者审阅不能直接覆盖原文；抽取只保留已验证条目并标部分完成。
- 参数不支持时仅移除被明确拒绝的可选参数；不把所有 400 都重试成裸请求。失败原因及每次降级均留在同一逻辑调用的尝试记录。

**验收：** 同一结构任务可独立选择允许推理；支持和不支持 schema 的端点都能工作；未知字段/错误枚举无法写库；截断不显示完成；旧 provider 配置迁移不偷偷改用户采样参数。

### 16.7 Q6：流式生命周期与受限重试（P0）

**实施位置：** 修改 `fetchWithTimeout` / `readSSE` / `chat` 的资源所有权。取消监听和 reader 由一次调用持有，直到响应体消费完毕、失败或主动取消后统一释放。

- 分开处理首响应、首个有效输出与后续空闲期限。保留原首响应默认值，流式空闲初始建议 120 秒且可随 provider 配置；有有效内容或协议认可的推理进展才重置，心跳不能无限维持任务。长篇有持续输出时不受固定总时长一刀切限制。
- 响应头之后取消必须中断底层 fetch/reader，停止本轮生成、重试及尚未开始的应用；已进入主记录提交的操作按 §3.3 结清核对，不能声称回滚。取消不保证服务商停止计费，界面与账本只记录客户端已停止。
- 识别 SSE 错误事件、结束标记、finish reason 与异常断流；HTTP 200 之后的错误不能作为成功。保留已收到片段并交 Q1 标记 incomplete；不把片段拼接到一次全新生成的结果上。
- 结束判据按协议能力登记：有正式结束标记的端点缺标记视为不完整；已确认以正常 EOF 结束的兼容端点可接受 EOF，但记录 finishReason 未知。不能把所有无 usage/无 finish reason 的旧兼容端点都判坏；网络异常和显式 length 仍按不完整处理。
- 429 中区分配额耗尽与暂时限流，401/403、拒答、取消和校验错误不自动重试。临时网络/5xx/限流仅在尚无输出且原因允许时重试；遵守 Retry-After，自动等待上限 30 秒，超过转交用户选择。
- 每次逻辑调用默认最多两次实际请求；已登记的旧接口三级参数兼容路径允许上限三次，并在同一尝试预算内计数，不能三级降级之后再额外乘两轮网络重试。成功能力缓存到端点配置摘要，配置变化后失效。已输出后默认不自动重新生成；用户手动重试显示可能再次消耗额度。重试前验证取消与任务基准。
- 在逻辑调用预算之外增加批次/步骤总请求预算，计入补字、压缩、自检、设定整理、降级与重试，明确显示预计范围和上限；上限到达暂停而非嵌套追加。不同任务仍真并行，不设全局强制排队；同一资源仅提交短时互斥。无法确认远端是否接收的断网记为“结果未知”，不承诺重试免重复计费。

**验收：** 响应头后/生成中停止不触发新的应用；提交已持久化则保留已应用回执；首输出后停滞能结束等待；断流保留草稿且不报完成；配额耗尽不反复请求；重试次数可核对。

### 16.8 Q7：并行追踪、真实用量与提示词依据（P0）

**实施位置：** `aiCore/usage` / `chat` → `aiRunLedger` / `aiRunTypes` / `db/aiRuns`，上下文返回对象，提示词注册与设置面板。复用原账本存储、任务中心和 B3 的统一迁移，不维护另一份任务执行状态。

- 每次任务显式传入关联对象 `{projectId,taskId,stepId,callId,attemptId}`；任务外单次调用也有独立 ID。用按 ID 分发的回执替换单个全局订阅和活动任务变量。两个任务交错结束时，各自保存自己的调用和上下文。
- 从非流式响应与流式尾包提取服务端 usage，Ollama 按实际返回计数读取。记录输入/输出、可获得的缓存/推理 token、耗时、首输出延迟、结束原因和成功/失败；不提供的值保存 unknown，估算另列且不能显示为 0 或精确费用。
- 同一逻辑调用的每次实际请求独立计数，包括降级和重试；包括嵌入与外部搜索在内的外部调用登记服务类型、次数、耗时及可获得的 usage，不能把未知费用填 0。用途路由固定到步骤；所有 §3.11 入口及市场雷达、取名、酒馆辅助调用登记覆盖情况。
- 装配直接返回带来源引用/摘要、裁剪与遗漏、检索状态的快照，由当前调用接收。记录功能提示词版本、用户覆盖摘要、实际模型参数、模板语义与可读权限依据，不在默认账本保存密钥或完整正文。
- 完整提示词/上下文仅在作者主动开启本机复盘时保存，遵循项目权限并可删除；默认仅摘要和诊断。原文后来变更时只能显示“当时依据摘要”，不能宣称可精确重放。即使保留了完整请求，随机模型也不保证逐字复现。
- 独立调用使用轻量运行记录；沿用账本 schema 迁移默认值，缺失旧字段显示 unknown。每项目诊断明细初始上限为 500 条已结束记录或 8 MiB，达到上限汇总并轮换无候选/提交引用的旧明细；活动任务和被引用依据不删除。无法继续保存时提示统计不完整，不能使 AI 调用失败，也不能将候选全文塞入该额度。
- 提示词编辑增加当前默认版本、用户覆盖及兼容诊断。默认升级后保留用户覆盖并提示差异；不自动用新默认覆盖用户内容，也不允许提示词授予字段读取/回写权限。
- 用量/诊断写入是旁路，可失败而不打断生成；候选载荷、提交意图和主记录持久化是关键路径，失败必须停止相应应用。原账本中缺少项目 ID 的全局服务调用不强塞进当前小说；使用明确的全局作用域，切项目不改变归属。

**验收：** 两个任务加一个无父调用交错运行不串账；缺 usage 显示未知；降级两次就计两次；各候选关联自己的快照；导出诊断不含凭证；旧账本可读；统计写入失败不影响生成。

### 16.9 Q8：文本守卫、审校证据与质量对照（基础 P0，深化 P1）

**P0 实施：** 复用原文风指纹、去 AI 味和字数校准，在生成器输出边界增加确定性检查，证据适配使用 B1 的 `findingAdapters`。

- 检测空输出、未结束/截断、异常缩水、整段精确重复、续写重复粘贴前文、无效结构及未知目标字段。提醒绑定具体片段，不能因简单启发式就删除原文或强迫重跑。
- 审校返回证据引用、原文、定位结果、规则类别、判断性质（事实冲突/疑点/写作建议）及实际检查范围。引文必须在当前来源中本地核对；同名、重复引文或不存在引用标为歧义/未定位，不能成为可执行修订依据。
- 事实与动机核查不能仅靠关键词出现判通过。P0 允许保留人工审阅提示；跨工具相似问题可分组，冲突建议并列并保留来源，不由模型默默取舍。
- 补写/压缩沿用原轮数上限，并增加无进展/重复输出终止。实际请求累计进入 Q7；字数仍不足或超限显示原因，不悄悄硬截正文，不以更多隐性重试凑字数。

**固定对照样本：** 在 M0 从可使用的本机材料冻结不少于 24 个用例，覆盖补全/抽取、续写/伴写、改写/压缩、审校/证据、长篇召回、酒馆/记忆六类，各至少 4 例；各类包含错误或边界情形。至少包含预设和自定义字段、真实缺资料、历史状态未知、长篇关键证据及权限收紧样本。不得将作者私人内容上传为公共评测集。

记录输入版本、预期关键事实/证据、允许偏离、功能参数和模型配置。样本必须包含“同义改名保留用途”和“改义后解除旧用途”，并与新增同义字段对照，检查模型材料有无残留旧说明。改造前后使用相同模型、路由、输入与采样配置；支持 seed 时固定，不支持则声明。真实评测至少覆盖一款已配置本地模型与一款已配置云端兼容模型；资源缺失时对应支持组合保持待验，不能虚构通过。运行评测产生额度，执行时按用户已有授权和可用配置安排。

验收记录包含：结构有效率、事实抽取准确/遗漏、审校误报与证据定位、权限违规、原稿保护、任务完成率、请求次数、首输出/总耗时；生成文本按衔接、事实保留、人物一致、重复、文风由作者或指定评审盲评。确定性权限/写稿保护用例必须零违规；各任务关键事实/证据用例不得出现未解释的回退。真实质量差异逐项列出，不能用一个综合平均分掩盖严重回退。协议/状态改变后重做受影响用例；真实文本质量不以静态字符串扫描代替。

新旧等价对照只用于未改义、未收紧权限且无既定缺陷的路径；T3 按新义解释、修复权限泄露、正确阻止过期写入属于预期行为变化，单列依据与验收，不能为了“等价”恢复旧缺陷。24 例是最小功能样本，不宣称统计显著；每个关键生成任务选至少一个样本重复三次，报告波动。缺少某种真实模型时保留该组合待验，不能宣称覆盖；发布支持范围与实际验证一致，变更范围须显式评审，不能让“缺资源”自动等于通过。

**P1 深化：** 在上述基线上增加场景推进、人物动机保留、跨章情节重复与改写前后关键事实对照。只作为有依据的建议或候选审查，不能自动“纠正”作者认可的剧情变化；额外 AI 审查按功能显式启用，预计调用数可见。若样本没有稳定收益，保留评测结论，不宣称该启发式已改善质量。

### 16.10 Q9：酒馆长期记忆深化（P1）

复用六栏记忆、原文召回、手动“结束本轮/整理本场”触发及原有检查点。不得改成每轮对话后自动追加多次总结，也不扩为所有长任务的重启恢复。

- 事实/关系条目保存来源会话、消息 ID、整理区间和修订版本。作者可固定关键事实；摘要重写不得删除或改写固定事实，发生冲突时保留双方依据供选择。
- 总结前保留上一份记忆与水位，生成后显示重要增删和关系变化；采纳时校验会话基准，取消/失败不推进水位。保存失败时保留待采纳草稿；不能因为总结过一次就漏掉未成功保存的消息。
- 可恢复上一份记忆，并清楚显示哪些旧情节已压缩。恢复记忆不回滚聊天正文或数值，相关检查点和来源关系分别处理。
- 采用固定对话连续整理至少五轮，对照关键事实、未解决伏笔、关系变化和来源隔离；记录遗失/捏造情况。没有漂移数据前只登记风险；P0 仍要求原酒馆权限、状态和追踪兼容。

| 原文恰好相同就推定 AI 已应用 | 唯一操作 ID 与主记录提交标记一起持久化，结合修订和正文核对；同文无标记需人工核对 | §3.3、§8.3 |
| 取消要求“不回写”，却可能正文已经落盘 | 主记录提交是边界；之前可取消，之后保留已应用事实并结清恢复，不回滚正文 | §3.3、§16.7 |
| 暂停自检要求保留草稿，但 B3 原范围不含连写 | 仅保存当前暂停章的最小检查点，不承诺整条连写重启续跑 | §1.3、§9、§16.2 |
| 模板最后发布但值可能已同步，且同 ID 改义不会出现未知键 | 发布代次与受影响数据清单校验；同步/备份不能采用中间态 | §3.6、§9.3、§17.2 |
| 单页解析失败关闭全部 AI，与兼容优先冲突 | 按字段/页签隔离，只阻止依赖该项的操作，其余明确授权资料继续可用 | §3.4、§3.7 |
| 只过滤原字段，摘要/旧缓存仍可能带出值 | 程序派生产物携带来源，复用与真正发送前重查；已发送内容不能撤回 | §3.8、§16.3 |
| 固定资料等于必发；换模型等于旧候选过期 | 工作区固定与本次 AI 选材分开；模型/提示词是生成快照，内容/权限依赖才判旧结果失效 | §3.2、§4.2、§16.5 |
| JSON schema 动态字段协议与保留的标准抽取槽位冲突 | 两类输出各校验自己的协议，统一经 T2 映射后校验真实落点 | §16.6 |
| 所有无结束标记兼容流都判失败；重试上限未覆盖补字循环 | 按端点协议判终结，保留 finishReason 未知；步骤与批次另设总请求预算 | §16.7 |
| 载荷额度漏算改前稿/暂停草稿、清理可能删在途产物 | 统一字节预留与引用保护，报告可完整分块，导出/准备提交中的载荷禁止清理 | §9.2 |
| 迁移副本、默认备份与新 schema 之间可能丢定义 | 恢复副本不是第二份正式内容；分片备份和导入同时携带已发布定义、确认与映射 | §3.6、§9.3、§17.2 |

不同状态域分别表达，不合并成一个万能状态枚举：

| 状态域 | 表达的问题 | 统一映射 |
|---|---|---|
| HTTP/流尝试 | 一次外部请求是否传输完、是否重试 | 记录 attemptId、传输结束原因和 usage，不能直接推出业务完成 |
| Q1 步骤结果 | 一项检查/生成是否有效、覆盖多少 | completed/partial/failed/cancelled/skipped/incomplete；有效空结果才可表示本项未发现问题 |
| 持久化任务 | 任务能否继续执行、是否等作者处理 | running/paused/interrupted/awaiting-review/completed 等；其执行壳可已停止但仍有待审产物 |
| 候选/提交 | 是否可应用、是否已持久化 | pending/stale/applying/applied/needs-reconcile/discarded；正文已应用不保证问题已修复 |

所有计数分别显示“已检查、未检、生成候选、已应用、效果待复核”。丢失载荷不能计为已完成；幂等操作以 operationId 而非模型文字或当前时间判重。

### 17.2 模板发布、同步与备份的一致性

**落点与责任：** WT1/WT3 定义发布元数据，WT2 接现有同步，W2 接导入/备份，W7 验证往返。复用项目设置、现有同步与 T1 本机日志，不建设第二个同步系统。

1. 每次结构/含义迁移生成 `publicationId`，记录父代次、模板/T3 覆盖摘要、受影响值的预期修订/摘要、完成状态与格式版本。清单只存引用和摘要，过大分块并受模板总额度限制；实际值仍在原资料记录。普通改名可无值转换，但仍有新的字段语义依据。
2. 本机先严格备份已发布状态，再持久化准备日志与旧值恢复引用；受影响写入关闭。需转换的记录带目标代次，只有清单及所有必要记录验证成功才将其作为有效代次发布。未转换的记录按明确保留关系复用，不要求为纯标签修改重写全部历史行。
3. 迁移中读写统一经 T0/存储协调点；旧组件自动保存、跨窗口写入、检索缓存、图谱和 AI 消费者不能绕过维护状态。不能提供一致旧视图时，显示“该资料更新中”，不以新定义展示部分旧值。非受影响页签继续工作。
4. 日常同步只发送已完成发布的迁移；远端无论先收到定义、清单还是记录，都先核对代次。缺清单/缺记录/摘要不符时暂不采用，显示缺项并允许重新拉取；禁止仅因字段 ID 存在就提前使用。模板目录是可重建索引，不作为早于定义和发布清单的权威开关。
5. 两台设备从同一父代次分别修改定义时视为分叉；不能逐键拼接为一个双方都未确认的混合定义。保留双方定义及其值依据，由作者选择或生成新的协调代次；权限收紧的分支在未协调前保守限制涉及字段，不能默默开放。来源不明的旧包进入兼容适配，不当成已发布的新代次。
6. 备份/导出在发布代次固定后读取；若读取期间实际依赖变化，重试捕获或返回“正在变更”，不能输出看似成功的不一致包。自动分片备份和手动全库导出都验证清单，候选携带选项只影响候选，不影响正式定义与已确认用途。
7. 日志恢复先比较实际记录与清单：已发布则补回执并清理暂存；未发布且基准未变可由作者继续；有外部变更则保留恢复副本等待核对。不能用迁移前整库备份覆盖期间其他页签的新编辑。
8. T3 改义后的旧值需要单独的待整理依据：字段新含义已确认不等于每条旧值已确认。可用“该字段旧代次默认待整理＋已确认记录集合”避免重写每条旧值；新填值带当前代次。同步/导出不得丢掉该区分。

**必验场景：** 定义先到、值先到、同 ID 改义、迁移中断、双设备同父分叉、迁移期间备份与旧草稿自动保存。每种场景同时检查人工页面、AI 发出材料和最终备份；不一致时必须可见、可恢复。

### 17.3 类型、包格式与生命周期遗漏补齐

- **统一值编解码：** 沿用 `Record<string,string>` 和图鉴六类型的现有编码，不把新增字段另存成互不兼容的原生布尔/数组。T0 在边界统一 decode/validate/encode，区分未填、数字 0、布尔 false、空多选和未知非法旧值；单位仅格式化展示，不改原值。非法值保留并标待整理，不因转换失败变为空白。
- **系统字段分层：** 记录 ID、存储键、同步归属、保密/弃用、内部编号与引用元数据仍是程序契约，不因标签变更改义；可调整的业务字段（人物身份/境界等）按 T3 处理。所有确定性消费者必须检查当前用途是否有效，禁止因底层键仍叫旧名称而绕过解除绑定。
- **导入验证：** 模板包先做 schema/版本/大小检查，拒绝重复字段 ID、非法存储键、原型污染键、重复选项 ID、无法解释的引用和越界数量。标签允许跨分组重名但提示歧义，定位仍靠 ID；不得把外来“已验证”或 AI 建议当成本项目已授权。新模板权限在采用预览中确认，已有权限不得因合并被扩大。
- **导出契约：** 项目 JSON、迁移包、分片备份及世界包携带所需的字段定义/确认/绑定/代次；CSV 等平面格式只提供值和当前可读列名时，明确不能保留完整模板语义。若支持可恢复往返，须附带稳定字段清单并由导入器使用，不能按显示列名猜同名字段或覆写另一列。字段说明/示例可能含作者资料，结构模板分享预览应可查看这些内容。
- **发布版本：** 项目模板按 `templateId + publishedVersion + 项目修订摘要` 区分，个人库同版本不可覆盖；项目独立编辑不冒充库的新发布版本。显式回退也是一次受保护的变更计划，历史值保留，相关新候选失效；不是直接复制旧定义覆盖当前数据。
- **生命周期：** 项目复制/删除、全库恢复、资料导入和格式升级统一处理章节固定引用、T3 覆盖、发布清单、来源映射、候选、暂停检查点与日志。跨项目候选只读并重发 ID；旧提交日志不在新项目重放。源项目被删除或恢复时，取消租约并拒绝迟到写入，不因网络返回再造已删除项目。
- **恢复与删除：** 从旧备份恢复到同项目应产生新恢复代次，使已有本机工作产物重新校验；正式数据恢复不默认回滚其他本机待审候选。载荷清理以引用计数/扫描为准，不依据某一列表里是否可见；手动删除仍被其他报告/提交引用的数据时先列出影响。

上述工作进入 WT0/WT1/WT2/WT3、W2/W3 的对应验收，不另起一套字段、备份或导入实现。

### 17.4 开发方法、试点与新增发布门槛

采用“共用契约 → 小范围完整流程 → 扩大入口覆盖”的推进方式：先用一个角色卡和一个图鉴页验证旧数据/同义改名/实质改义/禁读空写/原稿条件提交，再推广七页签及 T3 其他入口。每次推广有调用方清单与观察记录，不以完成一个通用函数替代全部接线。

共用接口应返回明确诊断与可恢复结果，UI 只解释作者需要采取的动作；不让作者选择数据库 store、迁移号、哈希或协议参数。保留可导出的本机诊断供排查；默认不发送遥测。实现评审可以合并小模块，禁止为每个规划名机械新增空文件或重写一套原执行器。

| ID | 新增必验项（P0） | 责任包 |
|---|---|---|
| CO-01 | 发布代次在同步乱序、同父分叉、备份读取与迁移中断时不产生混合有效资料 | WT1/WT2、W2/W7 |
| CO-02 | IDB 多窗口、文件目录多写入者、旧编辑草稿与 AI 并发更新均守住提交/迁移边界 | F0、WT1、W3/W7 |
| CO-03 | 主记录写入前后分别取消/崩溃；同文无标记、提交后又编辑不会重复改稿或记 AI 字数 | W3/W7 |
| CO-04 | 模型发送/重试前权限改变、派生摘要、旧缓存、历史待整理值不绕过当前规则 | WT2/WT3、WQ4/WQ6 |
| CO-05 | 0/false/空多选、同名字段、非法包、CSV 与完整包、世界包均按声明契约往返 | WT0/WT2/WT3、W7 |
| CO-06 | 暂停草稿写失败、容量并行触顶、导出与清理并发、项目删除后迟到回调均可控 | W2/W3、WQ1/WQ7 |
