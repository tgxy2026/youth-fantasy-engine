## 🔑 关键设计决策

| 决策 | 依据 |
|---|---|
| **词表只在一处对齐**（`checkAdapters.ts`） | 分散 if/else 漏一处 ⇒ 冲突级被当提示 ⇒ 按 A 策略不落库 ⇒ 作者隔天查不到 |
| **一章落一份、不按引擎各落一份** | 配额是「每章 5 份」；五项各落一份的话跑两轮就把同章其它检查挤掉 |
| **固定 jobId `local-ticket`** | `persistCheckReports` 的去重按 jobId 圈定；每次诊断新 id 会让去重形同虚设、200 份额度被刷满 |
| **多章一次调用**（`reports[]` 自带 chapterId） | 逐章各调一次会把全项目载荷反复列举，大书明显变慢；input 级仍生效 ⇒ 老调用行为不变 |
| **检查项粒度＝章** | `runChapterCheck` 内部把五个引擎的失败各自 `.catch(() => [])`，外层分不清"引擎挂了"与"真没问题" ⇒ 不假装知道，只如实记到章 |
| **中止后剩余章记 `pending`** | 不记会让覆盖率显示 30/30 = 100%，作者以为全书都查过了（WQ1 登记病灶） |
| **复检按标题比对**（`recheckDelta`） | 正文已被改写，比片段无意义；工单条目与复检发现同形（含「错别字：X → Y」） |
| **复检是旁路** | 抛错只 `console.warn`，绝不把已落库的正文报成失败；界面三种态含"复检没跑成" |

## 🔴 已知限制

1. **本地诊断留档会占配额**：100 章全跑一遍 ≈ 100 份（每项目 200 份）。有双闸淘汰兜底（删最旧），但若长期全本诊断，连写自检的报告额度会被挤压 —— 实机时留意留档构成。
2. **复检只覆盖本地五引擎**：AI 侧审读（编辑意见/OOC/爽点）不在复检范围内，改完它们是否解决无从判断，界面也不会假装知道。
3. **工单条目状态不落盘**：每次「重新生成工单」都会重算（既有行为，本轮未改）；报告留档后会并入历史条目，靠去重键与"已有状态优先"避免堆叠。
4. **`recheckDelta` 依赖标题同形**：若将来改了工单条目的标题措辞，必须同步改 `chapterReportToFindings`，否则比对静默失效（测试 ⑤ 最后一条钉住了这个前提）。
