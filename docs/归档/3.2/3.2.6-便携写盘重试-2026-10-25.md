# 3.2.6 · 便携服务：写盘失败必须重试、必须回 500（2026-10-25）

> 结论：这是本轮抓到的**真缺陷**，不是探针问题。便携后端在大表（1000×74 / 整库 4.6MB）连续保存时，
> Windows 上 `renameSync` 会抛 `EPERM`（网盘客户端 / 杀软 / 索引器正在扫刚写完的文件）；
> 旧代码不重试、且异常从请求处理器里逃出去 ⇒ **这次保存被静默丢弃 + 前端永远停在「正在保存」**。
> 已修：rename 退避重试 + 写盘失败回 500 + 补齐回归测试（10 条断言）。

## 1. 怎么发现的

补采便携正式基线时（`--mode measure --backend portable --fixture large`）探针在 `save 2/10` 处
干等 180 秒超时。服务端日志：

```
⚠️ 未处理的 Promise 拒绝（服务继续运行）： 写入数据文件失败（可能被网盘客户端占用）：
EPERM: operation not permitted, rename '…\.data.json.tmp' -> '…\youth-fantasy-engine-data.json'
```

三条事实拼起来就是完整缺陷：

1. `rename` 在多平台都可能**瞬时**失败；本项目作者的真实场景就是「数据放在 OneDrive/坚果云/百度网盘同步目录」。
2. 旧 `atomicWrite` 只把错误包成一句话**抛出去**，没有重试 —— 一次扫描窗口就丢掉一次保存。
3. 抛出点在 `withWriteLock(() => …)` 的回调里，没人接 ⇒ 变成未处理的 Promise 拒绝 ⇒ **HTTP 响应永远不发**。
   前端 `fetch` 挂着，界面停在「正在保存」，用户完全不知道数据没存上。

## 2. 修法（`scripts/portable-server.mjs`）

```js
// rename 覆盖目标：退避重试 20/40/80/160/320ms（约 0.6s，够跨过一次扫描窗口）
function renameWithRetry(from, to) {
  const delays = [20, 40, 80, 160, 320]
  for (let attempt = 0; ; attempt++) {
    try { return renameSync(from, to) } catch (e) {
      const transient = e && ['EPERM', 'EBUSY', 'EACCES', 'ENOTEMPTY'].includes(e.code)
      if (!transient || attempt >= delays.length) throw e
      sleepSync(delays[attempt])
    }
  }
}
```

- `atomicWrite()` 现在把**写 tmp 与 rename 一起**包进 try：tmp 目录被占、磁盘满、只读路径，
  都会得到同一句可读文案，而不是裸 `EISDIR/EACCES`（这一点是测试逼出来的，第一版只在 rename 那层兜）。
- 失败时清掉 tmp（原数据文件一个字节都不动），再把错误抛给路由。
- `PUT /api/data` 自己接住异常，返回 **500 + `code: 'WRITE_FAILED'`**：
  ```js
  try { atomicWrite(text) } catch (e) {
    return sendJson(res, 500, { ok: false, code: 'WRITE_FAILED', error: String(e?.message ?? e) })
  }
  ```
- sidecar（备份载荷/向量/知识库）的 blob 写也走 `renameWithRetry`。

## 3. 回归测试 `tests/portableWriteFailure.test.ts`（10/10）

起**真实的便携服务进程**（真磁盘、真 HTTP），把写入路径堵死（把 `.data.json.tmp` 变成目录）：

| 断言 | 内容 |
|---|---|
| ① | 首次空库 GET 404 且带可复算的 `revision` |
| ② | 写不进去时**必须有响应**（6 秒超时兜住「挂死」），实测 5ms 返回 |
| ② | 状态 **500**，不是 200 假成功 |
| ② | 文案含「写入数据文件失败」且带 `WRITE_FAILED` |
| ③ | 原数据文件**没有**被写出来（不留半个文件） |
| ③ | 服务还活着（不是崩了） |
| ④ | 堵点解除后同一份数据 PUT → **200**，`revision` 可复算 |
| ④ | 磁盘内容与提交内容逐字节一致 |
| ⑤ | 日志里**没有**「未处理的 Promise 拒绝」（旧缺陷的直接特征） |

## 4. 顺带修掉的取证工具问题

`scripts/verify/draft-failure.mjs` 的首屏等待是 60s，vite 冷缓存 + 机器忙时会顶到边界

## 5. 影响与边界

- 影响面：便携后端所有整库写入（含导入、还原、自动备份的落盘）。桌面端（`main.cjs`）走的是自己的
  原子写，未受本次改动影响；云端在 Linux 上 rename 失败概率低，但**同样没有重试** —— 记录为待办，
  不在这轮改（改动面涉及线上服务，需要有部署窗口）。
- 未覆盖：多进程同时写同一数据目录（`identity.concurrency` 的欠项）；rename 重试次数与退避的
  真实观测量（本轮只有一次实测命中，没有统计意义上的分布）。
- 验收：`portableWriteFailure` 10/10；全量单测 330/330；便携 large 基线此后可达（保存 P95 999.9ms）。
