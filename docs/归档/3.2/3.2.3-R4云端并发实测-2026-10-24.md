# 3.2.3 R4：云端并发（同浏览器多标签）实测 —— 覆盖确实存在

> 日期：2026-10-24｜执行：可可｜基线 `main` / `b6cb9e1`
> 性质：**事实取证（不带通过/失败判定）**。结论是「缺口被证实」，不是「保护被验证」。
> 不改代码（待主人拍板）；不封装、不发布。

## 1. 为什么要单独测这一条

`src/lib/app/tabGuard.ts` 开头自己写着：

> 「同一个账号在两个标签页里同时编辑，后保存的会整体覆盖前一个，**先写的内容静默丢失**。」
> 「真正的互斥需要服务端版本号（`revision` + `If-Match`）—— 那是跨设备也能生效的方案，但要动前端整条保存链路。」

也就是说产品**知道**这件事，当前策略是「只提示、不拦人」。但「知道」和「实测过」是两回事 ——
方案 §7 的 `concurrency` 单元（two-tabs / replace-session / close-during-save）此前一直是"未取证"。
这轮把最危险的那一格（two-tabs 陈旧整库覆盖）**测成了事实**。

## 2. 做法

`scripts/audit/probes/web-cloud-concurrency-probe.cjs`（**finding 型探针**）：

- 本机真实 server + 隔离数据目录 + 临时账号（`probe-conc-*`），全程只允许 127.0.0.1；
- **同一个浏览器 context 开两个标签页**（共享 Cookie，正是「同一账号两个窗口」的真实形态）；
- 两页都加载真实生产构建（确认提示条是否出现）；
- 然后两个标签页各自发起一次整库 PUT：tab1 写「甲」，tab2 写「乙」（模拟 tab2 内存里没有甲）。

它输出 `findings`（观测事实），**不是** `checks`（门禁） —— 避免把「确认了缺口」伪装成「这道闸通过了」。

## 3. 实测结果（`.workbuddy/tmp/web-cloud-concurrency-fRJNt9/`）

| 观测项 | 结果 |
|---|---|
| 两标签提示 | ✅ **确实提示**：两页都出现「检测到另一个窗口也在用这个账号，同时编辑会互相覆盖」（`#yfe-tab-guard`） |
| **陈旧整库覆盖** | ❌ **确认发生**：甲先写（200）、乙后写（200）⇒ 读回只剩乙，**甲的内容消失**（`keptFirst: false`，最终正文 hash `20cb7085…`） |
| 版本前置条件 | ❌ **不存在**：带 `If-Match: "definitely-stale-revision"` 的 PUT 仍返回 **200**，响应无 `ETag`/`revision` |
| 页面异常 | 0 |
| 源码指纹前后一致 | ✅ |

一句话：**提示是有的，保护是没有的**。后保存的整库会把先保存的内容整段抹掉，服务端也没有可用的冲突判据。

## 4. 影响判断

| 维度 | 判断 |
|---|---|
| 数据风险 | 高 —— 丢的是**整库**（同一账号另一窗口的先写内容），且**无提示、无告警**，作者只会觉得"稿子怎么回去了" |
| 触发条件 | 同浏览器同账号开两个标签页且都编辑（`tabGuard` 已提示，可用户点「知道了」继续） |
| 跨设备 | 同样存在（桌面版靠单进程独占文件避开；网页版跨设备无任何协调） |
| 对矩阵 | `concurrency/web-cloud` **不得 verified**；状态从"未取证"升级为"**已取证：无保护**" |
| 是否该顺手加锁 | 不 —— 改保存链路 + 服务端协议是产品决策，按红线未点名不动代码 |

## 5. 三个处置方案（等主人选）

| 方案 | 做法 | 代价 | 备注 |
|---|---|---|---|
| **A. 维持现状** | 只保留提示条，把帮助文案写清「另开窗口可能整库覆盖」 | 零 | 现状；风险自担。前提是文案必须够直白 |
| **B. 服务端 version + `If-Match`（根治）** | 整库加 `revision`，PUT 带期望版本，不匹配返回 409；前端冲突时提示「另一处已更新，请刷新或导出草稿」 | 高：动服务端 + 前端整条保存链路 + 三种配置 | 跨设备也一并解决；需要单独一批，含迁移与回滚 |
| **C. 前端保存前比对** | 保存前先 GET 最新整库摘要，与自己内存基线不一致就停下来提示 | 中：只动前端 `flush` 路径，服务端零改动 | 有 TOCTOU 窗口（比对与写入之间），且跨设备仍是每设备各自比对 |

我的建议：**A 短期到位（把文案写死）+ B 立项**（因为跨设备同样需要版本号，C 只能缓解同浏览器那一半）。
但这属于功能/协议级改动，**等主人点名再做**。

## 6. 边界

- 本次只测了 `two-tabs` 这一子场景；`replace-session`（会话替换）与 `close-during-save`（关窗兜底）未测。
- 只在 Edge + 本机 server 上测；真实公网延迟、多设备、代理未涉及。
- 该探针**不接**进 reliability 契约（无通过判据），需要时手动跑：
  `node scripts/audit/probes/web-cloud-concurrency-probe.cjs --build-dir <本次构建> --result-file .workbuddy/tmp/x.json`

## 7. 主人决议与落实（2026-10-24 19:09）

主人选择「**3 按建议**」⇒ **A 短期到位 + B 立项**：

- **A 已落地**：`src/lib/app/tabGuard.ts` 提示条文案改硬 ——
  「检测到另一个窗口也在用这个账号：两边都是整库保存，后保存的会覆盖先保存的，先写的内容会丢失。建议只留一个窗口编辑。」
  旧文案只说"会互相覆盖"，没说整库、也没给动作；作者点掉「知道了」继续写就真丢。
- 门禁 `tests/saveFailureHint.test.ts` 第 ④ 组（契约 `copy.failure-hints`）：断言提示里出现「整库保存」「先写的内容会丢失」「只留一个窗口」，
  且**不得**出现"已锁定/已阻止"之类谎称已保护的字样。
- **B（服务端 revision + `If-Match`）已立项未开工**：要动服务端 + 前端整条保存链路 + 三端迁移，属功能/协议级改动，等主人点名。
- 本次改动**没有**新增任何保护，只是把风险讲清楚 —— 矩阵 `concurrency/web-cloud` 仍不点亮。
