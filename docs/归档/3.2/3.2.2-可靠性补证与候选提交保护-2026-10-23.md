# 3.2.2 可靠性补证与候选提交保护

日期：2026-10-23。起点：`main` / `da89306`，版本仍为 3.2.2。

本轮按交接的优先顺序，补验数据迁移、导出完整性、过期候选拒绝与迁移横幅，并修复验收中确认的候选提交保护缺口。使用源码开发前端、真实 Electron 主进程、真实临时文件和离线模型响应；未生成安装包或便携包。

## 一、确认并修复的问题

候选应用原本有三处会让“提交意图先落盘”失效：

1. `candidateApply` 用 `catch(() => undefined)` 忽略意图持久化异常，仍继续替换正文。
2. `candidateRunner` 将 `saveCandidate()` 的 `{ok:false}` 直接转换为成功完成的 Promise，编排器拿不到失败。
3. `saveCandidate` 回读只比较正文；更新 intent / receipt 时正文不变，即使读回旧状态也会判成功。文件后端的普通 put 还只更新内存，不能证明意图已经写入文件。

修复前新增回归用例得到 31 条通过、4 条失败：意图没有保存时正文仍被替换；回执保存失败则直接抛出异常，没有返回可恢复状态。

当前处理：

- 修订载荷优先使用严格写入能力；桌面、便携文件后端额外等待真实保存确认。已有保存正在进行时先等待它结束，最长 10 秒，再提交包含本次状态的快照；失败不会被当成持久化完成。
- 提交意图保存失败立即返回 `write-failed`，保留原候选，停止替换正文。
- 正文已写但回执保存失败时返回 `needs-reconcile`，保留带 intent 的 applying 状态。再次处理会核对正文，只补回执，避免重复替换和重复记账。
- 候选回读同时核对改前文本及状态元数据；调用方检查保存结果。同章候选失效计数只累计真正保存成功的项。
- 界面不再把所有写失败都描述为“正文没有被改动”，也不再把所有需核对状态都说成“正文既不是改前也不是改后”；具体原因随结果展示。

相关源码：`src/lib/db/revisionJobs.ts`、`src/lib/revision/candidateApply.ts`、`candidateRunner.ts`、`candidateStore.ts`、`src/components/revision/CandidatePanel.tsx`。

## 三、复现

在仓库根目录运行：

```powershell
node scripts/audit/probes/revision-reliability-probe.cjs
node node_modules/typescript/bin/tsc --noEmit
node node_modules/eslint/bin/eslint.js src tests
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run-batches.ps1 all
```

探针默认使用 5206 端口，可传 `--port <空闲端口>`。它自行启动和关闭 Vite/Electron，使用本机已安装的 Electron 与 Playwright，每次建立新的临时目录；不会清理历史证据、恢复 bundle 或发布产物。
