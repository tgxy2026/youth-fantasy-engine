# 2.3.0 · 创意写作改造：长篇分批（大纲规划 / 正文生成 两阶段）

> 2026-09-20 ｜ 未升版本号、未封装 ｜ 基线 tsc 0 / eslint 0 / 测试 75 个入口全过
> 实机：线上模型（硅基流动 `Qwen/Qwen3.8-27B`）+ 真 Chromium

---

## 一、需求（老大原话拆解）

「一句话创作 → 直接产出大纲 + 正文」这条流程**只能写短篇** —— 受模型上下文限制，
一次性产出几十万字甚至几百万字不现实。所以要把长篇支持补出来：

1. **短篇**保持现状：「只做大纲规划」或「大纲 + 正文」一次跑完；
2. **中长篇**把两个阶段**分开做**，各自可反复执行；
3. **大纲规划要能接着往下排**：库里没有分卷大纲 / 章节细纲时从第 1 卷第 1 章起；
   已有则读已有内容继续往下（例：已有 2 卷 × 20 章 ⇒ 写第 3 卷大纲 ⇒ 据它排第 41–60 章细纲）；
4. **正文生成要能对照已有进度接着写**：大纲排了 2 卷 40 章而正文一章没有 ⇒ 从第 1 章起；
   已写 5 章 ⇒ 第二次从第 6 章起。本次写几章由作者填；
5. （独立需求）「一句话想法」输入框要**能保存 / 能编辑 / 能一键清空**。

## 二、先确认的四项决策（老大拍板）

| 问题 | 决定 |
|---|---|
| 「这一次要产出什么」怎么摆 | **加「篇幅」维度**：短篇 = 只做大纲规划 / 大纲 + 正文；中长篇 = 只做大纲规划 / 只生成正文 |
| 大纲续排起点按什么算 | **已排到哪**（＝已有细纲最大章号 + 1），不看正文写到哪 |
| 每卷章数是硬指标还是软目标 | **硬指标**（第 k 卷 = 第 (k-1)×M+1 ~ k×M 章，便于对账与切卷） |
| 正文生成档是否保留「边写边排细纲」 | **不保留**（细纲必须先排好；没有大纲时如实报错，不静默改行为） |

## 三、由决策推导出的结论：起点不再由作者手选

老大的原话是「项目里没有分卷大纲和章节细纲的时候，那就默认从第一卷第一章开始生成……
已经有了……AI 模型就**需要接续**」—— 这是**自动判定**，不是让作者每批点一次
「从一句话创作 / 接着已有内容写」。于是：

- `probeCreativeProject()` 读一眼项目（卷大纲卡数 / 细纲最大章号 / 正文章数）；
- 有卷大纲或细纲 ⇒ `continue`，否则 `scratch`（先跑设定奠基）；
- 面板把判定结果**如实写出来**（状态行：「当前已有 2 卷大纲 · 40 章细纲 · 5 章正文 → 本次从第 41 章起接着往下排」）。

旧的两个起点按钮**已删除**（`MODE_META` / `MODES` 一并删掉）。

## 五、关键口径（红线级）

1. 🔴 **续排起点看「已排到哪」**。旧口径 `writtenNo + 1` 在"先排完大纲、再写正文"下必然卡死：
   正文 0 章 ⇒ 算出第 1 章 ⇒ 命中「第 1 章已有细纲，无需续排」⇒ **直接收工**。
2. 🔴 **章号与卷的章号范围都由系统算**。模型返回的 `no` 一律忽略（它经常从 1 重新数）。
3. 🔴 **切卷依据是「本卷章号范围」**，读不到就退回旧行为（落锚点所在卷）—— **不猜**
   （猜错就是整卷正文错位，而且一个错都不报）。
4. 🔴 **「只生成正文」在项目没有大纲时如实报错**，不静默改成"先排大纲"。
5. ⚠️ 提示词 id **沿用 `extend-outline`**（故意不换）：换了 id，作者此前在「模型设置 → AI 提示词」
   里改过的内容就会失效。只更新显示名与说明（它现在管"从零排 + 接着排"两条路）。
6. 🔴 **想法输入框**：`seed` 原本就在落盘范围内，但 `hydrateCreativeSession` 用的是一个
   **模块级一次性布尔量**，切项目后不会重读新项目的会话（跨项目串味）；且只有 1 秒防抖、
   没有"立刻写"的入口。现在：hydrate 按项目 id 去重 + 「保存」按钮走 `flushPersist()`（不等防抖）
   + 「清空」确认后立刻落盘。
7. 🔴 **产出不足不许静默**（实机跑出来后补的）。模型会**写一半就收尾**，而 JSON 是**闭合**的
   （不是截断，`parseLooseObject` 拿到的是"看起来正常"的半份）。两处兜底：
   - `aiPlanOutline`：实际章数 < 承诺数时**重试一次**，并把差额写进提示词（"还差 N 章"）；
   - `fillChapterRanges(…, actualChapters)`：按**实际**章数收敛最后一卷、丢掉越界的卷 ——
     否则第二卷会拿到「第32-41章」而**那 10 章根本不存在**（幽灵范围，作者会以为已排到 41 章）。
8. 🔴 **接续排纲要防"大结局"**。模型看到"已有 3 卷 21 章"就以为该收尾了，第一次实测把
   第 31 章写成「新纪元」（全书结局）。提示词因此加了一条：**这是长篇连载的其中一段，
   不是全书结局** —— 不许收束主线、不许"功成名就 / 开启新纪元"，本批结尾要留**新的**悬而未决。

# 第二轮：缺口优先（2026-09-20）

老大看完第一轮后提了两件事：**① 修正文里的 markdown 星号**；**② 缺口补齐能不能也用到正文上**。
中间补了一条口径：**卷大纲完整就按它排细纲，不完整则补细纲时一并补全卷大纲**。

## 一、需求（老大原话拆解）

> 「比如说我一开始的规划是一卷 10 章……目前是 3 卷 21 章，前两卷是完整的，第三卷还差 9 章。
> 那 AI 能不能优先把这 9 章补完？补完之后，再跟我下一次指示，再建新的一卷、新的 10 章。
> 要是没有办法实现，那我们就在前端要求用户按照卷去规划。」

> 「缺口补齐能不能应用到补充正文？比如第 21 章只有 2200 字，但目标通常是 4000 字，
> 那能否让他把第 21 章先补完之后再继续往下写？」

## 二、结论：能实现（附实证）

唯一的障碍是**怎么知道「第三卷该到第 30 章」**。第一轮加的「本卷章号范围」只覆盖新数据，
而示范项目这类老数据的范围只写在「本卷章数预估」的自由文本里。实测三种真实写法：

| 卷卡 | `本卷章数预估` 实际值 | 解析结果 |
|---|---|---|
| 第一卷 风起云州 | `第1-10章，约四万六千字` | `{1,10}` 完整区间，直接可用 |
| 第二卷 剑鸣中州 | `第11-20章，约四万六千字` | `{11,20}` 完整区间 |
| 第三卷 剑锁中州 | `第21章起（已写第21章，约2200字）` | `{21,21}` 只有起点 → 用「每卷章数」推定上界 = `21+10-1 = 30` |

于是缺口一目了然：**卷1满、卷2满、卷3 缺第 22-30 章（9 章）** ✓
所以**不需要**加"必须排满整卷"的限制 —— 作者随时可以在没排完的卷里续补。

## 三、四项决策（老大拍板）

| # | 问题 | 定论 |
|---|---|---|
| 1 | 有卷没排满时本次产出多少 | **只补缺口，不新开卷**（补齐后下一批才排新卷） |
| 2 | "这一卷本该多少章"按什么判 | **三级取用**：本卷章号范围 → 本卷章数预估 → 单章式文本用「每卷章数」推定上界 |
| 3 | 要不要顺带补卷大纲 | **卷大纲完整 → 只按它排细纲；不完整 → 补细纲时一并把卷大纲补全**（只填空 / 占位字段） |
| 4 | markdown 清理范围 | 星号（`**` / `__` / `*`）+ 行首 `#` 标题符 + 整行 `---` 分隔线 |

## 四、改造清单（按层）

**A. 正文净化（①）** —— `aiTasks/rewrite.ts` + `autoContinue.ts`
- `cleanChapterOutput` 增加 `stripInlineMarkdown`：剥 `**粗体**` / `__粗体__` / `*斜体*`、
  行首 `#` 标题符、整行 `---`/`***`/`___` 分隔线。
  ⚠️ 单星号斜体要求**内容首字符非空白**（`\*\S…\*`），否则 `a * b * c` 会被吃掉一半（误伤正文比留标记更糟）。
- 🔴 **接进逐章连写链路**（原先只有整章改写在调它）：初稿生成后、去 AI 味儿后、`selfRefine`+字数校准后
  落库前，共三处。
- 顺带修一个**既有顺序缺陷**：前言与围栏只按"先围栏、后前言"剥一遍，
  「好的，以下是修改后的内容：」+ 围栏 的组合会**把围栏留在开头** → 改成交替剥两轮。

**B. 缺口检测（②）** —— `lib/outlineCard.ts`（纯函数）
- `VOLUME_BOUND_SLOTS`：取边界的槽位优先级（`本卷章号范围` → `本卷章数预估`）。
- `volumeBoundTextsOf(card)` / `volumeBoundOf(texts, perVolume)`：三级取用（见上表）。
- `detectVolumeGap(volumes, maxOutlineNo, perVolume)`：按卡序找**第一个** `to > maxOutlineNo` 的卷。
  🔴 缺口起点取 `maxOutlineNo + 1`（不用"扫第一个空洞"）：细纲必须**连续**才能被按章号取到，
  补空洞会与"接着往下排"的语义打架；老大的场景也一直是**末尾缺**。
- `VOLUME_CORE_SLOTS` + `isPlaceholderText` + `isVolumeOutlineComplete`：判"卷大纲是否只有骨架"，
  只看**四个卷级走向字段**（第一大高潮 / 卷中转折 / 卷末高潮 / 本卷结尾）——
  伏笔、角色那些模块作者常常正文写完才回头补，拿它们当证据会把好卷判成残卷。

**C. 编排层（②）** —— `lib/aiWorkflow.ts` + `aiTasks/creative.ts`
- `probeCreativeProject()` 增加 `volumeBounds`（按 order 排好序的卷边界候选）——
  🔴 面板与编排器**共用这一份输入 + 同一个 `detectVolumeGap`**，两处各算一遍必然漂移。
- `outline` 阶段：检出缺口且目标是"只做大纲规划"时进入**缺口模式** ——
  起点 = 缺口起点、本批章数 = 缺口章数（**卷数参数不参与**）、卷名/卷范围全部由系统给。

  `needVolumeOutline` 为真时才允许产出 1 条该卷的完整卷大纲（`volLimit` 0/1）。

**D. 正文缺口优先（②的第二问）** —— `autoContinue.ts`

  低于 `targetWords - WORD_TOLERANCE` 就复用 `enforceWordRange` 把它**分幕补写**到目标字数。

- 🔴 `maxShrink: 0`：补字场景**绝不压缩**（原文若已比目标长，说明作者有意写短章）。
- 安全阀：补完反而变短 / 没补进去 → **保持原样**（宁可不补，也不能把正文改坏）。

**E. 会话层与面板** —— `creativeSession.ts` / `CreativeWritingPanel.tsx`

  （第 21-30 章）还差 9 章，本次先补完第 22-30 章」。

  「每卷章数」保留（它参与推定卷上界），title 跟着换成缺口语义。

## 五、关键口径（红线级）

1. 🔴 **卷边界只从卡里取，判不出来就不猜**：三级都取不到 → 退回"新开卷"的旧行为，
   绝不用"已有卷数 × 每卷章数"硬算（历史卷实际长度与本次参数不同就会误判缺口大小）。
2. 🔴 **缺口模式不产出卷**：卷大纲卡一个字不动，除非 `isVolumeOutlineComplete` 判为"只有骨架"。
3. 🔴 **回填范围只在原空时写**：`isPlaceholderText` 判定，作者手填的范围不可覆盖。
4. 🔴 **正文只补最后一章**：与「历史章冻结」是同一条纪律；这也是它能安全自动执行的前提。
5. 🔴 **面板与编排器共用 `detectVolumeGap`**：口径只留一个来源（界面说"缺 9 章"就必须真排 9 章）。

# 第三轮：整章改写 —— 补「续写」动作 + 字数硬校准 + 口径统一（2026-09-20）

老大三个反馈：

> 「目前有润色、扩写、精简、改写四个，但没有**续写**。改写是整章重写，续写是在**原有基础不变**的情况下达到目标字数。」
> 「目标字数限制不严：3000 字的内容要求改写到 4000，实际改到了 5000。」
> 「上下最多 300 字波动，而且所有字数要求都要确认口径 —— 前端以**汉字**为基础，如果 AI 那边按 token 或字符算，一定要转换。」

## 一、诊断（三条都不是"调参"能解决的）

| 现象 | 根因 |
|---|---|
| 目标 4000 实际 5000 | `aiRewriteChapter` **只靠提示词**要求字数（而且写的是"±10%"），**没有任何事后校准** —— 模型超多少都没人拦 |
| 没有「续写」 | 动作表只有 4 个；且「扩写」是**通篇加料**（会重写原文），不是"原文不动、往后接" |
| 口径 | `countWords` **本来就是汉字口径**（CJK 逐字 + 拉丁词，标点不计）✓ —— 缺的是**把口径写进给模型的提示词**，模型按 token / 字符估，必然偏长 |

## 二、改造

**A. 抽出 `lib/wordRange.ts`（字数校准的单一来源）**

- `WORD_TOLERANCE = 300` + `askSoft` + `enforceWordRange`（既补也压）从 `autoContinue.ts` 迁来。
- 🔴 **为什么必须抽**：整章改写（`aiTasks/rewrite.ts`）也要用它，而 `autoContinue.ts` 依赖 `aiTasks` 门面
  —— 直接 import 就是**循环依赖**（会被 importCycles 闸拦）。抽到只依赖 `ai` + `textStats` 的一层后方向干净。
- `autoContinue.ts` 再导出 `WORD_TOLERANCE`，保持既有 import 路径（面板）可用。

**B. 新增「续写」动作**

- 动作表：`polish | expand | condense | **continue** | rewrite`
  （界面顺序：润色 → 扩写 → 精简 → 续写 → 改写）。
- 🔴 **实现走结构保证，不靠提示词**：「原文一字不动」如果交给模型（"请保留原文、只往后写"），
  它**总会顺手把原段润色一遍** —— 所以续写时**原文由代码保留**，模型只吐**新增片段**，拼接后返回。
  实现直接复用 `enforceWordRange` 的增量补写循环（它本来就是"紧接着上文往下写"，与续写语义完全一致）。
- 🔴 `maxShrink: 0`：**绝不压缩** —— 原文是作者写的，续写只有"往长里补"一个方向。
- `maxExpand: 8`：从 1000 补到 4000 可能要好几轮。
- 历史章续写会给**红色劝阻**（那一章后面已有正文，往中间插情节会与后文打架）。

**C. 字数硬校准（±300）**

- 改写 / 扩写 / 精简 / 续写的结果**一律过** `enforceWordRange`（`targetWords ± WORD_TOLERANCE`）。
- 精简 `maxExpand: 0`（压到一半又被补回去很荒谬）；其余补 2 轮、压 2 轮。
- 提示词同步：从"一个数 + ±10%"改成 **区间 + 口径** ——
  `【目标字数】必须落在 3700~4300 个汉字之间（目标 4000；按汉字个数计，标点与空白不计）`。

**D. 口径统一（汉字）**

- 前端：`countWords`（汉字逐字 + 拉丁词，标点不计）—— 本来就对 ✓；
- AI 侧：**所有**给模型的字数都写明「按汉字个数计，标点不计」；
- 界面：`目标 4000 ± 300（3700~4300）` 一直就是汉字口径 ✓。

## 三、验证

- 基线：`tsc` 0 / `eslint` 0 / `node tests/run-all.mjs` **76 入口全过**
  （`creativeModes` 新增续写存在性、原文保留走结构保证、硬校准接线、精简不回流、
  口径文案、`wordRange` 单一来源、`countWords` 汉字口径、校准失败上报、压缩流式等断言）。
- 实机（线上模型）：见下节。

## 四、实机抓到的两个真 bug（不是"调参"能解决的）

**① 补写被喂了互相打架的提示词 → 模型干脆什么都不输出**

现象：续写目标 3500，结果**原样返回 2202**（补写零生效，两次一致）；
改写目标 3500，结果 2679 之后**不再往上补**。

根因：给 `enforceWordRange` 传的 `sys` 是**整章改写**的 system（"请改写这一章，只输出正文…"），
而补写的 user 指令是"只输出新增的正文片段" —— 两套指令互相矛盾，模型不动手。

修：`sys` 改为**可选**；不传就用 `DEFAULT_FILL_SYS`（"接着往下补写…只输出新增的正文片段"）。
续写与校准两条路径都**刻意不传** `sys`（并在代码里写明原因，防后人"顺手补上"）。

**② 压缩从来没成功过（`onToken` 漏传）**

`enforceWordRange` 的补写传了 `onToken`（**流式开关**）✓，但**压缩那一步没传** ⇒ 非流式请求
要等整段生成完才回响应头，几千字的压缩必撞 `CHAT_TIMEOUT_MS`(180s) ⇒
**压缩永远失败、超字永远压不下去**（实测：目标 3500、结果停在 3975 —— 补写生效了，压制没生效）。

修：压缩同样传 `onToken`。结构闸加断言 `onToken: o.onToken` 至少出现 **2 处**（补写 + 压缩），
漏一个就有一半校准静默失效。

**③ 附带的可见性修复**：`askSoft` 把模型失败吞成空串后**静默 break** —— 界面上只有
「2202 → 2202 字」一个线索，作者分不清"模型没干活"还是"本来就不用补"。
现在 `enforceWordRange` 有 `onLog`，失败时如实说「补写未生效（模型只返回 N 汉字，可能失败或被截断）」，
逐章连写（`cb.onLog`）与整章改写（`notice`）两条链路都接上了。

**④ 续写会补过头（按"目标正中"补）**

续写**不能压缩**（原文一字不动），所以按目标正中补时，模型一旦多写就永远超上限 ——
实测目标 3500、结果 **3968**（超 168）。

修：续写时给 `enforceWordRange` 传 `fillTarget = target - WORD_TOLERANCE`，即**补到区间下界为止** ——
实测改后 2202 → **3640**，落进 3200~3800 ✓。

## 五、实机验证（线上模型 `Qwen/Qwen3.8-27B`）

### 续写 + 字数校准（`ui-creative-rewrite.mjs`）—— **7 PASS / 0 FAIL**

| 验的 | 实测事实 |
|---|---|
| 动作按钮 | 润色 / 扩写 / 精简 / **续写** / 改写 —— 5 个都在 |
| 🔴 原文一字不动 | 结果**以原文全文开头**（判据 `out.startsWith(原文.trimEnd())`）|

| 🔴 改写受硬校准 | 结果 **3464 汉字**（目标 3500）—— 老大抱怨的"目标 4000 写成 5000"被夹住了 |
| 产品日志 | 两条都是空（没有"补写未生效"，说明一次成功、无需重试）|

### 缺口两个边界（`ui-creative-gap-edge.mjs`）—— **17 PASS / 0 FAIL**

| 验的 | 实测事实 |
|---|---|
| 🔴 缺口落在**非最后一卷** | 细纲削到只到第 5 章 ⇒ 缺口卷 = **第一卷**：状态行「还差 5 章，本次先补完第 6-10 章」；编排层计划量「补完《第一卷 风起云州》第 6 ~ 10 章（共 5 章）」；闸门「确认分卷大纲（**0 卷 / 5 章**）」 |
| 🔴 缺口**超单批上限** | 第三卷范围改成 `第21-100章` ⇒ 口径 79 章：状态行「还差 79 章，本次先补完第 22-81 章（单批上限 60 章，剩下的下次继续）」；编排层计划量「第 22 ~ 81 章（共 60 章）」 |

> 顺带撞到一个现实：**让模型一次排 60 章本身就跑不动**（超上限的批本来就该拆/慢）。
> 所以这两条边界验的是「**交给模型的计划量**」是否被正确夹住，而不是"模型真能一次写完 60 章"。
