## 三、🔴 两条「不实测就发现不了」的 `overrides` 坑

### 坑 1：`名字@范围` 形式的键**静默不生效**

第一版写的是（语义最漂亮的那版）：

```json
"overrides": { "brace-expansion@<1.1.21": "^1.1.21" }
```

**实测结果：完全没生效** —— 3 个 `1.1.18` 原地未动，只有同时写的 `http-cache-semantics` 被改了（说明覆盖机制本身是好的，是**这个键写法不被支持**）。

⚠️ 更值得记的是：**中途那次「探针验证」是假阳性**。可可写了个最小探针（`mm3`=`minimatch@3.1.5`、`mm9`=`minimatch@9.0.9` 用别名共存），跑出「mm3 → 1.1.21、mm9 → 2.1.7 未被误伤」，据此判定语法可用 —— 但 **`^1.1.7` 本来就会自然解析到 1.1.21（1.x 最新）**，与覆盖无关。探针**没有对照组**，等于什么也没证明。

> **判据**：探针要能证伪 —— 必须让「覆盖生效」与「覆盖不生效」两条路产生**不同**的结果。凡「自然解析值 == 覆盖目标值」的场景，都不构成有效验证。

### 坑 2：嵌套覆盖**只穿透一层**，够不到孙辈

第二版改成嵌套作用域（npm 文档明确支持的写法）：

```json
"overrides": { "eslint": { "brace-expansion": "^1.1.21" } }
```

实测：`eslint/node_modules/brace-expansion` → **1.1.21 ✅**，但 `@eslint/config-array` / `@eslint/eslintrc` 下的两个 `1.1.18` **纹丝不动**。

即：`eslint` 这个键**只覆盖了它自己直接边的传递依赖**，没有沿子树一路传下去。

> **正解**：把**每一个持有旧副本的父包**都显式列成顶层键（本批列了 3 个）。这是实测出来的行为，别按「嵌套应当递归」的直觉写。

| `roarr` | ✗ | `<=2.15.4` | 日志 |

### 为何不修

`npm audit` 给的**唯一** fix 是：**把 `electron-builder` 降级到 `26.5.0`**（它自己标了 `isSemVerMajor: true`）。三条硬理由：

1. 我们刚从 24 升到 **26.15.3**，降级等于退回旧链，还搭上第一批已清掉的漏洞；
2. **26.15.3 是已验证能出包的版本** —— builder 26 的「解包改名 EPERM」修复就是针对它验证并跑通三步法出包的（见 `docs/2.9.0-封装验证记录.md`）；降级会让这条实测结论作废；
3. 上游只有 `27.0.0-alpha.9`，**没有稳定版**。

**实务风险 ≈ 0**：8 条全在构建期、不进产物；且触发条件在本项目都够不着（如 `dmg-builder` 是 macOS 路径）。

### 再评估触发条件

- `electron-builder` 发布 **27.x 稳定版** ⇒ 立即立项升级（须重跑封装三路径实测）；
- 或上述任一条从 moderate 升为 high/critical。

### 附带实测发现

`npm audit fix`（**非 force**）**修不了这批**：dry-run 显示它只打算补**平台可选二进制包**（`lightningcss` / `@tailwindcss/oxide` / `@rolldown/binding` 的跨平台变体、`fsevents` 等），**完全不碰 `electron-builder`**。想一键清掉是走不通的。

只读仓库内的 `package.json` 与 `package-lock.json`（**不碰 `node_modules`**，A 批保持零 IO）。守四件事：

1. 这 4 条 `overrides` 还在（`npm audit fix --force` 或手工清理会掉）；
