## 七、本轮方法论增量（值得写进 skill）

1. **「本轮引入的」≠「扫描器报出的」**：`§8 星号` 与 `§15 isComposing` 各只报 1 处，
   **两处都是今天我自己改出来的**。改完立刻跑一次受影响的那支扫描器，比等下一轮全量审计便宜得多。
2. **`patch-delim.mjs` 是含 JSX 属性 / 反引号 / `${}` 的片段的唯一稳法**：本轮 23 处一次落盘、零转义问题。
   但 ⚠️ **JSX 里加 `{/* 注释 */}` 不能插在 `{cond && (` 与 JSX 元素之间** —— 那是两个同级节点，
   语法直接崩（本轮踩到，tsc 报了一串 `TS1005/1382/17015`）。
3. **审计「承诺 ↔ 实现」最有价值的判据：同一文件里自己写着规则、自己又违反**。
   本轮 `aiDataSources.ts` 就是 —— 第 50 行写着「必须是真名」，第 64 行起全是别名。
   这类「自相矛盾」不需要任何外部知识就能判定，命中率极高。
4. **文案与实现相反的一类，只有对着常量看才发现**：`AIWriterBudgetPanel` 写「1/4、不放大」，
   而 `aiWriterBudget.ts` 的常量是 `ratio: 0.30` + 注释写着「不再封顶在出厂值」。
   → 审「数字承诺」时，必须把文案里的数字与**常量/配置**逐个对齐，不能只看文案内部自洽。

## 八、跟进轮：P0 修复 + UX 优化（同日）

### 8.1 P0 修复：把「读本地库快照」提到**模块顶层**

**改法比原建议更进一步**：不是"在启动块里也注册一次"，而是把注册整体**提到模块顶层** ——
放在 `desktopCloudFileStore` 定义之后，位置**早于** `CLOUD_FILE_SYNC` 启动块与 `enableDesktopCloudSync()`。

理由：**接线要放在所有入口的必经之路上**。"两条路径各注册一次"是两处会各自漂移的口径，
将来新增第三条入口（比如"从模板开新项目时自动挂云盘"）还会漏 ——
而漏掉的那处**静态检查与单测都看不出来**（这正是它能长期存活的原因）。
顶层注册天然覆盖全部入口；且 `cloud.configure()` **不重置** `localSnapshotProvider`，
所以"先注册、后 configure"的时序是安全的。

**验证（三层，缺一不可）**：

| 层 | 断言 | 结果 |
|---|---|---|
| 行为 · 正向 | 注册了快照 ⇒ 被删记录不被云端旧快照带回 | PASS（原有 ⑧） |
| 行为 · **负面对照** | **拿掉注册** ⇒ 同一条记录立刻复活（= P0 的机制本身） | PASS（新增 ⑪） |
| 结构 · **位置关系** | 注册在 `desktopLocalStore` 之后、**早于**启动块与手动开启函数；全文件**只有这一处** | PASS（新增 ⑫） |

> 🔴 **为什么原来的用例 ⑧ 抓不到这个 P0**：它在测试里**手动**调了 `cloud2.onLocalSnapshot(...)` ——
> 等于替产品补上了那一步接线。于是"syncCore 的合并逻辑正确"恒成立，而"产品的启动路径有没有注册"谁也没验。
> **测试替身补上的那一步，正是产品漏掉的那一步。**

**⑫ 的注入式验证**（证明结构断言不是恒真）：把注册块临时挪回 `enableDesktopCloudSync` 内 →
⑫ 的两条位置断言精确 FAIL（`callIdx=17237` 同时大于 `bootIdx=11641` 与 `enableIdx=14914`），
而"全文件只有一处注册"那条**仍然 PASS** —— 恰好说明**位置断言不可省**（文本存在 ≠ 每条入口走得到）。
验证后按备份整份还原、复跑回 31/31。

### 8.2 UX 优化：AI 入口的「预先禁用」（F1）

3 处会调 AI 的按钮原先只按 `loading` 禁用 —— 未配置模型时按钮可点，点下去要等**一整轮请求失败**
才弹 toast，用户只会以为"点了没反应"。现在统一 `useAIReady` 预先禁用 + `AI_DISABLED_HINT` 提示：

| 文件 | 按钮 | 真实调用链（判据一致性的依据） |
|---|---|---|
| `AIOrganize.tsx:257` | 开始整理 | `aiTasks/organize.ts` → `requireActiveProvider` |
| `AITemplateFill.tsx:229` | 生成补全 | `ai.ts aiCompleteTemplate` → `requireActiveProvider` |
| `BookBreakPanel.tsx:402` | 开始抽取 | `aiTasks/extract.ts` / `formSummary.ts` → `requireActiveProvider` |

🔴 **加守卫的前提是「判据与真实调用链一致」** —— 否则会**误禁**（比不加更糟：用户以为功能坏了）。
因此**另两处刻意不加**：

- `InterviewChat`：实际发请求的是调用方给的 `callChat`（酒馆用会话指定的模型），本组件无从判断；
- `TavernFree`：酒馆可指定自己的面板默认模型（`defaultProviderId`），而**全局活动模型可能为空** ——
  用全局就绪守卫会把"配置有效"的场景禁掉。

（`TavernControl` 也被扫描器列出，但它**不触发 AI**（只读写设置 / 显示容量建议），无需守卫。）

> 🔴 **本轮踩到一个必须写进 skill 的坑**：脚本里 `page.evaluate(() => import('/src/lib/ai.ts'))`
> 拿到的模块实例**与 React 组件 import 的不是同一个** —— `saveProviders` 更新的是 A 实例、
> 广播的也是 A 的监听者，而组件订阅在 B 上，于是界面**完全不动**。
> 症状极具迷惑性：`aiReadySnapshot()` 读出 `true`，而按钮 title 仍是「需先接入 AI 模型」。
> **更危险的是假 PASS**：清空模型后按钮确实"禁用"了，但那是组件的 `aiReady` **从没被更新过**（一直 false）——
> 与"守卫生效"毫无关系。修法：写 provider 之后**必须 `page.reload()` 并重新进项目**
> （模板 `ui-extend-outline.mjs` 一直这么写，本轮漏了）。
>
> 另一条：**验「X 时禁用」必须先隔离出 X 这一个变量** ——「开始抽取」还有 `!raw.trim()` 这个条件，
> 不填原文就去断"未配置模型 ⇒ 禁用"是**必假的假 PASS**（真实原因是"没原文"）。
> 正确姿势：先把其它条件都满足，只留被测变量浮动，再跑「有 → 可点 / 无 → 禁用且提示说的是缺 X / 配回 → 可点」三点对照。
