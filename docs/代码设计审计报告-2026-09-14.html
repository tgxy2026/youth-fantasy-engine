一、P0 · 正确性缺陷（建议优先处理）

P0-1AI 温度参数形同虚设：14 个 JSON 任务实跑在创意温度上

证据

src/lib/ai.ts:50   export const DEFAULT_TEMPERATURE   = 0.85
src/lib/ai.ts:52   export const JSON_TASK_TEMPERATURE = 0.3
src/lib/ai.ts:51-52  /** 结构化 JSON 任务（校对 / 审读 / 改稿 / 抽取）专用：低温换取格式稳定 */

实测：aiTasks.ts 内共 20 处 `await chat(`，其中仅 1 处（:1132 aiRewritePassage）传了 temperature。
其余 19 处省略该参数 → 落到 ai.ts:329 / ai.ts:409 的 `o.temperature ?? DEFAULT_TEMPERATURE` = 0.85

典型受害者（函数体自述要求 JSON 输出，却未传低温）

aiTasks.ts:371  请返回问题清单的 JSON 数组。      ← aiProofread 的 system prompt
aiTasks.ts:381  { timeoutMs, signal, onToken }      ← 无 temperature，实跑 0.85

同样中招的还有：aiOrganizeRows、aiSuggestNames、aiReviewSensitive、 aiContinuityAudit、aiAnalyzeFeedback、aiDiagnoseProject、 aiForeshadowReview、aiDedupTerms、aiStyleCheck、 aiChapterReview、aiOocCheck、aiContinuationAdvice、 aiExtractSettingEntities。

根因　temperature 是「可选参数」，全靠任务层自觉传，无任何机制约束。

影响　代码注释亲口警告：「结构化 JSON 任务必须显式传低值，否则退到文本兜底（2.0.1 的『只剩标点』即由此放大）」。 即：注释承诺的实现从未在该路径生效，2.0.1 已修过的那个 bug 的温床原地保留。表现为解析失败率升高、AI 返回散文而非 JSON、退化成兜底文案。

建议　不要逐个补参数（下次新增任务还会漏）。在 ai.ts 的 chat 上层加一个语义开关， 例如 chat(cfg, messages, { json:true }) 由内部统一注入 JSON_TASK_TEMPERATURE， 任务层只声明「我是 JSON 任务」而非「温度填几」。

改动量　小（1 个函数签名 + 14 处调用点）；风险　低，但属行为变更（AI 输出会更结构化、更保守），需老大认可。

P0-2同步文件「读失败」被当成「空库」，随后 push 覆盖真实云端文件

证据

src/lib/syncTransport.ts:115-124  fsaRead  catch { return null }        ← 权限被拒 / 文件被云盘客户端锁住
src/lib/syncTransport.ts:157-173  nodeRead catch { return null }
src/lib/syncTransport.ts:199-207  parseRev: catch { return {rev:0} }   // 注释原文：损坏文件当作空库处理
src/lib/syncTransport.ts:221-231  push(): cur = parseRev(await readRaw(name))
                                  if (cur.rev > baseRev) return 409     ← 读失败得 rev=0，0 > baseRev 恒 false
                                  newRev = baseRev + 1
                                  await writeRaw(name, ...)             ← 直接覆盖

根因　「文件不存在」「权限被拒」「JSON 损坏」三种截然不同的情况被统一降级为 rev=0，丢掉了最危险的中间态：文件存在但读不到。

影响　数据丢失级，但需触发条件：云盘客户端同步瞬间锁文件、目录权限失效、或同步文件被写坏时， 一次 push 就会用本地内容整体覆盖云端文件。写后回读校验（:229-231）确实会返回 409 触发合并重试—— 但那时文件已经被覆盖了，对方设备的新内容当场消失。

建议　① 区分 ENOENT（可安全当空库）与其它读错误（必须中止 push）； ② parseRev 解析失败时不再返回 rev=0，而是标记 corrupt，先把原文件备份为 .corrupt 再拒绝 push。

改动量　小～中（1 个文件）；风险　低，且是纯加固方向。

三、P2 · 工程基建（地基，建议先补）

P2-1引入 ESLint / Prettier

现状　零配置。而源码里有 5 处 // eslint-disable-line（InspireTools.tsx:52、 NovelEditor.tsx:426,454、OutlineSheet.tsx:60、TableSheet.tsx:313）—— 这些注释目前是装饰品，因为根本没有 ESLint 在运行。

P2-2给测试加个 runner

现状　tests/ 下有 5 个测试文件（累计 61 个用例，手搓 ok(name, cond) 断言）， 但 package.json 里没有 test 脚本，也没有 vitest/jest 依赖——测试目前得靠手动拼命令行跑。 同时项目此前跑测试的方式是「esbuild 转译 TS 后直测」（见清单 #005/#023 的处理记录）。

建议　加一条 npm test（沿用 esbuild 转译方案即可，不必引入新框架）， 把「改完必须能一键跑回归」变成默认动作。

四、已核实并澄清（避免误报的说明）

审计过程中有若干「看起来很吓人、复核后不成立或已被接受」的项，单独说明，免得后续被当成新问题反复翻出来：

#初判复核结论
1 便携版 flushNow 与在途保存互斥，最后一次编辑可能不落盘 已知取舍不算新问题。清单 #034 已处理并明确登记为「FSA 无同步 API，本项是尽力而为」的残留， 且 UI 会提示「保存出错，点击重试」。原审计称「比注释更糟」属过度解读。
2 便携版未连接数据文件时 scheduleSave() 静默丢弃所有写入（portable.ts:197） 已缓解未连接时 App.tsx:262 会渲染 PortableGate 拦在编辑入口之前， 用户到不了编辑器，非活跃风险。可保留一道防御性报错，但不必按 P0 处理。
3 桌面版 flushDesktopSync 不检查 saving，与在途异步写竞态 窗口极窄两条路径序列化的是同一个内存 data 对象， 且 beforeunload 之后不再产生新编辑，内容一致。真实但窗口极窄，可加一个 generation 计数器兜底。
4 离线期间写入的本地数据，恢复联网后不回流云端（db.ts:303-308） 一致性问题复核成立，但性质是「分裂脑」而非丢失—— 数据仍在本地文件里，只是 UI 恢复在线后读云端而看不到。与 #011 相邻但未覆盖（#011 只做了「回退本地」，未做「回流云端」）。
为什么这一节单独列？ 因为审计报告最怕的不是漏报，而是把已接受的设计取舍当成新发现—— 那会让老大重复判断同一件事，也会稀释真正需要处理的项。本节四项都经过源码级复核，予以明确降级或排除。
