## 二、结果

### 2.1 读取延迟（服务端 HTTP，毫秒）

| 操作 | S1 p50 / p95 | S2 p50 / p95 | S3 p50 / p95 |
| --- | --- | --- | --- |
| 列表（一页 20） | 3.8 / 7.7 | 4.1 / 7.7 | 4.8 / 12.3 |
| 详情（含正文） | 1.9 / 3.4 | 3.0 / 4.6 | 3.3 / 4.8 |
| 评论分页（20 条） | 2.8 / 10.6 | 6.1 / 27.6 | 14.2 / 95.0 |
| 排行（日） | 7.5 / 8.6 | 19.5 / 20.6 | 35.0 / 40.7 |
| 列表 20 并发 | 19.1 / 29.7 | 18.4 / 28.7 | 28.3 / 48.6 |
| 详情 20 并发 | 8.3 / 13.5 | 6.2 / 9.8 | 5.8 / 9.6 |

读取整体随规模增长但可用；**评论分页在 S3 明显变慢**，因为每次请求都扫描 49,900 条评论并排序，没有按帖子索引。

### 2.2 写入延迟（毫秒）

| 操作 | S1 p50 / p95 | S2 p50 / p95 | S3 p50 / p95 |
| --- | --- | --- | --- |
| 投稿（写 posts.json） | 7.1 / 9.1 | 21.5 / 24.0 | 237.2 / 244.1（1/5 因容量满失败） |
| 评论（写 comments + posts） | 15.9 / 16.5 | 56.4 / 60.8 | 343.8 / 520.6 |
| 投票（写 votes + posts） | 9.4 / 11.2 | 22.8 / 24.1 | 277.5 / 308.2 |
| 投稿 5 并发 | 16.6 / 26.2 | 55.7 / 89.6 | 27.6 / 43.1（5/5 快速失败：容量已满） |

写入延迟与目标文件大小近似线性：投稿要重写 41.8 MB 的 `posts.json`，评论要写 13.1 MB + 41.8 MB，投票同样要重写 posts。**S3 的 244–521 ms 是单次请求的服务端时间，且同步写会阻塞事件循环。**

### 2.3 资源与备份

| 指标 | S1 | S2 | S3 |
| --- | --- | --- | --- |
| 服务进程 RSS（采样） | 58.7 MB | 109.8 MB | 183.6 MB |
| 堆使用 | 12.5 MB | 37.0 MB | 106.6 MB |
| 事件循环 p99 延迟 | 53.6 ms | 60.7 ms | **252.7 ms（峰值 520.6 ms）** |
| 备份耗时（8 文件 + 校验） | 93 ms | 342 ms | 1,768 ms |
| 恢复耗时（停写后） | 128 ms | 483 ms | 2,347 ms |

备份/恢复耗时包含 JSON 解析、重写、哈希与目录切换；S3 的 1.8–2.3 秒属于一次性停写窗口，需纳入演练与维护窗口评估。

### 2.4 S2 读写交错（补测）

同一服务上同时发出 20 个读取（列表/详情/评论）与 5 个评论写入：

| 指标 | 结果 |
| --- | --- |
| 读取 p95（列表 / 详情 / 评论） | 41.4 / 41.7 / 40.1 ms |
| 写入 p95 | 307.1 ms |
| 事件循环 p99 | 282.9 ms（均值 36.7 ms） |
| RSS | 103.8 MB |
| 正确性 | 全部成功；评论 total +5；详情计数与 total 一致 |

交错时写入排队会把单个写延迟抬高，读取仍可在 50 ms 内完成；这是单进程同步写的预期表现。

### 2.5 正确性

三档均通过同一组检查（11/11）：列表一页 20 条、详情正文、评论 `total` 为数值且与详情计数一致、写入后 total 增加 5、投票计数增加、新投稿进入待审并出现在「我的投稿」、排行可读、备份前一致性检查 `repairs=0`、备份与恢复成功。S2 交错补测 3/3 通过。未发现数据错乱。

S3 的「投稿 1/5 失败」与「并发写 5/5 失败」是 **5,000 篇容量闸**按设计拒绝（`CAPACITY_FULL`），不是数据损坏或崩溃；拒绝很快，没有写入半份数据。

## 三、容量结论与存储路线建议

### 3.1 结论

- **S1/S2：当前 JSON 存储可支撑。** 读取 p95 在 30 ms 内、串行写入 p95 ≤ 61 ms、事件循环 p99 ≤ 61 ms、备份恢复亚秒级；S2 并发写 p95 约 90 ms。
- **S3：出现明确瓶颈。** 单次写入 244–521 ms、事件循环 p99 252.7 ms（峰值 520.6 ms）、RSS 183.6 MB；并发写会排队，评论读延迟上升。此时仍能正确拒绝超限写入，但用户体验与并发能力受限。
- **读多写少、单进程、单机、可接受秒级停写备份窗口** 是 JSON 继续可用的前提；不满足时应评估结构化存储。

### 3.2 保留 JSON 的补强（本版已做/建议）

1. 已做：评论 `total` 权威计数、计数自愈、写失败缓存清理、核心文件丢失拒绝启动、停写一致性备份/校验/恢复工具、备份读取前后文件状态复核、协作式备份锁（服务启动/写入/备份/恢复共同遵守）。
2. 建议（未实施）：
   - 评论按帖子建立内存索引或分文件，避免每次分页扫描全表；
   - 写入合并/去抖（同一帖计数批量写），降低 posts.json 重写频率；
   - 为 atomic 写入增加 fsync（文件与目录），明确断电语义；
   - 监测写入 p95 与事件循环延迟，达到阈值前提早限流/告警。
3. 锁的边界：只约束遵守协议的进程；旧版本或外部写入者可绕过，不能替代停写确认与运维检查。

### 3.3 SQLite 评估项（未迁移，需决策）

若社区目标接近 S3 或写入 p95 持续 >500 ms，建议单机 SQLite（WAL）方案，迁移前需单独评审：

| JSON | SQLite 映射 |
| --- | --- |
| posts.json / versions | `posts` + `post_versions`（`post_id`, `vid`, `created_at`） |
| comments.json | `comments`（索引 `post_id, status, created_at, id`） |
| votes.json | `votes`（唯一键 `post_id, uid`） |
| reports.json | `reports`（`kind`, `target_type`, `target_id`, `status`） |
| profiles.json | `profiles`（uid 主键） |
| rank.json | `rank_rows`（唯一键 `uid, device_id, project_id, date`） |
| audit.json | `audit`（环形保留，按时间索引） |
| state.json | `state`（键值） |

迁移要求：停写或双写窗口、逐条校验记录数与关键关联、事务边界（评论 + 计数同一事务）、失败回滚到 JSON、备份用 SQLite 在线备份/一致性快照、恢复演练、旧版客户端兼容与回滚策略。**本版不做自动迁移，也不宣称 SQLite 一定更快；需按目标、预算与运维能力决策。**

## 四、监测方案（本机已启用；加密异地/外部告警未启用）

### 4.1 指标（只聚合，不记录正文/账号标识）

| 类别 | 指标 | 采集方式建议 |
| --- | --- | --- |
| 容量 | `community/` 目录字节、各文件字节、帖子/评论/投票/举报/档案/排行/审计条数 | `node server/community-backup.mjs inspect --json`（默认不含正文/内部快照） |
| 磁盘 | 数据盘剩余字节、使用率 | 主机 agent / `df` |
| 进程 | RSS、heapUsed、事件循环 p99/max | 进程内采样或 `/proc`/主机 agent |
| 请求 | 各接口 p50/p95/p99、5xx/429/503 次数 | 反向代理日志或进程内计数器 |
| 写入 | 写失败次数、`CAPACITY_FULL`、`RATE_LIMITED` | 进程内计数器（只计数，不含正文） |
| 备份 | 最近成功时间、耗时、校验结果、失败次数、备份目录体积 | CLI 退出码 + `manifest.json`（不含正文） |
| 恢复 | 最近演练时间、结果、耗时 | 演练记录 |

**备份 CLI 边界**：`backup`/`restore` 必须 `--confirm-stopped`，并获取协作式 `<community>.backup.lock`；服务启动会拒绝残留锁，运行中的写请求返回 503，读取仍可用。读取前统一记录 8 文件状态、读取后统一复核，检测到并发写入返回 `CONCURRENT_WRITE`，不生成正式备份。`verify --users <users.json>` 只报告「多少个社区引用找不到账号」，不输出 uid/登录名。锁冲突返回 `LOCKED`；崩溃残留锁需人工核对后 `unlock --confirm-stale`，不得自动清理未知锁。

### 4.2 阈值建议（按推荐方案作为计划默认，待演练）

| 指标 | 警告 | 严重 |
| --- | --- | --- |
| `community/` 体积 | 45 MB | 60 MB（接近 S3 69 MB） |
| 写入 p95 | 300 ms | 700 ms |
| 事件循环 p99 | 200 ms | 400 ms |
| 评论分页 p95 | 80 ms | 150 ms |
| 最近成功备份 | > 26 h | > 52 h |
| 备份失败 | 连续 1 次告警 | 连续 2 次升级 |
| 数据盘使用率 | 70% | 85% |

上述为计划默认，不是产品承诺。生产已安装 `/opt/yfe/scripts/community-backup-daily.sh`（每日 03:15）与 `community-monitor.sh`（每小时第 5 分）；告警写入 `/opt/yfe/logs/community-*.log` 并调用 `logger`，**未接外部告警通道**。告警接收方式、值班负责人、异地副本与加密密钥保管仍需生产授权；当前未创建外部通知任务。

### 4.3 原则与边界

- 不自动删除用户内容来释放空间；容量满时返回明确提示并停止新写入（现有 `CAPACITY_FULL`）。
- 监测输出不得包含正文、登录名、uid、昵称、令牌或密钥；`inspect`/`verify` 默认只输出统计与诊断。
- 备份失败必须可发现；「没有告警」不能等同于「备份正常」。
- 备份锁是协作式协议，不防旧版本/外部写入者；写入在锁检查后、落盘前仍有被备份窗口切入的间隙，停写确认、启动前检查与人工核对仍必需。
- 本版已在生产安装本地备份工具与 cron 脚本；未接外部告警通道、未做加密异地副本，未部署应用代码。
