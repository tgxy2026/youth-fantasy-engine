## 二、已修问题

### P1（3 项）

**P1-1 ·「恢复云端章节」在云模式下会被静默撤销**（`src/lib/db/core.ts` · `src/lib/db/syncConflicts.ts`）

- 根因：云模式下 `ops.put` 只写**云端实例的内存 cache**，本机数据文件自开启同步那刻起就不再更新。
  恢复完成后 `SyncConflictCenter` 隔 500ms 就 `location.reload()`，而**本机文件仍是被冻结的旧稿** ⇒
  三路合并拿它当「本地那一份」、按「本地优先」把恢复结果盖回去 —— 作者看到「已恢复」，数据其实没变
  （还会再产生一份新的冲突副本）。
- 证据：兄弟路径「从云端备份恢复」早已防这一手 ——
  `syncCore.ts:742-745` 明确要求 `cloudRestoreHandler?.(restored)`，对应 `db/core.ts:262` 注册的
  `onCloudRestored`（镜像 `mirrorCloudCacheToLocal(cache, true)` ＋ `flushDesktop()`）。
  本轮新增的 `restoreServerChapterFromConflict` **绕过了这条**。
- 修复：`db/core.ts` 新增并导出 `persistAfterRestore()` —— 云模式「推云端 → 镜像本机 → 落盘」；
  便携模式走 `flushPortable()`；浏览器兜底直接放行；桌面非云只落盘。`syncConflicts.ts` 恢复流程末尾调用。
- 说明：`tests/syncConflicts.test.ts` 用的是 `memoryOps`（`ops` 就是本地），**结构上覆盖不到云模式**，
  这正是它没被单测拦住的原因。已在本报告「待办」中记一条「补带 cloudStore 的用例」。

**P1-2 ·「资料提及」面板检索失败会永久卡在「检索中…」**（`src/components/app/MentionPanel.tsx`）

- 根因：`useEffect` 里 `findMentions(...).then(...)` **没有 `.catch`**。`findMentions` 内部要读
  `getAllChapters()` / `getAllVolumes()`，一旦 reject（磁盘占用 / 索引异常 / 切项目竞态），
  `hits` 恒为 `null` ⇒ 界面永远停在「检索中…」，既没有失败提示，也没有重试入口（违反「绝不静默」）。
- 修复：加 `error` 态与 `.catch`；失败时渲染「检索失败：<原因>」，底栏计数改为「检索失败」，不再显示误导性的「0 章提及」。

**P1-3 · 章节冲突「不可恢复」时既没按钮也没说明**（`src/components/app/SyncConflictCenter.tsx`）

- 根因：恢复按钮条件是「`store==='chapters'` ＆ `server!=null` ＆ `projectId` 相符」，
  而说明行只在 `store !== 'chapters'` 才渲染。于是「章节冲突但**云端已删**」与「章节冲突但**属其它项目**」
  两种情形下，面板上**既没有恢复按钮、也没有任何原因说明** —— 作者很可能直接点「删除副本」，
  把本可导出的云端版本丢掉（同样违反「绝不静默」）。
- 修复：抽出 `canRestore`（四条件）与 `restoreBlockedReason()`，按情形给差异化说明：
  非章节 / 云端已删（可导出）/ 本机已删（可导出核对）/ 属其它项目（请打开对应项目）。

## 三、判定不改（7 项 · 附理由）

1. **`lib/tavern/prompt.ts` 未包 `promptGuard`（扫描器 P6 命中）** —— 三份历史审计（2.8.0 / 2.9.3 / 3.0）均已书面判定：该处拼的是**字段名** `content` 与**扮演前提材料**（角色卡 / 剧本 / 我的档案），
   不是被分析的作者正文；包成「不可信数据块」会与「让模型成为那个角色」冲突。属**设计**，非漏包。
2. **`README.md` / `package.json` 仍写 3.0.4** —— 版本号在发布流水线里随封装同步（「版本号 → 打包 → 同步 → Release」），
   源码树开发期保持上一发布版号是既有约定；现在改会与已发布 Release 打架。**发版时一并同步**（已入待办）。
3. **`aiDataSources` items 里的「本章细纲」** —— 与**界面勾选标签**（`jiewenji/jieWenJiParts.tsx:65` 的 `CONTINUE_PICKS`）逐字一致；
   schema 真名是「章节细纲」，二者指同一份数据。改 aiDataSources 反而会与作者实际看到的勾选框不符；
   要统一就该**同时**改 UI 标签（属文案设计决策），故本轮只记录、不动。
4. **`ai/aiAssist.ts` 的 `'续写'` 与 `'在已有正文后自动续写'`** —— 二者是**不同字段**：前者是给作者看的来源**标签**，后者是「用在什么环节」的**白话说明**。分工不同，非不一致。
5. **非 `chapters` 冲突不支持原位恢复** —— 设计取舍（projects / volumes / tableRows / formData 等有跨记录关联，原位覆盖风险高）。
   文案已如实披露「此类型暂不支持安全的原位恢复」，且「删除副本」有 danger 确认、「标为已处理」不丢数据 ⇒ 无静默丢弃路径。
6. **`NovelEditorChapterTree.tsx:295 / 325` 可点击 `span`/`div` 键盘不可达** —— 确属缺陷，但正解是 `role="tree"` ＋ roving tabindex；
   给 300+ 章节行各加 `tabIndex={0}` 会让键盘 Tab 流被逐行吞掉、**反而更差**。记入后续专项，不做半吊子修。
   （扫描器点名的 `:144` 是 `aria-hidden` 装饰遮罩，本就豁免。）
7. **`audit-label-consistency` 的「并列按钮字数不齐」清单**（toggle 组 3/9、相邻组 59/108、常量组 83/127）——
   工具自述「只给线索」，且清单里绝大多数是**排除项**（主操作＋取消、含数字/英文的规格、数据表如人名与主题名）。
   改按钮文案属**设计决策**（会动到界面语感），不在代码审计的处置范围。

### 另两处「看着像、实为误报」的复核记录

- `lib/flow/pipeline.ts` 的 `exec()`：是**阶段执行器回调**（`StageExecutor`，见该文件 `on(id, exec)`），
  与 `child_process.exec` 无关 —— 扫描器 S2 误报。
- `editor/NovelEditor.tsx:572` 的 `dangerouslySetInnerHTML={{ __html: highlightHTML }}`：
  `highlightHTML` 由 `novelEditorHelpers.buildHighlight()` 产出，**每一段文本都先过 `escapeHtml`**
  （`& < >` 三字符映射，`:19` / `:45` / `:53` / `:54` / `:58`），只有自造的 `<mark class="ref-mark">` 是标签 ——
  无注入面，与历史两处判定一致。
