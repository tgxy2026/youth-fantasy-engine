# 青春幻想引擎 3.1.1 版本规划

> 规划日期：2026-10-16 ｜ 源码基线：3.1.0
> 来源：3.1.0 独立复核（`docs/3.1.0-独立验收复核报告-2026-10-15.md`、`docs/3.1.0-皎皎交付独立复核-2026-10-16.md`）与第二轮全量六维审计（`docs/3.1.0-全量审计报告-2026-10-16.md`）的遗留项。
> 排序依据：**主人 2026-10-16 拍板的实施顺序** —— 冲突中心优化 → 章节规划板优化 → 「纯黑白」范围补齐。

---

## 1. 版本定位

3.1.0 已把「长篇创作工作流」与「同步分叉可查看、可恢复」的主干打通（P0-A/B/C/D + P1，含两轮独立复核与两轮全量审计）。3.1.1 **不新增功能组、不引入新数据模型**，只做三件收尾：

1. 3.1.0 里「能用，但量一大就不好用」的**冲突中心**；
2. 3.1.0 里「只读 MVP 够用，但缺关键提示」的**章节规划板**；
3. 3.1.0 里**主动保留了范围差异**、用户已明确要求补齐的**「纯黑白」全覆盖**。

三项都在 3.1.0 的既有结构上改，**不改项目数据格式、不改同步协议、不做迁移**。

### 版本成功标准

- 冲突记录上百条时，作者能**筛出想看的那几条**、看得见每条占多大体积、知道什么时候会被清掉。
- 章节规划板上能一眼看出「这一章最后动过是什么时候」「状态标着完稿但正文还是空的」这类不一致。
- 切到「纯黑白」后，图谱 / 地图 / 情节画布 / 结构节奏带里的信息**照样分得清** —— 靠线型、符号、文字，而不是靠颜色深浅。
- 旧项目、便携版、自定义项目（未启用部分模块）**全部照常可用**。

## 2. 范围

### 2.1 冲突中心优化（优先级 1）

**现状**：`SyncConflictCenter.tsx` 全量读取并渲染冲突记录，无分页 / 无类型筛选 / 无体积显示 / 无保留期限。冲突副本正文会累计增大单文件数据量。

**交付内容**

| 项 | 说明 |
|---|---|
| 分页 / 分批渲染 | 默认按发生时间倒序，分批加载（与「资料提及」面板同一范式：`PAGE=50` + 底部状态条）；避免大型正文副本一次性全渲染 |
| 类型筛选 | 按 `store`（章节 / 项目 / 分卷 / 设定表 / 表单）与「已处理 / 未处理」筛选；未处理数量沿用现有的入口角标 |
| 记录体积显示 | 逐条显示副本大小；顶部显示冲突数据合计占用，让作者对「为什么数据文件变大了」有据可查 |
| 保留期限与大小上限 | **先定义并展示**，再谈自动清理 —— 见下方「不做」 |

**验收口径**

1. 300 条冲突样本下，首屏不渲染全部记录；筛选与分页切换无卡顿。
2. 每条冲突能看出类型、发生时间、记录名 / 键、体积。
3. 体积统计与导出 / 备份后的实际增量吻合（误差可解释）。
4. 关闭重开后筛选状态可恢复（或明确重置为默认）。

**预估**：4–6 人日；难度：中。

### 2.2 章节规划板优化（优先级 2）

**现状**：3.1.0 的规划板是只读 MVP —— 展示标题、卷、状态、摘要、字数，缺「更新时间」与「状态与正文不一致」提示；且工作面板仍**一次读入整章正文**。

**交付内容**

| 项 | 说明 |
|---|---|
| 更新时间 | 章节卡显示 `updatedAt`（相对时间，如「3 天前」） |
| 状态不一致提示 | 标着「完稿 / 已发布」但正文为空、或标着「构思」却已写了几千字 —— **提示而不自动改**（沿用项目「不擅自替作者决定」的口径） |
| 长篇读取优化 | 先测量，再决定方案（见下） |

**长篇读取优化的实施前提**：`Dashboard.tsx` 目前调 `getAllChapters()`（含整章正文）。**必须先做测量**：用 300–500 章 / 百万字级样本记录首屏耗时与内存，再在两条路线里选：

- **A. 元数据投影**：新增只读元数据查询（标题 / 卷 / 状态 / 字数 / 时间），卡片列表不再触碰 `content`；
- **B. 惰性加载**：仍走整章读取，但只在展开某张卡时读正文。

⚠️ 以测量结果为准，**不以「列表分批渲染」代替数据读取验收** —— 那是渲染层的事，不解决读取层的问题。

**验收口径**

1. 300+ 章样例下，首屏渲染不读取整本正文（或经测量确认读取成本可接受并记录数据）。
2. 更新时间与状态提示来自现有章节字段，不新增持久化字段。
3. 提示文案是「提示」而非「质量判断」（如「状态标为完稿，但正文为空」而非「这章没写完」）。

**预估**：3–5 人日（含测量）；难度：中。

### 2.3 「纯黑白」范围补齐（优先级 3）

**现状**：3.1.0 的 P0-D 完成了界面、弹窗、交互状态与**码字热力图**（3.1.0 审计补），但**主动保留**了三处范围差异。**主人 2026-10-16 已明确要求全部收成黑白**，故该取舍作废。

**交付内容**

| 处 | 现状 | 目标 |
|---|---|---|
| 图谱 / 地图 / 情节画布 / 结构节奏带的**语义数据色** | `palette.ts` 的 `BEAT_COLORS`、`REL_*`、`GROUP_*`、`MAP_*`、`PLOT_*`、`GOAL_ACTUAL_COLOR` 为渲染时取值的固定 hex，主题切换不触发重渲染 | 全部收成二值；类别区分改由**线型 / 符号 / 文字标记**承担 |
| 图表内部 1px 细线级透明度混色 | 时间轴轨道、正文缩进导向线、画布点格保留原样 | 一并收进二值 |
| 内置背景图案 | 可开关装饰、不做反色 | 保持（不做全屏阈值滤镜，避免破坏文字渲染）—— **仍豁免** |

**验收口径**

1. 纯黑白下，图谱 / 地图 / 画布 / 节奏带里**同类节点同形、异类节点异形**，无需依赖颜色即可分辨。
2. 图例同步更新（图例本身也不得用颜色区分）。
3. 切回其他主题时，语义色**恢复原样**（不因本轮改动而丢失）。
4. 在 Windows 桌面端与预览环境检查，最终由提出需求的用户确认。

**预估**：4–6 人日；难度：中高。主要成本在各图表的「颜色 → 形状」映射设计与图例改造。

---

## 3. 明确不做

- **冲突副本的自动清理 / 自动删除** —— 保留期限与大小上限**先定义、先展示**，自动删除策略须主人单独确认（数据不可逆）。
- **章节规划板的拖拽改序 / 跨卷移动 / 一章多场景** —— 会动到卷序、编号、时间线，属独立立项。
- **图谱的自动布局算法重做** —— 本轮只改配色承载方式。
- **移动端、实时多人协作、平台自动发布** —— 沿用 3.1 的边界。
- **数据格式 / 同步协议变更** —— 3.1.1 不动这些，因此**不需要迁移**。

---

## 4. 风险与应对

| 风险 | 级别 | 应对 |
|---|---|---|
| 自动清理误删作者数据 | 高 | 本轮**不做**自动删除；只做展示与上限定义 |
| 语义色改二值后图表可读性下降 | 中 | 先做一版形状映射并在真实项目上看效果；必要时按图类型分别设计 |
| 长篇读取优化方向选错 | 中 | 先测量后决策，两条路线的数据都要落到文档里 |
| 三项并行导致回归面扩大 | 中 | 按 1 → 2 → 3 顺序做，每项独立提交、独立跑门禁 |

## 5. 里程碑建议

| 阶段 | 内容 | 退出条件 |
|---|---|---|
| M1 | 冲突中心分页 / 筛选 / 体积展示 | 300 条样本可用；筛选状态行为明确 |
| M2 | 章节规划板更新时间与状态提示 | 提示不自动改数据；文案经复核 |
| M3 | 长篇读取测量与优化 | 300–500 章样本数据落档，方案确定并实现 |
| M4 | 「纯黑白」语义色全覆盖 | 四类图表无颜色依赖可辨；其他主题无回归 |
| M5 | 整合与回归 | 全量单测 / 构建 / 实机通过；旧项目与自定义项目兼容 |

---

## 6. 与 3.1.0 的关系

3.1.0 已发布的内容**不回改**：3.1.1 只做上述三项补齐。若三项之间出现资源冲突，**按主人拍板的顺序执行**（冲突中心 → 规划板 → 黑白）。
