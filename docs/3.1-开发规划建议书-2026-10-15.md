# 青春幻想引擎 3.1 开发规划建议书

> 文档类型：版本规划建议（供 3.1 排期与需求评审）  
> 调研日期：2026-10-15  
> 项目基线：青春幻想引擎 v3.0.4  
> 调研范围：项目代码与现有文档、长篇小说创作管理产品的官方功能资料  
> 本文只提出规划建议，不代表功能已承诺进入版本。

---

## 一、建议结论

3.1 不建议继续横向增加独立页签。项目现有功能已经覆盖长篇小说从开书、设定、大纲、正文到审校、归档与导出的主要环节，且在伏笔闭环、网文节奏、连续性检查、世界构建、数据本地化和 AI 上下文治理上形成了鲜明特色。

建议 3.1 的版本主题定为：

> **把已有创作资产串成更短、更直观、更安全的写作闭环。**

优先补三个方面：

1. **规划与正文之间的可视化联动**：增加一个真正连着章节、情节线、人物/地点和写作状态的场景规划板，让作者能从全书视图直接进入写作、调整顺序并看出缺口。
2. **降低功能学习与日常操作成本**：为新项目提供循序渐进的工作流入口，把灵感、设定、细纲、正文和检查结果之间的下一步动作说清楚。
3. **加强跨设备同步的冲突处理**：在已有本地备份、WebDAV/S3 同步和并发分叉检测基础上，补足冲突查看、恢复与人工选择流程；评估轻量移动端写作入口，但不把实时多人协作作为 3.1 前提。

建议将“系列级资料更新”和“面向网文平台的发布辅助”列为 3.1.x 或后续候选，先做需求验证与数据模型设计。

## 二、调研方法与判断口径

### 2.1 项目核查

以仓库当前版本 `v3.0.4` 为基线，核对 `README.md`、3.0.4 更新说明、功能讲解文档、版本演进记录，以及 `src/lib/schema*`、`src/lib/semantic`、`src/lib/sync`、`src/lib/tavern`、`src/lib/audit` 等实现目录。2.8.0 的竞品规划只作为历史线索，不直接作为当前缺口结论。

### 2.2 竞品抽样

选取覆盖不同路线的产品：Scrivener（桌面长文项目与出版）、Plottr（视觉大纲与系列规划）、Novelcrafter（Codex 设定库与 AI 上下文）、Campfire（模块化世界构建与协作）、Dabble（写作、Plot Grid 与云同步），以及作家助手、番茄作家助手、橙瓜码字等中文网文写作产品。

### 2.3 限制

对比依据为厂商官网、帮助中心、应用商店官方介绍和本项目仓库文档。厂商页面能够说明其公开功能方向，但不能代替同一数据规模下的实机体验或用户研究。因此本文比较“产品能力和工作流”，不比较未公开的性能、准确率或用户规模；商业产品的宣传性描述不视作独立验证结果。

## 三、项目现有能力画像

项目不是单一的码字编辑器，而是一个以本地项目数据为中心的长篇创作工作台。完整项目目前有 10 个功能组、约 51 个页签，支持自定义项目启用部分模块。

| 创作阶段     | 现有能力（v3.0.4）                                        |
| -------- | --------------------------------------------------- |
| 开书与构思    | 作品定位、题材包、灵感工具、创意访谈、结构模板、创意写作流程、一键拆书                 |
| 设定与资料    | 主要/次要角色、NPC、关系图、势力与地理、地图、历史、术语、物品、力量体系、世界引擎、参考资料库   |
| 规划与连载管理  | 全书/分卷/章节大纲、章节总表、伏笔状态与回收条件、故事时间线、支线、知情权限、爽点节奏、写作进度   |
| 正文与审稿    | 分卷章节树、正文编辑、全文检索、章节快照、写作目标、AI 续写/改写/校对/审读、章节建议段、投稿导出 |
| 长篇一致性    | 设定检索、章节摘要、语义向量检索、知识库、连续性检查、伏笔闭环看板、设定变更、创作轨迹与证据包     |
| AI 与隐私控制 | 多模型路由、上下文预算、可编辑提示词、AI 数据来源说明、保密等级与防剧透、本地模型支持        |
| 数据与维护    | 本机存储、自动/手动备份、数据健康检查、加密迁移、WebDAV/S3 私有网盘同步、并发分叉检测    |
| 发行与复盘    | TXT/Markdown/DOCX/EPUB/平台粘贴版导出、读者反馈台账、市场雷达          |

### 3.1 已经补齐的历史规划

2.8.0 的旧规划曾把语义 RAG、多模型路由、文风档、全书优化工单、参考资料库、市场雷达列为缺口；README 的 3.0 演进记录显示这些能力已经陆续落地。因此它们**不是 3.1 的新增缺失项**。同样，结构模板、伏笔闭环、AI 修订 diff、关系/时间线/地图等已有能力，也不应重复立项。

### 4.4 开源工具给出的趋势与本项目判断

这批开源项目显示，AI 小说工具正在从“单次续写按钮”走向“带状态的创作任务”：规划、写作、审稿、修订、状态更新由多个阶段组成；运行过程需要暂停、恢复、重试和审阅；生成的设定和正文变更需要预览、校验后再写入。部分项目进一步把自然语言聊天做成跨模块操作入口。

青春幻想引擎已经拥有长任务中心、AI 运行账本、语义检索、多模型路由、章后设定同步、审读、优化工单和章节快照，因此不能把“缺少 Agent”简单等同为“需要重写成 Agent 产品”。相对薄弱处是：**AI 能力按专用面板分布，尚缺一个可选的跨功能任务编排层，能把用户提出的目标拆成可见步骤、调用现有能力，并在改动正文/设定前交给作者确认。**

建议只把它作为 3.1.x 候选：先在现有 AI 任务中心上验证一个小范围工作流（例如“整卷检查→列问题→选定问题→生成建议段/修订工单”），复用当前功能和数据结构，明确每一步读写范围、模型调用、预算、产物和撤销方式。若作者偏好按钮式、逐项控制的操作，就保留现有入口，不为了追逐 Agent 趋势而增加聊天入口。

## 五、当前最值得补强的差距

### A. 规划到正文缺少一个场景级的“工作现场”——建议 P0

项目拥有总纲、卷纲、细纲、情节推演画布、支线、爽点、伏笔和时间线，但它们按不同管理主题分布在多个页签。相较 Plottr/Dabble 的场景卡与剧情线矩阵，当前较难在一个视图里同时回答：

- 哪个场景属于哪条主线/支线，涉及哪些人物和地点？
- 这一场写到什么状态，是否有细纲、正文和检查结果？
- 改变场景顺序会影响哪些章节、伏笔或时间安排？

建议增加可选的“场景规划板”，优先复用现有章节、剧情线和角色/地点引用，不另造一套平行数据。第一期以章节或场景卡、剧情线泳道、状态/人物/地点筛选、拖拽排序、点击跳转正文为范围；跨章依赖和自动改写大纲留到后续。

### B. 功能很全，但学习路径和日常入口偏分散——建议 P0

51 个页签为深度管理提供了空间，也提高了新用户理解“先做什么、什么时候来这里”的成本。现有使用指南和首启流程有基础，但仍可将新建项目后的关键路径做成项目内引导：作品定位 → 角色/世界 → 大纲 → 章节 → 写作 → 检查/定稿。每一步应显示必要资料、已完成状态与直接入口，允许跳过，不应强制作者采用固定写法。

同时建议把灵感收集、未整理条目、待写章节、临近回收伏笔和待修订工单汇总为“下一步”列表。已有数据应由现有模块读取；不要再建立重复待办表。

### C. 跨设备同步能保护分叉，但用户仍缺少可操作的冲突解决体验——建议 P0/P1

项目支持私有网盘直连同步、备份和并发分叉检测，这是优势。现行说明仍提醒多设备并发时避免同时推送；发现分叉后，作者需要理解备份、同步状态和版本选择，才能避免覆盖。相较云端产品的自动同步体验，当前的安全策略偏底层、恢复决策不够直观。

3.1 应优先把“冲突检测”做成清晰的用户流程：显示本机/远端修改时间、版本标识和受影响项目；先自动留存两份快照，再提供“保留本机 / 保留远端 / 导出副本供人工合并”；任何无法安全自动合并的情况都不应静默覆盖。数据库级或章节级合并先调研，不建议未经验证直接承诺自动合并。

### D. 缺少轻量移动写作入口——建议先立项验证，后续分期

当前正式形态为 Windows 桌面安装版和需本机 Node.js 的便携版，适合主力电脑创作；竞品中的手机端主要覆盖灵感速记、阅读资料、短段落修改和跨端接续写。若现有用户确有移动创作需求，可先做手机浏览器适配的“伴随模式”：快速记灵感、查看资料、编辑正文、查看同步状态。完整的移动端设定管理、复杂图谱和地图编辑不进入第一期。

该方向依赖同步冲突流程与小屏交互评估，建议 3.1 先完成可行性原型和用户访谈，满足验证条件后再排开发。

### E. 系列级世界资料的版本演进能力还有提升空间——建议 P2

世界引擎已经支持将世界设定封装成世界包并用于其他项目，解决“复制一次”的问题。系列创作中还会出现源世界更新、子作品只接受部分变更、已经分叉的设定不应被覆盖等情况。可考虑为世界包增加版本号、变更摘要、差异对比和逐项导入，先不做跨项目实时双向同步。

### F. 发布与作品运营的连接较弱——列为观察项

项目已有投稿格式、平台粘贴版、读者反馈台账和市场雷达，但不直接发布到平台，也不自动获取阅读、收藏、追读和稿酬数据。平台 API、账号授权、内容合规要求和服务可用性都会增加维护与隐私成本。3.1 建议先补平台格式预检配置（标题、章节字数、空行、敏感词提醒、导出预览）并验证实际投稿痛点；自动发布和数据同步须在存在稳定官方接口且作者明确需要后再立项。

### G. AI 能力缺少可选的跨功能任务编排入口——建议先验证，不列入 3.1.0 核心

开源 Agent 项目把规划、正文生成、审稿、修订、状态结算串成可观察、可暂停和可恢复的任务；本项目已有这些单项能力，也有后台任务中心和运行记录，但目前主要由作者进入各专用页面逐项发起。若作者确实希望用自然语言启动跨模块工作，可在现有任务中心上做受控原型；重点是任务步骤、读写范围、成本、审批点和回退清楚，而非增加完全自动化权限。

## 六、3.1 建议版本范围

### 6.1 版本目标

作者能更快进入创作状态，在一个视图中把规划、正文和长篇状态联系起来；跨设备异常发生时，能看懂并安全处理；新作者能在不读完全部手册的情况下走完一条完整的小型创作流程。

### 6.2 3.1.0：创作工作流贯通（建议核心版本）

| 优先级 | 建议事项           | 主要交付                                                    | 验收口径                                           |
| --- | -------------- | ------------------------------------------------------- | ---------------------------------------------- |
| P0  | **场景规划板（MVP）** | 场景/章节卡按剧情线组织；展示标题、简纲、人物、地点、状态；支持筛选、拖拽和跳转正文；卡片可从现有章节细纲生成 | 不复制正文；调整顺序与现有章节关系有明确预览；单次操作可撤销或有快照；大纲/正文缺失状态可见 |
| P0  | **项目下一步面板**    | 汇总待写章节、未整理灵感、临近伏笔、待修订工单、最近检查异常；每项跳回原功能                  | 只读聚合现有数据；每条建议可忽略/稍后处理；不创建重复业务记录                |
| P0  | **新项目分步引导**    | 可关闭、可跳过的项目起步清单；空状态提供样例与入口；每步能打开对应功能                     | 新建空项目后可在不依赖 AI 的条件下完成“建书—建章—写正文—备份”；不覆盖现有项目和偏好 |
| P0  | **同步冲突处理界面**   | 冲突双方摘要、自动保护快照、明确的本机/远端保留与导出副本选项                         | 故障注入验证：任何冲突分支至少有一份可恢复完整数据；失败状态明确显示；不静默丢弃任一方    |
| P1  | **资料反向导航增强**   | 从角色/地点/术语条目查看正文提及和相关章节；从正文可跳回资料卡                        | 索引结果可定位到章节；别名与相似名称不自动合并；扫描结果允许人工确认             |

### 6.3 3.1.x：经过验证再扩展

| 优先级 | 候选事项                                | 前置条件                                         |
| --- | ----------------------------------- | -------------------------------------------- |
| P1  | 手机浏览器伴随模式：灵感速记、资料查看、轻量正文编辑          | 同步冲突 UI 完成；小屏可用性原型验证；明确离线与同步状态               |
| P1  | 跨功能 AI 工作流原型：把现有检查、工单和修订串成可暂停/确认的任务 | 先访谈目标作者；沿用任务中心与运行账本；明确每一步的数据范围、预算、审批、撤销与失败恢复 |
| P2  | 世界包版本、变更摘要、差异对比与选择性更新               | 明确源项目/引用项目的版本语义；已有数据迁移方案和回滚测试                |
| P2  | 网文平台发布预检配置                          | 作者访谈确认常用平台、规则变化维护方式与误报接受度                    |
| 观察  | 官方平台发布、阅读/稿酬数据同步、实时多人协作             | 官方 API 与授权条件稳定；隐私边界和服务成本可接受                  |

### 6.4 建议不纳入 3.1 核心范围


- 再做一套与现有数据并行的角色、伏笔、支线、待办或知识库。
- 用“自动写完整本书”作为产品主线；项目当前的“人主导、AI 辅助”定位仍有区分度。
- 未经用户确认的自动改稿、自动覆盖冲突、自动同步发布。
- 无稳定官方接口时抓取平台后台数据或自动登录发布。
- 以自动生成 AI 检测分数或掩盖 AI 参与过程作为功能方向；创作轨迹继续保持如实记录定位。

## 七、工程与数据设计原则

1. **沿用现有数据源**：规划板、下一步面板和引导读取当前章节、伏笔、灵感、工单、检查结果；新结构只存现有 schema 无法表达的场景属性。
2. **以渐进兼容为先**：字段增加必须有缺省值与迁移；旧项目打开后行为不变；任何批量结构改动提供预览与撤销。
3. **本地优先与 AI 可选**：基本规划、导航、同步、备份流程不要求接入模型；AI 只作为可选加速器。
4. **冲突先保护、再解决**：写入前保留来源快照；不能确认合并正确时，保留双份并交给作者选择。
5. **长篇性能列入验收**：沿用仓库既有大数据压测经验，对 300+ 章、百万字级项目检查搜索、章节树、规划板、全书预检和导出响应。
6. **沿用数据透明原则**：移动端或外部同步仍明确说明数据存储位置、发送对象和恢复路径，不新增默认上传稿件的服务。

## 八、建议的验收指标

| 目标      | 建议指标                                                 |
| ------- | ---------------------------------------------------- |
| 规划与正文衔接 | 从规划卡片进入目标章节不超过 2 次点击；在规划板能区分未有细纲、未开写、草稿、完稿等状态        |
| 工作流可发现性 | 首次打开的空项目中，使用者可按引导完成建章、写入正文和建立备份；步骤可跳过且可重新打开          |
| 冲突安全性   | 构造双端并发、断网、写入失败、重复恢复等场景；不出现静默覆盖；每次冲突都能恢复本机与远端版本       |
| 大项目性能   | 以 300+ 章、百万字级种子数据执行搜索、筛选、加载和导出；无明显卡死或数据串位，耗时记录纳入发版说明 |
| 数据兼容    | 至少覆盖当前稳定版样例库、含空数据的项目、旧字段项目、备份恢复及便携版项目迁移              |
| 移动端候选   | 先完成原型测试：灵感记录、资料查看、轻量改稿三类任务可在窄屏完成；若频繁回桌面才算需求未满足       |

## 九、风险与决策点

| 风险/决策           | 处理建议                                                |
| --------------- | --------------------------------------------------- |
| 场景卡是否会形成新的平行大纲  | MVP 只做现有章节细纲的视图层；新增场景实体前先验证作者是否确实需要“一章多场景”的独立正文结构   |
| 同步方案是否升级到记录级合并  | 3.1 先做好冲突可见与双副本恢复；待明确数据表依赖、删除墓碑、外置载荷和旧版本兼容后再定自动合并范围 |
| 移动端是否偏离桌面本地优先定位 | 先验证伴随模式，不承诺完整移动版；同步仍由用户可控的私有通道承载                    |
| 平台运营功能是否引入平台锁定  | 先做可编辑的导出预检规则，不默认连接平台账号；各平台规则变化要能单独更新和关闭             |
| 页签数继续增长         | 3.1 新功能优先进入现有正文、写作面板和数据坞；若需新入口，必须明确它替代或整合哪条旧路径      |

## 十、最终建议

青春幻想引擎当前的核心竞争力已经不是“有没有大纲、设定卡或 AI 续写”，而是把长篇管理做到足够细，同时保持本机数据自控。3.1 的机会在于把这些深功能变得更容易进入、更容易互相跳转，并让跨设备写作在异常时也能让作者放心。

建议立项顺序：

1. **场景规划板 MVP**：先把现有章节规划、剧情线和正文状态放到一起。
2. **项目下一步面板 + 新项目引导**：降低学习成本，让已有数据直接推动下一步创作。
3. **同步冲突处理与恢复**：把底层安全能力变成用户能理解、能操作的体验。
4. **资料反向导航增强**：缩短“正文提到某设定—查资料—回到原文”的路径。
5. **验证后再决定移动伴随模式、系列包差异更新和平台预检。**

这条路线能继续放大项目在长篇一致性与网文创作管理上的优势，同时减少多页签、多设备和多模块协作带来的操作成本。
