# 3.0 · 工程目录结构优化（含 §11.1 L5）—— 实施方案

> 归属：主人 2026-10-10 追加，**排在便携版轨道（WP-1~WP-4）之前**
> 前置：第 0~4 批功能开发**已全部完成**（W4-3 跑团互动收官 2026-10-10）
> 状态：**待主人拍板（见第五节 4 个决策点）**；本方案只固化范围与设计，**未动源码**

---

## 一、目标

把 `src/` 的分层从「顶层大平地」改成「按领域可查找」，并且**不改变任何运行时行为**：

1. **可查找**：找一个功能的代码，不用在 190 个 `.tsx` / 149 个 `.ts` 里靠文件名猜；
2. **可扩展**：新功能知道该往哪儿放（现在只能"继续往顶层堆"）；
3. **不越权**：本方案**不做**「顺手重构逻辑」「顺手改命名」——只搬位置、只改 import；
4. **带上 L5**：`TavernScript.tsx` 中/右栏拆分（§11.1 L5 遗留，W4-3e 已实测边界）。

## 二、🔴 硬约束（红线，违反即回滚）

| # | 约束 | 依据 |
|---|---|---|
| **C1** | **打包链路引用零改动** | 不许动 `electron/**`、`scripts/build-desktop.mjs`、`scripts/prune-electron-dist.cjs`、`build/**`、`package.json` 的 `main`/`scripts`、`electron-builder.yml`。`electron-builder.yml` 的 `files` 只含 `electron/**` `dist/**` `package.json` ⇒ **源码目录怎么搬都不影响安装包**（改这些才会变） |
| **C2** | **搬前先 grep 谁在引用** | 记忆红线：搬文件前先 grep 谁 `read()`/import 它 —— 扫描器（`structureGates` ③-b / `importCycles` / `audit-*`）按**路径前缀**判定，路径一变就可能**静默失明** |
| **C3** | **闸同步四件** | ① `importCycles` 的 `NO_UI_DIRS`（分层方向，按 `'src/lib/'`、`'src/data/'` 前缀判定）② `structureGates` 的 `TYPE_FILE_OK`（纯类型文件豁免）③ `SIZE_FROZEN`（大文件冻结账本，**键是路径**）④ `src/data/**` 禁运行时 import |
| **C4** | **`src/data/**` 只放数据** | `src/data/` 内**禁运行时 import**（只允许 `import type`）—— 搬东西**进** `data/` 前先确认它没有运行时依赖 |
| **C5** | **`lib`/`data` 不许 import `components`** | 既有分层方向；新目录不得破坏 |
| **C6** | **分批 + 每批全量验证** | 每批搬完跑 tsc 0 / eslint 0 / 全量单测（**197 入口**）＋ 真 Chromium 实机走一遍主链路；**分批提交**，出问题可精确定位并可回滚单批 |

## 四、设计

### 4.1 `components/` 分组（D1）

建议按**领域**分组（与 `lib/` 已有子目录同风格 —— 找东西靠「这是什么功能」而不是「它长得像什么」）：

```
components/
  editor/      正文编辑（NovelEditor / EditorModals / useNovelEditorModel / DraftBits …）
  tavern/      酒馆模式（TavernXxx / RunPanel / useTavernXxxModel …）
  bookbreak/   一键拆书
  world/       世界构建（CharacterSheet / GeoMap / worldSets 相关）
  outline/     大纲与章节
  settings/    设置面板（AIConfigPanel / ModelSettingsPanel / *Preferences …）
  dialogs/     通用弹窗（Modal / confirmDialog / *Dialog 通用件）
  common/      通用件（Button / Avatar / HelpPopover / SelectRow / SIZE 基线件 …）
  App 级       顶层保留 App.tsx / main.tsx
```
> ⚠️ 具体清单在开工时按**实际 import 图**定（不凭文件名猜），本节只定「按领域分」这条口径与目标形状。

### 4.2 `lib/` 补齐分组（D2）

顶层 149 个 `.ts` 同样按领域收进子目录（`ai*` / `sync*` / `storage*` / `editor*` / `outline*` / `settings*` …），与既有 10 个子目录**口径统一**。

### 4.3 L5（已定，随本任务做）

`TavernScript.tsx`（846 行）：左栏已拆（`TavernScriptTree`，W3-3）。
实测 `dep-cost`：**中栏 460-637**（178 行，props 面 **11**，低风险）／**右栏 638-845**（208 行，props 面 **24**，宽）。
⇒ 先拆中栏（低风险），右栏视中栏成效再定；拆后 846 → ~668 行。

### 4.4 路径别名（D4）

现在**全项目用相对路径**（`../lib/xxx`）。若引入 `@/` 别名（`@/lib/xxx`）：
- ✅ 好处：**以后搬目录不必改任何 import**（一次投入，长期省）；
- 🔴 代价（必须一起处理，否则**静默失明**）：
  ① `vite.config.ts` 的 `resolve.alias` ＋ `tsconfig.json` 的 `paths`（两处必须一致）；
  ② **`importCycles` 的分层判定按 `'src/lib/'` 前缀** ⇒ 别名后要同步改判据；
  ③ `structureGates` 里按路径的账本（`SIZE_FROZEN` / `TYPE_FILE_OK`）与 `AI_CHAIN` 正则；
  ④ 一次全仓 import 改写（475 文件），本身是一次高风险批量操作。

## 五、🔴 待主人拍板的 4 个决策点

| # | 问题 | 选项 | 可可推荐与理由 |
|---|---|---|---|
| **D1** | `components/` 怎么分组 | A 按**领域**（editor/tavern/outline/…）／B 按**形态**（panels/dialogs/widgets/hooks）／C 只把 hooks 摘出去 | **A** —— 与 `lib/` 既有子目录口径一致；按形态分会导致「一个功能散在 4 个目录」 |
| **D2** | `lib/` 顶层要不要一起收 | A 一起收（口径统一）／B 本轮只动 `components/`／C 都不动 | **A** —— 只收一半会让「该去哪找」更乱；但**分步做**（先最明确的簇） |
| **D3** | 是否顺带拆大文件 | A **只搬目录、不拆文件**（＋ 只做 L5）／B 顺带拆 top-5 大文件／C 只做 L5 | **A** —— 搬目录是**零行为变化**的重构（可一刀切验证）；拆文件是**有行为风险**的，混在一起出了事难定位。大文件另开一轮 |
| **D4** | 是否引入 `@/` 路径别名 | A 引入（以后搬迁零改 import）／B 不引（保持相对路径） | **A** —— 本轮正是「一次性把 475 文件的 import 都动一遍」的最佳时机；但**必须**同步改 4 处闸（4.4 的 ②③），否则扫描器静默失明 |

| **G1** | 搬 `components/` 第一批（领域最清晰的：`tavern/` ＋ `dialogs/` ＋ `common/`） | 同上 ＋ 实机主链路 |

## 七、风险与边界

- 🔴 **最大风险＝扫描器静默失明**（C2/C3）：判据按路径前缀写死，搬迁后若不同步，**闸会"全绿但什么都没查"**。每批搬完**必须跑一次 `audit-arch` / `directoryOwnership` 类自检并人工核对命中数**（不能只看 PASS/FAIL）。
- 🔴 **不做**：不顺手改逻辑、不改命名、不合并文件、不动 `src/data/**` 内容、不动打包链路。
- 🔴 **可回滚**：每批独立提交，出问题 `git revert` 单批即可（禁用 `git stash`／手工 `gc` —— 项目红线）。
- ⚠️ `dist/` 与 `release/` 是产物，**不进本任务范围**；改完要让**预览**可见，须重跑 `vite build`（W4-3e 的教训）。
