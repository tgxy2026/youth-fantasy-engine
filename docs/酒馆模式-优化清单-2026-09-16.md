## 二、逐条明细

### #1　自由对话上方不再显示角色状态；原角色状态迁入右栏统一面板
- **现状 / 问题**：此前约定自由对话聊天窗口上方不再显示角色状态，但实机仍在显示，未去掉。
- **新约定**：
  1. 顶部聊天窗口上方**确认去掉**角色状态展示。
  2. 角色状态**不删除**，改为与「本场状态」合并进右栏同一个可切换面板（具体见 #2）。
- **关联**：与 #2 耦合，应一并设计与实现右栏统一面板。

### #2　右栏统一为「角色状态 / 本场状态」双标签页面板
- **现状 / 问题**：① 原 #2 反馈——控制面板勾选启用「本场数值」后，聊天窗口右侧未把数值渲染出来；② 角色状态散在顶部。
- **新约定**：右栏合并为一个面板，提供页面切换两个标签页：
  - **Tab A —— 角色状态**：点击显示 人物关系、关键事实、未爆的雷、纪念、待办 这些统计信息（即原上方/某处展示的那套记忆与关系统计）。
  - **Tab B —— 本场状态**：点击显示当前对话下的人物状态，即那 **5 个数值**（好感 / 信任 / 精神 / 心情 / 地点；字段定义见 #3，刷新机制见 #4）。
- **顺带解决**：原「右侧不显示」问题——本场状态直接落在这个统一面板的「本场状态」标签页内，不再依赖控制面板开关另开独立右栏。
- **关联红线**：本场数值唯一入口仍指向 `TavernVarsPanel.tsx`（右栏「本场状态」）；中间 `TavernStatusBar` 只保留场景 + 角色状态（只读），不再叠加数值。

### #3　控制面板「本场数值」5 项字段调整（含数值分区定义）
- **五项构成（全两字）**：**好感 / 信任 / 精神 / 心情 / 地点**
  - 好感、信任、精神 → **数值型**，范围 **−100 ~ +100**，默认 **0**。
  - 心情、地点 → **文字型**，自由表述，不填具体数值（修正早先误将心情当数值的记录）。
- **字段改名**：
  - 第 3 项「剧情进度」→ 改名为「**精神数值**」。
  - 「当前地点」→ 改名为「**地点**」（使 5 项均为两字）。
  - 推断当前 5 项顺序约为：好感 / 信任 / 剧情进度→精神 / 心情 / 当前地点→地点（**待老大确认实际顺序**）。
- **语义锚点（数值型三项）**：
  - **好感**：−100 对说话对象极度厌恶；+100 极强亲密与依赖——同性→好兄弟，异性→恋人/情侣/夫妻。
  - **精神**：>0 精神正常、理性；<0 精神状态混乱、出现与角色卡设定不一致的言行，数值越低越严重。
  - **信任**：范围 −100~+100、默认 0（**老大未给具体锚点，出文档时标「待补」**）。
- **➕ 设计补充（落地方案必做）：数值分区定义**
  - 老大认为 −100~+100 跨度偏大，未来实际落地时应**把三项数值划分区块并给出明确定义**（如厌恶区 / 冷淡区 / 中立区 / 亲近区 / 依赖区等分段，以及每段对应的行为指引）。
  - 目的：让 AI 能更合理地判断「当前数值落在哪个区间 → 该表现出什么行为」，而非对着连续大区间自己瞎猜。

### #4　本场状态刷新机制改为「每次回复都刷新」
- **现状 / 问题**：当前设计是 vars（好感/心情）**只在收尾（结束本轮对话）刷新**。
- **新约定**：人物五项状态应在**每次回复后**刷新，并随对话交流过程产生**起伏变化**。
- **⚠️ 规则变更**：这**推翻**了此前「vars 只在收尾刷新」的设计决策（见 `MEMORY.md` 酒馆模式§）。出文档 / 落地时须按新约定实现，并清理旧的「仅收尾刷新」相关逻辑与说明。
- **关联**：与 #2 的「本场状态」标签页、#3 的 5 项字段配套。

### #5　用量明细弹窗：固定注入部分按四类拆项显示额度
- **背景**：当前弹窗把固定占用笼统归为「角色卡」和「其他固定部分」两类，粒度太粗。
- **需确认 / 固定的注入信息（老大列的三类）**：
  1. **参与对话的角色卡**
  2. **角色扮演协议**（规定的那套）
  3. **故事模式设置** —— 含故事的世界设定；若选定了具体**剧本**，还要导入该剧本的相关设定。
- **核心诉求**：把弹窗里的固定占用**拆细**，明确区分以下四类各自占了多少字数 / 额度预算：
  - **角色卡**
  - **故事**（世界设定）
  - **剧本**（若选中）
  - **协议**
- **目的**：让用户能根据实际使用体验，针对性删减 / 调整某一类内容（如角色卡写太肥、或剧本设定太长），而非只能看到一个糊在一起的「其他固定部分」。
- **关联红线**：上下文预算 `historyBudget`＝预算−400−整条 system（别传记忆）；`contextBudget` 24000（三处一致）。拆项显示时各分类额度之和应与总量对账。

### #6　「想指挥他」指令示例：复制按钮移到最左、示例文字跟其后
- **作用范围**：**剧情推演** 与 **自由对话** 两个模式顶部，都有的「想指挥他」指令示例区。
- **现状 / 问题**：每行里指令示例的**说明在左侧**，而**复制按钮在窗口最右侧**——实际要点复制得挪到最右边，不顺手。
- **新约定**：把**复制按钮移到该窗口最左侧**，按钮后边紧接着是对应的使用示例文字。
  - 顺序由「说明（左）…… 复制按钮（最右）」改为「**复制按钮（最左）→ 示例文字**」。

### #7（协议级 · 扩写）　对话内描写改为第三人称
- **改动内容**：
  - AI 输出仍分两类：①对白（角色直接说的话 / 消息）；②描写（环境、动作、心理）。
  - 第②类「描写」由**第一人称**改为**第三人称**；文中「我」「你」一律替换为对应人物的**名字或人称代词**。
- **为什么不是简单提示词微调**：描写格式写在「角色扮演协议 / 输出规范」里（当前协议 v1.8），改它等于改协议，不止某段 prompt 文案。提示词（怎么要求写）与**解析器（怎么读回这些描写）必须一起动**，否则会出现「要求第三人称输出、但解析仍按第一人称锚点切」的错位。
- **必须同步处理的事项（按工程红线）**：
  1. 角色扮演协议正文：描写格式条款改写（第一人称→第三人称、我/你→人名/代词）。
  2. 协议版本号 bump：v1.8 → 下一版（如 v1.9），并同步四处——正文版号、`LEGACY_PROTOCOLS`、旧全文追加、`PROTOCOL_VERSION`、两处版本断言（⚠️ 断言已要求改「与正文标题一致」，别再写死版本号）。
  3. 提示词模板 / few-shot 示例：凡是拿描写当例子的地方，示例本身也要改成第三人称写法，避免 AI 照旧样例学回第一人称。
  4. 解析器对齐：标题整行匹配、描写块切分规则需随格式变更复核（禁 `includes`、按整行匹配原则不变）。
- **待评估的连带影响**：
  - 防剧透两层（段落级 `viewMode:"character-view"` + 字段级 `AUTHOR_SIDE_FIELDS`）：第三人称描写若仍承载作者侧信息，字段登记口径是否需调整。
  - 两条模式（剧情推演 / 自由对话）是否共用同一套描写规范，还是分模式有差异——落地方案里点明。

### #8　自由对话日记：只写 AI 角色视角 + 改正常分段
- **背景**：多轮对话 →「结束本次对话」→ AI 总结。日记仍有问题。
- **决策 1 —— 日记只写 AI 扮演角色视角，砍掉用户角色日记**：
  - 现状问题：日记从 AI 扮演角色视角写，但此前还试图兼顾「用户扮演角色的视角」，而这一块 AI 写不好。
  - 新约定：日记**只生成 AI 扮演角色的那部分**（第一人称回顾），**不再生成用户扮演角色的日记**（直接妥协掉用户侧日记）。
- **决策 2 —— 日记文本格式改为正常分段**：
  - 现状问题：当前生成的日记**每个句子单独成段**，不像正常写日记。
  - 新约定：改成正常文本格式，**合理地分段**（按内容层次断段，而非一句一段）。
- **明确不动的两块（老大点名）**：
  - **系统提示 / 设定更新部分**：总结准确、没搞错人物关系 → 不改。
  - **记忆**：已实现且现今产出较精简 → 不改。
- **落实时需留意**：`tests/tavernRoundEnd.test.ts` 钉着日记形态 6 条断言（第一人称 / 写经过＋写感受 / 不进记忆不进提示词 / 只读可删）。「第一人称」断言保留；**若其中有「每句一段」之类格式断言，落地时需同步放宽**，否则会挂。日记 `JOURNAL_HEAD='〖本场日记〗'`、200–600 字、第一人称等仍有效。

### #9　角色卡片管理页：在「上传图片」右侧加一份 复制新卡 / 删除 / 保存 按钮
- **位置**：角色卡片管理页面（左列选人后进入的编辑区）。
- **现状 / 问题**：选人后编辑区底部才有「复制新卡 / 删除 / 保存」三枚按钮，得**拉到最底下**才点得到，不顺手。
- **新约定**：
  - 把这三枚按钮（**复制新卡、删除、保存**）**复制一份相同的功能按钮**，放到「**上传图片**」按钮的**右侧**（编辑区头部 / 工具栏区域）。
  - 目的：用户不滚动到底也能快速操作。
  - **一致性要求**：复制调整后的 UI 按钮**保持与现有按钮风格、间距、交互一致协调**（同一套样式 / 尺寸 / 危险操作语气，删除仍走危险样式等）。
- **待确认**：原底部三枚按钮是否保留（「复制一份」语义上应是顶部新增、底部原有仍在）。默认**底部保留、顶部新增**，除非老大另说。

### #10　AI 起草角色卡片：内容偏单薄，需优化提示词使其更丰富
- **背景对比**：
  - **AI 起草世界设定**：试下来还算完整 → **不改**。
  - **AI 起草角色卡片**：内容单薄、不够丰富 → **需优化**。
- **改动方向**：
  - 优化「AI 起草角色卡片」的**提示词**，提升生成的人物形象丰满度。
  - **重点场景**：以某个**现实中存在的人物**，或**游戏 / 小说等艺术作品中存在的人物**为**原型**创建卡片时。
  - **信息不足时的处理**：在已搜集到的原有内容基础上，做**一定程度的扩散和发挥**，把角色卡人物形象写得更饱满。
- **老大兜底态度（写进落地方案）**：**不必过度担心「与原型不符」或「出戏」**——生成后用户本就可再手动修改，所以扩散发挥可以放开一点。
- **落实提示**：这条是**提示词层**改动（角色卡起草 prompt），与世界设定起草 prompt 相互独立，改的时候别把那边也顺手动歪了。

### #11　「结束本轮对话」收尾后主动卸载模型缓存（新增设置项）
- **现状 / 问题**：即使删除了上次对话产生的**记忆和日记**，只要**模型未被卸载**，模型侧仍保留上一轮对话的上下文（它"自己记得"），导致下次扮演时人物行为与新状态不一致、出现不符合预期的言行。
- **新约定 —— 新增一个设置项（开关）**：
  - 触发点：用户点击「结束本轮对话」→ AI 依次执行完 **①人物日记总结 ②人物记忆总结 ③人物设定总结** 这一整套收尾流程**之后** → **主动发出指令，将缓存中的模型卸载掉**。
  - 目的：保证**下次对话时模型重新加载我们重新注入的信息**（已清理过的记忆/日记/本场状态），避免历史上下文污染新会话。
  - 形态：作为一项**可由用户开关的设置**提供（默认开 / 关待定），而非强制行为。
- **关联红线 / 待调研**：
  - 模型加载 / 卸载由推理层（本地 Ollama / Open WebUI / 千问3.8 27B uncensored）控制，需确认客户端 / Electron 侧能否**主动触发模型 unload**（例如 Ollama 的 `keep_alive=0` 让其在请求后即刻释放，或 `ollama stop <model>`）。
  - 卸载后下次对话会有**冷启动加载延迟**，UI 上需给出相应提示或让用户自行权衡（尤其长上下文模型加载耗时明显）。
  - 该设置应与「本场状态 / 记忆 / 日记」等收尾逻辑在 `roundEnd.ts` 同一链路里收口，避免多处散落触发。
- **关联**：与 #8（结束本轮对话 → 日记 / 记忆 / 设定总结）共用同一收尾入口，本条是在该入口**之后**追加的缓存清理动作。

### #12　对话动作描写高度重复（如「指节因过度用力而泛白」高频）—— 根因已诊断 ✅
- **现状 / 问题**：扮演楚楠与苏念对话时，模型的**动作 / 肢体描写高度重复**，典型高频片段「指节因为过度用力而泛白」出现频率极高，观感机械化、出戏。
- **需定位根因（原假设：二选一 / 叠加）—— ✅ 2026-09-16 已核实，两个假设均被推翻或降级**：
  - 假设①「参数偏低」→ **部分成立但性质不同**：缺陷不在**强度**（1.05 正在手册推荐段内），而在**射程** —— 三种 penalty 共用 `penalty_last_n` 窗口，Ollama 默认 **64 token**，跨轮复读**在窗口外，调多高都碰不到**；且 `frequency_penalty` **从未下发**（默认 0）。

### #13　发送后输入框焦点保持（沉浸聊天体验）
- **现状 / 问题**：在剧情推演 / 自由对话，把鼠标放在文本编辑框、点「发送」（或输入后按回车发送）后，光标 / 焦点会**自动移出输入框**；想继续输入必须再把光标移回框内，沉浸聊天时每轮都要多点一次，很别扭。
- **新约定**：
  - 在输入框内输入文字、**按回车发送**后，光标（焦点）应**保持在已清空的文本框内**，可直接接着输入下一句。
  - 只有当用户**主动把鼠标点到别处**时，才失去焦点。
  - 作用范围：**剧情推演** 与 **自由对话** 两个模式的输入区。
- **关联红线 / 落地提示**：
  - 与既有输入红线协同：Enter 发送 / Shift+Enter 换行，**必须挡 `isComposing`**（输入法候选中不可触发发送）；本 #13 是在该基础上新增「发送后保持焦点」。
  - 常见成因：发送后组件重渲染 / 主动 `blur()` / 焦点被消息列表或滚动逻辑抢走。落地时确保在清空内容后**将焦点重新 `focus()` 回该 textarea**，并避免副作用把它挤走。
  - 与 #2 / #6 / #9 同属 UI 体验类改动，但本条目特指**焦点行为**而非布局，单独验证即可。
