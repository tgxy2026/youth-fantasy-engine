## 二、P0-1 评论分页与数量

### 2.1 修前复现（隔离真实服务）

脚本：`.workbuddy/tmp/352-repro/repro-comments.mjs`；证据：`.workbuddy/tmp/352-repro/repro-result.json`。

用真实 `server/index.mjs`、临时 `YFE_DATA`、合成账号与正文，生成 21 条公开评论：

- `GET /api/community/posts/:id/comments` 第一页 20 条、第二页 1 条，**响应没有 `total` 字段**；

- 结果：21 条评论时界面只能得到 20 条，显示的总数也是 20。复现记录 `R2` 未通过。

### 2.2 修改

**服务端**（`server/lib/communityApi.mjs`）：

- 评论列表按公开可见评论（`status === visible`）计算 `total` 并返回；待审、被拒、已删除不计入。
- 返回前发现 `post.counts.comments` 与权威数不一致时**自愈写回**（只在真的不一致时写），列表卡片与详情随后一致。
- 排序仍为 `(createdAt desc, id desc)`，游标条件与排序严格一致，保证同时间戳稳定。

**前端**（`src/components/community/FeedPanel.tsx`）：

- 增加评论游标、`commentTotal`、加载中/失败/到底状态；「加载更多评论」「刷新评论」「重新读取评论 / 重试加载更多」。
- 标题与详情顶部评论数都使用服务端 `total`；旧服务端无 `total` 时只按已加载数量给出下限，不冒充权威总数。
- 每次打开/关闭/切换帖子递增会话序号；详情与评论的所有异步回执都校验「当前帖子 + 会话序号」，迟到响应直接丢弃。
- 详情读取失败区分 404（不可见）与网络/服务失败（保留页面并提供「重新读取」），不再把网络失败误报为投稿不存在。

## 三、P0-2 评论提交与网络重试

### 3.1 修前复现

同一脚本与证据：

- 同一条正文、第一次 `clientToken=repro-retry-A`，重试 `clientToken=repro-retry-B`（旧前端每次点击生成新令牌）→ **产生两条评论**（`R3`）。
- 同一令牌、不同正文 → 返回 200 `duplicate` 和旧评论，不报冲突（`R4`），用户会误以为新内容已发出。
- 先把该账号当日评论配额打满，再用已确认令牌重试 → **429**（`R5`）：限流发生在去重之前，合法重试被误判。

### 3.2 修改

**服务端**（评论 POST）：

1. 先解析并校验正文（长度/空内容），再校验令牌；
2. 令牌查询已先验证登录、帖子存在且公开可见，并按 `uid + postId + token` 归属；
3. 同令牌且正文/展示方式一致 → 200 `duplicate`，返回完整公共评论与权威 `total`；
4. 同令牌但内容/展示方式不同 → **409 `TOKEN_CONFLICT`**，不回传旧评论正文；
5. 限流与每日上限移到去重之后：已确认的重试不消耗配额、不会被 429 误判；新内容仍受限；
6. 令牌截断到 64 字符（与投稿一致）；写入后返回公共评论视图（不含 uid/登录名）与 `total`。

**前端**（`src/lib/community/pendingComment.ts` + `FeedPanel`）：

- 令牌绑定「帖子 + 正文 + 展示方式」这一份意图；同一意图重试复用令牌，改正文/换帖子/换展示方式即新令牌。
- 结果分类：`NO_ENDPOINT` 与 4xx（含 409/429/503）为确定失败；网络异常、超时、5xx 为**结果未确认**，保留令牌并提示「可直接再点一次重试，不会重复发表」。
- 提交期间用户继续输入的新内容保留，只清空与本次提交一致的内容；切换帖子后的迟到回执不应用。
- 令牌只在当前页面会话内存中有效；**刷新页面或换设备后不保证去重**，界面文案没有承诺这一点。

### 3.3 修后验证

- `tests/communityCommentPending.test.ts`：**16/16**（令牌复用/上下文隔离/有界 50 条/失败分类）。
- `tests/communityComments.test.ts`：
  - 同令牌同内容重试同 id、total 不重复增加；
  - 同令牌不同内容 409，响应不含旧评论正文，不写入新评论；
  - 同令牌换帖子/换账号是独立评论（作用域正确）；
  - 配额用尽后同令牌重试仍 200 duplicate，新内容仍 429。
- 浏览器「写入成功但响应丢失」：
  - 代理把第一次 POST 转发到真实服务（实际写入）后中断响应；
  - 前端提示「评论结果未确认」，输入保留，服务端 total 已 +1；
  - 再点「发表评论」复用同一令牌，服务端 total 仍为 23，页面上同内容只有 1 条。

## 四、P0-3 备份、恢复与一致性

### 4.1 现状盘点（只读）

- `server/deploy.sh` 只在部署 www/server 前把旧目录 `mv` 到 `/opt/yfe/backups/<target>.bak.<ts>`，保留 3 份；**这是部署回滚备份，不包含 `<DATA_DIR>/community`**。
- `server/yfe-web.service` 只有 `Restart=always`；`server/scripts/healthcheck.sh` 只检查接口与重启；未发现社区数据备份、保留期、异地副本或备份失败告警。
- 规划记录的只读检查（2026-11-12 约 08:16）显示 `/opt/yfe/backups` 最近完整归档为 11 月 10 日且未发现 community 目录、root 定时任务与 systemd timer 无明确社区备份任务。该结论受检查范围限制，**不能据此断言完全没有其他路径/账号/云端备份**。
- 存储形态：8 个 JSON 文件，单文件临时文件 + rename；没有跨文件事务，也没有 fsync。**不能把单文件原子替换等同于跨文件一致性或断电不丢数据**。

### 4.2 新增工具

- `server/lib/communityBackup.mjs`：校验、备份、恢复、可见性差异。
- `server/community-backup.mjs` CLI：
  - `inspect`：只读检查结构、关联、计数漂移；
  - `backup --data <dir> --out <dir>`：一致性快照；
  - `verify <backupDir>`：清单/哈希/结构/关联/计数；
  - `restore <backupDir> --data <dir> --confirm-stopped [--accept-visibility-changes]`。
- 备份格式：8 个数据文件 + `manifest.json`（格式版本、时间、来源目录名、每文件字节/哈希、记录数、警告、计数重算记录）。**清单不含正文、账号 id、登录名或凭据**。
- 默认保留期由 `--keep` 控制（默认 14），只清理同父目录下 `community-*` 旧备份，不自动删除用户内容。
- 恢复必须在停写后执行；先校验备份、复制当前数据到 `<root>.pre-restore-<ts>`、写恢复暂存目录、再目录切换。恢复失败回滚；成功保留 pre-restore 供核对。

### 4.3 可见性保护

恢复旧快照可能把「备份时公开、现在已下架/删除」的内容重新公开。工具在切换前生成差异：

- `would-republish`：备份可见、当前不可见；
- `would-hide`：备份不可见、当前可见；
- `restored-absent`：备份有、当前不存在（可能是已删除）。

存在差异且未加 `--accept-visibility-changes` 时**拒绝恢复**（退出码 2），只输出不透明 postId 与状态；操作者核对后才能继续。该设计不新增墓碑文件，因此对「物理删除后恢复」只能依赖差异清单人工确认，不能自动推断删除意图。

### 4.4 隔离演练

脚本：`.workbuddy/tmp/352-repro/backup-drill.mjs`；证据：`drill-result.json`（**26/26**）。

真实隔离服务生成：2 篇合成投稿（公开 + 已下架）、1 条公开评论 + 1 条待审、1 票、1 举报 + 1 申诉、昵称/匿名档案、排行、审计；停服务后用 CLI 备份并校验：

- 备份包含 3 篇（含服务启动时幂等创建的内置示例）、2 条评论、举报/申诉、档案、排行、审计；
- 清单不含正文；
- 备份 **119ms**、恢复 **134ms**（合成小数据；S3 见容量文档）；
- 篡改当前数据（公开稿下架 + 新增评论）后，未接受可见性变化 → 拒绝恢复，live 保持下架；
- 显式接受后恢复：公开稿回到快照时点、下架稿仍不可见、待审评论仍不可见、新增评论不在快照；恢复前副本保留「下架 + 新增评论」证据；
- 重启服务后 HTTP 核对：举报、申诉、排行仍在；匿名展示仍为「匿名用户」；评论 total 与公开评论一致。

### 4.5 故障点（单元 + 演练）

- 备份写失败（模拟 ENOSPC）→ 失败、无正式备份目录、临时目录清理、live 不变；
- 备份中途抛错（模拟进程中断）→ 同上；
- 备份篡改正文/缺文件/结构损坏 → `verify` 拒绝；
- 备份内计数漂移 → 备份时在副本中重算（`repairs`），live 不改；备份校验要求计数一致，漂移备份拒绝恢复；
- 恢复切换中断 → 回滚 live、保留 pre-restore、不残留 `.restore-`；
- 损坏备份恢复 → 拒绝，live 不变；
- 未确认停写 → 拒绝。

**限制**：目录 rename 的跨进程/断电原子性依赖文件系统；本次在 Windows 本地 NTFS 验证，未做真实断电、跨分区或网络文件系统测试。

## 五、存储层补充修复

1. **写失败缓存污染**（规划补充风险）：`mutate()` 先修改缓存对象再写盘；写失败后继续命中缓存会读到从未落盘的「幽灵数据」。现在写失败或 `fn` 抛错时删除对应缓存，下次从磁盘读回旧内容。故障注入：ENOSPC 后 `getPost` 读回磁盘旧状态。
2. **核心文件意外丢失**：`posts.json` 丢失但目录还有其他社区文件，或帖子计数显示有评论但 `comments.json` 丢失 → 启动拒绝，要求从备份恢复，避免用空表写回。真正空目录仍可首次使用。
3. **计数漂移**：备份校验以评论/投票表为权威重算副本；运行时评论列表在不一致时自愈写回 `post.counts.comments`。
