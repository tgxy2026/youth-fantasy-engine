## 🔍 人工复核（2026-08-30 07:50 · 老巴迪）
> 自动化只能读日志，以下是追到**文件系统与代码**层面的结论。

### 🔴 P0：云端推送「假成功」—— 老大 8/29 全天编辑从未落盘

**现象**：老大（182.200.137.126）19:48–22:21 共 21 次 push，日志**全部显示成功**（rev 6），但槽位文件 `rev` 恒为 **5**、mtime 停在 **08-29 10:39** 纹丝不动。

**根因链**（每一环都缺一不可）：
1. 槽位文件属主为 **`root:root`**（历史上用 sudo 复制产生），服务进程是 **`www-data`**，权限 644 → **无写权限**；
2. `writeFile(...).catch(() => {})` 把 `EACCES` **静默吞掉**，仍然返回 `{"ok":true,"rev":6}` 并记录 push 成功；
3. 客户端信以为真，本地 rev 涨到 6，而服务端 rev 恒为 5；
4. 之后每次 push 带 `baseRev=6` ≠ 服务端 `5` → 永远 409 → 旧客户端用云端 rev5 覆盖本地 → **数据"被刷新掉"**（与老大报障完全吻合）。

**已修复并上线**：
- 止血：`chown www-data:www-data` 老大槽位（实测 `WRITABLE_BY_WWWDATA=YES`）。
- 治本（`server/feedback-server.mjs`，已重启生效）：
  1. 写盘失败**不再静默吞**，改返回 500 + 记录 `pushfail` 事件；
  2. 新增**按槽位串行写锁** `withSlotLock`，杜绝并发 POST 交错 `read→write` 互相覆盖；
  3. 临时文件 + `rename` **原子落盘**，避免半截快照；
  4. 启动自检 `write-probe`，目录不可写时直接 FATAL 报错（正是这次的坑）；
  5. `authfail` 补记失败码短哈希（`bad` 字段，不可逆），便于诊断用户到底输错了什么。

**线上实测**（用未分发空闲码，测后已清理槽位）：写入真实落盘 ✅｜并发 push 恰好一个 200 + 一个 409（**修复前会是两个 200 互相覆盖、rev 不递增**）✅｜错 rev 正确 409 ✅｜无效码 401 ✅。启动日志已打印 `write-probe OK: /var/lib/yfe 可写`。
