## 二、联网调研：行业最佳实践 vs 本项目

调研对象：NovelAI / Sudowrite / NovelCrafter / SillyTavern 生态、结构化输出工程化、
本地 LLM 采样参数、中文网文 AI 实践。

| 维度 | 行业最佳实践 | novel-studio 现状 | 判定 |
|---|---|---|---|
| 结构化任务温度 | 0 ~ 0.2 | 0.3（`json:true` 时） | ✅ |
| 创意写作温度 | 0.8 ~ 1.0 | 0.85 | ✅ |
| `repeat_penalty` | **≤ 1.2**（超了用词生硬 / 中英混杂） | 保持默认、红线禁调高 | ✅ 完全吻合 |
| `repeat_last_n` | 长篇 512 | 512 | ✅ |
| `frequency_penalty` / `presence_penalty` | 0.1~0.5 / 0.2~0.4 | 0.1 / 0.2 | ✅（保守） |
| 内容 ↔ 指令分离 | XML 标签最可靠 | **随机 nonce 围栏**（`promptGuard.authorBlock`） | ✅ 比 XML 更抗注入 |
| 上下文注入 | 按需注入 + 预算控制 + 硬约束放末尾 | PRIORITY 累加 + ROW_CAP + 预算 + 末尾硬约束 | ✅ |
| 结构化可靠性 | 解析 → 校验 → 重试兜底 | `aiParse.ts` 单一收口 | ✅ |
| **markdown 污染** | **双保险：提示词禁用 ＋ 代码剥离** | 仅改写 / 校对链有代码剥离；13 条提示词仍带 `**` | ⚠️ **唯一缺口** |

> 行业原话（多来源一致）：**「LLMs do not consistently follow formatting instructions.
> For any production system, code-based stripping after the API response is more reliable
> than relying on prompt instructions alone.」** —— 光靠提示词不够，必须代码兜底。

**结论**：novel-studio 的 AI 架构整体处于行业第一梯队（温度真源、内容/指令分离、
分层预算、结构化收口、去 AI 味、采样惩罚射程，均吻合或超越行业最佳实践）。
真正要补的只有「markdown 污染」这一条双保险。

## 三、验尸确证的缺陷与改进（4 项，已全部落实）

| 编号 | 位置 | 问题 | 依据 | 处置 |
|---|---|---|---|---|
| **G4** | `src/lib/ai.ts` `aiCompleteTemplate` | 走 `parseTemplateJSON` 做 JSON 解析，却**没传 `json:true`** ⇒ 静默跑在 **0.85 创意温度** | 行业共识：结构化须≈0；项目注释记载同类问题历史已犯过一次 | ✅ 补 `json: true` |
| **G3** | 21 个文件 × **95 行**（已登记 33 条提示词的 `**` 96 处 → **0 处**） | 星号全是**叙述性强调**，但对模型是**格式示范**，会诱导正文 / 表格 / JSON 里也带 `**` | `proofread.ts` 文件头已写明此纪律且**实测 0 处星号**（项目内成功先例） | ✅ 全部改「」（嵌套用「『』」） |
| **G2** | `paceAnalysis.locateQuote` / `proofread` / `bookbreak.aiSplit` | 定位函数**不剥 markdown** ⇒ 引文带 `**` 即定位失败、条目**静默丢弃** | 行业：代码剥离比提示词可靠 | ✅ 抽 `mdLite.stripEmphasis` + 三处「先剥后比」兜底 |
| **G5** | `aiContext.findRelatedChapters` | 用 `flattenChapters` **不含孤儿章**，而 `buildChapterDigest` / `idsUpToAnchor` 都含 ⇒ 焦点章若是孤儿则**召回整体失效** | 项目内部口径不一致 | ✅ 并入孤儿章，三处口径对齐 |

### G3 的执行边界（重要，防误伤）

**规则**：**「导出 Markdown」保留星号，「提示词 / 纯文本渲染 / HTML 导出」一律去星号。**

| 处置 | 对象 | 理由 |
|---|---|---|
| ✅ 改 | 21 个文件（`aiTasks/*`、`interview`、`wordRange`、`deAiStyle`、`draftMaterial`、`webSearch`、`aiWorkflow`、`evidencePack`、`bookbreak/*`） | 喂给模型 / 纯文本渲染（`{m.why}`）/ 导出 HTML |
| ⛔ 保留 | `exporter.ts`、`tableIO.ts` | **导出 `.md` 文件**，`**` 是目的（有测试断言 `**必填**`） |
| ⛔ 保留 | `tavern/**` | 独立体系；输出已有净化器（`protocol.ts:85` 的 `/\*\*(.+?)\*\*/g`）；版本锁定 |
| ⛔ 不动 | `manuscriptCheck.ts` 的 `(n-mean)**2` | **JS 幂运算符**，不是 markdown |

**嵌套引号**：内容已含「」时外层改用『』（如 `『尺度由「动作」确定…』`），避免 `「…「…」…」`。

**同步改测试**：`tests/chapterRewrite.test.ts:166/172` 直接断言了带星号的提示词原文，已同步更新为「」。

## 五、已排除（不做）与观察项

| 项 | 判定 | 理由 |
|---|---|---|
| **G1** `asText` 全局剥 markdown | ❌ 不做 | `asText` 用于 113 处取值**含正文类字符串**，全局剥会误伤；风险 > 收益 |
| **G6** `ollamaChatRaw` thinking 兜底 | ❌ 撤回 | 复核后确认是**刻意设计**（伴写用 `think:false` 规避），非缺陷 |
| `min_p` 采样 | 🔶 观察 | provider 支持不一，项目已用 `top_p` + 惩罚组合；收益不明 |
| `hasSubstance` 语义校验覆盖面 | 🔶 观察 | 行业建议「结构化保 shape 不保内容」需语义校验；现仅 `aiRewritePassage` 一处调用 |
