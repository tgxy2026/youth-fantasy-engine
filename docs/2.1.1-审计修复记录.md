## 四、🔴 待商量（严重，未动）

> 这几条都在**存储 / 同步层**，属数据安全类，按老大的规矩「严重的先商量」。均已回源码验尸确认因果链成立。

### P0 · 更换同步目录到空目录会写入一份空快照

- 链路：`CloudFileSyncBar.pickDir` → `enableDesktopCloudSync(handle)` → `enableDesktopCloud()` 里 `cloud.configure()` **把单例 cache 清空** → 拉新目录快照（空）→ `empty` 分支调 `seedDesktopFromLocal((s) => ops.getAll(s))`。
- 此时若同步**本来就开着**，`ops` 仍是同一个 `desktopCloudFileStore`（cache 刚被清空）→ 读回来全是空数组 → 写成 rev=1 落到新目录；空推守卫比较的 `baseCache` 也被 `configure()` 清零 → **不拦**。
- 后果：界面看起来「书全没了」，app 判定空库还会播种示范项目到云目录，另一台设备可能拉到这份空快照。旧目录的 `.yfe` 仍在（可人工捞回），但这不是用户能自己想到的操作。
- 建议修法：播种前先取**旧传输层**的快照（或在 `configure()` 前 flush + 抓一份本地快照），并把空推守卫改成按「记录总数为 0」判断。

### P1 · 关闭云同步会静默丢掉未推送的改动

`disableDesktopCloud()` 直接把 cache 与 code 清空，800ms 防抖窗口内的改动（或离线期推送失败的改动）就没了，同时 `ops` 切回本地旧快照。建议：关闭前 `await flushNow()`，失败则走 `onFallback` 落到本地。

### P1 · 云端载荷解密失败会被静默覆盖

外层 JSON 合法、`enc` 段损坏时，`parseRev` 不隔离；core 的 409 分支解密抛错 → `serverCache = null` → 跳过合并 → 以本地 cache 重试写入，云端那版**没有 `.corrupt` 备份**。建议：409 且 enc 非空但解密失败时直接抛错停重试。

### P1 · IPC 写同步文件失败被吞，状态永远停在「同步中」

`syncWrite` 失败时主进程返回 `{ok:false}` 而不抛，`nodeWrite` 不查返回值；写后回读 rev 不匹配 → 走 409 重试 5 次 → 返回 `{conflict:true}`（不抛）。而 `flushNow` 只对抛错设 `error` 状态 → 目录不可写 / 磁盘满时 UI 一直显示同步中，实际一条都没上传。建议：查 `syncWrite` 返回值 + `flushNow` 处理 `conflict`。

### P1 · 启动时云端为空留在本地，但 UI 仍显示「已开启」

`applyDesktopCloudFromPersisted()` 已配好 code/transport/watch，`db.ts` 拉快照若为空则 return 保持本地 ops，但 `ENABLED_KEY` 没清 → 界面显示「已开启（待命）」，实际静默不同步（网盘只在线未下载 `.yfe` 时最常见）。建议：空/失败时清标记，或让 UI 以「ops 是不是云」为准。

### P2（可随 P1 一起做）
- `writeLocked` 未覆盖 `relocate / reset / export` 三个入口（锁定期仍能写新位置/导出）。
- 索引与分条的 4 处残留缺口（无章节的项目快照不清理、删卷不清该卷设置、`deleteTableRow` 反向幽灵、`NeovelEditor` 直接 `saveChapter` 未伴 `syncChapterMaster`）。
- 两个同步入口（改数据文件位置 vs 云盘文件同步）没有互斥校验，可以指向同一目录。
