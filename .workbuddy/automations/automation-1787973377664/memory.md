## 经验教训（下次照做）
1. **上百行别肉眼数**：`ssh > 临时jsonl` 后写 node 脚本重建 md，用完 `rm -rf`。
2. **追加模式，不是重建**：第 2 次起脚本必须保留已有「已收录访问」正文再追加新明细（上版脚本 `doc.split('最近巡检：')[0]` 会冲掉历史明细）。抽取旧正文时注意**别把 `<!-- 在此追加新事件 -->` 注释也带进来**，否则重复。
3. **概览表必须全量重算**：独立 IP 按日累加或 `Math.max` 都是错的（跨批次有重叠）。直接拿全量日志重新分组，并用历史行（如 08-29 的 20）自校验。
4. **ts 是 UTC，本地日期分组必须 +8h**。
5. **`bad` 字段是鉴权类故障的判官**（服务端 `providedCodeHash`，失败码短哈希）：`bad=null` ⇒ 请求**根本没带 Authorization**，不是"用户输错码"。本次靠它推翻了"用户反复试错同步码"的假设。排查 authfail 第一件事：看 bad 的分布。
6. **异常先证伪再下结论**（连续两次都应验）：①上版猜"换同步码致老码失效"→ grep systemd 推翻；②本版据"全 POST 无 GET + #007 未修"下结论 → 查清单发现 #007 早已处理、靠 bad 字段才找到真凶。脚本自动生成的推测**必须人工复核**，且要回头更正历史文档里的错误结论。
7. **服务端新增 act 类型时要同步更新映射表**，否则明细里会出现「未知动作」。巡检前可先 `grep -o '"act":"[a-z-]*"' | sort -u` 枚举本期所有 act 值。
8. **`bad` 字段可以反算身份**：`bad` 是失败码 sha256 前 12 位，拿候选码本地算一遍 sha256 就能认出用户到底填了什么。本次由此确认 `bad=22a0db482a8e` ＝ `sha256("YFE-D49E-6MPG")`，即"把入门邀请码当同步码填"。排查带码失败时必做这一步。
9. **要点段是手写的，时间也必须 +8h**：明细走脚本不会错，但「本次巡检要点」里的时分极易直接抄 UTC（本次犯过一次：13:41 应为本地 21:41，已修正）。写完要点回头核一遍时间。
10. **追加时保留旧正文尾部空行**：脚本用 `body.replace(/\s+$/,'\n')` 会把旧正文末尾空行削掉，导致新条目紧贴上一条（本次需手补一行）。日期分隔头判重只看「旧正文最后一个头」，与新增第一条同日则不再插头。
11. 红线：只立案不改码、不封装。
