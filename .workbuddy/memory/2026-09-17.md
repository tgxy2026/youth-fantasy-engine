## 设定优先级 × 保密等级 · 融合方案（2026-09-17 晚，纯方案不开发）

### 长上下文问答（产出 `docs/AI上下文预算策略-为什么不是长上下文.md`）

- 核实数据：模型标称 **262144（256K）**，项目 `numCtx` **32768**，各功能预算 **2000~12000 字符** —— 差 100 倍，老大的疑问合理。答案是三个独立硬约束：
  1. 🔴 **显存（决定性）**：实测本机模型 65 层/4 KV 头/head_dim 256 → 每 token KV cache **260 KB**。32K=**8.7GB**（+模型 23GB≈31.7，几乎塞满 32GB 的 5090）、64K=17.4GB（溢出）、128K=34.9GB、**256K=69.8GB**。→ **单卡物理上限就是 32K 左右**，"标称 256K"是架构容量（要多多卡/大显存）。
  2. **有效上下文 ≠ 标称**：RULER/NIAH-2 实测有效值通常只有标称 **30~65%**；多针检索比单针低 15~40 分。⭐ **ACL 2024 杰出论文 FLenQA**：固定逻辑只加无关填充，**250→3000 token 就让准确率从 0.92 掉到 0.68**（三千，不是三十万）。Chroma 测 18 模型全部随长度退化（纯长度因素占 ~7.9% 底线）。
  3. **延迟与成本**：prefill 随上下文增长（我们实测 27B prefill 一万二千字就被 180s 超时掐死，这正是"必须传 onBodyToken"红线的由来）；云 API 超 200K 后 Anthropic/Google 全部 token 按 2 倍计费（价格悬崖）。
- 结论：**256K 是"架构容量"，不是"可靠推理长度"，更不是单卡跑得动的长度**。我们的 1~2 万是"在预算内做精准选材"，而非能力不足。
- 已给出改进方向（待拍板）：① 低频一次性大任务（拆书/全书审计）加「深度模式」 ② 按 provider 上下文能力自适应预算 ③ 超长任务改"分章批处理+汇总"。
