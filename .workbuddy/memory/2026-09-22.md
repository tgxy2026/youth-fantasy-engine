## 2.4.0 · A2 长篇性能基线（已完成）→ **2.4.0 五项全齐**

- **结论：长篇不卡，瓶颈不在数据量。** 321 章 / 101 万字符下实机：**冷启动到可编辑 1542ms、切章 146ms**、保存 2114ms。
  Node 闸（内存桩口径）所有算法项离阈值 ≥17 倍余量，最重的是**检索建索引 121~150ms**。⇒ **本项无需优化动作，产出就是尺子本身。**
- 设计三决策：① 压测数据**程序化生成**（固定种子 LCG）不落文件（零仓库污染 + 可复现）；② 闸**常驻**全量测试（实测才 1s，放外面没人跑）；
  ③ **两条腿**——Node 闸管算法与数据量、浏览器实机管真实 IO 与 DOM（缺一条"长篇不卡"就只说了一半）。
- 🔴🔴 最大踩坑（方法论）：**第一次的数字可能全是噪音。** 首轮实测「逐条灌 300 章 + 3000 行 **22 分钟没跑完**」，
  差点写成"`importProject` 有严重性能问题"；换轮一测 **0.45ms/条、外推 300 章 0.1 秒**，完全正常。
  元凶＝**Vite dev 首次 `import('/src/lib/db.ts')` 要转译整条依赖图**（G 盘格外慢）。⇒ 涉及"第一次"的数字，先怀疑冷编译/冷连接，**重复测两轮再定性**。
