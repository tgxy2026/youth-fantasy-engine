## 追加：ESLint 11 处 warning 全部清零（依赖数组治理）

老大问「11 处 warning 都是什么内容，能否修复处理」→ 逐条读源码分成三类后全部修掉，

但性质完全不同，不能一把梭（MEMORY 里那条「11 warnings 别盲改」是对的）。

### 三类性质
| 类 | 条数 | 位置 |
|---|---|---|
| 🔴 真漏依赖 | 3 | `SettingSearch` 索引 effect 少 `hiddenTabs`；`TableSheet.filteredRows` 少 `drafts`（**真 bug**）；`TableSheet.tableFields` 读 `tab.columns` 只写 `tab.id` |
| 函数身份（普通函数被当依赖） | 3 | `BackupManager.load`、`TableSheet.validateCodes`、`TableSheet.cellVal` |
| 写法/派生值 | 5 | `CharacterSheet`/`FormSheet` 的 `[tab.id]`→`[tab]`；`HistoryTimeline`/`StoryTimeline` 的 `calValueOf` 内联进 useMemo；`SettingSearch.subOptions` 少 `activeTop` |

### 🔴 修出一个真 bug
`filteredRows` 依赖 `[sortedRows, colFilters, selectColNames]`，却经 `cellVal` 读 **drafts** ——
即「正按某列筛选时编辑该列单元格，命中结果不重算」：把某行改成不再匹配筛选词，**行不会消失**，
要等保存/刷新才对。修法：`cellVal` → `useCallback([drafts])`，再加进 `filteredRows` 依赖。
实机对照有判别力：修后编辑 → 命中行 **1 → 0**；未修版会停在 1。

### 两个"不能直接补依赖"的坑（靠改调用方 / 换依赖形态绕开）
1. 🔴 `SettingSearch` 索引 effect **不能直接依赖 `hiddenTabs`**：Set 每次 memo 重算都新建引用 →
   effect 重跑 → `setDocs` → 再渲染 → 循环。改为派生的**内容字符串**
   `hiddenTabsKey = [...hiddenTabs].sort().join(',')`（按值比较，真变了才重建）+ 一行 disable 注释说明。
2. 🔴 `TableSheet` 聚焦 effect 依赖 `onFocusConsumed`，而 App 传的是**内联箭头** → 补进依赖会让
   effect 每次渲染重跑、2.6 秒的高亮清除定时器被反复重置（**高亮永不消失**）。
   正解不是删依赖，而是**把调用方改成 `useCallback`**（`clearFocusRow`）—— 两处调用一起受益
   （`CharacterSheet` 依赖里本就含它，同病）。

实机一直卡在「闸门① 不出现」，分层诊断后抓到**两个真问题**，都已修 + 已上闸。

### 🔴 bug 1：批量生成走的是非流式 → 必撞 180s 总超时墙
- 机制：非流式请求的**响应头要等整段生成完**才回来，`fetchWithTimeout` 的 180s 定时器
  在响应头到达时才清；流式则首字节即清（`readSSE` 的 `onFirstByte`）。
- 证据：应用内 `ai.chat` 裸调用 3.0s 返回，而 `aiGenerateBible` **>180s 无返回**。
- 修：`aiTasks` 新增 `longStream(onToken?)`，三个大批量生成/校对调用统一传
  `onToken: longStream(opts.onToken)`；`aiWorkflow` 顺带把 onToken 接到进度条
  （「已收到 N 字」），既是实时反馈也是流式开关。
- ⚠️ 与既知红线同源：`runAutoContinue` 必须传 `onBodyToken`。

### 🔴🔴 bug 2：云端 Qwen3 系「思考开着 = 所有 AI 功能静默废掉」
对照实验（硅基流动 `Qwen/Qwen3.5-35B-A3B`，同一 prompt 连跑）：

| | 首字 | 总用时 | content | thinking | JSON |
|---|---|---|---|---|---|
| A1 思考开 | 49.1s | 50.5s | **271 字（截断）** | 12687 字 | ❌ |
| A2 思考开 | 98.1s | **129.6s** | 3021 字 | 13798 字 | ✅ |
| B 思考关 | 0.4s | **35.0s** | 3318 字 | 0 | ✅ |

- 机制：思考**吃光输出预算**（A2 的 `reasoning_tokens` 4321），且思考内容**不进 `delta.content`**
  → 留给 JSON 的额度被挤没，结构必残；更极端一次拿到 0 字。
- 修：`ai.ts` 新增 `HYBRID_THINKING_RE`，`openaiChat` 在「**非本地 + Qwen3 系**」时自动下发
  `enable_thinking:false`；**端点 400 就丢掉该字段重试一次**（不给别的服务商添乱）。
  逃生口：调用方显式 `think:true` 时不下发。本地 Ollama 完全不碰（项目刻意保留思考）。
- 🔴 已在 `ChatOptions.think` 的约定注释里补「**例外三**」——否则后人会按
  「切勿全局关闭」把这条修复纠正掉。

### 其它发现
- **C 的全链路是通的**（直连追踪）：bible 43.2s →20 条 → 闸门① → outline 202s →1卷1章 →
  闸门② → draft（组装上下文 → AI 续写 → 编辑自检 13 条问题 → 改写修正）。
  所以早先「闸门② 不出现」是**我的脚本 300s 超时太短**，不是产品问题。
- ⚠️ **残留风险（未修）**：这两个生成入口没有输出上限，话痨模型会狂产出
  （参数只要 1 章，却吐了 6000+ 字），配合"流式无总超时"就是长时间等待。
  建议后续给 `aiGenerateOutline` 按 `volCount/chCount` 估一个 `max_tokens` 上限。

### 追加修法（同日）：改成「提示词层面的体量预算」
上面那条说"估 max_tokens"，实机跑起来发现问题比预想严重 —— 只要 1 卷 1 章，
模型**连吐 13000+ 字还在继续**，5 分钟等不到闸门②。
但**不能用 `max_tokens` 硬截断**：截断会把 JSON 切残，整批结果报废，比慢更糟。
最终改用提示词纪律（`aiTasks.outlineSys` 新增第 8/9 条 + `outlineCharCap()`）：
- 单字段 ≤ 40 字（events/subplots ≤ 60）、scenes 每条 ≤ 30 字；
- 整份 JSON 目标 = `300 + 卷数×420 + 章数×160` 字；
- **只写给定卷数/章数**，多写的会被丢弃（点明"白耗时间"）。
把"上限"写成"目标"而不是"硬切"，是为了保住 JSON 完整性。

### 经验
- 🔴 **诊断长链路别用 `page.evaluate(整流程)`** —— 它只在结束时返回，中途零可见性；
  要把进度写进 `window.__x` 再由脚本轮询落盘，否则只能靠猜。
- 🔴 **一次测量不足以定论**：bug 2 我第一次只跑了一轮（拿到 0 字），结论差点写成
  「思考完全不可用」；补跑复现轮后才发现真相是「思考=慢且易截断」。**对照实验要重复**。
- 🔴 实机脚本必须用**动态文本**判阶段（「已收到 N 字」「第 N/M 章」）；
  面板里的「设定奠基/分卷大纲」是静态阶段图例，页面一开就有，拿来当进度会永远假匹配。
- ⚠️ dev 环境的 provider 是脚本每次注入的（Playwright 用临时 profile，IndexedDB 不跨次留存）；
  硅基流动密钥从本仓记忆文件读取，**不写进脚本、不提交**。
