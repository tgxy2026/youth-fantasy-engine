## 追加：ESLint 11 处 warning 全部清零（依赖数组治理）

老大问「11 处 warning 都是什么内容，能否修复处理」→ 逐条读源码分成三类后全部修掉，

### 三类性质
| 类 | 条数 | 位置 |
|---|---|---|
| 🔴 真漏依赖 | 3 | `SettingSearch` 索引 effect 少 `hiddenTabs`；`TableSheet.filteredRows` 少 `drafts`（**真 bug**）；`TableSheet.tableFields` 读 `tab.columns` 只写 `tab.id` |

| 写法/派生值 | 5 | `CharacterSheet`/`FormSheet` 的 `[tab.id]`→`[tab]`；`HistoryTimeline`/`StoryTimeline` 的 `calValueOf` 内联进 useMemo；`SettingSearch.subOptions` 少 `activeTop` |

### 🔴 修出一个真 bug
`filteredRows` 依赖 `[sortedRows, colFilters, selectColNames]`，却经 `cellVal` 读 **drafts** ——
即「正按某列筛选时编辑该列单元格，命中结果不重算」：把某行改成不再匹配筛选词，**行不会消失**，
要等保存/刷新才对。修法：`cellVal` → `useCallback([drafts])`，再加进 `filteredRows` 依赖。
实机对照有判别力：修后编辑 → 命中行 **1 → 0**；未修版会停在 1。

### 两个"不能直接补依赖"的坑（靠改调用方 / 换依赖形态绕开）
1. 🔴 `SettingSearch` 索引 effect **不能直接依赖 `hiddenTabs`**：Set 每次 memo 重算都新建引用 →
   effect 重跑 → `setDocs` → 再渲染 → 循环。改为派生的**内容字符串**
   `hiddenTabsKey = [...hiddenTabs].sort().join(',')`（按值比较，真变了才重建）+ 一行 disable 注释说明。
2. 🔴 `TableSheet` 聚焦 effect 依赖 `onFocusConsumed`，而 App 传的是**内联箭头** → 补进依赖会让
   effect 每次渲染重跑、2.6 秒的高亮清除定时器被反复重置（**高亮永不消失**）。
   正解不是删依赖，而是**把调用方改成 `useCallback`**（`clearFocusRow`）—— 两处调用一起受益
   （`CharacterSheet` 依赖里本就含它，同病）。

实机一直卡在「闸门① 不出现」，分层诊断后抓到**两个真问题**，都已修 + 已上闸。

### 🔴 bug 1：批量生成走的是非流式 → 必撞 180s 总超时墙
- 机制：非流式请求的**响应头要等整段生成完**才回来，`fetchWithTimeout` 的 180s 定时器
  在响应头到达时才清；流式则首字节即清（`readSSE` 的 `onFirstByte`）。
- 证据：应用内 `ai.chat` 裸调用 3.0s 返回，而 `aiGenerateBible` **>180s 无返回**。
- 修：`aiTasks` 新增 `longStream(onToken?)`，三个大批量生成/校对调用统一传
  `onToken: longStream(opts.onToken)`；`aiWorkflow` 顺带把 onToken 接到进度条
  （「已收到 N 字」），既是实时反馈也是流式开关。
- ⚠️ 与既知红线同源：`runAutoContinue` 必须传 `onBodyToken`。

### 🔴🔴 bug 2：云端 Qwen3 系「思考开着 = 所有 AI 功能静默废掉」
对照实验（硅基流动 `Qwen/Qwen3.5-35B-A3B`，同一 prompt 连跑）：

| | 首字 | 总用时 | content | thinking | JSON |
|---|---|---|---|---|---|
| A1 思考开 | 49.1s | 50.5s | **271 字（截断）** | 12687 字 | ❌ |
| A2 思考开 | 98.1s | **129.6s** | 3021 字 | 13798 字 | ✅ |
| B 思考关 | 0.4s | **35.0s** | 3318 字 | 0 | ✅ |

- 机制：思考**吃光输出预算**（A2 的 `reasoning_tokens` 4321），且思考内容**不进 `delta.content`**
  → 留给 JSON 的额度被挤没，结构必残；更极端一次拿到 0 字。
- 修：`ai.ts` 新增 `HYBRID_THINKING_RE`，`openaiChat` 在「**非本地 + Qwen3 系**」时自动下发
  `enable_thinking:false`；**端点 400 就丢掉该字段重试一次**（不给别的服务商添乱）。
  逃生口：调用方显式 `think:true` 时不下发。本地 Ollama 完全不碰（项目刻意保留思考）。
- 🔴 已在 `ChatOptions.think` 的约定注释里补「**例外三**」——否则后人会按
  「切勿全局关闭」把这条修复纠正掉。

### 其它发现
- **C 的全链路是通的**（直连追踪）：bible 43.2s →20 条 → 闸门① → outline 202s →1卷1章 →
  闸门② → draft（组装上下文 → AI 续写 → 编辑自检 13 条问题 → 改写修正）。
  所以早先「闸门② 不出现」是**我的脚本 300s 超时太短**，不是产品问题。
- ⚠️ **残留风险（未修）**：这两个生成入口没有输出上限，话痨模型会狂产出
  （参数只要 1 章，却吐了 6000+ 字），配合"流式无总超时"就是长时间等待。
  建议后续给 `aiGenerateOutline` 按 `volCount/chCount` 估一个 `max_tokens` 上限。

### 追加修法（同日）：改成「提示词层面的体量预算」
上面那条说"估 max_tokens"，实机跑起来发现问题比预想严重 —— 只要 1 卷 1 章，
模型**连吐 13000+ 字还在继续**，5 分钟等不到闸门②。
但**不能用 `max_tokens` 硬截断**：截断会把 JSON 切残，整批结果报废，比慢更糟。
最终改用提示词纪律（`aiTasks.outlineSys` 新增第 8/9 条 + `outlineCharCap()`）：
- 单字段 ≤ 40 字（events/subplots ≤ 60）、scenes 每条 ≤ 30 字；
- 整份 JSON 目标 = `300 + 卷数×420 + 章数×160` 字；
- **只写给定卷数/章数**，多写的会被丢弃（点明"白耗时间"）。
把"上限"写成"目标"而不是"硬切"，是为了保住 JSON 完整性。

### 🔴 更正（同日）：上面的「13000+ 字」有我的错，不是模型话痨
深挖后发现真正原因是**我的实机脚本按序号填参数填错了**：
页面上的 number 输入框实际是 `[0]=界面缩放开(无关) [1]=卷数 [2]=连写章数 [3]=每章目标字数`，
而脚本写的是 `nth(1)=连写章数, nth(2)=每章字数` → **把「连写章数」填成了 800**（被钳到 60）。
所以 UI 一直在生成 **60 章**大纲，13000~16000 字完全合理。

- 更正后的证据：直连探针（1 卷 1 章）不论摘要 48 字还是 11952 字、不论流式与否，
  产出都稳定在 **619~684 字 / 7~33 秒**。
- 所以「模型无视数量约束」这个结论**不成立**；提示词体量纪律仍是**有益**的加固
  （字段长度上限确实能压内容），但它不是"修复"。
- 🔴 **教训：按序号定位表单元素极不可靠**（页面上多一个同类输入框就整体错位，且错得很隐蔽
  —— 断言"输入框数量 ≥ 3"照样通过）。一律**按标签/文字定位**，并**断言值真的落进了目标字段**。
- 🔴 另一个教训：我把"参数填错"这个自造变量当成了产品缺陷，还据此写了"残留风险"。
  **下结论前先排除自己的测试脚本**：输出体量异常时，第一件事是核对**实际请求参数**
  （把 `volCount/chCount` 打出来），而不是先改产品代码。

### ✅ 最终验收：端到端 17/17 通过（修好参数定位后，硅基流动 Qwen3-30B-Instruct）
`ui-creative.mjs` 全程真跑（1 卷 1 章 / 每章 800 字）：
```
参数 1/1/800 ✓ → 设定奠基 20 条草稿 → 闸门① 确认
→ 分卷大纲 → 闸门②《风起云州》/「第1章 胎记发烫」→ 确认
→ 连写：AI 续写 → 编辑自检(16 条问题) → 改写修正 → 生成标题并保存 → 抽取并补登设定
→ 完成卡片：设定 20 条 / 大纲 1 卷 1 章（新建 1 卷+1 份分卷大纲+1 份章节细纲）/ **正文 1 章已落库**
→ 无页面级 JS 错误
```
耗时 5m27s（其中审校闭环"16 条问题→改写"占大头，属产品设计内的多轮自检）。

提示词体量纪律**保留**（`outlineSys` 第 8/9 条 + `outlineCharCap` + user 末尾重申）——
它把单字段长度和总量都写清了，是有益加固；但**不是**我以为的那个"修复"。

### C 的 4 个变体实测（同一条缓存基线，60 条，一次跑完可比）
| 变体 | 额外调用 | 复核耗时 | 模型判泛称 | 与登记表冲突 | 兜底后净剔 |
|---|---|---|---|---|---|
| V1 仅名单 | +1 | 12.4s | **59/60** | 31 | 28 |

| V3 三档（确定/疑似） | +1 | 16.5s | 33/60 | 13 | 20 |

🔴 **三个致命问题**：
1. **V1 整体报废**：单给名单不给语境，模型把 59/60 全判泛称（`陈渊`/`青岚宗`/`混沌吞天诀` 一个不留）。
2. **V2 白跑 175 秒**：一条没判。同一模型同一输入，**提示词两句话之差（加一句"别因名字像某类就判泛称"）
   行为从"删 33 条"翻成"删 0 条"** → 不可复现，不能用于破坏性操作。
3. **V3/V4 精度仅约 60%**，误伤落在**核心元素**上：`镇界塔`/`神契`/`叛神`/`七道残简`/`封仙路`。

⚠️ **指标陷阱**：兜底后"保留里判重命中率 51.7%→77.5%"是**循环论证**（兜底把命中项排除在剔除范围外，
分母自然变好），**不能当改善证据**。真实评价只能靠逐条人工判读。

### 🔴 两个改变判断的发现
1. **项目自己的登记表里本来就有泛称**（`演武场`/`杂役院`/`大比`/`残简`/`玄脉`）→
   「泛称＝噪音」这个前提要修正；自动剔除会删掉**作者本来就要登记**的东西。
2. **真噪音是「同物多写法」**：9 簇 / 12 条冗余 / **占 20%**（`胎记`+`左腕胎记`+`暗金胎记`、
   `青玉牌`+`青玉腰牌`、`残简`+`无名残简`+`七道残简`、`混沌吞天诀`+`吞天诀`、
   `[地理]封仙路`+`[术语]封仙路`…）。字符串规则即可归并，**可单测、可复现**。

### 评价口径（以后一律照此）
抽出条数 / 判重命中 / 耗时；且改动需**超过噪声带**才认：条数 **±5%**、命中率 **±2.5pp**、耗时 **±25%**
（三次独立运行：63/60/60 条，54.0%/56.7%/51.7%，389s/496.9s/385.1s）。

### 方法论收获
- **基线缓存**：`bb-c-cache.json` 存下抽取结果后，4 个复核变体共用一条基线 ——
  省掉每个变体重跑 8 分钟抽取，**变体实验才做得起**。以后做"同一输入、多种处理"的对照都应先缓存。
- **要设计能暴露失败的变量**：V1 的"仅名单"就是关键的负面对照，它证明了语境是必需的。

### 🔴 规则被实机数据纠错了两次（都不是想出来的）
1. **前缀位误并**：最初允许「前缀或后缀」→ 实机 6 章跑出 `青岚宗` 被并进 `青岚宗藏经阁`、

## 20:30-21:15 推进 B2：全字段抽取落地（排期最后一项）

### 做了什么
| 改动 | 要点 |
|---|---|
| 提示词全字段化 | 字段键**从 `flow/fieldMap` 的 slots 派生**（`SLOT_HINT` 只管中文措辞）→「schema 改了 prompt 没跟」**结构上不可能** |
| 解析抽成纯函数 | `aiTasks.parseExtractedEntities()`：顶层/`fields` 子对象、英文键/中文列名、relations 两种形态都认；**只认该类型 slots 的键**（给「地点」塞 identity 一律丢） |
| 字段冲突检测 | `draft.mergeExtraField()`：空→写／相同→略／**包含→取长不算矛盾**／否则取长 + **只有硬事实字段才记冲突** |
| 落点优先级 | **slots 先落、desc 让位**（人物 descFields 与 slot identity 都指「身份定位」，identity 更准）；`descKey` 仍指向那一格，界面摘要不空 |
| 抽取改流式 | B2 输出是 B1 数倍 → 非流式必撞 180s 总超时墙；顺带把「已收到 N 字」显示进节点时间线（节流 120 字） |
| 补 `age` slot | 实测发现角色卡有「年龄/性别」列却**没有对应 slot** → 该字段永远抽不到 |
| 耗时估算上调 | `recommend.secPerCall` 云端 8~18s → **25~60**（实测 ≈51s/次）；本地 20~40 → 60~150 |
| 修 importCycles 闸 | **擦除 `import type` 类型边**（`aiTasks ↔ fieldMap` 是假环：fieldMap 只 type 引用）+ 5 条擦除器自检 + 依赖边下限 |

### 与详细设计的偏差（写进文档了）
1. 🔴 **「第二遍」用确定性代码做，不再调模型**：C 实测证明模型复核 JSON 清单精度~60%、提示词微调即翻转，
   而合并是破坏性操作；长书输入规模也炸。代价：跨块**语义同指**（玄真子=国师）识别不了，留作可选模型遍。
2. form 型（worldbase/power/定位）**不做**（需新写入通道 + 末尾汇总）→ 下一批
3. 关系表 kind（relations/faction-rels）**不做** → 下一批

### 实测（示范项目 6 章 / 9 次调用 / 446s）
- **64 条草稿 / 423 字段值 / 平均 6.6 个/条**（人物 8.4）；B1 那时固定 4 格
- 冲突 **13/64（20%）共 14 处**，全落在 类别/实力境界/品级 —— 初版无护栏时 **38%**，且大半是
  「壮实」vs「身板结实」这类互补描述，真矛盾反被埋
- 字段级命中率 **32.5%**（严格包含口径的**下限**）
- 抽样人工核对三类真问题：① 字段错位（`王铁柱.外貌=四仰八叉睡姿，怀中抱馒头` ← 场景当外貌）
  ② 漏字段（年龄/性别，本轮已补 slot）③ `萧景行.首次出场=第1章` 而登记是第3章（**把"提及"当"出场"**）
- 🔎 **标准答案自己有脏数据**：`陈瑶` 已登记「年龄/性别/外貌特征」写着 `20岁/男，身材魁梧、剑眉星目`，
  抽取的「六岁、梳双丫髻」反而更合理 → **对照法要留一分怀疑给"标准答案"**

### 方法论收获（可复用）
- 🔴 **一致性闸用「派生 + 断言」双保险**：能派生的就派生（结构上不可能漂移），不能派生的（中文措辞）就断言。
  补 `age` slot 时忘了加提示，`extractFields` 当场报红 —— 闸按设计工作了。
- 🔴 **做对照实验前先问「这个指标能不能缓存」**：给 B2 脚本加缓存后，改口径重算从 8 分钟变 3 秒。
- 🔴 **探针/对照脚本自己会骗人，且要修的是脚本不是产品**：本轮又踩两个 ——
  ① 抽取结果没缓存 → 改口径必须重跑 8 分钟；
  ② 登记表里同一名字有多条，其中 `relations` 表那条只是「人物A/人物B」的引用、没有字段值，
     按「后写覆盖」处理后把 陈渊/陈瑶/萧景行 的标准答案覆盖成空 → 字段级命中率被严重低估（25.7% → 32.5%）。
