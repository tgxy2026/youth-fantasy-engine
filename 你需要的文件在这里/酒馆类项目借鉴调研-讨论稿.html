酒馆类成熟产品 · 功能借鉴调研（讨论稿）

目的：看看 SillyTavern 这类成熟产品有哪些能提升使用体验的功能，值得我们兼收并蓄。 状态：仅调研与建议，未改动任何项目代码。 讨论定案后再决定做哪些、按什么顺序做。 调研对象：SillyTavern（事实标准，GitHub 34k★）、RisuAI、Agnai、NovelAI、AI Dungeon、Character.AI（2026 新记忆系统），以及中文社区的「状态栏 / MVU 变量框架」生态。

0. 一页看完

三句话结论：

  1. 我们的核心链路不弱于 ST 的默认配置 —— 角色卡四章、按角色的长期记忆、多角色同场、防剧透、与作品设定打通。这几块 ST 要么没有，要么得靠第三方扩展拼出来。
  2. 真正拉开差距的是两类东西：「一场对话进行中的微观操作」（重说 / 编辑 / 隐藏 / 分支 / 检查点）和 「世界设定的按需注入」（World Info / Lorebook）。
  3. 建议先做 A 档 6 项（成本低、感知强），B 档 5 项要先设计，C 档 4 项慎做或换轻量替代。

如果只做三件：A1 消息级操作 → B2 临时导演指令 → A3 分支/检查点。

4. 建议

A 档 —— 建议做（成本低、感知强）

A1 · 消息级操作：重说 / 编辑 / 隐藏 / 删除

  • 解决：3.1。这是全清单里性价比最高的一项。
  • 做法：消息气泡加 hover 工具条。
  • 重说：保存"生成这条时的输入"，丢弃这条 assistant 消息后重放一次（可循环到满意）。
  • 编辑：就地改内容，历史里直接生效（把 AI 输出当草稿，是写作者最顺手的用法）。
  • 隐藏：消息加 hidden: true，组装上下文时跳过、界面仍显示（灰显）。长对话里太好用。
  • 删除：直接从 messages 移除。
  • 数据：TavernMessage 增可选 hidden，向后兼容，旧数据无影响。
  • 成本：小。

A2 · 快捷指令条

  • 解决：3.3 的一半 + 日常效率。
  • 预置按钮：继续 / 换个方向重说 / 补一段环境 / 推进时间 / 收束本场 / Ta 心里在想什么 / 存档。
  • 做法：本质上是一组"预设输入"，点一下即触发一次生成；复用现有提示词层，不动引擎。
  • 成本：小。

A3 · 分支与检查点

  • 解决：3.1 的"想试另一条路"。
  • 剧情推演天生适合：从第 N 轮分叉再演一遍，两个版本都留着。
  • 做法：分支 = 复制会话到新 id 并截断到第 N 条（我们的会话是"整场一个 JSON 记录"，复制很便宜）；检查点 = 记住 messages.length + 记忆水位线，可一键回滚。
  • 成本：中（主要在 UI 与列表命名）。

A4 · 控制面板预设方案

  • 解决：3.8。
  • 命名预设（如「快速脑暴」「精修成稿」），一键切换整套参数 + 协议快照。
  • 成本：小。

A5 · 全局「我」的档案（Persona）

  • 解决：3.5 —— 正好接上一轮那个问题。
  • 全局一条 tavern.persona（名字 / 希望被怎么称呼 / 一句话自我设定 / 可选头像）。本场没有"我演的角色"时，把它作为"用户"注入身份层，AI 就知道在跟谁说话。
  • 与已有的「默认我演的角色」互补：那个是"我演某个角色卡里的人"，这个是"我就是我"。
  • 成本：小。

A6 · 角色健谈度 + 静音 + 点名

  • 解决：3.4。
  • 会话内每个参演角色一个 0–100 的「健谈度」；静音 = 本场在场但不发言；点名 = 已实现的"指定下一位"。
  • 做法：现在完全交给模型自觉。可加一层轻约束（保证每人至少说过一轮 / 被点名者优先）+ 把健谈度写进发言规则。
  • 成本：小-中。

B 档 —— 值得做，要先设计

B1 · 世界书 / Lorebook（最大的能力缺口）

  • 解决：3.2。ST 的"杀手功能"：条目只在关键词出现时才注入，既不占常驻预算，又能让 AI 记得海量细节。
  • 两段走：
  • 第一步（手动条目）：新页签「世界书」，条目 = { 关键词[], 内容, 启用, 优先级, 是否常驻 }；组装时扫最近 N 条消息（扫描深度），命中就把内容插进设定层。
  • 第二步（从现有设定自动生成）：把世界观 / 势力 / 人物 / 法宝 / 伏笔各自生成条目，关键词取"名字 + 别名"，作者可编辑。
  • 可抄 ST 的细节：二级关键词（主命中后再判副条件）、token 预算上限、插入位置（角色卡前 / 后）、常驻条目。
  • 不抄：递归扫描（A 触发 B、B 再触发 C）—— 自激风险高、收益一般。
  • 成本：中偏大；价值：最大。

B2 · 临时导演指令（Author's Note / depth prompt）

  • 解决：3.3 的另一半。
  • 会话级一个"临时指令"框：按深度插入（默认插在最近 4 条之前），可设"只影响接下来 N 轮"。ST 的实测结论是越靠近生成点影响越大 —— 比改全局设置精准得多。
  • 我们的层序里加一层「〖临时导演指令〗」，位置在记忆之后、协议之前（协议必须继续钉末尾）。
  • 成本：小而效果明显。

B3 · 输出后处理规则（正则修正）

  • 解决：3.7。本地小模型偶尔写半角括号、加引号、用 *动作*、写行首「名字：」。
  • 做法：一组可编辑规则（正则 → 替换），生成后自动跑，默认带四条：半角括号转全角、*动作* → （动作）、去掉行首说话人标签、去掉 markdown 标记。命中时留一条可关闭的日志。
  • 成本：小；对本地模型价值高。

B4 · 兼容 ST 角色卡导入（接社区生态）

  • 解决：3.10。ST 的卡是 PNG（tEXt 块 chara / ccv3，base64 JSON）或 JSON（chara_card_v2 / v3）。
  • 解析 PNG 分块是纯前端可做的（读 ArrayBuffer 找 tEXt），不需要新依赖。
  • 字段映射：description + personality → 人物档案；scenario → 世界与开场；first_mes → 开场白；mes_example → 第 4 章；character_book → 将来可进世界书。
  • 好处：直接用 Chub / JanitorAI 那类社区里成千上万的现成卡（拿来参考或自娱都行）。
  • 代价：别人的卡没有我们的"防剧透"语义（他们的 description 常混着作者视角）。建议只导入不改写，导入时给字段映射预览。
  • 成本：中。

B5 · 导出为文档（对话 → 素材）

  • 解决：3.6。现有的"归档"是给模型看的状态摘要；作者真正需要的是整场对话导出成 Markdown / HTML（对白、动作、环境各自样式），直接当"试演片段"存档，改改就能进正文。
  • 做法：复用渲染层的行分类逻辑，导出两份（纯 MD + 带样式 HTML）。
  • 成本：小；价值高（我们用户是写小说的）。

C 档 —— 慎做 / 换轻量替代

C1 · 向量记忆（暂缓）

  • ST 的 Vector Storage / Data Bank 用 embedding 做语义召回（社区还在上面加时间衰减、事件抽取）。
  • 我们是零联网、纯前端取向 —— 要做必须带本地 embedding 模型，成本与不确定性都高。
  • 替代：把"事件"做成结构化条目，用与世界书同一套关键词机制触发。效果接近"检索"，但可控、可读、可手改。
  • 建议：先做事件条目 + 世界书，向量留到确实不够用时再议。

C2 · 状态栏 / 变量面板（收益高、工程量大）

  • 中文社区现在最热：角色卡内嵌 HTML 状态栏，变量（好感度 / 心情 / 物品 / 时间 / 关系阶段）由 AI 输出增量，前端解析并渲染进度条。
  • 我们的接法建议分两步：
  • 第一步只做只读可视化 —— 把六栏记忆里的「关系状态」「关键事实」渲染成面板（含关系温度、时间线），不动数据模型。
  • 第二步再考虑"变量 + AI 输出增量"。
  • 成本：中偏大（变量 schema + 解析 + 渲染）。

C3 · 立绘 / 表情 / 背景图

  • 我们已有看板娘 PNG 的先例。做法：角色卡加可选立绘，命中情绪词则切图；没有图就不显示，做成纯可选。
  • 成本：中（要美术资源）。

C4 · TTS 朗读

  • 建议不做：用户是"读文本改文本"的写作者，朗读价值低，还要多一套依赖。

5. 明确不学的

不学理由
脚本引擎 / 宏系统（STscript、RisuScript）对作者是噪音；我们要的是"少参数、好默认值"
多后端 / API 管理大面板已收敛到控制面板选模型
翻译、图像生成、网络搜索扩展与"写小说"这一目标无关

需要服务端的记忆 / RAG 托管与零联网取向冲突
内容分级开关不做

6. 我们比 ST 强的地方（别改坏）

  1. 记忆是结构化的：六栏 + 水位线 + 按角色分别整理 + 作者可在角色卡里手改。ST 的 Summarize 扩展只是把一段摘要塞进上下文。
  2. 剧情推演这一整套：叙事锚点 + 我演/AI 演 + 防剧透 + 推演报告 —— ST 没有对应物。
  3. 与作品打通：设定、人物、章节、伏笔都在同一个库里，AI 拿得到"作者侧的真相"；ST 是纯聊天，没有"作品"这个概念。
  4. 中文网文向的篇幅纪律：协议规定一轮 60–160 字、最多两句对白、结尾留钩子。ST 默认没有这种约束，容易一次写一大段。

7. 请老大定夺

  1. 世界书做不做？ 若做，先做"手动条目"，还是直接从现有设定自动生成条目？
  2. 「重说」要不要一次生成多个候选？多候选更省事，但按候选数烧额度。
  3. 分支 / 检查点要不要？ 它会让会话数据从"一条线"变成"一棵树"，列表与命名要重新设计。
  4. 要不要兼容 ST 角色卡导入？ 生态红利很大，代价是长期维护别人的格式。
  5. 状态栏 / 变量面板：先做只读可视化，还是先放着？
